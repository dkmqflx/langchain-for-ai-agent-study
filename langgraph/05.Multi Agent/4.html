5-5. Multi Agent — 감독관이 지휘하거나, 서로에게 넘기거나

실습 노트북: 4.ipynb · # Multi-Agent (Supervisor) / # Multi-Agent (Handoff) 절  ·  대상 범위: with_structured_output() 라우팅 · Command(goto=) · ToolRuntime · ToolNode · tools_condition  ·  난이도: 🟡 중급

드디어 마지막 장, 진짜 멀티 에이전트입니다. 5-1의 interrupt(), 5-3의 Command(goto=), 5-4의 Subgraph — 지금까지 만든 부품을 전부 조립해서 에이전트 여럿이 업무를 나눠 하는 조직을 두 가지 형태로 만듭니다. 하나는 감독관이 지시하는 Supervisor(중앙 집중형), 다른 하나는 동료끼리 서로 넘기는 Handoff(네트워크형)입니다. 새 문법은 거의 없습니다 — 배운 문법을 어떤 조직도로 배치하느냐가 이 장의 전부입니다.

이 장에서 배우는 것

멀티 에이전트 조직도 두 가지를 직접 구현합니다. 가르는 기준은 하나 — "다음에 누가 일할지"를 누가 정하느냐입니다.

  1. Supervisor(중앙 집중형) — 감독관 LLM이 with_structured_output()으로 다음 작업자를 고르고, Command(goto=)로 보냅니다. 작업자는 일을 마치면 반드시 감독관에게 복귀 보고합니다.
  2. Handoff(네트워크형) — 감독관이 없습니다. 동등한 에이전트들이 "연결 버튼(툴)"을 눌러 서로에게 직접 일을 넘깁니다. 버튼이 눌리면 ToolNode가 Command(goto=)로 담당 노드에 점프시킵니다.

선행 지식: 5-3의 Command(goto=) · with_structured_output(), 5-4의 서브그래프, 3-4의 Orchestrator-Worker 패턴, 4-3의 툴 기반(Tool-based) 접근. 전부 그대로 다시 씁니다.

1. Supervisor란 — 감독관 하나, 작업자 여럿

구조는 단순합니다. 유저 요청이 들어오면 메인 에이전트가 하위 에이전트에게 업무를 토스하고, 하위 작업자가 일을 끝내면 다시 메인 에이전트에게 보고합니다. 3-4에서 배운 Orchestrator-Worker와 같은 그림인데, 결정적 차이가 하나 있습니다 — 그때의 워커는 단일 노드였지만, 지금의 워커는 각각이 하나의 에이전트 그래프가 될 수 있습니다. 5-4에서 만든 "그래프를 노드로 접어 넣는" 벽돌이 여기서 쓰입니다.

🔍 비유 — 잡지 편집장

편집장은 기사를 직접 쓰지 않습니다. "이 주제는 김 기자가 취재해 와" → (취재 보고를 읽고) → "이제 박 작가가 원고 써" → (원고를 읽고) → "됐다, 마감!" — 매 단계마다 지금까지의 결과물을 읽고 다음 담당자를 정하는 것이 편집장의 일이죠.

Supervisor 노드가 정확히 이 편집장입니다. 그리고 편집장의 판단 능력은 구조화된 답변을 하는 LLM이 맡습니다.

호출 결정권이 개발자에서 LLM에게 넘어간다

5-4의 서브그래프에서는 브릿지 노드에 도달하면 무조건 자식 그래프가 invoke()되도록 개발자가 흐름을 하드코딩해 뒀습니다. "음식이 완료되면 반드시 배달 업체를 부른다" — 플로우가 고정이었죠.

Supervisor는 그 호출 결정권을 언어 모델에게 줍니다. 요청이 들어오면 감독관 노드 안의 LLM이 "지금은 조사가 필요하니 researcher에게", "조사가 끝났으니 writer에게", "다 끝났으니 FINISH"를 스스로 판단하고, 그 판단대로 Command(goto=)가 해당 노드(사실은 에이전트 그래프)로 점프시킵니다. 판단이 제멋대로 튀지 않도록 답의 형태는 with_structured_output()으로 고정합니다 — 5-3에서 의도를 confirm/change/cancel 셋 중 하나로 못박았던 것과 같은 수법입니다.

2. Supervisor 구현 — 만들 것: 블로그 작성 팀

"AI 최신 트렌드에 대해 블로그 글 써줘"라는 요청을 처리하는 3인 팀을 만듭니다.

supervisor ★

관리자. 대화 내용을 읽고 다음 작업자(researcher / writer / FINISH)를 결정해 Command(goto=)로 보냅니다. 실체는 구조화된 답변을 하는 LLM입니다.

researcher

검색 담당. 주제에 대한 조사 보고서를 작성하고 supervisor에게 복귀 보고합니다.

writer

집필 담당. researcher의 조사 결과를 바탕으로 블로그 글을 쓰고 supervisor에게 복귀 보고합니다.

이번 실습에서 두 작업자는 LLM 한 번 호출로 끝나는 단일 노드로 만듭니다. 하지만 자리 자체는 그래프가 들어갈 수 있는 자리입니다 — writer를 "초안 작성 → 첨삭 → 최종본"으로 도는 서브그래프로 바꿔 끼워도 나머지 코드는 그대로입니다. 공식 문서(Multi-agent)도 같은 구조를 소개하니 함께 열어 두고 보세요.

STEP 1. Model & State 정의

from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")
from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class TeamState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

State는 messages 필드 하나뿐입니다. 이 대화 기록 한 권을 팀 전체가 돌려 씁니다 — researcher의 조사 결과도, writer의 원고도 전부 여기에 쌓이고, supervisor는 매번 이 기록을 처음부터 읽고 다음 담당자를 정합니다.

STEP 2. 감독관의 결정 목록 — RouteResponse ★

from typing import Literal
from pydantic import BaseModel, Field

# 감독관이 내릴 수 있는 결정 목록
class RouteResponse(BaseModel):
    next_step: Literal["researcher", "writer", "FINISH"] = Field(
        description="다음 작업을 수행할 팀원을 선택하거나, 모든 작업이 완료되었으면 FINISH를 선택"
    )
    reason: str = Field(description="선택한 이유")
supervisor_agent = model.with_structured_output(RouteResponse)

supervisor_agent.invoke(...)의 결과는 문장이 아니라 필드 두 개짜리 객체입니다. next_step에는 반드시 셋 중 하나가 담기고, reason에는 그 선택의 근거가 담깁니다. reason은 라우팅에 쓰이진 않지만 감독관이 왜 그렇게 판단했는지 로그로 확인할 수 있어 디버깅에 아주 유용합니다.

⚠️ Literal의 문자열 = 나중에 노드를 등록할 이름

"researcher"와 "writer"는 STEP 5에서 add_node("researcher", ...)로 등록할 노드 이름과 글자가 정확히 같아야 합니다. LLM이 고른 이 문자열이 그대로 Command(goto=문자열)에 들어가기 때문입니다. 한 글자라도 다르면 존재하지 않는 노드로 점프하다 에러가 납니다. FINISH만은 노드 이름이 아니라 "끝내라"는 신호로, 코드에서 END로 바꿔 처리합니다.

STEP 3. supervisor 노드 — 판단하고, 보낸다

from langchain.messages import SystemMessage
from langgraph.types import Command
from langgraph.graph import StateGraph, START, END

def supervisor_node(state: TeamState):
    print("\n👔 [Supervisor] 다음 작업자 결정 중...")

    # 1. 현재까지의 대화 내용을 보고 판단
    system_prompt = """
    당신은 블로그 작성 팀의 관리자입니다.
    1. 사용자 요청이 들어오면 'researcher'에게 조사를 시키세요.
    2. 조사 결과가 나오면 'writer'에게 글 작성을 시키세요.
    3. 글 작성이 완료되면 'FINISH'를 선언하세요.
    """

    # 2. LLM에게 판단 요청 (앞서 정의한 RouteResponse 구조로 정확히 반환됩니다)
    messages = [SystemMessage(content=system_prompt)] + state["messages"]
    decision = supervisor_agent.invoke(messages)

    print(f"👉 [지시] {decision.next_step} (이유: {decision.reason})")

    # 3. 판단 결과에 따라 Command(goto=...)를 이용해 다음 노드로 직행(라우팅)시킵니다.
    if decision.next_step == "FINISH":
        return Command(goto=END)
    else:
        return Command(goto=decision.next_step)

마지막 네 줄이 이 노드의 전부입니다. next_step이 FINISH면 END로 끝내고, 아니면 decision.next_step에 담긴 문자열 그대로 점프시킵니다 — 값이 "researcher"면 researcher 노드로, "writer"면 writer 노드로. 어디로 갈지가 코드에 고정돼 있지 않고 실행할 때마다 LLM의 판단으로 정해지는, 아주 다이나믹한 라우팅입니다.

⚠️ 노트북(4.ipynb)의 이 셀에는 같은 코드가 두 번 적혀 있습니다

실습 노트북의 supervisor_node에는 messages = ...와 decision = supervisor_agent.invoke(messages)가 실수로 두 번 반복돼 있습니다 (강의 중 복사-붙여넣기 흔적). 동작은 같지만 매번 LLM을 한 번씩 더 호출해 비용이 두 배가 되니, 위 코드처럼 한 번만 남기면 됩니다.

STEP 4. 작업자 노드 2개 — 일하고, 복귀 보고한다

① researcher_node — 검색 담당

from langchain.messages import AIMessage

# [팀원 1] 검색 담당 (Researcher)
def researcher_node(state: TeamState):
    print("\n🔎 [Researcher] LLM이 자료를 조사/생성 중입니다...")

    # 시스템 프롬프트 부여
    system_msg = SystemMessage(content="""
    당신은 IT 트렌드 전문 리서처입니다.
    사용자의 요청 주제에 대해 핵심 트렌드, 기술 용어, 통계 등을 포함하여
    전문적인 조사 보고서를 3줄 요약 형태로 작성하세요.
    """)

    # 이전 대화 내용 + 내 역할(System)을 합쳐서 LLM에게 전달
    # state["messages"] 안에 사용자의 요청이 들어있음
    messages = [system_msg] + state["messages"]

    # LLM 실행
    response = model.invoke(messages)

    # 결과 반환 (name을 지정해야 감독관이 누가 말했는지 앎)
    return Command(
        update={"messages": [AIMessage(content=response.content, name="Researcher")]},
        goto="supervisor"
    )

② writer_node — 집필 담당

# [팀원 2] 집필 담당 (Writer)
def writer_node(state: TeamState):
    print("\n✍️ [Writer] LLM이 블로그 포스팅을 작성 중입니다...")

    system_msg = SystemMessage(content="""
    당신은 테크 블로그 전문 작가입니다.
    위의 대화 내역에 있는 'Researcher'의 조사 결과를 바탕으로
    매력적인 블로그 포스팅(제목+본문)을 작성하세요.
    이모지를 적절히 사용하여 가독성을 높이세요.
    """)

    # 공유된 대화 기록(Researcher의 결과 포함)을 다 같이 넘겨줌
    messages = [system_msg] + state["messages"]

    response = model.invoke(messages)

    return Command(
        update={"messages": [AIMessage(content=response.content, name="Writer")]},
        goto="supervisor"
    )

마지막 return에 이 조직도의 규칙이 다 들어 있습니다. ① 결과물을 update로 공용 대화 기록에 남기고, ② goto="supervisor"로 반드시 감독관에게 복귀합니다. 이 goto를 빼먹으면 작업자에서 그래프가 그냥 끝나 버립니다 — 나가는 엣지를 하나도 안 그렸으니까요.

name 속성 — 이 글을 누가 썼는지 적어 두기

supervisor는 매번 messages 리스트 전체를 읽고 다음 차례를 정합니다. 이때 name이 없으면 내용만 보고 "이게 조사 결과인지 원고인지"를 추측해야 하지만, name="Researcher" / name="Writer"가 붙어 있으면 "조사는 끝났고 원고는 아직이구나"를 훨씬 정확하게 인지할 수 있습니다. 필수는 아니지만, 멀티 에이전트에서는 붙이는 쪽이 확실히 유리합니다.

🔍 비유 — 회의록의 발언자 이름

이름 없는 회의록은 "…라고 했다. …라는 의견이 나왔다"의 연속이라, 다음 안건을 누구에게 맡길지 정하려면 문맥을 한참 더듬어야 합니다. 발언자 이름이 붙은 회의록은 한눈에 업무 진행 상황이 보이죠. name은 대화 기록에 발언자 이름을 붙이는 일입니다.

STEP 5. 그래프 조립 — 엣지는 딱 하나

workflow = StateGraph(TeamState)

workflow.add_node("supervisor", supervisor_node)
workflow.add_node("researcher", researcher_node)
workflow.add_node("writer", writer_node)

workflow.add_edge(START, "supervisor")
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()
app = workflow.compile(checkpointer=checkpointer)
app
▶ 출력 — app
__start__ → supervisor → __end__
(researcher, writer는 연결선 없이 떠 있음)

정적 엣지는 START → supervisor 하나뿐입니다. 그래서 그래프 그림에는 researcher와 writer가 연결선 없이 둥둥 떠 있는 것처럼 보입니다. 화면에는 보이지 않지만 supervisor는 필요에 따라 Command(goto=)로 researcher·writer·END 어디로든 순간이동시킬 수 있고, 작업자들도 goto로 supervisor에 복귀합니다 — 동적 라우팅은 그림에 그려지지 않는다는 것, 5-3에서 본 그대로입니다.

3. 실행 — 감독관의 지시 로그 읽기

from langchain.messages import HumanMessage

config = {"configurable": {"thread_id": "team-blog-1"}}

app.invoke(
    {"messages": [HumanMessage(content="AI 최신 트렌드에 대해 블로그 글 써줘")]},
    config=config
)

👉 [지시] researcher (이유: 블로그 글 작성을 위해 최신 AI 트렌드에 대한 신뢰 가능한 자료를 수집하고 방향성(...)을 정리하기 위함.)

🔎 [Researcher] LLM이 자료를 조사/생성 중입니다...

👔 [Supervisor] 다음 작업자 결정 중...
👉 [지시] writer (이유: 조사 결과를 바탕으로 블로그 글 작성을 시작합니다. ...)

✍️ [Writer] LLM이 블로그 포스팅을 작성 중입니다...

👔 [Supervisor] 다음 작업자 결정 중...
👉 [지시] FINISH (이유: 작업 완료: Writer가 AI 최신 트렌드에 관한 블로그 글 작성을 마쳤습니다. ...)

로그가 조직도 그대로 읽힙니다 — supervisor → researcher → supervisor → writer → supervisor → FINISH. 매번 supervisor가 먼저 찍히는 건 작업자가 일을 마칠 때마다 감독관에게 복귀 보고하기 때문이고, 👉 [지시] 줄의 이유(reason)도 전부 LLM이 직접 작성한 것입니다.

researcher가 두 번 불린 게 보이시나요?

시스템 프롬프트에는 "조사 한 번 → 글 한 번"이라고 썼지만, 이번 실행에서 감독관은 조사가 더 필요하다고 판단해 researcher를 연달아 두 번 불렀습니다. Supervisor 구조의 순서는 코드에 고정된 것이 아니라 매번 LLM이 새로 판단한다는 증거입니다 — 유연함이자, 프롬프트를 명확하게 써야 하는 이유이기도 합니다.

⚠️ Pydantic serializer warning이 떠도 놀라지 마세요

실행 중 PydanticSerializationUnexpectedValue ... 경고가 여러 줄 출력될 수 있습니다. 구조화된 답변 객체를 직렬화하는 과정에서 나오는 경고일 뿐 동작에는 문제가 없으니 무시해도 됩니다.

3노드 등록

라우팅 코드는 한 줄도 안 고칩니다. Command(goto=decision.next_step)이 이미 "LLM이 고른 문자열로 점프"이기 때문에, 선택지가 늘면 감독관이 알아서 새 팀원을 부릅니다. 이게 Supervisor 구조의 확장성입니다.

4. Handoff란 — 감독관 없이, 서로에게 넘긴다

마지막으로 배울 조직도는 네트워크형(Handoff형)입니다. 분산형 구조, 매시(Mesh) 구조라고도 부릅니다. 고객센터에 전화를 걸면 리셉션이 먼저 받고, 담당 부서로 연결해 주고, 그 부서가 "이건 우리도 아니네요" 하면 또 다른 부서로 연결하는 — 수평적인 부서들이 협업으로 고객 하나를 응대하는 구조입니다. 참고로 Handoff라는 용어 자체는 OpenAI가 먼저 제안했습니다 (OpenAI 공식 문서 · LangChain 공식 문서).

receptionist

안내 데스크(시작점). 인사하고, 기술 문제면 기술팀으로 / 환불 문제면 환불팀으로 넘기고, 잡담은 직접 답변합니다.

tech_support

기술 지원팀. 직접 해결하거나, 환불 얘기가 나오면 billing으로 / 다 끝나면 reception으로 넘깁니다.

billing

환불팀. 환불을 처리하거나, 기술 질문이면 tech_support로 / 다 끝나면 reception으로 넘깁니다.

tools ★

연결 교환대(ToolNode). 누가 "연결" 버튼을 누르면 Command(goto=)로 해당 노드에 점프시킵니다.

작동 방식 — 반드시 Tool-based로 구현한다

핵심은 노드끼리 직접 엣지로 잇는 게 아니라, 툴을 통해 넘긴다는 점입니다. 4-3 Store에서 장기 메모리를 다룰 때를 떠올려 보세요 — "이건 기억해 둬야겠다"고 LLM이 추론하면 저장 툴을 호출했고, 실제 저장 로직은 툴 쪽에서 처리했습니다. Handoff도 똑같습니다. 리셉션의 LLM이 "이건 기술팀 일이다"라고 추론하면 바인딩된 transfer_to_tech_support 버튼을 누르고, 그 버튼이 모여 있는 ToolNode가 Command(goto=)로 기술팀 노드에 점프시킵니다.

메시지 4종 세트 미리 보기

순서메시지내용
1HumanMessage"제 컴퓨터 화면이 안 나와요. 고장난 것 같아요."
2AIMessagecontent는 빈칸, tool_calls=transfer_to_tech_support — 리셉션이 직접 답하지 않고 버튼을 누름
3ToolMessage"기술 지원팀으로 성공적으로 연결되었습니다." — 고정 문구. 이 순간 Command(goto=)로 점프
4AIMessage"해결 방법은 …" — tech_support 노드의 LLM이 작성한 실제 답변

5. Handoff 구현 — STEP 1. 이동 버튼(툴) 3개 ★

from langchain.tools import tool
from langgraph.types import Command
from langchain.messages import ToolMessage
from langchain.tools import ToolRuntime

@tool
def transfer_to_tech_support(runtime: ToolRuntime):
    """기술적인 문제(컴퓨터, 코드, 에러 등)를 해결해야 할 때 이 도구를 사용하여 기술팀으로 연결하세요."""

    # runtime.tool_call_id로 현재 도구 호출 ID에 안전하게 접근
    tool_id = runtime.tool_call_id
    print(f"   [System] 기술 지원팀으로 이동합니다... (Tool Call ID: {tool_id})")

    # Command를 반환하여 상태를 업데이트하고 tech_support 노드로 점프(Hand-off)
    return Command(
        update={
            "messages": [
                ToolMessage(
                    content="기술 지원팀으로 성공적으로 연결되었습니다.",
                    tool_call_id=tool_id # runtime에서 꺼낸 ID 매핑
                )
            ]
        },
        goto="tech_support"
    )

이 툴은 실제 업무를 처리하지 않습니다. 하는 일은 딱 두 가지 — ① "연결했습니다"라는 고정 문구의 ToolMessage를 기록에 남기고, ② goto="tech_support"로 점프시키는 것. 실제 응대는 도착한 노드의 LLM이 합니다. 그리고 goto의 "tech_support"는 STEP 5에서 노드를 등록할 때 붙일 이름과 정확히 같아야 합니다.

ToolRuntime — tool_call_id를 직접 파낼 필요가 없다

ToolMessage에는 tool_call_id가 필수입니다. 예전에 도쿄·서울 날씨를 동시에 물었을 때를 기억하세요 — 툴이 여러 개 동시에 호출될 수 있어서, 어느 요청에 대한 응답인지 ID로 짝을 맞춰야 충돌이 나지 않았습니다. 원래라면 AIMessage의 tool_calls 안에서 id를 직접 꺼내 와야 하지만, 매개변수로 runtime: ToolRuntime을 선언하면 LangChain이 현재 호출의 tool_call_id를 알아서 담아 넣어 줍니다 (ToolRuntime 레퍼런스). 코드가 그만큼 깔끔해집니다.

나머지 버튼 두 개 — 로직은 복사, goto와 문구만 교체

@tool
def transfer_to_billing(runtime: ToolRuntime):
    """환불, 결제, 금액 관련 문제를 해결해야 할 때 이 도구를 사용하여 환불팀으로 연결하세요."""
    tool_id = runtime.tool_call_id

    return Command(
        update={
            "messages": [
                ToolMessage(
                    content="환불/결제팀으로 성공적으로 연결되었습니다.",
                    tool_call_id=tool_id
                )
            ]
        },
        goto="billing"
    )
@tool
def transfer_to_reception(runtime: ToolRuntime):
    """일반적인 문의거나, 인사가 끝났으면 안내 데스크로 다시 연결하세요."""
    tool_id = runtime.tool_call_id

    return Command(
        update={
            "messages": [
                ToolMessage(
                    content="안내 데스크로 복귀했습니다.",
                    tool_call_id=tool_id
                )
            ]
        },
        goto="receptionist"
    )
🔍 비유 — 상담원 책상 위의 "돌려주기" 버튼 3개

콜센터 상담원 책상에는 [기술팀 연결] [환불팀 연결] [안내 데스크 연결] 버튼이 있습니다. 버튼 자체는 문제를 해결하지 않죠 — 누르면 "연결해 드리겠습니다" 안내 멘트(ToolMessage)가 나가고 전화가 넘어갈 뿐(goto)입니다. 문제 해결은 전화를 받은 그 팀이 합니다. docstring은 버튼에 붙은 라벨입니다 — LLM은 이 라벨을 읽고 어떤 버튼을 누를지 정합니다.

STEP 2. State 정의

from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

STEP 3. 상담원 노드 3개 — 각자 자기 버튼만 들고 있다

① receptionist_node — 안내 데스크 (시작점)

# [상담원 1] 안내 데스크 (시작점)
def receptionist_node(state: AgentState):
    print("\n💁 [Reception] 안녕하세요.")

    system_prompt = """
    당신은 고객센터의 친절한 안내 데스크입니다.
    1. 고객의 말을 듣고 인사하세요.
    2. '기술 문제'라면 tech_support 도구를 쓰세요.
    3. '돈/환불 문제'라면 billing 도구를 쓰세요.
    4. 그 외 잡담은 직접 답변하세요.
    """

    # 안내 데스크는 기술팀과 환불팀으로 보낼 수 있음
    tools = [transfer_to_tech_support, transfer_to_billing]
    model_with_tools = model.bind_tools(tools)

    messages = [SystemMessage(content=system_prompt)] + state["messages"]
    response = model_with_tools.invoke(messages)

    return {"messages": [response]}

Supervisor의 작업자와 달리 goto가 없습니다. 대신 bind_tools로 버튼 두 개를 쥐여 줬으니, LLM의 추론에 따라 직접 답변(content 채움)하거나, 버튼을 누르거나(tool_calls 채움) 둘 중 하나의 AIMessage가 반환됩니다. 어디로 갈지는 다음 단계의 조건부 엣지가 처리합니다.

② tech_node — 기술 지원팀

# [상담원 2] 기술 지원팀
def tech_node(state: AgentState):
    print("\n🛠️ [Tech Support] 기술적인 문제를 해결해드립니다.")

    system_prompt = """
    당신은 베테랑 기술 지원 엔지니어입니다.
    컴퓨터 고장, 파이썬 코드 에러 등을 해결해줍니다.
    만약 고객이 '환불'을 요구하면 즉시 billing 도구를 써서 넘기세요.

    messages = [SystemMessage(content=system_prompt)] + state["messages"]
    response = model_with_tools.invoke(messages)

STEP 4. ToolNode — 버튼들이 모이는 교환대

from langgraph.prebuilt import ToolNode

# 도구를 실행할 노드 (ToolNode)
# 에이전트가 도구를 호출하면 -> Tool Node로 가서 -> 함수 실행 -> Command 반환 -> 다른 노드로 점프
all_tools = [transfer_to_tech_support, transfer_to_billing, transfer_to_reception]
tool_node = ToolNode(all_tools)

마지막 조각입니다. 상담원 노드 3개 말고 버튼(툴) 3개가 모여 있는 노드가 하나 더 필요했죠 — 에이전트가 툴콜을 하면 여기로 와서 해당 툴 함수가 실행되고, 그 함수가 반환한 Command(goto=)가 실제 점프를 일으킵니다. tool_node를 출력해 보면 세 툴의 name·description·args_schema가 등록된 StructuredTool 목록이 자동으로 만들어져 있는 걸 확인할 수 있습니다.

STEP 5. 그래프 조립 — tools_condition으로 조건부 엣지 ★★

workflow = StateGraph(AgentState)

workflow.add_node("receptionist", receptionist_node)
workflow.add_node("tech_support", tech_node)
workflow.add_node("billing", billing_node)
workflow.add_node("tools", tool_node)

# 시작은 안내 데스크
workflow.add_edge(START, "receptionist")
from langgraph.prebuilt import tools_condition

# 조건부 엣지 연결 (도구 호출 여부에 따라 tools 또는 END로 분기)
workflow.add_conditional_edges("receptionist", tools_condition, ["tools", END])
workflow.add_conditional_edges("tech_support", tools_condition, ["tools", END])
workflow.add_conditional_edges("billing", tools_condition, ["tools", END])

각 상담원 노드가 끝났을 때 갈 곳은 둘 중 하나입니다 — 버튼을 눌렀으면(tool_calls 있음) tools 노드로, 답변을 다 했으면 END로. 이 분기 함수는 직접 짤 필요가 없습니다. 랭그래프 prebuilt의 tools_condition이 정확히 이 판별을 해 주니, 세 노드에 그대로 등록만 하면 됩니다. 

from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()
app = workflow.compile(checkpointer=checkpointer)
app

* tools 노드에서 각 상담원으로 가는 Command(goto=) 점프는 그림에 나타나지 않음
⚠️ 그림이 설계도와 달라 보이는 게 정상입니다

우리가 설계한 건 상담원들이 서로 얽힌 매시(Mesh)인데, 출력된 그림은 각 노드가 tools/END에만 연결된 밋밋한 모양입니다. 툴 안의 Command(goto=) 점프는 정적 엣지가 아니라서 그림에 그려지지 않기 때문입니다. 실제 실행 흐름은 곧 로그로 확인합니다.

7. 두 조직도 비교 — 언제 뭘 쓰나

Supervisor (중앙 집중형)Handoff (네트워크형)
다음 담당자를 정하는 주체 감독관 노드 하나가 전담 현재 담당자 각자가 결정
결정의 도구 with_structured_output() — 결정 목록(Literal)에서 선택 bind_tools() — 이동 버튼(툴) 중 하나를 툴콜
점프 방식 감독관이 직접 Command(goto=) 툴 함수가 Command(goto=) — ToolNode가 브릿지
작업 후 행선지 항상 supervisor로 복귀 보고 다른 팀으로 또 넘기거나, 끝나면 바로 END
엣지 구성 START → supervisor 단 하나 START → receptionist + 노드마다 tools_condition 조건부 엣지
통제력 높음 모든 흐름이 감독관을 거침 — 추적·개입이 쉬움 낮음 흐름이 분산 — 대신 감독관 병목이 없음
이럴 때 쓴다 정해진 산출물을 향해 단계를 밟는 작업. 조사→집필→검수 같은 파이프라인 어디로 튈지 모르는 대화형 응대. 고객센터처럼 담당이 수시로 바뀌는 상황
🔍 고르는 기준 한 줄

"업무 흐름을 한 명이 다 지켜봐야 하는가?"

그렇다면 Supervisor — 편집장이 모든 원고의 진행을 챙기는 편집국처럼.
아니라면 Handoff — 각 부서가 알아서 연결해 주는 고객센터처럼.

자주 걸리는 함정 8가지

  1. Literal / goto의 문자열 = add_node 등록 이름 — Supervisor의 RouteResponse 값도, Handoff 툴의 goto 값도 노드를 등록한 이름과 글자가 정확히 같아야 합니다. 여기가 이 장 오류의 1순위입니다.
  2. FINISH는 노드가 아니다 — 결정 목록에 있는 신호일 뿐이며, 코드에서 if decision.next_step == "FINISH": return Command(goto=END)로 END로 번역해 줘야 합니다.
  3. ⚠️ 작업자의 goto="supervisor"를 빼먹지 말 것 — Supervisor 구조의 작업자는 나가는 엣지가 없으므로, 복귀 goto가 없으면 작업자에서 그래프가 그냥 끝납니다.
  4. 메시지에 name을 붙여라 — 없어도 돌아가지만, 감독관이 누가 어디까지 했는지를 content 추측만으로 판단하게 됩니다. 멀티 에이전트에서는 사실상 필수 습관입니다.
  5. Supervisor의 순서는 고정이 아니다 — 매번 LLM이 새로 판단하므로 같은 작업자가 연속으로 불리거나 예상 밖 순서가 나올 수 있습니다. 시스템 메시지를 명확하게 쓰고, 필요하면 최대 반복 횟수 같은 안전장치를 고민하세요.
  6. Handoff 툴에서 ToolMessage + tool_call_id는 필수 — 툴콜에 대한 응답 짝이 맞지 않으면 에러가 납니다. runtime: ToolRuntime으로 받아 runtime.tool_call_id를 쓰면 직접 파낼 필요가 없습니다.
  7. ⚠️ 상담원 노드마다 tools_condition 조건부 엣지를 등록할 것 — 빼먹은 노드는 툴콜을 해도 tools 노드로 가지 못하고 그 자리에서 끝나 버립니다. 또한 bind_tools에는 그 노드가 실제로 보낼 수 있는 버튼만 담으세요 (reception은 tech+billing, tech는 billing+reception…).
  8. 그래프 그림을 믿지 마라 — Command(goto=)에 의한 동적 점프는 그림에 그려지지 않습니다. Supervisor에선 작업자들이 떠 있는 것처럼, Handoff에선 매시가 아닌 것처럼 보이는 게 정상이며, 실제 흐름은 실행 로그로 확인해야 합니다.

① Supervisor — 블로그 작성 팀

from langchain.chat_models import init_chat_model
from langchain.messages import AnyMessage, HumanMessage, SystemMessage, AIMessage
from typing_extensions import TypedDict, Annotated
from typing import Literal
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.types import Command
from langgraph.checkpoint.memory import InMemorySaver

model = init_chat_model("gpt-5-nano")

# ── State (팀 공용 대화 기록) ─────────────────────────────
class TeamState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

# ── 감독관의 결정 목록 ────────────────────────────────────
class RouteResponse(BaseModel):
    next_step: Literal["researcher", "writer", "FINISH"] = Field(
        description="다음 작업을 수행할 팀원을 선택하거나, 모든 작업이 완료되었으면 FINISH를 선택"
    )
    reason: str = Field(description="선택한 이유")

supervisor_agent = model.with_structured_output(RouteResponse)

# ── 감독관 노드 ───────────────────────────────────────────
def supervisor_node(state: TeamState):
    print("\n👔 [Supervisor] 다음 작업자 결정 중...")

    system_prompt = """
    당신은 블로그 작성 팀의 관리자입니다.
    1. 사용자 요청이 들어오면 'researcher'에게 조사를 시키세요.
    2. 조사 결과가 나오면 'writer'에게 글 작성을 시키세요.
    3. 글 작성이 완료되면 'FINISH'를 선언하세요.
    """

    messages = [SystemMessage(content=system_prompt)] + state["messages"]
    decision = supervisor_agent.invoke(messages)

    print(f"👉 [지시] {decision.next_step} (이유: {decision.reason})")

    if decision.next_step == "FINISH":
        return Command(goto=END)
    else:
        return Command(goto=decision.next_step)

# ── 작업자 노드 2개 ───────────────────────────────────────
def researcher_node(state: TeamState):
    print("\n🔎 [Researcher] LLM이 자료를 조사/생성 중입니다...")
    system_msg = SystemMessage(content="""
    당신은 IT 트렌드 전문 리서처입니다.
    사용자의 요청 주제에 대해 핵심 트렌드, 기술 용어, 통계 등을 포함하여
    전문적인 조사 보고서를 3줄 요약 형태로 작성하세요.
    """)
    response = model.invoke([system_msg] + state["messages"])
    return Command(
        update={"messages": [AIMessage(content=response.content, name="Researcher")]},
        goto="supervisor"
    )

def writer_node(state: TeamState):
    print("\n✍️ [Writer] LLM이 블로그 포스팅을 작성 중입니다...")
    system_msg = SystemMessage(content="""
    당신은 테크 블로그 전문 작가입니다.
    위의 대화 내역에 있는 'Researcher'의 조사 결과를 바탕으로
    매력적인 블로그 포스팅(제목+본문)을 작성하세요.
    이모지를 적절히 사용하여 가독성을 높이세요.
    """)
    response = model.invoke([system_msg] + state["messages"])
    return Command(
        update={"messages": [AIMessage(content=response.content, name="Writer")]},
        goto="supervisor"
    )

# ── 그래프 조립 ───────────────────────────────────────────
workflow = StateGraph(TeamState)
workflow.add_node("supervisor", supervisor_node)
workflow.add_node("researcher", researcher_node)
workflow.add_node("writer", writer_node)
workflow.add_edge(START, "supervisor")     # 정적 엣지는 이것 하나

checkpointer = InMemorySaver()
app = workflow.compile(checkpointer=checkpointer)

# ── 실행 ──────────────────────────────────────────────────
config = {"configurable": {"thread_id": "team-blog-1"}}
app.invoke(
    {"messages": [HumanMessage(content="AI 최신 트렌드에 대해 블로그 글 써줘")]},
    config=config
)

② Handoff — 고객센터 3개 팀

from langchain.chat_models import init_chat_model
from langchain.messages import AnyMessage, HumanMessage, SystemMessage, ToolMessage
from langchain.tools import tool, ToolRuntime
from typing_extensions import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.types import Command
from langgraph.prebuilt import ToolNode, tools_condition
from langgraph.checkpoint.memory import InMemorySaver

model = init_chat_model("gpt-5-nano")

# ── 이동 버튼(툴) 3개 ─────────────────────────────────────
@tool
def transfer_to_tech_support(runtime: ToolRuntime):
    """기술적인 문제(컴퓨터, 코드, 에러 등)를 해결해야 할 때 이 도구를 사용하여 기술팀으로 연결하세요."""
    tool_id = runtime.tool_call_id
    print(f"   [System] 기술 지원팀으로 이동합니다... (Tool Call ID: {tool_id})")
    return Command(
        update={"messages": [ToolMessage(content="기술 지원팀으로 성공적으로 연결되었습니다.",
                                         tool_call_id=tool_id)]},
        goto="tech_support"
    )

@tool
def transfer_to_billing(runtime: ToolRuntime):
    """환불, 결제, 금액 관련 문제를 해결해야 할 때 이 도구를 사용하여 환불팀으로 연결하세요."""
    tool_id = runtime.tool_call_id
    return Command(
        update={"messages": [ToolMessage(content="환불/결제팀으로 성공적으로 연결되었습니다.",
                                         tool_call_id=tool_id)]},
        goto="billing"
    )

@tool
def transfer_to_reception(runtime: ToolRuntime):
    """일반적인 문의거나, 인사가 끝났으면 안내 데스크로 다시 연결하세요."""
    tool_id = runtime.tool_call_id
    return Command(
        update={"messages": [ToolMessage(content="안내 데스크로 복귀했습니다.",
                                         tool_call_id=tool_id)]},
        goto="receptionist"
    )

# ── State ─────────────────────────────────────────────────
class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

# ── 상담원 노드 3개 ───────────────────────────────────────
def receptionist_node(state: AgentState):
    print("\n💁 [Reception] 안녕하세요.")
    system_prompt = """
    당신은 고객센터의 친절한 안내 데스크입니다.
    1. 고객의 말을 듣고 인사하세요.
    2. '기술 문제'라면 tech_support 도구를 쓰세요.
    3. '돈/환불 문제'라면 billing 도구를 쓰세요.
    4. 그 외 잡담은 직접 답변하세요.
    """
    tools = [transfer_to_tech_support, transfer_to_billing]
    model_with_tools = model.bind_tools(tools)
    response = model_with_tools.invoke([SystemMessage(content=system_prompt)] + state["messages"])
    return {"messages": [response]}

def tech_node(state: AgentState):
    print("\n🛠️ [Tech Support] 기술적인 문제를 해결해드립니다.")
    system_prompt = """
    당신은 베테랑 기술 지원 엔지니어입니다.
    컴퓨터 고장, 파이썬 코드 에러 등을 해결해줍니다.
    만약 고객이 '환불'을 요구하면 즉시 billing 도구를 써서 넘기세요.
    해결이 끝나면 reception으로 넘기세요.
    """
    tools = [transfer_to_billing, transfer_to_reception]
    model_with_tools = model.bind_tools(tools)
    response = model_with_tools.invoke([SystemMessage(content=system_prompt)] + state["messages"])
    return {"messages": [response]}

def billing_node(state: AgentState):
    print("\n💰 [Billing] 결제 및 환불 담당입니다.")
    system_prompt = """
    당신은 환불 담당자입니다.
    고객의 환불 요청을 처리해줍니다.
    기술적인 질문을 하면 tech_support로 넘기세요.
    해결이 끝나면 reception으로 넘기세요.
    """
    tools = [transfer_to_tech_support, transfer_to_reception]
    model_with_tools = model.bind_tools(tools)
    response = model_with_tools.invoke([SystemMessage(content=system_prompt)] + state["messages"])
    return {"messages": [response]}

# ── 그래프 조립 ───────────────────────────────────────────
workflow = StateGraph(AgentState)
workflow.add_node("receptionist", receptionist_node)
workflow.add_node("tech_support", tech_node)
workflow.add_node("billing", billing_node)

all_tools = [transfer_to_tech_support, transfer_to_billing, transfer_to_reception]
workflow.add_node("tools", ToolNode(all_tools))

workflow.add_edge(START, "receptionist")
workflow.add_conditional_edges("receptionist", tools_condition, ["tools", END])
workflow.add_conditional_edges("tech_support", tools_condition, ["tools", END])
workflow.add_conditional_edges("billing", tools_condition, ["tools", END])

checkpointer = InMemorySaver()
app = workflow.compile(checkpointer=checkpointer)

# ── 실행 ──────────────────────────────────────────────────
config = {"configurable": {"thread_id": "handoff-demo-1"}}
app.invoke({"messages": [HumanMessage(content="제 컴퓨터 화면이 안 나와요. 고장난 것 같아요.")]},
           config=config)
app.invoke({"messages": [HumanMessage(content="아직 안 되는데, 그냥 환불하고 싶어요.")]},
           config=config)

📚 한 장 정리

Multi Agent — 딱 이것만 기억하면 됩니다
질문답

Handoff가 뭔가동등한 에이전트끼리 서로 넘기는 네트워크형(Mesh). 감독관 없음

tool_call_idruntime: ToolRuntime으로 받아 runtime.tool_call_id — 직접 파낼 필요 없음
엣지 구성Supervisor: START→supervisor 하나 · Handoff: 노드마다 tools_condition으로 ["tools", END]
  • Supervisor는 "서브그래프 호출 결정권의 이관"이다 — 5-4에서 개발자가 하드코딩했던 자식 그래프 호출을, 구조화된 답변을 하는 LLM이 대신 결정합니다. 선택지를 늘리고 시스템 메시지만 고치면 팀원이 얼마든지 늘어나는 확장 구조입니다.
  • Handoff는 "버튼과 교환대"다 — 각 에이전트는 자기가 넘길 수 있는 곳의 버튼만 들고, 버튼이 눌리면 ToolNode가 점프시킵니다. 실제 응대는 언제나 도착한 노드의 LLM이 하고, 툴은 고정 문구의 ToolMessage만 남깁니다.
  • 두 구조 모두 새 문법이 아니라 배치의 문제다 — goto, 구조화된 답변, 툴 바인딩, 서브그래프… 전부 이미 배운 부품이고, 조직도를 어떻게 그리느냐만 달랐습니다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

편집국과 고객센터를 나란히 떠올리세요. 편집국(Supervisor)에서는 모든 원고가 편집장의 책상을 거칩니다 — 누가 다음 일을 할지는 편집장이 정합니다. 고객센터(Handoff)에는 편집장이 없습니다 — 상담원 각자가 "제 담당이 아니네요" 하며 책상 위 연결 버튼을 누릅니다. 결정권이 가운데 모여 있느냐, 각자에게 흩어져 있느냐 — 멀티 에이전트 조직도는 결국 이 한 가지 질문입니다.
