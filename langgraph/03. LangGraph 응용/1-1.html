3-1. 기초 아키텍처 패턴 — Prompt Chaining · Parallelization

실습 노트북: 1.ipynb  ·  대상 범위: 1-1 Prompt Chaining ~ 1-2 Parallelization  ·  난이도: 🟢 입문~초급

2강까지 우리는 State · Node · Edge · 조건부 엣지라는 네 개의 부품을 손에 익혔습니다. 3강은 새 부품을 배우는 시간이 아닙니다. 이미 가진 그 부품을 "어떻게 배치하느냐"만 바꿔서 전혀 다른 모양의 그래프를 만드는 시간입니다. 이번 문서에서는 그중 가장 기본이 되는 두 가지 — 노드를 일렬로 줄 세우는 Prompt Chaining과, 노드를 부챗살처럼 펼치는 Parallelization을 다룹니다.

이 장에서 배우는 것

문법은 add_node와 add_edge 두 개가 전부입니다. 새로 배우는 문법이 사실상 없습니다. 대신 배우는 건 "이 업무에는 어떤 모양이 어울리는가"라는 감각입니다. 같은 add_edge를 어떻게 긋느냐에 따라 그래프는 일자 체인도 되고 부챗살도 됩니다.

2강이 이 강의에서 가장 빡센 구간이었다면, 3강은 그 부품을 갖고 노는 시간입니다. 훨씬 수월합니다.

왜 "그래프 모양"을 따로 배우는가 — 사라진 LangChain의 체인

2강에서 만든 그래프를 떠올려 보면 모양이 거의 하나였습니다. START에서 출발해 한 방향으로 흐르다가, 갈림길에서 한 번 갈라지고, END로 끝난다. 그런데 노드와 엣지는 그것보다 훨씬 자유롭게 이을 수 있습니다.

이 이야기가 특히 반가울 분들이 있습니다. 2025년 10월 이전, 즉 LangChain 버전 0 시절에 개발해 본 분들입니다. 그때 LangChain은 이름 그대로 "체인(Chain)"을 얼기설기 엮는 라이브러리였습니다. 입력이 하나 들어오면 체인들이 연쇄 반응(chain reaction)을 일으키며 차례로 일을 하고, 마지막에 최종 결과가 툭 튀어나오는 방식이었죠.

그런데 버전 1로 올라가면서 LangChain은 에이전트에 집중했습니다. 가드레일, 미들웨어 같은 기능이 전면에 나오는 대신 기존의 체인 문법은 많이 정리되었습니다. 실제로 지난 강의 댓글에도 "그 문법이 없어져서 아쉽다"는 반응이 있었고요.

💡 좋은 소식 — 없어진 게 아니라 옮겨졌습니다

오늘 배우는 노드 + 엣지 조합이 바로 그 체인의 자리를 대신합니다. 버전 0에서 체인을 엮어 연쇄 반응을 일으키던 것과 완전히 똑같은 구조를 add_edge 몇 줄로 다시 만들 수 있습니다. 오히려 중간 상태가 State에 남고, 그래프가 그림으로 보이고, 조건부 분기까지 붙일 수 있다는 점에서 더 나아졌습니다.

아키텍처 패턴 지도 — 다섯 가지 모양

LangChain 공식 문서(Workflows & Agents)는 실무에서 반복적으로 등장하는 그래프 모양을 다섯 가지 패턴으로 정리해 두었습니다. 먼저 전체 지형도를 보고 시작하죠.

패턴한 줄 요약모양다루는 곳
Prompt Chaining한 번에 다 하지 말고 단계별로일자 (직렬)이 문서
Parallelization독립적인 일을 동시에 시키고 취합부챗살 → 깔때기이 문서
Routing상황을 보고 갈 길을 고른다갈림길다음 문서 (2강에서 맛봄)
Orchestrator-Worker지휘자가 일을 쪼개 나눠주고 종합동적 부챗살3강 2장
Evaluator-Optimizer평가자가 퇴짜를 놓으면 다시루프3강 2장
🔍 비유 — 회사의 업무 배치

다섯 패턴은 결국 "일을 사람들에게 어떻게 배치할 것인가"의 다섯 가지 방식입니다.

  • Chaining = 컨베이어 벨트 — 앞사람이 끝내야 뒷사람이 시작
  • Parallelization = 팀 회의 — 셋이 각자 조사하고 한자리에 모여 합침
  • Routing = 안내데스크 — "그건 3층으로 가세요"
  • Orchestrator-Worker = 팀장 — 일을 몇 개로 쪼갤지 그때그때 정함
  • Evaluator-Optimizer = 상사의 컨펌 — 반려되면 다시 씀

1-1. Prompt Chaining — 한 명에게 다 시키지 말고, 줄을 세운다

Chaining은 말 그대로 여러 개의 노드를 체인처럼 얼기설기 연결하는 것입니다. 핵심 문장은 딱 하나입니다.

한 번에 일을 다 시키지 않고, 단계별로(Step-by-Step) 시킨다.

예를 들어 고객 이메일에 답장하는 에이전트를 만든다면 — ①이메일을 읽고 → ②관련 문서를 검색하고 → ③답변 초안을 만들고 → ④검수하고 → ⑤최종 출력. 각 단계를 노드 하나씩 맡기고, 그 노드들을 엣지로 이어 연쇄 반응을 일으키는 것이 Chaining입니다.

언제 쓰는가 — 세 가지 신호

신호무슨 뜻인가예시
① 입출력 토큰 제한 업무가 너무 복잡해서 한 노드에 다 넣으면 입력이 감당이 안 될 때 200페이지 보고서를 통째로 넣는 대신, 장별 요약 → 요약본 종합
② 작업 성격이 명확히 다를 때 각 단계가 서로 다른 종류의 일일 때 사용자 의도 파악 → RAG 검색 → 답변 생성 (셋은 완전히 다른 일)
③ 검증/개선이 필요할 때 결과물이 단계를 거치며 좋아져야 할 때 문서 초안 작성 → 검토 → 수정

Before / After — 왜 쪼개면 좋아지는가

이제 실제로 만들어 볼 농담 생성기로 이 차이를 확인해 봅시다. 만약 노드 하나로 끝내려 한다면 프롬프트는 이렇게 생겼을 겁니다.

❌ Before — 한 노드에 전부 몰아넣기
"○○을 주제로 아재 개그를 만들고, 개선한 뒤, 이모지를 많이 넣어 글 작성해 줘"

한 문장 안에 지시가 세 개 들어 있습니다. 이러면 언어 모델의 주의(attention)가 분산됩니다. 개그를 만드는 데 집중하다가 개선을 대충 하거나, 이모지만 잔뜩 붙이고 정작 농담은 밋밋해지거나 하는 식이죠.

✅ After — 노드 세 개로 쪼개기
① "먼저 ○○을 주제로 아재 개그 만들어"      → generate_joke  노드
② "작성한 글을 개선해"                        → improve       노드
③ "개선한 글에 이모지를 넣어줘"                → polish        노드
🔍 비유 — 심부름 세 개를 한 번에 시키기

후배에게 "은행 가서 입금하고, 오는 길에 우체국 들러서 등기 부치고, 편의점에서 커피 세 개 사와"라고 한 번에 말하면 꼭 하나는 빠뜨립니다. 사람이 멍청해서가 아니라, 지시가 길수록 각 항목에 배분되는 주의가 옅어지기 때문입니다.

대신 은행 갔다 오게 하고 → 돌아오면 우체국 시키고 → 그다음 편의점을 시키면 하나도 안 빠집니다. Chaining이 정확히 이겁니다. 모델이 한 번에 한 가지 일만 신경 쓰게 만드는 구조죠.

기획 3단계 — 2강에서 배운 순서 그대로

2강에서 코드보다 기획이 먼저라고 배웠습니다. 순서도 그대로입니다. 요구사항 → 그래프 → State.

1요구사항

농담 생성기를 만든다. 기능 하나 = 노드 하나

2그래프 구성

스텝바이스텝이니 Chaining으로 일렬 연결

3State 설계

단계별 결과물을 어떤 칸에 담아 넘길지

기획 1 · 요구사항 → 노드 세 개

단계하는 일노드 이름
1단계주제를 받아 농담 초안 작성generate_joke
2단계초안을 보고 더 웃기게 개선critique_and_improve
3단계이모지를 붙여 최종 포장polish_joke

기획 2 · 그래프 구성

셋은 반드시 이 순서대로여야 합니다. 개선할 초안이 없으면 2단계가 할 일이 없고, 개선안이 없으면 3단계가 꾸밀 대상이 없으니까요. 그래서 일자 체인입니다. 조건부 엣지는 필요 없습니다 — 갈림길이 없으니까요.

기획 3 · State 설계 — 칸을 몇 개로 할 것인가

2강의 원칙을 다시 꺼냅니다. "다음 노드 혹은 다다음 노드가 읽어야 하는 값이라면 State에 담는다." 이 기준으로 보면 필요한 칸이 자연스럽게 나옵니다.

필드누가 쓰나누가 읽나
topic사용자 (invoke 입력)generate_joke
draft_jokegenerate_jokecritique_and_improve
improved_jokecritique_and_improvepolish_joke
final_jokepolish_joke사용자 (최종 반환)
🔍 비유 — 원고 교정지

출판사에서 원고를 고칠 때 원본 위에 덮어쓰지 않습니다. 초고 · 1교 · 2교 · 최종교를 따로 보관하죠. 나중에 "어느 단계에서 이상해졌지?"를 되짚어야 하니까요.

draft_joke · improved_joke · final_joke가 정확히 초고 · 1교 · 최종교입니다. 실행 후 result를 출력해 보면 세 버전이 전부 남아 있어서 각 노드가 실제로 뭘 했는지 눈으로 확인할 수 있습니다.

STEP 1. Model 정의

기획이 끝났으니 이제 코딩입니다. 코딩 순서는 2강과 동일하게 ①모델 → ②State → ③Node → ④그래프 → ⑤실행입니다.

📥 코드
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano", temperature=1.0)

init_chat_model은 모델 이름만 바꾸면 제공사가 바뀌는 범용 초기화 함수입니다. 여기서는 OpenAI의 gpt-5-nano를 썼지만, Gemini를 쓰신다면 모델 이름만 갈아끼우면 됩니다. (노트북에는 OpenAI와 Google 패키지가 둘 다 설치되도록 준비되어 있습니다.)

temperature=1.0 — 왜 굳이 올렸을까

temperature는 "얼마나 의외의 단어를 고를 것인가"를 조절하는 손잡이입니다. 0에 가까울수록 가장 확률 높은 단어만 고르고(= 무난하고 반복적), 1에 가까울수록 덜 뻔한 단어도 후보에 넣습니다(= 창의적이지만 산만할 수 있음).

🔍 비유 — 주사위의 크기

temperature=0은 주사위를 아예 안 던지는 것입니다. 늘 1등 후보만 뽑죠. 그래서 같은 질문에 늘 비슷한 답이 나옵니다. 요약·분류·추출처럼 정답이 정해진 일에 적합합니다.

temperature=1.0은 주사위를 크게 던지는 것입니다. 2등, 3등 후보도 뽑힐 수 있죠. 농담처럼 뻔하면 재미없는 일에 씁니다. 이번 실습에서 1.0을 준 이유가 이겁니다.

STEP 2. State 정의

기획 3단계에서 확정한 네 칸을 그대로 옮깁니다. 기획을 해뒀으니 이 단계는 10초입니다.

📥 코드
from typing import TypedDict

class JokeState(TypedDict):
    topic: str          # 초기 주제
    draft_joke: str     # 1단계: 초안
    improved_joke: str  # 2단계: 수정안
    final_joke: str     # 3단계: 최종 결과
💡 리듀서가 하나도 없습니다

2강 실전 2에서는 messages: Annotated[list, add_messages]처럼 리듀서를 붙였습니다. "덮어쓰지 말고 이어 붙여라"는 규칙이었죠.

이번엔 전부 평범한 str입니다. 그리고 그게 맞습니다 — 각 칸은 한 노드가 딱 한 번만 채우고 끝이니까요. 누적할 일이 없습니다. "여러 번 쌓여야 하는 값에만 리듀서를 붙인다"는 원칙을 기억하세요. (이 원칙은 잠시 뒤 병렬 처리에서 다시 중요해집니다.)

STEP 3. Node 정의 — 세 명의 작업자

노드의 계약은 2강과 똑같습니다. ①state를 인자로 받고, ②State 양식에 맞는 딕셔너리를 반환한다. 세 노드 모두 이 계약을 그대로 따릅니다.

① generate_joke — 초안 작성

📥 코드
# [Step 1] 초안 생성 노드
def generate_joke(state: JokeState):
    topic = state["topic"]
    print(f"\n--- [1단계] '{topic}' 주제로 농담 초안 생성 중 ---")

    msg = model.invoke(f"'{topic}'에 대한 짧고 재미있는 농담을 하나 만들어줘. 다른 말은 하지 말고 농담 하나만 해")
    return {"draft_joke": msg.content}

한 줄씩 뜯어봅시다.

topic = state["topic"] — 공책에서 꺼내 읽기

사용자가 invoke({"topic": "고양이"})로 넣은 값이 여기로 들어옵니다. 노드는 절대 함수 인자로 값을 직접 주고받지 않습니다. 오직 State를 통해서만 소통하죠.

msg.content — 봉투가 아니라 편지만 꺼낸다

model.invoke()는 문자열이 아니라 AIMessage 객체를 돌려줍니다. 그 안에는 토큰 사용량, 모델 이름 같은 메타데이터도 함께 들어 있죠. 우리가 필요한 건 본문뿐이므로 .content로 꺼냅니다.

return {"draft_joke": ...} — 자기가 채운 칸만 반환

네 칸짜리 State인데 딕셔너리에는 키가 하나뿐입니다. 이게 정상입니다. LangGraph는 반환된 키만 골라서 State에 병합합니다. 나머지 topic·improved_joke·final_joke는 건드리지 않고 그대로 둡니다.

프롬프트의 "다른 말은 하지 말고 농담 하나만 해" — 사소해 보이지만 중요합니다

이 문장이 없으면 모델은 "네! 재미있는 농담 하나 준비했습니다 😊" 같은 군더더기를 붙입니다. 그런데 이 반환값은 다음 노드의 입력 원문으로 그대로 쓰입니다. 2단계에서 원문: 네! 재미있는 농담 하나 준비했습니다...가 들어가면 개선 품질이 떨어지죠.

💡 Chaining의 숨은 규칙 — 노드의 출력은 사람이 아니라 "다음 노드"가 읽는다

중간 노드의 출력은 사용자에게 보여줄 글이 아니라 부품입니다. 그래서 인사말·설명·"원하시면 더 만들어 드릴게요" 같은 건 전부 노이즈입니다. 중간 노드일수록 프롬프트에 "다른 말 하지 말고"를 붙이는 습관을 들이세요.

② critique_and_improve — 개선

📥 코드
# [Step 2] 윤색/수정 노드
def critique_and_improve(state: JokeState):
    original_joke = state["draft_joke"]
    print(f"\n--- [2단계] 더 웃기게 수정 중 (아재개그 스타일) ---")

    prompt = f"""
    다음 농담을 보고, 더 썰렁하고 재미있는 '아재개그' 스타일로 개선해줘. 다른 말은 하지 말고 하나만 답변해.
    원문: {original_joke}
    """
    msg = model.invoke(prompt)
    return {"improved_joke": msg.content}
⚠️ 여기가 Chaining의 심장입니다

만약 이 노드가 state["draft_joke"]가 아니라 state["topic"]을 읽었다면? 그래프 그림은 똑같이 일자로 보이지만, 실제로는 1단계 결과를 완전히 무시하고 처음부터 다시 만드는 셈이 됩니다. 이건 체인이 아니라 그냥 세 번 따로 물어본 것이죠.

"체인이냐 아니냐"는 엣지가 아니라 노드 안의 state[...] 한 줄이 결정합니다.

③ polish_joke — 최종 포장

📥 코드
# [Step 3] 최종 포장 노드
def polish_joke(state: JokeState):
    improved_joke = state["improved_joke"]
    print(f"\n--- [3단계] 이모지 추가 및 마무리 ---")

    prompt = f"""
    다음 농담에 적절한 이모지를 듬뿍 넣어서 SNS에 올리기 좋게 꾸며줘.
    농담: {improved_joke}
    """
    msg = model.invoke(prompt)
    return {"final_joke": msg.content}
🔍 비유 — 릴레이 경주의 배턴

세 노드는 서로 말을 걸지 않습니다. 1번 주자가 배턴을 바닥(State)에 놓고 사라지면, 2번 주자가 바닥에서 주워 달립니다.

배턴을 어느 칸에 놓았느냐(return의 키)와 어느 칸에서 줍느냐(state[...])가 어긋나면 경주는 그 자리에서 멈춥니다. Chaining에서 가장 흔한 버그가 정확히 이겁니다 — 키 이름 오타.

STEP 4. 그래프 생성 — 엣지 네 줄이 전부

📥 코드
from langgraph.graph import StateGraph, START, END

# 그래프 객체 생성
app = StateGraph(JokeState)

# 노드 등록
app.add_node('generate_joke', generate_joke)
app.add_node('critique_and_improve', critique_and_improve)
app.add_node('polish_joke', polish_joke)

# 엣지 연결: 일직선으로 연결 (Linear Chain)
# START -> 1단계 -> 2단계 -> 3단계 -> END
app.add_edge(START, 'generate_joke')
app.add_edge('generate_joke', 'critique_and_improve')
app.add_edge('critique_and_improve', 'polish_joke')
app.add_edge('polish_joke', END)

# 컴파일
chain = app.compile()

add_node(이름, 함수)의 첫 번째 인자는 이름표, 두 번째 인자는 실제 함수입니다. 여기서는 이름표와 함수 이름을 똑같이 맞췄습니다. 굳이 다르게 지을 이유가 없고, 맞춰두면 add_edge를 쓸 때 헷갈릴 일이 없습니다.

💡 조건부 엣지가 하나도 없다는 점을 눈여겨보세요

2강에서는 add_conditional_edges와 라우팅 함수를 만드느라 고생했죠. Chaining에는 갈림길이 없으므로 그게 통째로 필요 없습니다. add_edge(A, B)는 "A가 끝나면 무조건 B로 간다"는 뜻입니다. 무조건 = 실선, 조건부 = 점선이라고 기억하세요.

⚠️ 변수 이름에 속지 마세요 — app은 아직 "설계도"입니다

이 코드에서 app = StateGraph(...)은 아직 실행할 수 없는 빌더(설계도)이고, chain = app.compile()이 실제로 돌릴 수 있는 완제품입니다.

헷갈리기 쉬운 이유가 있습니다 — 뒤에 나올 병렬 처리 실습에서는 이름이 정반대거든요. 거기서는 workflow = StateGraph(...)가 설계도, app = workflow.compile()이 완제품입니다. 변수 이름은 아무래도 상관없고, .compile()을 거쳤는지가 유일한 기준입니다.

컴파일한 결과를 그냥 출력하면(주피터/코랩 기준) 그래프 그림이 나옵니다. 기획서와 모양이 같은지 눈으로 확인하고 넘어가는 습관을 들이세요.

📥 코드
chain
📤 출력
__start__ → generate_joke → critique_and_improve → polish_joke → __end__
(위아래로 곧게 떨어지는 일자 그래프)

STEP 5. 실행

실행할 때 넣는 딕셔너리는 State 양식을 따라야 합니다. 첫 노드가 state["topic"]을 읽으므로, topic 칸이 채워진 채로 들어와야 하죠.

📥 코드

로그가 1 → 2 → 3 순서대로, 한 번에 하나씩 찍히는 게 보입니다. 전체 실행에는 1분 남짓 걸립니다. LLM 호출 세 번이 순서대로 기다렸다 돌기 때문이죠. (이 "기다림"이 바로 다음에 배울 병렬 처리가 해결하려는 문제입니다.)

⚠️ 솔직히 말하면 — 결과물 품질은 기대하지 마세요

강사님도 그대로 말씀하십니다. GPT든 Gemini든 유머에는 유독 약합니다. "재밌게 해줘"라고 하면 어색한 결과를 내놓는 걸 이미 겪어보셨을 겁니다. 2차 수정본도 사실 한 문장 덧붙인 수준이고, 최종본은 시키지도 않은 "버전 A/B/C"를 만들어냈죠.

하지만 이 실습의 목표는 농담의 품질이 아니라 배선(wiring)입니다. "앞 노드의 결과가 진짜로 다음 노드에 흘러 들어갔는가" — result에 세 버전이 다 남아 있는 게 그 증거입니다.

🟡 관찰 포인트 마지막 출력의 "다음처럼 …올리면 SNS에 어울려요:"와 "원하시면 …변형해 드릴게요"가 바로 앞에서 말한 군더더기입니다. polish_joke 프롬프트에는 "다른 말은 하지 말고"가 빠져 있죠. 한 줄 차이가 결과에 그대로 드러납니다.

1-2. Parallelization — 줄 세우지 말고, 펼쳐서 동시에

Chaining이 "한 명씩 차례로"였다면, Parallelization은 "여러 명이 한꺼번에"입니다. 입력이 들어오면 노드 하나가 아니라 세 개, 다섯 개, 백 개가 동시에 출발하고, 그 결과를 취합 노드 하나가 모아서 최종 결과를 만듭니다.

두 가지 목적 — 속도, 그리고 정확도

목적 A · 속도 — 기다리는 시간을 없앤다

LLM 호출은 대부분의 시간이 "기다림"입니다. 세 개를 순서대로 호출하면 20초 + 20초 + 20초 = 60초지만, 동시에 던지면 가장 느린 하나만큼(약 20초)이면 끝납니다.

강사님의 예시가 직관적입니다 — "오늘 나온 뉴스 100개를 요약해 줘". 하나씩 요약하면 하세월이지만, 노드 100개를 한 방에 돌리면 한 개 요약하는 시간이면 끝납니다.

목적 B · 정확도 — 여러 관점으로 보게 한다

의외로 이쪽이 실무에서 더 자주 쓰입니다. 두 가지 방식이 있습니다.

방식어떻게 하나예시
다수결 투표 같은 질문을 여러 노드에 동시에 던지고 표를 센다 "A 기업에 투자할까?" → 노드 3개에 찬반 요청 → 찬성 2 : 반대 1 → 찬성으로 결정
관점 다각화
(페르소나)		 노드마다 다른 역할을 주고 각자의 시각으로 분석 "A 프로젝트를 진행할까?" → 노무사 / 변호사 / 회계사 관점으로 각각 분석 후 종합
🔍 비유 — 전문가 자문 회의

중요한 의사결정을 할 때 한 사람에게 "종합적으로 판단해 주세요"라고 하지 않습니다. 노무사, 변호사, 회계사를 따로 불러 각자의 관점에서 의견을 받고, 그걸 모아서 결정하죠.

왜 따로 부를까요? 같이 앉히면 서로 눈치를 보기 때문입니다. LLM도 똑같습니다 — 한 프롬프트에 세 관점을 다 넣으면 서로 섞여서 뭉개진 답이 나옵니다. 노드를 분리해야 관점도 분리됩니다.

전제조건 — 세 노드가 서로 독립이어야 한다

병렬 처리에는 반드시 지켜야 할 조건이 하나 있습니다. 동시에 도는 노드들끼리 서로의 결과에 의존하면 안 됩니다.

ChainingParallelization
의존 관계 있어야 함 — 3번은 2번 결과가 있어야 일할 수 있음 없어야 함 — 셋 다 topic만 보면 됨
읽는 칸 topic → draft_joke → improved_joke (계단식) 셋 다 topic (동일)
총 소요 시간노드 시간의 합가장 느린 하나
⚠️ 자가 진단 — 이 업무를 병렬로 돌려도 되나?

스스로에게 이렇게 물어보세요. "B 작업자에게 A의 결과물을 보여줘야 하나?"

보여줘야 한다 → Chaining. 병렬로 돌리면 B는 A의 결과를 못 봅니다(아직 안 끝났으니까).
안 보여줘도 된다 → Parallelization.

이번 실습의 시 · 소설 · 농담이 딱 후자입니다. 시를 쓰는 데 농담이 필요하지 않죠.

기획 · 그래프와 State

이번에 만들 건 "동일 주제, 다양한 스타일의 글 작성기"입니다. 주제 하나를 받아 시 · 소설 · 농담 세 가지를 동시에 만들고, 하나로 묶어 반환합니다.

그래프가 정해졌으니 State를 설계합니다. 필요한 칸을 세어 보죠 — 입력 주제 1칸 + 워커 세 명의 결과물 3칸 + 최종 취합본 1칸 = 총 5칸.

STEP 1~2. Model & State 정의

📥 코드
model = init_chat_model("gpt-5-nano")

class WriterState(TypedDict):
    topic: str          # 주제
    poem: str           # 시 (결과물 A)
    story: str          # 소설 (결과물 B)
    joke: str           # 농담 (결과물 C)
    final_report: str   # 최종 편집본
💡 이번엔 temperature를 안 줬습니다

Chaining 실습에서는 temperature=1.0이었는데 여기는 기본값입니다. 큰 의도가 있다기보다, 시·소설은 굳이 온도를 올리지 않아도 충분히 다양하게 나오기 때문입니다. 필요하면 넣고, 아니면 빼는 파라미터 정도로 보시면 됩니다.

STEP 3. Node 정의 — 워커 3명 + 편집장 1명

여기서부터 "워커(Worker)"라는 용어를 함께 씁니다. 노드 = 일하는 작업자였으니 같은 말인데, 병렬 구조에서는 "위에서 시킨 일을 나눠 맡는 하위 작업자"라는 뉘앙스로 워커라고 부릅니다. (3강 2장의 Orchestrator-Worker 패턴에서 이 용어가 다시 나옵니다.)

📥 코드 — 워커 3명
# [Worker A] 시인 노드
def write_poem(state: WriterState):
    topic = state["topic"]
    print(f"   [Worker A] '{topic}' 주제로 시(Poem) 작성 시작...")

    msg = model.invoke(f"'{topic}'에 대한 아름다운 시를 짧게 써줘.")
    return {"poem": msg.content}


# [Worker B] 소설가 노드
def write_story(state: WriterState):
    topic = state["topic"]
    print(f"   [Worker B] '{topic}' 주제로 소설(Story) 작성 시작...")

    msg = model.invoke(f"'{topic}'에 대한 감동적인 짧은 이야기를 써줘.")
    return {"story": msg.content}


# [Worker C] 개그맨 노드
def write_joke(state: WriterState):
    topic = state["topic"]
    print(f"   [Worker C] '{topic}' 주제로 농담(Joke) 작성 시작...")

    msg = model.invoke(f"'{topic}'에 대한 재미있는 아재개그를 하나 해줘.")
    return {"joke": msg.content}

세 함수를 나란히 놓고 보면 다른 곳이 딱 두 군데입니다 — 프롬프트 문장과 반환하는 키 이름. 나머지는 완전히 동일하죠. 그리고 셋 다 state["topic"]만 읽습니다. 이게 "독립적"이라는 말의 코드 상 정의입니다.

편집장 — Aggregator 노드

📥 코드
# [Aggregator] 편집장 노드 (모든 결과를 취합)
def aggregator(state: WriterState):
    print("\n--- [Aggregator] 모든 원고 도착! 최종 편집 중 ---")

    # State에 저장된 각 결과물을 꺼내서 합침
    final_text = f"""
    [주제: {state['topic']} 종합 선물세트]

    1. 시 (Poem)
    ----------------
    {state['poem']}

    2. 소설 (Story)
    ----------------
    {state['story']}

    3. 농담 (Joke)
    ----------------
    {state['joke']}
    """
    return {"final_report": final_text}
💡 취합 노드를 LLM으로 바꿀 수도 있습니다

지금은 f-string으로 그냥 이어 붙이기만 합니다. 가장 단순한 형태죠. 하지만 여기서 모델을 한 번 더 호출해도 됩니다 — "이 시·소설·농담을 바탕으로 하나의 완성된 리포트를 써줘" 라고 던지고, 그 결과를 final_report에 담는 식으로요.

취합 노드는 "붙이기"일 수도 있고 "종합하기"일 수도 있습니다. 다수결 투표 예시에서는 표를 세는 파이썬 코드가 들어가고, 관점 다각화 예시에서는 LLM이 세 의견을 종합합니다. 상황에 맞게 고르시면 됩니다.

STEP 4. 그래프 생성 — Fan-out과 Fan-in

📥 코드
workflow = StateGraph(WriterState)

# 노드 추가
workflow.add_node('write_poem', write_poem)
workflow.add_node('write_story', write_story)
workflow.add_node('write_joke', write_joke)
workflow.add_node('aggregator', aggregator)

# 엣지 연결: START에서 3개의 노드로 동시에 뻗어 나가기 (Fan-out)
workflow.add_edge(START, 'write_poem')
workflow.add_edge(START, 'write_story')
workflow.add_edge(START, 'write_joke')

# 3개의 노드가 모두 하나의 노드로 모이기 (Fan-in)
workflow.add_edge('write_poem', 'aggregator')
workflow.add_edge('write_story', 'aggregator')
workflow.add_edge('write_joke', 'aggregator')

workflow.add_edge('aggregator', END)

# 컴파일
app = workflow.compile()
용어뜻코드
Fan-out (팬 아웃) 한 지점에서 여러 노드로 뻗어나감 add_edge(START, ...) × 3
Fan-in (팬 인) 여러 노드가 한 지점으로 모임 add_edge(..., 'aggregator') × 3
🚫 여기서 가장 많이 헷갈리는 것 — "갈라지니까 조건부 엣지 아닌가요?"

아닙니다. 전부 그냥 add_edge입니다.

2강에서 add_conditional_edges를 쓴 이유는 "셋 중 하나를 골라야" 했기 때문입니다. 그런데 지금은 고르는 게 아니라 셋 다 갑니다. 고를 일이 없으니 판단 함수도 필요 없죠.

Fan-in도 마찬가지입니다. 세 워커는 "보고할지 말지"를 고르지 않습니다. 전원 무조건 보고합니다. 그래서 조건부가 아닙니다.

🔍 비유 — 갈림길 vs 폭죽

조건부 엣지는 삼거리 표지판입니다. 내 차 한 대가 좌회전·직진·우회전 중 하나를 고릅니다.

Fan-out은 폭죽입니다. 하나가 터지면서 모든 방향으로 동시에 퍼집니다. 고르는 게 없죠.

그림으로는 둘 다 "여러 갈래"라 비슷해 보이지만 — 조건부는 점선, Fan-out은 실선으로 그려집니다. 그래프 그림에서 선의 종류를 보면 바로 구분됩니다.

STEP 5. 실행

📥 코드
inputs = {"topic": "직장인의 월요일"}
result = app.invoke(inputs)
📤 실행 로그 — 실제 노트북 출력 그대로
   [Worker C] '직장인의 월요일' 주제로 농담(Joke) 작성 시작...   [Worker A] '직장인의 월요일' 주제로 시(Poem) 작성 시작...

   [Worker B] '직장인의 월요일' 주제로 소설(Story) 작성 시작...

--- [Aggregator] 모든 원고 도착! 최종 편집 중 ---
💡 이 지저분한 출력이 사실 "증거"입니다

로그를 자세히 보세요. 순서가 C → A → B로 뒤엉켰고, 심지어 C의 줄이 끝나기도 전에 A의 줄이 같은 줄에 끼어들었습니다.

이건 버그가 아니라 세 노드가 진짜로 동시에 돌고 있다는 증거입니다. Chaining의 로그는 1 → 2 → 3 순서로 얌전히 찍혔죠? 이 차이가 바로 병렬 처리입니다.

그리고 Aggregator 로그는 항상 맨 마지막에, 딱 한 번만 찍힙니다. 이유는 바로 다음에.

Aggregator는 전원이 도착해야 움직인다

여기가 병렬 처리에서 가장 중요한 규칙입니다.

취합 노드는 들어오는 엣지가 전부 도착해야 실행됩니다.

시와 농담이 먼저 끝나고 소설이 아직 쓰이는 중이라면? aggregator는 먼저 온 두 개만 갖고 일하지 않습니다. 소설이 도착할 때까지 가만히 기다렸다가, 셋이 다 모인 순간 한 번만 실행됩니다.

그래서 위 로그에서 [Aggregator]가 세 번이 아니라 한 번 찍힌 겁니다.

🔍 비유 — 단체 사진

사진사가 "세 분 다 오시면 찍을게요"라고 했다면, 두 명이 먼저 와도 셔터를 누르지 않습니다. 세 번째 사람이 올 때까지 기다렸다가 한 번 찍죠.

다르게 말하면 — 병렬 처리의 전체 소요 시간은 "가장 늦게 오는 사람"이 결정합니다. 워커 하나가 유독 느리면 나머지가 아무리 빨라도 소용이 없습니다. 실무에서 병렬 구조를 튜닝할 때 제일 느린 노드부터 손보는 이유가 이겁니다.

START

{'topic': '직장인의 월요일'} — 세 워커에게 동시에 전달

write_poem
write_story
write_joke

셋이 나란히 실행. 각자 topic만 읽고, 각자 다른 칸(poem/story/joke)에 결과를 적음. 서로의 결과는 보지 못하고, 볼 필요도 없음

⏳ (대기)

먼저 끝난 워커는 기다립니다. 셋이 다 끝나야 다음 단계로 넘어감

aggregator

세 칸을 전부 읽어 f-string으로 엮고 final_report에 담음. 단 한 번 실행

END

다섯 칸이 모두 찬 State가 result로 반환됨

📥 코드
result["final_report"]
📤 출력 (길어서 일부만)
    [주제: 직장인의 월요일 종합 선물세트]

    1. 시 (Poem)
    ----------------
    월요일의 직장인, 알람이 도시를 깨운다.
컵 속 뜨거운 빛이 오늘의 길을 밝히고,
타자 소리가 심장 박동처럼 흐른다.
...

    2. 소설 (Story)
    ----------------
    월요일은 늘 그렇듯이, 공기가 조금 무거웠다. 비가 내리면 더 그렇고,
출근길은 늘 지하철의 쇠고동 같은 숨 고르기로 시작된다. ...

    3. 농담 (Joke)
    ----------------
    ...

맨 위의 "종합 선물세트"라는 표현이 어디서 왔는지 궁금하셨다면 — aggregator 함수의 f-string 안에 우리가 직접 써넣은 문구입니다. 모델이 만든 게 아니라 파이썬 문자열이죠. 취합 노드에 LLM이 없다는 걸 확인하는 좋은 단서입니다.

그런데 — 세 노드가 같은 State를 동시에 건드려도 괜찮나?

좋은 질문입니다. 그리고 이 실습이 잘 도는 이유가 여기에 숨어 있습니다. 세 워커는 같은 State를 쓰지만 서로 다른 칸에 씁니다 — poem, story, joke. 충돌할 일이 없죠.

🚫 만약 세 워커가 같은 칸에 쓰려고 하면?

예를 들어 셋 다 return {"result": ...}처럼 같은 키를 반환하도록 만들면 LangGraph가 에러를 냅니다. "한 스텝에 같은 칸으로 값이 여러 개 들어왔는데, 어느 걸 남길지 모르겠다"는 뜻이죠.

해결책은 리듀서(reducer)입니다. 2강에서 messages에 붙였던 그것이요. "덮어쓰지 말고 이어 붙여라"는 규칙을 알려주면 됩니다.

📌 참고 — 같은 칸에 모아야 할 때의 State
from typing import Annotated
import operator

class VoteState(TypedDict):
    topic: str
    # 여러 워커가 같은 칸에 쓸 때는 리듀서로 "이어 붙이기" 규칙을 준다
    opinions: Annotated[list, operator.add]

이렇게 해두면 세 워커가 각각 return {"opinions": ["찬성"]}을 반환해도 덮어쓰지 않고 ["찬성", "찬성", "반대"]로 쌓입니다. 앞서 이야기한 다수결 투표를 구현하려면 정확히 이 형태가 필요하죠.

🔍 비유 — 화이트보드 한 칸에 세 명이 동시에 쓰기

세 사람이 각자 다른 칸에 쓰면 아무 문제가 없습니다. 지금 실습이 그 경우죠.

그런데 같은 칸에 셋이 동시에 쓰려 하면 글씨가 겹쳐서 아무것도 못 읽습니다. 그래서 규칙이 필요합니다 — "덮어쓰지 말고 아래로 한 줄씩 이어 써". 이 규칙이 리듀서입니다.

②③이 병렬 구간, ①②와 ③④⑤가 체인 구간입니다. "의존이 있으면 이어 붙이고, 없으면 펼친다"는 기준으로 구간마다 따로 판단하시면 됩니다.

① Prompt Chaining — 농담 생성기

# ══ STEP 1. Model ═════════════════════════════════════
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano", temperature=1.0)

# ══ STEP 2. State ═════════════════════════════════════
from typing import TypedDict

class JokeState(TypedDict):
    topic: str
    draft_joke: str
    improved_joke: str
    final_joke: str

# ══ STEP 3. Node ══════════════════════════════════════
def generate_joke(state: JokeState):
    topic = state["topic"]
    print(f"\n--- [1단계] '{topic}' 주제로 농담 초안 생성 중 ---")
    msg = model.invoke(f"'{topic}'에 대한 짧고 재미있는 농담을 하나 만들어줘. 다른 말은 하지 말고 농담 하나만 해")
    return {"draft_joke": msg.content}

def critique_and_improve(state: JokeState):
    original_joke = state["draft_joke"]          # ★ 앞 노드의 결과를 읽는다
    print(f"\n--- [2단계] 더 웃기게 수정 중 (아재개그 스타일) ---")
    prompt = f"""
    다음 농담을 보고, 더 썰렁하고 재미있는 '아재개그' 스타일로 개선해줘. 다른 말은 하지 말고 하나만 답변해.
    원문: {original_joke}
    """
    msg = model.invoke(prompt)
    return {"improved_joke": msg.content}

def polish_joke(state: JokeState):
    improved_joke = state["improved_joke"]       # ★ 앞 노드의 결과를 읽는다
    print(f"\n--- [3단계] 이모지 추가 및 마무리 ---")
    prompt = f"""
    다음 농담에 적절한 이모지를 듬뿍 넣어서 SNS에 올리기 좋게 꾸며줘.
    농담: {improved_joke}
    """
    msg = model.invoke(prompt)
    return {"final_joke": msg.content}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END

app = StateGraph(JokeState)

app.add_node('generate_joke', generate_joke)
app.add_node('critique_and_improve', critique_and_improve)
app.add_node('polish_joke', polish_joke)

app.add_edge(START, 'generate_joke')
app.add_edge('generate_joke', 'critique_and_improve')
app.add_edge('critique_and_improve', 'polish_joke')
app.add_edge('polish_joke', END)

chain = app.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
result = chain.invoke({"topic": "고양이"})
print(result["final_joke"])

② Parallelization — 시 · 소설 · 농담 동시 생성

# ══ STEP 1~2. Model & State ═══════════════════════════
model = init_chat_model("gpt-5-nano")

class WriterState(TypedDict):
    topic: str
    poem: str
    story: str
    joke: str
    final_report: str

# ══ STEP 3. Node ══════════════════════════════════════
def write_poem(state: WriterState):
    topic = state["topic"]                       # ★ 셋 다 topic만 읽는다 = 서로 독립
    print(f"   [Worker A] '{topic}' 주제로 시(Poem) 작성 시작...")
    msg = model.invoke(f"'{topic}'에 대한 아름다운 시를 짧게 써줘.")
    return {"poem": msg.content}

def write_story(state: WriterState):
    topic = state["topic"]
    print(f"   [Worker B] '{topic}' 주제로 소설(Story) 작성 시작...")
    msg = model.invoke(f"'{topic}'에 대한 감동적인 짧은 이야기를 써줘.")
    return {"story": msg.content}

def write_joke(state: WriterState):
    topic = state["topic"]
    print(f"   [Worker C] '{topic}' 주제로 농담(Joke) 작성 시작...")
    msg = model.invoke(f"'{topic}'에 대한 재미있는 아재개그를 하나 해줘.")
    return {"joke": msg.content}

def aggregator(state: WriterState):
    print("\n--- [Aggregator] 모든 원고 도착! 최종 편집 중 ---")
    final_text = f"""
    [주제: {state['topic']} 종합 선물세트]

    1. 시 (Poem)
    ----------------
    {state['poem']}

    2. 소설 (Story)
    ----------------
    {state['story']}

    3. 농담 (Joke)
    ----------------
    {state['joke']}
    """
    return {"final_report": final_text}

# ══ STEP 4. Graph ═════════════════════════════════════
workflow = StateGraph(WriterState)

workflow.add_node('write_poem', write_poem)
workflow.add_node('write_story', write_story)
workflow.add_node('write_joke', write_joke)
workflow.add_node('aggregator', aggregator)

# Fan-out — 조건부가 아니라 그냥 엣지 (셋 다 간다)
workflow.add_edge(START, 'write_poem')
workflow.add_edge(START, 'write_story')
workflow.add_edge(START, 'write_joke')

# Fan-in — 셋이 다 도착해야 aggregator가 실행된다
workflow.add_edge('write_poem', 'aggregator')
workflow.add_edge('write_story', 'aggregator')
workflow.add_edge('write_joke', 'aggregator')

workflow.add_edge('aggregator', END)

app = workflow.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
result = app.invoke({"topic": "직장인의 월요일"})
print(result["final_report"])

자주 걸리는 함정 6가지

🕳️ 이번 장에서 실제로 밟게 되는 지뢰

1. 체인인 줄 알았는데 그냥 세 번 물어본 것

critique_and_improve가 state["draft_joke"]가 아니라 state["topic"]을 읽고 있으면 그래프 그림은 똑같아도 체인이 아닙니다. 엣지가 아니라 노드 안의 state[...]가 체인을 만든다는 걸 기억하세요.

2. 키 이름 오타 — KeyError

return {"draft_joke": ...}인데 다음 노드가 state["drafted_joke"]를 읽으면 배턴을 못 주워서 그 자리에서 멈춥니다. 반환 키와 읽는 키는 항상 짝으로 확인하세요.

3. 병렬 브랜치가 같은 칸에 쓴다

워커 셋이 전부 return {"result": ...}를 반환하면 "한 스텝에 같은 칸으로 값이 여러 개 들어왔다"는 에러가 납니다. 칸을 따로 두거나, Annotated[list, operator.add] 리듀서를 붙이세요.

4. 병렬로 묶어놓고 순서를 기대한다

add_edge를 poem → story → joke 순서로 썼다고 해서 그 순서로 실행되지 않습니다. 코드 줄 순서와 실행 순서는 아무 관계가 없습니다. 순서가 필요하면 병렬이 아니라 체인으로 만드세요.

5. 빌더와 컴파일 결과를 헷갈린다

StateGraph(...)는 설계도, .compile()의 결과가 완제품입니다. 노트북에서 실습 ①은 app이 설계도·chain이 완제품인데, 실습 ②는 workflow가 설계도·app이 완제품이라 이름이 뒤집혀 있습니다. 이름 말고 .compile()을 거쳤는지로 판단하세요.

6. 노드를 고쳐놓고 그래프를 다시 컴파일하지 않는다

컴파일된 그래프는 그 시점의 함수를 붙들고 있는 사본입니다. 노드 함수 셀만 다시 실행해도 동작은 그대로예요. StateGraph(...)부터 .compile()까지 전부 다시 실행하세요. (2강에서도 나왔던 함정입니다.)

💡 디버깅 요령 — print를 아끼지 마세요

이번 실습의 모든 노드에 print가 하나씩 들어 있는 건 우연이 아닙니다. 어느 노드까지 갔는지, 순서대로 갔는지 동시에 갔는지를 로그만 봐도 알 수 있기 때문이죠. 실제로 병렬 실습에서 로그가 뒤엉킨 것이 병렬 동작의 유일한 육안 증거였습니다.

📚 한 장 정리

오늘의 핵심 한 문장

노드와 엣지는 그대로인데 배치만 바꾸면 전혀 다른 시스템이 된다 — 의존이 있으면 줄을 세우고(Chaining), 없으면 펼친다(Parallelization).

  • 왜 배우나 — LangChain v0의 "체인"이 v1에서 정리되었지만, 노드 + 엣지로 그 구조를 그대로(오히려 더 낫게) 재현할 수 있다.
  • Prompt Chaining — 한 번에 다 시키지 말고 Step-by-Step으로.
    • 쓰는 신호 3가지 — ①토큰 제한 ②작업 성격이 다름 ③검증/개선 필요
    • 한 프롬프트에 지시를 몰아넣으면 어텐션이 분산돼서 뭔가 빠진다.
    • State는 단계마다 칸을 따로 — topic → draft_joke → improved_joke → final_joke. 덮어쓰지 않아야 어느 단계에서 무슨 일이 있었는지가 남는다.
    • 체인의 정체는 엣지가 아니라 state["앞_노드_칸"] 한 줄.
  • Parallelization — 독립적인 일은 한 방에.
    • 목적 둘 — 속도(Latency)와 정확도(다수결 투표 · 관점 다각화)
    • 전제조건은 독립성. "B에게 A의 결과를 보여줘야 하나?"가 판단 기준.
    • Fan-out(START → 여럿) / Fan-in(여럿 → Aggregator). 둘 다 조건부 엣지가 아니라 그냥 add_edge — 고르는 게 아니라 전부 가니까.
    • Aggregator는 전원이 도착해야 딱 한 번 실행된다. 그래서 전체 시간은 가장 느린 워커가 결정한다.
    • 워커들이 같은 칸에 쓰려면 리듀서가 필요하다 (Annotated[list, operator.add]). 다른 칸에 쓰면 아무 문제 없다.
  • 실습 결과에 실망하지 마세요 — LLM은 유머에 약합니다. 이번 실습에서 확인할 것은 농담의 완성도가 아니라 "데이터가 설계대로 흘렀는가"입니다.
🔍 마지막으로 — 두 패턴의 관계

둘은 대립하는 선택지가 아닙니다. 하나의 그래프 안에서 구간마다 섞여 쓰입니다.

판단 기준은 언제나 하나입니다 — "이 작업자가 저 작업자의 결과물을 봐야 하는가?" 봐야 하면 이어 붙이고(Chaining), 안 봐도 되면 펼칩니다(Parallelization).

다음 예고

Routing — 상황을 보고 갈 길을 고르는 패턴입니다. 2강의 조건부 엣지에서 이미 맛봤지만, 이번엔 패턴으로 정리합니다.

그리고 1장을 마치면 2장 응용 아키텍처로 넘어갑니다 — 결과물을 평가해서 퇴짜를 놓는 Evaluator(평가자)와, 일을 몇 개로 쪼갤지 실행 중에 정하는 Orchestrator(지휘자)를 만듭니다. 오늘까지가 미리 그려둔 도면대로 흐르는 구조였다면, 그다음은 도면을 실행 중에 그리는 구조입니다.

끝으로 "Workflow와 Agent는 뭐가 다른가" — 자주 혼용되는 두 용어를 정리하며 3강을 마무리합니다.
