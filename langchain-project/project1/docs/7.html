7

골든 평가셋 + RAGAS — 세 구성을 숫자로 비교

서비스화 층 · 핵심 ⏱ 반나절~1일
🎯 목표

"hybrid·rerank로 좋아진 것 같다"를 숫자로 바꾼다. 같은 정답지로 baseline / hybrid / rerank 세 구성을 채점해 개선 스토리를 표로 완성한다 — STEP 3에서 만든 mode 팩토리가 여기서 빛을 발합니다.

🧠 개념

개선을 주장하려면 측정이 필요합니다. 그런데 RAG의 답은 정답/오답으로 딱 떨어지지 않습니다 — "환불 기한은 14일입니다"와 "수령일로부터 14일 이내에 신청해야 합니다"는 같은 말인데 겹치는 글자가 거의 없죠. 그래서 점수를 매겨 줄 도구가 따로 필요하고, 그 역할을 하는 게 RAGAS입니다.

📌 이 문서에 계속 나오는 말 두 개

정답지 — 내가 문서를 직접 읽고 "이 질문의 답은 이거다"를 손으로 적어 둔 파일입니다. 채점의 기준이 되는 종이 한 장이라고 보면 됩니다. 업계에서는 골든셋이라 부르고 이 STEP의 제목에 붙은 "골든 평가셋"이 바로 이것인데, 아래에서는 계속 정답지라고만 쓰겠습니다.

채점 LLM — 점수 매기는 일만 맡기는 LLM입니다. 답을 만들어 주는 LLM과 이름은 같아도(둘 다 gpt-5-mini일 수 있습니다) 하는 일이 다른 별개의 호출이에요 — 한쪽은 답을 쓰고, 한쪽은 그 답에 점수를 매깁니다.

❓ 그래서 RAGAS가 대체 뭔가요?

RAGAS = RAG Assessment(RAG 평가)의 줄임말이고, STEP 0에서 uv add ragas로 이미 설치해 둔 파이썬 라이브러리입니다. 바로 앞 STEP의 Langfuse처럼 가입해서 대시보드를 보는 서비스가 아니라, 표를 넣으면 점수를 돌려주는 함수 한 덩어리예요.

우리가 넣는 표 — 질문 수만큼의 행
question answer contexts ground_truth
ragas.evaluate() ▼
돌려받는 점수 — 0~1 소수
faithfulness 0.82 context_recall 0.75 …

넣는 표의 네 칸이 각각 뭔지부터 짚고 가면 뒤가 훨씬 쉬워집니다. 앞의 둘은 사람이, 뒤의 둘은 시스템이 채웁니다.

칸 이름담기는 것누가 채우나
question우리가 던질 질문사람이 손으로
ground_truth그 질문의 정답 — 문서에 적힌 대로사람이 손으로
answer우리 RAG가 실제로 내놓은 답시스템이 자동
contexts그 답을 쓸 때 검색해 온 문서 조각들시스템이 자동

위 두 칸을 모아 둔 파일이 곧 정답지(eval_data.json)이고, 아래 두 칸은 그 질문을 우리 시스템에 넣어 받아 오는 값입니다. 즉 사람이 절반, 시스템이 절반을 채워 표 하나를 완성한 뒤 RAGAS에 넘기는 거예요.

어려운 지점은 "채점 기준"입니다. 우리 시스템의 답과 사람이 쓴 정답을 글자 그대로 비교할 수는 없습니다 — 위의 두 문장처럼 뜻이 같아도 글자가 안 겹칠 수 있고, 반대로 글자가 많이 겹쳐도 뜻이 정반대일 수 있으니까요.

그래서 RAGAS는 채점을 또 다른 LLM에게 맡깁니다 — 위에서 말한 채점 LLM이 이 일을 합니다. (이 방식을 부르는 이름이 LLM-as-a-judge입니다.) 예를 들어 faithfulness는 이렇게 계산됩니다 — 우리 답을 주장 단위로 쪼갠 뒤, 주장마다 "이게 검색해 온 문서 조각에 실제로 적혀 있나?"를 채점 LLM에게 묻고, 근거 있는 주장의 비율을 점수로 냅니다.

우리 시스템의 답 "환불은 14일 이내에 신청해야 하며, 배송비는 회사가 부담합니다."
주장 2개로 분해 ▼
① 환불은 14일 이내 신청 ✅ 문맥에 있음
② 배송비는 회사 부담 ❌ 문맥에 없음 모델이 지어냄
근거 있는 주장의 비율 ▼
faithfulness = 1 / 2 = 0.5

점수가 0~1 소수로 나오는 이유가 이겁니다 — 비율이거든요. 그리고 채점에도 API 비용이 드는 이유, 답만이 아니라 contexts까지 넘겨야 하는 이유도 여기서 나옵니다. 채점 LLM이 "이 주장이 문서 조각에 있나"를 판정하려면 그 조각을 직접 읽어야 하니까요.

대신 이 점수를 절대 기준으로 믿으면 안 됩니다. 채점하는 쪽도 결국 LLM이라, 같은 답을 두 번 채점하면 점수가 조금씩 흔들립니다. RAGAS는 "0.82니까 합격"에 쓰는 도구가 아니라, 같은 정답지 · 같은 채점 LLM으로 여러 구성을 나란히 돌려 비교하는 데 쓰는 도구예요. 이 STEP이 하려는 게 정확히 그것입니다.

RAGAS가 매기는 대표 지표는 4개입니다. 모두 0~1 사이 소수이고 높을수록 좋습니다. 위 둘은 생성(답)을 보고, 아래 둘은 검색(문맥)을 봅니다 — 점수가 떨어졌을 때 어느 쪽을 손봐야 하는지 갈라 주는 구분이에요.

지표무엇을 재나낮으면 손볼 곳
faithfulness답이 검색 문맥에 충실한가(환각 여부)생성 프롬프트(STEP 2)
answer_relevancy답이 질문에 맞는가생성/질문 이해(STEP 2)
context_precision검색된 문맥이 군더더기 없이 관련 있나검색 노이즈 → rerank의 top_n·후보 폭(STEP 4)
context_recall정답 근거를 검색이 빠짐없이 가져왔나검색 누락 → hybrid 가중치·k(STEP 3)
🎓 표가 네 줄이 아니라 "두 줄씩 두 덩어리"로 보이면 쉬워집니다

RAG를 오픈북 시험이라고 해봅시다. 하는 일이 순서대로 두 가지예요 — ① 질문을 보고 책에서 해당 페이지를 찾아 펼친다(검색), ② 펼친 페이지를 읽고 답안을 쓴다(생성).

점수가 나빴을 때 페이지를 잘못 펼친 탓인지, 펼쳐 놓고 답을 못 쓴 탓인지를 갈라야 고칠 수 있습니다. 위 표의 네 지표가 정확히 그 구분이에요. context_로 시작하는 아래 둘은 페이지 찾기 채점, 위 둘은 답안 쓰기 채점입니다. "낮으면 손볼 곳" 칸이 STEP 3·4(검색)와 STEP 2(생성)로 갈리는 이유가 이것뿐입니다.

🔍 검색 쪽 둘 — "빠뜨렸나" vs "군더더기가 붙었나"

context_recall은 "필요한 페이지를 다 펼쳤나"입니다. 채점 LLM이 정답지(ground_truth)를 문장 단위로 쪼갠 뒤, 문장마다 "이 내용이 검색해 온 조각들 안에 있나?"를 확인해요. 정답에 네 문장이 필요한데 검색이 두 문장어치만 가져왔다면 0.5입니다. 빠뜨린 것을 재는 지표라, 낮으면 원인은 무조건 검색 쪽이에요.

그래서 손볼 곳이 STEP 3의 hybrid 가중치와 k입니다. 벡터 검색은 "뜻"으로 찾기 때문에 할부항변권처럼 딱 떨어지는 단어를 의외로 놓치는데, BM25(키워드 검색)를 섞으면 바로 그걸 잡아 줍니다. k를 키워 더 많이 가져오는 것도 같은 방향이고요.

context_precision은 반대로 "펼친 페이지에 헛것이 섞였나"입니다. 가져온 조각 중 쓸모 있는 것이 앞쪽에 왔는지를 봐요. 10개를 가져왔는데 3개만 관련 있으면 낮게 나옵니다. 그래서 손볼 곳은 STEP 4의 rerank top_n — 일단 넉넉히 가져온 뒤 정밀한 모델로 다시 줄 세워 위에서 몇 개만 남기는 겁니다.

⚖️ 이 둘은 서로 잡아당깁니다

k를 키우면 context_recall은 오르고 context_precision은 떨어집니다. 그물을 넓게 던지면 놓치는 건 줄지만 잡어도 같이 올라오니까요. 그래서 네 지표를 동시에 최고로 만드는 설정은 없고, 어디서 타협할지를 정하는 게 일이 됩니다 — 그 줄다리기를 정면으로 다루는 것이 STEP 8입니다.

✍️ 생성 쪽 둘 — "지어냈나" vs "딴소리했나"

faithfulness는 "펼친 페이지에 없는 말을 답안에 썼나" — 환각 여부입니다. 위에서 본 예시(답을 주장 2개로 쪼개 1 ÷ 2 = 0.5)가 이거예요. 여기서 헷갈리기 쉬운 게 있는데, 이건 검색을 탓하는 지표가 아닙니다. 검색이 엉뚱한 페이지를 가져왔더라도 그 엉뚱한 페이지에 적힌 대로만 답했다면 점수는 높게 나옵니다. "책에 있는 말만 옮겼는가"만 보거든요. 그래서 낮으면 프롬프트를 고칩니다 — "문맥에 없으면 모른다고 답하라"를 STEP 2 프롬프트에 못 박는 식으로요.

answer_relevancy는 "질문에 대한 답을 하긴 했나" — 동문서답 여부입니다. 계산 방식이 넷 중 가장 특이한데, 우리 답을 보고 채점 LLM이 "이런 답이 나올 법한 질문"을 거꾸로 지어낸 뒤, 그 역질문이 원래 질문과 얼마나 비슷한지를 임베딩으로 잽니다. 네 지표 중 임베딩을 쓰는 게 이 하나뿐인 이유가 여기 있습니다.

🧭 그래서 표를 어떻게 읽나 — 예시 한 번

baseline을 돌려 이런 숫자가 나왔다고 해봅시다. 

[baseline]  faithfulness       0.88   # 답안: 책에 있는 말만 옮겼나
            answer_relevancy   0.48   # 답안: 질문에 맞는 답을 했나
            context_precision  0.62   # 검색: 군더더기 없이 가져왔나
            context_recall     0.58   # 검색: 빠뜨리지 않고 가져왔나

context_recall이 0.58이라는 건 정답에 필요한 근거의 40%쯤을 검색이 아예 못 가져왔다는 뜻입니다. 그런데도 faithfulness는 0.88이죠 — "가져온 것 안에서는 성실하게 답했다"는 겁니다. 두 숫자를 같이 읽어야 이 결론이 나옵니다: 지금 병목은 답 쓰는 쪽이 아니라 페이지 찾는 쪽이다. 순수 벡터 검색인 baseline에서는 자연스러운 결과이고, hybrid·rerank를 켜면 오르기를 기대하는 지점이 정확히 여기입니다.

⚠️ "낮으면 손볼 곳"은 출발점이지 결론이 아닙니다

위 예시에서 answer_relevancy 0.48은 표대로라면 "생성(STEP 2)을 봐라"입니다. 하지만 실제로는 검색 누락의 2차 피해일 때가 많아요 — 근거를 못 찾으면 모델이 얼버무리게 되고, 얼버무린 답은 역질문이 넓게 퍼져 유사도가 떨어집니다. 이때 프롬프트만 붙들고 고치면 헛다리를 짚게 됩니다. 진짜 원인은 검색이니까요.

여기에 LLM returned 1 generations instead of requested 3 경고까지 겹치면 더 흔들립니다 — 역질문을 3개 만들어 평균을 내야 하는데 1개만 와서 표본 하나로 계산된 점수가 되거든요.

정리하면, 표는 "어디부터 의심할지"를 알려 줄 뿐입니다. 어떤 문항이 점수를 깎았는지는 eval_*.csv를 열어야 보이고, 보통 거기에 진짜 원인이 있습니다.

① 정답지 — 질문과 정답을 손으로 적는다

채점을 하려면 기준이 될 정답이 먼저 있어야 합니다. 그게 정답지고, 내용물은 질문과 그 질문의 정답을 짝지어 적어 둔 목록이 전부입니다. 그리고 이건 직접 만들 수밖에 없습니다 — 내 문서에 대한 정답을 아는 건 나뿐이니까요. 이 프로젝트에서 가장 귀찮지만 가장 중요한 작업이고, 실무 RAG도 똑같습니다.

eval_data.json
[
  {"question": "질문 1?", "ground_truth": "문서 기준 정답 1"},
  {"question": "질문 2?", "ground_truth": "문서 기준 정답 2"}
]

처음엔 5개로 시작해 20~50개까지 늘리세요. 5개로도 파이프라인이 도는지는 확인되지만, 그 정도로는 점수가 질문 하나에 크게 출렁여서 "좋아졌다"고 말하기 어렵습니다.

⚠️ ground_truth는 "내 상식"이 아니라 "문서에 쓰인 말"로

평가는 우리 시스템이 이 문서에서 정답을 잘 찾아오는가를 재는 것입니다. 그러니 정답도 문서에 실제로 적힌 내용이어야 해요. 문서에 없는 내용을 정답으로 적으면 시스템은 영원히 틀린 것으로 채점됩니다. 질문은 골고루 섞으세요 — 조항 번호나 고유 용어가 든 질문(BM25가 유리), 풀어쓴 일상적인 질문(의미 검색이 유리), 여러 쪽을 합쳐야 답이 되는 질문까지요. 그래야 세 구성의 차이가 드러납니다.

② 채점기 준비 — 부품 불러오고 mode 받기

from ragas.embeddings import LangchainEmbeddingsWrapper  # 어댑터 — 임베딩용

# 어떤 검색 구성을 채점할지 터미널에서 받는다. 파일 하나로 세 구성을 각각 돌리기 위한 장치.
#   uv run python evaluate.py hybrid  →  mode = "hybrid"

# 정답지를 읽어 온다. 형식: [{"question": ..., "ground_truth": ...}, ...]
rows = json.load(open("eval_data.json", encoding="utf-8"))

mode를 실행 인자로 받는 게 핵심입니다. 파일 하나로 세 구성을 각각 채점하려는 것이고, 이게 가능한 건 STEP 3에서 검색기를 문자열로 갈아끼울 수 있게 만들어 뒀기 때문입니다. Wrapper가 붙은 둘은 어댑터예요 — RAGAS가 우리 랭체인 모델을 쓸 수 있게 모양을 맞춰 주는 변환 플러그입니다.

③ 질문마다 실제 RAG를 돌려 답안 모으기

채점 전에, 우리 시스템이 실제로 답을 쓰게 하는 단계입니다. 정답지의 질문을 하나씩 우리 시스템에 넣습니다.

evaluate.py (이어서)
records = []                               # 채점기에 넘길 '표'의 행들을 모을 리스트
for r in rows:                             # 정답지의 질문을 하나씩 꺼내
    out = answer(r["question"], mode=mode) # 실제로 RAG를 돌린다 (여기서 STEP 3~4의 mode 팩토리가 쓰인다)
    records.append({
        "question": r["question"],         # 물어본 질문
        "answer": out["answer"],           # 우리 시스템이 낸 답  → ground_truth와 비교해 '답의 품질'을 잰다
        "contexts": out["contexts"],       # 검색된 원문 전체    → 이게 없으면 검색 관련 지표를 계산할 수 없다
        "ground_truth": r["ground_truth"], # 사람이 만든 정답    → 모든 비교의 기준
    })
# ※ 여기서 API 비용이 발생한다. 질문 수만큼 검색 + LLM 호출이 실제로 일어나기 때문.
🔗 STEP 2의 contexts가 여기서 쓰입니다

STEP 2에서 answer()가 contexts(검색된 원문 전체)를 함께 돌려주게 만들었죠. 사람에게는 필요 없어서 STEP 5의 API 응답에서도 뺐던 그 값입니다. 그 이유가 지금 드러납니다 — 검색 관련 지표 두 개는 이게 없으면 계산 자체가 안 됩니다. 답만 보고는 "검색이 정답 근거를 가져오긴 했나"를 알 수 없으니까요.

네 항목이 각각 채점의 재료입니다. answer와 contexts를 비교하면 환각 여부가, contexts와 ground_truth를 비교하면 검색 누락이 드러납니다.

❓ 이 네 개의 키 이름은 마음대로 정해도 되나요?

안 됩니다. 키 이름이 곧 약속입니다. RAGAS는 표의 몇 번째 칸인지가 아니라 이름으로 값을 찾습니다. 그래서 question을 query로, ground_truth를 gt로 바꾸면 에러가 나는 게 아니라 값이 통째로 비어 채점이 조용히 망가집니다(점수가 전부 NaN).

참고로 우리가 쓰는 이 네 이름은 RAGAS의 옛 이름이고, 요즘 버전은 evaluate() 안에서 새 이름으로 자동 번역해 씁니다. 공식 문서를 찾아보다 낯선 이름이 나오면 이 대응표를 떠올리세요 — 같은 것을 가리킵니다. 

우리가 넣는 이름              RAGAS 내부 이름
──────────────────────────────────────────────
question         →           user_input
answer           →           response
contexts         →           retrieved_contexts
ground_truth     →           reference

④ 채점하고 CSV로 남기기

evaluate.py (이어서)
result = evaluate(
    Dataset.from_list(records),   # 위에서 모은 행들을 RAGAS가 읽는 표 형식으로 변환
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],  # 이 4개 지표로 채점
    # 채점을 맡는 LLM — 답을 만드는 모델이 아니라 점수를 매기는 모델이다.
    # "이 답이 저 문맥에 근거하고 있나?" 같은 판단은 규칙으로 짜기 어려워 LLM에게 맡긴다.
    # → 그래서 평가를 돌릴 때도 API 비용이 든다 (질문 수 × 지표 4개만큼 호출)
    # bypass_temperature=True: gpt-5 계열은 temperature 기본값(1) 외를 거부한다 (아래 ⚠️ 참고)
    llm=LangchainLLMWrapper(init_chat_model("gpt-5-mini"), bypass_temperature=True),
    # 문장끼리 의미가 얼마나 가까운지 재는 데 쓰는 임베딩 — answer_relevancy 하나가 쓴다
    embeddings=LangchainEmbeddingsWrapper(OpenAIEmbeddings(model="text-embedding-3-small")),
)

print(f"[{mode}]", result)                                  # 지표별 '평균'을 화면에 출력
result.to_pandas().to_csv(f"eval_{mode}.csv", index=False)  # 문항별 상세 점수를 CSV로 저장
# 평균만 보면 '왜' 떨어졌는지 모른다. 어떤 질문이 점수를 깎아먹었는지는 이 CSV를 열어야 보인다.

llm=에 넘기는 모델은 답을 만드는 모델이 아니라 채점을 맡는 LLM입니다. "이 답이 저 문맥에 근거하고 있나?" 같은 판단은 규칙으로 짜기 어려워서, RAGAS는 LLM에게 채점을 시킵니다. 그래서 평가를 돌릴 때도 API 비용이 듭니다 — 질문 수 × 지표 4개만큼 호출이 나가니, 정답지를 50문항으로 늘릴 때는 감안하세요.

❓ 표 하나를 던지면 RAGAS가 알아서 비교해 주는 건가요?

"알아서"는 아닙니다. 4개 지표가 같은 표를 보지만, 각자 필요한 칸만 골라 읽습니다. 지표마다 채점 방식이 정해져 있고, 그 방식에 필요한 재료가 다르기 때문이에요.

지표읽는 칸안 읽는 칸
faithfulnessquestion · answer · contextsground_truth
answer_relevancyquestion · answercontexts · ground_truth
context_precisionquestion · contexts · ground_truthanswer
context_recallquestion · contexts · ground_truthanswer

눈여겨볼 것은 사람이 만든 정답(ground_truth)을 아래 두 개만 쓴다는 점입니다. faithfulness는 "답이 문맥에 충실한가"를 보는 거라 정답지가 필요 없어요 — 우리가 검색해 온 문맥이 곧 채점 기준이니까요. 반대로 검색 지표 둘은 answer를 안 봅니다. 검색이 잘 됐는지는 답을 만들기 전에 이미 결정된 문제라서요.

그러면 llm=과 embeddings=는요? 이 둘은 데이터가 아니라 채점 LLM이 채점할 때 쓰는 도구입니다. 그리고 역할이 갈립니다. llm은 네 지표 전부가 씁니다 — 주장을 쪼개고 "이게 문맥에 있나"를 판정하는, 규칙으로 짤 수 없는 일이니까요. embeddings는 answer_relevancy 하나만 씁니다.

왜 그 하나만 임베딩이 필요한지가 재밌습니다. answer_relevancy는 답을 보고 질문을 거꾸로 만들어 보는 방식으로 채점하거든요. 

답: "할부항변권은 20만원 이상인 거래에 행사할 수 있습니다."
      ↓ 채점 LLM에게 "이 답을 보고 원래 질문을 역으로 만들어봐" (3개)
   "할부항변권 행사 기준 금액은?"
   "얼마 이상이어야 할부항변권을 쓸 수 있나?"
   "할부항변권의 최소 거래금액은?"
      ↓ 이 3개와 '진짜 질문'을 각각 벡터로 만들어 거리를 잰다  ← 임베딩이 필요한 지점
   코사인 유사도 평균 0.95  =  answer_relevancy

답이 질문과 겉돌면 거꾸로 만든 질문이 원래 질문에서 멀어지고, 그 거리가 그대로 점수가 됩니다. 거리를 재려면 문장을 벡터로 바꿔야 하니 임베딩을 넘기는 것이고요. 실행하면 LLM returned 1 generations instead of requested 3 같은 경고가 보일 수 있는데, 바로 이 "역질문 3개 만들기"입니다 — 3개를 못 만들면 1개로 채점하니 점수가 조금 더 출렁일 뿐 멈추지는 않습니다.

⚠️ 점수가 전부 NaN으로 나온다면 — temperature 함정

RAGAS는 채점을 일관되게 만들려고 채점 LLM의 temperature를 0.01로 낮춰 호출합니다. 그런데 gpt-5 계열은 기본값(1) 외의 temperature를 거부해서 호출이 400 에러로 실패합니다. 

Exception raised in Job[2]: BadRequestError(Error code: 400 -
  "Unsupported value: 'temperature' does not support 0.01 with this model.
   Only the default (1) value is supported.")
...
RESULT: {'faithfulness': nan, 'answer_relevancy': nan, 'context_precision': nan, 'context_recall': nan}

고약한 건 프로그램이 죽지 않는다는 것입니다. 채점 job이 전부 실패해도 예외가 올라오지 않고 조용히 NaN만 남아요. 그래서 "돌아가긴 했는데 점수가 없네?"로 보입니다. LangchainLLMWrapper에 이런 모델을 위한 플래그가 이미 있으니 켜 주면 됩니다 — RAGAS가 temperature를 건드리지 않고 모델 기본값 그대로 호출합니다. 

llm=LangchainLLMWrapper(init_chat_model("gpt-5-mini"), bypass_temperature=True),

교훈 하나 — 평가 코드는 처음 돌릴 때 정답지를 2문항으로 줄여 한 번 시험해 보세요. 15문항 × 3구성을 다 돌린 뒤에 전부 NaN인 걸 발견하면 그만큼의 API 비용이 그냥 날아갑니다.

print는 평균만 보여주지만, CSV에는 문항별 점수가 다 들어갑니다. 평균이 떨어졌을 때 어떤 질문이 깎아먹었는지는 CSV를 열어야 보이고, 보통 거기에 개선의 실마리가 있습니다.

📄 전체 코드 (위 세 조각을 이어 붙인 것)
evaluate.py
# ═══════════════════════════════════════════════════════════════════
# STEP 7 · RAGAS 평가: '좋아진 것 같다'를 숫자로 바꾼다.
# 정답지(eval_data.json)에 answer(question, mode=...)를 돌려, 4개 지표로 채점한다:
#   faithfulness(환각 여부) · answer_relevancy(질문 적합) · context_precision(문맥 정확) · context_recall(누락 없음)
# 실행:  uv run python evaluate.py baseline   → eval_baseline.csv
#       uv run python evaluate.py hybrid     → eval_hybrid.csv
#       uv run python evaluate.py rerank     → eval_rerank.csv
# 세 번 실행해 나온 지표를 한 표에 모으면 '개선 스토리'가 완성된다.
# ═══════════════════════════════════════════════════════════════════
import json, sys
from datasets import Dataset                                   # RAGAS에 넣을 표(데이터셋) 형식
from ragas import evaluate                                     # 채점 실행 함수
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall  # 지표 4종
from ragas.llms import LangchainLLMWrapper                     # RAGAS가 LangChain LLM을 쓰게 감싸는 어댑터
from ragas.embeddings import LangchainEmbeddingsWrapper        # RAGAS가 쓸 임베딩 어댑터
from langchain.chat_models import init_chat_model
from langchain_openai import OpenAIEmbeddings
from rag import answer                                         # 평가 대상: 우리 RAG 파이프라인

mode = sys.argv[1] if len(sys.argv) > 1 else "baseline"     # 어떤 검색 구성(mode)을 채점할지
rows = json.load(open("eval_data.json", encoding="utf-8"))     # 정답지 로드: [{question, ground_truth}, ...]
records = []
for r in rows:                                                 # 질문마다 실제로 RAG를 돌려 채점용 행을 만든다
    out = answer(r["question"], mode=mode)                     # STEP 3~4의 mode 팩토리가 여기서 쓰인다
    records.append({
        "question": r["question"],                             # 질문
        "answer": out["answer"],                               # 우리 시스템이 낸 답
        "contexts": out["contexts"],                           # 검색된 문맥(정확/누락 지표 계산에 필요)
        "ground_truth": r["ground_truth"],                     # 사람이 만든 정답(기준)
    })

result = evaluate(                                             # 4개 지표로 일괄 채점
    Dataset.from_list(records),
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
    # 채점을 맡는 LLM. bypass_temperature=True가 없으면 gpt-5 계열은 400 에러 → 전 지표 NaN
    llm=LangchainLLMWrapper(init_chat_model("gpt-5-mini"), bypass_temperature=True),
    embeddings=LangchainEmbeddingsWrapper(OpenAIEmbeddings(model="text-embedding-3-small")),  # answer_relevancy가 쓰는 임베딩
)
print(f"[{mode}]", result)                                    # 지표 평균을 화면에 출력
result.to_pandas().to_csv(f"eval_{mode}.csv", index=False)    # 문항별 상세 점수를 CSV로 저장 → 구성 간 비교

실행: uv run python evaluate.py baseline → hybrid → rerank 순서로 세 번.

💡 팁 — RAGAS는 버전을 많이 탑니다

evaluate()의 인자와 데이터 형식이 버전마다 다를 수 있어요. 컬럼 이름은 question · answer · contexts · ground_truth가 기본이고, 형식 에러가 나면 설치된 RAGAS 문서의 "EvaluationDataset" 예시에 맞춰 records만 바꾸면 됩니다. 설치된 버전은 uv run python -c "import ragas; print(ragas.__version__)"로 확인하세요.

실행하면 DeprecationWarning이 여럿 뜰 수 있습니다 — ragas.metrics의 지표들은 앞으로 ragas.metrics.collections로, LangchainLLMWrapper는 llm_factory로 옮겨간다는 안내예요. 지금은 그대로 동작하니 무시해도 되고, 경고문에 적힌 새 경로가 곧 다음 버전의 정답입니다.
