3-4. 응용 아키텍처 패턴 — Orchestrator-Worker

실습 노트북: 2-2.ipynb  ·  대상 범위: 응용 아키텍처 패턴 두 번째 — Orchestrator-Worker  ·  난이도: 🟡 중급

지금까지의 그래프는 노드가 몇 개인지 코드를 쓰는 순간 이미 정해져 있었습니다. Orchestrator-Worker는 그 전제를 깹니다 — 일감을 받아본 다음에야, 실행 중에, 작업자를 몇 명 만들지 결정합니다. 실습으로는 주제 하나를 던지면 목차를 스스로 짜고, 그 목차 수만큼 집필자를 뽑아 보고서를 완성하는 서비스를 만듭니다.

이 장에서 배우는 것

새 문법은 딱 하나, Send API입니다. 나머지는 전부 이미 배운 것들입니다 — add_conditional_edges·with_structured_output(Routing), Annotated + 리듀서(Parallelization). 진짜 관문은 문법이 아니라 State 설계입니다 — 처음으로 State를 두 개 만듭니다. 전원이 함께 보는 공책 하나와 작업자 한 명에게만 건네는 쪽지 하나.

이 패턴을 지금 배우는 이유

2026년 1월 테슬라 어닝콜에서 일론 머스크는 자사 Grok 모델로 "오케스트레이터"를 만들어 공장 신설 같은 주요 의사결정에 활용하겠다고 말했습니다. 기업들이 언어 모델로 실제로 만들고 있는 것이 바로 이 구조이고, 오늘 배울 패턴이 그 오케스트레이션의 가장 기본형입니다.

1. Orchestrator-Worker — 지휘자가 악단을 그 자리에서 꾸린다

한 문장 정의 — "지휘자가 동적으로 작업자의 수와 역할을 계획하고 생성하는 시스템." 슬라이드는 더 짧게 적습니다. Parallelization + Dynamic.

병렬 처리와 딱 하나 다른 점 — "누가 워커를 만들었나"

Parallelization에서는 워커 셋을 개발자가 add_node로 미리 못 박아 두었습니다. Orchestrator-Worker에서는 그 숫자를 맨 위 노드가 실행 중에 결정합니다 — 일감을 보고 필요한 수만큼 워커를 그 자리에서 만들어 역할을 배분합니다.

구분ParallelizationOrchestrator-Worker
워커 수를 정하는 주체개발자 (코드 작성 시점)LLM (실행 시점)
워커 수항상 고정 (3개면 늘 3개)매 실행마다 달라짐 (3개, 5개, 100개…)
각 워커의 역할함수마다 하드코딩실행 중에 배분받음
노드 등록add_node ×3add_node ×1 (복제되어 실행됨)
엣지add_edge ×3Send 객체 리스트
맨 위 노드없음 (START에서 바로 갈라짐)Orchestrator — 계획 수립 담당
🔍 비유 — 정규직 3명 vs 프로젝트마다 꾸리는 팀

Parallelization은 정규직 3명이 늘 자리에 앉아 있는 회사입니다. 일이 작으면 놀고, 크면 셋이서 밤을 새웁니다. Orchestrator-Worker는 프로젝트가 들어올 때마다 팀을 새로 꾸리는 회사입니다. 팀장이 일감을 훑어보고 "이번 건은 네 명"이라 판단해 그 자리에서 뽑고 파트를 나눠줍니다. 일이 끝나면 팀은 해산합니다.

언제 쓰는가 — "몇 명이 필요한지 개발자가 알 수 없을 때"

판단 기준은 딱 하나 — 들어올 일감의 크기나 범위를 사전에 알 수 있는가? 알 수 있으면 Parallelization으로 충분하고, 모르면 이 패턴이 답입니다.

  • ① 작업량을 사용자가 정하는 경우 — "첨부한 파일을 전부 마이그레이션해줘." 오케스트레이터가 첨부 목록을 세어보고 그 수만큼 워커를 만들면 끝입니다.
  • ② 심층 조사(Deep Research) — ChatGPT·Gemini·Perplexity의 딥 리서치 모드가 이 구조입니다. 질문이 단순하면 조사원이 적게, 복잡하면 많이 붙습니다.
  • ③ 긴 문서 작성 — 언어 모델은 한 번에 다룰 수 있는 분량에 한계가 있습니다. 워커 10명이 각자 10쪽씩 쓰면 각 워커는 자기 몫의 컨텍스트만 쓰면 되죠. 모델의 한계를 구조로 우회하는 것 — 슬라이드의 "컨텍스트 윈도우 한계 극복"이 이 뜻입니다.
⚠️ 워커 수에 상한을 걸어두세요

워커 수를 모델에게 맡긴다는 건 비용과 시간도 모델에게 맡긴다는 뜻입니다. 제어는 프롬프트 한 줄이면 됩니다 — "3개 섹션 이내로 구성해." 실습 코드에도 이 제한이 들어가 있습니다.

2. 기획 — 보고서 생성 서비스

만들 것은 보고서 작성 서비스입니다. "자율주행에 대해 보고서를 써줘"처럼 주제 하나만 던지면, 목차를 짜고 → 목차 수만큼 집필자를 뽑아 동시에 쓰게 하고 → 하나로 엮어서 돌려줍니다. Chaining으로 쓴 짧은 글과 달리, 파트를 쪼개 각자 쓰게 하면 훨씬 깊고 긴 글이 나옵니다. (기획 3단계 방법론은 2강 2번 문서 참고.)

1요구사항

주제 하나로 고도화된 보고서 생성

2그래프 구성

지휘자 1 + 워커 N + 병합 1

3State 설계

공용 공책 1 + 쪽지 1

기획 2 · 그래프 구성 — 노드는 셋, 그런데 워커는 N명

💡 그림에 worker_node가 하나뿐인 게 정상입니다

워커가 셋 만들어져도 등록한 노드는 하나라 그림에는 상자 하나로만 그려집니다. 실행될 때 그 하나가 N벌 복제되어 동시에 돌아갈 뿐입니다. "설계도에는 한 명, 현장에는 N명."

기획 3 · State 설계 — 공책 한 권과 쪽지 여러 장

여기가 이 장에서 제일 헷갈리는 대목입니다. 지금까지는 모든 노드가 같은 공책(State 하나)을 돌려봤지만, 이번엔 워커에게 공용 공책을 통째로 주지 않고 "너는 2장 담당, 이런 내용을 써라"라고 적힌 쪽지 한 장만 건넵니다. 이유는 둘입니다 — ① 메모리: 워커가 100명 생겼을 때 전체 State를 100벌 복사할 이유가 없습니다. ② 독립성: 2장을 쓰는 사람이 3장 내용을 알 필요가 없습니다. 자기 파트만 알면 됩니다.

🔍 비유 — 외주 작가에게 원고 뭉치 전체를 보내지는 않는다

외주 작가 열 명에게 챕터를 하나씩 맡길 때, 전체 원고를 복사해서 보내지 않죠. "3장 담당, 분량 5쪽, 이런 내용을 다뤄주세요" — A4 한 장짜리 의뢰서를 보냅니다. 대신 완성된 원고는 전부 편집부의 한 폴더로 모입니다. 그게 공용 State고, 의뢰서가 쪽지 State입니다. 내려갈 땐 쪽지, 올라올 땐 공책 — 이 비대칭이 핵심입니다.

클래스 4개의 관계도 — 그림 한 장으로

클래스정체역할
Section pydantic 스키마 작업 지시서 한 장의 양식. name(담당 목차 제목) + description(다룰 내용)
Plan pydantic 스키마 Section을 리스트로 담는 그릇. 오케스트레이터의 답안지로 쓰임
ReportState TypedDict (공용 State) 모두가 함께 보는 공책. 주제 · 목차 · 완성 원고들 · 최종 보고서
WorkerState TypedDict (쪽지 State) 워커 한 명에게만 건네는 쪽지. Section 하나만 들어 있음
💡 한 문장으로 관통하기

ReportState의 sections 리스트에서 원소 하나를 떼어 WorkerState의 section에 넣어주는 것 — 이 그래프에서 벌어지는 일의 전부입니다. 워커 수 = sections 리스트의 길이이고, 그 리스트를 채우는 건 오케스트레이터 안의 언어 모델입니다. "모델이 리스트 길이를 정한다 = 모델이 노드 개수를 정한다" — 이 연결고리가 이 패턴의 심장입니다.

STEP 1. Model 정의

순서는 늘 같습니다 — ①모델 → ②State → ③Node → ④그래프 → ⑤실행.

📥 코드
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END
from typing import TypedDict
from pydantic import BaseModel, Field

model = init_chat_model("gpt-5-nano")

모델은 하나만 만듭니다. 지휘자·워커·편집자 전부 이 모델을 공유하고, 역할은 프롬프트로 나눕니다. (지휘자만 잠시 뒤 답안지를 물린 버전으로 한 번 더 가공합니다.)

STEP 2. State 정의 — 네 개의 클래스를 순서대로

ReportState와 WorkerState 둘 다 Section을 필요로 하므로 Section부터 씁니다.

① Section — 작업 지시서 한 장의 양식

📥 코드
from typing import List

# 1. 데이터 모델 정의 (Plan & Section)
# 팀장(Orchestrator)이 짤 계획표의 양식
class Section(BaseModel):
    name: str = Field(description='목차의 제목')
    description: str = Field(description='이 섹션에서 다뤄야 할 핵심 내용')

워커는 이 지시서를 받아 "내 담당은 name, 다룰 내용은 description" 두 줄만 보고 자기 파트를 씁니다.

📤 실제로 채워지면 이런 모양
Section(name='섹션 1. 생성형 AI의 현황과 핵심 기술',
        description='최근 상용화 동향, 트랜스포머 기반 LLM과 확산 모델, RAG·멀티모달 ...')

Section(name='섹션 2. 사회경제적 영향과 정책·윤리',
        description='노동시장 변화, 산업생태계 재편, 프라이버시·보안, 규제와 거버넌스 ...')
⚠️ Field(description=...)은 주석이 아닙니다

Routing에서 강조했듯 이 문장은 모델에게 그대로 전달되어 판단 근거가 됩니다. 목차의 결이 마음에 안 들면 모델을 바꾸기 전에 이 문장부터 손보세요. 예: "다른 섹션과 내용이 겹치지 않도록 범위를 명확히 적을 것"을 추가하면 워커들끼리 같은 말을 반복하는 문제가 눈에 띄게 줄어듭니다.

② ReportState — 모두가 함께 보는 공책

📥 코드
import operator
from typing import Annotated

# 2. State 정의 (Reducer 필수!)
class ReportState(TypedDict):
    topic: str
    sections: List[Section]
    completed_sections: Annotated[List[str], operator.add]
    final_report: str
필드누가 쓰나누가 읽나왜 필요한가
topic 사용자 (invoke 입력) orchestrator_node 무슨 주제로 목차를 짤지
sections orchestrator_node assign_workers 이 리스트의 길이가 곧 워커 수
completed_sections 워커 N명 전원 synthesizer_node 완성된 원고 조각이 쌓이는 자리
final_report synthesizer_node 사용자 (최종 반환) 하나로 엮인 최종 보고서

🔑 Annotated[List[str], operator.add] — 왜 이 한 칸만 특별한가

나머지 세 칸은 한 노드가 한 번만 채우지만, completed_sections는 워커 N명이 동시에 쓰려고 달려듭니다. LangGraph의 기본 동작은 덮어쓰기라 리듀서 없이 여러 노드가 같은 칸에 쓰면 에러가 납니다 — 동시 쓰기와 리듀서 충돌은 Parallelization 문서에서 자세히 다뤘습니다.

💥 리듀서를 빼먹으면
InvalidUpdateError: At key 'completed_sections': Can receive only one value per step.
Use an Annotated key to handle multiple values.
💡 2강의 add_messages와 정확히 같은 원리입니다

operator.add는 리스트에 쓰면 [1] + [2] = [1, 2], 즉 이어붙이기입니다. 2강의 messages: Annotated[list, add_messages]와 완전히 같은 자리에 다른 함수를 끼운 것 — add_messages는 메시지 전용(ID 기반 병합 포함), operator.add는 일반 리스트용 범용 이어붙이기입니다.

③ WorkerState — 워커에게 건네는 쪽지

📥 코드
# Worker에게 전달할 별도의 State (작업 지시서)
class WorkerState(TypedDict):
    section: Section

이게 전부입니다. 워커는 topic도, 다른 워커가 뭘 쓰는지도 모릅니다. 오직 자기 지시서 한 장만 보고 일합니다.

⚠️ 워커 노드의 타입 힌트를 ReportState로 쓰면 안 됩니다

워커에게 실제로 들어오는 건 {'section': ...} 딕셔너리 하나라 state["topic"]을 꺼내면 없습니다. 반대로 지휘자와 병합 노드는 반드시 ReportState여야 합니다. 노드마다 보는 State가 다르다는 게 이 패턴의 특이점입니다.

④ Plan — 지휘자에게 쥐여줄 답안지

마지막 조각은 State가 아니라 스키마입니다. 오케스트레이터에게 목차를 그냥 물으면 줄글로 답해서 파싱 지옥이 열립니다. Routing에서 라우터에게 RouteDecision을 물렸던 Structured Outputs 그대로이고, 다른 점은 답이 문자열 하나가 아니라 Section 객체의 리스트라는 것뿐입니다.

📥 코드
class Plan(BaseModel):
    sections: List[Section] = Field(description="보고서 작성을 위한 목차 리스트")

planner_llm = model.with_structured_output(Plan)
📤 planner_llm.invoke(...)의 반환값 모양
Plan(
  sections=[
    Section(name='섹션 1. 생성형 AI의 현황과 핵심 기술', description='...'),
    Section(name='섹션 2. 사회경제적 영향과 정책·윤리',   description='...'),
    Section(name='섹션 3. 미래 전망과 전략',              description='...')
  ]
)
💡 Routing의 Literal과 비교하면 차이가 선명합니다

Routing의 Literal은 "넷 중 하나만 골라"(선택지 고정), 여기의 List[Section]은 "이 양식에 맞게, 몇 개든 적어"(모양만 고정, 개수는 개방)입니다. 이 "개수를 열어둠"이 바로 Dynamic의 정체입니다 — OMR 카드가 아니라 행을 얼마든지 추가할 수 있는 표 양식이고, 그 행 수만큼 뒤에서 사람이 채용됩니다.

STEP 3. Node 정의 — 지휘자 · 작업자 · 편집자

노드는 셋 — 계획을 짜는 지휘자, 실제로 쓰는 작업자, 합치는 편집자. 계약은 여전히 같습니다: state를 받아 딕셔너리를 반환한다.

① orchestrator_node — 목차만 짜고 손을 떼는 노드

📥 코드
# [Orchestrator] 팀장 노드: 계획 수립
def orchestrator_node(state: ReportState):
    topic = state["topic"]
    print(f"\n--- [Orchestrator] '{topic}' 보고서 계획 수립 중 ---")

    # 보고서 목차를 생성 (최대 3개로 제한하여 속도 조절)
    plan = planner_llm.invoke(f"'{topic}'에 대한 보고서 목차를 짜줘. 3개 섹션 이내로 구성해.")

    print(f"생성된 계획: {[s.name for s in plan.sections]}")
    return {"sections": plan.sections}
  • 3개 섹션 이내로 구성해 — 워커 수를 통제하는 유일한 장치. 실습은 속도·비용 때문에 3개로 묶었고, 늘리고 싶으면 이 문자열 하나만 바꾸면 됩니다.
  • plan.sections — 대괄호가 아니라 점(.) — 반환값이 AIMessage가 아니라 Plan 객체이기 때문입니다. State는 딕셔너리라 대괄호, 스키마는 객체라 점.
💡 이 return 한 줄이 노드 개수를 결정합니다

return {"sections": plan.sections} — 여기 담긴 리스트의 길이가 곧 잠시 뒤 생성될 워커의 수입니다. 모델의 판단이 그래프의 모양으로 번역되는 지점이 정확히 여기입니다.

② worker_node — 여러 벌 복제되어 동시에 도는 노드

📥 코드
# [Worker] 팀원 노드: 섹션 집필
# 이 노드는 여러 개가 복제되어 동시에 실행
def worker_node(state: WorkerState):
    section = state["section"]
    print(f"   --- [Worker] 집필 중: {section.name} ---")

    prompt = f"""
    다음 섹션에 대한 내용을 짧게 작성해줘.
    제목: {section.name}
    내용 가이드: {section.description}
    """

    response = model.invoke(prompt)
    content = f"## {section.name} \n {response.content}"
    return {'completed_sections': [content]}
  • 입력이 WorkerState다 — state["section"]으로 지시서 한 장을 꺼내 프롬프트에 끼웁니다. 워커가 아는 정보는 이게 전부입니다.
  • 결과 앞에 제목을 붙인다 — 세 워커의 결과물이 한 리스트에 뒤섞여 쌓이므로, 마크다운 제목을 미리 달아 어느 섹션 것인지 라벨링해 둡니다.
  • 반드시 리스트로 감싸 반환한다 — 리듀서가 기존리스트 + 반환값을 계산하므로 문자열을 그냥 주면 list + str이 되어 TypeError가 납니다. "리스트에 이어붙일 거니까 나도 리스트로 준다." [content]의 대괄호는 "묶음 단위로 제출"하라는 접수 규칙의 클립인 셈입니다.

③ synthesizer_node — 조각을 하나로 엮는 편집자

📥 코드
# [Synthesizer] 편집자 노드: 취합
def synthesizer_node(state: ReportState):
    print("\n--- [Synthesizer] 모든 원고 취합 및 최종 편집 ---")

    # 리스트에 모인 조각글들을 하나로 합침
    completed = state["completed_sections"]
    final_report = "\n".join(completed)

    return {"final_report": final_report}

Parallelization의 Aggregator와 같은 역할입니다 — 워커 전원이 끝날 때까지 기다렸다가 실행되며, 이 대기는 LangGraph가 알아서 해줍니다.

⚠️ 지금 이 노드는 "물리적 결합"입니다

join은 글 세 덩어리를 나란히 붙일 뿐 — 서론도 결론도 없고 연결도 끊깁니다. "화학적 결합"으로 바꾸는 방법을 심화 파트에서 다루며, 바꿀 곳은 이 노드 하나뿐입니다.

STEP 4. 그래프 생성 — 엣지를 몇 개 그어야 할까?

🚫 add_edge를 쓸 수가 없다

workflow.add_edge("orchestrator_node", ???) — 워커가 몇 명일지도 모르고, 각자에게 어떤 Section을 줘야 할지도 모릅니다. 둘 다 실행해봐야 아는 값이라 코드를 쓰는 시점에는 답이 존재하지 않습니다.

필요한 도구는 ①노드를 리스트 길이만큼 만들고 ②각자에게 다른 데이터를 꽂아주는 두 가지 일을 동시에 해야 합니다. 그 도구가 Send입니다.

🔑 Send API — 이름표와 내용물이 적힌 송장

📥 문법
Send("보낼_노드_이름", {전달할_데이터_딕셔너리})
인자값뜻
1. 노드 이름'worker_node'이 노드를 하나 실행시켜라
2. 데이터{'section': section}그 노드의 State는 이걸로 채워라

Send 객체를 리스트로 3개 반환하면 워커가 3개, 5개 반환하면 5개 돕니다. 개수 제어와 데이터 배분이 한 번에 끝납니다.

🔍 비유 — 택배 송장

Send는 택배 송장 한 장입니다. 받는 사람: worker_node, 내용물: 2번 섹션 지시서. 송장을 세 장 쓰면 택배가 세 개 나가고, 각 상자에는 서로 다른 내용물이 들어갑니다. 기사에게 "몇 개 배송할지"와 "뭘 담을지"를 따로 말할 필요가 없죠 — 송장에 둘 다 적혀 있으니까요.

💡 두 번째 인자는 쪽지 State의 양식과 맞아야 합니다

{'section': section}의 키가 'section'인 이유는 WorkerState의 필드 이름이 section이기 때문입니다. 오타를 내거나 Send('worker_node', section)처럼 객체를 그냥 넘기면 워커 안의 state["section"]이 터집니다. Send의 두 번째 인자 = 그 노드가 받을 State의 딕셔너리. 공식 문서: langgraph.types.Send

assign_workers — 송장을 리스트로 찍어내는 함수

📥 코드
from langgraph.types import Send

# 5. 동적 라우팅 로직 (Map: 1 -> N)
# 일반적인 edge가 아니라, 리스트 개수만큼 노드를 생성해서 뿌려주는 역할
def assign_workers(state: ReportState):
    sections = state['sections']

    return [Send('worker_node', {'section': section}) for section in sections]

풀어서 읽으면 — "공용 State의 sections 리스트를 하나씩 돌면서, worker_node에게 그 섹션을 담은 송장을 한 장씩 쓴다."

📤 실제로 반환되는 값 (섹션이 3개일 때)
[Send('worker_node', {'section': Section(name='섹션 1. 생성형 AI의 현황과 핵심 기술', ...)}),
 Send('worker_node', {'section': Section(name='섹션 2. 사회경제적 영향과 정책·윤리',   ...)}),
 Send('worker_node', {'section': Section(name='섹션 3. 미래 전망과 전략',              ...)})]

→ worker_node 3개가 동시에 실행됨. 각자 다른 section을 들고.
⚠️ Routing의 조건부 함수와 반환 타입이 다릅니다

같은 add_conditional_edges에 들어가지만 반환값의 성격이 완전히 다릅니다.

구분Routing의 route_to_expert여기의 assign_workers
반환값'billing_expert' (문자열)[Send(...), Send(...)] (객체 리스트)
의미이미 있는 노드 중 하나를 고름노드를 N개 만들어냄
데이터 전달공용 State를 그대로 봄각자에게 다른 값을 꽂아줌
실행 수항상 1개리스트 길이만큼

"고르기"에서 "만들어내기"로 바뀐 것 — 이게 Routing과 Orchestrator-Worker의 결정적 차이입니다.

그래프 조립 — 노드 3개, 엣지 4줄

📥 코드
# 6. 그래프 조립
workflow = StateGraph(ReportState)

workflow.add_node('orchestrator_node', orchestrator_node)
workflow.add_node('worker_node', worker_node)
workflow.add_node('synthesizer_node', synthesizer_node)

# 6-1. 시작 -> 팀장
workflow.add_edge(START, 'orchestrator_node')

# 6-2. 팀장 -> (Map) -> 팀원들 (Conditional Edge)
workflow.add_conditional_edges(
    'orchestrator_node',
    assign_workers,
    ['worker_node']
)

# 6-3. 팀원들 -> (Reduce) -> 편집자
workflow.add_edge('worker_node', 'synthesizer_node')

# 6-4. 편집자 -> 종료
workflow.add_edge('synthesizer_node', END)

app = workflow.compile()
  • StateGraph(ReportState) — 그래프에 등록하는 State는 공용 하나뿐입니다. WorkerState는 Send가 워커에게 직접 꽂아주는 임시 데이터라 등록하지 않습니다.
  • 세 번째 인자 ['worker_node'] — 생략해도 실행은 되지만, LangGraph는 명시하지 않은 경로를 그래프 그림에 그려주지 않습니다. 적어두면 점선이 제대로 그려지고 오타도 컴파일 시점에 잡힙니다.
  • worker_node → synthesizer_node는 그냥 add_edge 한 줄 — 몇 벌이 복제됐든 전부 여기로 모이고, LangGraph가 전원이 끝날 때까지 기다려줍니다.

상자가 셋뿐 — 복잡함이 그림이 아니라 실행 시점으로 옮겨간 것입니다. 그래서 이 패턴은 그림보다 로그를 봐야 하고, 노드마다 print를 심어둔 이유가 여기 있습니다.

💡 워커는 공책을 읽지 못하지만, 공책에 쓸 수는 있습니다

워커에게 들어가는 것은 쪽지(WorkerState)지만, 워커가 반환하는 값은 공용 공책(ReportState)의 칸으로 들어갑니다. 내려갈 땐 쪽지, 올라올 땐 공책 — 이 비대칭이 메모리를 아끼면서도 결과를 모을 수 있게 하는 설계입니다.

심화 — 편집자를 진짜 편집자로 만들기 (화학적 결합)

지금 final_report는 섹션 셋이 그냥 나란히 붙어 있을 뿐입니다 — 서론도 결론도 없고, 각자 다른 사람이 쓴 티가 그대로 납니다. 해법은 간단합니다. 편집자에게도 언어 모델을 쥐여주고 "이 원고들을 하나의 보고서로 다시 써줘"라고 시키는 겁니다.

📥 코드 — synthesizer_node만 교체
# [Synthesizer] 편집자 노드: 단순 취합이 아니라 '화학적 결합'을 수행
def synthesizer_node(state: ReportState):
    topic = state["topic"]
    completed_docs = state["completed_sections"]

    print(f"\n--- [Synthesizer] 원고 {len(completed_docs)}건 도착. 최종 편집 시작 ---")

    # 1. 일단 텍스트 덩어리로 병합
    raw_content = "\n\n".join(completed_docs)

    # 2. LLM에게 '전문 편집자' 역할 부여
    prompt = f"""
    당신은 전문 리포트 편집자입니다.
    다음은 '{topic}'에 대해 여러 작가가 나누어 쓴 원고들입니다.

    이 초안들을 바탕으로 **하나의 자연스럽고 전문적인 보고서**로 다시 작성해주세요.

    [지시사항]
    1. 각 섹션의 연결이 매끄러워야 합니다.
    2. 전체를 아우르는 '서론'과 '결론'을 추가해주세요.
    3. 마크다운(Markdown) 형식을 사용하여 가독성을 높여주세요.

    [원고 내용]
    {raw_content}
    """

    # 최종 생성을 위한 LLM 호출
    message = model.invoke(prompt)

    return {'final_report': message.content}

🔍 비유 — 스테이플러 vs 편집장

join 버전은 스테이플러입니다. 원고 세 뭉치를 탁 찍어서 넘깁니다. LLM 버전은 편집장입니다. 원고를 전부 읽고 앞에 서론을 붙이고, 문체를 맞추고, 중복을 걷어내고, 뒤에 결론을 답니다. 같은 재료로 전혀 다른 완성도의 결과물이 나옵니다.

노드만 갈아끼웠으니 그래프를 다시 조립하고 컴파일한 뒤 같은 주제로 실행해봅니다.

📤 실행 로그 — 두 번째 실행
--- [Orchestrator] '생성형 AI의 미래' 보고서 계획 수립 중 ---
생성된 계획: ['1. 기술 진화와 생태계', '2. 사회경제적 영향과 도전', '3. 미래 전망과 전략적 시사점']
   --- [Worker] 집필 중: 1. 기술 진화와 생태계 ---
   --- [Worker] 집필 중: 2. 사회경제적 영향과 도전 ---
   --- [Worker] 집필 중: 3. 미래 전망과 전략적 시사점 ---

--- [Synthesizer] 원고 3건 도착. 최종 편집 시작 ---
⚠️ 같은 주제인데 목차가 달라졌습니다 — 버그가 아닙니다

계획을 세우는 주체가 언어 모델이니 매 실행마다 결과가 달라지는 게 정상입니다. 동적이라는 건 곧 예측하기 어렵다는 뜻이기도 하죠. 실무에서 결과를 일정하게 유지해야 한다면 목차의 골격을 프롬프트에 못 박거나 ("반드시 서론·본론·결론 구성으로") 아예 Parallelization으로 고정하는 편이 맞습니다. 유연함과 안정성은 맞바꾸는 관계입니다.

💡 이 구조가 한 번에 쓰는 것보다 나은 이유

같은 모델에게 한 번만 물으면 한 페이지짜리 개괄이 나옵니다. 이 그래프는 같은 모델을 다섯 번 부릅니다(계획 1 + 집필 3 + 편집 1). 각 호출은 좁은 범위에만 집중하고, 마지막에 전체를 다듬는 호출이 한 번 더 들어가죠. 모델을 바꾸지 않고 구조만으로 품질을 끌어올린 것입니다.

마지막 개념 정리 — Workflow와 Agent는 뭐가 다른가

3강을 마무리하기 전에 용어 하나를 정리합니다. 워크플로우(Workflow)와 에이전트(Agent) — 지금까지 거의 같은 뜻으로 섞어 썼지만, 공식 문서는 이 둘을 명확히 구분합니다.

구분 기준은 딱 하나 — "다음에 어디로 갈지를 누가 정하는가?"

구분WorkflowAgent
경로를 정하는 주체개발자 (코드에 미리 명시)언어 모델 (실행 중 스스로 판단)
코드에 나타나는 모습add_edge로 길이 다 그려짐엣지를 안 그린 구간이 있음
예측 가능성높음 정해진 길로만 감낮음 상황 따라 바뀜
적합한 업무절차가 명확한 일 (번역, 정형 리포트)문제·해법이 불확실한 일
도구 사용언제 뭘 쓸지 미리 정해둠스스로 판단해서 호출
💡 그럼 오늘 만든 건 Workflow일까요, Agent일까요?

Workflow입니다. 워커 수는 모델이 정했지만, 경로 자체(오케스트레이터 → 워커 → 편집자 → END)는 우리가 다 그려뒀고 실행할 때마다 절대 안 바뀝니다. 공식 문서 설명도 "LLM directs control flow through predefined code paths" — 모델이 흐름에 관여하긴 하지만 어디까지나 미리 정해둔 길 안에서라는 뜻입니다.

🔍 비유 — 정해진 노선의 버스 vs 목적지만 아는 택시

Workflow는 버스입니다. 정류장 순서가 노선도에 다 적혀 있고, 승객이 몇 명 타든 같은 길로 갑니다. 오늘 만든 그래프는 정원이 유동적인 버스인 셈이에요 — 그래도 노선은 고정입니다.

Agent는 택시입니다. 목적지만 말하면 기사가 막히는 길을 피해가며 경로를 그때그때 정합니다. 2강에서 만든 Tool 호출 Agent가 정확히 이랬습니다 — 도구를 부를지 말지를 우리가 add_edge로 정해준 적이 없었죠.

어느 쪽이 더 좋은 기술인가 — 그런 건 없습니다

Agent가 더 발전된 형태처럼 들리지만, 제어권을 개발자가 쥐고 있는 건 단점이 아니라 장점이기도 합니다 — 예측 가능하고, 안전하고, 디버깅이 쉽습니다. 절차가 딱 정해진 업무에 Agent를 쓰면 불필요한 변동성만 얻고, 어떤 입력이 들어올지 모르는 상황에서는 Agent의 유연함이 필요합니다. 업무의 성격에 맞춰 고르는 것이 답입니다.

💡 실무의 정답은 대개 "섞기"입니다

안정성이 중요한 구간은 Workflow로 못 박고, 유연함이 필요한 구간만 Agent로 열어둡니다. 예 — ①입력 검증(Workflow) → ②Agent가 알아서 자료 수집 → ③정해진 양식으로 보고서 생성(Workflow) → ④승인 요청 발송(Workflow). "어디까지 모델에게 맡길 것인가"를 구간별로 정하는 것이 설계자의 일입니다.

3강에서 배운 다섯 패턴 한자리에

패턴한 줄 요약핵심 문법노드 수이럴 때
Prompt Chaining 단계별로 차례차례 add_edge 고정 초안 → 검토 → 수정
Parallelization 독립적인 일을 동시에 add_edge ×N + 리듀서 고정 다수결 투표, 관점 다각화
Routing 보고 나서 골라서 add_conditional_edges
with_structured_output		 고정 (1개만 실행) 상담 챗봇, 모델 등급 분기
Evaluator-Optimizer 퇴짜 나면 되돌아가서 add_conditional_edges (루프) 고정 (반복 실행) 품질 기준이 명확한 생성물
Orchestrator-Worker 일감을 보고 그때그때 뽑아서 Send + 리듀서
with_structured_output		 가변 실행 중 결정 딥 리서치, 긴 문서, 일괄 처리
💡 패턴 고르는 질문 세 개

Q1. 작업자들이 서로의 결과물을 봐야 하는가? → 그렇다면 Chaining

Q2. 결과를 검사해서 다시 시켜야 하는가? → 그렇다면 Evaluator-Optimizer

Q3. 작업자가 몇 명 필요한지 코드 짤 때 알 수 있는가?
→ 안다 + 전부 필요 = Parallelization
→ 안다 + 골라 씀 = Routing
→ 모른다 = Orchestrator-Worker

실무 그래프는 이 다섯을 구간마다 섞어서 씁니다. ①라우팅으로 담당 결정 → ②그 담당이 오케스트레이터로 자료를 동적 수집 → ③평가자가 검수하고 미달이면 재작성처럼요.

전체 코드 한눈에 보기

# ══ STEP 1. Model ═════════════════════════════════════
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, List, Annotated
from pydantic import BaseModel, Field
import operator

model = init_chat_model("gpt-5-nano")

# ══ STEP 2. State ═════════════════════════════════════
# ① 작업 지시서 한 장의 양식
class Section(BaseModel):
    name: str = Field(description='목차의 제목')
    description: str = Field(description='이 섹션에서 다뤄야 할 핵심 내용')

# ② 공용 공책 — 모든 노드가 함께 본다
class ReportState(TypedDict):
    topic: str
    sections: List[Section]                                    # ★ 이 리스트 길이 = 워커 수
    completed_sections: Annotated[List[str], operator.add]     # ★ 리듀서 필수 (동시 쓰기)
    final_report: str

# ③ 쪽지 — 워커 한 명에게만 건넨다
class WorkerState(TypedDict):
    section: Section

# ④ 지휘자에게 물릴 답안지
class Plan(BaseModel):
    sections: List[Section] = Field(description="보고서 작성을 위한 목차 리스트")

planner_llm = model.with_structured_output(Plan)               # ★ 목차를 리스트로 뱉게 강제

# ══ STEP 3. Node ══════════════════════════════════════
# [Orchestrator] 계획만 세우고 손을 뗀다
def orchestrator_node(state: ReportState):
    topic = state["topic"]
    print(f"\n--- [Orchestrator] '{topic}' 보고서 계획 수립 중 ---")
    plan = planner_llm.invoke(f"'{topic}'에 대한 보고서 목차를 짜줘. 3개 섹션 이내로 구성해.")
    print(f"생성된 계획: {[s.name for s in plan.sections]}")
    return {"sections": plan.sections}                          # ★ plan.sections — 점(.)으로 접근

# [Worker] 여러 벌 복제되어 동시에 실행 — 입력이 WorkerState임에 주의
def worker_node(state: WorkerState):
    section = state["section"]
    print(f"   --- [Worker] 집필 중: {section.name} ---")

    prompt = f"""
    다음 섹션에 대한 내용을 짧게 작성해줘.
    제목: {section.name}
    내용 가이드: {section.description}
    """

    response = model.invoke(prompt)
    content = f"## {section.name} \n {response.content}"        # ★ 제목을 앞에 붙여 라벨링
    return {'completed_sections': [content]}                    # ★ 반드시 리스트로 감싸기

# [Synthesizer] 전원이 끝날 때까지 기다렸다가 합친다 (화학적 결합 버전)
def synthesizer_node(state: ReportState):
    topic = state["topic"]
    completed_docs = state["completed_sections"]
    print(f"\n--- [Synthesizer] 원고 {len(completed_docs)}건 도착. 최종 편집 시작 ---")

    raw_content = "\n\n".join(completed_docs)

    prompt = f"""
    당신은 전문 리포트 편집자입니다.
    다음은 '{topic}'에 대해 여러 작가가 나누어 쓴 원고들입니다.

    이 초안들을 바탕으로 **하나의 자연스럽고 전문적인 보고서**로 다시 작성해주세요.

    [지시사항]
    1. 각 섹션의 연결이 매끄러워야 합니다.
    2. 전체를 아우르는 '서론'과 '결론'을 추가해주세요.
    3. 마크다운(Markdown) 형식을 사용하여 가독성을 높여주세요.

    [원고 내용]
    {raw_content}
    """

    message = model.invoke(prompt)
    return {'final_report': message.content}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.types import Send

# 동적 라우팅 (Map: 1 -> N) — 리스트 개수만큼 노드를 만들어 뿌린다
def assign_workers(state: ReportState):
    sections = state['sections']
    return [Send('worker_node', {'section': section}) for section in sections]

workflow = StateGraph(ReportState)                              # ★ 등록하는 State는 공용 하나뿐

workflow.add_node('orchestrator_node', orchestrator_node)
workflow.add_node('worker_node', worker_node)                   # ★ 노드는 1개만 등록
workflow.add_node('synthesizer_node', synthesizer_node)

workflow.add_edge(START, 'orchestrator_node')                   # 실선

workflow.add_conditional_edges(                                 # 점선 — Send로 N개 복제
    'orchestrator_node',
    assign_workers,
    ['worker_node']                                             # 생략 가능하지만 그림을 위해 명시
)

workflow.add_edge('worker_node', 'synthesizer_node')            # 실선 — 전원 도착까지 대기
workflow.add_edge('synthesizer_node', END)

app = workflow.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
result = app.invoke({"topic": "생성형 AI의 미래"})
print(result["final_report"])

자주 걸리는 함정 7가지

🕳️ Orchestrator-Worker에서 실제로 밟게 되는 지뢰

1. completed_sections에 리듀서를 안 붙인다

가장 먼저 만나는 에러입니다. 워커 셋이 같은 칸에 동시에 쓰는 순간 InvalidUpdateError. Annotated[List[str], operator.add] — "동시에 쓰는 칸에는 리듀서", 예외 없습니다.

2. 워커 노드에 ReportState를 쓴다

보기엔 멀쩡하지만 state["topic"]을 꺼내는 순간 KeyError — 워커에게 들어오는 건 Send가 꽂아준 section 하나뿐입니다. 워커만 WorkerState, 나머지 둘은 ReportState.

3. return {'completed_sections': content} — 대괄호를 빼먹는다

문자열을 그냥 반환하면 리스트 + 문자열 연산이 되어 TypeError. [content]로 감싸세요 — "리듀서가 이어붙일 대상과 같은 타입으로 준다"가 원칙입니다.

4. Send의 두 번째 인자를 객체로 넘긴다

Send('worker_node', section)은 틀립니다. 두 번째 인자는 그 노드가 받을 State 딕셔너리 — {'section': section}이 맞고, 키 이름은 WorkerState의 필드명과 정확히 일치해야 합니다.

5. plan["sections"]라고 쓴다

planner_llm.invoke()는 Plan 객체를 반환하므로 plan.sections가 맞습니다. State는 대괄호, 스키마 객체는 점(.) — Routing의 그 실수가 여기서도 반복됩니다.

6. 워커 수에 상한을 안 건다

프롬프트에서 "3개 섹션 이내로"를 빼면 목차가 15개 나올 수도 있고, 그러면 LLM 호출이 열일곱 번 일어납니다. 동적이라는 건 통제하지 않으면 폭주할 수 있다는 뜻 — 상한은 프롬프트 한 줄이면 됩니다.

7. add_conditional_edges의 세 번째 인자를 생략한다

실행은 되지만 컴파일 후 그림에서 오케스트레이터 다음이 끊겨 보입니다. ['worker_node']를 적어두면 그림도 정확해지고 오타도 미리 잡힙니다.

💡 디버깅 요령 — 오케스트레이터만 따로 돌려보세요

planner_llm.invoke("'주제'에 대한 보고서 목차를 짜줘. 3개 섹션 이내로 구성해.")만 단독으로 여러 번 호출해 목차 개수와 섹션 간 중복을 몇 초 만에 확인할 수 있습니다. 이 그래프의 품질은 사실상 이 한 줄이 결정합니다.

📚 한 장 정리

오늘의 핵심 한 문장

오케스트레이터가 만든 리스트의 길이가 곧 워커의 수가 되고, 그 리스트를 Send로 한 원소씩 떼어 뿌리면 코드에 없던 노드가 실행 중에 그만큼 생겨난다.

  • Orchestrator-Worker란 — Parallelization + Dynamic. 워커 수와 역할을 개발자가 아니라 LLM이 실행 중에 정한다.
  • 쓰는 신호 — 일감의 크기를 코드 짤 때 알 수 없을 때. 첨부 파일 일괄 처리 · 딥 리서치 · 긴 문서 작성. 컨텍스트 윈도우 한계도 우회된다.
  • State는 두 개 — 공용 공책 ReportState(결과가 모이는 곳)와 쪽지 WorkerState(Section 하나뿐). 내려갈 땐 쪽지, 올라올 땐 공책 — 이 비대칭이 메모리를 아낀다.
  • 클래스 네 개의 관계 — Plan(답안지) 안에 List[Section], 그게 ReportState.sections가 되고, 원소 하나가 WorkerState.section으로 떨어진다. Section이 허브다.
  • 리듀서는 필수 — completed_sections: Annotated[List[str], operator.add]. 워커 N명이 같은 칸에 동시에 쓰기 때문. 빼먹으면 InvalidUpdateError.
  • 이 장의 심장 — Send API — Send("노드이름", {"키": 값})을 리스트로 N개 반환하면 워커가 N개 돈다. Routing의 조건부 함수는 문자열(고르기), 여기는 Send 리스트(만들기). 두 번째 인자의 키는 쪽지 State의 필드명과 일치해야 한다.
  • 노드는 하나만 등록 — 실행 시점에 N벌 복제될 뿐. "설계도엔 한 명, 현장엔 N명."
  • Synthesizer는 두 가지 급 — join은 물리적 결합(스테이플러), LLM 호출은 화학적 결합(편집장). 고칠 곳은 이 노드 하나뿐.
  • Workflow vs Agent — 기준은 "다음 경로를 누가 정하는가". 개발자면 Workflow, 모델이면 Agent. 오늘 만든 건 Workflow(워커 수만 동적, 경로는 고정). 우열이 아니라 용도의 문제이고, 실무는 구간별로 섞어 쓴다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

출판사 편집회의를 떠올리세요. 기획자가 "자율주행 특집을 하자"고 던지면 편집장이 그 자리에서 목차를 짜고, 작가 세 명에게 의뢰서를 한 장씩 보냅니다. 작가들은 서로 누가 뭘 쓰는지 모른 채 각자 원고를 써서 편집부 폴더에 넣고, 마지막에 편집장이 서론과 결론을 붙여 한 권으로 묶습니다. 목차가 다섯 챕터였다면 작가는 다섯 명이 뽑혔을 겁니다 — 몇 명일지는 회의 전에 아무도 몰랐죠. 그 의뢰서 한 장이 Send이고, 편집부 폴더가 operator.add가 붙은 칸입니다.

3강을 마치며

기초 세 패턴(Chaining · Parallelization · Routing)에 이어 응용 두 패턴(Evaluator-Optimizer · Orchestrator-Worker)까지 끝났습니다. 실무의 그래프는 대부분 이 다섯을 이어 붙인 조합입니다 — 새 패턴을 외우기보다 "이 구간은 뭐가 맞을까"를 질문하는 습관이 훨씬 오래 갑니다.
