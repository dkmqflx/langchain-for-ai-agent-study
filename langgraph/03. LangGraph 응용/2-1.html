3-3. 응용 아키텍처 패턴 — Evaluator-Optimizer

실습 노트북: 2-1.ipynb  ·  대상 범위: 응용 아키텍처 패턴 첫 번째 — Evaluator-Optimizer  ·  난이도: 🟡 중급

지금까지의 그래프는 전부 앞으로만 흘렀습니다. 이번에 배울 Evaluator-Optimizer에서 처음으로 뒤로 가는 화살표가 등장합니다 — 결과물을 만들고, 다른 노드가 채점하고, 불합격이면 피드백을 들려 다시 돌려보내는 구조입니다. 실습으로는 신입 카피라이터가 광고 문구를 쓰고, 깐깐한 마케팅 팀장이 퇴짜를 놓는 서비스를 만듭니다.

이 장에서 배우는 것

새로운 문법은 하나도 없습니다. add_edge, add_conditional_edges, with_structured_output을 조합했을 때 지금까지 없던 루프(loop)라는 성질이 생기고, 루프가 생기는 순간 새로운 걱정거리가 따라옵니다 — "이 그래프, 안 끝나면 어떡하지?" 이 장의 절반은 그 걱정을 다루는 이야기입니다.

1. Evaluator-Optimizer — 만들고, 검사하고, 되돌린다

1Generator (생성자)

입력을 받아 결과물을 만든다

2Evaluator (평가자)

그 결과물을 채점한다

3분기

합격 → END / 불합격 → 다시 1번으로

왜 "Evaluator"만이 아니라 "Evaluator-Optimizer"인가

평가자가 퇴짜를 놓을 때 그냥 "다시 해와"가 아니라 "어디를 어떻게 고쳤으면 좋겠는지"를 함께 적어서 돌려보내기 때문입니다. 합격/불합격만 오면 생성자는 매번 운에 맡긴 재시도를 할 뿐이지만, 구체적인 지적이 오면 그걸 반영해 개선합니다 — 그래서 이름에 Optimizer가 붙었습니다.

🔍 비유 — "다시 써 와" vs 빨간펜

팀장이 "이거 아니야, 다시" 한마디만 하고 돌려주면 뭐가 문제인지 모른 채 감으로 다시 씁니다. 반면 "3페이지 그래프를 표로 바꾸고, 결론을 맨 앞으로 빼세요"라고 빨간펜으로 첨삭해서 돌려주면 두 번째 원고는 확실히 좋아집니다.

Evaluator-Optimizer의 핵심은 이 빨간펜입니다. 코드로는 State에 feedback 칸이 있느냐 없느냐의 차이일 뿐인데, 결과물이 좋아지는 속도가 완전히 달라집니다.

기초 패턴 세 개가 하나로 합쳐진 구조

필요한 재료는 앞에서 이미 배운 것들입니다 — Chaining(3-1장)과 Routing(3-2장), 그리고 새로 등장하는 성질이 Loop입니다.

그림에서 이 부분필요한 개념쓰는 문법
Generator → Evaluator Chaining add_edge
Evaluator → END 또는 Generator Routing add_conditional_edges
Rejected 화살표 (왔던 노드로 되돌아감) 🆕 Loop 새 문법 없음 — 조건부 엣지의 목적지를
이미 지나온 노드로 적으면 그게 루프
💡 루프에는 전용 문법이 없습니다 — 이 장의 첫 번째 깨달음

while이나 add_loop 같은 건 없습니다. 조건부 함수가 return "copywriter_node"처럼 이미 지나온 노드의 이름을 반환하는 한 줄이 전부입니다. 그래프에 "앞으로만 가야 한다"는 규칙이 애초에 없기 때문이죠.

편리한 만큼 위험합니다. 실수로 뒤를 가리키면 영원히 도는 그래프가 되는데, 문법적으로는 아무 잘못이 없어서 에러도 안 납니다.

언제 쓰는가 — 속도보다 품질이 우선일 때

이 패턴은 느리고 비쌉니다. 평가자를 하나 더 붙였고, 그 평가자가 몇 번이고 퇴짜를 놓을 수 있으니까요. 그럼에도 쓰는 이유는 하나 — 결과물이 확실히 좋아지기 때문입니다.

사례Generator가 하는 일Evaluator가 하는 일
코드 작성 – 유닛 테스트 – 루프 요구사항을 보고 코드를 짠다 테스트를 돌려본다. 실패하면 에러 메시지를 피드백으로 붙여 반려
번역 – 평가 – 루프 원문을 번역한다 원문과 대조해서 누락·오역·어색한 표현을 지적
데이터 생성 – 평가 – 루프 요청한 더미 데이터를 만든다 형식·개수·중복 등 조건 충족 여부를 검사

셋의 공통점은 "한 번에 잘 나올 확률이 낮고, 잘 됐는지 판단할 기준이 명확한 일"입니다. 테스트는 통과하거나 실패하고, 번역은 원문과 대조할 수 있고, 데이터는 조건을 만족하거나 안 합니다.

⚠️ 반대로, 이럴 땐 쓰지 마세요

"더 감동적인 시를 써줘"처럼 평가 기준을 말로 설명할 수 없는 일에는 평가자도 판단을 못 합니다. 루프가 돌긴 도는데 좋아지지는 않는, 시간과 돈만 태우는 그래프가 되죠. 판단법: "평가자에게 줄 채점 기준을 세 줄로 적을 수 있는가?" 못 적겠으면 Chaining으로 충분합니다.

특징 ① 최소 두 개의 인격이 필요하다

만드는 주체와 평가하는 주체를 반드시 분리해야 합니다.

🔍 비유 — 자기가 쓴 답안지를 자기가 채점하면

대부분 자기 답에 후한 점수를 줍니다. 방금 그렇게 쓴 논리로 다시 읽으니까 맞아 보이는 거죠. 언어 모델도 똑같아서, "방금 네가 쓴 글 괜찮아?"라고 물으면 대체로 괜찮다고 합니다. 그래서 평가자에게는 "당신은 깐깐한 마케팅 팀장입니다"처럼 아예 다른 사람인 것처럼 말을 겁니다. 모델은 같은 gpt-5-nano 하나지만 프롬프트가 다르면 판단도 달라집니다.

"최소"라고 한 건 더 늘려도 되기 때문입니다. 평가자 셋을 병렬로 채점시켜 다수결로 정할 수도 있죠 — Parallelization을 얹는 겁니다. 기초 패턴은 이렇게 계속 조립해서 씁니다.

특징 ② 무한 루프의 위험 — iteration_count

평가자가 깐깐하고, 생성자가 그 기준을 끝내 못 맞추면 어떻게 될까요?

💀 그래프가 이렇게 됩니다
생성 → 퇴짜 → 생성 → 퇴짜 → 생성 → 퇴짜 → 생성 → 퇴짜 → ...
(LLM 호출이 계속 쌓이고, 청구서도 계속 쌓이고)

그래서 "몇 번 돌았는지" 세는 숫자가 필요하고, 그 자리는 State입니다. 노드 안의 지역 변수는 함수가 끝나면 사라져 다음 호출 때 0부터 시작하고, 전역 변수는 invoke()를 두 번 부르면 이전 실행의 카운트가 남아버립니다. State에 넣으면 실행마다 깨끗하게 초기화됩니다 — "노드끼리 주고받는 값은 State에"라는 2강의 원칙 그대로입니다.

동작은 이렇습니다. 생성자 노드가 호출될 때마다 +1, 분기 함수가 그 값을 읽어 한도를 넘었으면 합격 여부와 무관하게 END로 내보냅니다. 현실의 결재 프로세스에서 팀장이 스무 번씩 반려하지 않고 두세 번이면 넘어가는 "반려는 세 번까지" 사규를 코드로 옮긴 것이죠.

2. 기획 — 홍보 문구 생성 서비스

1요구사항

상품명을 주면 합격점 나올 때까지 광고 문구를 다듬어 준다

2그래프 구성

노드 둘 + 되돌아가는 조건부 엣지

3State 설계

피드백과 반복 횟수까지 담는 다섯 칸

기획 2 · 그래프 구성

  • 신입 카피라이터 노드가 상품명을 보고 광고 문구를 쓴다
  • 팀장 노드가 그 문구를 평가한다
  • 합격(pass)이면 END로 종료
  • 불합격(fail)이면 피드백과 함께 신입 노드로 돌려보낸다
  • 단, 세 번 넘게 반려됐다면 그냥 종료한다 탈출 조건

마지막 줄이 iteration_count입니다. 탈출 조건은 나중에 버그로 발견해 덧붙이는 게 아니라, 루프를 그리는 순간 기획서에 같이 적어야 하는 것입니다.

기획 3 · State 설계 — 칸이 다섯 개로 늘어난 이유

필드누가 쓰나누가 읽나왜 필요한가
product_name 사용자 (invoke 입력) copywriter_node 무엇에 대한 광고인지 매 라운드마다 다시 읽어야 함
ad_copy copywriter_node manager_node + 사용자 신입이 쓴 문구. 팀장의 채점 대상이자 최종 결과물
feedback manager_node copywriter_node 🔴 빨간펜 거꾸로 흐르는 유일한 값
status manager_node 조건부 함수 이 값을 보고 END로 갈지 되돌아갈지 결정
iteration_count copywriter_node 조건부 함수 🛡️ 안전장치 무한 루프 탈출용

가장 특별한 건 feedback입니다. 지금까지 State의 값은 전부 앞 노드가 쓰고 뒤 노드가 읽었는데, feedback은 뒤에 있는 팀장이 쓰고 앞에 있는 신입이 읽습니다 — 정보가 그래프를 거슬러 올라갑니다.

🔍 비유 — 원고와 함께 돌아오는 첨삭지

State는 클리어 파일 한 장입니다. 신입이 [원고] 칸을 채워 넘기면, 팀장이 [판정] 도장을 찍고 [첨삭] 칸에 빨간 글씨를 적어 파일째로 돌려줍니다. 신입이 다시 열면 자기 원고와 첨삭이 나란히 있으니 뭘 고쳐야 할지 알 수 있죠. 파일은 처음부터 끝까지 한 장이고, 오갈 때마다 칸이 덧칠될 뿐입니다.

한 번 더 짚기 — status에는 pass 아니면 fail만

3-2장 라우팅에서 다룬 것과 같은 문제입니다 — 조건부 함수가 비교하는 문자열과 모델이 뱉는 문자열은 사전에 약속돼 있어야 합니다. 팀장 노드에게 그냥 "평가해줘"라고 물으면 이런 답이 옵니다.

❌ 그냥 물어봤을 때 — 매번 다른 모양의 판정
"음, 나쁘지 않지만 조금 아쉽네요."
"불합격입니다."
"FAIL"
"기준 3번을 충족하지 못했습니다."
"통과시켜도 될 것 같습니다."
💥 그 결과 — 영원히 끝나지 않는 그래프
if status == 'pass':      # "통과시켜도 될 것 같습니다." != 'pass'  → False
    return END
...
return "copywriter_node"  # ← 합격인데도 계속 신입에게 되돌아감
🚫 라우팅 때보다 결과가 훨씬 나쁩니다

라우팅에서 이 실수는 문의가 엉뚱한 전문가에게 가는 정도였고 그래프는 어쨌든 끝났습니다. 루프에서는 합격 판정이 영원히 인식되지 않아 루프가 절대 안 끝납니다. 루프가 있는 그래프에서 "약속된 값"은 선택이 아니라 필수입니다. 해결책은 라우팅 때와 같은 Structured Outputs — 구현 파트에서 바로 다룹니다.

STEP 1. Model 정의

📥 코드
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model
from typing import TypedDict, Literal

model = init_chat_model("gpt-5-nano", temperature=0.7)

이번에는 temperature를 0.7로 올렸습니다. 카피라이터는 창작을 하는 직업이라, temperature=0이면 퇴짜 후에도 비슷한 문구가 또 나와 루프가 제자리걸음을 합니다. 반대로 너무 높이면 문장이 무너지니, 0.7이 "매번 다르되 문장은 멀쩡한" 지점입니다.

STEP 2. State 정의

📥 코드
class AdState(TypedDict):
    product_name: str        # 상품명
    ad_copy: str             # 생성된 광고 문구
    feedback: str            # 피드백
    status: str              # 상태 (pass / fail)
    iteration_count: int     # 반복 횟수

기획서를 그대로 옮겼습니다. 두 가지만 짚습니다.

리듀서가 하나도 없다

ad_copy는 같은 칸에 여러 번 쓰이지만(1차, 2차, 3차 원고…) 에러가 안 납니다. 병렬 실행처럼 같은 스텝에 동시에 쓰는 게 아니라 시간 차를 두고 한 번씩 쓰기 때문이죠. 덮어쓰기(overwrite)가 정상 동작입니다.

iteration_count도 그냥 int다

리듀서(operator.add)는 필요 없습니다. 노드가 count + 1이라는 최종값을 직접 계산해 반환하기 때문입니다. 리듀서는 "여러 노드의 반환값을 합치는" 장치이지 "이전 값에 더하기" 장치가 아닙니다. 혼자 순서대로 도는 루프에서는 덮어쓰기가 맞습니다.

🔑 status를 "약속"시키기 — EvaluationResult 스키마

방법은 3-2장에서 배운 Structured Outputs 그대로 — 스키마(class)를 만들고 with_structured_output()으로 모델에 결합하는 두 단계입니다. 새로운 것은 필드가 두 개라는 점입니다.

📥 코드
from pydantic import BaseModel, Field

class EvaluationResult(BaseModel):
    status: Literal["pass", "fail"] = Field(description="기준 충족 여부")
    feedback: str = Field(description="탈락 시 구체적인 수정사항")

Literal["pass", "fail"]은 "이 둘 중 하나여야만 함"이라는 제약이 모델에게 그대로 전달되므로, "음, 나쁘지 않지만..." 같은 답이 나올 수 없습니다. 공장 검사원 책상에 [합격]·[불합격] 도장 딱 두 개만 놓아둔 것과 같습니다 — "보류" 도장은 애초에 만들어주지 않았죠. 도장 옆의 [지적 사항] 메모지가 feedback 필드입니다.

description의 "탈락 시 구체적인 수정사항"은 모델이 실제로 읽는 지시문입니다. "구체적인"이라는 단어 하나가 "별로예요" 같은 쓸모없는 피드백을 막아줍니다. 피드백 품질이 나쁘면 루프가 돌아도 좋아지지 않으므로 이 문장이 그래프 전체의 성능을 좌우합니다. 또한 판정과 이유를 한 번의 호출로 받으니 비용도 절반이고, "합격이라면서 지적을 늘어놓는" 논리적 모순도 없습니다.

evaluator_llm — 채점표가 물린 모델

📥 코드
evaluator_llm = model.with_structured_output(EvaluationResult)

원래 model은 그대로 남고, 채점표가 물려 있는 또 다른 모델 객체가 생깁니다.

구분modelevaluator_llm
.invoke() 반환 타입AIMessage 객체EvaluationResult 객체
본문 꺼내는 법msg.contentresult.status / result.feedback
답의 자유도무엇이든 줄글로status는 두 값 중 하나
실습에서 쓰는 곳copywriter_node (창작)manager_node (채점)
⚠️ 두 모델을 섞어 쓰면 바로 터집니다

evaluator_llm의 결과에 .content를 쓰거나 model의 결과에 .status를 쓰면 AttributeError입니다. 기억법: State는 딕셔너리라 대괄호(state["ad_copy"]), 스키마 객체는 클래스라 점(result.status).

왜 State는 TypedDict이고, 스키마만 Pydantic일까

같은 status인데 State에서는 str, 스키마에서는 Literal["pass", "fail"]입니다. State에도 Literal을 쓰거나 아예 BaseModel로 만들면 더 안전하지 않을까요?

State의 Literal은 아무것도 막아주지 않습니다. TypedDict의 타입은 런타임에 검사되지 않는 메모라서, 노드가 이상한 문자열을 반환하면 그대로 State에 들어갑니다. 반면 EvaluationResult의 Literal은 with_structured_output()이 JSON 스키마로 변환해 모델에게 전달하고, 어겨진 값은 Pydantic이 런타임 에러로 잡아냅니다 — 실제로 힘을 씁니다.

State를 통째로 Pydantic으로 만드는 것도 손해입니다. ① 노드는 어차피 "바뀐 칸만" 담은 딕셔너리를 반환하므로 검증 지점이 그대로 뚫려 있고, ② State는 "아직 안 채워진 칸"이 정상이라 모든 필드에 Optional을 달아야 해서 타입 약속이 흐려지며, ③ 매 스텝의 State 복사·직렬화에 검증·변환 비용이 붙는데 루프 그래프에서는 이게 계속 쌓입니다.

구분AdState (TypedDict)EvaluationResult (Pydantic)
역할노드들이 나눠 채우는 공유 화이트보드바깥 값이 들어오는 세관 검사대
런타임 검증없음 (타입은 메모)있음 (+ 모델에게 제약 전달)
빈 칸정상 — .get()으로 접근불가 — 모든 필드가 채워져야 함
채우는 방식바뀐 칸만 부분 반환한 번에 통째로 생성
비용공짜 (그냥 dict)검증 · 변환 비용
🔍 비유 — 자물쇠는 현관문에 답니다

믿을 수 없는 값이 들어오는 유일한 입구는 LLM의 출력이고, 그 자리가 EvaluationResult입니다. 거기서 한 번 걸러내면 State의 status는 이미 pass 아니면 fail이죠. 검사대를 복도마다 세우면 통행만 느려집니다.

STEP 3. Node 정의 — 신입 하나, 팀장 하나

노드의 계약은 언제나 같습니다 — state를 받고, State 양식에 맞는 딕셔너리를 반환한다.

① copywriter_node — 초안이냐 재작업이냐를 스스로 판단하는 노드

📥 코드
# [Generator] 신입 카피라이터
def copywriter_node(state: AdState):
    product = state["product_name"]
    count = state.get("iteration_count", 0)
    feedback = state.get("feedback")

    print(f"\n--- [Copywriter] 광고 문구 작성 중 (시도: {count + 1}) ---")

    if not feedback:
        # 첫 시도는 좀 건조하게 작성하도록 유도 (Fail을 유발하기 위해)
        prompt = f"'{product}'의 기능 위주로 인스타그램 홍보 문구를 건조하게 작성해줘. 홍보 문구만 답변하고 반드시 20자 이하로 작성하시오."
    else:
        # 피드백 반영
        prompt = f"""
        '{product}' 인스타그램 홍보 문구를 다시 작성해.

        <반드시 지켜야 할 수정 사항>
        {feedback}
        </반드시 지켜야 할 수정 사항>

        <작성 시 반드시 지켜야할 사항>
        홍보 문구만 답변하고 절대 50자 이하로 작성하시오.
        </작성 시 반드시 지켜야할 사항>
        """

    message = model.invoke(prompt)
    ad_copy = message.content

    return {"ad_copy": ad_copy, "iteration_count": count + 1}

왜 state["feedback"]이 아니라 state.get("feedback")인가

첫 실행 때 사용자는 {"product_name": ...}만 넣으므로 나머지 네 칸은 존재하지도 않습니다. TypedDict는 설계도일 뿐 없는 칸을 만들어주지 않기 때문에, 대괄호로 접근하면:

💥 대괄호로 접근하면
KeyError: 'feedback'
코드키가 있을 때키가 없을 때
state["feedback"]그 값KeyError 그래프 중단
state.get("feedback")그 값None ← 두 번째 인자 생략 시 기본값
state.get("iteration_count", 0)그 값0 ← 명시한 기본값

iteration_count에 0을 명시한 건 바로 다음 줄에서 count + 1을 하기 때문입니다(None + 1은 TypeError). 루프에서는 같은 노드가 "State가 텅 빈 첫 바퀴"에도, "다 채워진 두 번째 바퀴"에도 실행되므로, 루프 안의 노드는 State 접근을 전부 .get()으로 쓰는 습관이 안전합니다.

첫 프롬프트가 일부러 "건조하게" 쓰라고 시키는 이유

첫 시도부터 잘 쓰면 한 번에 통과해 루프가 한 번도 안 도는 실습이 되기 때문입니다. 퇴짜 → 피드백 → 재작성 흐름을 눈으로 보려고 탈락할 수밖에 없는 조건을 심어둔 것이죠.

🎯 첫 프롬프트에 심어둔 함정
"기능 위주로"  →  감성적인 톤이 나올 수 없음           → 평가 기준 3번 위반
"건조하게"     →  활기찬 문구가 나올 수 없음           → 평가 기준 3번 위반
"20자 이하"    →  해시태그 3개 + '할인' 넣을 공간 없음  → 평가 기준 1·2번 위반

재작성 프롬프트에서는 제한이 50자로 늘어나 지적을 반영할 공간을 열어줍니다. 실무에서는 이런 함정 없이 처음부터 제대로 쓰면 됩니다. 프롬프트 속 <반드시 지켜야 할 수정 사항> 태그는 특별한 문법이 아니라, 다른 곳에서 온 텍스트(팀장의 자연어 피드백)가 어디부터 어디까지인지 모델에게 알려주는 울타리입니다.

반환값은 두 칸 — 쓴 문구와 1 늘린 카운터. 이 +1이 빠지면 카운터가 영원히 0에 머물러 탈출 조건이 절대 참이 되지 않습니다.

② manager_node — 채점만 하고 글은 쓰지 않는 노드

📥 코드
# [Evaluator] 감성적인 마케팅 팀장
def manager_node(state: AdState):
    ad_copy = state["ad_copy"]
    print(f"\n--- [Manager] 문구 검수 중 ---")
    print(f"   ㄴ 신입이 쓴 글: {ad_copy}")

    prompt = f"""
    당신은 깐깐한 마케팅 팀장입니다. 신입 사원이 쓴 다음 광고 문구를 평가하세요:

    "{ad_copy}"

    <평가 기준>
    1. (정량) 해시태그(#)가 3개 이상 있어야 합니다.
    2. (정량) '할인' 또는 '특가'라는 단어가 포함되어야 합니다.
    3. (정성 - 중요!) **문구가 너무 설명문 같거나 딱딱하면 안 됩니다. 소비자의 감성을 자극하는 '활기차고 매력적인 톤'이어야 합니다.**
    </평가 기준>

    위 3가지 기준 중 하나라도 부족하면 fail을 주세요.
    특히 3번(톤앤매너)이 부족하다면 "좀 더 감성적으로 쓰세요" 같이 100자 이내로 조언하세요.
    """

    result = evaluator_llm.invoke(prompt)          # ★ model이 아니라 evaluator_llm

    print(f"   ㄴ 판정: {result.status.upper()}")
    if result.status == "fail":
        print(f"   ㄴ 지적: {result.feedback}")

    return {"status": result.status, 'feedback': result.feedback}

평가 기준을 정량 2개 + 정성 1개로 섞은 이유

기준종류판정 방식
해시태그 3개 이상정량세면 끝. 누가 봐도 답이 같음
'할인' 또는 '특가' 포함정량있냐 없냐. 논란의 여지 없음
활기차고 매력적인 톤정성읽고 느껴야 함. 사람마다 다를 수 있음

정량 기준만 있다면 ad_copy.count("#") >= 3 같은 파이썬 몇 줄이 더 빠르고 정확하고 공짜입니다. LLM 평가자를 쓰는 이유는 코드로 판정할 수 없는 정성 기준(3번) 때문이고, 실제로 실습에서 가장 여러 번 퇴짜를 놓는 것도 3번입니다. 실무에서는 정량은 코드로 먼저 거르고, 통과한 것만 LLM에게 톤 평가를 맡기는 분업이 더 싸고 정확합니다.

또 하나 — return을 보면 합격이든 불합격이든 feedback을 항상 저장합니다. 덕분에 최종 결과에 합격 판정의 근거까지 남아 디버깅할 때 요긴합니다.

STEP 4. 그래프 생성 — 드디어 루프를 만든다

조건부 함수 route_submission — 나가는 문이 두 개

📥 코드
# 4. 루프 로직
def route_submission(state: AdState):
    status = state["status"]
    count = state["iteration_count"]

    if status == 'pass':
        return END

    if count > 3:
        return END

    else:
        return "copywriter_node"
⚠️ 이 함수는 그래프의 브레이크입니다

라우팅의 조건부 함수는 "누구에게 일을 줄까"를 정할 뿐, 잘못 골라도 그래프는 끝났습니다. 여기서는 이 함수가 END를 반환하지 않으면 그래프가 끝나지 않습니다. 루프를 만드는 것도, 끊는 것도 전부 이 함수의 책임입니다.

탈출구 ① status == 'pass' — 정상 종료. Literal 덕분에 이 비교가 빗나갈 일이 없습니다. 탈출구 ② count > 3 — 합격 못 해도 강제로 내보내는 비상구, "반려는 세 번까지" 사규입니다. 이 두 줄이 없으면 무한 루프입니다.

🚫 슬라이드는 count >= 3, 노트북은 count > 3 — 한 글자가 한 바퀴를 바꿉니다

카운터는 신입이 글을 쓸 때마다 올라가므로 "카운터 값 = 지금까지 쓴 원고 수"입니다. >= 3은 3번째 원고까지, > 3은 4번째 원고까지 쓰고 종료합니다. 기획서의 "3번 이상 fail 시 종료"에 맞는 쪽은 >= 3이죠. 루프의 종료 조건은 항상 손으로 한 바퀴 세어서 확인하세요 — off-by-one 한 바퀴가 LLM 호출 두 번의 비용입니다.

🔢 손으로 세어 보기 (count > 3, 계속 fail이라고 가정)
copywriter #1 → count=1 → manager: fail → 1 > 3? 아니오 → 되돌아감
copywriter #2 → count=2 → manager: fail → 2 > 3? 아니오 → 되돌아감
copywriter #3 → count=3 → manager: fail → 3 > 3? 아니오 → 되돌아감   ← 여기서 끝날 줄 알았는데
copywriter #4 → count=4 → manager: fail → 4 > 3? 예     → END

참고로 else는 빈 줄 때문에 맨 위 if와 짝처럼 보이지만 바로 위의 if count > 3과 짝입니다(파이썬은 들여쓰기로만 짝을 정함). 동작은 정상이지만 사람이 잘못 읽기 좋은 모양이니, else 없이 return "copywriter_node"만 두는 편이 또렷합니다.

그래프 조립 — 실선 둘, 점선 둘

📥 코드
# 5. 그래프 생성
workflow = StateGraph(AdState)

workflow.add_node("copywriter_node", copywriter_node)
workflow.add_node("manager_node", manager_node)

workflow.add_edge(START, 'copywriter_node')            # 실선 — 무조건 신입부터
workflow.add_edge('copywriter_node', 'manager_node')   # 실선 — 쓰면 무조건 검수

workflow.add_conditional_edges(
    'manager_node',                       # 출발지
    route_submission,                     # 판단 로직 함수
    ['copywriter_node', END]              # 도착 후보 — 되돌아가거나, 끝나거나
)

app = workflow.compile()
💡 도착 후보 리스트 ['copywriter_node', END]가 핵심입니다

END는 LangGraph가 미리 만들어 둔 특수 종착점이라 노드 이름처럼 취급됩니다. 그리고 후보의 첫 원소가 이미 지나온 노드라는 것 — 이 한 줄이 이 그래프를 루프로 만드는 전부입니다.

📤 출력 — 컴파일된 그래프 모양 확인
              __start__
                  │            (실선)
           copywriter_node ◀────────┐
                  │            (실선)│
             manager_node           │ (점선 = fail이면 되돌아감)
                  ├────────────────  ┘
                  │            (점선 = pass이거나 횟수 초과면)
               __end__
⚠️ recursion_limit은 설계가 아니라 비상 정지 버튼입니다

탈출 조건을 깜빡해도 LangGraph의 기본 상한(25스텝)이 GraphRecursionError를 내며 멈춰주긴 합니다. 하지만 그때는 결과물이 아니라 예외가 나오고, 멈추기 전까지 LLM은 이미 스무 번 넘게 호출된 뒤죠. 사용자에게 "서버 오류입니다"를 보여주느냐 "세 번 다듬어 봤습니다"라며 결과물을 보여주느냐의 차이 — iteration_count는 그래서 있는 것입니다.

STEP 5. 실행 — 신입과 팀장이 실제로 부딪치는 걸 보기

📥 코드
inputs = {"product_name": "자율주행 자동차"}
result = app.invoke(inputs)

넣는 값은 product_name 하나. 나머지 네 칸은 노드들이 돌면서 채웁니다.

라운드 1 — 예상대로 탈락

📤 실행 로그
--- [Copywriter] 광고 문구 작성 중 (시도: 1) ---

--- [Manager] 문구 검수 중 ---
   ㄴ 신입이 쓴 글: 자율주행차:안전·경로최적
   ㄴ 판정: FAIL
   ㄴ 지적: 정량 1 미달: 해시태그가 3개 이상 필요합니다. 정량 2 미달: '할인' 또는 '특가' 단어를
           포함해야 합니다. 정성 3 미달: 문구가 너무 설명문 같고 딱딱합니다.
           조언: 좀 더 감성적으로 쓰세요. 소비자의 감성을 자극하는 활기찬 톤으로 바꿔보세요.

"자율주행차:안전·경로최적" — 광고라기보다 제품 사양서죠. 의도한 대로 탈락했습니다. 지적 내용이 세 기준을 하나씩 짚으며 고칠 방향까지 적고 있는데, 이 문장이 그대로 다음 라운드의 프롬프트 안으로 들어갑니다.

라운드 2 — 정량은 맞췄는데 톤이 걸림

📤 실행 로그
--- [Copywriter] 광고 문구 작성 중 (시도: 2) ---

--- [Manager] 문구 검수 중 ---
   ㄴ 신입이 쓴 글: 자율주행으로 더 자유롭게! 할인 중 #자율주행 #미래모빌리티 #특가
   ㄴ 판정: FAIL
   ㄴ 지적: 1) 해시태그 3개 이상 충족. 2) 할인/특가 포함 충족. 3) 톤앤매너가 다소 딱딱합니다.
           좀 더 감성적으로 쓰세요. 예: 자율주행의 자유로움을 활기차게 표현하고 할인을 강조.

세기만 하면 되는 정량 기준 둘은 한 라운드 만에 해결됐고, 가장 애매한 정성 기준(3번)만 남았습니다 — 가장 애매한 기준이 가장 오래 버팁니다. 피드백이 라운드를 거치며 "예: ..."라고 방향까지 제시하도록 구체화되는 것도 눈여겨보세요.

   ㄴ 판정: PASS

세 라운드 내내 같은 gpt-5-nano가 썼고, 바뀐 건 매번 프롬프트에 들어가는 feedback 한 덩어리뿐입니다. 구조가 품질을 만든다는 게 이 패턴의 주장이고, 로그 세 줄이 그 증거입니다.

전체 코드 한눈에 보기

# ══ STEP 1. Model ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END
from langchain.chat_models import init_chat_model
from typing import TypedDict, Literal

model = init_chat_model("gpt-5-nano", temperature=0.7)   # 창작이라 온도를 조금 올림

# ══ STEP 2. State ═════════════════════════════════════
class AdState(TypedDict):
    product_name: str        # 상품명
    ad_copy: str             # 생성된 광고 문구
    feedback: str            # 피드백  ← ★ 유일하게 "거꾸로" 흐르는 값
    status: str              # 상태 (pass / fail)
    iteration_count: int     # 반복 횟수  ← ★ 무한 루프 탈출용

# ══ 평가자의 답을 pass/fail로 못 박는 스키마 ═══════════════
from pydantic import BaseModel, Field

class EvaluationResult(BaseModel):
    status: Literal["pass", "fail"] = Field(description="기준 충족 여부")
    feedback: str = Field(description="탈락 시 구체적인 수정사항")

evaluator_llm = model.with_structured_output(EvaluationResult)

# ══ STEP 3. Node ══════════════════════════════════════
# [Generator] 신입 카피라이터
def copywriter_node(state: AdState):
    product = state["product_name"]
    count = state.get("iteration_count", 0)      # ★ 첫 실행엔 없는 칸 → 기본값 0
    feedback = state.get("feedback")             # ★ 첫 실행엔 None

    print(f"\n--- [Copywriter] 광고 문구 작성 중 (시도: {count + 1}) ---")

    if not feedback:
        # 첫 시도는 좀 건조하게 작성하도록 유도 (Fail을 유발하기 위해)
        prompt = f"'{product}'의 기능 위주로 인스타그램 홍보 문구를 건조하게 작성해줘. 홍보 문구만 답변하고 반드시 20자 이하로 작성하시오."
    else:
        # 피드백 반영
        prompt = f"""
        '{product}' 인스타그램 홍보 문구를 다시 작성해.

        <반드시 지켜야 할 수정 사항>
        {feedback}
        </반드시 지켜야 할 수정 사항>

        <작성 시 반드시 지켜야할 사항>
        홍보 문구만 답변하고 절대 50자 이하로 작성하시오.
        </작성 시 반드시 지켜야할 사항>
        """

    message = model.invoke(prompt)
    return {"ad_copy": message.content, "iteration_count": count + 1}   # ★ +1을 빼먹으면 무한 루프

# [Evaluator] 감성적인 마케팅 팀장
def manager_node(state: AdState):
    ad_copy = state["ad_copy"]
    print(f"\n--- [Manager] 문구 검수 중 ---")
    print(f"   ㄴ 신입이 쓴 글: {ad_copy}")

    prompt = f"""
    당신은 깐깐한 마케팅 팀장입니다. 신입 사원이 쓴 다음 광고 문구를 평가하세요:

    "{ad_copy}"

    <평가 기준>
    1. (정량) 해시태그(#)가 3개 이상 있어야 합니다.
    2. (정량) '할인' 또는 '특가'라는 단어가 포함되어야 합니다.
    3. (정성 - 중요!) **문구가 너무 설명문 같거나 딱딱하면 안 됩니다. 소비자의 감성을 자극하는 '활기차고 매력적인 톤'이어야 합니다.**
    </평가 기준>

    위 3가지 기준 중 하나라도 부족하면 fail을 주세요.
    특히 3번(톤앤매너)이 부족하다면 "좀 더 감성적으로 쓰세요" 같이 100자 이내로 조언하세요.
    """

    result = evaluator_llm.invoke(prompt)        # ★ model이 아니라 evaluator_llm

    print(f"   ㄴ 판정: {result.status.upper()}")
    if result.status == "fail":
        print(f"   ㄴ 지적: {result.feedback}")

    return {"status": result.status, 'feedback': result.feedback}   # ★ 점(.)으로 접근

# ══ STEP 4. Graph ═════════════════════════════════════
# 루프 로직: 나가는 문이 두 개 — 합격이거나, 횟수를 다 썼거나
def route_submission(state: AdState):
    status = state["status"]
    count = state["iteration_count"]

    if status == 'pass':
        return END                    # 탈출구 ① 정상 종료

    if count > 3:
        return END                    # 탈출구 ② 비상 종료 (기획 의도대로면 >= 3)

    else:
        return "copywriter_node"      # 🔄 되돌아가기 = 루프

workflow = StateGraph(AdState)

workflow.add_node("copywriter_node", copywriter_node)
workflow.add_node("manager_node", manager_node)

workflow.add_edge(START, 'copywriter_node')            # 실선
workflow.add_edge('copywriter_node', 'manager_node')   # 실선

workflow.add_conditional_edges(                        # 점선 둘
    'manager_node',
    route_submission,
    ['copywriter_node', END]                           # ★ 후보에 "지나온 노드"가 들어가면 루프
)

app = workflow.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
inputs = {"product_name": "자율주행 자동차"}
result = app.invoke(inputs)

자주 걸리는 함정 7가지

🕳️ 루프가 생기는 순간 새로 밟게 되는 지뢰

1. iteration_count를 +1 하는 걸 빼먹는다

이 장 최악의 버그. 카운터가 영원히 0이라 count > 3이 절대 참이 되지 않고, 문법 에러도 아니라서 GraphRecursionError가 뜰 때까지 조용히 돕니다. 탈출 조건에 쓰이는 값은 "누가 올려주나"를 반드시 확인하세요.

2. state["feedback"]처럼 대괄호로 읽는다

첫 라운드에는 그 칸이 존재하지 않아 KeyError. 루프 안의 노드는 .get()으로 읽고, 숫자 칸이라면 기본값까지 (state.get("iteration_count", 0)) 챙기세요.

3. 탈출 조건의 부등호를 하나 잘못 쓴다

>와 >= 사이에서 루프가 한 바퀴 더 돕니다. 에러가 안 나 발견도 어렵죠. 카운터를 어느 노드에서 올리고 어느 시점에 검사하는지 손으로 한 바퀴 세어 보세요.

4. 평가자를 그냥 model로 호출한다

줄글 답변이 나와 result.status에서 AttributeError가 납니다. 차라리 에러가 나는 게 다행입니다 — .content를 status에 그대로 넣으면 합격해도 안 끝나는 그래프가 되니까요.

5. 조건부 함수에서 END를 반환하는 걸 잊는다

루프에서 END 반환은 유일한 출구입니다. add_conditional_edges의 도착 후보 리스트에도 END를 넣어야 그래프 그림에 종료 경로가 그려집니다.

6. 평가 기준을 애매하게 적어놓고 루프 탓을 한다

같은 문구를 두 번 평가시켰는데 결과가 다르면 기준이 애매하다는 신호입니다. "해시태그 3개 이상" 같은 셀 수 있는 정량 조건을 최소 하나 넣으면 루프가 훨씬 안정적으로 수렴합니다.

7. 피드백을 프롬프트에 넣는 걸 잊는다

State에 저장만 하고 생성자 프롬프트에 끼워 넣지 않으면 신입은 매번 마음대로 다시 씁니다 — Evaluator만 있고 Optimizer가 없는 상태. "두 번째 라운드의 프롬프트에 팀장의 지적이 실제로 들어 있는가"를 print로 찍어보면 바로 확인됩니다.

💡 디버깅 요령 — 루프는 반드시 print로 계측하세요

①생성자에 라운드 번호, ②평가자에 판정, ③평가자에 지적 사항 — 이 세 줄만 찍어두면 루프가 도는지, 개선되고 있는지, 왜 안 끝나는지가 로그만 보고 파악됩니다.

📚 한 장 정리

오늘의 핵심 한 문장

조건부 엣지의 목적지를 이미 지나온 노드로 적으면 그 순간 루프가 되고, 그때부터는 "어떻게 반복할까"보다 "어떻게 빠져나올까"가 더 중요한 설계 문제가 된다.

  • Evaluator-Optimizer란 — 만드는 노드와 채점하는 노드를 나누고, 불합격이면 피드백(빨간펜)을 들려 되돌려 보내는 구조. "다시 해와"가 아니라 "여기를 이렇게 고쳐와"라서 Optimizer다.
  • 새 문법은 없다 — Chaining + Routing + Loop의 조합이고, 루프는 조건부 함수가 지나온 노드 이름을 반환하는 것이 전부다.
  • 쓰는 상황 — 속도보다 품질이 우선이고, 채점 기준을 말로 적을 수 있는 일 (코드+테스트, 번역 검수, 데이터 검증). 기준을 못 적겠으면 쓰지 마라.
  • State는 다섯 칸 — 그중 feedback만 그래프를 거슬러 올라가고 (뒤 노드가 쓰고 앞 노드가 읽음), iteration_count는 무한 루프 안전장치다.
  • 두 개의 인격 분리 — 자기 답안지를 자기가 채점하면 후해진다. 같은 모델이라도 다른 페르소나로 불러야 한다.
  • Literal["pass", "fail"]은 필수 — 라우팅에서는 약속이 깨져도 엉뚱한 노드로 갈 뿐이지만, 루프에서는 합격을 못 알아들어 영원히 안 끝난다.
  • 루프 안의 노드는 .get()으로 읽는다 — 같은 함수가 텅 빈 첫 바퀴와 다 채워진 두 번째 바퀴를 모두 감당해야 하기 때문.
  • 탈출구는 두 개 — ① 합격(정상 종료), ② 횟수 초과(비상 종료). recursion_limit은 비상 정지 버튼이지 설계가 아니다.
  • 같은 칸은 덮어써진다 — 중간 원고를 남기려면 리스트 + 리듀서로 히스토리를 쌓는다.

이번 장에서 "앞으로만 간다"는 전제가 깨졌다면, 다음 장에서는 "노드의 개수가 코드를 쓰는 시점에 정해져 있다"는 전제가 깨집니다. Orchestrator-Worker에서는 지휘자 노드가 일을 몇 조각으로 쪼갤지 실행 중에 정하고, 그 개수만큼 워커를 그 자리에서 만들어 뿌립니다. 실습으로는 주제 하나를 던지면 목차를 스스로 짜고, 그 목차 수만큼 집필자를 뽑아 보고서를 완성하는 서비스를 만듭니다.
