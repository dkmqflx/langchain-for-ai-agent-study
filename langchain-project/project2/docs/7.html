7

Multi-LLM Provider 추상화

서비스화 층 Model Router 축소판 ⏱ 2시간
🎯 목표

모델을 코드에서 떼어내 설정과 요청으로 고를 수 있게 만든다. 같은 질문을 OpenAI와 Gemini로 각각 돌려 비용·지연·도구 선택을 비교한다.

🧠 개념

지금 agent.py에 있는 "openai:gpt-5-mini"가 문제입니다

모델 이름이 코드 한복판에 박혀 있으면 바꿀 때마다 코드를 고쳐야 하고, 그건 배포를 해야 한다는 뜻입니다. 이걸 떼어내야 하는 이유가 넷 있는데, 넷 다 실제로 벌어지는 일입니다.

상황박혀 있으면
가격이 바뀐다더 싼 모델이 나와도 코드 수정 + 배포를 거쳐야 갈아탄다
장애가 난다OpenAI가 30분 죽으면 우리 서비스도 30분 죽는다. 대안이 없다
강점이 다르다긴 문서 요약은 A가, 도구 호출은 B가 나은데 하나만 쓴다
실험이 안 된다"다른 모델이 나을까?"를 확인하려면 매번 코드를 고쳐야 한다
🔌 비유 — 콘센트 규격

가전마다 전선을 벽에 직접 납땜해 놨다고 생각해 보세요. 청소기를 바꾸려면 벽을 뜯어야 합니다. 콘센트라는 규격을 하나 만들어 두면, 가전은 플러그만 꽂으면 되고 벽은 건드릴 일이 없죠.

get_model("openai")이 그 콘센트입니다. Agent는 "모델 하나 주세요"라고만 하고, 어떤 모델이 오는지는 관심을 끊습니다. 이 얇은 함수 하나가 앞으로 만들 LLM Gateway의 씨앗이에요 — 여기에 라우팅 규칙·요금 로깅·재시도를 얹으면 그게 Model Router입니다.

바꾸는 층이 세 개 있습니다

층언제 정해지나쓰임
① 기본값서버 시작 시 .env에서평소에 쓸 모델. 운영에서 갈아탈 때 재배포 없이 환경변수만
② 요청별요청이 들어올 때마다A/B 실험, 사용자 등급별 모델 차등, 비교 측정
③ 대체(fallback)기본 모델이 실패했을 때장애 대응. 죽는 대신 다른 모델로 계속 서비스
🛠 할 일

① providers.py — 콘센트 만들기

P1에서 get_retriever(mode)로 검색기를 갈아끼웠던 것과 완전히 같은 구조입니다. 문자열 하나를 받아 객체를 돌려주고, 한 번 만든 건 보관해 두고 재사용하죠.

providers.py
# ═══════════════════════════════════════════════════════════════════
# STEP 7 · Provider 추상화: 'openai' 같은 이름 하나로 모델 객체를 얻는 창구.
# Agent는 어떤 회사의 어떤 모델인지 몰라도 되고, 바꾸고 싶으면 여기만 고치면 된다.
# P1의 get_retriever(mode)와 똑같은 모양이다 — 이름 → 객체, 그리고 캐시.
# ═══════════════════════════════════════════════════════════════════
import os
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model

load_dotenv()          # GOOGLE_API_KEY·OPENAI_API_KEY를 여기서도 읽는다 (STEP 2의 임포트 순서 교훈)

# 이름 → "provider:model" 문자열.
# init_chat_model이 앞의 provider 부분을 보고 알맞은 패키지를 골라 준다.
# 새 모델을 늘리는 건 이 딕셔너리에 한 줄 추가하는 일이 전부다.
PROVIDERS = {
    "openai": "openai:gpt-5-mini",
    "gemini": "google_genai:gemini-2.5-flash",
    # "claude": "anthropic:claude-sonnet-4-5",   ← 키만 있으면 이 한 줄로 늘어난다
}

# 평소에 쓸 모델. .env에 LLM_PROVIDER=gemini 라고 적으면 재배포 없이 갈아탄다.
DEFAULT_PROVIDER = os.getenv("LLM_PROVIDER", "openai")

_models = {}           # 한 번 만든 모델 객체를 담아 두는 보관함

def get_model(name: str | None = None):
    """provider 이름을 받아 모델 객체를 돌려준다. 이름을 안 주면 기본값을 쓴다."""
    name = name or DEFAULT_PROVIDER
    if name not in PROVIDERS:
        # 오타가 조용히 넘어가지 않게 즉시 알린다 (P1의 unknown mode와 같은 방어)
        raise ValueError(f"unknown provider: {name} (가능: {list(PROVIDERS)})")
    if name not in _models:
        _models[name] = init_chat_model(PROVIDERS[name])
    return _models[name]
⚠️ 모델 이름은 자주 바뀝니다

gemini-2.5-flash 같은 이름은 몇 달이면 새 버전이 나오고 옛 이름이 사라지기도 합니다. NotFoundError나 model not found가 뜨면 제공사의 현재 모델 목록부터 확인하세요. 바로 이렇게 이름을 딕셔너리 한 곳에 모아 두는 이유이기도 합니다 — 고칠 자리가 한 군데뿐이니까요.

② agent.py — 기본값 연결 + 요청별 교체

기본값은 get_model()로 바꾸면 끝입니다. 재미있는 건 요청별 교체인데, 03에서 배운 @wrap_model_call을 그대로 씁니다 — "메시지 길이에 따라 모델을 고르던" 그 예제와 구조가 똑같아요.

agent.py — 추가·수정
from dataclasses import dataclass
from langchain.agents.middleware import wrap_model_call

from providers import get_model          # ← 추가


# 요청마다 달라지는 '실행 환경 정보'를 담는 상자.
# state(대화 내용)와 달리 Agent가 도는 동안 바뀌지 않는 값들이 여기 들어간다.
@dataclass
class Context:
    provider: str | None = None          # None이면 기본 모델을 쓴다


# Wrap-style 미들웨어 = 모델 호출을 '가로채서' 요청을 바꿔치기하는 훅.
@wrap_model_call
def select_provider(request, handler):
    """요청에 provider가 지정돼 있으면 그 모델로 갈아끼운다."""
    name = getattr(request.runtime.context, "provider", None)
    if name:
        # override는 요청 객체를 통째로 다시 만들지 않고 일부만 바꿔 준다
        request = request.override(model=get_model(name))
    return handler(request)              # 바뀐 요청으로 실제 모델 호출을 진행시킨다


agent = create_agent(
    model=get_model(),                   # ← "openai:gpt-5-mini" 대신 기본 모델 객체
    tools=[get_today, calculate, web_search, search_internal_docs],
    system_prompt=SYSTEM_PROMPT,
    checkpointer=checkpointer,
    context_schema=Context,              # ← 추가: 이 Agent가 받을 Context의 모양
    middleware=[
        input_guardrail,
        select_provider,                 # ← 추가
        PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
    ],
    response_format=ToolStrategy(ChatReply),
)
agent.py — ask()에 provider 인자 추가
def ask(message: str, session_id: str = "default", provider: str | None = None) -> dict:
    with langfuse.start_as_current_observation(name="agent-chat", as_type="span"):
        # 어떤 모델로 돌렸는지 트레이스에 남겨야 나중에 provider별 비용을 비교할 수 있다
        langfuse.update_current_trace(
            session_id=session_id,
            input=message,
            metadata={"provider": provider or DEFAULT_PROVIDER},
        )
        result = agent.invoke(
            {"messages": [{"role": "user", "content": message}]},
            {"configurable": {"thread_id": session_id}, "callbacks": [langfuse_handler]},
            context=Context(provider=provider),          # ← 추가
        )
        ...  # 나머지는 STEP 6과 동일

DEFAULT_PROVIDER도 providers에서 함께 import하세요 (from providers import get_model, DEFAULT_PROVIDER).

③ main.py — API로 노출

main.py — 두 군데 수정
class ChatIn(BaseModel):
    message: str
    session_id: str = "default"
    provider: str | None = None          # ← 추가. 안 보내면 기본 모델을 쓴다


@app.post("/chat", response_model=ChatOut)
def chat(body: ChatIn):
    result = ask(body.message, session_id=body.session_id, provider=body.provider)
    return {**result, "session_id": body.session_id}
💡 실무라면 provider를 아무나 지정하게 두지 않습니다

지금은 실험을 편하게 하려고 요청 본문으로 받았지만, 공개 API에서 클라이언트가 모델을 고르게 하면 가장 비싼 모델만 골라 쓰는 사람이 생깁니다. 실제로는 서버가 사용자 등급 · A/B 실험 그룹 · 질문 난이도를 보고 정하죠. 그게 Model Router가 하는 일이고요. 지금 만든 select_provider 미들웨어는 그 라우팅 규칙이 들어갈 자리를 미리 뚫어 둔 것입니다.

④ 대체 모델(fallback) — 선택

기본 모델이 실패했을 때 다른 모델로 넘기는 것도 @wrap_model_call에서 try/except로 됩니다. 랭체인에는 ModelFallbackMiddleware 내장도 있으니 그걸 써도 좋습니다.

agent.py — select_provider를 이렇게 확장해도 된다
@wrap_model_call
def select_provider(request, handler):
    name = getattr(request.runtime.context, "provider", None)
    if name:
        request = request.override(model=get_model(name))
    try:
        return handler(request)
    except Exception as e:
        # 기본 모델이 죽었을 때 서비스를 통째로 멈추는 대신 다른 모델로 넘긴다.
        # 어떤 예외에서 넘길지는 신중히 골라야 한다 — 인증 오류로 넘기면
        # 두 번째 모델도 똑같이 실패하며 비용과 지연만 두 배가 된다.
        fallback = "gemini" if (name or DEFAULT_PROVIDER) != "gemini" else "openai"
        print(f"⚠️ {name or DEFAULT_PROVIDER} 실패({e}) → {fallback}로 대체")
        langfuse.update_current_trace(tags=["fallback", fallback])
        return handler(request.override(model=get_model(fallback)))

두 모델을 비교해 보면 십중팔구 비용·속도만 다른 게 아니라 행동이 다릅니다. 한쪽은 search_internal_docs를 부르는데 다른 쪽은 그냥 아는 대로 답하거나, 한쪽만 sources를 제대로 채우거나 하죠. 같은 프롬프트, 같은 도구인데도요.

그러면 "어느 쪽이 더 낫나?"라는 질문이 생기는데, 답변 두 개를 눈으로 보고는 정할 수 없습니다. 질문 하나로 판단하면 그건 표본 1개짜리 결론이니까요. 여러 케이스로 채점해야 답이 나옵니다 — 그게 STEP 8입니다.

⚠️ Gemini 비용이 0으로 보일 수 있습니다

Langfuse는 모델별 단가표를 갖고 비용을 계산합니다. 새로 나온 모델이나 등록 안 된 모델은 토큰은 찍히는데 비용이 0이나 공란으로 나옵니다. 관측이 고장 난 게 아니에요. 이럴 땐 토큰 수로 비교하거나, Langfuse에 해당 모델 단가를 등록하면 됩니다.

🎓 배우는 것

벤더를 코드에서 떼어내는 설계, 그리고 그걸 세 층(기본값·요청별·대체)으로 나눠 생각하는 법. @wrap_model_call이라는 훅이 곧 라우팅 규칙이 들어갈 자리라는 것도요. 무엇보다 "모델을 바꾸면 행동이 바뀐다"를 직접 확인한 게 큽니다 — 그래서 모델·프롬프트를 손댈 때마다 측정이 따라붙어야 한다는 결론에 스스로 도달하게 됩니다.
