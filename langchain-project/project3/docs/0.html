🎯 목표

project3/를 혼자서도 도는 프로젝트로 세우고, P1·P2 두 서버와 말이 통하는지까지 확인합니다. 코드는 아직 한 줄도 안 씁니다.

🧠 개념 — 딱 하나만

시험 감독관은 수험생 교실에 책상을 두지 않습니다

P3가 필요한 건 P1·P2의 응답뿐입니다. Chroma도, 리랭커 모델도, LangGraph 체크포인터도 필요 없어요. P3 환경에 깔리는 건 딱 세 부류입니다 — 전화기(requests), 채점 도구(RAGAS · LLM), 장부(pandas · Langfuse).

P2 때와 같은 결정입니다. 폴더를 나누고 HTTP로만 만나면, P1이 패키지를 바꿔도 P3는 흔들리지 않고, 나중에 LangGraph로 만든 새 서비스도 주소 하나만 더하면 같은 시험지로 채점됩니다.

POST /query
←
🧪 P3 · 스크립트시험지 · 러너 · 채점자
서버가 아니라 명령이다
→
🤖 P2 · 포트 8001도구 · Agent · 메모리

📞 비유 — 감독관은 전화로 문제를 내고, 답만 받아 적는다

P3는 서버가 아닙니다. 명령 한 번에 시험지를 들고 두 서비스에 전화를 걸어, 답을 받아 적고, 채점표를 남기는 스크립트예요. 그래서 포트도 없고 uvicorn도 없습니다. 있는 건 .env의 전화번호 둘 — P1_API_URL, P2_API_URL입니다.

의존성 — 세 묶음으로 나눠서

— 어느 패키지가 어느 STEP 것인지 알고 넘어간다
터미널 C
# 1묶음 · 시험지·러너 (STEP 1~3)
#   pydantic  → 케이스 파일의 '모양'을 검증한다
#   requests  → P1·P2의 창구를 두드린다
#   pandas    → 케이스별 점수를 표로 모으고 평균을 낸다
uv add pydantic requests python-dotenv pandas

# 2묶음 · 채점자 (STEP 4~5)
#   ragas + datasets → RAG 지표 4종. ragas 0.4.x는 langchain-community 0.4.1과 맞물리므로 그 버전으로 고정한다
#   langchain + langchain-openai → RAGAS의 심판 LLM과 STEP 5의 채점자(judge)
uv add ragas datasets langchain langchain-openai "langchain-community>=0.4.1,<0.4.2"

# 3묶음 · 플랫폼 (STEP 7~8)
#   tabulate → pandas가 표를 마크다운으로 찍을 때 쓴다(리포트)
#   pytest   → 품질 게이트. 개발용(--dev)이라 배포 의존성에는 안 들어간다
uv add langfuse tabulate
uv add --dev pytest
패키지쓰이는 곳역할
pydantic1~2케이스 · 데이터셋 · RunResult의 모양 선언과 검증
requests2P1 /query · P2 /chat 호출
pandas3~8점수표 · 평균 · 비교표
python-dotenv전체.env의 키·주소를 환경변수로 로드
ragas · datasets4RAG 지표 4종 (P1 STEP 7에서 쓴 것 그대로)
langchain · langchain-openai4~5심판 LLM 연결 · with_structured_output으로 점수를 정해진 모양으로 받기
langchain-community4RAGAS가 내부적으로 쓰는 어댑터. 0.4.1로 고정
langfuse7dataset · run · trace · score 기록
tabulate8DataFrame → 마크다운 표
pytest (dev)8회귀 게이트를 테스트 한 줄로

나중에 ImportError가 나면 이 표를 보세요. "아 이건 STEP 7용이었지" 하고 바로 짚입니다.

.env — 키와 주소 둘

— P2에서 쓰던 파일을 복사해 오고 한 줄 더한다
.env
OPENAI_API_KEY=sk-...                   # RAGAS 심판 LLM · STEP 5 채점자

# P1·P2에서 쓰던 값 그대로 — 한 프로젝트에 세 서비스 기록이 함께 쌓인다
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...

# 시험 대상 두 곳의 주소. 코드에 박지 않고 설정으로 빼 둔다

P2_API_URL=http://localhost:8001

Langfuse 키를 P1·P2와 같은 값으로 두는 이유는 STEP 7에서 드러납니다 — P3가 남긴 점수와 P2가 남긴 도구 호출 기록이 한 대시보드에 있어야 "점수가 낮은 케이스에서 Agent가 실제로 무슨 도구를 불렀나"를 바로 찾아갈 수 있어요.

🎓 한 줄 정리

평가 하네스는 서버가 아니라 스크립트이고, 시험 대상에 대해 아는 건 주소 둘뿐이다. 그래서 시험 대상이 늘어나도(다음 단계의 LangGraph 서비스) 주소 하나만 더하면 된다.

더 알아보기 — P2가 어디까지 돼 있어야 하나 / 세 서버의 Langfuse 키

P2는 STEP 6까지면 충분합니다

P3가 P2에서 쓰는 건 POST /chat의 응답 — answer · sources · used_tools · blocked 네 칸입니다. 이건 P2 STEP 5에서 이미 완성됐어요. P2의 STEP 7(Multi-LLM)·8(프롬프트 A/B)은 P3와 무관하게 나중에 해도 되고, 오히려 P3를 먼저 만들어 두면 P2 STEP 8을 P3 하네스로 대신할 수 있습니다.

세 서비스가 같은 Langfuse 프로젝트를 쓰는 이유

P1 · P2 · P3가 각자 다른 키를 쓰면 대시보드가 셋으로 갈라집니다. 같은 키를 쓰면 STEP 7에서 P3가 남긴 점수(score)와 P2가 남긴 트레이스(도구 호출 · 토큰)가 한 화면에 있어, "이 케이스 점수가 왜 낮지?"에서 "아, 도구를 안 불렀네"까지 클릭 두 번이면 갑니다.
