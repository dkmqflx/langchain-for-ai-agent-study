Agent 코어 ① — Tool 3종과 첫 Agent

🟢 랭체인 집중 ⏱ 1~2시간
🎯 목표

도구 3개(날짜 · 계산 · 웹검색)를 만들고 create_agent로 묶어, 질문에 따라 LLM이 스스로 다른 도구를 고르는 것을 눈으로 확인한다.

🧠 개념

Tool은 "함수"지만, LLM은 그 함수를 실행하지 않는다

이게 처음에 가장 헷갈리는 지점입니다. @tool을 붙였다고 LLM이 파이썬을 돌리는 게 아니에요. LLM이 하는 일은 딱 하나 — "calculate라는 도구를 expression="1234*5678"로 불러 주세요"라는 요청서를 쓰는 것입니다. 실제로 함수를 실행하는 건 랭체인이고, 결과를 다시 LLM에게 돌려주는 것도 랭체인입니다.

🍽 비유 — 주방 없는 셰프

LLM은 레시피는 완벽히 아는데 손이 없는 셰프입니다. "양파 200g을 채썰어 줘"라고 주문서는 쓸 수 있지만 칼을 쥘 수는 없어요. 랭체인이 그 주문서를 받아 실제로 썰고, "썬 양파 200g 나왔습니다" 하고 셰프에게 되돌려 줍니다. 셰프는 그걸 보고 다음 주문서를 쓰거나, 이제 됐다 싶으면 요리를 내놓습니다.

그래서 도구 설명(docstring)이 곧 메뉴판입니다. 메뉴판에 안 적힌 요리는 셰프가 주문할 수 없고, 설명이 애매하면 엉뚱한 걸 주문합니다. STEP 2에서 이 점이 더 뼈아프게 드러납니다.

Agent의 한 바퀴 — 이 6단계가 계속 돈다

"1234 곱하기 5678이 얼마야?"를 물었을 때 안에서 벌어지는 일입니다.

단계주체하는 일
1사용자HumanMessage("1234 곱하기 5678이 얼마야?")
2LLM"이건 calculate를 써야겠군" 판단
3LLMAIMessage(content='', tool_calls=[{"name":"calculate","args":{"expression":"1234*5678"}}]) — 내용은 비어 있고 주문서만 있다
4랭체인실제로 calculate("1234*5678") 실행
5랭체인ToolMessage("7006652")를 대화에 추가
6LLM결과를 보고 판단 — 더 필요하면 2번으로 돌아가고, 됐으면 최종 답변 생성
💡 P1과의 결정적 차이가 6단계에 있습니다

P1의 RAG는 "검색 → 생성"으로 끝이었습니다. 코드에 그렇게 적혀 있었으니까요. Agent는 6단계에서 루프를 한 번 더 돌지 스스로 정합니다. "오늘부터 100일 뒤는 며칠이야?" 같은 질문이면 날짜 도구 → 계산 도구로 두 바퀴를 돌죠. 몇 바퀴 돌지 코드에 안 적혀 있다는 것 — 그게 Agent의 힘이자, 관측·평가가 필요해지는 이유입니다.

🛠 할 일

① tools.py — 도구 3종

도구를 만들 때 신경 쓸 건 네 가지입니다: 함수 본문 · 타입 힌트 · docstring · @tool. 이 중 타입 힌트와 docstring만이 LLM에게 전달됩니다. 함수 본문은 LLM이 못 봅니다 — LLM 입장에서 도구는 "이름 + 설명 + 인자 목록"이 전부예요.

tools.py
# ═══════════════════════════════════════════════════════════════════
# STEP 1 · 도구(Tool) 정의: Agent가 골라 쓸 수 있는 능력들을 함수로 만든다.
# 여기서 중요한 건 '함수가 잘 도는가'보다 'LLM이 언제 이걸 써야 하는지 아는가'다.
# → 그 정보는 오직 함수 이름 · 타입 힌트 · docstring 세 가지로만 전달된다.
# ═══════════════════════════════════════════════════════════════════
import ast
import operator
from datetime import datetime
from zoneinfo import ZoneInfo          # 파이썬 3.9+ 내장. 시간대를 다룰 때 쓴다

from langchain.tools import tool       # 평범한 함수를 '도구'로 등록해 주는 데코레이터
from ddgs import DDGS                  # DuckDuckGo 검색 클라이언트 (API 키 불필요)


# ── 도구 1 · 오늘 날짜 ────────────────────────────────────────────
# LLM은 '오늘'이 며칠인지 모른다. 학습 데이터가 끝난 시점까지만 알고,
# 지금 이 순간이 언제인지는 알 방법이 없다 → 알려 주는 도구가 필요하다.
@tool
def get_today() -> str:
    """오늘 날짜와 현재 시각(한국 시간)을 알려준다.

    '오늘', '지금', '이번 주', '며칠 남았는지' 처럼 현재 시점을 알아야 답할 수 있는
    질문에는 다른 무엇보다 먼저 이 도구를 호출한다.
    """
    now = datetime.now(ZoneInfo("Asia/Seoul"))
    weekday = "월화수목금토일"[now.weekday()]      # weekday()는 월=0 … 일=6
    return now.strftime(f"%Y-%m-%d %H:%M ({weekday}요일)")


# ── 도구 2 · 계산기 ──────────────────────────────────────────────
# 아래 세 줄은 '안전한 계산기'를 만들기 위한 재료다.
# 파이썬의 eval()을 쓰면 한 줄로 끝나지만, 그건 절대 하면 안 된다 (아래 경고 참고).
_OPS = {
    ast.Add: operator.add, ast.Sub: operator.sub,
    ast.Mult: operator.mul, ast.Div: operator.truediv,
    ast.Pow: operator.pow, ast.USub: operator.neg,   # USub = -5 같은 단항 마이너스
}

def _eval_node(node):
    """수식을 해석한 나무(AST)를 타고 내려가며 계산한다. 허용한 연산만 통과시킨다."""
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
        return node.value                                        # 숫자면 그대로
    if isinstance(node, ast.BinOp) and type(node.op) in _OPS:     # a + b 같은 2항 연산
        return _OPS[type(node.op)](_eval_node(node.left), _eval_node(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _OPS:   # -a 같은 1항 연산
        return _OPS[type(node.op)](_eval_node(node.operand))
    raise ValueError("허용되지 않은 식")                           # 그 외는 전부 거부

@tool
def calculate(expression: str) -> str:
    """사칙연산과 거듭제곱으로 이루어진 수식을 계산한다.

    예: "1234 * 5678", "(120 - 45) / 3", "2 ** 10"
    숫자 계산이 필요하면 직접 암산하지 말고 반드시 이 도구를 사용한다.
    """
    try:
        # ast.parse(..., mode="eval") = 문자열을 '실행'하지 않고 '구조로 분해'만 한다.
        # .body가 그 구조의 뿌리 노드이고, 우리가 만든 _eval_node가 이걸 타고 내려가며 계산한다.
        return str(_eval_node(ast.parse(expression, mode="eval").body))
    except Exception:
        # 도구는 예외를 밖으로 던지지 않는다 — 자세한 이유는 아래 경고 참고
        return f"계산할 수 없는 식입니다: {expression}"


# ── 도구 3 · 웹 검색 ─────────────────────────────────────────────
@tool
def web_search(query: str, max_results: int = 3) -> str:
    """웹에서 최신 정보를 검색한다.

    뉴스, 시세, 최근에 일어난 일처럼 모델이 알 수 없는 '지금'의 정보가 필요할 때 사용한다.
    사내 문서나 약관의 내용은 이 도구로 찾을 수 없다.
    """
    try:
        hits = DDGS().text(query, max_results=max_results)
    except Exception as e:
        return f"웹 검색에 실패했습니다: {e}"
    if not hits:
        return "검색 결과가 없습니다."
    # LLM이 읽을 문자열로 정리한다. 출처(url)를 함께 넣어야 답변에 근거를 달 수 있다.
    return "\n\n".join(
        f"- {h.get('title')}\n  {h.get('body')}\n  ({h.get('href')})" for h in hits
    )
🚨 eval(expression)을 쓰면 안 되는 이유

계산기 도구를 return str(eval(expression)) 한 줄로 만들고 싶은 유혹이 큽니다. 하지만 이 문자열은 LLM이 만들어 낸 것이고, LLM은 사용자 입력에 휘둘립니다. 누군가 "계산해 줘: __import__('os').system('rm -rf ~')"라고 유도하면 그 코드가 내 서버에서 그대로 실행됩니다.

위 코드가 ast로 수식을 분해만 하고 허용한 연산자(_OPS)만 통과시키는 이유가 이것입니다. 외워 둘 원칙 하나: LLM이 만든 문자열은 사용자 입력과 똑같이 의심하라.

⚠️ 도구는 예외를 던지지 말고 "실패 메시지"를 반환한다

세 도구 모두 try/except로 감싸 실패를 문자열로 되돌려 준다는 점에 주목하세요. 도구가 예외를 던지면 Agent 실행 전체가 멈추고 사용자는 500 에러를 봅니다. 반면 "웹 검색에 실패했습니다: ..."를 돌려주면 그 문장이 ToolMessage로 LLM에게 전달되고, LLM은 "검색이 안 되니 다른 방법으로 답해 보자"고 스스로 대처합니다.

도구의 반환값은 사람이 아니라 LLM에게 하는 보고입니다. 그래서 실패도 보고 대상이에요.

⚠️ ddgs 버전 주의

이 패키지는 예전에 duckduckgo-search라는 이름이었고, 지금도 반환 키(title·body·href)나 호출 방식이 마이너 버전에서 바뀝니다. 위 코드가 .get()을 쓰는 건 키가 없어도 안 죽게 하려는 것입니다. 결과가 이상하면 uv run python -c "from ddgs import DDGS; print(DDGS().text('langchain', max_results=1))"로 실제 반환 모양부터 찍어 보세요.

② agent.py — 첫 Agent 조립

도구를 만들었으니 이제 모델에 쥐여 줍니다. create_agent 한 번이면 끝나는데, 같이 넘기는 system_prompt가 생각보다 큰 일을 합니다. LLM은 "1234 × 5678" 정도는 도구 없이 답하려 들거든요 — 그리고 종종 틀립니다. "반드시 도구를 써라"라고 못 박아야 실제로 씁니다.

agent.py
# ═══════════════════════════════════════════════════════════════════
# STEP 1 · Agent 조립: 모델 + 도구 + 시스템 프롬프트를 하나로 묶는다.
# 이 파일이 앞으로 메모리(STEP 3) · 가드레일(STEP 4) · 관측(STEP 6) · 모델선택(STEP 7)을
# 하나씩 얹어 가며 자라날 자리다. 지금은 가장 앙상한 뼈대만 세운다.
# ═══════════════════════════════════════════════════════════════════
from dotenv import load_dotenv
from langchain.agents import create_agent

from tools import get_today, calculate, web_search   # STEP 1에서 만든 도구들

load_dotenv()                                        # .env의 OPENAI_API_KEY 로드

# 시스템 프롬프트 = Agent의 '행동 지침서'. 매 요청마다 대화 맨 앞에 조용히 붙는다.
# 도구를 쥐여 줬다고 알아서 쓰지는 않는다 — '언제 써야 하는지'까지 여기서 못 박아야 한다.
SYSTEM_PROMPT = """너는 정확성을 최우선으로 하는 업무 비서다.

규칙:
1. 오늘 날짜·현재 시각이 필요하면 반드시 get_today를 호출한다. 날짜를 추측하지 않는다.
2. 숫자 계산은 반드시 calculate를 호출한다. 암산하지 않는다.
3. 최신 정보가 필요하면 web_search를 호출하고, 답변에 출처 URL을 함께 적는다.
4. 도구로도 확인할 수 없는 내용은 모른다고 말한다. 지어내지 않는다."""

# 모델은 "provider:model" 문자열로도 넘길 수 있다. STEP 7에서 이 부분을 갈아끼운다.
agent = create_agent(
    model="openai:gpt-5-mini",
    tools=[get_today, calculate, web_search],
    system_prompt=SYSTEM_PROMPT,
)

def ask(message: str):
    """질문 하나를 Agent에 던지고, 오간 메시지 전체를 돌려준다.

    최종 답변만이 아니라 messages 전체를 돌려주는 게 지금 단계에서는 중요하다.
    '어떤 도구를 왜 골랐는지'가 그 안에 다 들어 있고, 그걸 봐야 학습이 된다.
    """
    result = agent.invoke({"messages": [{"role": "user", "content": message}]})
    return result["messages"]


if __name__ == "__main__":
    import sys
    question = sys.argv[1] if len(sys.argv) > 1 else "오늘 며칠이야? 그리고 1234 곱하기 5678은?"

    for m in ask(question):
        # 메시지 종류(human / ai / tool)와 내용을 한 줄씩 찍는다.
        # AIMessage는 도구를 부를 때 content가 비어 있고 tool_calls에만 내용이 있다 —
        # 그래서 둘 다 찍어야 무슨 일이 있었는지 보인다.
        print(f"\n[{m.type}] {m.content}")
        if getattr(m, "tool_calls", None):
            print(f"    ↳ 호출: {[(c['name'], c['args']) for c in m.tool_calls]}")
✅ 검증 게이트

세 질문을 던져 매번 다른 도구가 호출되는지 확인합니다. 이게 확인되면 Agent가 "스스로 고르고 있다"는 증거입니다.

# 1) 도구 두 개를 연달아 쓰는가
uv run python agent.py "오늘 며칠이야? 그리고 1234 곱하기 5678은?"
#    → get_today · calculate 호출이 각각 보이고, 곱셈 결과가 7006652 로 정확해야 한다

# 2) 웹 검색을 고르는가
uv run python agent.py "LangChain 1.0의 주요 변화가 뭐야?"
#    → web_search 호출 + 답변에 출처 URL

# 3) 도구를 '안 쓰는' 판단도 하는가  ← 이게 가장 중요하다
uv run python agent.py "안녕? 너는 무슨 일을 할 수 있어?"
#    → tool_calls 가 하나도 없어야 한다

3번이 핵심입니다. 모든 질문에 도구를 부르는 Agent는 고르는 게 아니라 그냥 다 부르는 것이고, 그건 비용과 지연만 늘립니다. "안 쓰는 판단"까지 되어야 통과입니다.

🔍 잘 안 될 때 — docstring부터 의심하세요

엉뚱한 도구를 부르거나 안 불러야 할 때 부른다면, 코드가 아니라 설명이 문제일 확률이 훨씬 높습니다. LLM이 보는 정보는 이름·타입 힌트·docstring이 전부라는 걸 기억하세요. "언제 써야 하는지"와 "언제 쓰면 안 되는지"를 둘 다 적으면 정확도가 확 올라갑니다 — web_search의 docstring 마지막 줄("사내 문서나 약관의 내용은 이 도구로 찾을 수 없다")이 바로 그 장치이고, STEP 2에서 이 한 줄이 왜 필요했는지 드러납니다.

🎓 배우는 것

Agent의 실행 모델 — LLM은 도구를 주문하고 랭체인이 실행한다는 역할 분담. 그리고 도구 설계는 함수 작성이 아니라 설명서 작성이라는 것. 여기에 실무 습관 두 개가 붙었습니다: LLM이 만든 문자열은 의심하고(eval 금지), 도구의 실패는 예외가 아니라 LLM에게 보고할 메시지로 다룬다.
