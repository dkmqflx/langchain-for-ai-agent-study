5

FastAPI로 서빙

서비스화 층(얇음) ⏱ 반나절
🎯 목표

answer()를 HTTP API로 노출한다. 이 순간 "노트북 코드"가 "서비스"가 됩니다.

🧠 개념

FastAPI는 파이썬 함수를 타입이 검증되는 HTTP 엔드포인트로 바꿔줍니다. pydantic 모델로 요청/응답 스키마를 정의하면, 잘못된 입력은 자동으로 거부되고 응답 형태가 문서화됩니다. 토스 "실험→서빙→운영", 카카오 "서비스에 탑재 가능한 형태"의 첫걸음입니다. 랭체인 관점에서 새로 배울 것은 없고, 이미 만든 함수를 감싸는 50줄입니다.

🛠 할 일

만들 파일은 main.py 하나입니다. RAG 로직은 한 줄도 새로 안 씁니다 — 이미 완성된 answer()를 HTTP로 감싸기만 해요. 네 조각으로 나눠 보고, 맨 아래 전체 코드를 복사하세요.

🧭 네 조각 한눈에

① 앱 만들고 answer 가져오기  →  ② 주고받을 데이터 모양 선언  →  ③ /health  →  ④ /query

① 앱 만들고 answer 가져오기

main.py
from fastapi import FastAPI          # 파이썬 함수를 HTTP 창구로 바꿔 주는 웹 프레임워크
from pydantic import BaseModel       # 주고받을 데이터의 '모양(스키마)'을 선언하는 클래스
from rag import answer               # STEP 2~4에서 만든 RAG 함수를 그대로 가져다 쓴다

# 앱 객체 — 앞으로 만들 창구(엔드포인트)들이 여기에 등록된다.
# title은 서버를 켠 뒤 http://localhost:8000/docs 에 자동 생성되는 문서 페이지의 제목이 된다.
app = FastAPI(title="P1 RAG Search Service")

from rag import answer — 이 한 줄이 STEP 2~4를 통째로 재사용합니다. 검색기를 mode 문자열로 갈아끼울 수 있게 만들어 둔 덕분에, API 쪽은 그저 함수를 부르기만 하면 돼요. title은 잠시 뒤 자동 생성되는 문서 페이지의 제목이 됩니다.

② 주고받을 데이터의 "모양" 선언하기

API는 낯선 사람이 아무 JSON이나 보낼 수 있는 창구입니다. 그래서 먼저 계약서를 씁니다 — "요청은 이런 모양이어야 하고, 응답은 이런 모양으로 주겠다." 이걸 스키마라 하고, pydantic의 BaseModel로 선언합니다.

main.py (이어서)
# 요청 스키마 — 사용자가 보내야 하는 JSON의 모양
class QueryIn(BaseModel):
    question: str          # 반드시 있어야 한다. 없으면 FastAPI가 자동으로 422 에러로 거절한다
    mode: str = "rerank"   # 기본값이 있으니 안 보내도 된다. 보내면 검색 구성을 골라 실험할 수 있다

# 근거 1건의 스키마
class Citation(BaseModel):
    source: str | None = None   # 파일 경로. | None = '없어도 된다'는 뜻
    page: int | None = None     # 쪽 번호. PDF에 따라 안 잡히는 경우가 있어 없음을 허용해 둔다
                                # (허용 안 하면 page가 없는 순간 응답 전체가 에러로 터진다)

# 응답 스키마 — 우리가 돌려주겠다고 약속하는 JSON의 모양
class QueryOut(BaseModel):
    answer: str                 # 답변 텍스트
    citations: list[Citation]   # 위 Citation이 여러 개 담긴 목록

선언만 해두면 FastAPI가 알아서 검사합니다. question 없이 요청이 오면 내 코드가 실행되기 전에 자동으로 거절되고(422 응답), 무엇이 잘못됐는지도 알려줍니다. if not question: return "에러" 같은 검사 코드를 직접 안 써도 되는 거죠.

  • mode: str = "rerank" — 기본값이 있으니 안 보내도 됩니다. 대신 보내면 검색 구성을 골라 실험할 수 있어요.
  • source: str | None = None — "없을 수도 있음"을 허용합니다. PDF에 따라 page가 안 잡히는 경우가 있는데, 이걸 허용 안 하면 그때 응답 전체가 에러로 터집니다.

③ /health — 서버가 살아있는지 묻는 창구

main.py (이어서)
# @app.get("/health") = "누가 GET 방식으로 /health 주소를 찾아오면 아래 함수를 실행해라"는 등록표.
# 함수 위에 붙는 이런 표시를 데코레이터라 한다.
@app.get("/health")
def health():
    return {"status": "ok"}   # dict를 돌려주면 FastAPI가 알아서 JSON으로 바꿔 보낸다
                              # RAG를 태우지 않으므로 빠르고 공짜 — 그래서 감시 도구가 몇 초마다 찔러볼 수 있다

하는 일이 없어 보이지만 운영의 기본기입니다. 실제 서비스에서는 감시 도구가 이 주소를 몇 초마다 찔러 보고, 응답이 없으면 "서버가 죽었다"고 알림을 보내거나 자동으로 다시 띄웁니다. RAG를 태우지 않아 빠르고 공짜라는 게 핵심이에요 — 살아있는지 확인하는 데 매번 LLM을 부를 순 없으니까요.

④ /query — 진짜 창구

main.py (이어서)
# post = 질문을 주소창이 아니라 '본문(body)'에 담아 보내는 방식. 긴 문장·한글을 담기에 적합하다.
# response_model=QueryOut → 돌려주는 값이 QueryOut 모양인지 검사하고, /docs 문서에도 그 모양이 적힌다.
@app.post("/query", response_model=QueryOut)
def query(body: QueryIn):                              # body: QueryIn → 들어온 JSON이 자동으로 검사·변환되어 넘어온다
    result = answer(body.question, mode=body.mode)     # RAG 실행 (검색 + 생성 + 근거)
    # contexts(검색된 원문 전체)는 일부러 뺀다 — 응답만 무거워지고 사용자에게는 필요 없다.
    # 그건 STEP 7 채점용이며, response_model이 이 약속을 강제해 준다.
    return {"answer": result["answer"], "citations": result["citations"]}

post인 이유는 질문을 본문(body)에 담아 보내기 때문입니다. get은 주소창에 정보를 붙이는 방식이라 긴 문장이나 한글을 담기에 불편하죠. body: QueryIn이라고 적어두면 들어온 JSON이 자동으로 검사·변환되어 넘어옵니다.

💡 contexts는 왜 응답에서 뺐을까요?

answer()는 answer·citations·contexts 셋을 돌려주지만, API는 앞의 둘만 내보냅니다. contexts는 검색된 원문 전체라 응답이 몇 배로 무거워지는데, 정작 사용자에게는 필요 없거든요(어디서 왔는지는 citations로 충분). 그건 STEP 7의 채점용입니다. response_model=QueryOut이 이 약속을 강제해서, 실수로 딴 게 섞여 나가는 것도 막아 줍니다.

📄 전체 코드 (위 네 조각을 이어 붙인 것)
main.py
# ═══════════════════════════════════════════════════════════════════
# STEP 5 · FastAPI 서빙: answer()를 HTTP API(POST /query)로 노출한다.
# pydantic 모델로 요청/응답 '스키마'를 선언 → 잘못된 입력은 자동 거부, /docs에 문서가 자동 생성.
# 이 순간 '노트북 코드'가 '서비스'가 된다.
# ═══════════════════════════════════════════════════════════════════
from fastapi import FastAPI
from pydantic import BaseModel          # 요청/응답의 형태(스키마)를 선언하는 클래스
from rag import answer                  # STEP 2~4에서 만든 핵심 함수 그대로 재사용

app = FastAPI(title="P1 RAG Search Service")   # 앱 객체. title은 /docs 문서 제목에 표시됨

class QueryIn(BaseModel):               # 요청 본문 스키마
    question: str
    mode: str = "rerank"                # baseline|hybrid|rerank — 검색 구성도 API로 고를 수 있게(실험용)

class Citation(BaseModel):              # 근거 1건의 스키마
    source: str | None = None           # 파일 경로 (없을 수 있어 None 허용)
    page: int | None = None             # 쪽 번호

class QueryOut(BaseModel):              # 응답 스키마: 답변 + 근거 목록
    answer: str
    citations: list[Citation]

@app.get("/health")                     # 헬스체크: 서버가 살아있는지 확인하는 운영 기본 엔드포인트
def health():
    return {"status": "ok"}

@app.post("/query", response_model=QueryOut)   # POST /query. 응답을 QueryOut 형태로 검증·문서화
def query(body: QueryIn):               # body는 요청 JSON이 QueryIn으로 자동 파싱·검증된 결과
    result = answer(body.question, mode=body.mode)   # RAG 실행(검색 + 생성 + 근거)
    return {"answer": result["answer"], "citations": result["citations"]}   # contexts는 응답에서 제외

실행: uv run uvicorn main:app --reload

✅ 검증 게이트 서버를 켜고 아래가 답변 + citations JSON을 돌려주면 통과. 브라우저로 http://localhost:8000/docs(자동 생성 API 문서)도 열어보세요. 
curl -X POST http://localhost:8000/query \
  -H "Content-Type: application/json" \
  -d '{"question": "문서에 있는 내용을 물어보세요"}'
