Agent 코어 ② — P1의 RAG를 Tool로 장착

🟢 랭체인 집중 ⏱ 1~2시간
🎯 목표

P1이 만들어 둔 POST /query를 부르는 도구를 하나 더 만들어 Agent에 꽂습니다. 그러면 약관 질문에는 이 도구를, 일반 질문에는 다른 도구를 Agent가 알아서 고릅니다.

🧠 개념 — 딱 하나만

같은 RAG인데, 감싸는 방식이 바뀌면 동작이 바뀝니다

P1의 RAG는 질문이 뭐든 무조건 벡터DB를 뒤졌습니다. 코드가 그렇게 생겼으니까요. "안녕하세요"라고 인사해도 약관을 검색했고, "1+1은?"에도 약관을 검색했습니다. 검색은 공짜가 아닙니다 — 임베딩 호출과 리랭커 실행이 들고, 엉뚱한 청크가 프롬프트에 실려 답변까지 흐려집니다.

같은 RAG를 도구로 감싸면 "이 질문은 우리 문서에 답이 있을 법한가"라는 판단이 LLM에게 넘어갑니다. P1 코드는 한 줄도 안 고치는데 동작이 달라져요. 바뀐 건 그걸 부르는 쪽의 구조뿐입니다.

마지막 줄이 이 STEP의 전부입니다. 판단을 LLM에게 넘겼으니, LLM이 읽는 문장(docstring)이 곧 코드가 됩니다. 도구를 만드는 코드는 15줄이면 끝나요. 어려운 건 web_search와 search_internal_docs를 헷갈리지 않게 설명하는 일입니다 — 둘 다 "찾아본다"는 도구니까요.

docstring결과
"""문서를 검색한다.""" ❌ 어떤 문서인지 없음 → 웹 검색과 구분이 안 돼 아무 질문에나 부른다
"""사내 문서를 검색한다.""" △ 나아졌지만 "거기 뭐가 들었는지"를 모르니 여전히 헛다리를 짚는다
무엇이 들었는지 + 어떤 질문에 쓰는지 + 언제 쓰면 안 되는지 ✅ 약관 질문에만 정확히 걸린다
🗂 비유 — 신입에게 넘기는 인수인계서

"저 캐비닛 참고하세요"라고만 하면 신입은 아무 때나 캐비닛을 열어 봅니다. "저 캐비닛엔 우리 회사 금융 약관 네 종이 들어 있어요. 조항이나 수수료 규정을 물어보면 거기서 찾고, 바깥 뉴스는 거기 없으니 인터넷을 보세요." 이렇게 적어 줘야 제대로 씁니다. docstring이 딱 이 인수인계서예요. 그리고 "거기 없는 것"까지 알려 주는 게 절반입니다.

tools.py 맨 아래 — 네 번째 도구

— 이 STEP의 본체. 절반이 docstring이다
# ── 도구 4 · 사내 문서 검색 (P1 RAG 서비스 호출) ──────────────────
@tool
def search_internal_docs(question: str) -> str:
    """사내 문서에서 근거와 함께 답을 찾는다.

    보유 문서: 예금거래기본약관, 전자금융거래기본약관, 신용카드 개인회원 표준약관,
    은행여신거래기본약관(가계용), 금융소비자의 소리 자료.

    약관·조항·수수료·책임 범위·해지 절차처럼 "우리 문서에 뭐라고 적혀 있는가"를
    묻는 질문에 사용한다. 일반 상식이나 최신 뉴스에는 사용하지 않는다(그건 web_search).

    Args:
        question: 사용자의 질문을 한 문장으로 전달한다. 대명사("그거", "거기")는
            앞 대화를 참고해 구체적인 말로 바꿔서 넘긴다.
    """
    try:
        r = requests.post(
            f"{P1_API_URL}/query",
            json={"question": question, "mode": "rerank"},   # P1이 만든 최고 성능 구성
            timeout=60,          # 리랭커는 느리다. 첫 호출은 모델 다운로드까지 겹친다
        )
        r.raise_for_status()     # 4xx·5xx면 여기서 예외 → 아래 except로 간다
    except requests.exceptions.RequestException as e:
        # P1이 꺼져 있어도 Agent는 멈추지 않는다. '실패했다'는 사실을 LLM에게 보고할 뿐이다.
        # 뒷문장이 중요하다 — '그럼 어떻게 하라'까지 알려 줘야 엉뚱하게 지어내지 않는다.
        return (f"사내 문서 검색 서비스에 연결할 수 없습니다({e}). "
                "이 질문은 사내 문서로 확인할 수 없다고 사용자에게 알려라.")

    data = r.json()

    # 근거 정리: 같은 페이지에서 여러 청크가 걸리는 일이 흔해 중복을 걷어낸다.
    # (dict.fromkeys는 순서를 지키면서 중복만 없애는 관용구다)
    cites = list(dict.fromkeys(
        f"{c.get('source')} p.{c.get('page')}" for c in data.get("citations", [])
    ))

    # 근거를 같이 넘겨야 Agent가 최종 답변에 "「신용카드 표준약관」 40쪽에 따르면..."처럼 인용할 수 있다.
    return f"{data['answer']}\n\n[근거] " + " / ".join(cites)

서비스 경계에서 해야 하는 세 가지가 이 함수에 다 들어 있습니다 — timeout을 정하고, 실패를 예외 대신 문자열로 바꾸고, 그 문자열에 LLM이 다음에 할 행동까지 적는 것. 예외를 그대로 올리면 Agent 전체가 멈추지만, 문자열로 돌려주면 LLM은 "그 도구는 지금 못 쓰는구나" 하고 나머지로 답을 맺습니다.

agent.py — 등록하고 우선순위 적기

— 도구가 넷이 되면 프롬프트에서 한 번 더 정리해 준다
from tools import get_today, calculate, web_search, search_internal_docs   # ← 추가

SYSTEM_PROMPT = """너는 정확성을 최우선으로 하는 업무 비서다.

규칙:
1. 오늘 날짜·현재 시각이 필요하면 반드시 get_today를 호출한다. 날짜를 추측하지 않는다.
2. 숫자 계산은 반드시 calculate를 호출한다. 암산하지 않는다.
3. 약관·규정·계약 조건에 관한 질문은 web_search보다 search_internal_docs를 먼저 쓴다.
   우리 문서에 있는 내용을 인터넷에서 찾으면 틀린 답이 나온다.
4. search_internal_docs의 결과를 쓸 때는 답변에 [근거]의 문서명과 쪽수를 반드시 적는다.

agent = create_agent(
    model="openai:gpt-5-mini",
    tools=[get_today, calculate, web_search, search_internal_docs],   # ← 추가
    system_prompt=SYSTEM_PROMPT,
)

새로 붙은 건 규칙 3번과 4번입니다. 3번은 약관 질문이 web_search로 새지 않게 우선순위를 못 박고, 4번은 찾은 근거를 답변에 인용하게 합니다. docstring은 도구 하나를 설명하고, 시스템 프롬프트는 도구 사이의 순서를 정합니다 — 역할이 다릅니다.

✅ 검증 — 네 가지

uv run python agent.py "신용카드를 분실하면 회원 책임은 어디까지야?"

# 2) 일반 상식 → 사내 문서를 부르지 '않는가'

uv run python agent.py "카드 연회비 관련 조항 찾아보고, 연회비가 15000원이면 5년치는 얼마야?"

  • 부른다 — ↳ 호출: [('search_internal_docs', ...)]이 찍히고, 답변에 문서명·쪽수가 인용돼 있다
  • 안 부른다 — 리스트와 튜플 질문에는 도구를 하나도 부르지 않는다

네 번째가 서비스를 두 개로 나눈 값입니다. P1이 멈춰도 P2는 나머지 도구로 계속 일해요. 확인했으면 P1을 다시 켜 두세요.

🎓 한 줄 정리

같은 RAG라도 체인으로 부르면 개발자가 판단하고, 도구로 감싸면 LLM이 판단한다. 판단을 넘긴 이상 docstring이 곧 코드이고, 다른 서비스를 부르는 자리에서는 실패도 답변의 일부로 만들어야 한다.

더 알아보기 — 첫 호출이 느릴 때 / 왜 import 대신 HTTP인가 / 규칙 3번이 막는 것

첫 호출이 유독 느리다면

P1의 rerank 모드는 Cross-Encoder 모델을 씁니다. 그 서버에서 처음 한 번은 모델을 내려받느라 수십 초가 걸릴 수 있어요. 도구에 timeout=60을 넉넉히 잡아 둔 이유입니다. 그래도 넘친다면 P1을 curl로 한 번 미리 깨워 두거나, 도구에서 "mode": "hybrid"로 바꿔 리랭커를 건너뛰면 됩니다.

P1을 import 하지 않고 HTTP로 부르는 이유

같은 컴퓨터에 있으니 from project1.rag import ...처럼 가져다 쓸 수도 있습니다. 그렇게 하면 P2가 Chroma도, 임베딩 모델도, 리랭커도 전부 같이 짊어지게 됩니다. 라이브러리 버전이 하나만 어긋나도 두 프로젝트가 함께 막히고요.

HTTP로 부르면 P2가 아는 건 주소 하나와 JSON 모양뿐입니다. P1을 다른 서버로 옮겨도 .env의 P1_API_URL만 바꾸면 되고, P1이 멈춰도 P2는 살아 있어요. 도구 하나를 이렇게 감싸 두면 나중에 P1을 통째로 다른 구현으로 갈아끼워도 P2는 모릅니다.

규칙 3번이 실제로 막는 것

이 줄이 없으면 Agent는 약관 질문에도 web_search를 곧잘 부릅니다. 그리고 인터넷에서 찾은 다른 회사의 약관으로 그럴듯하게 답해요. 문장은 매끄러운데 우리 약관과 내용이 다릅니다. 이런 답은 틀린 티가 안 나서 사람이 읽어도 잘 못 잡습니다. 그래서 STEP 8의 평가 케이스에는 답변 내용뿐 아니라 expect_tool(어떤 도구를 썼어야 하는가)을 함께 적습니다 — "맞는 도구를 골랐는가"는 사람 대신 코드가 셀 수 있는 항목이거든요.
