2. Agent 구축 실전 — 기획부터 LLM·Tool 결합까지

실습 노트북: 2.ipynb  ·  대상 범위: 2-1 프로젝트 기획 ~ 2-2 실전 구현 (실전 1 · 실전 2)  ·  난이도: 🟡 초급~중급

1장에서 State · Node · Edge · Conditional Edge라는 네 개의 부품을 손에 익혔습니다. 이번 장은 그 부품으로 진짜 프로젝트 하나를 처음부터 끝까지 만듭니다 — 고객 이메일 자동 응대 에이전트. 다만 바로 코드로 들어가지 않습니다. 실무에서 에이전트를 만들 때 코드보다 먼저 해야 하는 "기획 3단계"를 배우고, 그 기획서를 그대로 코드로 옮기는 과정을 두 번 반복합니다 — 실전 1(키워드 라우팅)로 뼈대를 잡고, 실전 2(LLM + Tool)로 지능을 얹습니다.

2-1. 프로젝트 기획 — 왜 코드보다 기획이 먼저인가

회사에서 이런 업무를 하나 받았다고 해봅시다.

1장에서 배운 순서대로라면 ①모델·도구 → ②State → ③Node → ④그래프 → ⑤실행이니 곧장 class State(TypedDict):부터 치고 싶어집니다. 그런데 그러면 안 됩니다.

🚫 기획 없이 시작하면 벌어지는 일

State를 대충 두 칸으로 만들고 코딩을 시작합니다. 노드를 세 개쯤 짜다 보면 "아, 여기서 분류 결과도 State에 담아야 다음 노드가 쓸 수 있네"를 깨닫습니다. State 클래스를 고칩니다. 그러면 이미 만든 노드들의 반환 딕셔너리도 전부 손봐야 합니다. 또 짜다 보면 또 필드가 필요해집니다. 코드가 스파게티처럼 꼬입니다.

기획을 먼저 하면 두 번 일하지 않고, 코드도 깔끔해집니다.

🔍 비유 — 집 짓기 전 설계도

벽돌부터 쌓기 시작한 집을 상상해 보세요. 방 세 개를 다 만들고 나서 "화장실 배관을 어디로 빼지?"를 고민하면 이미 늦었습니다. 벽을 부숴야 하죠.

State는 정확히 배관입니다. 모든 노드가 State를 통해서만 데이터를 주고받기 때문에, State를 나중에 바꾸면 모든 방의 벽을 뜯어야 합니다. 그래서 배관 도면(State 설계)을 벽 세우기(코딩) 전에 그리는 겁니다.

기획도 3단계 — 코드 순서와 "일부러" 다릅니다

재미있는 건, 기획의 순서가 코딩 순서와 다르다는 점입니다. 코드는 State를 먼저 짜지만, 기획은 State를 맨 마지막에 합니다. 이유는 간단합니다 — 노드들이 무슨 일을 하는지 다 정해져야, 그 노드들이 뭘 주고받을지 알 수 있기 때문입니다.

이 에이전트가 어떤 기능을 해야 하나? → 기능 하나 = 노드 하나

2그래프 구성

노드를 어떻게 배치하고 이을까? → 유저 플로우 그리기

3State 설계

노드끼리 뭘 주고받아야 하나? → 필드와 키 이름 확정

💡 기획 순서 vs 코딩 순서

기획: 요구사항 → 노드 → 그래프 → State  (무슨 일을 할지 정하고, 그 일에 필요한 데이터를 뽑는다)
코딩: 모델·도구 → State → 노드 → 그래프 → 실행  (데이터 양식이 있어야 노드 함수를 쓸 수 있다)

방향이 정반대인 게 헷갈릴 수 있는데, 기획은 "무엇을 할까"에서 데이터로 내려가고, 코딩은 데이터에서 "무엇을 할까"로 올라간다고 생각하면 됩니다.

기획 1단계 · 요구사항 분석 — 기능 하나가 노드 하나

"고객 이메일 자동 응대 에이전트"가 어떤 기능을 해주면 좋을까?를 자유롭게 나열합니다. 아직 코드 생각은 하지 마세요. 기획자 모드입니다.

왜 기능이 그대로 노드가 될까요? 1장의 정의를 떠올려 보면 당연합니다. 노드는 State를 기반으로 일하는 "작업자"였죠. 그리고 우리가 방금 나열한 것들 — 이메일을 읽고, 긴급성을 판단하고, 문서를 검색하고, 상담원을 연결하고 — 이게 전부 "하나의 일"입니다. 일 하나 = 작업자 하나 = 노드 하나.

이제 각 기능에 노드 이름(함수 이름)을 붙입니다. 여기서 이름을 확정해 두면 나중에 add_node·add_edge·라우팅 함수까지 전부 이 이름을 재사용하게 됩니다.

💡 "뼈대만"이라는 선택지

search_manual은 원래 RAG(검색 증강 생성)로 사내 문서를 뒤져야 합니다. 그런데 임베딩·청킹·벡터DB까지 지금 붙이면 정작 배우려던 그래프 구조가 안 보입니다. 그래서 이번엔 print() 한 줄만 넣고 넘어갑니다.

이건 대충 하는 게 아니라 의도적인 학습 전략입니다. 흐름을 먼저 완성해 두면 나중에 그 노드 안쪽만 진짜 RAG 코드로 갈아끼우면 되니까요. 실전 2에서 실제로 그렇게 합니다.

기획 2단계 · 그래프 구성 — 노드를 어떻게 배치할까

노드 이름표가 다섯 장 생겼습니다. 지금은 책상 위에 흩어져 있는 상태입니다.

순서대로 생각해 봅시다. 사용자 입장에서 이야기를 만들어 보는 것이 요령입니다.

  1. 이메일이 들어오면 먼저 읽는다. → START → read_email
  2. 읽은 메일의 의도와 주제를 파악한다(분류). → read_email → classify_intent
  3. (Case A) 급하지 않은 문의라면 — 매뉴얼을 검색한 뒤 답변을 작성한다. → search_manual → write_reply → END
  4. (Case B) 긴급한 메일이라면 — 사람(상담원)에게 넘긴다. → escalate_to_human → END
🔍 비유 — 실선은 복도, 점선은 갈림길

사무실 바닥에 화살표를 그린다고 생각해 보세요. 실선은 "여기서 나가면 무조건 저기"인 복도입니다. read_email → classify_intent가 그렇죠. 이메일을 읽었으면 분류는 무조건 합니다.

점선은 갈림길에 세워둔 표지판입니다. classify_intent를 나오는 순간 "긴급하면 왼쪽, 아니면 오른쪽"을 그때그때 판단해야 하죠. 기획 단계에서 실선/점선을 구분해 두면, 코드에서 add_edge와 add_conditional_edges가 저절로 갈립니다.

기획 3단계 · State 설계 — 노드끼리 뭘 주고받을까

마지막입니다. 그래프 그림을 보면서 화살표를 하나씩 따라가며 묻습니다 — "이 노드가 다음 노드한테 뭘 넘겨줘야 하지?"

노드를 하나씩 짚어가며 State에 담을지 말지를 결정한 과정은 이렇습니다.

START

고객이 보낸 이메일 원문이 들어옵니다. 이건 뒤에 나오는 거의 모든 노드가 봐야 하죠. → 필드로 담는다 (str)

read_email

원래대로면 키워드를 뽑아 담을 수도 있지만, 이번엔 단순히 넘기기만 합니다. → 새로 담을 것 없음

classify_intent

① 고객이 메일을 보낸 의도(주제) → 담는다 (str)
② 분류 결과(상담원 연결이냐, 매뉴얼 검색이냐) → 반드시 담는다. 이 값이 있어야 다음 갈림길에서 분기 판단을 할 수 있으니까요. (str)

RAG 검색 결과를 담아야 정석이지만, 이번엔 RAG를 구현하지 않으므로 → 이번엔 담지 않음

💡 next_step의 값을 "노드 이름과 똑같이" 맞추는 이유

next_step에 담을 문자열은 자유입니다. "긴급"이라고 써도 되고 "급함"이라 써도 됩니다. 그런데 강의에서는 굳이 "escalate_to_human", "search_manual" — 즉 실제 노드 이름과 글자 하나까지 똑같이 맞췄습니다.

이유는 뒤에서 드러납니다. 조건부 엣지의 라우팅 함수는 "갈 노드의 이름 문자열"을 반환해야 하는데, next_step 값이 이미 노드 이름이면 그대로 return하기만 하면 되고, 오타로 인한 에러 확률이 확 줄어듭니다. 기획 단계의 작은 결정이 코딩 단계의 버그를 미리 막은 셈입니다.

1장과 똑같습니다. Gemini Flash 모델 객체를 하나 만듭니다. 도구(Tool)는 이번 실전 1에서는 만들지 않습니다.

💡 왜 실전 1에는 도구가 없을까

도구를 붙이면 tool_calls 딕셔너리를 꺼내고 ToolMessage로 포장하는 코드가 따라붙습니다. 1장에서 이미 한 번 겪었듯 그 부분이 난이도의 대부분이죠.

실전 1의 목표는 "기획서를 코드로 옮기는 감각"을 익히는 것이므로, 도구는 실전 2로 미룹니다. 한 번에 한 가지씩만 새로 배우는 게 훨씬 빠릅니다.

STEP 2. State 정의 — 기획서를 그대로 옮기기

기획 3단계에서 확정한 네 개의 키를 그대로 TypedDict로 옮깁니다. 기획을 해두면 이 단계가 10초 만에 끝납니다.

📥 코드
from typing_extensions import TypedDict

class AgentState(TypedDict):
    email_content: str   # 고객이 보낸 이메일 원문
    category: str        # 분류된 주제/의도 (inquiry / complaint)
    next_step: str       # 다음에 갈 노드 이름 → 분기 판단 기준
    response: str        # LLM이 만든 최종 답변
💡 1장의 State와 다른 점 — 리듀서가 없다

1장에서는 messages: Annotated[list[AnyMessage], add_messages]처럼 리듀서(add_messages)를 붙였습니다. "덮어쓰지 말고 이어 쓰라"는 규칙이었죠.

이번 State에는 리듀서가 하나도 없습니다. 전부 덮어쓰기입니다. 그리고 그게 맞습니다 — category는 최신 분류 결과 하나만 있으면 되고, response도 최종 답변 하나만 있으면 되니까요. "누적해야 하는 값"에만 리듀서를 붙인다고 기억하면 됩니다.

STEP 3. Node 정의 — 다섯 명의 작업자

기획 1단계에서 이름까지 다 지어놨으니, 이제 함수 다섯 개를 씁니다. 1장에서 배운 노드의 계약은 그대로입니다.

💡 노드의 계약(contract) — 딱 두 줄
  1. state를 입력 파라미터로 받는다. (공책을 건네받아야 하니까)
  2. State 양식에 맞는 딕셔너리를 반환한다. (공책에 적을 내용만 적어서 돌려주니까)

① read_email — 이메일을 받아 공책에 옮겨 적기

📥 코드
# [Node 1] 이메일 읽기
def read_email(state: AgentState):
    return {'email_content': state['email_content']}

코드가 너무 단순해서 오히려 당황스러운 노드입니다. state['email_content']를 꺼내서 그대로 다시 email_content에 넣고 있죠. 아무것도 안 바꾸는데 왜 있는 걸까요?

답은 "원래는 여기서 일을 해야 하기 때문"입니다. 원래 이 노드는 이메일을 읽고 키워드를 뽑거나 전처리를 해야 합니다. 이번엔 그걸 생략했기 때문에 "받은 걸 그대로 넘기는" 뼈대만 남은 겁니다. 실무에서는 이 자리에 로깅, 첨부파일 파싱, 발신자 조회 같은 게 들어갑니다.

더 중요한 것 — 이 노드가 invoke()의 입력 형식을 결정한다

1장에서는 agent.invoke({"messages": [HumanMessage(...)]})처럼 넣었습니다. 그런데 이번 State에는 messages가 없습니다. 그럼 뭘 넣어야 할까요?

read_email이 state['email_content']에 접근하고 있으니, 그 칸이 채워진 채로 들어와야 합니다. 즉 실행할 때 이렇게 넣어야 하죠.

▶ 그래서 실행은 이렇게 됩니다 (STEP 5 미리보기)
inputs = {"email_content": "비밀번호 변경 방법을 알려주세요."}
response = agent.invoke(inputs)
🔍 비유 — 접수 창구의 서식

민원실에 가면 "성명 / 주소 / 용건" 칸이 있는 서식을 줍니다. 아무 종이에나 써 오면 접수가 안 되죠. invoke()에 넘기는 딕셔너리가 바로 그 서식입니다.

1장의 서식은 {"messages": [...]}였고, 이번 서식은 {"email_content": "..."}입니다. 서식(=State 클래스)이 바뀌면 접수 방법도 바뀐다는 것 — 이게 State를 먼저 설계해야 하는 또 하나의 이유입니다.

② classify_intent — 갈림길의 판단 근거를 만드는 노드

이 그래프에서 가장 중요한 노드입니다. 여기서 만든 값에 따라 흐름이 갈라지니까요.

📥 코드
# [Node 2] 의도 분류 (Router 로직의 기준점)
def classify_intent(state: AgentState):
    email = state['email_content']

    # 언어 모델 대신 "키워드"로 판단 — 실전 2에서 LLM으로 바꿉니다
    if '환불' in email or '긴급' in email or '빨리' in email:
        category = 'complaint'
        next_step = 'escalate_to_human'
    else:
        category = 'inquiry'
        next_step = 'search_manual'

    return {'category': category, 'next_step': next_step}

한 줄씩 뜯어봅시다.

email = state['email_content'] — 앞 노드가 남긴 것을 읽는다

read_email이 email_content를 채워서 넘겼기 때문에, 이 노드는 그 칸에 접근하기만 하면 이메일 원문을 얻습니다. 두 노드는 서로 직접 대화하지 않았습니다. 오직 공책(State)을 통해서만 소통했죠.

키워드 매칭 — 지금은 "지능"이 없습니다

'환불' in email은 그냥 파이썬 문자열 포함 검사입니다. 언어 모델은 여기에 관여하지 않습니다. 이건 의도된 단순화이고, 바로 이 지점이 실전 1의 한계가 됩니다. (뒤에서 직접 깨뜨려 봅니다.)

반환값 두 개 — 왜 next_step까지 담을까

category는 "이 메일이 무엇인가"를 기록하는 값입니다. 사람이 보는 라벨이죠.
next_step은 "그래서 어디로 갈 것인가"를 기록하는 값입니다. 기계가 보는 표지판이죠.

둘을 나눈 이유는, 같은 complaint라도 상황에 따라 갈 곳이 달라질 수 있기 때문입니다. 지금은 1:1로 대응하지만, 나중에 "complaint 중에서도 VIP 고객은 다른 노드로" 같은 규칙이 생기면 category는 그대로 두고 next_step만 바꾸면 됩니다.

🔍 비유 — 진료 접수증의 두 칸

병원 접수증에는 "증상: 복통"과 "안내: 내과 3번 진료실"이 따로 적힙니다. 증상이 판단의 근거라면, 진료실 번호는 지시죠.

category가 증상, next_step이 진료실 번호입니다. 그리고 진료실 번호는 실제로 존재하는 방 번호와 정확히 일치해야 합니다 — 그래서 next_step 값을 노드 이름과 똑같이 맞춰 둔 겁니다.

③ search_manual / escalate_to_human — 뼈대만 있는 두 노드

갈림길에서 갈라지는 두 노드입니다. 진짜 RAG와 진짜 상담원 API는 지금 붙일 수 없으니 print로 "여기 지나갔다"는 것만 표시합니다.

📥 코드
# [Node 3-A] 매뉴얼 검색 (AI 자동 처리 트랙)
def search_manual(state: AgentState):
    print('3-A 진입... 메뉴얼을 검색합니다')
    return


# [Node 3-B] 상담원 이관 (긴급 이슈 트랙)
def escalate_to_human(state: AgentState):
    print('3-B 진입... 상담원 인관합니다')
    return
💡 return만 쓰고 아무것도 안 돌려줘도 되나요?

됩니다. 값 없는 return은 파이썬에서 None을 반환하고, LangGraph는 이를 "이 노드는 State를 하나도 바꾸지 않았다"로 해석합니다. 공책을 받아서 아무것도 안 적고 그대로 다음 사람에게 넘긴 셈이죠.

덕분에 흐름은 완성해 두고 내용물은 나중에 채우는 개발이 가능합니다. 그래프 구조를 먼저 검증하고 싶을 때 아주 쓸모 있는 패턴입니다.

⚠️ 이 단순화가 남긴 구멍 — 검색 결과가 답변에 반영되지 않는다

search_manual이 State에 아무것도 안 쓰기 때문에, 바로 다음 write_reply는 매뉴얼 검색 결과를 볼 방법이 없습니다. 결국 write_reply는 이메일 원문만 보고 답을 만듭니다.

즉 지금 그래프에서 "RAG로 증강된 답변"은 아직 흉내만 낸 상태입니다. 이걸 제대로 이으려면 State에 manual_result 같은 필드를 추가하거나, 실전 2처럼 messages 기반으로 바꿔야 합니다. (실전 2에서 실제로 해결합니다.)

④ write_reply — 언어 모델이 답변을 만드는 노드

📥 코드
# [Node 4] 답변 생성
def write_reply(state: AgentState):
    email = state['email_content']
    response = model.invoke(email)      # 언어 모델 호출
    return {'response': response}

드디어 언어 모델이 실제로 일하는 첫 노드입니다. 흐름은 세 줄이 전부입니다 — 이메일을 꺼내고 → 모델에 넘기고 → 결과를 response 칸에 적는다.

왜 response를 State에 담아야 할까

그래프가 END에 도달하면 State 딕셔너리 전체가 반환됩니다. 즉 State에 적히지 않은 것은 사용자에게 도달하지 않습니다. 모델이 아무리 멋진 답을 만들어도 그냥 지역 변수에 두고 끝내면 증발합니다.

⚠️ 눈여겨볼 함정 — 타입이 str이 아니다

State에는 response: str이라고 선언했지만, model.invoke(email)이 돌려주는 것은 문자열이 아니라 AIMessage 객체입니다. 그런데 에러가 나지 않습니다.

TypedDict의 타입은 실행 시점에 검사되지 않는 "메모"에 가깝기 때문입니다. 개발자와 편집기를 위한 힌트일 뿐, 파이썬이 강제하지는 않습니다. 그래서 실제 출력에서 'response': AIMessage(content=[...])가 튀어나와도 놀라지 마세요.

깔끔하게 하려면 response.content(Gemini는 response.content[-1]['text'])로 문자열만 꺼내서 담는 편이 낫습니다. 이게 뒤에 나올 State 설계 원칙과도 이어지는 이야기입니다.

💡 시스템 메시지를 안 넣었습니다

model.invoke(email)은 이메일 원문만 던집니다. 모델 입장에서는 "이걸 나보고 어쩌라는 거지?" 싶을 수 있죠. 실제로 노트북 출력을 보면 "어떤 서비스의 비밀번호인가요?"라고 되묻는, 고객 응대 메일이라기엔 어색한 답이 나옵니다.

원래는 [SystemMessage(content="당신은 고객센터 상담원입니다...")]를 앞에 붙여야 합니다. 실전 2에서 실제로 시스템 메시지를 사용합니다.

STEP 4. 그래프 생성 — 기획서의 그림을 코드로

기획 2단계에서 그린 그림을 그대로 옮기면 됩니다. 순서는 1장과 동일합니다 — ①초기화 → ②노드 등록 → ③실선 → ④점선 → ⑤컴파일.

📥 코드 — ① 초기화 + ② 노드 등록 + ③ 실선 엣지
from langgraph.graph import StateGraph, START, END

# 1. 워크플로우(그래프) 생성 — 공책 양식(AgentState)을 알려주며 도면 펼치기
agent_builder = StateGraph(AgentState)


# 2. 노드(작업자) 배치 — 이름표와 함수 이름을 똑같이 맞춥니다
agent_builder.add_node('read_email', read_email)
agent_builder.add_node('classify_intent', classify_intent)
agent_builder.add_node('search_manual', search_manual)
agent_builder.add_node('escalate_to_human', escalate_to_human)
agent_builder.add_node('write_reply', write_reply)

# 3. 엣지(연결선) 연결 — 조건 없이 무조건 흐르는 실선 두 개
agent_builder.add_edge(START, 'read_email')
agent_builder.add_edge('read_email', 'classify_intent')
💡 이름표와 함수 이름을 똑같이 맞추는 습관

add_node('read_email', read_email)에서 첫 인자는 도면에 적을 이름표(문자열), 둘째 인자는 실제 함수 객체입니다. 둘은 달라도 됩니다 — add_node('첫번째작업', read_email)도 동작합니다.

하지만 똑같이 맞추면 라우팅 함수를 쓸 때 return 'search_manual'처럼 머릿속에서 이름을 한 번 더 변환할 필요가 없어집니다. 기획 단계에서 next_step 값까지 이 이름으로 통일해 둔 게 여기서 빛을 봅니다.

④ 조건부 엣지 — 갈림길 만들기

먼저 판단하는 함수를 씁니다. 이 함수도 노드처럼 state를 입력으로 받습니다 — 공책을 봐야 판단할 수 있으니 당연하죠.

📥 코드 — (1) 라우팅 함수
# 라우팅 함수: State의 정보를 보고 어디로 갈지 "문자열"로 반환
def route_email(state: AgentState):
    if state['next_step'] == 'escalate_to_human':
        return 'escalate_to_human'
    else:
        return 'search_manual'

classify_intent가 next_step에 이미 정답을 적어 놨기 때문에, 이 함수는 그 값을 읽어 그대로 돌려주는 게 전부입니다. 기획 단계에서 이름을 맞춰 둔 덕분에 변환 로직이 아예 없죠.

📥 코드 — (2) 그래프에 등록
# 4. 조건부 엣지 연결
agent_builder.add_conditional_edges(
    'classify_intent',                        # 1) 출발지
    route_email,                              # 2) 판단 함수
    ['escalate_to_human', 'search_manual']    # 3) 갈 수 있는 목적지 목록
)
🔍 비유 — 갈림길의 표지판 (1장 복습)
  • ① 출발지 — 표지판을 어느 갈림길에 세울지 (classify_intent 다음 지점)
  • ② 판단 함수 — 표지판을 읽고 어디로 갈지 정하는 규칙 (route_email)
  • ③ 목적지 목록 — 이 갈림길에서 갈 수 있는 길의 전체 목록

③이 필요한 이유는 LangGraph가 "이 길이 실제로 존재하는지" 미리 검증하기 위해서입니다. ②가 반환할 수 있는 값이 전부 ③ 안에 들어 있어야 하고, 하나라도 빠지면 컴파일에서 에러가 납니다.

🔑 세 번째 인자, 리스트로 쓸까 딕셔너리로 쓸까

위 코드에서 목적지 목록을 리스트로 넘겼습니다. 그런데 딕셔너리로도 쓸 수 있습니다. 언제 무엇을 쓸까요?

라우팅 함수의 반환값세 번째 인자이유
노드 이름과 같음
return 'search_manual'		 리스트
['escalate_to_human', 'search_manual']		 반환값이 곧 노드 이름이니 번역표가 필요 없음
별칭을 씀
return 'node_A'		 딕셔너리
{'node_A': 'escalate_to_human', ...}		 "이 반환값이 나오면 저 노드로" 번역표가 필요함
📥 (참고) 딕셔너리로 쓰는 경우 — 지금 노트북 코드는 고치지 마세요
# 라우팅 함수가 노드 이름이 아닌 "별칭"을 반환한다면
def route_email(state: AgentState):
    if state['next_step'] == 'escalate_to_human':
        return 'node_A'          # ← 노드 이름이 아님
    else:
        return 'node_B'          # ← 노드 이름이 아님

# 그러면 "별칭 → 실제 노드 이름" 번역표를 딕셔너리로 넘겨야 합니다
agent_builder.add_conditional_edges(
    'classify_intent',
    route_email,
    {
        'node_A': 'escalate_to_human',
        'node_B': 'search_manual'
    }
)
🔍 비유 — 출입 명단 vs 좌석 배치표

리스트는 출입 가능자 명단입니다. "이 문으로는 A와 B만 나갈 수 있다"고 적어두면, 경비원은 이름이 명단에 있는지만 확인하면 됩니다. 이름이 곧 목적지니까요.

딕셔너리는 좌석 배치표입니다. "1번 티켓 → A구역, 2번 티켓 → B구역". 티켓 번호와 구역 이름이 다르기 때문에 대조표가 있어야 안내가 됩니다.

강의에서는 실전 1은 리스트로, 실전 2는 두 방식을 하나씩 써보며 둘 다 익힙니다.

⑤ 나머지 엣지 + 컴파일

📥 코드
# 5. 나머지 엣지(연결선) 연결
agent_builder.add_edge('search_manual', 'write_reply')   # 매뉴얼 검색 후 → 답변 작성
agent_builder.add_edge('write_reply', END)               # 답변 작성 후 → 종료
agent_builder.add_edge('escalate_to_human', END)         # 상담원 이관 후 → 종료

# 6. 컴파일 (최종 에이전트 생성)
agent = agent_builder.compile()

agent   # 주피터/Colab에서 실행하면 그래프 그림이 그려집니다
💡 그림으로 검증하는 습관

컴파일이 에러 없이 끝났다면 모든 노드가 설계대로 연결됐다는 뜻입니다. 마지막에 agent를 그냥 실행해 기획 2단계에서 그린 그림과 같은지 눈으로 대조하세요.

선이 다르게 그려져 있으면 add_edge/add_conditional_edges 문제, 그림은 맞는데 실행이 깨지면 노드 함수 안쪽(반환 딕셔너리 모양) 문제입니다.

지금 만든 그래프는 구조가 이미 완성돼 있습니다. 실전 2에서 바꾸는 건 "판단하는 부분"과 "검색하는 부분"이고, 기획 → State → Node → Graph라는 골격은 그대로 재사용됩니다. 이게 흐름을 먼저 세워두는 개발의 이점입니다.

중요한 건, 자료실에 갈지 말지를 상담원이 스스로 정한다는 점입니다. 우리가 코딩하지 않습니다.

② 도구 — RAG "흉내"를 내는 search_manual

실전 1에서는 노드였던 search_manual이, 이번에는 도구(Tool)가 됩니다. 1장에서 배운 그대로 평범한 함수 + @tool 데코레이터 + docstring입니다.

📥 코드
from langchain.tools import tool

@tool
def search_manual(query: str) -> str:
    """
    고객의 질문에 답변하기 위해 참고할만한 규정이나 메뉴얼을 검색할 때 사용하는 도구
    """
    if '비밀번호' in query:
        return '비밀번호 변경은 마이페이지 - 보안 설정에 있음'
    elif '배송' in query:
        return '00택배에서 3일 내 배송 예정임'
    else:
        return '해당 내용 관련 메뉴얼은 찾을 수 없습니다'
💡 진짜 RAG 대신 하드코딩한 이유

제대로 하려면 문서 로딩 → 청킹 → 임베딩 → 벡터DB 저장 → 유사도 검색까지 붙여야 합니다. 코드가 길어져 정작 배우려던 "도구를 그래프에 끼우는 법"이 묻힙니다.

중요한 건 인터페이스입니다 — query(str)를 받아 str을 돌려주는 함수. 나중에 이 함수 안쪽만 진짜 벡터 검색으로 갈아끼우면 그래프는 한 글자도 안 바뀝니다.

🔍 비유 — docstring은 LLM에게 보내는 사용설명서 (1장 복습)

모델은 이 도구를 docstring을 읽고 고릅니다. "고객의 질문에 답변하기 위해 참고할만한 규정이나 메뉴얼을 검색할 때 사용"이라는 한 문장이 "언제 이 도구를 부를지"의 유일한 근거입니다.

여기를 "검색"처럼 대충 쓰면 모델이 엉뚱한 상황에 도구를 부르거나, 불러야 할 때 안 부릅니다. docstring은 주석이 아니라 사양서입니다.

③ 모델에 도구 바인딩

📥 코드

# 도구 목록이 붙은 "새로운" 모델 객체가 만들어집니다

⚠️ model과 model_with_tools를 구분해서 씁니다

실전 2에는 모델 객체가 두 개가 됩니다. 어느 노드에서 무엇을 쓰는지가 중요합니다.

  • classify_node → model (도구 없음). 분류는 단어 하나만 답하면 되는 일이라 도구를 알 필요가 없습니다.
  • consultant_node → model_with_tools. 답변 도중 매뉴얼 검색을 요청할 수 있어야 하니까요.

여기를 반대로 쓰면, 분류 노드가 "consultant" 대신 도구 호출 요청서를 돌려주는 이상한 일이 벌어집니다.

STEP 2. State 정의 — 다시 messages로

실전 1은 email_content·category·response처럼 칸을 잘게 나눈 State였습니다. 실전 2는 1장에서 쓰던 messages 방식으로 돌아옵니다.

📥 코드
from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]   # 대화 기록 (누적)
    next_step: str                                        # 분기 판단 기준

왜 messages로 돌아왔을까

도구를 쓰기 때문입니다. 도구를 쓰는 순간 이런 것들을 담아야 합니다.

  • 사용자 질문 (HumanMessage)
  • 모델의 도구 호출 요청서 (AIMessage.tool_calls)
  • 도구 실행 결과 (ToolMessage)
  • 모델의 최종 답변 (AIMessage.content)

이걸 각각 별도 필드로 만들면 순서와 대응 관계가 깨집니다. 게다가 모델에 다시 물어볼 때는 지금까지의 대화를 순서대로 넘겨야 하죠. 그래서 한 줄로 쌓이는 리스트 하나가 정답입니다.

🔍 비유 — 항목별 서류함 vs 시간순 대화록

실전 1의 State는 서류함입니다. "이메일 원문 칸", "분류 결과 칸"처럼 종류별로 나뉘어 있죠. 단계가 한 번씩만 지나가는 일직선 흐름에는 이게 깔끔합니다.

실전 2는 대화록이 필요합니다. 상담원이 자료실에 두 번, 세 번 물어볼 수도 있고, 그때마다 "누가 언제 무슨 말을 했는지 순서대로" 남아야 하니까요. 루프가 생기는 순간 서류함으로는 감당이 안 됩니다.

💡 next_step은 왜 남겨뒀나

분류 결과는 대화의 일부가 아니라 "제어 신호"이기 때문입니다. "consultant"라는 단어를 messages에 AIMessage로 넣어버리면, 나중에 상담 모델이 그 메시지를 읽고 혼란스러워합니다.

대화에 남길 것과 흐름 제어에만 쓸 것을 분리한 설계입니다. 좋은 습관이에요.

STEP 3. Node 정의 — 네 명의 작업자

① classify_node — LLM에게 분류를 맡기는 노드

📥 코드
# [Node 1] 분류 노드 (Manager)
from langchain.messages import SystemMessage


def classify_node(state: AgentState):
    print("\n--- [1] 분류 단계 (LLM 판단) ---")
    last_message = state["messages"][-1]      # 사용자의 질문(HumanMessage)

    # 분류를 위한 프롬프트 (System Prompt)
    prompt = """
    당신은 고객 센터 관리자입니다. 고객의 이메일을 분석해서 다음 단계를 결정하세요.

    1. 단순 문의나 정보 요청이라면 -> 'consultant' 반환
    2. 환불 요청, 불만 제기, 화난 고객이라면 -> 'escalate' 반환

    답변은 오직 단어 하나만 하세요.
    """

    # LLM 호출 — 도구가 붙지 않은 model 사용
    response = model.invoke([SystemMessage(content=prompt), last_message])
    raw_content = response.content

    if isinstance(raw_content, list):
        # Gemini 등: 리스트로 오는 경우 텍스트 블록만 추출해서 합침
        decision = "".join([block['text'] for block in raw_content if block.get('type') == 'text'])
    else:
        # OpenAI 등: 문자열로 오는 경우 그대로 사용
        decision = str(raw_content)

    # 공백 제거 및 소문자 변환
    decision = decision.strip().lower()
    print(f"   -> LLM 판단 결과: {decision}")

    # 다음 단계(next_step)를 상태에 저장
    if "escalate" in decision:
        return {"next_step": "escalate"}
    else:
        return {"next_step": "consultant"}

길어 보이지만 하는 일은 딱 세 덩어리입니다.

덩어리하는 일
① 물어보기시스템 프롬프트 + 사용자 질문을 모델에 넘겨 단어 하나를 받아온다
② 꺼내기모델마다 다른 content 형태에서 텍스트만 안전하게 추출한다
③ 기록하기추출한 단어를 보고 next_step에 escalate / consultant를 적는다

① 프롬프트가 곧 "판단 기준"이 되었다

실전 1에서 if '환불' in email이 하던 일을, 이번엔 한국어로 쓴 지시문이 대신합니다. "환불 요청, 불만 제기, 화난 고객이라면" — 이제 "환급"이든 "돈 돌려줘"든 모델이 의미로 이해합니다. 실전 1의 한계가 이 세 줄로 해결됩니다.

💡 "답변은 오직 단어 하나만 하세요."가 중요한 이유

이 문장이 없으면 모델은 "이 고객은 환불을 요청하고 있으므로 escalate로 처리하는 것이 적절합니다"처럼 친절하게 설명해 버립니다. 그러면 뒤에서 값을 비교하기가 지저분해지죠.

물론 이 코드는 if "escalate" in decision처럼 포함 검사를 쓰기 때문에 문장이 와도 어느 정도 버팁니다. "출력 형식을 지시하고, 코드에서도 방어한다"는 이중 안전장치입니다.

② isinstance(raw_content, list) — 모델 갈아끼우기 대비

1장에서 배운 그 차이입니다. Gemini는 content가 리스트 ([{'type':'text','text':'consultant'}]), OpenAI는 문자열('consultant'). isinstance로 갈라놓으면 모델을 바꿔도 이 노드는 안 고쳐도 됩니다.

③ .strip().lower() — 사소하지만 자주 터지는 곳

모델이 " Consultant\n"처럼 앞뒤 공백이나 대문자를 섞어 보낼 수 있습니다. strip()으로 공백을 털고 lower()로 소문자로 맞춘 뒤에 비교해야 안전합니다. LLM 출력은 항상 "지저분할 수 있다"고 가정하세요.

🚫 강의 중 실제로 에러가 났던 지점 — +인가 ,인가

강의에서는 처음에 이렇게 썼다가 에러가 났습니다.

model.invoke([SystemMessage(content=prompt)] + last_message)  ❌

왜 틀렸을까요? last_message는 메시지 객체 하나이지 리스트가 아닙니다. 리스트에 +로 이어붙이려면 양쪽이 다 리스트여야 하죠. (1장에서 [SystemMessage(...)] + state["messages"]가 됐던 건 state["messages"]가 리스트였기 때문입니다.)

고치는 방법은 둘 중 하나입니다.

  • [SystemMessage(content=prompt), last_message]  ✅ 쉼표로 한 리스트 안에 (강의에서 택한 방법)
  • [SystemMessage(content=prompt)] + [last_message]  ✅ 굳이 +를 쓰려면 오른쪽도 리스트로

📌 노트북 확인: 배포된 2.ipynb의 해당 셀에는 아직 + last_message 버전이 남아 있습니다. 그대로 실행하면 TypeError가 나므로 위 코드처럼 쉼표로 고친 뒤 실행하세요.

② consultant_node — 답할지 도구를 부를지 스스로 정하는 노드

📥 코드
# [Node 2] 상담 AI 노드 (Worker)
def consultant_node(state: AgentState):
    print("\n--- [2-A] 상담 AI 답변 생성 중 ---")
    response = model_with_tools.invoke(state['messages'])
    return {'messages': [response]}

코드는 두 줄인데 이 그래프에서 가장 "에이전트다운" 노드입니다. 1장의 llm_call과 사실상 같은 역할이죠.

⚠️ 여기서 도구가 "실행"되지는 않습니다

model_with_tools.invoke(...)를 부르면 도구가 자동 실행될 것 같지만 아닙니다. 모델은 "search_manual을 query='비밀번호 변경 방법'으로 불러줘"라는 요청서(tool_calls)만 돌려줍니다.

실제로 함수를 돌리는 건 tool_node의 몫입니다. 이 분리가 LangGraph의 핵심이고, 덕분에 "도구 실행 전에 사람에게 확인받기" 같은 개입이 가능해집니다.

따라서 이 노드가 만들어내는 AIMessage는 두 가지 얼굴을 가집니다.

상황AIMessage의 모습다음 행선지
바로 답할 수 있을 때 content에 답변이 차 있고 tool_calls는 빈 리스트 END
매뉴얼을 봐야 할 때 content는 비어 있고 tool_calls에 요청서가 담김 tool_node
💡 이 노드는 "두 번" 실행됩니다

도구를 쓰는 경우 흐름이 이렇게 흐릅니다 — consultant_node(요청서 작성) → tool_node(실행) → consultant_node(결과 보고 답변 작성).

두 번째로 들어올 때는 state['messages']에 ToolMessage가 이미 추가되어 있으므로 모델이 검색 결과를 읽고 최종 답변을 만들 수 있습니다. 같은 함수인데 State가 달라져서 결과가 달라지는 것 — 이게 add_messages 리듀서가 만들어내는 효과입니다.

③ escalate_node — 고정 답변을 돌려주는 노드

📥 코드
from langchain_core.messages import AIMessage

# [Node 3] 상담원 이관 노드
def escalate_node(state: AgentState):
    return {'messages': [AIMessage(content='해당 메일은 전문 상담원에게 이관되었습니다.')]}

실전 1에서 escalate_to_human을 고쳐 안내 문구를 넣었던 것과 같은 발상입니다. 다만 이번 State는 messages이므로 문자열이 아니라 AIMessage로 감싸서 넣습니다.

💡 LLM을 부르지 않는 노드도 AIMessage를 만들 수 있습니다

AIMessage는 "AI 쪽에서 온 메시지"라는 자리표일 뿐, 반드시 모델이 생성해야 하는 건 아닙니다. 고정 문구를 넣어도 대화 기록상으로는 똑같이 취급되고, add_messages 리듀서가 알아서 messages 뒤에 이어 붙입니다.

덕분에 API 호출 비용 0원, 응답 지연 0초로 확정된 안내를 돌려줄 수 있습니다. "모든 걸 LLM에게 시킬 필요는 없다"는 실무 감각이기도 합니다.

④ tool_node — 요청서를 읽고 실제로 실행하는 노드

1장에서 만든 것과 글자 하나 다르지 않습니다. 도구 목록만 바뀌었을 뿐이죠. 먼저 이름 → 함수 전화번호부를 만듭니다.

📥 코드
tools = [search_manual]
tools_by_name = {tool.name: tool for tool in tools}
▶ 이렇게 생겼습니다
{'search_manual': StructuredTool(name='search_manual',
                                 description='고객의 질문에 답변하기 위해 참고할만한 규정이나 메뉴얼을 검색할 때 사용하는 도구',
                                 ...)}
📥 코드 — tool_node 본체
from langchain.messages import ToolMessage

# [Node 4] Tool Node
def tool_node(state: AgentState):
    print("\n--- [Tool Node] 도구 직접 실행 ---")
    result = []
    # 가장 최근 메시지에서 도구 호출 요청 꺼내기
    last_message = state["messages"][-1]

    for tool_call in last_message.tool_calls:
        # 1. 도구 이름으로 실제 함수 찾기
        tool = tools_by_name[tool_call["name"]]

        # 2. 함수를 실행하여 결과를 얻기
        print(f"   -> 실행 중: {tool_call['name']}")
        tool_result = tool.invoke(tool_call["args"])

        # 3. 결과를 ToolMessage 형태로 포장 (tool_call_id 필수!)
        result.append(ToolMessage(content=str(tool_result), tool_call_id=tool_call["id"]))

    # 실행 결과를 대화 기록에 추가
    return {"messages": result}
💡 이 코드가 1장과 똑같다는 게 포인트입니다

도구가 add·multiply에서 search_manual로 바뀌었는데도 tool_node는 손댈 게 없습니다. "마지막 메시지에서 tool_calls를 꺼내 이름으로 함수를 찾아 인자를 넣고 실행한 뒤 ToolMessage로 포장한다"는 절차가 도구와 무관하기 때문이죠.

그래서 강사님도 말합니다 — LangGraph 개발자들이 이걸 ToolNode라는 이름으로 이미 만들어 뒀다고요. (다음 강의에서 다룹니다.) 지금은 안이 어떻게 생겼는지 알고 넘어가는 단계입니다.

🚫 tool_call_id는 택배 송장 번호 (1장 복습)

ToolMessage에 tool_call_id를 안 넣으면 모델이 "어느 요청에 대한 답인지 대조하지 못해" 에러가 납니다. 모델이 요청할 때 스스로 발급한 고유번호를 그대로 복사해 붙여서 돌려주는 것뿐입니다.

STEP 4. 그래프 생성 — 라우터 두 개, 루프 하나

📥 코드 — ① 초기화 + ② 노드 등록 + ③ 첫 실선
from langgraph.graph import StateGraph, START, END

# 1. 워크플로우(그래프) 생성
agent_builder = StateGraph(AgentState)


# 2. 노드(작업자) 배치
agent_builder.add_node('classify_node', classify_node)
agent_builder.add_node('consultant_node', consultant_node)
agent_builder.add_node('escalate_node', escalate_node)
agent_builder.add_node('tool_node', tool_node)


# 3. 엣지(연결선) 연결 — 시작하면 무조건 분류부터
agent_builder.add_edge(START, 'classify_node')

실전 1과 달리 read_email이 없으므로 START에서 바로 classify_node로 갑니다. 사용자가 invoke({"messages": [...]})로 넣은 HumanMessage가 add_messages 리듀서 덕분에 자동으로 messages에 담기기 때문에, "받아서 옮겨 적는" 노드가 아예 필요 없어진 겁니다.

라우터 두 개 — 갈림길이 두 군데

📥 코드 — 라우터 1: 분류 결과에 따른 분기
def route_after_classify(state: AgentState):
    if state['next_step'] == 'escalate':
        return 'escalate'          # ← 노드 이름이 아닌 "별칭"
    else:
        return 'consultant'        # ← 노드 이름이 아닌 "별칭"
📥 코드 — 라우터 2: 도구 사용 여부 판단 (1장과 동일)
def should_continue(state: AgentState):
    last_message = state["messages"][-1]

    # LLM이 도구 호출(tool_calls)을 포함한 응답을 보낸 경우
    if last_message.tool_calls:
        return "tool_node"

    # 도구 호출이 없으면 종료
    return END

어디에 세우나classify_node 뒤consultant_node 뒤
무엇을 보나state['next_step'] — 제어 신호messages[-1].tool_calls — 메시지 내용
누가 정했나LLM이 분류한 결과LLM이 도구를 부를지 정한 결과
반환값'escalate' / 'consultant' (별칭)'tool_node' / END (실제 이름)
📥 코드 — ④ 조건부 엣지 두 개
# 4-1. 분류 결과에 따른 분기 → 반환값이 별칭이므로 "딕셔너리"로 번역표를 넘김
agent_builder.add_conditional_edges(
    'classify_node',
    route_after_classify,
    {
        'escalate': 'escalate_node',
        'consultant': 'consultant_node'
    }
)

# 4-2. 상담 AI 후 도구 사용 여부 → 반환값이 실제 이름이므로 "리스트"면 충분
agent_builder.add_conditional_edges(
    'consultant_node',
    should_continue,
    ['tool_node', END]
)
💡 한 그래프 안에서 리스트와 딕셔너리를 하나씩 써봤습니다

4-1은 라우터가 'escalate'라는 별칭을 반환하는데 노드 이름은 'escalate_node'이므로 번역표(딕셔너리)가 필요합니다.

4-2는 라우터가 'tool_node'라는 실제 이름을 반환하므로 명단(리스트)이면 충분합니다.

강의에서 일부러 두 방식을 섞은 이유가 이겁니다 — 실무에서는 둘 다 만나게 되니까요.

📥 코드 — ⑤ 나머지 엣지 + 컴파일

agent_builder.add_edge('escalate_node', END)             # 이관 후 종료

이 줄이 없으면 도구는 실행되지만 그 결과를 아무도 안 읽고 그래프가 멈춥니다. 1장의 tool_node → llm_call과 정확히 같은 역할이에요.

State 설계 원칙 2가지 — LangGraph 개발팀의 권고

원칙 1 · 꼭 필요한 것만 저장하라

슬라이드의 나쁜 예를 보면 email_content_length: 4가 있습니다. 이메일 원문이 이미 State에 있는데 그 길이를 굳이 따로 저장한 거죠. len(state["email_content"])로 언제든 즉시 계산되는 값입니다. llm_token_usage도 마찬가지로, 다음 노드가 쓰지 않는다면 뺍니다.

🔍 비유 — 매번 들고 다니는 배낭

State는 노드에서 노드로 계속 실려 다니는 배낭입니다. 들어갈 때마다 꺼내 읽고, 나올 때마다 다시 싸서 넘기죠.

배낭에 안 쓰는 짐을 넣어두면 이동할 때마다 그 무게를 그대로 짊어집니다 — 연산이 늘고 메모리를 더 먹습니다. 체크포인트를 켜면 저장 용량까지 늘죠.

실전 1에서 RAG 검색 결과 필드를 만들지 않은 것도 이 원칙과 통합니다 — 쓰지도 않을 필드를 미리 만들어 둘 이유가 없으니까요.

💡 이 원칙으로 우리 State를 되짚어 보면

next_step — 바로 다음 라우터가 씁니다. ✅ 유지
email_content — classify_intent도, write_reply도 씁니다(다다음 노드). ✅ 유지
category — 솔직히 지금 그래프에서는 어떤 노드도 읽지 않습니다. 분기는 next_step이 담당하니까요. 원칙대로라면 뺄 후보지만, "왜 이렇게 분류됐는지"를 사람이 확인하는 로그·감사 용도로는 가치가 있습니다. 원칙은 규칙이 아니라 판단 기준이라는 좋은 예입니다.

원칙 2 · 가공되지 않은 '날 것(Raw)'을 저장하라

차이는 라우팅 함수를 써보면 즉시 드러납니다.

📥 Good Case — 구조화된 데이터
state["customer_info"] = {
    "grade": "VIP",
    "status": "Angry"
}

def route(state):
    if state["customer_info"]["grade"] == "VIP":   # 정확하게 한 번에 꺼냄
        return "vip_service"
📥 Bad Case — 사람이 읽기 좋게 가공한 문장
state["customer_info"] = "이 고객은 VIP 등급이며 매우 화가 난 상태입니다."

def route(state):
    if "VIP" in state["customer_info"]:            # 문자열을 뒤져야 함 (불안정)
        return "vip_service"
⚠️ Bad Case가 왜 나쁜가
  • 추출 비용이 다시 든다 — 문장에서 등급을 뽑으려면 키워드 검색을 하거나, 심하면 언어 모델을 한 번 더 호출해야 합니다. 돈과 시간이 두 번 나갑니다.
  • 깨지기 쉽다 — 문구가 "VIP등급"으로 바뀌거나 "non-VIP"가 되면 "VIP" in ...이 조용히 잘못 걸립니다.
  • 이미 아는 정보를 버린 것 — 처음엔 구조화된 데이터였는데 일부러 문장으로 뭉개서 저장한 셈이죠.
🔍 비유 — 엑셀 표 vs 줄글 보고서

같은 매출 데이터를 엑셀 표로 받으면 정렬·필터·합계가 즉시 됩니다. 줄글 보고서로 받으면 사람이 읽기엔 좋지만, 숫자를 다시 쓰려면 하나씩 옮겨 적어야 하죠.

State는 사람이 읽는 보고서가 아니라 노드가 처리하는 데이터입니다. 보기 좋게 만드는 건 맨 마지막, 사용자에게 보여줄 때 하면 됩니다.

💡 실전 1의 response를 다시 보면

앞에서 write_reply가 AIMessage 객체를 통째로 response에 넣는다고 했죠. 원칙 2 관점에서는 오히려 "날 것"에 가까운 선택입니다 — 토큰 사용량, 메타데이터가 다 살아 있으니까요.

다만 State에 str이라고 선언해 놓고 객체를 넣은 것은 별개의 문제입니다. 타입 선언과 실제 값을 일치시키거나, 아예 response: AIMessage로 선언을 고치는 게 정직합니다.

실전 1 · 키워드 라우팅 에이전트

📥 전체 코드
# ══ STEP 1. Model & Tool ══════════════════════════════
from langchain_google_genai import ChatGoogleGenerativeAI

model = ChatGoogleGenerativeAI(model="gemini-3-flash-preview")
# (실전 1은 도구를 쓰지 않습니다)

# ══ STEP 2. State ═════════════════════════════════════
from typing_extensions import TypedDict

class AgentState(TypedDict):
    email_content: str   # 고객 이메일 원문
    category: str        # 분류 결과 라벨 (inquiry / complaint)
    next_step: str       # 다음에 갈 노드 이름 → 분기 기준
    response: str        # 최종 답변

# ══ STEP 3. Node ══════════════════════════════════════
# [1] 이메일 읽기 — 지금은 그대로 넘기기만
def read_email(state: AgentState):
    return {'email_content': state['email_content']}

# [2] 의도 분류 — 키워드 매칭 (실전 2에서 LLM으로 교체)
def classify_intent(state: AgentState):
    email = state['email_content']
    if '환불' in email or '긴급' in email or '빨리' in email:
        category, next_step = 'complaint', 'escalate_to_human'
    else:
        category, next_step = 'inquiry', 'search_manual'
    return {'category': category, 'next_step': next_step}

# [3-A] 매뉴얼 검색 — 뼈대만 (State 변경 없음)
def search_manual(state: AgentState):
    print('3-A 진입... 메뉴얼을 검색합니다')
    return

# [3-B] 상담원 이관 — 고정 안내 문구를 response에 담아 반환
def escalate_to_human(state: AgentState):
    print('3-B 진입... 상담원 인관합니다')
    return {'response': '불편을 드려 죄송합니다. 상담원에게 이관하였으니 잠시 대기해 주시기 바랍니다.'}

# [4] 답변 생성 — 언어 모델 호출
def write_reply(state: AgentState):
    email = state['email_content']
    response = model.invoke(email)
    return {'response': response}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END

agent_builder = StateGraph(AgentState)

agent_builder.add_node('read_email', read_email)
agent_builder.add_node('classify_intent', classify_intent)
agent_builder.add_node('search_manual', search_manual)
agent_builder.add_node('escalate_to_human', escalate_to_human)
agent_builder.add_node('write_reply', write_reply)

agent_builder.add_edge(START, 'read_email')
agent_builder.add_edge('read_email', 'classify_intent')

# next_step 값을 그대로 반환 (값 = 노드 이름으로 맞춰 뒀기 때문)
def route_email(state: AgentState):
    if state['next_step'] == 'escalate_to_human':
        return 'escalate_to_human'
    else:
        return 'search_manual'

agent_builder.add_conditional_edges(
    'classify_intent',
    route_email,
    ['escalate_to_human', 'search_manual']   # 반환값 = 노드 이름 → 리스트로 충분
)

agent_builder.add_edge('search_manual', 'write_reply')
agent_builder.add_edge('write_reply', END)
agent_builder.add_edge('escalate_to_human', END)

agent = agent_builder.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
response = agent.invoke({"email_content": "비밀번호 변경 방법을 알려주세요."})   # → 3-A 트랙
response = agent.invoke({"email_content": "당장 환불해줘!"})                 # → 3-B 트랙

실전 2 · LLM + Tool 결합 에이전트

📥 전체 코드
# ══ STEP 1. Model & Tool ══════════════════════════════
from langchain_google_genai import ChatGoogleGenerativeAI
from langchain.tools import tool

model = ChatGoogleGenerativeAI(model="gemini-3-flash-preview")

@tool
def search_manual(query: str) -> str:
    """
    고객의 질문에 답변하기 위해 참고할만한 규정이나 메뉴얼을 검색할 때 사용하는 도구
    """
    if '비밀번호' in query:
        return '비밀번호 변경은 마이페이지 - 보안 설정에 있음'
    elif '배송' in query:
        return '00택배에서 3일 내 배송 예정임'
    else:
        return '해당 내용 관련 메뉴얼은 찾을 수 없습니다'

tools = [search_manual]
model_with_tools = model.bind_tools(tools)   # 분류용 model / 상담용 model_with_tools 를 구분해 씁니다

# ══ STEP 2. State ═════════════════════════════════════
from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]   # 대화 기록 (덮어쓰지 않고 누적)
    next_step: str                                        # 제어 신호 (대화에는 남기지 않음)

# ══ STEP 3. Node ══════════════════════════════════════
from langchain.messages import SystemMessage, ToolMessage
from langchain_core.messages import AIMessage

# [1] 분류 — LLM이 읽고 판단
def classify_node(state: AgentState):
    print("\n--- [1] 분류 단계 (LLM 판단) ---")
    last_message = state["messages"][-1]

    prompt = """
    당신은 고객 센터 관리자입니다. 고객의 이메일을 분석해서 다음 단계를 결정하세요.

    1. 단순 문의나 정보 요청이라면 -> 'consultant' 반환
    2. 환불 요청, 불만 제기, 화난 고객이라면 -> 'escalate' 반환

    답변은 오직 단어 하나만 하세요.
    """

    # 주의: [SystemMessage(...)] + last_message 는 TypeError (오른쪽이 리스트가 아님)
    response = model.invoke([SystemMessage(content=prompt), last_message])
    raw_content = response.content

    if isinstance(raw_content, list):
        decision = "".join([b['text'] for b in raw_content if b.get('type') == 'text'])   # Gemini
    else:
        decision = str(raw_content)                                                      # OpenAI

    decision = decision.strip().lower()
    print(f"   -> LLM 판단 결과: {decision}")

    if "escalate" in decision:
        return {"next_step": "escalate"}
    else:
        return {"next_step": "consultant"}

# [2] 상담 — 바로 답할지 도구를 부를지 모델이 스스로 판단
def consultant_node(state: AgentState):
    print("\n--- [2-A] 상담 AI 답변 생성 중 ---")
    response = model_with_tools.invoke(state['messages'])
    return {'messages': [response]}

# [3] 이관 — LLM 호출 없이 고정 메시지
def escalate_node(state: AgentState):
    return {'messages': [AIMessage(content='해당 메일은 전문 상담원에게 이관되었습니다.')]}

# [4] 도구 실행 — 1장에서 만든 것과 동일
tools_by_name = {tool.name: tool for tool in tools}

def tool_node(state: AgentState):
    print("\n--- [Tool Node] 도구 직접 실행 ---")
    result = []
    last_message = state["messages"][-1]
    for tool_call in last_message.tool_calls:
        tool = tools_by_name[tool_call["name"]]
        print(f"   -> 실행 중: {tool_call['name']}")
        tool_result = tool.invoke(tool_call["args"])
        result.append(ToolMessage(content=str(tool_result), tool_call_id=tool_call["id"]))
    return {"messages": result}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END

agent_builder = StateGraph(AgentState)

agent_builder.add_node('classify_node', classify_node)
agent_builder.add_node('consultant_node', consultant_node)
agent_builder.add_node('escalate_node', escalate_node)
agent_builder.add_node('tool_node', tool_node)

agent_builder.add_edge(START, 'classify_node')

# 라우터 1 — 별칭을 반환하므로 딕셔너리(번역표) 필요
def route_after_classify(state: AgentState):
    if state['next_step'] == 'escalate':
        return 'escalate'
    else:
        return 'consultant'

# 라우터 2 — 실제 노드 이름을 반환하므로 리스트면 충분
def should_continue(state: AgentState):
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tool_node"
    return END

agent_builder.add_conditional_edges(
    'classify_node',
    route_after_classify,
    {'escalate': 'escalate_node', 'consultant': 'consultant_node'}
)

agent_builder.add_conditional_edges(
    'consultant_node',
    should_continue,
    ['tool_node', END]
)

agent_builder.add_edge('tool_node', 'consultant_node')   # ★ 이 한 줄이 루프를 만든다
agent_builder.add_edge('escalate_node', END)

agent = agent_builder.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
from langchain.messages import HumanMessage

response = agent.invoke({"messages": [HumanMessage(content="비밀번호 변경은 어디서 해?")]})
# Gemini는 content가 리스트라 한 번 더 꺼냄
print(response["messages"][-1].content[-1]['text'])

response = agent.invoke({"messages": [HumanMessage(content="당장 환불해줘!")]})   # → escalate 트랙

자주 걸리는 함정 6가지

🕳️ 이번 장에서 실제로 밟게 되는 지뢰

1. [SystemMessage(...)] + last_message — 리스트에 객체를 더한다

+는 리스트끼리만 됩니다. last_message는 객체 하나이므로 TypeError.
[SystemMessage(...), last_message] ✅ 또는 [SystemMessage(...)] + [last_message] ✅

2. 노드를 고쳐놓고 그래프를 다시 컴파일하지 않는다

agent는 컴파일 시점의 함수를 붙들고 있는 사본입니다. 노드 함수 셀만 다시 실행해도 동작은 그대로입니다. StateGraph(...)부터 compile()까지 전부 다시 실행하세요.

3. invoke()에 넘기는 딕셔너리 모양을 State와 안 맞춘다

실전 1은 {"email_content": "..."}, 실전 2는 {"messages": [HumanMessage(...)]}입니다. State 클래스가 바뀌면 입력 서식도 바뀝니다. 1장 습관대로 {"messages": ...}를 넣으면 실전 1에서는 KeyError: 'email_content'가 납니다.

4. 라우팅 함수 반환값과 세 번째 인자를 안 맞춘다

반환값이 노드 이름 그대로면 리스트, 별칭이면 딕셔너리(번역표). return 'escalate'인데 ['escalate_node', ...]를 넘기면 목적지를 못 찾습니다.

5. 분기해서 끝나는 트랙에 답변을 안 담는다

escalate_to_human이 return만 하면 response가 영영 비어 있습니다. 모든 종료 경로가 사용자에게 돌려줄 값을 남기는지 확인하세요.

6. 분류용 모델에 도구를 바인딩한다

classify_node에서 model_with_tools를 쓰면 "consultant" 대신 도구 호출 요청서가 돌아올 수 있습니다. 판단만 시킬 모델에는 도구를 붙이지 마세요.

💡 디버깅 요령

에러가 나면 먼저 agent를 실행해 그래프 그림을 확인하세요. 그림이 기획서와 다르면 add_edge/add_conditional_edges 문제, 그림은 맞는데 실행이 깨지면 노드 함수의 반환 딕셔너리를 의심하면 됩니다. 노드마다 print를 하나씩 심어두면(실전 2처럼) 어디까지 갔는지가 바로 보입니다.

📚 한 장 정리

오늘의 핵심 한 문장

에이전트 개발은 코드가 아니라 기획에서 시작한다 — 요구사항을 노드로 쪼개고 → 그래프로 잇고 → 그제서야 State를 설계하면, 코드는 그 기획서를 기계적으로 번역하는 일이 된다.

  • 기획 3단계 — ①요구사항 분석(기능 하나 = 노드 하나) → ②그래프 구성(실선/점선 구분) → ③State 설계(다음 노드가 쓸 것만). 코딩 순서와 정반대인 이유는, 일이 정해져야 데이터가 정해지기 때문.
  • 이름 통일의 힘 — next_step 값 = 노드 이름 = add_node 이름표. 맞춰 두면 라우팅 함수가 값을 그대로 return하는 한 줄이 된다.
  • 실전 1 (키워드) — State는 칸 나눈 서류함(리듀서 없음), 분기는 if '환불' in email. "환급"에서 무너진다 — 단어를 볼 뿐 의미를 못 보기 때문.
  • 실전 2 (LLM + Tool) — 분류를 프롬프트가 맡고, 검색을 @tool이 맡는다.
    • State가 messages + add_messages로 돌아온 이유는 루프가 생겼기 때문. 대화록이 필요하다.
    • model(분류)과 model_with_tools(상담)를 구분해서 쓴다.
    • consultant_node는 요청서만 쓰고, 실제 실행은 tool_node가 한다. 이 분리가 LangGraph의 핵심.
    • add_edge('tool_node', 'consultant_node') 한 줄이 루프를 만들고, 그 덕분에 검색 결과가 답변에 반영된다.
  • 조건부 엣지의 세 번째 인자 — 반환값이 노드 이름이면 리스트(출입 명단), 별칭이면 딕셔너리(좌석 배치표).
  • State 설계 원칙 — ① 꼭 필요한 것만(다음/다다음 노드가 쓰는가? 금방 계산되는 값 아닌가?) · ② 날 것(Raw)으로(사람이 읽기 좋은 문장이 아니라 컴퓨터가 처리하기 좋은 dict/list/number).
🔍 마지막으로 — 실전 1과 실전 2의 관계

실전 2는 실전 1을 버리고 다시 만든 게 아닙니다. 골격(기획 → State → Node → Graph)은 그대로 두고, "판단하는 부분"과 "검색하는 부분"만 갈아끼운 겁니다.

이게 LangGraph로 흐름을 먼저 세워두는 이유입니다 — 부품은 갈아끼울 수 있지만, 골격을 잘못 세우면 전부 다시 지어야 하니까요.

강사님 말씀대로, 2강까지 오면 LangGraph 코드의 60~70%는 밟은 셈입니다. 3·4·5강은 오늘 배운 것을 조금씩 응용할 뿐이에요. 막히면 1장의 "공책 한 권이 도는 사무실" 비유로 돌아갔다가, 노트북을 처음부터 끝까지 한 번 돌려본 뒤 이 문서를 다시 읽어보세요. 훨씬 잘 붙습니다.
