01. RAG Load: PDFPlumber

실습 노트북: 04/01.ipynb  ·  원문: docs/04.rag.md 2장 Load  ·  난이도: 🟢 입문

이 자료는 실습 노트북(04/01.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 이번 장부터 RAG(검색 증강 생성) 파이프라인을 한 단계씩 만들어 갑니다. 그 첫걸음이 Load — PDF 같은 원본 문서를 LangChain이 다룰 수 있는 Document 객체로 바꾸는 일입니다. 오늘은 빠르고 간단한 로더 PDFPlumber로 실제 PDF를 읽어 보고, 그 결과가 어떤 모양인지 뜯어봅니다.

🔍 비유 — 폐쇄형 시험 vs 오픈북 시험 LLM에게 그냥 질문하는 것은 아무 자료 없이 순수 암기력으로 치르는 시험과 같습니다. 모델은 학습이 끝난 시점까지 외운 것만 알고, 그 뒤에 나온 정보나 우리 회사 내부 문서는 알지 못하죠. RAG는 이 시험을 오픈북 시험으로 바꿔 줍니다 — 질문이 들어오면 먼저 관련 자료를 책에서 찾아 펼쳐 놓고(검색), 그 내용을 보면서 답을 쓰게(생성) 하는 것이죠. 그래서 이름이 Retrieval(검색)-Augmented(증강) Generation(생성)입니다.
이 장에서 배우는 것 RAG는 LLM의 두 가지 약점을 보완합니다. ① 한 번에 넣을 수 있는 글자 수가 제한되어 있다는 점, ② 지식이 특정 시점에 멈춰 있다는 점(Knowledge Cutoff). 외부 문서를 그때그때 검색해 참고시키면 최신·전용 정보로도 정확히 답하게 만들 수 있습니다. 그 재료가 되는 문서를 시스템 안으로 들여오는(Load) 단계가 오늘의 주제입니다.

RAG 5단계 파이프라인 — 지금 어디에 있나

RAG 시스템은 미리 문서를 정리해 두는 과정(인덱싱)과 질문이 들어왔을 때 검색·답변하는 과정(런타임)으로 나뉩니다. 우리가 이번 폴더에서 하나씩 만들 단계는 아래 다섯 개입니다. 오늘은 맨 앞의 Load에 있습니다.

1Load

PDF·CSV 등을 Document 객체로 변환 (← 오늘)

2Split

Document를 작은 청크로 분할

3Embed

각 청크를 숫자 벡터로 변환

4Store

벡터를 Vector DB에 저장

5Retrieve

질문과 유사한 문서를 검색

🔍 비유 — 도서관을 새로 여는 준비 RAG를 하나의 도서관이라고 생각해 보세요. 손님(질문)이 오기 전에 사서가 할 일이 있습니다. 책을 들여오고(Load), 두꺼운 책을 챕터로 나누고(Split), 내용에 따라 분류 번호를 붙이고(Embed), 서가에 꽂아(Store) 둡니다. 그래야 나중에 손님이 오면 딱 맞는 책을 빠르게 찾아(Retrieve) 건넬 수 있죠. 오늘 배우는 Load는 바깥 세상의 책을 도서관 안으로 실어 오는 첫 작업입니다.

1. Load — 문서 불러오기

Load는 RAG 파이프라인의 첫 번째 단계입니다. 우리가 가진 자료는 PDF, CSV, 웹페이지, Google Drive 문서 등 형태가 제각각입니다. 이 다양한 소스를 LangChain이 일관되게 다룰 수 있는 하나의 규격 — Document 객체 — 로 변환하는 일이 바로 Load입니다.

🔍 비유 — 식자재 손질 시장에서 사 온 재료는 흙 묻은 당근, 껍질째의 양파, 통마늘처럼 제각각의 원래 모습입니다. 요리(LLM)에 바로 넣을 수는 없죠. 먼저 씻고 다듬어 손질된 재료로 만들어야 합니다. Load가 이 손질 과정입니다 — PDF라는 원재료를 받아, 뒤 단계(Split·Embed…)가 곧바로 요리할 수 있는 표준 재료(Document)로 다듬어 내는 것이죠.
💡 핵심 규칙 — 페이지 1개당 Document 1개 PDF를 로드하면 보통 페이지 하나가 Document 객체 하나로 만들어집니다. 그래서 3페이지짜리 PDF를 읽으면 결과는 3개의 Document가 담긴 리스트가 됩니다. 이 1:1 대응만 기억해 두면 뒤에 나오는 출력이 훨씬 잘 읽힙니다.

2. Document 객체 — 내용물 + 송장

Load가 만들어 내는 Document 객체는 딱 두 가지 핵심 속성을 가집니다. 하나는 실제 글자이고, 다른 하나는 그 글자에 대한 부가 정보입니다.

속성담기는 것예시
page_content페이지의 실제 텍스트"Holdings Data - ARKK …"
metadata소스 경로·페이지 번호·생성일 등 부가 정보{'page': 0, 'total_pages': 3, ...}
🔍 비유 — 택배 상자와 송장 라벨 Document 객체는 택배 상자 하나와 같습니다. 상자를 열면 나오는 내용물이 page_content(실제 글자)이고, 상자 겉면에 붙은 송장 라벨이 metadata입니다. 송장에는 "어디서 왔는지(source·file_path)", "몇 번째 상자인지(page)", "전체 몇 개인지(total_pages)", "언제 포장됐는지(CreationDate)"가 적혀 있죠. 나중에 검색해서 "이 답변은 3페이지에서 나왔어요"라고 출처를 밝힐 수 있는 것도 바로 이 송장 덕분입니다.

3. PDFPlumber로 PDF 읽기

PDF를 Document로 바꿔 주는 도구를 로더(Loader)라고 부릅니다. LangChain에는 여러 PDF 로더가 있는데, 오늘 쓰는 PDFPlumberLoader는 그중 빠르고 단순한 축에 속합니다.

🔍 비유 — 고속 문서 스캐너 PDFPlumber는 사무실의 고속 스캐너 같습니다. 종이를 넣으면 드르륵 하고 글자만 빠르게 쭉 긁어 텍스트로 뽑아 줍니다. 내부가 C 언어 기반이라 처리 속도가 아주 빠르죠. 대신 표의 칸을 정교하게 구분하거나 복잡한 레이아웃을 살리는 정밀 작업에는 덜 특화되어 있습니다. 그래서 대량 문서에서 단순 텍스트만 빠르게 뽑을 때 특히 잘 어울립니다.
💡 어떤 로더를 고를까 빠른 처리·단순 텍스트가 목적이면 PDFPlumber(오늘), 표가 많거나 정밀 추출·풍부한 메타데이터가 필요하면 PyMuPDF(다음 노트북)를 선택합니다. 목적에 맞는 스캐너를 고르는 것과 같습니다.

4. 코드 한 줄씩 실행해보기

실제 노트북의 코드는 아래 한 셀이 전부입니다. PDF를 로드하고, 몇 개의 Document가 나왔는지 세어 보고, 전체를 찍어 본 다음, 첫 페이지의 텍스트만 따로 꺼내 봅니다. 먼저 코드 전체를 보고, 그 아래에서 부분별로 결과를 확인하겠습니다.

📥 코드
from langchain_community.document_loaders import PDFPlumberLoader

# ① 로더 객체 생성 — 읽어올 PDF 파일 경로를 지정한다.
loader = PDFPlumberLoader("./pdf-file.pdf")

# ② load() 호출 — PDF를 읽어 Document 객체 리스트로 반환한다.
docs = loader.load()

# ③ 몇 개의 Document가 만들어졌는지 확인 (= 페이지 수)
print(len(docs))

# ④ Document 리스트 전체를 출력
print(docs) # 업로드한 파일이 총 3개의 페이지가 있기 때문에 총 3개의 Document 객체가 생성됨

# ⑤ 첫 번째 페이지의 실제 텍스트만 꺼내 출력
print(docs[0].page_content)
💡 딱 두 줄이 핵심 PDFPlumberLoader("경로")로 로더를 만들고, loader.load()로 실제로 읽어 들입니다. 이 두 줄이면 PDF가 곧바로 Document 리스트로 바뀝니다. 나머지 print는 그 결과를 눈으로 확인하는 용도예요.

5. metadata 들여다보기

송장(metadata)만 따로 꺼내 보면 이 Document가 어떤 파일의 몇 번째 페이지에서 왔는지 한눈에 보입니다. 아래처럼 .metadata를 찍어 확인할 수 있습니다.

📥 코드
# 첫 번째 Document의 송장(metadata)만 확인
print(docs[0].metadata)

📚 한 장 정리

오늘의 핵심 Load는 바깥 세상의 문서(PDF)를 RAG가 다룰 수 있는 Document 객체 리스트로 들여오는 첫 단계다. PDFPlumber는 그 일을 빠르고 단순하게 해내는 로더다.
  • RAG — LLM을 오픈북 시험으로 바꾸는 기술. 외부 문서를 검색해 최신·전용 정보로 답하게 한다.
  • 파이프라인 — Load → Split → Embed → Store → Retrieve. 오늘은 맨 앞 Load.
  • Load — 다양한 소스를 표준 규격인 Document 객체로 변환하는 식자재 손질 단계.
  • Document = 상자 + 송장 — page_content(실제 텍스트) + metadata(출처·페이지 등 부가 정보).
  • 페이지 1개 = Document 1개 — 3페이지 PDF → 3개 리스트, 'page'는 0부터 센다.
  • PDFPlumber — C 기반 고속 스캐너. 대량 문서의 단순 텍스트 추출에 강하다. 딱 두 줄: PDFPlumberLoader("경로") → .load().
