05. Middleware: TodoList — 할 일 자동 관리

실습 노트북: 05.ipynb  ·  원문: docs/02.agent-basic.md  ·  난이도: 🟢 입문  ·  선행: 04. Tool Emulator

이 자료는 실습 노트북(05.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. "메일 다 확인하고 → 요약 보고하고 → 답장 보내고 → 결과 보고해"처럼 여러 단계가 얽힌 복잡한 요청을 Agent가 빠뜨리지 않고 척척 해내게 하려면 어떻게 할까요? 이 장에서는 TodoListMiddleware가 AI에게 스스로 할 일 목록(To-Do)을 쓰고 하나씩 체크하게 만드는 원리와, 그것이 실제로 동작하는지 로그에서 확인하는 방법을 배웁니다.

개요 — 미들웨어(Middleware)란?

🔍 비유 — 무대 뒤 스태프 Agent가 사용자와 대화하는 것을 연극 무대라고 해봅시다. 배우(AI 모델)는 무대 위에서 열심히 연기합니다. 그런데 무대 뒤에는 여러 스태프가 있어요 — 조명을 조절하고, 소품을 챙기고, 대본 진행을 점검하죠. 미들웨어가 바로 이 무대 뒤 스태프입니다. 배우와 관객(사용자) 사이에 슬쩍 끼어들어 요청과 응답을 다듬거나 보조하는 존재죠. 배우는 자기 연기에만 집중하고, 나머지 잔손질은 스태프가 알아서 해줍니다.

LangChain에서 미들웨어(middleware)는 Agent가 돌아가는 과정 사이사이에 끼어들어 추가 기능을 얹어주는 부품입니다. Agent를 만들 때 middleware=[...] 리스트에 필요한 미들웨어들을 넣어두면, 실행할 때마다 이들이 자동으로 동작합니다. 이번 노트북에서는 그중 두 가지를 함께 얹어봅니다.

미들웨어한 줄 역할비유
TodoListMiddleware
(이 장의 주인공)		 복잡한 요청을 할 일 목록으로 쪼개고, 진행 상태를 관리하게 함 주방의 주문표(order ticket)
LLMToolEmulator
(04장에서 배움)		 실제 도구를 호출하지 않고 결과를 흉내(모킹)냄 — 실제 메일 발송 X 실제 공연 대신 리허설
이 장에서 배우는 것 TodoListMiddleware는 AI에게 write_todos라는 내장 도구를 쥐여줍니다. 요청이 복잡하면 AI는 이 도구를 스스로 불러 "할 일 목록"을 작성하고, 하나씩 처리하면서 상태를 갱신합니다. 핵심은 두 가지 — ① 어떻게 얹는가, ② 정말 동작했는지 로그에서 어떻게 확인하는가입니다.
⚠️ 실행 전 준비 코드를 직접 돌려보려면 프로젝트 루트에 .env 파일이 있고 그 안에 OPENAI_API_KEY가 들어 있어야 합니다. 이 교재만 읽을 때는 필요 없습니다.

0. 모델 준비

늘 그렇듯 먼저 "말을 걸 상대(모델)"와 Agent를 만들 재료들을 불러옵니다. 이번에는 도구(tool)와 Agent 생성 함수(create_agent)도 함께 가져옵니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent

# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")

1. 이메일 도구 정의

Agent가 "일할 도구"로 이메일 보내기 · 이메일 읽기 두 가지를 만들어 줍니다. 아직은 진짜로 메일을 주고받는 게 아니라 동작을 흉내 내는 프로토타입입니다 (실제 발송/조회 대신 고정된 문자열·리스트를 돌려줍니다).

🔍 비유 — 소품용 가짜 전화기 연극 무대에 등장하는 전화기는 진짜로 통화가 되지 않습니다. 배우가 수화기를 들면 "따르릉" 소리만 나는 소품이죠. 여기서 정의하는 send_email_tool, read_email_tool도 마찬가지입니다 — 겉모습(입력·출력 형태)은 진짜 도구지만, 속은 미리 정해둔 값을 돌려주는 연습용 소품이에요.
📥 코드
from typing import List, Dict
from langchain.tools import tool

@tool
def send_email_tool(to: str, subject: str, body: str) -> str:
    """지정한 주소로 이메일을 보내는 도구(프로토타입)."""
    return f"Email sent. to={to}, subject={subject}"

@tool
def read_email_tool(limit: int = 3) -> List[Dict[str, str]]:
    """최근 받은 이메일을 조회하는 도구(프로토타입)."""
    return [{"from": "hr@example.com", "subject": "정책 안내", "body": "..."}][:limit]
💡 함수 안의 """..."""(docstring)이 중요합니다 도구 함수 첫 줄의 설명문은 단순 주석이 아니라, AI에게 "이 도구가 무슨 일을 하는지" 알려주는 안내문입니다. AI는 이 설명을 읽고 "지금 상황엔 이 도구를 써야겠다"고 판단합니다. 그래서 도구 설명은 사람이 아니라 AI가 읽는 사용설명서라고 생각하면 됩니다.

2. 미들웨어를 얹은 Agent 실행

드디어 Agent를 만듭니다. create_agent에 모델 · 도구 · 미들웨어를 넘기는데, 이번엔 middleware 자리에 LLMToolEmulator와 TodoListMiddleware 두 개를 나란히 넣습니다.

🔍 비유 — 주방의 주문표(Order Ticket) 바쁜 식당 주방을 떠올려 보세요. 손님이 "스테이크는 미디엄으로, 파스타는 면 따로, 디저트는 마지막에"처럼 여러 요구가 섞인 주문을 하면, 요리사는 이걸 머릿속에만 담아두지 않습니다. 주문표(order ticket)를 뽑아 벽에 걸어두고 하나씩 완성될 때마다 줄을 그어 지우죠. TodoListMiddleware가 바로 이 주문표 시스템입니다. AI가 복잡한 요청을 받으면 할 일을 목록으로 적어 걸어두고, 하나씩 처리하며 완료 표시를 해나갑니다. 덕분에 단계를 빠뜨리지 않아요.
📥 코드
from langchain.agents.middleware import LLMToolEmulator
from langchain.agents.middleware import TodoListMiddleware

agent = create_agent(
    model=model,
    tools=[send_email_tool, read_email_tool],
    # tool emulator: 실제 도구 호출 대신 LLM으로 시뮬레이션, 즉, 도구가 만든 결과를 모킹하는것. gemini-2.5-flash 모델 사용
    middleware=[LLMToolEmulator(model="gpt-4o-mini"), TodoListMiddleware()],
    )

result = agent.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "온 메일 다 확인한 뒤 요약해 보고해. 그 다음 답장 작성해 회신 보내줘. 마지막으로 어떻게 보냈는지 보고해.",
            }
        ]
    }
)
print("=== 이메일 읽고 쓰기 결과 ===")
print(result)
print(result['messages'][-1].content)

사용자의 요청을 잘 보세요. 한 문장 안에 세 가지 일이 들어 있습니다 — ① 메일을 다 읽고 요약 보고, ② 답장을 써서 회신, ③ 어떻게 보냈는지 보고. 딱 TodoListMiddleware가 빛을 발하는 복잡한 다단계 요청입니다.

▶ 이렇게 나와요 (최종 답변 = result['messages'][-1].content)
=== 이메일 읽고 쓰기 결과 ===
{'messages': [HumanMessage(...), AIMessage(...), ToolMessage(...), ... ]}   # ← 아래 3번에서 뜯어봅니다
이메일 요약과 회신 작업이 완료되었습니다.

### 이메일 요약:
1. **프로젝트 업데이트**: 팀에서 최근 프로젝트 타임라인에 대한 간단한 업데이트를 제공했습니다.
2. **주간 뉴스레터**: 최신 기사 및 통찰력에 대한 정보를 담은 뉴스레터가 발송되었습니다.
3. **회의 알림**: 내일 오전 10시에 예정된 회의에 대한 알림이 있었습니다.

### 회신 내용:
- **받는 사람**: team@company.com
- **제목**: Re: Project Update
- **내용**:
  Hi Team,
  Thank you for the update on the project timeline. ...
  Best, [Your Name]

회신이 성공적으로 발송되었습니다.

최종 답변만 보면 그냥 "요약 → 답장 → 보고"를 잘 해낸 것처럼 보입니다. 하지만 이 매끄러운 결과 뒤에서 TodoListMiddleware가 정말 일을 했을까요? 그 증거는 최종 답변이 아니라 중간 로그에 숨어 있습니다. 다음 절에서 그 흔적을 찾아봅니다.

3. 로그에서 write_todos 확인하기

TodoListMiddleware가 실제로 동작했다는 결정적 증거는, AI가 write_todos라는 도구를 스스로 호출하는 장면입니다. print(result)로 찍힌 메시지 리스트를 살펴보면 이 호출이 여러 번 나타납니다.

🔍 비유 — CCTV 녹화 되감기 가게에 도둑이 들었는지 확인하려면 결과(없어진 물건)만 봐선 부족하죠. CCTV를 되감아 누가 언제 무엇을 했는지 봐야 확실합니다. result['messages'] 리스트가 바로 이 CCTV 녹화본입니다. AI의 발언(AIMessage)과 도구의 응답(ToolMessage)이 시간 순서대로 다 찍혀 있어서, 우리는 그걸 되감아 "아, 여기서 write_todos를 불렀구나"를 두 눈으로 확인할 수 있습니다.

확인 포인트 ① — AIMessage의 tool_calls에서 첫 할 일 등록

AI가 요청을 받자마자 이메일을 읽고(read_email_tool), 이어서 할 일 목록을 만들기 위해 write_todos를 호출합니다. 이때 인자(args)로 할 일(content)과 상태(status)의 리스트가 넘어갑니다.

▶ 로그에서 이렇게 보여요
"tool_calls": [{
    "name": "write_todos",
    "args": {"todos": [
        {"content": "Summarize the emails received",                    "status": "in_progress"},
        {"content": "Draft a reply to the relevant email",              "status": "pending"},
        {"content": "Send the reply email and report how it was sent",  "status": "pending"}
    ]},
    ...
}]

AI가 "이제 이메일 요약부터 시작하겠다(in_progress)"고 선언하고, 나머지 두 개는 대기(pending) 상태로 예약해 둔 장면입니다.

확인 포인트 ② — ToolMessage로 돌아오는 응답

write_todos 호출 직후, 미들웨어가 "목록을 저장했어요"라고 응답을 돌려줍니다. 이 응답은 ToolMessage 형태로 로그에 남습니다.

▶ 로그에서 이렇게 보여요
ToolMessage(
    content='{ "todos": [ {"content": "Summarize the emails received", "status": "in_progress"}, ... ] }',
    name='write_todos',
    ...
)

확인 포인트 ③ — 진행에 따라 status를 계속 갱신

한 번 쓰고 끝나는 게 아닙니다. 작업이 진행될 때마다 AI는 write_todos를 다시 호출해 상태를 바꿉니다. 요약이 끝나면 그 항목을 completed로 바꾸고, 다음 할 일(답장 작성)을 in_progress로 넘깁니다.

▶ 로그에서 이렇게 보여요
"args": {"todos": [
    {"content": "Summarize the emails received",                                    "status": "completed"},
    {"content": "Draft a reply to the relevant email regarding the project update", "status": "in_progress"},
    {"content": "Send the reply email and report how it was sent",                  "status": "pending"}
]}

확인 포인트 ④ — 마지막으로 전부 completed

모든 작업(요약 → 답장 → 보고)이 끝나기 직전, 목록을 마지막으로 한 번 더 갱신해 세 항목 모두 완료 처리합니다.

▶ 로그에서 이렇게 보여요
"args": {"todos": [
    {"content": "Summarize the emails received",                                    "status": "completed"},
    {"content": "Draft a reply to the relevant email regarding the project update", "status": "completed"},
    {"content": "Send the reply email and report how it was sent",                  "status": "completed"}
]}

이 흐름을 그림으로 정리하면 이렇습니다.

1목록 작성

3개 할 일 등록 · 첫 항목 in_progress

21개 완료

요약 completed · 답장 in_progress

32개 완료

답장까지 completed · 보고 진행

4전부 완료

3개 모두 completed → 최종 답변

📘 보충 — 할 일의 세 가지 상태(status)

write_todos가 관리하는 각 할 일에는 딱 세 가지 상태가 있습니다. 마치 스마트폰 배달 앱의 주문 추적과 같아요 — "접수됨 → 조리 중 → 배달 완료"처럼요.

status의미배달 앱에 비유
pending아직 시작 안 한 대기 상태주문 접수됨
in_progress지금 처리 중인 항목 (보통 한 번에 하나)조리 중
completed처리를 마친 항목배달 완료
💡 요약 — 무엇을 보면 "동작했다"고 말할 수 있나 로그에서 write_todos 호출이 여러 번 나타나고, 그 인자로 content와 status가 담긴 리스트가 오가며 상태가 pending → in_progress → completed로 바뀌어 간다면, TodoListMiddleware가 AI의 작업 순서를 실제로 관리하고 있다는 확실한 증거입니다.

4. "항상 동작"하지만 "쓸지 말지는 AI가 판단"

여기서 흔한 오해 하나를 짚고 갑니다. TodoListMiddleware를 얹었다고 해서 모든 질문에 할 일 목록이 만들어지는 건 아닙니다. 미들웨어는 항상 켜져 있지만, 실제로 목록을 쓸지 말지는 AI가 질문의 복잡도를 보고 스스로 결정합니다.

🔍 비유 — 항상 대기 중인 비서 유능한 비서가 늘 곁에 대기(감시 모드)하고 있다고 해봅시다. 당신이 "지금 몇 시야?"라고 물으면 비서는 굳이 수첩을 꺼내지 않고 바로 답합니다. 하지만 "출장 준비 좀 해줘"처럼 여러 일이 얽힌 요청이면, 비서는 그제야 수첩을 펼쳐 체크리스트를 적기 시작하죠. 비서(미들웨어)는 항상 옆에 있지만, 수첩을 펼칠지(=write_todos 호출)는 요청의 복잡도에 따라 판단하는 겁니다.
질문 유형예시AI의 행동로그의 write_todos
단순한 질문"지금 몇 시야?"바로 답변호출 없음
복잡한 다단계 요청"메일 확인 → 요약 → 답장 → 보고"할 일 목록을 만들어 단계별 수행여러 번 호출됨
💡 왜 이렇게 설계할까? 모든 질문에 억지로 To-Do를 만들면 응답이 느려지고 토큰 비용도 늘어납니다. 그래서 간단하면 바로 답, 복잡하면 목록 작성처럼 AI가 상황을 보고 판단하게 두는 것이 속도와 비용 면에서 훨씬 효율적입니다.
⚠️ 그래서 로그에 안 보일 수도 있어요 간단한 질문을 던졌는데 write_todos가 로그에 없다고 해서 "미들웨어가 고장 났다"고 오해하지 마세요. 미들웨어 자체는 언제나 실행되고 있고, 단지 AI가 "지금은 목록이 필요 없다"고 판단했을 뿐입니다.

📚 한 장 정리

오늘의 핵심 TodoListMiddleware는 복잡한 요청을 만난 AI가 스스로 할 일 목록을 쓰고(write_todos) 하나씩 체크하게 만드는 "주문표 시스템"이다. 동작 여부는 로그의 write_todos 호출로 확인한다.
  • 미들웨어 — Agent 실행 사이에 끼어드는 "무대 뒤 스태프". middleware=[...]에 넣어 얹는다.
  • TodoListMiddleware — AI에게 write_todos 도구를 줘서 복잡한 요청을 단계별 To-Do로 관리하게 한다(주문표).
  • 동작 확인법 — result['messages']를 되감아 write_todos 호출이 여러 번 있고, args에 content+status 리스트가 오가는지 본다(CCTV 되감기).
  • 상태 3종 — pending(대기) → in_progress(진행 중) → completed(완료), 배달 앱 추적처럼.
  • 항상 vs 판단 — 미들웨어는 항상 켜져 있지만, 목록을 쓸지는 질문의 복잡도를 보고 AI가 결정한다. 간단한 질문엔 로그에 안 나올 수 있다.
  • 함께 쓴 LLMToolEmulator — 실제 메일을 보내지 않고 결과를 모킹하는 "리허설" 미들웨어(04장).
