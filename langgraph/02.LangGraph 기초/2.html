2. Agent 구축 실전 — 기획부터 LLM·Tool 결합까지

실습 노트북: 2.ipynb  ·  대상 범위: 2-1 프로젝트 기획 ~ 2-2 실전 구현 (실전 1 · 실전 2)  ·  난이도: 🟡 초급~중급

1장에서 익힌 State · Node · Edge · 조건부 엣지로 진짜 프로젝트 하나를 처음부터 끝까지 만듭니다 — 고객 이메일 자동 응대 에이전트. 다만 바로 코드로 들어가지 않고, 실무에서 코드보다 먼저 해야 하는 "기획 3단계"를 배운 뒤 그 기획서를 코드로 옮기는 과정을 두 번 반복합니다 — 실전 1(키워드 라우팅)로 뼈대를 잡고, 실전 2(LLM + Tool)로 지능을 얹습니다. 실무에서 진짜 어려운 건 문법이 아니라 "내 프로젝트를 어떻게 노드로 쪼갤 것인가"이고, 이번 장의 절반은 그 쪼개는 방법에 씁니다.

2-1. 프로젝트 기획 — 왜 코드보다 기획이 먼저인가

회사에서 이런 업무를 하나 받았다고 해봅시다.

1장의 순서(①모델·도구 → ②State → ③Node → ④그래프 → ⑤실행)대로라면 곧장 class State(TypedDict):부터 치고 싶어집니다. 그런데 그러면 안 됩니다.

🚫 기획 없이 시작하면 벌어지는 일

State를 대충 만들고 노드를 세 개쯤 짜다 보면 "여기서 분류 결과도 State에 담아야 하네"를 깨닫고 State 클래스를 고칩니다. 그러면 이미 만든 노드들의 반환 딕셔너리도 전부 손봐야 하고, 이 일이 반복되며 코드가 꼬입니다. 기획을 먼저 하면 두 번 일하지 않습니다.

🔍 비유 — 집 짓기 전 설계도

방 세 개를 다 만들고 나서 "화장실 배관을 어디로 빼지?"를 고민하면 벽을 부숴야 합니다. State가 정확히 배관입니다 — 모든 노드가 State를 통해서만 데이터를 주고받으므로, 나중에 바꾸면 모든 방의 벽을 뜯어야 합니다. 그래서 배관 도면(State 설계)을 벽 세우기(코딩) 전에 그리는 겁니다.

기획도 3단계 — 코드 순서와 "일부러" 다릅니다

기획은 코딩과 반대로 State를 맨 마지막에 정합니다. 노드들이 무슨 일을 하는지 다 정해져야, 그 노드들이 뭘 주고받을지 알 수 있기 때문입니다.

1요구사항 분석

이 에이전트가 어떤 기능을 해야 하나? → 기능 하나 = 노드 하나

2그래프 구성

노드를 어떻게 배치하고 이을까? → 유저 플로우 그리기

3State 설계

노드끼리 뭘 주고받아야 하나? → 필드와 키 이름 확정

💡 기획 순서 vs 코딩 순서

기획: 요구사항 → 노드 → 그래프 → State  ·  코딩: 모델·도구 → State → 노드 → 그래프 → 실행

기획은 "무엇을 할까"에서 데이터로 내려가고, 코딩은 데이터에서 "무엇을 할까"로 올라갑니다.

기획 1단계 · 요구사항 분석 — 기능 하나가 노드 하나

"고객 이메일 자동 응대 에이전트"가 어떤 기능을 해주면 좋을지 자유롭게 나열합니다. 아직 코드 생각은 하지 않는 기획자 모드입니다.

1장에서 노드는 State를 기반으로 일하는 "작업자"였습니다. 방금 나열한 것들이 전부 "하나의 일"이므로, 일 하나 = 작업자 하나 = 노드 하나가 됩니다. 이제 각 기능에 노드 이름을 붙입니다 — 이 이름은 나중에 add_node·add_edge·라우팅 함수까지 전부 재사용됩니다.

💡 "뼈대만"이라는 선택지

search_manual에 임베딩·청킹·벡터DB까지 지금 붙이면 정작 배우려던 그래프 구조가 안 보입니다. 그래서 print() 한 줄만 넣고 넘어갑니다 — 의도적인 학습 전략입니다. 흐름을 먼저 완성해 두면 나중에 노드 안쪽만 진짜 RAG로 갈아끼우면 되고, 실전 2에서 실제로 그렇게 합니다.

기획 2단계 · 그래프 구성 — 노드를 어떻게 배치할까

사용자 입장에서 이야기를 만들어 보는 것이 요령입니다.

  1. 이메일이 들어오면 먼저 읽는다. → START → read_email
  2. 읽은 메일의 의도와 주제를 파악한다(분류). → read_email → classify_intent
  3. (Case A) 급하지 않은 문의라면 — 매뉴얼을 검색한 뒤 답변을 작성한다. → search_manual → write_reply → END
  4. (Case B) 긴급한 메일이라면 — 사람(상담원)에게 넘긴다. → escalate_to_human → END
🔍 비유 — 실선은 복도, 점선은 갈림길

실선은 "여기서 나가면 무조건 저기"인 복도(read_email → classify_intent), 점선은 갈림길에 세워둔 표지판 — 나오는 순간 그때그때 판단합니다. 기획 단계에서 실선/점선을 구분해 두면 코드에서 add_edge와 add_conditional_edges가 저절로 갈립니다.

기획 3단계 · State 설계 — 노드끼리 뭘 주고받을까

그래프 그림의 화살표를 하나씩 따라가며 묻습니다 — "이 노드가 다음 노드한테 뭘 넘겨줘야 하지?"

START

이메일 원문 — 뒤의 거의 모든 노드가 봐야 함 → 담는다 (str)

read_email

이번엔 단순히 넘기기만 → 새로 담을 것 없음

classify_intent

① 메일의 의도(주제) → 담는다 (str)
② 분류 결과 → 반드시 담는다 — 이 값이 있어야 갈림길에서 분기 판단이 가능 (str)

search_manual

RAG를 구현하지 않으므로 → 이번엔 담지 않음

write_reply

LLM이 만든 답변 → 담는다 (str). END에서 반환되는 건 State 전체이므로, 답변이 State에 있어야 사용자가 받아볼 수 있습니다.

💡 next_step의 값을 "노드 이름과 똑같이" 맞추는 이유

조건부 엣지의 라우팅 함수는 "갈 노드의 이름 문자열"을 반환해야 합니다. next_step 값이 이미 노드 이름("escalate_to_human", "search_manual")이면 그대로 return하기만 하면 되고 오타 에러 확률이 확 줄어듭니다. 기획 단계의 작은 결정이 코딩 단계의 버그를 미리 막은 셈입니다.

실전 1 · 키워드 라우팅 에이전트 — 완성 결과 미리보기

⚠️ 슬라이드와 실제 노트북 출력의 차이

위 슬라이드는 완성형을 보여주기 위한 예시입니다. 실제 2.ipynb는 3-A 진입... 메뉴얼을 검색합니다만 찍히고, Case 2의 'response': '티켓 #1234...'도 기본 코드에는 없습니다(뒤에서 직접 넣어봅니다). 슬라이드는 목표, 노트북은 최소 구현입니다.

STEP 1. Model 및 Tool 정의

📥 코드
from langchain_google_genai import ChatGoogleGenerativeAI

model = ChatGoogleGenerativeAI(model="gemini-3-flash-preview")
💡 왜 실전 1에는 도구가 없을까

도구를 붙이면 tool_calls·ToolMessage 처리 코드가 따라붙고, 그게 난이도의 대부분입니다. 실전 1의 목표는 "기획서를 코드로 옮기는 감각"이므로 도구는 실전 2로 미룹니다. 한 번에 한 가지씩만 새로 배우는 게 빠릅니다.

STEP 2. State 정의 — 기획서를 그대로 옮기기

기획 3단계에서 확정한 네 개의 키를 그대로 TypedDict로 옮깁니다. 기획을 해두면 이 단계가 10초 만에 끝납니다.

📥 코드
from typing_extensions import TypedDict

class AgentState(TypedDict):
    email_content: str   # 고객이 보낸 이메일 원문
    category: str        # 분류된 주제/의도 (inquiry / complaint)
    next_step: str       # 다음에 갈 노드 이름 → 분기 판단 기준
    response: str        # LLM이 만든 최종 답변
💡 1장의 State와 다른 점 — 리듀서가 없다

1장의 messages: Annotated[list[AnyMessage], add_messages]와 달리 이번 State는 전부 덮어쓰기입니다. category도 response도 최신 값 하나만 있으면 되니까요. "누적해야 하는 값"에만 리듀서를 붙인다고 기억하면 됩니다.

STEP 3. Node 정의 — 다섯 명의 작업자

1장에서 배운 노드의 계약 그대로 — ① state를 입력으로 받고, ② State 양식에 맞는 딕셔너리를 반환하는 함수 다섯 개를 씁니다.

① read_email — 이메일을 받아 공책에 옮겨 적기

📥 코드
# [Node 1] 이메일 읽기
def read_email(state: AgentState):
    return {'email_content': state['email_content']}

받은 값을 그대로 되돌려주는, 아무것도 안 바꾸는 노드입니다. 원래는 여기서 키워드 추출·전처리 같은 일을 해야 하는데 이번엔 생략해서 뼈대만 남은 겁니다. 더 중요한 건 — 이 노드가 state['email_content']에 접근하므로 invoke()의 입력에 그 칸이 채워져 있어야 한다는 점입니다.

▶ 그래서 실행은 이렇게 됩니다 (STEP 5 미리보기)
inputs = {"email_content": "비밀번호 변경 방법을 알려주세요."}
response = agent.invoke(inputs)
🔍 비유 — 접수 창구의 서식

민원실 서식에 없는 종이는 접수가 안 됩니다. invoke()에 넘기는 딕셔너리가 그 서식입니다 — 1장은 {"messages": [...]}, 이번엔 {"email_content": "..."}. 서식(State 클래스)이 바뀌면 접수 방법도 바뀝니다.

② classify_intent — 갈림길의 판단 근거를 만드는 노드

📥 코드
# [Node 2] 의도 분류 (Router 로직의 기준점)
def classify_intent(state: AgentState):
    email = state['email_content']

    # 언어 모델 대신 "키워드"로 판단 — 실전 2에서 LLM으로 바꿉니다
    if '환불' in email or '긴급' in email or '빨리' in email:
        category = 'complaint'
        next_step = 'escalate_to_human'
    else:
        category = 'inquiry'
        next_step = 'search_manual'

    return {'category': category, 'next_step': next_step}

이 그래프에서 가장 중요한 노드입니다. '환불' in email은 그냥 파이썬 문자열 포함 검사 — 언어 모델은 관여하지 않는 의도된 단순화이고, 바로 이 지점이 실전 1의 한계가 됩니다. 반환값이 두 개인 이유: category는 "이 메일이 무엇인가"(사람이 보는 라벨), next_step은 "그래서 어디로 갈 것인가"(기계가 보는 표지판)입니다. 나중에 "complaint 중 VIP는 다른 노드로" 같은 규칙이 생겨도 category는 그대로 두고 next_step만 바꾸면 됩니다.

🔍 비유 — 진료 접수증의 두 칸

접수증엔 "증상: 복통"(판단의 근거)과 "안내: 내과 3번 진료실"(지시)이 따로 적힙니다. category가 증상, next_step이 진료실 번호이고 — 진료실 번호는 실제 존재하는 방 번호와 정확히 일치해야 하므로 next_step 값을 노드 이름과 똑같이 맞춰 둔 겁니다.

③ search_manual / escalate_to_human — 뼈대만 있는 두 노드

📥 코드
# [Node 3-A] 매뉴얼 검색 (AI 자동 처리 트랙)
def search_manual(state: AgentState):
    print('3-A 진입... 메뉴얼을 검색합니다')
    return


# [Node 3-B] 상담원 이관 (긴급 이슈 트랙)
def escalate_to_human(state: AgentState):
    print('3-B 진입... 상담원 인관합니다')
    return
💡 return만 쓰고 아무것도 안 돌려줘도 되나요?

됩니다. 값 없는 return은 None이고, LangGraph는 이를 "이 노드는 State를 하나도 바꾸지 않았다"로 해석합니다. 덕분에 흐름은 완성해 두고 내용물은 나중에 채우는 개발이 가능합니다.

⚠️ 이 단순화가 남긴 구멍 — 검색 결과가 답변에 반영되지 않는다

search_manual이 State에 아무것도 안 쓰므로 다음 노드 write_reply는 검색 결과를 볼 방법이 없고, 이메일 원문만 보고 답을 만듭니다. "RAG로 증강된 답변"은 아직 흉내만 낸 상태 — 실전 2에서 messages 기반으로 바꿔 해결합니다.

④ write_reply — 언어 모델이 답변을 만드는 노드

📥 코드
# [Node 4] 답변 생성
def write_reply(state: AgentState):
    email = state['email_content']
    response = model.invoke(email)      # 언어 모델 호출
    return {'response': response}

이메일을 꺼내 → 모델에 넘기고 → 결과를 response 칸에 적습니다. State에 담는 이유는 명확합니다 — END에서 반환되는 건 State 전체이므로, State에 적히지 않은 것은 사용자에게 도달하지 않습니다.

⚠️ 눈여겨볼 함정 — 타입이 str이 아니다

model.invoke(email)가 돌려주는 건 문자열이 아니라 AIMessage 객체인데 에러가 나지 않습니다. TypedDict의 타입은 실행 시점에 검사되지 않는 "메모"이기 때문입니다. 깔끔하게 하려면 response.content(Gemini는 response.content[-1]['text'])로 문자열만 꺼내 담는 편이 낫습니다 — 뒤의 State 설계 원칙과도 이어지는 이야기입니다.

💡 시스템 메시지를 안 넣었습니다

이메일 원문만 던지면 모델이 "어떤 서비스의 비밀번호인가요?"라고 되묻는 어색한 답이 나옵니다. 원래는 SystemMessage("당신은 고객센터 상담원입니다...")를 앞에 붙여야 하고, 실전 2에서 실제로 사용합니다.

STEP 4. 그래프 생성 — 기획서의 그림을 코드로

📥 코드 — ① 초기화 + ② 노드 등록 + ③ 실선 엣지

# 1. 워크플로우(그래프) 생성 — 공책 양식(AgentState)을 알려주며 도면 펼치기
agent_builder = StateGraph(AgentState)


# 2. 노드(작업자) 배치 — 이름표와 함수 이름을 똑같이 맞춥니다
agent_builder.add_node('read_email', read_email)
agent_builder.add_node('classify_intent', classify_intent)

agent_builder.add_node('escalate_to_human', escalate_to_human)

💡 이름표와 함수 이름을 똑같이 맞추는 습관

add_node('read_email', read_email)의 두 인자(이름표 문자열, 함수 객체)는 달라도 되지만, 똑같이 맞추면 라우팅 함수에서 이름을 한 번 더 변환할 필요가 없어집니다. 기획 단계에서 next_step 값까지 통일해 둔 게 여기서 빛을 봅니다.

④ 조건부 엣지 — 갈림길 만들기

📥 코드 — (1) 라우팅 함수

def route_email(state: AgentState):

agent_builder.add_conditional_edges(

    ['escalate_to_human', 'search_manual']    # 3) 갈 수 있는 목적지 목록
)

🔑 세 번째 인자, 리스트로 쓸까 딕셔너리로 쓸까

# 라우팅 함수가 노드 이름이 아닌 "별칭"을 반환한다면
def route_email(state: AgentState):
    if state['next_step'] == 'escalate_to_human':
        return 'node_A'          # ← 노드 이름이 아님
    else:
        return 'node_B'          # ← 노드 이름이 아님

agent_builder.add_conditional_edges(
    'classify_intent',
    route_email,
    {
        'node_A': 'escalate_to_human',
        'node_B': 'search_manual'
    }
)
🔍 비유 — 출입 명단 vs 좌석 배치표

리스트는 출입 가능자 명단 — 이름이 곧 목적지이니 명단에 있는지만 확인하면 됩니다. 딕셔너리는 좌석 배치표 — "1번 티켓 → A구역"처럼 티켓 번호와 구역 이름이 다르니 대조표가 필요합니다. 강의에서는 실전 1은 리스트, 실전 2는 두 방식을 하나씩 써보며 둘 다 익힙니다.

② 도구 — RAG "흉내"를 내는 search_manual

실전 1에서 노드였던 search_manual이 이번에는 도구(Tool)가 됩니다 — 1장 그대로 평범한 함수 + @tool 데코레이터 + docstring.

📥 코드
from langchain.tools import tool

@tool
def search_manual(query: str) -> str:
    """
    고객의 질문에 답변하기 위해 참고할만한 규정이나 메뉴얼을 검색할 때 사용하는 도구
    """
    if '비밀번호' in query:
        return '비밀번호 변경은 마이페이지 - 보안 설정에 있음'
    elif '배송' in query:
        return '00택배에서 3일 내 배송 예정임'
    else:
        return '해당 내용 관련 메뉴얼은 찾을 수 없습니다'
💡 진짜 RAG 대신 하드코딩한 이유

중요한 건 인터페이스입니다 — query(str)를 받아 str을 돌려주는 함수. 나중에 이 함수 안쪽만 진짜 벡터 검색으로 갈아끼우면 그래프는 한 글자도 안 바뀝니다. docstring이 모델이 "언제 이 도구를 부를지" 판단하는 유일한 근거라는 점은 1장에서 배운 그대로입니다.

③ 모델에 도구 바인딩

📥 코드

# 도구 목록이 붙은 "새로운" 모델 객체가 만들어집니다
model_with_tools = model.bind_tools(tools)
⚠️ model과 model_with_tools를 구분해서 씁니다
  • classify_node → model (도구 없음) — 분류는 단어 하나만 답하면 되는 일.
  • consultant_node → model_with_tools — 답변 도중 매뉴얼 검색을 요청할 수 있어야 함.

반대로 쓰면 분류 노드가 "consultant" 대신 도구 호출 요청서를 돌려주는 이상한 일이 벌어집니다.

STEP 2. State 정의 — 다시 messages로

📥 코드
from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]   # 대화 기록 (누적)
    next_step: str                                        # 분기 판단 기준

왜 messages로 돌아왔을까

도구를 쓰기 때문입니다. 사용자 질문(HumanMessage) → 도구 호출 요청서(AIMessage.tool_calls) → 실행 결과(ToolMessage) → 최종 답변(AIMessage)을 순서대로 담아 모델에 다시 넘겨야 하므로, 한 줄로 쌓이는 리스트 하나가 정답입니다.

🔍 비유 — 항목별 서류함 vs 시간순 대화록

실전 1의 State는 종류별로 칸이 나뉜 서류함 — 일직선 흐름엔 깔끔합니다. 실전 2는 상담원이 자료실에 몇 번이고 물어볼 수 있어 "누가 언제 무슨 말을 했는지"가 순서대로 남는 대화록이 필요합니다. 루프가 생기는 순간 서류함으로는 감당이 안 됩니다.

💡 next_step은 왜 남겨뒀나

분류 결과는 대화의 일부가 아니라 "제어 신호"이기 때문입니다. messages에 넣으면 상담 모델이 그 메시지를 읽고 혼란스러워합니다. 대화에 남길 것과 흐름 제어에만 쓸 것을 분리한 설계입니다.

STEP 3. Node 정의 — 네 명의 작업자

① classify_node — LLM에게 분류를 맡기는 노드

📥 코드
# [Node 1] 분류 노드 (Manager)
from langchain.messages import SystemMessage


def classify_node(state: AgentState):
    print("\n--- [1] 분류 단계 (LLM 판단) ---")
    last_message = state["messages"][-1]      # 사용자의 질문(HumanMessage)

    # 분류를 위한 프롬프트 (System Prompt)
    prompt = """
    당신은 고객 센터 관리자입니다. 고객의 이메일을 분석해서 다음 단계를 결정하세요.

    1. 단순 문의나 정보 요청이라면 -> 'consultant' 반환
    2. 환불 요청, 불만 제기, 화난 고객이라면 -> 'escalate' 반환

    답변은 오직 단어 하나만 하세요.
    """

    # LLM 호출 — 도구가 붙지 않은 model 사용
    response = model.invoke([SystemMessage(content=prompt), last_message])
    raw_content = response.content

    if isinstance(raw_content, list):
        # Gemini 등: 리스트로 오는 경우 텍스트 블록만 추출해서 합침
        decision = "".join([block['text'] for block in raw_content if block.get('type') == 'text'])
    else:
        # OpenAI 등: 문자열로 오는 경우 그대로 사용
        decision = str(raw_content)

    # 공백 제거 및 소문자 변환
    decision = decision.strip().lower()
    print(f"   -> LLM 판단 결과: {decision}")

    # 다음 단계(next_step)를 상태에 저장
    if "escalate" in decision:
        return {"next_step": "escalate"}
    else:
        return {"next_step": "consultant"}

하는 일은 세 덩어리입니다 — ① 시스템 프롬프트 + 질문을 모델에 넘겨 단어 하나를 받고, ② 모델마다 다른 content 형태에서 텍스트만 추출하고, ③ 그 단어를 보고 next_step을 적습니다. 실전 1의 if '환불' in email이 하던 일을 한국어 지시문이 대신하므로, 이제 "환급"이든 "돈 돌려줘"든 모델이 의미로 이해합니다. isinstance 분기는 1장에서 본 Gemini(리스트) vs OpenAI(문자열) 응답 차이 대비이고, .strip().lower()는 "LLM 출력은 항상 지저분할 수 있다"는 방어입니다.

💡 "답변은 오직 단어 하나만 하세요."가 중요한 이유

이 문장이 없으면 모델이 문장으로 설명해 버려 값 비교가 지저분해집니다. 코드도 if "escalate" in decision처럼 포함 검사로 방어합니다 — "출력 형식을 지시하고, 코드에서도 방어한다"는 이중 안전장치입니다.

🚫 강의 중 실제로 에러가 났던 지점 — +인가 ,인가

model.invoke([SystemMessage(content=prompt)] + last_message) ❌ — last_message는 메시지 객체 하나라 리스트에 +로 이어붙일 수 없습니다. [SystemMessage(content=prompt), last_message] ✅ 처럼 쉼표로 한 리스트에 넣거나, + [last_message]로 오른쪽도 리스트로 만드세요.

📌 노트북 확인: 배포된 2.ipynb에는 아직 + last_message 버전이 남아 있습니다. 그대로 실행하면 TypeError가 나므로 쉼표로 고친 뒤 실행하세요.

from langchain.messages import ToolMessage

# [Node 4] Tool Node
def tool_node(state: AgentState):
    print("\n--- [Tool Node] 도구 직접 실행 ---")
    result = []
    # 가장 최근 메시지에서 도구 호출 요청 꺼내기
    last_message = state["messages"][-1]

    for tool_call in last_message.tool_calls:
        # 1. 도구 이름으로 실제 함수 찾기
        tool = tools_by_name[tool_call["name"]]

        # 2. 함수를 실행하여 결과를 얻기
        print(f"   -> 실행 중: {tool_call['name']}")
        tool_result = tool.invoke(tool_call["args"])

        # 3. 결과를 ToolMessage 형태로 포장 (tool_call_id 필수!)
        result.append(ToolMessage(content=str(tool_result), tool_call_id=tool_call["id"]))

    # 실행 결과를 대화 기록에 추가
    return {"messages": result}
💡 이 코드가 1장과 똑같다는 게 포인트입니다

"마지막 메시지에서 tool_calls를 꺼내 이름으로 함수를 찾아 실행하고 ToolMessage로 포장한다"는 절차는 도구가 무엇이든 무관합니다. 그래서 LangGraph는 이걸 ToolNode라는 이름으로 이미 만들어 뒀습니다(다음 강의에서 다룹니다). tool_call_id가 택배 송장 번호(요청-응답 대조용 필수값)라는 것도 1장 그대로입니다.

💡 이 원칙으로 우리 State를 되짚어 보면

next_step — 바로 다음 라우터가 씁니다. ✅ 유지
email_content — 다다음 노드까지 씁니다. ✅ 유지
category — 사실 어떤 노드도 읽지 않습니다. 원칙대로라면 뺄 후보지만, "왜 이렇게 분류됐는지"를 확인하는 로그·감사 용도로는 가치가 있습니다. 원칙은 규칙이 아니라 판단 기준이라는 좋은 예입니다.

원칙 2 · 가공되지 않은 '날 것(Raw)'을 저장하라

차이는 라우팅 함수를 써보면 즉시 드러납니다.

📥 Good Case — 구조화된 데이터
state["customer_info"] = {
    "grade": "VIP",
    "status": "Angry"
}

def route(state):
    if state["customer_info"]["grade"] == "VIP":   # 정확하게 한 번에 꺼냄
        return "vip_service"
📥 Bad Case — 사람이 읽기 좋게 가공한 문장
state["customer_info"] = "이 고객은 VIP 등급이며 매우 화가 난 상태입니다."

def route(state):
    if "VIP" in state["customer_info"]:            # 문자열을 뒤져야 함 (불안정)
        return "vip_service"
⚠️ Bad Case가 왜 나쁜가
  • 추출 비용이 다시 든다 — 문장에서 등급을 뽑으려면 키워드 검색이나 LLM 재호출이 필요합니다. 돈과 시간이 두 번 나갑니다.
  • 깨지기 쉽다 — 문구가 "non-VIP"로 바뀌면 "VIP" in ...이 조용히 잘못 걸립니다.
  • 이미 아는 정보를 버린 것 — 구조화된 데이터를 일부러 문장으로 뭉갠 셈입니다.
🔍 비유 — 엑셀 표 vs 줄글 보고서

같은 매출 데이터도 엑셀 표면 정렬·필터·합계가 즉시 되고, 줄글 보고서면 숫자를 하나씩 옮겨 적어야 합니다. State는 사람이 읽는 보고서가 아니라 노드가 처리하는 데이터입니다 — 보기 좋게 만드는 건 맨 마지막, 사용자에게 보여줄 때 하면 됩니다.

💡 실전 1의 response를 다시 보면

AIMessage 객체를 통째로 담은 건 원칙 2 관점에서는 오히려 "날 것"에 가깝습니다. 다만 str이라고 선언해 놓고 객체를 넣은 것은 별개의 문제 — 타입 선언과 실제 값을 일치시키거나 response: AIMessage로 선언을 고치는 게 정직합니다.

실전 1 · 키워드 라우팅 에이전트

📥 전체 코드
# ══ STEP 1. Model & Tool ══════════════════════════════
from langchain_google_genai import ChatGoogleGenerativeAI

model = ChatGoogleGenerativeAI(model="gemini-3-flash-preview")
# (실전 1은 도구를 쓰지 않습니다)

# ══ STEP 2. State ═════════════════════════════════════
from typing_extensions import TypedDict

class AgentState(TypedDict):
    email_content: str   # 고객 이메일 원문
    category: str        # 분류 결과 라벨 (inquiry / complaint)
    next_step: str       # 다음에 갈 노드 이름 → 분기 기준
    response: str        # 최종 답변

# ══ STEP 3. Node ══════════════════════════════════════
# [1] 이메일 읽기 — 지금은 그대로 넘기기만
def read_email(state: AgentState):
    return {'email_content': state['email_content']}

# [2] 의도 분류 — 키워드 매칭 (실전 2에서 LLM으로 교체)
def classify_intent(state: AgentState):
    email = state['email_content']
    if '환불' in email or '긴급' in email or '빨리' in email:
        category, next_step = 'complaint', 'escalate_to_human'
    else:
        category, next_step = 'inquiry', 'search_manual'
    return {'category': category, 'next_step': next_step}

# [3-A] 매뉴얼 검색 — 뼈대만 (State 변경 없음)
def search_manual(state: AgentState):
    print('3-A 진입... 메뉴얼을 검색합니다')
    return

# [3-B] 상담원 이관 — 고정 안내 문구를 response에 담아 반환
def escalate_to_human(state: AgentState):
    print('3-B 진입... 상담원 인관합니다')
    return {'response': '불편을 드려 죄송합니다. 상담원에게 이관하였으니 잠시 대기해 주시기 바랍니다.'}

# [4] 답변 생성 — 언어 모델 호출
def write_reply(state: AgentState):
    email = state['email_content']
    response = model.invoke(email)
    return {'response': response}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END

agent_builder = StateGraph(AgentState)

agent_builder.add_node('read_email', read_email)
agent_builder.add_node('classify_intent', classify_intent)
agent_builder.add_node('search_manual', search_manual)
agent_builder.add_node('escalate_to_human', escalate_to_human)
agent_builder.add_node('write_reply', write_reply)

agent_builder.add_edge(START, 'read_email')
agent_builder.add_edge('read_email', 'classify_intent')

# next_step 값을 그대로 반환 (값 = 노드 이름으로 맞춰 뒀기 때문)
def route_email(state: AgentState):
    if state['next_step'] == 'escalate_to_human':
        return 'escalate_to_human'
    else:
        return 'search_manual'

agent_builder.add_conditional_edges(
    'classify_intent',
    route_email,
    ['escalate_to_human', 'search_manual']   # 반환값 = 노드 이름 → 리스트로 충분
)

agent_builder.add_edge('search_manual', 'write_reply')
agent_builder.add_edge('write_reply', END)
agent_builder.add_edge('escalate_to_human', END)

agent = agent_builder.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
response = agent.invoke({"email_content": "비밀번호 변경 방법을 알려주세요."})   # → 3-A 트랙
response = agent.invoke({"email_content": "당장 환불해줘!"})                 # → 3-B 트랙

실전 2 · LLM + Tool 결합 에이전트

📥 전체 코드
# ══ STEP 1. Model & Tool ══════════════════════════════
from langchain_google_genai import ChatGoogleGenerativeAI
from langchain.tools import tool

model = ChatGoogleGenerativeAI(model="gemini-3-flash-preview")

@tool
def search_manual(query: str) -> str:
    """
    고객의 질문에 답변하기 위해 참고할만한 규정이나 메뉴얼을 검색할 때 사용하는 도구
    """
    if '비밀번호' in query:
        return '비밀번호 변경은 마이페이지 - 보안 설정에 있음'
    elif '배송' in query:
        return '00택배에서 3일 내 배송 예정임'
    else:
        return '해당 내용 관련 메뉴얼은 찾을 수 없습니다'

tools = [search_manual]
model_with_tools = model.bind_tools(tools)   # 분류용 model / 상담용 model_with_tools 를 구분해 씁니다

# ══ STEP 2. State ═════════════════════════════════════
from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]   # 대화 기록 (덮어쓰지 않고 누적)
    next_step: str                                        # 제어 신호 (대화에는 남기지 않음)

# ══ STEP 3. Node ══════════════════════════════════════
from langchain.messages import SystemMessage, ToolMessage
from langchain_core.messages import AIMessage

# [1] 분류 — LLM이 읽고 판단
def classify_node(state: AgentState):
    print("\n--- [1] 분류 단계 (LLM 판단) ---")
    last_message = state["messages"][-1]

    prompt = """
    당신은 고객 센터 관리자입니다. 고객의 이메일을 분석해서 다음 단계를 결정하세요.

    1. 단순 문의나 정보 요청이라면 -> 'consultant' 반환
    2. 환불 요청, 불만 제기, 화난 고객이라면 -> 'escalate' 반환

    답변은 오직 단어 하나만 하세요.
    """

    # 주의: [SystemMessage(...)] + last_message 는 TypeError (오른쪽이 리스트가 아님)
    response = model.invoke([SystemMessage(content=prompt), last_message])
    raw_content = response.content

    if isinstance(raw_content, list):
        decision = "".join([b['text'] for b in raw_content if b.get('type') == 'text'])   # Gemini
    else:
        decision = str(raw_content)                                                      # OpenAI

    decision = decision.strip().lower()
    print(f"   -> LLM 판단 결과: {decision}")

    if "escalate" in decision:
        return {"next_step": "escalate"}
    else:
        return {"next_step": "consultant"}

# [2] 상담 — 바로 답할지 도구를 부를지 모델이 스스로 판단
def consultant_node(state: AgentState):
    print("\n--- [2-A] 상담 AI 답변 생성 중 ---")
    response = model_with_tools.invoke(state['messages'])
    return {'messages': [response]}

# [3] 이관 — LLM 호출 없이 고정 메시지
def escalate_node(state: AgentState):
    return {'messages': [AIMessage(content='해당 메일은 전문 상담원에게 이관되었습니다.')]}

# [4] 도구 실행 — 1장에서 만든 것과 동일
tools_by_name = {tool.name: tool for tool in tools}

def tool_node(state: AgentState):
    print("\n--- [Tool Node] 도구 직접 실행 ---")
    result = []
    last_message = state["messages"][-1]
    for tool_call in last_message.tool_calls:
        tool = tools_by_name[tool_call["name"]]
        print(f"   -> 실행 중: {tool_call['name']}")
        tool_result = tool.invoke(tool_call["args"])
        result.append(ToolMessage(content=str(tool_result), tool_call_id=tool_call["id"]))
    return {"messages": result}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END

agent_builder = StateGraph(AgentState)

agent_builder.add_node('classify_node', classify_node)
agent_builder.add_node('consultant_node', consultant_node)
agent_builder.add_node('escalate_node', escalate_node)
agent_builder.add_node('tool_node', tool_node)

agent_builder.add_edge(START, 'classify_node')

# 라우터 1 — 별칭을 반환하므로 딕셔너리(번역표) 필요
def route_after_classify(state: AgentState):
    if state['next_step'] == 'escalate':
        return 'escalate'
    else:
        return 'consultant'

# 라우터 2 — 실제 노드 이름을 반환하므로 리스트면 충분
def should_continue(state: AgentState):
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "tool_node"
    return END

agent_builder.add_conditional_edges(
    'classify_node',
    route_after_classify,
    {'escalate': 'escalate_node', 'consultant': 'consultant_node'}
)

agent_builder.add_conditional_edges(
    'consultant_node',
    should_continue,
    ['tool_node', END]
)

agent_builder.add_edge('tool_node', 'consultant_node')   # ★ 이 한 줄이 루프를 만든다
agent_builder.add_edge('escalate_node', END)

agent = agent_builder.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
from langchain.messages import HumanMessage

response = agent.invoke({"messages": [HumanMessage(content="비밀번호 변경은 어디서 해?")]})
# Gemini는 content가 리스트라 한 번 더 꺼냄
print(response["messages"][-1].content[-1]['text'])

response = agent.invoke({"messages": [HumanMessage(content="당장 환불해줘!")]})   # → escalate 트랙

자주 걸리는 함정 6가지

🕳️ 이번 장에서 실제로 밟게 되는 지뢰

1. [SystemMessage(...)] + last_message — 리스트에 객체를 더한다

+는 리스트끼리만 됩니다. last_message는 객체 하나이므로 TypeError.
[SystemMessage(...), last_message] ✅ 또는 [SystemMessage(...)] + [last_message] ✅

2. 노드를 고쳐놓고 그래프를 다시 컴파일하지 않는다

agent는 컴파일 시점의 함수를 붙들고 있는 사본입니다. StateGraph(...)부터 compile()까지 전부 다시 실행하세요.

3. invoke()에 넘기는 딕셔너리 모양을 State와 안 맞춘다

실전 1은 {"email_content": "..."}, 실전 2는 {"messages": [HumanMessage(...)]}. State 클래스가 바뀌면 입력 서식도 바뀝니다. 1장 습관대로 {"messages": ...}를 넣으면 실전 1에서는 KeyError: 'email_content'가 납니다.

4. 라우팅 함수 반환값과 세 번째 인자를 안 맞춘다

반환값이 노드 이름 그대로면 리스트, 별칭이면 딕셔너리(번역표). return 'escalate'인데 ['escalate_node', ...]를 넘기면 목적지를 못 찾습니다.

5. 분기해서 끝나는 트랙에 답변을 안 담는다

escalate_to_human이 return만 하면 response가 영영 비어 있습니다. 모든 종료 경로가 사용자에게 돌려줄 값을 남기는지 확인하세요.

6. 분류용 모델에 도구를 바인딩한다

classify_node에서 model_with_tools를 쓰면 "consultant" 대신 도구 호출 요청서가 돌아올 수 있습니다. 판단만 시킬 모델에는 도구를 붙이지 마세요.

💡 디버깅 요령

먼저 agent를 실행해 그래프 그림을 확인하세요. 그림이 기획서와 다르면 엣지 문제, 그림은 맞는데 실행이 깨지면 노드 함수의 반환 딕셔너리를 의심하면 됩니다. 노드마다 print를 심어두면 어디까지 갔는지 바로 보입니다.

📚 한 장 정리

오늘의 핵심 한 문장

에이전트 개발은 코드가 아니라 기획에서 시작한다 — 요구사항을 노드로 쪼개고 → 그래프로 잇고 → 그제서야 State를 설계하면, 코드는 그 기획서를 기계적으로 번역하는 일이 된다.

  • 기획 3단계 — ①요구사항 분석(기능 하나 = 노드 하나) → ②그래프 구성(실선/점선 구분) → ③State 설계(다음 노드가 쓸 것만). 코딩 순서와 정반대인 이유는, 일이 정해져야 데이터가 정해지기 때문.
  • 이름 통일의 힘 — next_step 값 = 노드 이름 = add_node 이름표. 맞춰 두면 라우팅 함수가 값을 그대로 return하는 한 줄이 된다.
  • 실전 1 (키워드) — State는 칸 나눈 서류함(리듀서 없음), 분기는 if '환불' in email. "환급"에서 무너진다 — 단어를 볼 뿐 의미를 못 보기 때문.
  • 실전 2 (LLM + Tool) — 분류를 프롬프트가, 검색을 @tool이 맡는다.
    • State가 messages + add_messages로 돌아온 이유는 루프가 생겼기 때문 — 대화록이 필요하다.
    • model(분류)과 model_with_tools(상담)를 구분해서 쓴다.
    • consultant_node는 요청서만 쓰고, 실제 실행은 tool_node가 한다. 이 분리가 LangGraph의 핵심.
    • add_edge('tool_node', 'consultant_node') 한 줄이 루프를 만들고, 그 덕분에 검색 결과가 답변에 반영된다.
  • 조건부 엣지의 세 번째 인자 — 반환값이 노드 이름이면 리스트(출입 명단), 별칭이면 딕셔너리(좌석 배치표).
  • State 설계 원칙 — ① 꼭 필요한 것만(다음/다다음 노드가 쓰는가?) · ② 날 것(Raw)으로(사람용 문장이 아니라 코드가 처리하기 좋은 dict/list/number).
지금 다 이해되지 않아도 괜찮습니다

실전 2는 실전 1을 버리고 다시 만든 게 아니라 골격은 그대로 두고 부품만 갈아끼운 것입니다 — 골격을 잘못 세우면 전부 다시 지어야 하기에 흐름을 먼저 세우는 겁니다. 막히면 노트북을 처음부터 끝까지 한 번 돌려본 뒤 이 문서를 다시 읽어보세요.

다음 장 예고 — 아키텍처 패턴입니다. 오늘까지가 미리 그려둔 도면대로 흐르는 에이전트였다면, 3강에서는 체이닝·병렬화·라우팅부터 도면을 실행 중에 그리는 오케스트레이션까지, 그래프의 "모양"들을 하나씩 익힙니다.
