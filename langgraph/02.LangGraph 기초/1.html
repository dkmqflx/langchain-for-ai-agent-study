이 자료는 실습 노트북(1.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. LangChain에서 create_agent() 한 줄로 만들었던 에이전트를, 이번에는 LangGraph로 바닥부터 직접 조립해 봅니다. 그 과정에서 앞으로 이 강의가 끝날 때까지 계속 마주칠 네 가지 개념 — State · Node · Edge · Conditional Edge — 을 비유와 예시로 천천히 풀어봅니다.

이 장에서 배우는 것

지난 시간 LangChain에서는 create_agent(model, tools) 한 줄이면 에이전트가 만들어졌습니다. 편했지만, 그 안에서 무슨 일이 일어나는지는 볼 수 없었습니다. 이번 장은 그 상자를 열어 똑같이 동작하는 에이전트를 부품 단위로 직접 조립합니다. 완성품은 같지만, 조립할 줄 알게 되면 원하는 대로 개조할 수 있게 됩니다.

1-1. LangGraph 시작하기 — LangGraph란 무엇인가

LangGraph는 에이전트를 구축하고, 관리하고, 배포할 때 사용하는 프레임워크입니다. LangChain과 가장 크게 다른 점은 딱 하나로 요약됩니다 — 저수준(low-level) 오케스트레이션이 가능하다는 것. 즉 "에이전트가 언제 어디로 움직일지"를 개발자가 직접 설계할 수 있습니다.

🔍 비유 — 완성차 vs 레고 부품

LangChain의 create_agent()는 완성차를 사는 것입니다. 키를 꽂으면 바로 굴러가죠. 빠르고 편합니다. 하지만 "여기서 좌회전 전에 확인 한 번 더 하게 해줘", "이 조건일 땐 사람한테 물어보고 가" 같은 요구가 생기면 보닛을 열 수 없어 막힙니다.

LangGraph는 레고 부품과 설계도입니다. 바퀴, 엔진, 핸들을 내가 직접 끼웁니다. 처음엔 손이 더 가지만, 어디를 뜯어고쳐야 할지 정확히 알게 됩니다. 실무에서 에이전트가 복잡해질수록 이 차이가 결정적입니다.

패키지 설치 — 3개면 됩니다

본격적으로 시작하기 전에 준비물부터 챙깁니다. 설치할 패키지는 세 개이고, 각각 역할이 명확히 다릅니다.

1번은 당연한데, 2번 LangChain은 왜 필요할까요? 에이전트의 심장은 결국 추론을 담당하는 언어 모델입니다. 그런데 OpenAI·Google·Anthropic의 API를 직접 감싸는 객체를 우리가 처음부터 만들 이유는 없습니다. LangChain이 이미 다 만들어 뒀거든요. 그래서 LangGraph 개발팀도 공식 문서에서 LangChain을 함께 설치할 것을 권장합니다.

💡 정리

LangGraph = 흐름(뼈대)을 만드는 도구, LangChain = 부품(모델·도구·메시지)을 제공하는 창고. 물론 언어 모델 객체까지 직접 밑바닥부터 구현하겠다면 LangChain은 없어도 됩니다. 하지만 이 강의에서는 있는 부품은 가져다 쓰고, 흐름 설계에 집중합니다.

1-2. Agent 구축 기초 — 4가지 핵심 개념

우리가 만들 에이전트는 지난 LangChain 강의에서 만든 것과 완전히 똑같은 구조입니다. 사용자 요청이 들어오면 → 언어 모델이 판단해서 → 바로 답하거나, 도구를 부르거나 → 도구 결과를 다시 보고 최종 답을 만드는 구조죠. 결과물은 같고, 만드는 방식만 다릅니다.

이 그림을 코드로 옮기려면 딱 네 가지 단어를 알아야 합니다.

개념정의위 그림에서
State
(공책)		 데이터를 작성할 공책. 노드들이 돌려 보며 읽고 적는 공용 기록장 그림에는 안 보이지만 화살표를 타고 함께 흐르는 것이 바로 State
Node
(작업자)		 데이터를 작성하는 작업자. State를 받아 일하고 결과를 적어 반환 네모 상자 — llm_call, tool_node
Edge
(선)		 Node와 Node를 연결하는 선. 무조건 이쪽으로 간다 실선 화살표 — __start__ → llm_call
Conditional Edge
(갈림길)		 라우팅 기능이 있는 선. 상황을 보고 갈 곳을 고른다 점선 화살표 — llm_call에서 __end__냐 tool_node냐
🔍 비유 — 공책 한 권을 돌려 쓰는 사무실

작은 사무실을 상상해 봅시다. 책상마다 직원(Node)이 앉아 있고, 공책 한 권(State)이 책상 사이를 돌아다닙니다. 규칙은 단순합니다.

  • 직원은 공책을 받으면 앞 사람이 뭘 써놨는지 읽고, 자기 일을 한 뒤 그 밑에 이어 씁니다.
  • 공책을 다음 누구에게 넘길지는 바닥에 그려진 화살표(Edge)를 따릅니다.
  • 어떤 화살표는 갈림길이라 표지판(Conditional Edge)을 보고 판단합니다.

중요한 건 직원들은 서로 직접 대화하지 않는다는 점입니다. 오직 공책을 통해서만 소통합니다. LangGraph의 노드가 정확히 이렇게 동작합니다.

공책 한 권이 도는 이야기 — 한 바퀴 따라가 보기

개념만으로는 잘 안 와닿으니, "3과 4를 더해줘"라는 요청이 들어왔을 때 공책이 어떻게 돌고 어떻게 채워지는지 한 바퀴 따라가 봅시다.

__start__

빈 공책을 펼치고 사용자 입력을 적습니다. 공책의 messages 칸에 HumanMessage("3과 4를 더해줘")가 첫 줄로 들어갑니다.

llm_call ①

공책을 읽고 언어 모델이 판단합니다. "이건 내가 암산할 게 아니라 계산기(도구)를 불러야겠다." 그래서 답변 내용은 비워두고, 대신 "add 도구를 a=3, b=4로 호출해줘"라는 요청서를 공책에 적습니다. 그리고 llm_calls 칸을 1 올립니다.

(갈림길)

표지판이 공책의 마지막 줄을 봅니다. "도구 호출 요청서가 적혀 있네? → tool_node로 가라."

tool_node

공책의 마지막 줄에서 요청서를 꺼내 진짜 add(3, 4) 함수를 실행합니다. 결과 7을 ToolMessage로 포장해 공책에 이어 적습니다.

llm_call ②

공책을 다시 읽습니다. 질문("3과 4를 더해줘")과 도구 결과("7")가 모두 보입니다. "이제 답할 수 있겠다." → "3과 4를 더하면 7입니다"를 공책에 적습니다. llm_calls는 2가 됩니다.

(갈림길)

표지판이 마지막 줄을 봅니다. "도구 요청서가 없네? 그냥 답변이네 → __end__로 가라."

__end__

공책을 통째로 반환합니다. 우리는 그 마지막 줄만 꺼내 화면에 출력하면 됩니다.

💡 여기서 딱 하나만 기억한다면

모든 노드는 State를 입력으로 받아, State에 적을 내용을 반환한다. 축구로 치면 선수(노드)들이 공(State)을 패스하며 전진하는 것과 같습니다. 그리고 패스가 성립하려면 공의 규격(데이터 구조)이 정해져 있어야 하죠. 그게 State 클래스입니다.

에이전트 구축 5단계

LangGraph로 에이전트를 만드는 순서는 항상 이 다섯 단계입니다. 앞으로 만들 모든 에이전트가 이 순서를 반복하므로, 지금 통째로 외워두면 편합니다.

1Model & Tool

추론할 언어 모델과 사용할 도구를 정의하고 서로 연결

2State

노드들이 돌려 쓸 공책 양식을 클래스로 정의

3Node

실제로 일할 작업자를 함수로 작성

4Graph

노드를 등록하고 선(Edge)으로 연결한 뒤 컴파일

5Run

invoke()로 실행하고 결과 확인

STEP 1. Model 및 Tool 정의

① 언어 모델 객체 만들기

앞서 말했듯 언어 모델은 직접 만들지 않고 LangChain의 통합 패키지를 가져다 씁니다. Gemini를 쓸 것이므로 langchain_google_genai에서 ChatGoogleGenerativeAI를 가져옵니다.

📥 코드
# 모델 객체 생성
# https://docs.langchain.com/oss/python/integrations/providers/google

from langchain_google_genai import ChatGoogleGenerativeAI

model = ChatGoogleGenerativeAI(
    model="gemini-3.1-flash-preview",
)
💡 왜 Flash 모델인가

Pro 계열은 더 똑똑하지만 느리고 비쌉니다. 사칙연산 도구를 부르는 정도의 판단이라면 Flash로 충분하고, 실습 중 수십 번 호출해도 부담이 적습니다. temperature 같은 하이퍼파라미터는 지금은 기본값으로 두겠습니다.

OpenAI를 쓰고 싶다면 init_chat_model("gpt-5-nano") 처럼 바꾸기만 하면 됩니다. 뒤에 나오는 그래프 코드는 한 글자도 바뀌지 않습니다. 실제로 갈아끼우는 과정은 맨 아래 보너스 — OpenAI로 갈아끼우기에서 직접 해봅니다.

② 도구(Tool) 정의하기

도구는 LangChain에서 배운 그대로입니다. 평범한 파이썬 함수에 @tool 데코레이터만 붙이면 LangChain·LangGraph가 인식하는 도구가 됩니다.

📥 코드
from langchain.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """Multiply `a` and `b`.

    Args:
        a: First int
        b: Second int
    """
    return a * b


@tool
def add(a: int, b: int) -> int:
    """Adds `a` and `b`.

    Args:
        a: First int
        b: Second int
    """
    return a + b


@tool
def divide(a: int, b: int) -> float:
    """Divide `a` and `b`.

    Args:
        a: First int
        b: Second int
    """
    return a / b
🔍 비유 — 도구는 "설명서가 붙은 공구"

공구함에 드라이버를 넣어두기만 하면 남이 알 수 없습니다. "십자 드라이버 / 나사 조일 때 사용"이라는 라벨이 붙어야 쓸 사람이 고를 수 있죠.

  • 타입 힌트(a: int, -> int) = 공구의 규격. "여기엔 정수를 넣어야 해"
  • docstring("""Adds a and b.""") = 공구의 라벨. LLM은 이 문장을 읽고 도구를 고릅니다.

즉 docstring은 주석이 아니라 LLM에게 보내는 사용설명서입니다. 대충 쓰면 도구를 엉뚱하게 고릅니다.

📥 코드
# tools 정의 — 에이전트가 쓸 수 있는 도구 목록
tools = [multiply, add, divide]

③ 모델과 도구 연결하기 — 여기가 LangChain과 갈리는 지점

지난 LangChain 강의에서는 여기서 create_agent()를 불렀습니다. 모델과 도구를 넣으면 에이전트가 통째로 완성됐죠.

📥 (참고) LangChain 방식 — 지금은 쓰지 않습니다
from langchain.agents import create_agent

agent = create_agent(model, tools=[get_weather])   # 끝. 대신 이 안이 안 보인다.

LangGraph에서는 create_agent()를 쓰지 않습니다. 대신 모델에 도구를 "바인딩"만 해두고, 실제 실행 흐름은 우리가 직접 짭니다.

📥 코드
# model - tool 바인딩
model_with_tools = model.bind_tools(tools)
🔍 비유 — create_agent는 "직원 채용", bind_tools는 "명함 건네기"

create_agent()는 일 다 하는 직원을 한 명 뽑는 것입니다. 알아서 판단하고 도구도 쓰고 답도 만듭니다. 대신 그 사람이 어떤 순서로 일하는지 우리는 관여할 수 없습니다.

bind_tools()는 "우리 회사엔 이런 부서들이 있어"라고 명함을 건네주는 것에 가깝습니다. 모델은 이제 어떤 도구가 있는지 알게 될 뿐, 도구를 직접 실행하지는 않습니다. "add 부서에 3, 4를 넘겨주세요"라고 요청서만 작성하고, 실제 전화는 우리가(tool_node가) 겁니다.

⚠️ 자주 하는 오해

model_with_tools.invoke(...)를 부르면 도구가 자동으로 실행될 것 같지만 아닙니다. 모델은 "이 도구를 이런 인자로 불러줘"라는 요청(tool_calls)만 돌려줍니다. 그 요청을 읽고 실제 함수를 돌리는 일은 STEP 3에서 우리가 만들 tool_node의 몫입니다. 이 분리가 LangGraph의 핵심이며, 덕분에 "도구 실행 전에 사람에게 확인받기" 같은 개입이 가능해집니다.

STEP 2. State 정의 — 공책 양식 만들기

이제 노드들이 돌려 쓸 공책의 양식을 정합니다. 이번 에이전트가 기록해야 할 것은 두 가지입니다.

  • messages — 사용자 입력, 모델의 답변, 도구 실행 결과가 차곡차곡 쌓이는 대화 기록
  • llm_calls — 언어 모델이 몇 번 호출됐는지 세는 카운터
📥 코드
# State 정의
# https://docs.langchain.com/oss/python/langgraph/quickstart#2-define-state

from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class State(TypedDict):
    # 대화 기록은 리스트 형태로 '누적'되도록 add_messages 리듀서 적용
    messages: Annotated[list[AnyMessage], add_messages]
    # 모델 호출 횟수 기록용
    llm_calls: int

세 줄짜리 코드에 담긴 세 가지 개념

① TypedDict — 칸이 정해진 딕셔너리

State는 결국 딕셔너리입니다. 다만 아무 키나 넣을 수 있는 딕셔너리가 아니라, "이 공책에는 messages 칸과 llm_calls 칸이 있다"고 미리 못 박아 둔 것이죠. 지난 강의에서 구조화된 답변을 만들 때 Pydantic 클래스로 스키마를 정의했던 것과 같은 발상입니다.

② AnyMessage — 어떤 메시지든 들어올 수 있다

messages 리스트에는 여러 종류의 메시지가 섞여 들어옵니다 — SystemMessage(시스템 지시), HumanMessage(사용자 입력), AIMessage(모델 응답), ToolMessage(도구 결과). AnyMessage는 "이 넷 중 뭐가 와도 괜찮다"고 표시해 주는 타입입니다.

③ add_messages — 덮어쓰지 말고 이어 쓰라는 규칙

이게 가장 중요하고, 가장 처음 헷갈리는 부분입니다. LangGraph에서 노드가 State를 반환하면 기본 동작은 "덮어쓰기"입니다. 그런데 대화 기록을 덮어쓰면 어떻게 될까요? 도구 결과가 들어오는 순간 사용자 질문이 통째로 사라집니다.

그래서 Annotated의 두 번째 자리에 add_messages라는 함수를 끼워 넣습니다. 이런 함수를 리듀서(reducer)라고 부르며, 뜻은 단순합니다 — "이 칸에 새 값이 들어오면 덮어쓰지 말고, 기존 리스트 뒤에 append 해라."

🔍 비유 — 화이트보드 vs 일기장

일반 필드(llm_calls)는 화이트보드입니다. 새 값을 쓰면 앞의 값은 지워집니다. 호출 횟수는 최신 값만 알면 되니 이게 맞죠.

messages는 일기장이어야 합니다. 오늘 일기를 쓴다고 어제 일기를 지우면 안 되니까요. add_messages가 바로 "지우지 말고 다음 장에 이어 쓰기" 규칙입니다. 이 한 줄 덕분에 앞으로 모든 노드는 새로 생긴 메시지만 반환하면 되고, 누적은 LangGraph가 알아서 해줍니다.

💡 공식 문서와 살짝 다른 점

LangGraph 공식 문서에는 Annotated[list[AnyMessage], operator.add] 처럼 파이썬 내장 operator.add를 쓰는 예시도 나옵니다. 동작은 비슷하지만, langgraph.graph.message의 add_messages가 메시지 병합 규칙(ID가 같으면 교체 등)까지 알아서 처리해 주기 때문에 더 안전하고 코드도 깔끔합니다.

STEP 3. Node 정의 — 작업자 함수 만들기

이제 실제로 일할 작업자를 만듭니다. 앞의 그림에서 __start__와 __end__는 LangGraph가 이미 만들어 둔 것이므로, 우리가 만들 노드는 딱 두 개입니다 — llm_call과 tool_node.

💡 노드의 계약(contract) — 딱 두 줄
  1. 노드는 반드시 state를 입력 파라미터로 받는다. (공책을 건네받아야 하니까)
  2. 노드는 State 양식에 맞는 딕셔너리를 반환한다. (공책에 적을 내용만 적어서 돌려주니까)

① llm_call 노드 — 판단하는 작업자

📥 코드
# llm_call 노드

from langchain.messages import SystemMessage

def llm_call(state: State):
    """LLM이 현재 상태를 보고 답변하거나, 도구 사용을 요청하는 작업자"""

    # 시스템 메시지를 맨 앞에 추가하고 기존 대화 기록을 뒤에 붙여서 LLM에게 전송
    response = model_with_tools.invoke(
        [
            SystemMessage(
                content="당신은 사칙연산을 완벽하게 해내는 유능한 Agent입니다."
            )
        ] + state["messages"]
    )

    # 작업이 끝나면, 새로 생성된 메시지 1개와 카운터 1 증가분을 공책에 업데이트
    return {
        "messages": [response],
        "llm_calls": state.get('llm_calls', 0) + 1  # 초기값이 없으면 0으로 시작
    }

한 줄씩 뜯어봅시다.

[SystemMessage(...)] + state["messages"] — 지시문을 맨 앞에 끼우기

state["messages"]에는 지금까지의 대화가 전부 들어 있습니다. 그 앞에 시스템 메시지를 하나 붙여서 모델에 전달합니다. 결과적으로 모델이 받는 리스트는 이런 모양이 됩니다.

▶ 모델이 실제로 받는 것
[
  SystemMessage("당신은 사칙연산을 완벽하게 해내는 유능한 Agent입니다."),
  HumanMessage("3과 4를 더해줘"),
  ... (턴이 쌓이면 AIMessage, ToolMessage 가 계속 뒤에 붙음)
]
🔍 비유 — 매번 붙였다 떼는 포스트잇

시스템 메시지는 공책에 영구히 적어두는 게 아니라, 모델에게 넘기기 직전 맨 앞에 포스트잇으로 붙였다 떼는 것에 가깝습니다. "너는 사칙연산 전문가야"라는 역할을 매 호출마다 상기시켜 주는 셈이죠.

state.get('llm_calls', 0) + 1 — 왜 state["llm_calls"] + 1이 아닐까?

우리가 agent.invoke({"messages": messages})로 실행할 때 llm_calls는 넘기지 않습니다. 그러면 첫 호출 시점에 그 칸은 비어 있죠. 이때 state["llm_calls"]로 접근하면 KeyError가 납니다.

.get('llm_calls', 0)은 "있으면 그 값을 쓰고, 없으면 0으로 치자"는 딕셔너리 메서드입니다. 덕분에 첫 호출은 0 + 1 = 1, 두 번째 호출은 1 + 1 = 2로 자연스럽게 올라갑니다.

반환값 — 새로 생긴 것만 적는다

{"messages": [response], "llm_calls": ...}를 보면 기존 대화 기록은 하나도 안 넣었습니다. 왜냐하면 STEP 2에서 add_messages를 걸어뒀기 때문입니다. 새로 생긴 메시지 하나만 리스트에 담아 반환하면, 누적은 LangGraph가 알아서 합니다. 반면 llm_calls는 리듀서가 없으니 계산한 최종값을 통째로 반환해야 합니다.

이 노드가 만들어내는 두 가지 결과

상황response(AIMessage)의 모습
바로 답할 수 있을 때 content에 답변 텍스트가 채워지고, tool_calls는 빈 리스트
도구가 필요할 때 content는 비어 있고, tool_calls에 {"name": "add", "args": {"a": 3, "b": 4}, "id": "call_xxx"} 같은 요청서가 담김

이 두 가지 중 어느 쪽이냐가 바로 다음 갈림길의 판단 기준이 됩니다. 기억해 두세요.

② tool_node 노드 — 실제로 실행하는 작업자

llm_call이 "add를 3, 4로 불러줘"라고 요청서만 써준 상태입니다. 이제 그 요청서를 읽고 진짜 파이썬 함수를 실행할 작업자가 필요합니다.

준비물 — 이름 → 함수 전화번호부

모델이 준 요청서에는 도구 이름이 문자열로 적혀 있습니다("add"). 그런데 우리가 가진 tools는 함수 객체의 리스트죠. 매번 리스트를 뒤져 이름을 비교하는 대신, 이름으로 바로 찾을 수 있는 딕셔너리를 미리 만들어 둡니다.

📥 코드
# 도구 이름을 키로, 실제 함수를 값으로 가지는 딕셔너리 준비
tools_by_name = {tool.name: tool for tool in tools}
▶ 이렇게 생겼습니다
{
  'multiply': StructuredTool(name='multiply', ...),
  'add':      StructuredTool(name='add', ...),
  'divide':   StructuredTool(name='divide', ...)
}
🔍 비유 — 전화번호부

회사에 부서가 100개 있는데 매번 전 부서에 전화를 돌려 "혹시 add 부서세요?"라고 물을 순 없죠. tools_by_name은 "부서 이름 → 내선번호" 전화번호부입니다. 모델이 "add"라고 적어주면 한 번에 그 함수로 연결됩니다.

tool_node 본체

📥 코드
from langchain.messages import ToolMessage

def tool_node(state: State):
    """LLM이 도구 사용을 요청했을 때, 실제로 함수를 실행하는 작업자"""

    result = []
    # 공책의 맨 마지막 메시지(LLM의 요청장)에서 tool_calls 리스트 꺼내기
    last_message = state["messages"][-1]

    for tool_call in last_message.tool_calls:
        # 1. 도구 이름으로 실제 파이썬 함수 찾기
        tool = tools_by_name[tool_call["name"]]

        # 2. 인자(args)를 넣고 함수 실행
        tool_result = tool.invoke(tool_call["args"])

        # 3. 실행 결과를 ToolMessage로 포장 (tool_call_id를 반드시 맞춰주어야 모델이 인식함)
        result.append(ToolMessage(content=tool_result, tool_call_id=tool_call["id"]))

    # 도구 실행 결과들을 공책에 업데이트
    return {"messages": result}

코드가 리스트 → 딕셔너리 → 리스트를 오가서 어지럽게 느껴질 수 있습니다. 데이터가 어떻게 생겼는지 먼저 그림으로 잡아둡시다.

▶ 이 시점의 state 모습
state = {
  "messages": [
      SystemMessage(content="당신은 사칙연산을 ..."),
      HumanMessage(content="3과 4를 더해줘"),
      AIMessage(                          ← [-1] 마지막 메시지가 바로 이것
          content='',                     ← 비어 있음 (아직 답 못 만듦)
          tool_calls=[                    ← 요청서가 "리스트" 안에 "딕셔너리"로
              {"name": "add", "args": {"a": 3, "b": 4}, "id": "call_abc123"}
          ]
      )
  ],
  "llm_calls": 1
}

이 구조를 알고 코드를 다시 보면 흐름이 그대로 읽힙니다.

  1. state["messages"][-1] → 마지막 메시지(모델의 요청서)를 꺼낸다.
  2. last_message.tool_calls → 요청서 리스트를 for문으로 하나씩 돈다.
  3. tool_call["name"](= "add")으로 전화번호부를 조회해 진짜 함수를 얻는다.
  4. tool_call["args"](= {"a": 3, "b": 4})를 넣어 실행한다 → 결과 7.
  5. 결과를 ToolMessage로 포장해 result 리스트에 담는다.
  6. 모두 끝나면 {"messages": result}로 반환 → add_messages가 알아서 공책에 이어 붙인다.
⚠️ 왜 for문으로 도는가

tool_calls가 리스트인 이유는 한 번에 여러 도구를 호출할 수 있기 때문입니다. "서울이랑 도쿄 날씨 알려줘"라고 하면 모델은 weather 도구를 두 번 요청합니다. 그래서 요청서가 하나뿐일 때도 항상 리스트를 순회하도록 짜야 합니다.

🔑 tool_call_id는 도대체 왜 필요할까

ToolMessage(content=tool_result, tool_call_id=tool_call["id"]) — 결과만 담으면 될 것 같은데 tool_call_id를 굳이 왜 같이 넘길까요? 빼면 에러도 납니다. 이유를 예시로 보면 단번에 이해됩니다.

사용자가 이렇게 물었다고 해봅시다 — "서울이랑 도쿄 날씨 알려줘"

▶ 모델이 만든 요청서 (AIMessage.tool_calls)
tool_calls = [
    {"name": "weather", "args": {"city": "Seoul"}, "id": "call_12345"},  # 서울 요청 (ID: 12345)
    {"name": "weather", "args": {"city": "Tokyo"}, "id": "call_67890"}   # 도쿄 요청 (ID: 67890)
]

도구를 두 번 실행하면 결과도 두 개가 나옵니다. 그런데 ID 없이 결과만 돌려준다면?

▶ ID가 없다면 — 모델의 입장
ToolMessage(content="맑음")
ToolMessage(content="비")

→ 모델: "...어느 쪽이 서울이고 어느 쪽이 도쿄지?" 🤔

ID를 붙이면 문제가 사라집니다.

▶ ID가 있다면
ToolMessage(content="맑음", tool_call_id="call_12345")   → 아, 서울이 맑음
ToolMessage(content="비",   tool_call_id="call_67890")   → 도쿄는 비
🔍 비유 — 택배 송장 번호

같은 날 택배 두 개를 주문했는데 송장 번호가 없다면, 배송 완료 문자 두 개가 와도 어느 게 어느 물건인지 알 수 없습니다. tool_call_id는 송장 번호입니다. 모델이 요청할 때 스스로 발급한 고유번호이고, 우리는 결과를 돌려줄 때 그 번호를 그대로 붙여서 돌려주는 것뿐입니다. 그래야 모델이 자기 요청과 대조할 수 있습니다.

🚫 빼먹으면 에러

tool_call_id는 선택이 아니라 필수입니다. "요청한 tool_call에 대응하는 응답이 없다"며 에러가 납니다. tool_call["id"]를 그대로 복사해 넣는다고 외워두세요.

STEP 4. 그래프 생성 — 작업자들을 배치하고 선 긋기

부품은 다 만들었습니다. 이제 도면 위에 작업자를 배치하고, 화살표를 긋는 단계입니다. 순서는 ① 그래프 초기화 → ② 노드 등록 → ③ 실선 연결 → ④ 점선(조건부) 연결 → ⑤ 컴파일 입니다.

① 그래프 초기화 + ② 노드 등록 + ③ 실선 엣지

📥 코드
# 그래프 생성

from langgraph.graph import StateGraph, START

# 1. 빈 작업장(그래프) 도면 펼치기 (공책 양식을 알려줌)
agent_builder = StateGraph(State)

# 2. add_node: 도면에 작업자(노드) 배치하기
agent_builder.add_node("llm_call", llm_call)
agent_builder.add_node("tool_node", tool_node)

# 3. add_edge: 고정된 연결선(Edge) 긋기
# 시작(START)하자마자 무조건 llm_call 작업자에게 최초로 공책을 넘깁니다.
agent_builder.add_edge(START, "llm_call")
# 도구 실행이 끝나면 결과값을 얻었으니 무조건 다시 llm_call 작업자에게 공책을 넘겨 최종 답변 생성
agent_builder.add_edge("tool_node", "llm_call")
코드의미
StateGraph(State) "이 작업장에서 돌려 쓸 공책 양식은 State다"라고 알려주며 빈 도면을 편다
add_node("이름", 함수) 1번째 인자 = 도면에 적을 이름표, 2번째 인자 = 실제 함수. 이름은 마음대로 정해도 되며("tools"로 해도 됨), 이후 모든 연결에서 이 이름을 씁니다
add_edge(출발, 도착) 1번째 = 출발 노드, 2번째 = 도착 노드. 조건 없이 무조건 흐르는 실선
💡 START는 왜 따로 있나

START와 END는 LangGraph가 미리 만들어 둔 특수 노드입니다. add_edge(START, "llm_call")은 "입력이 들어오면 제일 먼저 llm_call에게 넘겨라"는 뜻이고, add_edge("tool_node", "llm_call")은 "도구가 일을 끝냈으면 무조건 모델에게 돌려줘라"는 뜻입니다. 후자가 있어야 도구 → 모델 → 도구 → 모델… 하는 루프가 생깁니다.

④ 조건부 엣지 — 점선 긋기

이제 남은 건 llm_call에서 나가는 점선입니다. 상황에 따라 __end__로 끝낼 수도, tool_node로 갈 수도 있죠. 이걸 만들려면 먼저 "판단하는 함수"부터 작성해야 합니다.

📥 코드 — (1) 라우팅 함수
# 조건부 함수 작성

from langgraph.graph import END

def should_continue(state: State):
    """
    LLM의 응답을 보고 다음 단계로 어디를 갈지 결정하는 라우팅 함수
    """
    last_message = state["messages"][-1]

    # LLM이 도구 호출(tool_calls) 요청장을 작성했다면? -> 도구 작업자(tool_node)에게 가라고 문자열 반환
    if last_message.tool_calls:
        return "tool_node"

    # 도구 호출이 없고 최종 답변을 작성했다면? -> 작업 종료(END) 반환
    return END

로직은 놀랄 만큼 단순합니다. 공책의 마지막 줄을 열어보고, 도구 요청서가 있으면 도구로, 없으면 끝으로. 이 함수도 노드와 마찬가지로 state를 입력으로 받는다는 점에 주목하세요. 공책을 봐야 판단할 수 있으니 당연합니다.

📥 코드 — (2) 그래프에 등록
# 조건부 엣지 연결

# 4. add_conditional_edges: 라우팅 기능을 하는 선 설치
agent_builder.add_conditional_edges(
    "llm_call",         # 1) 출발지: llm_call 작업이 끝나면 무조건 이 라우터 함수가 발동합니다.
    should_continue,    # 2) 라우팅 함수: 위에서 만든 함수가 공책을 보고 어디로 갈지 판단합니다.
    ["tool_node", END]  # 3) 도착지 목록: 갈 수 있는 목적지들을 리스트나 딕셔너리로 명시합니다.
)
🔍 비유 — 갈림길의 표지판

add_conditional_edges의 세 인자를 표지판으로 옮기면 이렇습니다.

  • ① 출발지 — 표지판을 어느 갈림길에 세울지 ("llm_call" 다음 지점)
  • ② 판단 함수 — 표지판을 읽고 어디로 갈지 정하는 규칙 (should_continue)
  • ③ 도착지 목록 — 이 갈림길에서 갈 수 있는 길의 전체 목록 (["tool_node", END])

③이 필요한 이유는 LangGraph가 "이 길이 실제로 존재하는지" 미리 검증하기 위해서입니다. ②가 반환할 수 있는 값이 전부 ③ 안에 들어 있어야 합니다. 하나라도 빠지면 컴파일 단계에서 에러가 납니다.

🚫 실제 강의에서 에러가 났던 지점 — 문자열 vs 함수

이 부분은 강의 중에도 한 번 에러가 났던 곳입니다. 두 가지를 조심하세요.

  1. 모든 분기에 return이 있어야 합니다. if만 쓰고 return END를 빠뜨리면 함수가 None을 반환해 라우팅이 실패합니다.
  2. 노드 함수가 아니라 노드 이름 문자열을 반환해야 합니다. return tool_node (❌ 함수 객체) 가 아니라 return "tool_node" (✅ add_node에 등록한 이름) 입니다. LangGraph는 이름표를 보고 작업자를 찾기 때문입니다.

⑤ 컴파일 — 도면을 실제 에이전트로

📥 코드
# 컴파일 (최종 에이전트 생성)
agent = agent_builder.compile()

agent   # 주피터/Colab에서 실행하면 그래프 그림이 그려집니다
💡 여기서 말하는 "컴파일"의 뜻

일반 프로그래밍에서 컴파일은 사람이 쓴 코드를 컴퓨터가 이해할 수 있는 형태로 바꾸는 것이죠. LangGraph의 compile()은 두 가지 일을 합니다.

  • 지금까지 등록한 노드·엣지·조건부 엣지를 실행 가능한 에이전트 객체로 조립
  • 그래프가 끊긴 곳은 없는지 검증 — 갈 수 없는 노드, 목록에 없는 도착지 등을 잡아냄

컴파일에서 에러가 나지 않았다면, 설계한 대로 모든 노드가 제대로 연결됐다는 뜻입니다. Colab에서 agent를 그냥 실행하면 앞에서 본 그 그래프 그림이 그려집니다. 머릿속으로 그린 도면과 같은지 눈으로 확인하는 습관을 들이면 디버깅이 훨씬 쉬워집니다.

STEP 5. 실행 — 공책을 던져 넣기

📥 코드
# 사용자 입력은 HumanMessage로 감싸 리스트에 담습니다
from langchain.messages import HumanMessage

messages = [HumanMessage(content="3과 4를 더해줘")]

# State 양식({"messages": [...]})에 맞춰 그래프 실행
# → 모든 노드를 거친 뒤 완성된 State(공책 전체)가 반환됩니다
response = agent.invoke({"messages": messages})

invoke()에 넘기는 것은 State 양식에 맞는 딕셔너리입니다. llm_calls는 넣지 않았죠? 앞서 state.get('llm_calls', 0)으로 방어해 뒀으니 괜찮습니다.

실행되면 안에서 벌어지는 일

1. START

State 딕셔너리를 초기화하고, invoke로 들어온 HumanMessage를 messages 리스트에 넣습니다.

2. llm_call

시스템 메시지 + 대화 기록을 model_with_tools에 invoke. 모델은 add(a=3, b=4) 요청서를 만들어 반환. add_messages가 이를 messages 뒤에 붙이고, llm_calls는 1이 됩니다.

3. should_continue

마지막 메시지에 tool_calls가 있음 → "tool_node" 반환

4. tool_node

요청서를 꺼내 add(3, 4) 실행 → 7. ToolMessage(content=7, tool_call_id=...)로 포장해 반환 → 공책에 append

5. (실선 엣지)

add_edge("tool_node", "llm_call")에 따라 무조건 llm_call로 복귀

6. llm_call

이번엔 도구 결과까지 다 보이므로 최종 답변을 생성. tool_calls는 비어 있고 content만 채워집니다. llm_calls는 2.

7. should_continue

tool_calls가 없음 → END 반환 → 그래프 종료, State 전체를 반환

반환값 확인하기

agent.invoke()가 돌려주는 것은 답변 문자열이 아니라 State 딕셔너리 전체입니다. 즉 공책을 통째로 받는 셈이죠.

▶ response 구조 (요약)
{
  'messages': [
      HumanMessage(content='3과 4를 더해줘'),
      AIMessage(content='', tool_calls=[{'name': 'add', 'args': {'a': 3, 'b': 4}, 'id': 'call_abc'}]),
      ToolMessage(content='7', tool_call_id='call_abc'),
      AIMessage(content=[{'type': 'text', 'text': '3과 4를 더하면 7입니다.'}])
  ],
  'llm_calls': 2
}

대화가 Human → AI(요청) → Tool(결과) → AI(최종답변) 순서로 정확히 쌓여 있고, llm_calls가 2인 것도 확인할 수 있습니다. 우리가 화면에 보여줄 것은 마지막 메시지뿐입니다.

⚠️ Gemini와 OpenAI의 응답 형태가 다릅니다

위 결과에서 이상한 점을 발견하셨나요? 마지막 AIMessage의 content가 문자열이 아니라 리스트이고, 그 안에 딕셔너리가 들어 있습니다.

모델AIMessage.content 형태텍스트 꺼내는 법
OpenAI (GPT) '정답은 7입니다.' 문자열 response["messages"][-1].content
Gemini [{'type': 'text', 'text': '3과 4를 더하면 7입니다.'}] 리스트 response["messages"][-1].content[-1]['text']
🔍 왜 이렇게 다를까 — 편지 봉투 vs 소포 상자

OpenAI는 편지를 보내듯 텍스트를 그대로 담아 보냅니다. 열면 바로 글자죠.

Gemini는 소포 상자처럼 보냅니다. 상자를 열면 "이건 텍스트입니다"라는 라벨이 붙은 내용물이 들어 있어요. 번거로워 보이지만 이유가 있습니다. Gemini는 멀티모달을 표방하는 모델이라 텍스트뿐 아니라 이미지·음성·영상도 같은 자리에 담아 보낼 수 있어야 합니다. 그래서 "타입이 무엇인지"를 항상 함께 알려주도록 설계된 것입니다.

▶ 출력
'3과 4를 더하면 7입니다.'
⚠️ 꼭 기억하세요

어떤 언어 모델을 연결했느냐에 따라 최종 반환값의 형태가 달라질 수 있습니다. 그래프 코드(State·Node·Edge)는 하나도 안 바뀌는데 출력 파싱만 달라지는 것이죠. 모델을 교체했을 때 TypeError: string indices must be integers 같은 에러가 나면 대개 이 차이 때문입니다.

도구가 두 번 불리는 경우

조금 더 복잡한 요청을 넣어보면 루프가 실제로 도는 것을 볼 수 있습니다.

📥 코드
# 계산이 두 단계라 도구가 add → multiply 순서로 "두 번" 호출됩니다
# (llm_call ↔ tool_node 루프가 두 바퀴 도는 셈)
messages = [HumanMessage(content="3과 4를 더한 뒤 7을 곱해줘.")]
response = agent.invoke({"messages": messages})
▶ messages에 쌓이는 순서
HumanMessage : "3과 4를 더한 뒤 7을 곱해줘."
AIMessage    : tool_calls = [add(a=3, b=4)]           ← 1차 도구 요청
ToolMessage  : "7"                                     ← 덧셈 결과
AIMessage    : tool_calls = [multiply(a=7, b=7)]       ← 2차 도구 요청 (앞 결과를 인자로!)
ToolMessage  : "49"                                    ← 곱셈 결과
AIMessage    : "3과 4를 더하면 7이고, 여기에 7을 곱하면 49입니다."   ← 최종 답변

주목할 부분은 4번째 줄입니다. 모델이 1차 도구 결과(7)를 읽고, 그것을 2차 도구의 인자로 넣었습니다. 우리가 "덧셈 먼저, 곱셈 나중"이라고 코딩한 적이 없는데도요. 이게 바로 tool_node → llm_call 실선 엣지가 만들어낸 루프의 힘입니다. llm_calls는 이 경우 3이 됩니다.

보너스 — 똑같은 그래프를 OpenAI로 갈아끼우기

노트북 마지막에는 방금 만든 에이전트를 OpenAI 모델(GPT-5 nano)로 다시 돌려보는 실습이 이어집니다. 여기서 확인할 것은 단 하나입니다 — 바뀌는 건 "모델을 만드는 줄"뿐, State · Node · Edge는 그대로라는 사실입니다.

① 패키지 설치 & 모델만 교체

🔍 비유 — 엔진만 교체하고 차체는 그대로

레고 자동차에서 엔진(모델) 하나만 다른 브랜드로 갈아 끼우는 것과 같습니다. 바퀴·핸들·차체(State · Node · Edge)는 손댈 필요가 없습니다. 노트북에서도 llm_call · tool_node · should_continue · 그래프 조립 코드를 그대로 다시 등록해 컴파일할 뿐입니다.

② 실행 — 코드는 그대로인데 결과의 "형태"가 다르다

나머지 그래프 코드를 동일하게 다시 컴파일한 뒤, Gemini 때와 똑같은 질문을 던집니다.

📥 코드

# (State·Node·Edge 코드는 앞과 동일)

messages = [HumanMessage(content="3과 4를 더해줘")]

▶ OpenAI 응답 (마지막 메시지 요약)
AIMessage(content='정답은 7입니다.', ...)   ← content 가 그냥 "문자열"
▶ 앞서 본 Gemini 응답 (마지막 메시지 요약)
AIMessage(content=[{'type': 'text', 'text': '3과 4를 더하면 7입니다.'}], ...)   ← content 가 "리스트"
⚠️ 그래서 "출력을 꺼내는 코드"는 모델마다 갈립니다

OpenAI는 response["messages"][-1].content로 바로 문자열이 나오지만, Gemini는 response["messages"][-1].content[-1]['text']처럼 리스트에서 한 번 더 꺼내야 합니다. 그래프 로직(State · Node · Edge)은 완전히 재사용되는데 "출력 파싱"만 갈라지는 것 — 이 점만 기억하면 어떤 모델로 바꿔도 TypeError에 당황할 일이 없습니다.

💡 이 보너스의 교훈 한 줄

LangGraph로 흐름을 한 번 잘 설계해 두면, 모델 제공사(Google ↔ OpenAI)는 부품처럼 갈아 끼울 수 있습니다. 이것이 앞에서 create_agent() 대신 굳이 bind_tools + 직접 조립을 택한 이유이기도 합니다.

전체 코드 한눈에 보기

흩어져 있던 조각을 5단계 순서대로 모으면 이렇습니다. 앞으로 만들 모든 에이전트가 이 골격을 반복합니다.

📥 전체 코드
# ══ STEP 1. Model & Tool ══════════════════════════════
from langchain_google_genai import ChatGoogleGenerativeAI
from langchain.tools import tool

# 추론을 담당할 언어 모델(에이전트의 두뇌)
model = ChatGoogleGenerativeAI(model="gemini-3.1-flash-preview")

# @tool 데코레이터 + docstring = LLM이 읽고 고르는 "도구"
@tool
def multiply(a: int, b: int) -> int:
    """Multiply `a` and `b`."""
    return a * b

@tool
def add(a: int, b: int) -> int:
    """Adds `a` and `b`."""
    return a + b

@tool
def divide(a: int, b: int) -> float:
    """Divide `a` and `b`."""
    return a / b

tools = [multiply, add, divide]
model_with_tools = model.bind_tools(tools)   # 모델에 도구 목록을 붙인 새 모델

# ══ STEP 2. State ═════════════════════════════════════
from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

# State = 노드들이 돌려 쓰는 "공책"
class State(TypedDict):
    # add_messages 리듀서 → 덮어쓰지 않고 뒤에 이어붙임
    messages: Annotated[list[AnyMessage], add_messages]
    llm_calls: int   # 모델 호출 횟수 카운터

# ══ STEP 3. Node ══════════════════════════════════════
from langchain.messages import SystemMessage, ToolMessage

# 판단하는 작업자: 답하거나 / 도구 사용을 요청
def llm_call(state: State):
    response = model_with_tools.invoke(
        # 시스템 지시문을 맨 앞에 붙여 매 호출마다 역할을 상기시킴
        [SystemMessage(content="당신은 사칙연산을 완벽하게 해내는 유능한 Agent입니다.")]
        + state["messages"]
    )
    return {
        "messages": [response],                       # 새로 생긴 메시지만 반환(누적은 리듀서가)
        "llm_calls": state.get('llm_calls', 0) + 1    # 없으면 0에서 시작
    }

tools_by_name = {tool.name: tool for tool in tools}   # 이름 → 함수 "전화번호부"

# 실행하는 작업자: 요청서를 읽고 실제 함수를 돌림
def tool_node(state: State):
    result = []
    last_message = state["messages"][-1]              # 모델이 남긴 마지막 요청서
    for tool_call in last_message.tool_calls:         # 도구를 여러 번 부를 수 있어 순회
        tool = tools_by_name[tool_call["name"]]       # 이름으로 실제 함수 찾기
        tool_result = tool.invoke(tool_call["args"])  # 인자를 넣어 실행
        # tool_call_id = 요청과 응답을 잇는 송장번호(필수)
        result.append(ToolMessage(content=tool_result, tool_call_id=tool_call["id"]))
    return {"messages": result}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END

agent_builder = StateGraph(State)                     # 공책 양식(State)을 알려주며 도면 펼치기

agent_builder.add_node("llm_call", llm_call)          # 작업자(노드) 배치
agent_builder.add_node("tool_node", tool_node)

agent_builder.add_edge(START, "llm_call")             # 시작하면 무조건 llm_call로
agent_builder.add_edge("tool_node", "llm_call")       # 도구 실행 후 다시 모델로 → 루프

# 마지막 메시지를 보고 다음 목적지를 고르는 라우팅 함수
def should_continue(state: State):
    last_message = state["messages"][-1]
    if last_message.tool_calls:      # 도구 요청이 있으면
        return "tool_node"           # → 도구 실행하러
    return END                       # 없으면 → 종료

agent_builder.add_conditional_edges(
    "llm_call",          # 출발지
    should_continue,     # 판단 함수
    ["tool_node", END]   # 갈 수 있는 목적지 목록
)

agent = agent_builder.compile()      # 조립 + 연결 검증 → 실행 가능한 에이전트

# ══ STEP 5. Run ═══════════════════════════════════════
from langchain.messages import HumanMessage

response = agent.invoke({"messages": [HumanMessage(content="3과 4를 더해줘")]})
# Gemini는 content가 리스트라 [-1]['text']로 한 번 더 꺼냄 (OpenAI는 .content가 문자열)
print(response["messages"][-1].content[-1]['text'])

자주 걸리는 함정 5가지

🕳️ 처음 짤 때 거의 모두가 밟는 지뢰

1. 라우팅 함수에서 함수 객체를 반환한다

return tool_node ❌ → return "tool_node" ✅
LangGraph는 add_node("이름", 함수)에서 등록한 이름 문자열로 노드를 찾습니다.

2. should_continue에 return을 하나 빠뜨린다

if 안쪽만 return하고 밖에서 안 하면 None이 반환되어 "그런 목적지는 없다"는 에러가 납니다. 모든 분기에 return이 있어야 합니다.

3. add_conditional_edges 세 번째 인자에 목적지를 빠뜨린다

라우팅 함수가 반환할 수 있는 값이 전부 목록에 들어 있어야 합니다. should_continue가 "tool_node"와 END를 반환하니 목록도 ["tool_node", END]여야 하죠. 빠지면 compile 단계에서 걸립니다.

4. ToolMessage에 tool_call_id를 안 넣는다

결과만 담고 ID를 빼면 모델이 어느 요청에 대한 답인지 대조하지 못해 에러가 납니다. tool_call["id"]를 그대로 복사해 넣으세요.

5. State에 없는 키를 state["..."]로 꺼낸다

invoke에 넘기지 않은 필드는 처음엔 비어 있습니다. state["llm_calls"] ❌ → state.get("llm_calls", 0) ✅

💡 디버깅 요령

에러가 나면 먼저 agent를 실행해 그래프 그림을 확인하세요. 선이 예상과 다르게 그려져 있다면 add_edge/add_conditional_edges 문제이고, 그림은 맞는데 실행이 깨진다면 노드 함수 안쪽(반환 딕셔너리 모양)을 의심하면 됩니다.

📚 한 장 정리

오늘의 핵심 한 문장

LangGraph 에이전트란 공책(State)을 작업자(Node)들이 돌려 보며 이어 쓰고, 선(Edge)과 표지판(Conditional Edge)이 정한 순서대로 흐르는 작업장이다.

  • LangGraph vs LangChain — 완성차(create_agent) 대신 레고 부품. 손이 더 가지만 흐름을 내가 설계할 수 있다.
  • State — 공책. TypedDict로 양식을 정의. Annotated[..., add_messages]를 붙이면 덮어쓰기 대신 이어 쓰기(리듀서).
  • Node — 작업자 함수. 계약은 두 줄: state를 받는다 / State 모양의 딕셔너리를 반환한다.
    • llm_call — 판단만 한다. 도구가 필요하면 요청서(tool_calls)만 작성.
    • tool_node — 요청서를 읽고 실제 함수를 실행, 결과를 ToolMessage로 포장. tool_call_id는 택배 송장 번호 — 필수.
  • Edge — add_edge(출발, 도착). 무조건 흐르는 실선. tool_node → llm_call 실선이 루프를 만든다.
  • Conditional Edge — add_conditional_edges(출발, 판단함수, 도착지목록). 판단 함수는 노드 이름 문자열을 반환해야 하고, 반환 가능한 값이 전부 목록에 있어야 한다.
  • compile() — 조립 + 연결 검증. 에러가 없으면 설계대로 연결된 것.
  • 모델별 응답 차이 — OpenAI는 content가 문자열, Gemini는 [{'type':'text','text':...}] 리스트(멀티모달 철학).
🔍 마지막으로 한 번 더 — 5단계 주문처럼 외우기

모델·도구를 붙이고 → 공책 양식을 정하고 → 작업자를 만들고 → 선을 긋고 → 컴파일해서 실행한다.
앞으로 나올 메모리, 멀티 에이전트, Human-in-the-loop… 모두 이 다섯 단계 위에 살을 붙이는 것일 뿐입니다.
