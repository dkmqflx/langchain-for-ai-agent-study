5-3. Command with Goto — 엣지를 그리지 않고 노드로 순간이동하기

실습 노트북: 2.ipynb · # Command with Goto 절  ·  대상 범위: Command(goto=) · Command(update=) · 엣지 없이 흐르는 그래프  ·  난이도: 🟡 중급

5-1에서 Command는 멈춘 그래프를 되살리는 열쇠였습니다 — Command(resume="일식"). 이번 장에서 같은 객체가 두 번째 얼굴을 보여 줍니다. Command(goto="booking"). "다음에 실행할 노드는 여기다"라고 노드가 직접 지목하는 기능이에요. 이게 왜 중요하냐면, 엣지를 하나도 그리지 않고도 그래프가 흐르게 되기 때문입니다. 그리고 그 순간 에이전트끼리 일을 넘기는 것(Handoff)이 문법적으로 가능해집니다. 5강 후반부 전체가 이 한 줄 위에 세워집니다.

이 장에서 배우는 것

딱 하나입니다. Command 객체의 goto와 update 두 속성. 새 개념도, 새 import도 없습니다. 5-1에서 이미 가져다 쓴 그 Command예요.

대신 이 한 줄이 그래프의 모양을 어떻게 바꾸는지를 끝까지 따라갑니다. 오마카세 예약 에이전트를 만들면서 노드 3개짜리 그래프에 엣지를 단 2개만 그리고, 나머지 길은 전부 goto로 잇습니다. 그 결과로 그래프 그림이 이상해지는 현상도 만나는데, 이게 버그가 아니라 당연한 결과라는 걸 4장에서 자세히 뜯어봅니다.

선행 지식: 5-1의 interrupt() · Command(resume=) · checkpointer · thread_id. 전부 그대로 다시 씁니다.

1. 5강 후반부를 열며 — 단일 에이전트에서 여러 에이전트로

지금까지 우리가 만든 건 전부 에이전트 하나, 그래프 하나였습니다. 노드가 몇 개든 결국 한 덩어리였죠. 이제부터는 여러 그래프를 만들어 업무를 나눠 시킵니다.

오른쪽 표를 회사 조직도라고 생각하면 편합니다. Single Agent는 1인 기업이에요. 사장이 직접 도구를 들고 다 합니다. Supervisor는 팀장 한 명에 팀원 여럿 — 팀장이 일을 나눠 주고 받아 옵니다. Hierarchical은 여기에 중간 관리자를 한 층 더 얹은 거고, Network는 직급 없이 서로 직접 넘기는 수평 조직입니다.

왜 goto부터 배우나

조직도가 커지면 연결선도 같이 폭발합니다. 노드가 100개인 그래프를 상상해 보세요. 지금까지 배운 방식대로라면 노드 사이의 모든 길을 add_edge와 add_conditional_edges로 일일이 선언해야 합니다. 코드가 감당이 안 됩니다.

🔍 비유 — 100층 건물에 계단만 놓기

엣지는 미리 깔아 둔 복도이자 계단입니다. 3층에서 7층으로 갈 일이 있으면 3층과 7층을 잇는 계단을 미리 만들어 둬야 하죠. 층이 100개가 되면 계단이 몇 개 필요할까요.

Command(goto=...)는 엘리베이터 버튼입니다. 계단을 놓는 대신 "7층"이라고 누르면 그냥 갑니다. 길을 미리 만들어 두지 않아도, 목적지 이름만 알면 도착하는 거예요.

Command의 두 얼굴 — 5-1과 5-3

5-1: Command(resume="일식") — 바깥에서 그래프 안으로 던지는 값. "멈춰 있는 interrupt()에 이 답을 넣고 다시 걸어라."

5-3: Command(goto="booking") — 노드가 그래프 엔진에게 돌려주는 지시. "내 일은 끝났고, 다음은 booking으로 보내라."

같은 클래스인데 쓰는 쪽과 방향이 반대입니다. 헷갈리면 resume은 사용자가 채우는 칸, goto는 노드가 채우는 칸이라고 기억하세요.

2. 만들 것 — 오마카세 예약 에이전트

고급 식당 예약을 대신 해 주는 에이전트를 만듭니다. 음식값이 비싸니까 확정 전에 반드시 사람의 승인을 받아야 하고, 거절당하면 더 싼 메뉴를 다시 제안해야 합니다.

설계도 읽기 — 노드 3개, 갈림길 1개

1recommender

메뉴를 추천한다. 처음이면 A코스(20만원), 거절당해 돌아왔으면 B코스(8만원)

2approval

interrupt()로 멈추고 사람에게 승인을 묻는다. 답에 따라 갈 곳을 지정한다

3booking

예약을 확정한다. 승인받았을 때만 실행된다

핵심은 2번 노드가 두 가지 일을 겸한다는 점입니다. 사람에게 묻는 일(Interrupt)과 답에 따라 길을 정하는 일(Router)이죠. 3강에서 배운 방식대로라면 라우팅은 add_conditional_edges의 몫이었습니다. 이번에는 그 역할을 노드 안으로 끌고 들어옵니다.

이번 절에는 LLM이 등장하지 않습니다

노트북 맨 위에서 model = init_chat_model("gpt-5-nano")로 모델을 만들긴 하는데, 2-1절 코드 어디에서도 model.invoke()를 부르지 않습니다. 판단은 전부 사람이 yes/no로 합니다.

일부러 그런 겁니다. 이번 장의 주제는 "어떻게 판단하느냐"가 아니라 "판단 결과대로 어떻게 이동하느냐"거든요. LLM은 맨 뒤 실습에서 등장합니다.

3. 구현 — STEP 1. State 정의

from langchain.chat_models import init_chat_model
from langchain.messages import HumanMessage, AnyMessage
from langgraph.types import interrupt, Command
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

model = init_chat_model("gpt-5-nano")

class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    selected_menu: str   # 선택된 메뉴 저장

selected_menu가 이 그래프의 기억 전체입니다. "A 코스 (20만원)" 아니면 "B 코스 (8만원)", 둘 중 하나의 문자열이죠. 리듀서가 없으니 기본 동작 — 덮어쓰기입니다. 노드가 새 값을 반환하면 통째로 갈아 끼워집니다.

이 한 칸이 "몇 번째 제안인지"를 대신한다

보통이라면 attempt: int 같은 카운터를 두고 싶어집니다. 그런데 여기서는 selected_menu 값 자체가 카운터 역할을 해요.

비어 있으면 = 아직 아무것도 제안 안 했다 → A코스. "A 코스"가 들어 있으면 = A코스를 제안했다가 퇴짜 맞았다 → B코스. 상태 하나로 두 가지를 표현하는 거죠. 간결하지만, 메뉴가 세 개 이상이 되는 순간 무너집니다. (C코스를 추가하려면 결국 카운터가 필요해집니다.)

STEP 2. recommender 노드 — 상태를 보고 메뉴를 고른다

# [Node 1] 메뉴 추천
def recommender_node(state: ChatState):
    # 현재 상태(이전에 추천했던 메뉴)를 확인
    last_menu = state.get("selected_menu")

    # 만약 이전에 A코스를 추천했다면 -> 거절당하고 다시 온 것이므로 B코스 추천
    if last_menu == "A 코스 (20만원)":
        print("\n🍣 [Recommender] 그렇다면. 실속형 'B 코스 (8만원)'을 추천합니다.")
        return {"selected_menu": "B 코스 (8만원)"}

    # 기본(최초) 추천
    else:
        print("\n🍣 [Recommender] 쉐프 추천: 'A 코스 (20만원)'")
        return {"selected_menu": "A 코스 (20만원)"}

state["selected_menu"]가 아니라 state.get("selected_menu")인 이유는 5-1과 같습니다. 맨 처음 invoke할 때 이 키를 넣지 않기 때문이에요. []로 접근하면 KeyError로 터지지만 .get()은 얌전히 None을 돌려줍니다.

그리고 이 노드는 평범한 딕셔너리를 반환합니다. Command가 아니에요. 다음에 어디로 갈지는 이 노드가 정하지 않기 때문입니다. recommender → approval은 항상 같은 길이라 엣지로 미리 깔아 둘 겁니다.

STEP 3. approval 노드 ★ — 이 장의 전부

# [Node 2] 승인/거절 및 경로 변경 (Router 역할 겸임)
def human_approval_node(state: ChatState):
    menu = state["selected_menu"]

    print(f"\n👮 [Approval] '{menu}'은(는) 고가이므로 승인이 필요합니다.")

    # 1. 멈추고 물어봄 (Dynamic Interrupt)
    # 멈춘 후 Command(resume="yes" 또는 "no")로 전달된 값이 approved 변수에 들어옵니다.
    approved = interrupt(f"'{menu}' 예약을 진행하시겠습니까? (yes/no)")

    # 2. [핵심] 답변에 따라 즉시 순간이동 (Command with goto)
    if approved == "yes":
        print("▶️ [Decision] 승인됨 -> 예약 확정으로 이동")

        # update: 상태 업데이트 (예약 승인 로그 남기기)
        # goto: 다음 실행할 노드 이름 명시
        return Command(
            update={"messages": ["사용자가 예약을 승인했습니다."]},
            goto="booking",  # booking 노드로 즉시 점프!
        )

    else:
        print("▶️ [Decision] 거절됨 -> 다시 추천받으러 이동")

        return Command(
            update={"messages": ["사용자가 거절했습니다. 다른 메뉴를 찾습니다."]},
            goto="recommender",  # recommender 노드로 즉시 점프!
        )

앞부분은 5-1에서 이미 배운 것입니다. interrupt()가 양방향으로 동작하죠 — 나갈 때는 괄호 안 문자열을 질문으로 내보내고 실행을 정지시키고, 돌아올 때는 Command(resume="yes")의 그 값이 이 함수의 반환값이 됩니다. 그래서 approved에 "yes"가 들어앉습니다.

새로운 건 return 쪽입니다. 두 속성을 하나씩 봅시다.

goto — 다음에 실행할 노드 이름

return Command(goto="booking")

문자열 하나입니다. 그리고 이 문자열은 나중에 add_node("booking", ...)로 등록할 때 쓸 이름과 정확히 같아야 합니다. 함수 이름(booking_node)이 아니라 노드 이름("booking")이라는 점에 주의하세요.

🔍 비유 — 복도 vs 택배 송장

엣지는 건물에 미리 뚫어 둔 복도입니다. 복도가 있어야 그리로 갈 수 있죠. 설계 단계에서 모든 통로를 다 뚫어 놔야 합니다.

goto는 서류 봉투에 붙이는 송장이에요. "다음 수신처: 예약팀"이라고 적어서 내려놓으면, 사내 우편이 알아서 배달합니다. 예약팀으로 가는 복도가 뚫려 있는지는 상관없습니다. 주소만 정확하면 됩니다.

대신 주소를 잘못 적으면 반송됩니다 — 실제로 없는 노드 이름을 적으면 실행 중에 에러가 납니다. 컴파일 때는 아무 말도 안 해 줍니다. 오타 조심.

update — 떠나기 전에 남기는 메모

return Command(
    update={"messages": ["사용자가 예약을 승인했습니다."]},
    goto="booking",
)

점프하기 전에 State를 갱신하고 싶을 때 씁니다. 보통 노드가 return {"messages": [...]}로 하던 그 일을, Command를 반환할 때는 update= 안에 넣어서 하는 거예요.

return {...}와 Command(update={...})는 State 관점에서 완전히 같습니다

리듀서도 그대로 적용됩니다. messages에는 add_messages가 붙어 있으니 덮어쓰기가 아니라 뒤에 이어 붙기가 되죠.

차이는 딱 하나 — Command는 여기에 goto를 얹을 수 있다는 것. "상태를 이렇게 바꾸고, 다음은 저기로 가라"를 한 번에 전달하는 게 Command의 존재 이유입니다.

⚠️ 문자열을 넣으면 HumanMessage가 됩니다

update={"messages": ["사용자가 예약을 승인했습니다."]} — 그냥 문자열을 넣었죠. add_messages 리듀서는 맨 문자열을 받으면 자동으로 HumanMessage로 감싸서 붙입니다.

편하지만 함정이기도 합니다. 실제로 사람이 입력한 문장이 아닌 시스템 로그가 사람이 말한 것처럼 대화 기록에 남기 때문이에요. 나중에 이 messages를 그대로 LLM에게 넘기면, 모델은 "사용자가 예약을 승인했습니다"를 사용자가 한 말로 읽습니다.

실전에서는 AIMessage(content=...)로 직접 감싸거나, 로그는 아예 messages가 아닌 별도 필드에 쌓는 편이 안전합니다.

STEP 4. booking 노드 — 승인받았을 때만 오는 곳

# [Node 3] 예약 확정 (승인 시 이동할 곳)
def booking_node(state: ChatState):
    menu = state["selected_menu"]
    print(f"\n✅ [Booking] '{menu}' 예약이 확정되었습니다! (문자 발송 완료)")
    return {"messages": [f"'{menu}' 예약 완료"]}

실제 서비스라면 이 자리에 예약 API 호출이 들어갑니다. 여기서는 print로 대신했어요. 중요한 건 이 노드가 언제 실행되는가입니다 — 오직 approval이 goto="booking"을 반환했을 때만. 들어오는 엣지가 하나도 없으니 다른 경로는 아예 존재하지 않습니다.

STEP 5. 그래프 조립 — 엣지가 두 개뿐

from langgraph.graph import StateGraph, START, END

workflow = StateGraph(ChatState)

workflow.add_node("recommender", recommender_node)
workflow.add_node("approval", human_approval_node)
workflow.add_node("booking", booking_node)
workflow.add_edge(START, "recommender")
workflow.add_edge("recommender", "approval")

끝입니다. 엣지 두 줄. add_conditional_edges가 한 줄도 없다는 게 포인트예요.

3강 방식이었다면 이렇게 썼어야 합니다 — 라우터 함수를 따로 만들고, approval에서 나가는 조건부 엣지를 선언하고, booking에서 END로 가는 엣지도 붙이고. 세 덩어리가 사라진 겁니다.

3강 방식 (조건부 엣지)이번 방식 (goto)
판단하는 곳 노드 바깥의 라우터 함수 노드 안
판단 결과 문자열을 return → 엣지 매핑이 해석 Command(goto=)가 곧 목적지
상태 갱신 노드에서 하고, 라우팅은 그다음 단계 같은 return 한 번에
필요한 선언 라우터 함수 + add_conditional_edges 없음
그래프 그림 정확히 그려진다 길이 안 보인다 
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()

app = workflow.compile(checkpointer=checkpointer)
⚠️ checkpointer는 여전히 필수입니다

goto 때문이 아니라 interrupt() 때문이에요. approval 노드 한가운데서 멈췄다가 나중에 이어서 실행하려면 "어디까지 갔었는지"를 저장할 곳이 필요합니다. 재개할 때 config(=thread_id)를 빠뜨리면 멈춰 있던 스레드를 못 찾습니다.

4. 그림이 거짓말을 한다 — 왜 booking이 떠 있나

app을 그냥 출력하면 Jupyter가 draw_mermaid_png()를 자동으로 호출해서 그래프를 그려 줍니다. 그런데 그 그림이 우리가 만든 것과 다르게 보입니다. 

app
⏹ 그려진 그래프 (Mermaid로 옮기면)
__start__ --> recommender
recommender --> approval
approval  --> __end__          <-- 우리가 만든 적 없는 엣지
booking                        <-- 아무 선도 없이 떠 있음

이상한 점이 두 가지입니다.

  • booking이 고립돼 있다 — 들어가는 선도, 나오는 선도 없습니다.
  • approval → __end__ 선이 있다 — add_edge("approval", END)를 쓴 적이 없는데도요.

둘 다 정상입니다. 그리고 원인은 하나예요.

🔍 비유 — 건물 도면에는 지름길이 안 그려진다

건축 도면에는 복도와 계단만 그려집니다. 직원들이 실제로 매일 쓰는 "주차장 통해서 옆 동으로 넘어가는 지름길"은 도면 어디에도 없죠. 도면이 틀린 게 아니라, 도면은 설계된 통로만 그리기 때문입니다.

goto는 설계된 통로가 아니라 실행 중에 생기는 지름길입니다. approval 노드가 실제로 실행돼서 Command를 반환해 봐야 어디로 갈지 알 수 있어요. 그런데 그림을 그리는 시점에는 노드 함수를 실행하지 않습니다. 그러니 그릴 방법이 없죠.

__end__는 그럼 누가 그렸나

이쪽이 더 헷갈립니다. 없는 길을 안 그리는 건 이해가 되는데, 왜 없는 길이 새로 생겼을까요. LangGraph가 그림을 조립하는 마지막 단계에 이런 규칙이 있기 때문입니다. (langgraph/pregel/_draw.py) 

# 도착점으로는 등장하는데, 출발점으로는 한 번도 안 나오는 노드 = 막다른 노드
termini = {d for _, d, _, _ in edges if d != END}.difference(s for s, _, _, _ in edges)
for src in sorted(termini):
    add_edge(graph, src, END)

그림을 그릴 때 LangGraph가 알고 있는 엣지는 우리가 선언한 두 개뿐입니다. START → recommender, recommender → approval. 여기에 위 규칙을 적용해 보죠.

노드도착점으로 등장?출발점으로 등장?결과
recommender ✅ (START →)✅ (→ approval) 평범한 중간 노드
approval ✅ (recommender →)❌ 나가는 선이 없다 "막다른 노드구나" → END를 붙여 준다
booking ❌ 아무도 안 온다❌ 후보에도 못 들어감 → 외톨이로 남는다

정리하면 "나가는 선을 못 찾았으니 여기서 끝나는 모양이겠지" 하고 그림에만 END를 대신 그려 넣은 것입니다. 코드에 그런 엣지가 생긴 게 아니에요. 실행하면 approval은 goto가 시키는 대로 멀쩡히 booking이나 recommender로 갑니다.

기억할 한 문장

그림은 "선언된 엣지"만 그린다. goto는 선언이 아니라 실행 결과다.

그래서 goto를 많이 쓸수록 그래프 그림은 점점 쓸모없어집니다. 노드 100개짜리 멀티 에이전트를 goto로만 이으면, 그림에는 섬 100개가 떠 있게 됩니다.

도면을 고치는 두 가지 방법

실행에는 문제가 없지만, 팀에게 구조를 설명하거나 디버깅할 때 그림이 맞는 편이 훨씬 낫습니다. "이 노드는 이런 곳들로 갈 수 있다"를 미리 알려 주면 LangGraph가 그려 줍니다.

① 반환 타입 힌트로 알려 주기

from typing import Literal

def human_approval_node(state: ChatState) -> Command[Literal["booking", "recommender"]]:
    ...

add_node()는 함수의 반환 타입 힌트를 읽습니다. Command[Literal[...]] 형태면 대괄호 안의 문자열들을 갈 수 있는 곳으로 등록해요. 코드는 한 줄도 안 바뀌고 힌트만 붙었는데 그림이 달라집니다.

② destinations=로 직접 알려 주기

workflow.add_node("approval", human_approval_node,
                  destinations=("booking", "recommender"))

# 딕셔너리로 주면 화살표에 라벨까지 붙는다
workflow.add_node("approval", human_approval_node,
                  destinations={"booking": "승인", "recommender": "거절"})
⏹ 두 방법 중 아무거나 적용한 뒤의 그래프
__start__ --> recommender
recommender --> approval
approval  -.-> booking          <-- 점선 = 조건부 경로
approval  -.-> recommender
booking   --> __end__           <-- 이제 진짜 막다른 노드는 booking

점선(-.->)으로 그려지는 게 포인트입니다. "항상 가는 길이 아니라 조건에 따라 갈 수도 있는 길"이라는 표시예요. 그리고 END가 제자리를 찾았습니다 — 이제 진짜 막다른 노드는 booking이니까요.

둘 중 뭘 쓸까

타입 힌트를 권합니다. 함수 바로 옆에 붙어 있어서 goto 대상을 고칠 때 같이 고치게 되거든요. destinations=는 그래프 조립부에 떨어져 있어서 잊어버리기 쉽습니다.

다만 화살표에 "승인"/"거절" 같은 라벨을 달고 싶으면 destinations=의 딕셔너리 형태를 써야 합니다.

둘 다 "그림용 메타데이터"일 뿐 동작을 바꾸지는 않습니다. 여기 없는 노드로 goto해도 실행은 그냥 됩니다.

6. 조건부 엣지 vs goto — 언제 뭘 쓰나

둘 다 "갈림길을 만든다"는 목적은 같습니다. 그러면 이제 add_conditional_edges는 안 써도 되는 걸까요? 그렇지 않습니다.

🔍 비유 — 표지판이냐, 송장이냐

조건부 엣지는 갈림길에 세워 둔 표지판입니다. 길 자체가 눈에 보이고, 지나가는 사람 누구나 "여기서 두 갈래로 나뉘는구나"를 알 수 있습니다.

goto는 서류에 붙이는 송장입니다. 봉투를 열어 봐야 어디로 갈지 알 수 있죠. 대신 수신처가 몇 백 곳이어도 송장 한 장이면 됩니다.

이럴 때추천이유
갈래가 2~3개로 고정돼 있다 조건부 엣지 그림에 그대로 드러나 구조를 읽기 쉽다
상태 갱신과 이동을 같이 해야 한다 goto update + goto를 한 번의 return으로
목적지가 수십 개다 (멀티 에이전트) goto 엣지 매핑을 전부 선언하는 게 불가능하다
에이전트끼리 일을 넘긴다 (Handoff) goto 넘기는 쪽이 받을 쪽을 직접 지목하는 게 자연스럽다
팀에게 구조를 설명해야 한다 조건부 엣지 goto는 그림이 안 나온다 (힌트를 붙이면 완화)

실무에서는 섞어 씁니다. 이번 그래프가 딱 그래요 — 항상 같은 길(recommender → approval)은 엣지로, 실행 중에 갈리는 길은 goto로. "뻔한 길은 그려 두고, 상황에 따라 갈리는 길만 코드로" 정도가 좋은 기준입니다.

자주 걸리는 함정 5가지

① goto는 기존 엣지를 대체하지 않는다 — 더할 뿐이다

가장 위험한 오해입니다. 노드에 나가는 엣지가 이미 있는데 goto를 반환하면, 둘 다 실행됩니다. 

def a(state):
    return Command(goto="c")     # c로 보내려는 의도

workflow.add_edge("a", "b")      # 그런데 b로 가는 엣지도 남아 있다면?
⏹ 실행 결과
[a] 실행 -> goto='c'
[b] 실행 (static edge a->b 때문에)
[c] 실행 (goto 때문에)

b와 c가 나란히 실행됐습니다. goto는 "대신 여기로 가"가 아니라 "여기도 추가로 보내"에 가깝습니다. goto=END도 마찬가지라서, 정적 엣지가 남아 있으면 끝나지 않습니다.

규칙

goto로 경로를 정하는 노드에서는, 그 노드에서 나가는 add_edge를 전부 지우세요. 이번 그래프에서 approval에 나가는 엣지가 하나도 없는 게 실수가 아니라 필수 조건입니다.

② 같은 thread_id로 다시 실행하면 이전 상태가 남아 있다

노트북을 만지다 보면 반드시 겪습니다. 첫 번째 셀을 다시 실행했는데 A코스가 아니라 B코스가 추천되는 현상이요.

⏹ 첫 실행 후, resume 없이 같은 셀을 다시 실행하면
🍣 [Recommender] 그렇다면. 실속형 'B 코스 (8만원)'을 추천합니다.

👮 [Approval] 'B 코스 (8만원)'은(는) 고가이므로 승인이 필요합니다.

>>> ['예약해줘', '예약해줘'] | selected_menu: B 코스 (8만원)

버그가 아닙니다. checkpointer가 thread_id="goto-demo"에 selected_menu="A 코스 (20만원)"를 이미 저장해 뒀기 때문이에요. 그 상태에서 recommender가 다시 돌면 if가 참이 되어 B코스가 나오고, "예약해줘"도 한 번 더 append됩니다.

해결 — 처음부터 다시 하려면 thread_id를 바꾸세요

{"configurable": {"thread_id": "goto-demo-2"}}처럼 새 번호표를 뽑으면 빈 상태에서 시작합니다. InMemorySaver()를 다시 만드는 셀부터 재실행해도 됩니다.

중간부터 셀을 다시 돌리는 습관이 있다면 이 함정에 계속 걸립니다. 실행 결과가 이상하면 먼저 app.get_state(config)로 지금 상태부터 확인하세요.

③ 재개하면 노드가 처음부터 다시 실행된다

5-1에서 배운 그대로입니다. 실행 로그에 👮 [Approval]이 세 번 찍힌 것을 보세요. 사람에게 물어본 건 두 번인데요. interrupt() 앞의 코드는 재개할 때마다 다시 돕니다.

부작용은 interrupt() 뒤에 두세요

DB 쓰기 · 결제 · 메일 발송 · 예약 API 호출을 interrupt() 앞에 두면 재개할 때마다 한 번씩 더 일어납니다. "읽기 → interrupt → 쓰기" 순서를 기억하세요.

이번 코드가 booking을 별도 노드로 분리한 이유이기도 합니다. 예약 확정을 approval 노드 안에 넣었다면 재실행 때마다 예약이 잡혔겠죠.

④ goto에 적는 건 노드 이름이지 함수 이름이 아니다

workflow.add_node("booking", booking_node)
#                  ~~~~~~~~~  <- goto에 적을 이름은 이쪽

return Command(goto="booking")      # ✅
return Command(goto="booking_node") # ❌ 실행 중에 에러

컴파일할 때는 아무 경고도 안 나옵니다. 실제로 그 goto가 실행되는 순간에야 터져요. 거절 경로를 한 번도 안 밟아 보고 배포하면 프로덕션에서 처음 만나게 됩니다. 타입 힌트나 destinations=를 붙여 두면 그림에서 오타가 눈에 띄어 조금 빨리 잡을 수 있습니다.

⑤ Command는 노드가 반환해야 한다

def approval(state):
    Command(goto="booking")          # ❌ 만들기만 하고 버림 — 아무 일도 안 일어남
    return Command(goto="booking")   # ✅

Command는 객체일 뿐입니다. 만든다고 이동이 일어나지 않아요. LangGraph는 노드의 반환값을 보고 판단합니다. 딕셔너리면 상태 갱신만, Command면 상태 갱신 + 이동으로 처리하는 거죠.

📝 실습 — yes/no 대신 자연어로 판단하기

문제를 정확히 짚어 봅시다. 사용자가 "응 그걸로 해줘"라고 입력하면 어떻게 될까요? approved == "yes"가 거짓이니까 else로 빠지고, 승인 의도인데 거절로 처리돼서 recommender로 돌아갑니다. 사람은 yes/no로 말하지 않습니다.

🎯 과제

사용자의 자연어 답변을 LLM이 해석해서 goto 대상을 정하도록 바꾸세요.

  • Pydantic 모델로 Literal["yes", "no"] 형태의 출력 스키마를 정의합니다.
  • model.with_structured_output(...)으로 구조화된 답변만 받는 분석기를 만듭니다.
  • interrupt()가 받은 값을 그대로 비교하지 말고 분석기에 넣어 판단하세요.

힌트: goto와 update를 쓰는 부분은 하나도 안 바뀝니다. if의 조건식만 바뀝니다.

먼저 직접 해 보시고, 아래는 참고 답안입니다.

from typing import Literal
from pydantic import BaseModel, Field

# 1. 출력 스키마 — 모델이 이 형태로만 답하도록 강제
class ApprovalIntent(BaseModel):
    action: Literal["yes", "no"] = Field(
        description="사용자가 예약에 동의하면 yes, 거절하거나 다른 메뉴를 원하면 no"
    )

# 2. 구조화된 답변만 뱉는 분석기
intent_analyzer = model.with_structured_output(ApprovalIntent)

# 3. approval 노드 — if 조건식만 바뀐다
def human_approval_node(state: ChatState) -> Command[Literal["booking", "recommender"]]:
    menu = state["selected_menu"]

    user_input = interrupt(f"'{menu}' 예약을 진행하시겠습니까?")

    # [변경점] 글자 비교 -> LLM 의도 분석
    intent = intent_analyzer.invoke(
        f"제안한 메뉴: {menu}\n"
        f"사용자 답변: {user_input}\n\n"
        f"이 답변이 승인인지 거절인지 판단하세요."
    )
    print(f"🧠 [AI Router] 의도='{intent.action}'")

    # [동일] 여기부터는 그대로
    if intent.action == "yes":
        return Command(
            update={"messages": ["사용자가 예약을 승인했습니다."]},
            goto="booking",
        )
    else:
        return Command(
            update={"messages": ["사용자가 거절했습니다. 다른 메뉴를 찾습니다."]},
            goto="recommender",
        )
이 실습이 진짜로 보여 주는 것

goto 부분은 한 글자도 안 바뀌었습니다. 바뀐 건 "판단하는 주체"뿐이에요 — == 연산자에서 LLM으로.

이게 중요한 이유는, 5강 후반부에서 만들 Supervisor가 정확히 이 구조이기 때문입니다. LLM이 "누가 이 일을 해야 하는가"를 판단하고, 그 답을 goto에 그대로 넣는 거죠. 지금은 목적지가 2개지만, Supervisor에서는 그게 하위 에이전트 이름들이 됩니다.

주의 — LLM이 라우터가 되면 검증이 필요해집니다

with_structured_output에 Literal을 쓰는 이유가 바로 이것입니다. 모델이 "yes"도 "no"도 아닌 엉뚱한 문자열을 뱉으면 goto가 터지니까, 애초에 그 두 개 말고는 못 만들게 막아 두는 거예요.

LLM의 출력을 goto에 직접 꽂는 코드는 절대 쓰지 마세요. goto=intent.action 같은 식이면 모델이 만든 문자열이 그대로 노드 이름이 됩니다. 반드시 if로 한 겹 걸러서 우리가 아는 이름만 넘기세요.

전체 코드 한눈에 보기

from langchain.chat_models import init_chat_model
from langchain.messages import HumanMessage, AnyMessage
from langgraph.types import interrupt, Command
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from typing_extensions import TypedDict, Annotated
from typing import Literal

model = init_chat_model("gpt-5-nano")      # 이번 절에서는 실제로 쓰지 않음

# ── State ──────────────────────────────────────────────
class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    selected_menu: str                     # 선택된 메뉴 저장

# ── Nodes ──────────────────────────────────────────────
def recommender_node(state: ChatState):
    last_menu = state.get("selected_menu")             # 없으면 None

    if last_menu == "A 코스 (20만원)":                  # 거절당하고 돌아온 경우
        print("\n🍣 [Recommender] 그렇다면. 실속형 'B 코스 (8만원)'을 추천합니다.")
        return {"selected_menu": "B 코스 (8만원)"}
    else:                                              # 최초 추천
        print("\n🍣 [Recommender] 쉐프 추천: 'A 코스 (20만원)'")
        return {"selected_menu": "A 코스 (20만원)"}

# 타입 힌트를 붙이면 그래프 그림에 goto 경로가 그려진다
def human_approval_node(state: ChatState) -> Command[Literal["booking", "recommender"]]:
    menu = state["selected_menu"]
    print(f"\n👮 [Approval] '{menu}'은(는) 고가이므로 승인이 필요합니다.")

    approved = interrupt(f"'{menu}' 예약을 진행하시겠습니까? (yes/no)")   # ⏸ 여기서 멈춤

    if approved == "yes":
        print("▶️ [Decision] 승인됨 -> 예약 확정으로 이동")
        return Command(
            update={"messages": ["사용자가 예약을 승인했습니다."]},
            goto="booking",                            # 노드 '이름'
        )
    else:
        print("▶️ [Decision] 거절됨 -> 다시 추천받으러 이동")
        return Command(
            update={"messages": ["사용자가 거절했습니다. 다른 메뉴를 찾습니다."]},
            goto="recommender",
        )

def booking_node(state: ChatState):
    menu = state["selected_menu"]
    print(f"\n✅ [Booking] '{menu}' 예약이 확정되었습니다! (문자 발송 완료)")
    return {"messages": [f"'{menu}' 예약 완료"]}

# ── Graph ──────────────────────────────────────────────
workflow = StateGraph(ChatState)

workflow.add_node("recommender", recommender_node)
workflow.add_node("approval", human_approval_node)
workflow.add_node("booking", booking_node)

workflow.add_edge(START, "recommender")
workflow.add_edge("recommender", "approval")
# approval에서 나가는 엣지 없음 — goto가 담당한다 (엣지를 두면 둘 다 실행됨)
# booking에서 나가는 엣지도 없음 — 여기서 그래프가 끝난다

app = workflow.compile(checkpointer=InMemorySaver())   # interrupt를 쓰므로 필수

# ── 실행 ───────────────────────────────────────────────
config = {"configurable": {"thread_id": "goto-demo"}}

app.invoke({"messages": [HumanMessage(content="예약해줘")]}, config=config)  # A코스 제안 후 멈춤

snapshot = app.get_state(config)
print(f"⚠️ 대기 중: {snapshot.tasks[0].interrupts[0].value}")

app.invoke(Command(resume="no"), config=config)        # 거절 -> B코스 제안 후 다시 멈춤
result = app.invoke(Command(resume="yes"), config=config)  # 승인 -> booking 실행

print(result['messages'][-1].content)                  # 'B 코스 (8만원)' 예약 완료

📚 한 장 정리

  • Command의 두 얼굴 — 바깥에서 안으로는 Command(resume=값)(5-1), 노드에서 엔진으로는 Command(goto="노드이름")(5-3). 같은 객체, 반대 방향.
  • goto는 엣지를 대신하는 지름길이다 — 노드가 직접 다음 목적지를 지목한다. 엣지를 미리 깔아 둘 필요가 없어서, 목적지가 수십 개인 멀티 에이전트에서 필수가 된다.
  • update는 떠나며 남기는 메모 — return {...}와 State 관점에서 완전히 동일하다. 리듀서도 그대로 적용된다. 차이는 여기에 goto를 얹을 수 있다는 것뿐.
  • 그림은 선언된 엣지만 그린다 — goto는 실행해 봐야 아는 길이라 draw_mermaid_png()가 못 그린다. 게다가 나가는 선이 없는 노드에는 END를 임의로 붙여 준다. approval에 END가 달리고 booking이 떠 있는 건 버그가 아니다.
  • 도면을 고치려면 미리 알려 준다 — 반환 타입 힌트 -> Command[Literal["booking", "recommender"]] 또는 add_node(..., destinations=("booking", "recommender")). 둘 다 그림용 메타데이터일 뿐 동작은 안 바뀐다.
  • ⚠️ goto는 엣지를 대체하지 않고 추가한다 — 나가는 add_edge가 남아 있으면 엣지 대상과 goto 대상이 둘 다 실행된다. goto로 경로를 정하는 노드에서는 나가는 엣지를 전부 지울 것.
  • 재개하면 노드는 처음부터 다시 돈다 — 👮 [Approval] 로그가 사람에게 물어본 횟수보다 한 번 더 찍히는 이유. 예약 확정을 별도 booking 노드로 뺀 것도 이 때문이다.
  • 같은 thread_id는 이전 상태를 기억한다 — 셀을 다시 돌렸는데 A코스가 아니라 B코스가 나오면 버그가 아니라 checkpointer다. thread_id를 바꾸거나 app.get_state()로 먼저 확인할 것.
  • 조건부 엣지를 버리는 게 아니다 — 항상 같은 길은 엣지로, 실행 중에 갈리는 길은 goto로. 갈래가 2~3개로 고정이면 여전히 조건부 엣지가 읽기 좋다.
  • LLM의 출력을 goto에 직접 꽂지 말 것 — Literal로 선택지를 묶고 if로 한 겹 걸러서 우리가 아는 노드 이름만 넘긴다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

결재 서류에 붙이는 송장을 떠올리세요. "승인 도장 찍고(update), 다음은 예약팀으로(goto)"라고 적어 내려놓으면 끝입니다. 예약팀으로 가는 복도가 뚫려 있는지는 신경 쓰지 않아도 됩니다.

대신 건물 도면에는 그 길이 안 그려집니다. 도면이 텅 빈 것처럼 보여도 서류는 정확히 도착하고 있다 — 이게 이번 장의 전부예요.

그리고 지금 "예약팀"이라고 적은 그 칸에, 다음 장부터는 다른 에이전트 이름이 들어갑니다.
