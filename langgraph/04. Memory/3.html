4-3. Store (Long-term Memory) — 스레드를 넘어 사람을 기억하기

실습 노트북: 3.ipynb  ·  대상 범위: 4강 Memory 세 번째 — 장기 메모리 Store와 LangGraph의 설계 철학  ·  난이도: 🟢 입문~중급

앞의 두 장에서 만든 기억은 전부 대화방 하나에 묶여 있었습니다. thread_id를 바꾸는 순간 에이전트는 초면이 됐죠. 이번 장에서는 그 벽을 넘는 장기 메모리(Long-term Memory)와 그 그릇 Store를 다룹니다. 같은 에이전트를 키워드 트리거 방식과 도구화 방식 두 가지로 만들어 보고, 마지막에는 "왜 LangGraph는 Store를 Runtime 밖으로 꺼냈나"라는 질문으로 LangGraph의 설계 철학까지 내려갑니다. 문법은 LangChain 때와 거의 같고, Store가 놓이는 자리 하나가 다릅니다 — 그리고 그 자리 하나가 철학 전체를 요약합니다.

1. 복습 다리 — LangChain에서는 장기 메모리를 이렇게 다뤘다

LangChain 강의에서 장기 메모리는 Runtime이라는 상자 안의 부품이었습니다. 미들웨어(@wrap_model_call)가 request.runtime.store를 열어 기억을 꺼내고, 시스템 프롬프트에 끼워 넣어 LLM에게 전달했죠. 그때 배운 namespace·key·put·get·search는 LangGraph에서도 철자 하나 안 바뀌고 그대로입니다 — 사실 그 저장소의 모듈 경로부터가 langgraph였으니, 우리는 이미 LangGraph의 Store를 빌려 쓰고 있었던 셈입니다. 아래 어휘만 다시 챙기고 바로 LangGraph로 넘어갑니다.

🔍 비유 — 미용실 고객 카드 캐비닛

1장(4-1)에서 단기 메모리는 오늘 상담하며 적는 수첩, 장기 메모리는 카운터의 고객 카드라고 했습니다. 고객 카드는 캐비닛에 들어 있고, 캐비닛은 고객별 서랍으로 나뉘고, 서랍에는 카드가 여러 장 꽂혀 있죠.

캐비닛 = Store, 서랍 = namespace, 카드 한 장 = key, 카드에 적힌 내용 = value. 이 네 단어면 이번 장의 절반은 끝납니다.

Store — 폴더와 파일 이름

이번 실습의 namespace는 ('jay', 'profile') — jay/profile/ 폴더라고 읽으면 됩니다. 그 안에 memory_001 같은 파일(key)이 쌓입니다. 실습용 저장소 InMemoryStore는 RAM 위의 임시 저장소라 프로세스가 죽으면 사라지며, 실서비스에서는 PostgreSQL·Redis 같은 DB 기반 스토어로 생성 두 줄만 교체하면 됩니다.

namespace는 왜 튜플인가

폴더 경로는 계층이기 때문입니다. ('jay', 'profile')은 "jay라는 사람의 → profile 카테고리"라는 두 단계 경로이고, ('jay', 'schedule')처럼 카테고리를 늘려도 사용자별로 섞이지 않습니다. 또 튜플은 불변(immutable)이라 키로 안전합니다. 리스트가 아니라 반드시 튜플이어야 합니다.

메서드 세 개 — put · get · search

메서드필요한 것돌아오는 것비유
put(ns, key, value) 폴더 + 파일명 + 내용 없음 (저장만) 파일 저장
get(ns, key) 폴더 + 파일명 Item 하나 → .value 파일 하나 열기
search(ns) 폴더만 Item 리스트 폴더 통째로 열기
왜 실전에서는 search를 쓰나

get은 파일 이름을 미리 알아야 합니다. 그런데 기억은 언제 몇 개가 쌓일지 모르죠. 그래서 저장할 때는 uuid로 겹치지 않는 이름을 자동 생성하고, 읽을 때는 폴더를 통째로 훑는(search) 조합이 자연스럽습니다. 이번 실습도 정확히 그 조합입니다.

저장만으로는 아무 일도 안 일어난다 — 주입

기억을 저장하는 일과 그 기억을 쓰는 일은 별개입니다. 고객 카드를 캐비닛에 잘 넣어놨어도 손님이 왔을 때 꺼내 읽지 않으면 없는 것과 같죠. 그래서 어느 프레임워크든 ① 누구의 기억인지 알아내고 → ② search로 꺼내고 → ③ 문자열로 합쳐 → ④ 시스템 프롬프트에 끼워 넣는 네 단계가 필요합니다. LangChain에서는 미들웨어가 이 일을 했고, LangGraph에서는 노드 함수 본문이 합니다. 바뀌는 건 ①·②를 "어디서 꺼내오느냐"뿐, ③·④는 문장 하나 안 바뀝니다.

2. LangGraph의 Store — 물건은 같고, 자리가 다르다

LangChain에서 Store를 꺼내려면 request.runtime.store처럼 상자를 열고 파고들어야 했습니다. LangGraph는 그 상자를 아예 안 씁니다. Store를 밖으로 꺼내 놓고, 필요한 노드에게 직접 건네줍니다. "왜 굳이?"라는 질문의 답은 5장 설계 철학에서 하고, 지금은 문법부터 봅니다.

① 그래프에 장착 — compile(store=...)

1장에서 체크포인터를 compile에 넘겼던 그 자리에, 인자 이름만 store로 하나 더 붙입니다. 그래프의 모양(노드·엣지)은 전혀 바뀌지 않습니다. 

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore

checkpointer = InMemorySaver()   # 단기 — 대화 스레드별 수첩
store = InMemoryStore()          # 장기 — 사용자별 고객 카드 캐비닛

app = workflow.compile(checkpointer=checkpointer, store=store)
🔍 비유 — 가게를 여는 준비

add_node·add_edge는 가게 동선을 짜는 일이고, compile은 개업 직전에 비품을 들이는 일입니다 — 상담 수첩(체크포인터)과 고객 카드 캐비닛(스토어)을 카운터에 놓는 것. 비품을 놓는다고 동선이 바뀌지는 않으니, app을 그려봐도 그림은 그대로입니다.

② 노드가 직접 받는다 — BaseStore

지금까지 노드의 인자는 state 하나였는데, 여기에 둘이 더 붙습니다.

1state

공책. 지금까지 오간 메시지가 담긴 그래프의 상태. 늘 첫 번째 자리.

2config

작업 지시서. thread_id·user_id가 들어 있다. LangChain의 Context 역할.

3store

캐비닛 열쇠. 장기 메모리 저장소 그 자체. 타입은 BaseStore.

이 셋은 우리가 넣어주는 게 아닙니다. LangGraph가 노드 함수의 파라미터 이름을 보고 알아서 채워 넣습니다. store 파라미터가 있으면 compile(store=...)에 넘겼던 객체가 그대로 들어오고, 안 쓸 거면 안 적으면 됩니다.

BaseStore는 무엇인가 — "저장소 표준 규격"

store: BaseStore의 BaseStore는 타입 힌트라 없어도 돌아갑니다. 그런데 왜 적을까요? 220V 콘센트 규격을 생각해 보세요 — 규격이 있으니 어떤 기기든 플러그만 맞으면 꽂힙니다. BaseStore는 "이 자리에 들어올 물건은 put·get·search를 갖고 있다"는 규격 선언입니다. 덕분에 실습에선 InMemoryStore, 실서비스에선 DB 기반 스토어를 꽂아도 노드 코드는 한 글자도 안 바뀌고, 에디터 자동완성도 됩니다.

③ 한눈에 비교 — 딱 두 줄만 다르다

하는 일LangChainLangGraph
저장소 장착 create_agent(..., store=store) workflow.compile(store=store)
주입 지점 미들웨어 (@wrap_model_call) 노드 함수 본문
사용자 식별 request.runtime.context.user_id config['configurable']['user_id']
저장소 접근 request.runtime.store.search(ns) store.search(ns)
LLM 호출 handler(request) model.invoke(prompt)
메서드 이름 put · get · search — 완전히 동일

표를 세로로 훑으면 LangGraph 쪽이 전부 짧습니다 — request.runtime.이라는 껍데기가 사라진 대신 함수 시그니처가 길어졌죠. 숨어 있던 정보를 문 앞으로 끄집어낸 것, 이게 LangGraph의 방식입니다. (왜 이 교환이 이득인지는 5장에서.)

3. 구현 ① — "기억해"라고 말하면 저장하는 에이전트

만들 것은 노드 하나짜리 에이전트입니다. 사용자 메시지에 "기억해"가 들어 있으면 Store에 저장하고, 답변할 때는 매번 Store를 읽어 참고합니다. Model과 State는 1장과 동일합니다.

STEP 1. Model 정의

from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")

STEP 2. State 정의

from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
왜 기억을 State에 안 넣나

State는 "이번 대화방에서 벌어지는 일"을 담는 공책이라 thread_id가 바뀌면 새것으로 바뀝니다. 장기 메모리는 방을 넘어 따라와야 하므로 State 바깥, 즉 Store에 둡니다. State는 대화, Store는 사람 — 이렇게 나눠 기억하세요.

STEP 3. Node 정의 — 읽고, 쓰고, 주입한다

import uuid
from langgraph.store.base import BaseStore
from langchain.messages import SystemMessage

def memory_agent_node(state: ChatState, config, store: BaseStore):

    # 1. 설정에서 user_id 가져오기 (누구의 기억인가?)
    user_id = config['configurable']['user_id']

    # 2. 기억 공간(Namespace) 정의: (사용자ID, 카테고리)
    namespace = (user_id, 'profile')

    # [WRITE] 기억 저장 로직 (간단한 키워드 트리거)
    last_message = state["messages"][-1]
    if "기억해" in last_message.content:
        # store.put(namespace, key, value)
        # key는 고유해야 하므로 uuid 사용
        memory_id = str(uuid.uuid4())
        store.put(
            namespace,
            memory_id,
            {
                'content' : last_message.content
            }
        )

    # [READ] 기억 조회 로직
    memories = store.search(namespace)

    # 기억이 있으면 문자열로 병합
    if memories:
        memory_text = "\n".join([f"- {m.value['content']}" for m in memories])
        system_msg = f"""
        당신은 사용자의 정보를 기억하는 비서입니다.

        [장기 기억 저장소]
        {memory_text}

        위 기억을 참고하여 답변하세요.
        """
    else:
        system_msg = "당신은 도움이 되는 비서입니다. 아직 사용자에 대해 아는 것이 없습니다."

    # 3. LLM 호출 (시스템 메시지 + 대화 내역)
    # SystemMessage를 맨 앞에 끼워넣어서 Context 주입
    prompt = [SystemMessage(content=system_msg)] + state["messages"]

    return {"messages": [model.invoke(prompt)]}

길어 보이지만 하는 일은 네 덩어리입니다.

① 누구?

config['configurable']['user_id']로 사용자를 특정합니다. 이 값이 없으면 어느 서랍을 열지 알 수 없습니다.

② 어느 서랍?

(user_id, 'profile') 튜플로 네임스페이스를 만듭니다. 'profile'은 우리가 정한 카테고리 이름이라 바꿔도 되지만, 쓸 때와 읽을 때가 같아야 합니다.

③ 쓰기 [WRITE]

마지막 메시지에 "기억해"가 들어 있으면 put. 파일 이름은 uuid4()로 매번 새로 뽑아 겹치지 않게 합니다.

④ 읽기 + 주입

search로 서랍을 통째로 꺼내 목록 문자열로 합치고, SystemMessage에 담아 대화 맨 앞에 끼워 넣고 LLM을 호출합니다.

③과 ④의 순서가 중요합니다 — 먼저 저장하고, 그다음 읽습니다. 덕분에 "이거 기억해"라고 말한 바로 그 턴에도 방금 저장한 내용이 답변에 반영됩니다. 뒤집으면 한 턴씩 늦게 반영돼요.

⚠️ 가장 많이 틀리는 곳 — 쓸 때의 키와 읽을 때의 키

# 쓸 때 — value 딕셔너리의 키를 'content'로 정했다
store.put(namespace, memory_id, {'content': last_message.content})
#                                 ~~~~~~~~~

# 읽을 때 — 그래서 꺼낼 때도 'content'로 꺼내야 한다
memory_text = "\n".join([f"- {m.value['content']}" for m in memories])
#                                    ~~~~~~~~~
키가 안 맞으면 KeyError

put에서 {'content': ...}로 넣고 읽을 때 m.value['data']로 꺼내면 터집니다. 더 고약한 건, 저장이 0건일 때는 for 문이 안 돌아 에러도 안 난다는 점 — 기억이 하나 쌓인 두 번째 실행에서야 터집니다. value의 키는 내가 정한 라벨이고, 정한 사람이 지켜야 하는 약속입니다. 잠시 후 도구화 버전에서는 이 키가 'data'로 바뀝니다. 그때 다시 짚겠습니다.

STEP 4. 그래프 만들고 두 메모리 장착하기

from langgraph.graph import StateGraph, START, END

workflow = StateGraph(ChatState)
workflow.add_node("agent", memory_agent_node)
workflow.add_edge(START, "agent")
workflow.add_edge("agent", END)
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore

checkpointer = InMemorySaver()   # 단기 기억 (대화 스레드)
store = InMemoryStore()          # 장기 기억 (사용자 정보 저장 - DB 역할)

app = workflow.compile(checkpointer=checkpointer, store=store)
▸ app 그려보기
__start__  →  agent  →  __end__

노드 하나, 엣지 둘 — 장기 메모리를 붙였다고 그래프가 복잡해지지 않습니다. 그림에 Store도 Checkpointer도 안 보이는 건 둘 다 그래프의 "모양"이 아니라 "설비"이기 때문입니다. 가게 동선도에 캐비닛이 안 그려지는 것과 같죠.

STEP 5. 실행 — config에 열쇠 두 개를 넣는다

config_1 = {'configurable': {
    'thread_id': 'store_demo',   # 단기 — 어느 대화방인가
    'user_id': 'jay'             # 장기 — 누구의 기억인가
}}
키담당쓰이는 곳바꾸면
thread_id 단기 · Checkpointer LangGraph가 자동으로 사용 대화 맥락이 끊긴다
user_id 장기 · Store 우리가 노드에서 직접 꺼내 씀 다른 사람의 서랍을 연다
user_id라는 이름은 "약속"일 뿐입니다

thread_id는 LangGraph의 예약어지만 user_id는 우리가 지어낸 이름이라 customer든 member_no든 상관없습니다. 대신 노드 안의 config['configurable']['user_id']와 철자가 정확히 같아야 합니다 — 어긋나면 곧바로 KeyError예요.

이 한 번의 invoke 안에서 "기억해" 감지 → put(카드 생성) → search(방금 넣은 카드까지 읽음) → 주입 후 답변이 순서대로 일어났습니다. 그래서 "기억하겠습니다"가 빈말이 아니라 실제 저장된 결과입니다. 다만 같은 대화방 안의 답변이라 아직 아무것도 증명되지 않았어요 — 단기 메모리만으로도 나올 수 있는 답변이니까요. 진짜 시험은 대화방을 갈아치우는 것입니다.

4. 구현 ② — 기억을 도구로 만들어 자동화하기

키워드 트리거에는 명백한 구멍이 있습니다. "기억해"라는 단어에만 반응한다는 것이죠. "내 이름은 Jay야"는 중요한 정보인데도 저장이 안 되고, "이 노래 좀 기억해뒀다가 틀어줘"는 프로필과 무관한데도 저장됩니다. if 문으로 단어를 늘려가는 건 답이 아닙니다 — 우리에겐 문맥을 판단할 줄 아는 LLM이 있으니, "저장할지 말지"라는 판단 자체를 LLM에게 넘기는 것, 그게 도구화입니다.

🔍 비유 — 단어에 반응시키기 vs 알아서 적게 하기

키워드 방식은 신입에게 "손님이 '기억해'라고 말하면 카드에 적어"라고 시키는 것 — 정확히 그 단어가 나올 때만 적습니다. 도구화는 "손님 정보 중 남겨둘 만한 게 나오면 적어. 인사말은 적지 말고"라고 기준만 알려주고 판단을 맡기는 것입니다. '기억해'라고 말하지 않아도 이름과 사는 곳은 알아서 적히게 됩니다.

STEP 1. 기억 버튼 만들기 — @tool

from langchain.tools import tool

# 1. 도구(Tool) 정의: AI에게 쥐어줄 '기억 버튼'
@tool
def save_profile(info: str):
    """
    사용자에 대한 중요한 정보(이름, 취미, 특징 등)를 저장할 때 사용합니다.
    단순한 대화나 인사는 저장하지 마세요.
    """
    print(f'저장한 정보 : {info}')
    # 이 함수는 실제로는 실행되지 않고, 스키마(껍데기)만 LLM에게 전달
    # 실제 저장 로직은 아래 'save_node'에서 store 객체를 이용해 수행
    return "saved"

tools = [save_profile]
model_with_tools = model.bind_tools(tools)
docstring이 곧 판단 기준 — 그리고 본문은 실행되지 않습니다

이 도구에서 가장 중요한 코드는 본문이 아니라 docstring입니다. LLM은 저 설명문만 읽고 "지금 이걸 눌러야 하나?"를 결정하므로, "단순한 대화나 인사는 저장하지 마세요" 한 줄이 "안녕하세요"까지 저장되는 사태를 막습니다.

그리고 print도 return도 실제로는 실행되지 않습니다. LangGraph가 store를 꽂아주는 건 그래프에 등록된 노드뿐이라 도구 함수 안에서는 캐비닛에 손이 닿지 않아요. 그래서 역할을 가릅니다 — 도구는 "무엇을 저장할지" LLM에게서 받아내는 양식(스키마), 노드는 그 양식을 들고 실제로 캐비닛을 여는 손.

STEP 2. agent_node — 읽기 + 판단

from langgraph.store.base import BaseStore

# [Node 1] 에이전트: 대화 및 판단
def agent_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")

    # 1. 저장된 기억을 조회해서 컨텍스트로 주입
    memories = store.search(namespace)
    if memories:
        info = "\n".join([f"- {m.value['data']}" for m in memories])
        system_msg = f"당신은 사용자의 기억을 담당하는 비서입니다.\n[기억된 정보]\n{info}"
    else:
        system_msg = "당신은 사용자의 기억을 담당하는 비서입니다."

    # 2. LLM 호출
    return {"messages": [model_with_tools.invoke([SystemMessage(content=system_msg)] + state["messages"])]}

앞의 memory_agent_node와 달라진 곳은 딱 둘 — if "기억해" in ... 쓰기 블록이 사라졌고(이 노드는 읽고 판단만), model 대신 model_with_tools를 호출합니다. 그래서 LLM은 답변을 만들 수도, 도구를 부를 수도 있습니다.

🔑 키가 'content'에서 'data'로 바뀌었습니다

m.value['data'] — 앞 절에서는 m.value['content']였죠. 이번엔 save_node가 {"data": info_to_save} 형태로 저장하기 때문입니다. 키 이름에 정답은 없고, put하는 쪽과 읽는 쪽이 짝만 맞으면 됩니다. 실수를 피하려면 프로젝트 안에서 키 이름을 하나로 통일하거나 상수로 뽑아 쓰세요.

STEP 3. save_node — 실제로 캐비닛을 여는 손

from langchain.messages import ToolMessage

# [Node 2] 저장 실행기: 실제 Store에 저장 (Action)
def save_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")

    # 에이전트가 보낸 '도구 호출' 메시지 가져오기
    last_message = state["messages"][-1]

    tool_outputs = []
    for tool_call in last_message.tool_calls:
        if tool_call["name"] == "save_profile":
            # AI가 저장하라고 한 정보
            info_to_save = tool_call["args"]["info"]

            print(f"\n💾 [System] AI의 요청으로 정보를 저장합니다: '{info_to_save}'")

            # [Store Write] 실제 저장 수행
            memory_id = str(uuid.uuid4())
            store.put(namespace, memory_id, {"data": info_to_save})

            # 도구 실행 결과 메시지 생성
            tool_outputs.append(
                ToolMessage(
                    content=f"정보 저장 완료: {info_to_save}",
                    tool_call_id=tool_call["id"]
                )
            )

    return {"messages": tool_outputs}

3강에서 쓰던 툴 노드를 직접 손으로 만든 버전입니다. 준비된 ToolNode 대신 직접 만든 이유가 바로 store를 파라미터로 받기 위해서예요. 직전 AIMessage의 tool_calls에서 LLM이 정리해 준 인자를 꺼내 store.put으로 저장하고, 반드시 tool_call_id를 짝지은 ToolMessage(몇 번 요청에 대한 응답인지 알리는 접수번호)를 돌려줍니다 — 이게 없으면 LLM이 대화 기록을 이해하지 못하고 에러가 납니다.

STEP 4. 분기와 엣지 — 저장할까, 끝낼까

workflow = StateGraph(ChatState)
workflow.add_node("agent", agent_node)
workflow.add_node("save_node", save_node)

workflow.add_edge(START, "agent")

# 조건부 함수
def should_continue(state: ChatState):
    last_message = state['messages'][-1]

    if last_message.tool_calls :
        return 'save_node'
    else:
        return END

# 조건부 엣지
workflow.add_conditional_edges(
    'agent',
    should_continue,
    ['save_node', END]
)

# save_node가 agent에게 보고 (엣지)
workflow.add_edge("save_node", "agent")
▸ 완성된 그래프
__start__
    ↓
  agent  ←─────────────────┐
    │                      │
    ├── tool_calls 있음 ──→ save_node
    │
    └── tool_calls 없음 ──→ __end__

핵심은 save_node에서 agent로 돌아오는 화살표입니다. 저장만 하고 끝내면 사용자는 답변을 못 받으니까요. 돌아온 agent_node는 store.search를 다시 호출하는데, 그사이 save_node가 새 카드를 넣어놨으므로 방금 저장한 정보까지 읽은 상태로 사람에게 할 말을 만듭니다. 같은 턴 안에서 쓰고 → 읽고 → 답하는 한 바퀴가 완성되는 겁니다. 

checkpointer = InMemorySaver()
store = InMemoryStore()
app = workflow.compile(checkpointer=checkpointer, store=store)

두 방식, 어느 쪽을 쓸까

키워드 트리거는 토큰을 안 쓰고 100% 예측 가능합니다 — "저장" 버튼이 UI에 따로 있는 서비스라면 이쪽이 낫습니다. 도구화는 자연스럽지만 LLM의 판단에 의존하고 토큰을 더 씁니다. 그래서 docstring을 다듬는 일이 곧 품질 관리가 되죠. 실전에서는 섞어 씁니다 — 명시적 요청은 키워드로 확실하게, 나머지는 LLM에게.

5. LangGraph 설계 철학 — 왜 Store를 밖으로 꺼냈나

2장에서 미뤄뒀던 질문에 답할 차례입니다. 코드만 놓고 보면 LangChain 쪽이 편해 보입니다 — request 하나만 받으면 Context든 Store든 다 꺼낼 수 있고 함수 시그니처도 짧으니까요. 그런데 LangGraph는 일부러 그 편의를 버렸습니다.

명시적인 것이 암시적인 것보다 낫다

이 빨간 상자의 위치 차이가 전부입니다.

LangChainLangGraph
함수 첫 줄 def inject_memory(request, handler) def save_node(state, config, store: BaseStore)
첫 줄만 보면 이 함수가 뭘 건드리는지 알 수 없다 Store를 건드린다는 게 바로 보인다
확인하려면 본문을 끝까지 읽어야 한다 안 읽어도 된다
노드 30개면 30개를 다 열어봐야 한다 시그니처만 훑으면 된다
🔍 비유 — 자재 반출 신청서

공사 현장에 작업자가 서른 명인데 어느 날 자재 창고에서 물건이 잘못 나갔습니다. 모두에게 마스터키(request)를 나눠준 현장이라면 서른 명의 작업 일지를 전부 뒤져야 합니다. 창고 열쇠를 신청서에 적고 받아 가는 현장이라면 신청서 목록만 보면 끝이죠 — 세 명으로 좁혀집니다.

노드 시그니처가 바로 그 신청서입니다. store라고 적혀 있으면 창고를 건드리는 노드, 없으면 안 건드리는 노드 — 읽지 않고도 알 수 있는 정보가 되는 겁니다.

테스트하기도 훨씬 쉬워집니다

save_node를 테스트하려면 가짜 state·config·store 세 개만 만들면 됩니다. 반면 request를 받는 함수는 request.runtime.store까지 갖춘 가짜 객체를 통째로 만들어야 하죠. 필요한 것만 받는 함수가 테스트하기 쉽다는 일반 원칙 그대로입니다.

로우 레벨 프레임워크의 대가

1강에서 LangGraph는 로우 레벨 오케스트레이션 프레임워크라고 했습니다. 그 말의 의미가 이제 구체적으로 와닿을 겁니다.

1결정권이 개발자에게

어떤 노드가 언제 실행될지, 어디로 갈지 전부 직접 정한다

2자동화 영역이 없다

알아서 되는 게 없으니 하나하나 다 적어야 한다

3코드가 길어진다

명시성이 올라가면 복잡성도 같이 올라간다

4그래서 더 명시한다

복잡해질수록 꼬이지 않게 못 박아두는 게 이득이다

③에서 ④로 넘어가는 게 핵심입니다. 보통 "코드가 길어진다"는 건 단점이지만, LangGraph는 어차피 길어질 코드라면 길어지는 방향을 "읽기 쉬운 쪽"으로 잡자고 결정한 겁니다.

🔍 비유 — 자동 변속기와 수동 변속기

LangChain은 자동 변속기 — create_agent 한 줄이면 루프도 분기도 알아서 돌아갑니다. LangGraph는 수동 변속기 — 기어를 직접 넣어야 하지만 지금 몇 단인지 늘 알고 있죠.

수동 변속기 차에서는 계기판이 더 중요해집니다. 직접 조작할 게 많을수록 지금 상태가 한눈에 보여야 하니까요. 노드 시그니처에 state·config·store를 다 적는 것이 그 계기판을 다는 일입니다.

정리하면 — LangGraph가 Store를 Runtime에서 꺼낸 것은 취향이 아니라 필연입니다. 모든 것을 직접 조립하는 프레임워크에서는 "이 부품이 무엇과 연결되는지"가 겉으로 드러나야 부품이 백 개로 늘어나도 조립도가 무너지지 않기 때문입니다.

자주 걸리는 함정

1. put의 키와 읽을 때의 키가 다르다
store.put(ns, mid, {'content': text})       # 넣을 때는 content
info = m.value['data']                      # 꺼낼 때는 data  ← KeyError!

이번 노트북에서 실제로 두 방식이 다른 키를 씁니다 (키워드 버전은 'content', 도구 버전은 'data'). 섞어 쓰면 반드시 터지고, 저장된 기억이 0건이면 에러가 안 나서 두 번째 실행에서야 발견됩니다.

2. config에 user_id를 안 넣었다
KeyError: 'user_id'

{'configurable': {'thread_id': '1'}}만 넘기면 노드 첫 줄에서 바로 터집니다. thread_id는 LangGraph가 챙겨주지만 user_id는 우리 책임입니다.

3. namespace를 리스트로 넘겼다
namespace = [user_id, 'profile']    # ✗ 리스트
namespace = (user_id, 'profile')    # ✓ 튜플

괄호 하나 차이입니다. namespace는 튜플이어야 합니다.

4. compile에 store를 안 넘겼다

노드에 store: BaseStore라고 적어놨어도 compile(store=...)을 빠뜨리면 들어오는 건 None — store.search(...)에서 AttributeError가 납니다.

5. thread_id를 그대로 두고 테스트했다

가장 흔한 "잘못된 성공"입니다. 장기 메모리를 전혀 안 쓰고 있어도 같은 결과가 나옵니다. 검증하려면 thread_id를 반드시 바꾸세요.

6. InMemoryStore는 휘발성이다

커널을 재시작하면 기억은 전부 사라집니다. "어제 저장했는데 왜 없지?"의 답은 대개 이것입니다. 영구 보관이 필요하면 DB 기반 스토어로 — 바꿀 곳은 store = ... 한 줄입니다.

7. 같은 내용이 계속 쌓인다

uuid로 매번 새 파일 이름을 만들기 때문에 "매운 거 싫어해"를 세 번 말하면 카드가 세 장 생깁니다. 중복 제거·갱신 로직은 직접 만들어야 합니다 (예: 고정 key로 덮어쓰기, 저장 전 search로 확인).

8. @tool 함수 안에서 store를 쓰려 했다

도구 함수는 노드가 아니라서 store가 주입되지 않습니다. 그래서 도구는 "양식"만 담당하고 실제 쓰기는 save_node가 맡습니다. 도구 본문의 print가 안 찍히는 것도 정상입니다 — 애초에 실행되지 않으니까요.

전체 코드 한눈에 보기

① 키워드 트리거 방식

# ══ 준비 ══════════════════════════════════════════════
import uuid
from langchain.chat_models import init_chat_model
from langchain.messages import AnyMessage, HumanMessage, SystemMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore
from langgraph.store.base import BaseStore

model = init_chat_model("gpt-5-nano")

# ══ STEP 2. State ═════════════════════════════════════
class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

# ══ STEP 3. Node ══════════════════════════════════════
def memory_agent_node(state: ChatState, config, store: BaseStore):
    user_id = config['configurable']['user_id']       # ★ 누구의 기억인가
    namespace = (user_id, 'profile')                  # ★ 튜플! 폴더 경로

    # [WRITE] "기억해"가 있으면 저장
    last_message = state["messages"][-1]
    if "기억해" in last_message.content:
        memory_id = str(uuid.uuid4())                 # ★ 파일 이름은 고유하게
        store.put(namespace, memory_id, {'content': last_message.content})

    # [READ] 폴더 통째로 조회
    memories = store.search(namespace)
    if memories:
        memory_text = "\n".join([f"- {m.value['content']}" for m in memories])
        system_msg = f"""
        당신은 사용자의 정보를 기억하는 비서입니다.

        [장기 기억 저장소]
        {memory_text}

        위 기억을 참고하여 답변하세요.
        """
    else:
        system_msg = "당신은 도움이 되는 비서입니다. 아직 사용자에 대해 아는 것이 없습니다."

    # [주입] 시스템 메시지를 맨 앞에 끼워넣기
    prompt = [SystemMessage(content=system_msg)] + state["messages"]
    return {"messages": [model.invoke(prompt)]}

# ══ STEP 4. 그래프 + 두 메모리 ════════════════════════
workflow = StateGraph(ChatState)
workflow.add_node("agent", memory_agent_node)
workflow.add_edge(START, "agent")
workflow.add_edge("agent", END)

checkpointer = InMemorySaver()                        # 단기
store = InMemoryStore()                               # 장기
app = workflow.compile(checkpointer=checkpointer, store=store)

# ══ STEP 5. 실행 ══════════════════════════════════════
config_1 = {'configurable': {'thread_id': 'store_demo', 'user_id': 'jay'}}
input1 = {"messages": [HumanMessage(content="내 이름은 Jay이고, 나는 매운 음식을 싫어해. 이거 꼭 기억해.")]}
resp1 = app.invoke(input1, config_1)
print(resp1['messages'][-1].content)

# ★ 방을 바꿔도(thread_id) 사람이 같으면(user_id) 기억은 따라온다
config_2 = {"configurable": {"thread_id": "thread-2", "user_id": "jay"}}
input2 = {"messages": [HumanMessage(content="점심 메뉴 추천해줘.")]}
resp2 = app.invoke(input2, config=config_2)
print(resp2['messages'][-1].content)

② 도구화 방식

from langchain.tools import tool
from langchain.messages import ToolMessage

# ══ 1. 기억 버튼(Tool) ════════════════════════════════
@tool
def save_profile(info: str):
    """
    사용자에 대한 중요한 정보(이름, 취미, 특징 등)를 저장할 때 사용합니다.
    단순한 대화나 인사는 저장하지 마세요.
    """
    print(f'저장한 정보 : {info}')   # ★ 실제로는 실행되지 않는다 (스키마 역할)
    return "saved"

tools = [save_profile]
model_with_tools = model.bind_tools(tools)

# ══ 2. agent_node — 읽고 판단 ═════════════════════════
def agent_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")

    memories = store.search(namespace)
    if memories:
        info = "\n".join([f"- {m.value['data']}" for m in memories])   # ★ 키가 'data'
        system_msg = f"당신은 사용자의 기억을 담당하는 비서입니다.\n[기억된 정보]\n{info}"
    else:
        system_msg = "당신은 사용자의 기억을 담당하는 비서입니다."

    return {"messages": [model_with_tools.invoke([SystemMessage(content=system_msg)] + state["messages"])]}

# ══ 3. save_node — 실제 저장 ══════════════════════════
def save_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")
    last_message = state["messages"][-1]

    tool_outputs = []
    for tool_call in last_message.tool_calls:
        if tool_call["name"] == "save_profile":
            info_to_save = tool_call["args"]["info"]
            print(f"\n💾 [System] AI의 요청으로 정보를 저장합니다: '{info_to_save}'")

            memory_id = str(uuid.uuid4())
            store.put(namespace, memory_id, {"data": info_to_save})    # ★ 키가 'data'

            tool_outputs.append(
                ToolMessage(content=f"정보 저장 완료: {info_to_save}",
                            tool_call_id=tool_call["id"])              # ★ 접수번호 필수
            )
    return {"messages": tool_outputs}

# ══ 4. 그래프 — 분기와 복귀 엣지 ══════════════════════
def should_continue(state: ChatState):
    last_message = state['messages'][-1]
    if last_message.tool_calls:
        return 'save_node'
    else:
        return END

workflow = StateGraph(ChatState)
workflow.add_node("agent", agent_node)
workflow.add_node("save_node", save_node)
workflow.add_edge(START, "agent")
workflow.add_conditional_edges('agent', should_continue, ['save_node', END])
workflow.add_edge("save_node", "agent")          # ★ 저장 후 다시 보고

checkpointer = InMemorySaver()
store = InMemoryStore()
app = workflow.compile(checkpointer=checkpointer, store=store)

# ══ 5. 실행 — "기억해"가 없어도 저장된다 ══════════════
config = {"configurable": {"thread_id": "1", "user_id": "jay"}}
input1 = {"messages": [HumanMessage(content="안녕, 나는 샌프란시스코에 사는 Jay라고 해.")]}
resp1 = app.invoke(input1, config=config)
print(resp1["messages"][-1].content)

input2 = {"messages": [HumanMessage(content="내 이름이 뭐고 어디 산다고 했지?")]}
resp2 = app.invoke(input2, config=config)
print(resp2["messages"][-1].content)

📚 한 장 정리

오늘의 핵심 한 문장

장기 메모리는 compile할 때 붙이고(store), invoke할 때 사람을 지목하며(user_id), 노드가 파라미터로 직접 받아서 put·search로 다룬다.

  • State는 대화, Store는 사람 — thread_id가 바뀌면 State는 새것이 되지만 user_id가 같으면 Store는 그대로다. 그래서 장기 기억은 State가 아니라 Store에 둔다.
  • Store의 구조는 파일 탐색기 — namespace(폴더, 반드시 튜플) + key(파일 이름) + value(내용 딕셔너리). 메서드는 put(저장)·get(파일 하나)·search(폴더 통째로) 셋뿐이고, 실전에서는 uuid로 저장 + search로 조회 조합을 쓴다.
  • LangChain과 딱 두 군데 다르다 — ① request.runtime.store → 노드 파라미터 store, ② request.runtime.context.user_id → config['configurable']['user_id']. 메서드 이름도, 주입 로직도 완전히 같다.
  • 노드는 최대 세 개를 받는다 — state(공책) · config(작업 지시서) · store(캐비닛 열쇠). 이름만 맞춰 적으면 LangGraph가 알아서 채워 넣고, BaseStore는 "저장소 표준 규격" 타입 힌트다.
  • 쓸 때의 키와 읽을 때의 키는 반드시 같아야 한다 — put에서 'content'로 넣었으면 m.value['content']로 꺼낸다. 기억이 0건일 땐 에러가 안 나서 늦게 발견된다.
  • 저장 방식은 두 가지 — 키워드 트리거(if "기억해" in ...)는 공짜·예측 가능하지만 말투가 다르면 놓치고, 도구화(@tool + bind_tools)는 LLM이 문맥으로 판단해 정보를 정리해서 저장한다. docstring이 곧 판단 기준이다.
  • 도구화 그래프의 모양 — START → agent → (조건부) save_node 또는 END, 그리고 save_node → agent 복귀 엣지. 돌아온 agent가 새로 저장된 기억까지 읽어서 답을 만든다. 단, 도구 함수 안에서는 store를 못 쓴다 — 노드가 아니기 때문.
  • 검증은 thread_id를 바꿔서 — 같은 방에서 물어보면 단기 메모리만으로도 맞힐 수 있어 아무것도 증명되지 않는다. 방은 바꾸고 사람은 유지한다.
  • 설계 철학 — 명시적인 것이 암시적인 것보다 낫다 — 노드가 무엇을 건드리는지 시그니처만 보고 알 수 있으면 노드가 서른 개로 늘어도 유지보수가 무너지지 않는다. 개발자가 모든 것을 직접 정하는 로우 레벨 프레임워크는 코드가 길어지는 대신, 읽기 쉬운 쪽으로 길어지게 설계됐다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

카운터 뒤의 고객 카드 캐비닛을 떠올리세요. 캐비닛을 들여놓는 일은 개업 준비(compile)고, 서랍은 손님별로 나뉘어(namespace) 있습니다. 그리고 이 가게의 규칙 — 캐비닛을 열 사람은 문 앞에서 열쇠를 받아 갑니다. 번거롭지만, 직원이 서른 명으로 늘어난 날 "누가 캐비닛을 열었나"를 열쇠 대장 한 장으로 알 수 있죠. 그게 def node(state, config, store)라는 한 줄이 사는 이유입니다.

4강을 마치며

1단기 메모리

compile(checkpointer=) · thread_id · State History로 되감기

2Time Travel

checkpoint_id로 과거로 돌아가 · interrupt로 사람이 끼어들기

3장기 메모리

compile(store=) · user_id · 스레드를 넘어 사람을 기억

이제 우리 에이전트는 대화를 이어갈 줄 알고, 과거로 돌아갈 줄 알고, 사람을 기억할 줄 압니다. 혼자서 할 수 있는 일은 거의 다 배운 셈입니다. 남은 것은 "혼자가 아닐 때" — 여러 에이전트가 역할을 나눠 협업하는 Multi Agent가 다음 이야기입니다. 에이전트끼리 무언가를 공유해야 할 때, 그 공유 지점으로 이번 장의 Store가 다시 등장합니다.
