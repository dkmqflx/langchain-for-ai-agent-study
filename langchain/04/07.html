07. RAG: 캐시 임베더로 저장·검색

실습 노트북: 07.ipynb  ·  원문: docs/04.rag.md 2장 Store · Retrieve  ·  난이도: 🟡 중급  ·  선행: 06. Retrieve

이 자료는 실습 노트북(07.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 앞선 04·05·06장에서 따로따로 배운 캐시 임베딩 · Chroma 저장 · 검색기를 이번에는 하나로 이어붙입니다. 이미 만들어 둔 Chroma 데이터베이스를 다시 열어, 실제 문서(ARKK ETF 보유 종목 PDF)를 대상으로 세 가지 방식(similarity_search · score_threshold · MMR)으로 검색해 봅니다. 특히 검색 결과가 0개로 나와 에러가 나는 함정도 직접 만나보고, 왜 그런지까지 파헤칩니다.

이 노트북이 하는 일 RAG 파이프라인은 Load → Split → Embed → Store까지가 "재료 준비", 그다음 Retrieve가 "실제 요리"입니다. 이번 노트북은 재료 준비를 이미 끝냈다고 가정하고, 저장된 재료(벡터 DB)를 다시 꺼내 검색만 집중적으로 연습합니다.
🔍 비유 — 어제 정리해 둔 도서관에 다시 출근하기 어제 온종일 책을 분류하고 서가에 꽂아(=문서를 임베딩해서 Chroma에 저장) 도서관을 완성했다고 해봅시다. 오늘 아침에는 책을 새로 꽂을 필요 없이, 문만 열고 들어가 손님 질문에 맞는 책을 찾아주면 됩니다. 이 노트북이 딱 그 "둘째 날"입니다. 저장은 이미 끝났으니 DB를 열어 검색하는 일에만 집중하죠.
⚠️ 실행 전 준비 이 노트북이 제대로 동작하려면 같은 폴더에 ./chroma_db(저장된 벡터 DB)와 ./cache(임베딩 캐시)가 이미 존재해야 합니다. 보통 05장에서 Chroma.from_documents(...)로 PDF를 저장하며 만들어집니다. 또 임베딩 API를 부르므로 .env의 OPENAI_API_KEY도 필요합니다.

💡 왜 임베더가 검색에도 필요할까? 저장할 때 문서를 벡터로 바꾼 그 "자(척도)"와 똑같은 자로 질문도 벡터로 바꿔야 거리를 잴 수 있기 때문입니다. 질문은 cm 자로 재고 문서는 inch 자로 쟀다면 비교가 안 되겠죠. 그래서 검색 단계에서도 임베더를 다시 넘겨줍니다.

1. 캐시 임베더 다시 준비 — CacheBackedEmbeddings

가장 먼저, 텍스트를 숫자 벡터로 바꿔 줄 임베딩 모델을 준비합니다. 그런데 그냥 OpenAIEmbeddings를 쓰는 대신, 그 위에 캐시(cache) 한 겹을 씌운 CacheBackedEmbeddings를 씁니다. 04장에서 배운 그 "임베딩 절약 장치"예요.

🔍 비유 — 번역가 옆에 놓인 '번역 노트' OpenAIEmbeddings는 유료로 문장을 번역해 주는 번역가입니다(한 문장 번역할 때마다 돈이 나가죠). CacheBackedEmbeddings는 그 번역가 옆에 번역 노트를 하나 붙여 준 것입니다. 새 문장이 오면 노트를 먼저 뒤져 보고, 전에 번역한 적 있으면 노트에서 그대로 베껴 공짜로 즉시 돌려줍니다. 노트에 없을 때만 번역가에게 돈을 주고 맡기죠. 같은 문장을 두 번 임베딩할 때 비용과 시간을 아끼는 이유가 여기 있습니다.
📥 코드
from langchain_openai import OpenAIEmbeddings
from langchain_classic.embeddings import CacheBackedEmbeddings
from langchain_classic.storage import LocalFileStore

underlying_embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

store = LocalFileStore("./cache/")

cached_embedder = CacheBackedEmbeddings.from_bytes_store(
    underlying_embeddings,
    store,
    namespace=underlying_embeddings.model
)

한 줄씩 뜯어보면 이렇습니다.

  • underlying_embeddings — 실제로 돈 받고 일하는 "진짜 번역가". 여기서는 OpenAI의 text-embedding-3-small 모델입니다.
  • store = LocalFileStore("./cache/") — 번역 결과를 적어 둘 "노트"의 물리적 위치. ./cache/ 폴더에 파일로 쌓입니다.
  • namespace=underlying_embeddings.model — 노트에 붙이는 "이름표". 아래 보충 카드에서 왜 필요한지 설명합니다.
  • from_bytes_store(...) — 번역가와 노트를 하나로 묶어 캐시 지원 임베더를 완성합니다.
⚠️ 실행하면 뜨는 경고 — SHA-1 안내 이 셀을 처음 돌리면 아래처럼 경고가 하나 출력됩니다. 에러가 아니라 안내이니 그대로 진행해도 됩니다. 캐시가 텍스트를 저장할 때 만드는 "열쇠(key)"를 기본값인 SHA-1 방식으로 만든다는 뜻입니다.

📘 보충 — namespace는 왜 붙일까?

캐시는 "이 텍스트 → 이 벡터"를 파일로 저장합니다. 그런데 같은 문장이라도 임베딩 모델이 다르면 벡터도 완전히 달라집니다. text-embedding-3-small이 만든 벡터와 text-embedding-3-large가 만든 벡터는 서로 호환되지 않죠.

🔍 비유 — 사물함마다 다른 이름표 한 캐시 폴더를 여러 모델이 공유하면, 이름표가 없을 경우 "small이 넣어 둔 벡터"를 "large가 자기 것인 줄 알고" 꺼내 쓰는 사고가 납니다. namespace는 각 모델에게 따로 이름표가 붙은 사물함 칸을 배정하는 것과 같습니다. 그래서 모델 이름(...small)을 이름표로 씁니다.

2. Chroma DB 열기 — documents= 없이 불러오기

이제 이미 저장돼 있는 벡터 데이터베이스를 엽니다. 여기서 가장 중요한 포인트는 05장에서 저장할 때 쓰던 Chroma.from_documents(...)가 아니라는 점입니다. 이번에는 그냥 Chroma(...)를 쓰고, documents= 인자를 주지 않습니다.

🔍 비유 — 도서관 '새로 짓기' vs '문 열기' Chroma.from_documents(documents=...)는 책을 한 아름 안고 들어가 서가에 꽂으며 도서관을 새로 짓는 일입니다. 반면 이번처럼 documents= 없이 Chroma(persist_directory=경로)만 쓰는 것은 이미 다 지어진 도서관의 문을 열고 들어가 열람만 하는 것입니다. 경로에 데이터가 있으면 그대로 불러오고, 없으면 빈 도서관이 하나 만들어질 뿐 새 책이 자동으로 들어오진 않습니다.
📥 코드
from langchain_chroma import Chroma

CHROMA_PATH = "./chroma_db"


db = Chroma(
    collection_name="rag_collection",
    embedding_function=cached_embedder,
    persist_directory=CHROMA_PATH,
    collection_metadata={"hnsw:space": "cosine"}  # 옵션: "cosine", "l2" (유클리드), "ip" (내적)
)

인자 하나하나가 무엇을 뜻하는지 노트북 저자의 주석을 그대로 풀어 보면 이렇습니다.

인자의미
collection_name DB 안에서 데이터를 담는 "테이블 이름" 같은 개념. 저장할 때 쓴 이름("rag_collection")과 똑같이 맞춰야 그 데이터를 찾습니다.
embedding_function 질문을 숫자로 바꿀 임베더. 앞에서 만든 cached_embedder를 넘깁니다. 즉 "이미 계산한 적 있는 내용은 다시 계산하지 말고 저장해 둔 값을 꺼내 쓰라"는 뜻입니다.
persist_directory 데이터가 저장된(또는 저장될) 폴더 경로. 이 경로에 데이터가 있으면 불러오고, 없으면 나중에 이 폴더에 영구 저장합니다.
collection_metadata {"hnsw:space": "cosine"} — 검색할 때 거리(유사도)를 어떤 방식으로 잴지 정합니다. 여기서는 코사인 유사도를 씁니다.
💡 hnsw:space가 뭐죠? hnsw는 Chroma가 내부적으로 쓰는 고속 검색 알고리즘(Hierarchical Navigable Small World)의 약자이고, space는 "거리를 재는 방식"입니다. 즉 이 설정은 "가장 의미가 가까운 문장을 코사인 유사도로 찾아라"라는 지시입니다.
🔍 비유 — 거리를 재는 세 가지 '자' 두 지점이 얼마나 가까운지 재는 방법은 하나가 아닙니다. 코사인(cosine)은 나침반처럼 "방향이 같은가"만 봅니다(크기 무시). 유클리드(l2)는 줄자처럼 두 점 사이 직선거리를 잽니다. 내적(ip)은 방향과 크기를 모두 고려하죠. 텍스트 의미 검색에서는 보통 코사인이 가장 무난해서 널리 씁니다.
📘 보충 — 노트북에 나온 '주석 가득한' 두 번째 버전

노트북에는 위와 완전히 같은 db = Chroma(...) 코드를 주석으로 상세히 설명한 버전이 한 번 더 나옵니다. 코드 동작은 동일하고, 핵심 메시지는 다음 한 문장입니다.

핵심 — documents= 인자가 없습니다. 즉 새 문서를 추가하려는 게 아니라, 기존에 저장된 데이터를 검색하기 위한 용도로 DB를 여는 것입니다.

3. similarity_search — 가장 단순한 검색

DB를 열었으니 이제 질문을 던져 봅니다. 가장 기본적인 검색은 db.similarity_search(query)입니다. 질문을 벡터로 바꾼 뒤, DB에 저장된 모든 문서와 유사도를 계산해 가까운 순서대로 몇 개를 돌려줍니다.

🔍 비유 — 사서에게 대뜸 질문하기 도서관에 들어가 사서에게 "테슬라 투자 비중이 얼마나 되나요?"라고 물으면, 사서는 그 질문과 가장 관련 있는 자료 몇 개를 자동으로 골라 책상 위에 턱 올려 줍니다. 기본값으로 상위 4개를 가져오는데, 우리는 보통 그중 맨 위(가장 가까운) 자료를 먼저 봅니다.
📥 코드
query = "Tesla 투자 비중이 얼마나 되나요?"
results = db.similarity_search(query)
# 벡터스토어에 있는 문서와 유사도를 계산하고, 유사도가 높은 순서대로 검색 결과를 반환한다

print(len(results))

print(f"검색된 문서 내용:\n{results[0].page_content}")
# 가장 유사한 문서의 내용을 반환한다

4. score_threshold 검색기 — 그리고 흔한 함정

db.as_retriever()를 쓰면 검색 규칙을 정해 둔 "검색기(retriever)" 객체를 만들 수 있습니다. 그중 search_type="similarity_score_threshold"는 "유사도 점수가 일정 기준 이상인 문서만 통과"시키는 방식입니다. 아래에서는 기준(score_threshold)을 0.4로 잡았습니다.

🔍 비유 — 합격 커트라인 score_threshold는 시험의 합격 커트라인입니다. "유사도 점수 0.4점 넘는 문서만 합격시켜 데려와"라는 뜻이죠. 기준을 낮추면 웬만하면 다 합격해 넉넉히 나오고, 기준을 너무 높이면 아무도 못 넘어서 결과가 0개가 될 수 있습니다. 바로 이 지점에서 초보자가 자주 걸려 넘어집니다.
📥 코드
# 검색기 생성
retriever = db.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.4}
    # score_threshold: 유사도 점수가 0.4 이상인 문서만 검색하겠다는 의미
    # 따라서 유사도 점수를 높이면 검색 결과가 없을 수도 있다.
)

results = retriever.invoke(query)

print(len(results))

print(results[0].page_content)
▶ 이렇게 나와요
No relevant docs were retrieved using the relevance score threshold 0.4

0

IndexError: list index out of range

방금 similarity_search로는 4개나 잘 찾았는데, 커트라인 0.4를 걸자마자 "기준 0.4를 넘는 문서가 하나도 없다"는 안내와 함께 len(results)가 0이 되었습니다. 그리고 텅 빈 리스트에서 results[0]을 꺼내려다 IndexError가 터졌죠.

🚨 왜 0개가 됐을까 — 점수의 정체 score_threshold가 재는 relevance score(0~1, 클수록 유사)는 우리가 흔히 상상하는 원점수가 아니라, Chroma가 거리(distance)를 0~1 점수로 환산한 값입니다. 이번 데이터에서는 가장 가까운 문서조차 이 환산 점수가 0.4에 못 미쳤기 때문에 전부 걸러진 것입니다. 즉 문서를 못 찾은 게 아니라, 커트라인을 너무 높게 잡은 것이죠.
⚠️ 두 가지 교훈

① 임계값은 데이터에 맞춰 조정하라. 0.4가 안 나오면 0.2, 0.1처럼 낮춰 보며 적절한 값을 찾습니다. 정답 값은 데이터·모델마다 다릅니다.

② 인덱싱 전에 개수를 확인하라. results[0]처럼 바로 첫 요소를 꺼내기 전에 if len(results) > 0:으로 비었는지 먼저 확인하면 IndexError를 막을 수 있습니다.

📘 보충 — similarity_search는 되는데 왜 여기선 0개?

둘 다 같은 DB를 쓰는데 결과가 다른 이유는 "거르는 기준의 유무"입니다. similarity_search는 커트라인 없이 무조건 가까운 순서대로 상위 N개를 줍니다(점수가 낮아도 일단 줌). 반면 score_threshold 검색기는 "0.4 미만은 버려"라는 필터를 한 겹 더 겁니다. 그래서 같은 문서라도 앞에서는 통과, 뒤에서는 탈락한 것입니다.

5. MMR 검색기 — 비슷하면서도 '다양하게'

마지막은 search_type="mmr"입니다. MMR은 Maximal Marginal Relevance(최대 한계 관련성)의 약자로, "질문과 관련 있으면서도 서로 겹치지 않는(다양한) 문서"를 골라 줍니다. 여기서는 k=3으로 3개를 요청합니다.

🔍 비유 — 뷔페에서 접시 담기 일반 유사도 검색은 "제일 맛있는 요리"만 찾다 보니 같은 파스타를 세 접시 담아 올 수 있습니다(중복). MMR은 "맛있으면서도 서로 다른" 요리를 담습니다 — 파스타 하나, 샐러드 하나, 스테이크 하나처럼요. 덕분에 LLM이 한쪽으로 치우치지 않고 폭넓은 근거로 답할 수 있습니다.
📥 코드
# 검색기 생성
retriever2 = db.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 3,}

)


results2 = retriever2.invoke(query)

print(len(results2))

print(results2[0].page_content)

방식한 줄 요약이번 결과언제 쓰나
similarity_search 커트라인 없이 가까운 순 상위 N개 4개 반환 ✅ 가장 단순·기본. 일단 관련 문서를 보고 싶을 때
score_threshold 점수 커트라인을 넘는 문서만 통과 0개 → IndexError ⚠️ "확실히 관련된 것만" 걸러내고 싶을 때 (임계값 튜닝 필수)
mmr 관련성 + 다양성(중복 제거)으로 k개 3개 반환 ✅ 비슷한 문서 중복을 피하고 폭넓은 근거가 필요할 때

📚 한 장 정리

오늘의 핵심 한 번 저장한 벡터 DB는 documents= 없이 다시 열어 검색만 반복할 수 있고, 검색 방식(기본 · 임계값 · MMR)에 따라 결과의 개수와 다양성이 달라진다.
  • 캐시 임베더 — 검색할 때도 저장할 때와 같은 임베더가 필요하다(같은 자로 재야 비교됨). CacheBackedEmbeddings로 비용까지 아낀다.
  • DB 열기 — Chroma.from_documents()는 "새로 짓기", documents= 없는 Chroma(persist_directory=...)는 "문 열기(불러오기)". collection_name은 저장 때와 똑같이 맞춘다.
  • similarity_search — 커트라인 없이 가까운 순 상위 N개(기본 4개). 가장 단순하고 확실하다.
  • score_threshold — 점수 커트라인 필터. 너무 높으면 0개가 되고, 빈 리스트에 results[0]을 하면 IndexError. 임계값은 데이터에 맞춰 낮춰 보고, 인덱싱 전 len()을 확인하라.
  • MMR — "관련 있으면서 서로 다른" 문서를 k개. 중복을 피해 LLM의 편향을 줄인다.
  • 거리 척도 — hnsw:space로 cosine(방향) · l2(직선거리) · ip(방향+크기) 중 선택. 의미 검색은 보통 cosine.
