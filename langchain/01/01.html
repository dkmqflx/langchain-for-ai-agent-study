01. Model — 텍스트 생성과 구조화된 답변

실습 노트북: 01.ipynb  ·  원문: docs/01.langchain.md 2장 Model  ·  난이도: 🟢 입문

이 자료는 실습 노트북(01.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. LangChain에서 "모델을 만들고, 답을 받아오는" 가장 기본적인 4가지 방법 — 스트리밍(stream) · 배치(batch) · 구조화된 출력(Pydantic · JSON Schema) — 을 비유와 예시로 천천히 풀어봅니다. 코드는 노트북에 있는 그대로 싣되, "왜 이렇게 쓰는지"에 초점을 둡니다.

이 장에서 배우는 것 LLM에게 말을 걸어 답을 받는 방법은 하나가 아닙니다. 상황에 따라 답을 어떻게 받을지(형태·타이밍·개수)를 골라 쓸 수 있어야 합니다. 이 장은 그 "받는 방식의 메뉴판"입니다.
방식한 줄 요약언제 쓰나
stream()답이 만들어지는 즉시 조각조각 받기채팅 UI처럼 체감 속도가 중요할 때
batch()여러 질문을 한 번에 묶어 처리대량 데이터 처리 · 비용/시간 절약
Pydantic 구조화답을 파이썬 객체(정해진 칸)로 강제답을 코드에서 바로 다뤄야 할 때
JSON Schema 구조화답을 JSON(언어 중립) 형태로 강제다른 시스템과 스키마를 공유할 때
⚠️ 실행 전 준비 코드를 직접 돌려보려면 프로젝트 루트에 .env 파일이 있고 그 안에 OPENAI_API_KEY 같은 API 키가 들어 있어야 합니다. 이 교재만 읽을 때는 필요 없습니다.

0. 모델 만들기 — init_chat_model

본격적으로 시작하기 전에, 먼저 "말을 걸 상대(모델)"를 하나 만들어야 합니다. LangChain에서는 딱 한 줄이면 됩니다.

🔍 비유 — 만능 리모컨 세상엔 삼성 TV, LG TV, 소니 TV가 있고 리모컨 버튼 배치가 제각각입니다. 그런데 만능 리모컨 하나만 있으면 어느 TV든 "전원", "볼륨" 버튼 위치가 똑같죠. init_chat_model이 바로 그 만능 리모컨입니다. 속에 있는 모델이 OpenAI든, Anthropic이든, Google이든 우리는 항상 똑같은 버튼(invoke, stream, batch)만 누르면 됩니다. 나중에 모델을 갈아끼워도 우리 코드는 거의 그대로인 이유가 여기 있습니다.
📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from pydantic import BaseModel, Field

# .env 파일에서 환경 변수(OPENAI_API_KEY 등)를 현재 프로세스로 로드
load_dotenv()

# gpt-4o-mini 모델로 ChatModel 객체 생성
# "provider:model" 형태로 공급자를 명시할 수도 있다. 예) init_chat_model("openai:gpt-4o-mini")
model = init_chat_model("gpt-4o-mini")

이제 model은 우리가 계속 말을 걸 상대입니다. 뒤에 나오는 stream, batch, 구조화 출력은 모두 이 model 하나에 서로 다른 방식으로 말을 거는 것뿐입니다.

1. stream() — 답을 흐르듯 받기

가장 단순한 호출은 invoke()입니다. 질문을 던지면 답이 100% 완성될 때까지 기다렸다가 결과를 통째로 돌려줍니다. 반면 stream()은 모델이 글자를 만들어내는 즉시 조각(chunk)을 흘려보냅니다.

🔍 비유 — 물통 vs 정수기 invoke()는 2L 물통에 물을 다 채운 뒤 통째로 건네주는 방식입니다. 다 찰 때까지 손님은 빈손으로 기다려야 하죠. stream()은 정수기입니다. 버튼을 누르면 물이 나오는 즉시 컵으로 받아 바로 마실 수 있습니다. ChatGPT에서 글자가 타닥타닥 흐르듯 나타나는 것이 바로 이 방식이에요. 답이 다 끝나지 않았어도 먼저 나온 부분부터 읽을 수 있어 체감 속도가 훨씬 빠릅니다.
📥 코드
# 답변이 생성되는 즉시 청크 단위로 출력한다.
# end='' 로 지정해 줄바꿈 없이 이어붙여 출력한다.
for chunk in model.stream('Explain about the movie The Truman Show, Reply it briefly'):
  print(chunk.text, end='')
  • 반복문이 한 바퀴 돌 때마다 chunk에는 답의 일부(부분 텍스트)가 담깁니다.
  • 조각의 텍스트는 chunk.text 또는 chunk.content로 꺼냅니다.
  • end=''는 조각 사이에 줄바꿈이 끼지 않도록 이어붙이기 위한 것입니다.
▶ 이렇게 나와요 (예상 출력)
The Truman Show is a 1998 film about a man who slowly realizes his entire
life is a live TV show... (글자가 한 조각씩 실시간으로 이어져 출력됩니다)
💡 핵심 결과물(최종 문장) 자체는 invoke와 같습니다. 다른 건 "받는 타이밍"뿐이에요. 사용자가 화면을 보며 기다리는 상황이라면 stream이 훨씬 좋은 경험을 줍니다.

2. batch() — 여러 질문을 몰아서 한 번에

batch()는 여러 개의 프롬프트를 리스트로 묶어 한 번에 모델에 전달합니다. 하나씩 invoke를 여러 번 부르는 대신, 한 방에 처리하는 것이죠.

🔍 비유 — 카페 주문 팀원 5명의 커피를 사러 갔다고 해봅시다. 카운터에 5번 왕복하며 한 잔씩 주문하면 줄 서고 결제하는 시간이 5배로 듭니다. 대신 "아메리카노 3, 라떼 2 한꺼번에요" 하고 한 번에 주문하면 훨씬 빠르고 편하죠. batch()가 바로 이 "한꺼번에 주문"입니다. 호출 왕복 횟수가 줄어 전체 시간이 짧아지고 비용도 아낄 수 있습니다.
📥 코드
# 여러 프롬프트를 리스트로 묶어 한 번에 전달
inputs = [
  'Explain about the movie The Truman Show',
  'Explain about the movie The Truman Show, Reply it briefly'
]

# 결과는 입력 순서와 동일한 AIMessage 리스트로 반환된다.
for response in model.batch(inputs):
  print(response.content)
💡 순서가 보장됩니다 결과 리스트는 입력 순서와 똑같은 자리에 답을 담아 돌려줍니다. 즉 inputs[0]의 답은 결과의 0번째, inputs[1]의 답은 1번째에 옵니다. 순서가 섞일까 걱정할 필요가 없어요.

실제로 이럴 때 씁니다 — 대량 데이터에 라벨 붙이기, 평가셋(eval)을 한 번에 돌리기, 같은 질문의 A/B 프롬프트 비교 등.

▶ 이렇게 나와요 (예상 출력)
The Truman Show (1998) is a satirical psychological drama directed by Peter Weir...
(긴 설명)

The Truman Show is a 1998 film about a man whose life is secretly a TV show.
(짧은 설명)

3. Structured Output — Pydantic 스키마로 답 형태 강제

지금까지는 답이 자연어 문장이었습니다. 그런데 실제 앱에서는 답을 DB에 저장하거나 다음 단계로 넘기기 위해 정해진 형태의 데이터(객체/JSON)가 필요할 때가 많습니다. "영화를 설명해줘"가 아니라 "제목·감독·개봉연도·장르를 이 칸에 맞춰 채워줘"가 필요한 것이죠.

🔍 비유 — 자유 서술 vs 빈칸 양식지 친구에게 "트루먼 쇼가 어떤 영화야?"라고 물으면 문단으로 줄줄 설명해 줍니다(자연어). 하지만 택배 송장이나 이력서 양식은 다릅니다 — "받는 사람", "주소", "연락처" 칸이 정해져 있고 그 칸을 반드시 채워야 하죠. Structured Output은 LLM에게 이 빈칸 양식지를 건네주는 것입니다. "네 맘대로 문장 쓰지 말고, 이 칸들을 채워서 돌려줘"라고 강제하는 거예요.

구현은 3단계입니다.

1양식 정의

Pydantic 클래스로 어떤 칸이 필요한지 스키마를 만든다

2모델에 씌우기

model.with_structured_output(스키마)로 새 모델을 만든다

3호출

invoke()하면 문장이 아니라 그 객체가 돌아온다

① 양식(스키마) 정의

📥 코드
# 영화 정보를 표현하는 Pydantic 스키마
# - docstring("영화 정보")은 모델 전체에 대한 설명으로 LLM에게 힌트로 전달된다.
# - Field(..., description=...)에서 ...(Ellipsis)는 "이 필드는 필수"라는 뜻이다.
class Movie(BaseModel):
  """영화 정보"""
  title: str = Field(..., description="영화 제목")
  director: str = Field(..., description="감독")
  year: int = Field(..., description="개봉 연도")
  genre: str = Field(..., description="장르")

각 필드의 description은 LLM에게 주는 힌트입니다. "이 칸에는 감독 이름을 넣어"라고 말해주는 라벨이죠. 클래스 맨 위의 docstring("영화 정보")은 양식 전체가 무엇에 대한 것인지 알려줍니다.

② 모델에 씌우고 ③ 호출

📥 코드
# Movie 스키마를 따르도록 모델을 래핑한다.
# 이 시점부터 반환값은 Movie 객체가 된다.
model_with_structured_output = model.with_structured_output(Movie)

# 자연어로 질문해도 결과는 Movie 인스턴스 형태로 돌아온다.
response = model_with_structured_output.invoke("Explain about the movie Truman Show")
print(response)
▶ 이렇게 나와요 (예상 출력)
title='The Truman Show' director='Peter Weir' year=1998 genre='Psychological comedy-drama'

문장이 아니라 Movie 객체가 왔습니다. 이제 response.title, response.year처럼 점(.)으로 각 칸을 바로 꺼내 코드에서 다룰 수 있습니다. 게다가 Pydantic은 year가 정수가 아니면 걸러주는 검증(validation)까지 해줍니다.

📘 보충 — Field(..., description="...")의 ...은 무슨 뜻일까?

Field(..., description="영화 제목")에서 맨 앞의 ...(Ellipsis, 생략 부호)는 Pydantic에서 "이 필드는 필수(Required) 값이다"라고 못 박는 문법입니다.

🔍 비유 — 회원가입 폼의 빨간 별표(*) 회원가입 화면에서 어떤 칸은 빨간 별표(*)가 붙어 "이건 꼭 입력해야 넘어갈 수 있어요"라고 표시되죠. ...이 바로 그 빨간 별표입니다. 반대로 별표가 없는 칸(기본값이 있는 필드)은 비워도 됩니다.

1) 필수 필드 vs 선택 필드

# 필수 — 값을 안 넣으면 에러
title: str = Field(..., description="영화 제목")
# Movie() 로 title 없이 만들면 -> ValidationError!

# 선택 — 안 넣으면 기본값이 자동으로 들어감
title: str = Field("제목 없음", description="영화 제목")

2) 왜 None 대신 ...을 쓰나?

파이썬에서 title: str = None이라고 쓰면 "기본값이 None"이라는 뜻이 되어버립니다(= 선택 필드). "기본값은 없지만 description 같은 메타데이터는 붙이고 싶을 때", Field의 첫 인자에 ...을 넣어 "이건 필수야!"라고 분명히 알려주는 것입니다.

3) LangChain / LLM에서의 역할

구조화 출력에서 ...이 붙은 필드는 LLM에게 "이 정보는 반드시 뽑아내거나 생성해야 해"라고 강제하는 신호가 됩니다. 양식지의 "필수" 칸을 비워두지 못하게 하는 것과 같습니다.

한 줄 요약 ... = "이 값은 필수야, 꼭 넣어줘!" · ... 자리에 다른 값을 넣으면 그게 기본값이 됩니다.

4. Structured Output — JSON Schema 사용

Pydantic 클래스 대신, JSON Schema(딕셔너리)로도 똑같이 출력 형태를 강제할 수 있습니다. 결과가 Pydantic 객체가 아니라 파이썬 딕셔너리(dict)로 온다는 점만 다릅니다.

🔍 비유 — 주민등록증 vs 여권 Pydantic 스키마는 주민등록증 같습니다 — 우리나라(파이썬 세계) 안에서 쓰기엔 가장 편하고 검증도 확실하죠. JSON Schema는 여권 같습니다 — 특정 나라 문서가 아니라 어느 나라(어느 언어·시스템)에서든 통하는 만국 공통 양식입니다. 다른 팀·다른 언어로 만든 시스템과 "이 형태로 주고받자"고 약속할 때 유리합니다.
📥 코드
# 영화 정보 스키마를 JSON Schema(딕셔너리)로 정의
# - "type": "object" → 결과는 객체(딕셔너리) 형태
# - "properties"     → 각 필드의 타입과 설명
# - "required"       → 반드시 포함되어야 하는 필드 목록
movie_json_schema = {
  "title": "Movie",
  "type": "object",
  "properties": {
    "title":    {"type": "string",  "description": "영화 제목"},
    "director": {"type": "string",  "description": "감독"},
    "year":     {"type": "integer", "description": "개봉 연도"},
    "genre":    {"type": "string",  "description": "장르"}
  },
  "required": ["title", "director", "year", "genre"]
}

# JSON Schema도 Pydantic과 동일하게 with_structured_output에 넘길 수 있다.
# 다만 결과는 Pydantic 객체가 아닌 dict로 반환된다.
model_with_json_schema = model.with_structured_output(movie_json_schema)
response = model_with_json_schema.invoke("Explain about the movie Truman Show")
print(response)
▶ 이렇게 나와요 (예상 출력)
{'title': 'The Truman Show', 'director': 'Peter Weir', 'year': 1998, 'genre': 'Drama, Sci-Fi'}

required 목록에 적힌 필드가 아까 Pydantic의 ...(필수)와 같은 역할을 합니다. "빨간 별표"가 여기서는 required 배열로 표현되는 것이죠.

Pydantic vs JSON Schema — 언제 뭘 쓸까?

방식장점단점
Pydantic
(주민등록증)		 파싱 + 데이터 검증까지 지원, 파이썬 객체(.title)로 바로 사용 파이썬 클래스 정의가 필요
JSON Schema
(여권)		 언어 중립적, 다른 시스템과 스키마 공유에 유리 파싱만 지원, 검증은 별도로 해야 함
💡 실전 감각 LangChain 단독 파이썬 프로젝트라면 보통 Pydantic이 더 편합니다(객체로 바로 쓰고 검증까지 됨). 외부 시스템·다른 언어와 스키마를 공유해야 한다면 JSON Schema를 택하세요.

📚 한 장 정리

오늘의 핵심 모델에게 답을 받는 방식은 "언제(타이밍) · 몇 개를(개수) · 어떤 형태로(구조)" 받을지의 선택이다.
  • init_chat_model — 만능 리모컨. 어떤 공급자든 같은 버튼으로 부른다.
  • stream() — 정수기. 답을 조각조각 즉시 받아 체감 속도를 높인다.
  • batch() — 카페 몰아 주문. 여러 입력을 한 번에 처리해 시간·비용을 아낀다(순서 보장).
  • Structured Output — 빈칸 양식지. 자연어 대신 정해진 칸에 답을 채우게 강제한다.
    • Pydantic(주민등록증): 객체 + 검증. ...은 "필수" 별표.
    • JSON Schema(여권): dict + 언어 중립. required가 "필수" 목록.
