Project 2 · 관측 가능한 Agent API 서비스

🟡 중급  ·  ⏱ 1~2주  ·  스택: LangChain 1.x Agent FastAPI Langfuse Multi-LLM LLM-as-judge

02·03에서 배운 Tool · Memory · Middleware · Guardrails · Structured Output을 흩어진 노트북 셀에서 꺼내 하나의 Agent로 조립합니다(STEP 1~4). 그 Agent를 FastAPI로 서빙하고, Langfuse로 전 실행을 추적하고, 모델을 설정으로 갈아끼우고, 마지막으로 프롬프트 A vs B를 숫자로 채점합니다(STEP 5~8). P1에서 만든 RAG는 버리지 않습니다 — 이 Agent의 도구 하나로 그대로 꽂힙니다.

📖 이 문서 사용법 각 STEP은 🎯 목표 → 🧠 개념(왜) → 🛠 할 일(코드) → ✅ 검증 게이트 → 🎓 배우는 것 순서입니다. 검증 게이트를 통과하지 못하면 다음 STEP으로 넘어가지 마세요. Agent는 RAG보다 움직이는 부품이 많아서, 한 STEP을 건너뛰면 "어디서 잘못됐는지" 찾는 데 몇 배의 시간이 듭니다.
⚙️ P1과 무엇이 다른가 — "정해진 길" vs "스스로 고르는 길"

P1의 RAG는 길이 하나뿐인 파이프라인이었습니다. 질문이 들어오면 무조건 검색하고, 무조건 답을 만들었죠. 순서가 코드에 박혀 있으니 예측 가능하고 디버깅도 쉽습니다.

Agent는 다릅니다. "어떤 도구를 쓸지, 몇 번 쓸지, 아예 안 쓸지"를 LLM이 매번 스스로 정합니다. "오늘 며칠이야?"엔 날짜 도구만, "약관에서 분실 책임 찾아줘"엔 P1 검색만, "그거 계산해서 알려줘"엔 두 개를 연달아 씁니다. 같은 코드가 질문에 따라 다르게 흐른다는 뜻이고, 그래서 관측(STEP 6)과 평가(STEP 8)가 선택이 아니라 필수가 됩니다. 길이 하나면 눈으로 따라갈 수 있지만, 길이 매번 달라지면 기록을 남기지 않는 한 무슨 일이 있었는지 알 방법이 없으니까요.

⚠️ 버전 주의 (한 번만 읽어두기) 이 가이드는 LangChain 1.x 기준입니다. Agent 관련 API(create_agent·미들웨어 훅 이름· ToolStrategy)는 1.0에서 새로 정리된 것이라 0.x 시절 블로그 글과 import 경로가 다릅니다. ImportError가 나면 에러 메시지의 모듈명을 그대로 공식 문서에서 검색하세요. Langfuse·ddgs 같은 외부 패키지도 마이너 버전에서 인자 이름이 바뀝니다 — 에러를 읽고 고치는 것까지가 이 프로젝트의 훈련입니다.

✅ 완성 정의 (Definition of Done)

아래가 모두 충족되면 이 프로젝트는 "완성"입니다. STEP들이 이 목록을 하나씩 채워 나갑니다.

  • Agent가 도구 4종(날짜·계산·웹검색·P1 문서검색)을 질문에 따라 스스로 골라 쓴다 STEP 1~2
  • POST /chat에 같은 session_id로 두 번 보내면 두 번째가 첫 번째를 기억한다 STEP 3·5
  • 금지 주제 질문은 LLM에 닿기 전에 차단되고, 차단 사유가 기록된다 STEP 4·6
  • 모든 대화가 Langfuse에 도구 호출별 span 트리 + 토큰·비용·지연으로 남는다 STEP 6
  • 설정 한 줄로 OpenAI ↔ Gemini를 교체할 수 있고, 둘의 비용·지연을 비교한 표가 있다 STEP 7
  • 케이스 10~20개로 프롬프트 A vs B 점수표(도구 선택 정확도·형식 준수·답변 품질)가 나온다 STEP 8
  • README에 문제정의·아키텍처·지표·배운 점이 정리돼 있다 STEP 9

🔗 P1과의 관계 — 왜 굳이 HTTP로 부르는가

P2의 Agent는 P1의 RAG를 도구 하나로 씁니다. 이때 P1의 rag.py를 import하지 않고 POST http://localhost:8000/query를 호출합니다. 조금 번거로워 보이지만 이유가 분명합니다.

비교코드 importHTTP 호출 이 가이드
의존성P1의 무거운 짐(Chroma·리랭커 모델·PDF)이 P2에도 전부 설치돼야 함P2는 requests만 있으면 됨. Agent 서버가 가볍게 뜬다
고장 범위P1이 임포트 시점에 죽으면 P2도 안 뜬다P1이 죽어도 P2는 살아 있고, 그 도구만 "지금 사용 불가"로 응답
배포두 프로젝트가 한 몸이라 항상 같이 배포각자 배포·각자 스케일. 실무의 기본 모양
P3에서P1·P2를 따로 평가하기 어려움둘 다 HTTP 창구가 있어 같은 방식으로 평가된다
💡 이력서에 남는 문장 "RAG 검색을 독립 서비스로 두고, Agent가 이를 도구로 호출하도록 분리해 검색 컴포넌트를 여러 서비스에서 재사용할 수 있게 설계했다." — 이게 토스 공고의 "재사용 컴포넌트" 서사입니다. P1을 그냥 복사해 붙였다면 나올 수 없는 문장이에요.
