06. RAG Retrieve — 검색기 생성

실습 노트북: 06.ipynb  ·  원문: docs/04.rag.md 2.5 Retrieve  ·  난이도: 🟢 입문  ·  선행: 05. RAG Store: Chroma DB

이 자료는 실습 노트북(06.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 앞 장(05)에서 문서를 숫자(벡터)로 바꿔 Chroma DB에 저장까지 마쳤습니다. 이제 드디어 "질문을 던지면 관련 있는 문서를 꺼내오는" 마지막 단계 — Retrieve(검색) 를 배웁니다. 저장된 DB를 다시 열고, as_retriever()로 검색기를 만들고, 세 가지 검색 방식을 비유와 함께 하나씩 실습합니다.

🔍 비유 — 질문을 들고 서가로 가는 도서관 사서 당신이 도서관에서 "테슬라 투자 비중이 궁금해요"라고 물으면, 유능한 사서는 그 질문의 의미를 이해하고 서가로 달려가 관련 있는 책 몇 권을 뽑아 옵니다. Retrieve가 바로 이 사서입니다. 사용자의 질문을 벡터로 바꿔서(임베딩), 저장고(Vector DB)에 꽂혀 있는 수많은 문서 중 의미가 가장 가까운 조각들을 골라 꺼내 옵니다. 그렇게 꺼내온 문서를 LLM에게 함께 건네주면, LLM은 그 근거를 읽고 답을 만들죠. 이것이 RAG의 심장입니다.
이 장에서 배우는 것 "검색"이라고 다 같은 검색이 아닙니다. 가장 비슷한 것 몇 개만 뽑을지, 일정 점수(합격선)를 넘는 것만 뽑을지, 아니면 비슷하면서도 서로 겹치지 않는 다양한 것을 뽑을지 — 상황에 맞는 검색 전략을 고르는 법을 배웁니다.

RAG 5단계 속에서 Retrieve의 자리

RAG 파이프라인은 크게 다섯 단계입니다. 앞의 네 단계(Load·Split·Embed·Store)는 미리 준비해 두는 작업이고, 마지막 Retrieve가 사용자의 질문이 들어올 때마다 실제로 실행되는 검색입니다.

1Load

PDF 등 원문 문서 불러오기

2Split

긴 문서를 청크로 쪼개기

3Embed

청크를 숫자 벡터로 변환

4Store

벡터를 Chroma DB에 저장

5Retrieve

질문으로 유사 문서 검색 ← 오늘

💡 오늘의 위치 1~4단계는 앞 장들에서 이미 끝냈습니다. 이 장은 이미 저장된 DB를 다시 열어, 질문을 던져 문서를 꺼내오는 순수한 "검색" 단계에만 집중합니다. 새로 저장하는 코드는 없습니다.

0. 검색에 쓸 캐시 임베더 준비

검색을 하려면 사용자의 질문도 문서와 똑같은 방식으로 벡터로 바꿔야 합니다. 그래서 저장할 때 썼던 것과 동일한 임베딩 모델을 다시 준비합니다. 여기서는 04장에서 배운 CacheBackedEmbeddings(캐시 임베더)를 그대로 사용합니다.

🔍 비유 — 같은 언어로 물어봐야 알아듣는다 문서를 "영어"로 번역해 서가에 꽂아 놨는데, 검색할 때 질문을 "일본어"로 번역해서 대조하면 전혀 엉뚱한 책이 나옵니다. 질문과 문서는 같은 임베딩 모델(같은 번역기)로 벡터화해야 의미 비교가 제대로 됩니다. 그래서 저장 때 썼던 모델을 검색 때도 똑같이 꺼내 쓰는 거예요. 게다가 캐시 임베더라서, 같은 질문을 또 던지면 이미 계산해 둔 벡터를 재활용해 API 호출을 아낍니다.
📥 코드
from langchain_openai import OpenAIEmbeddings
from langchain_classic.embeddings import CacheBackedEmbeddings
from langchain_classic.storage import LocalFileStore

underlying_embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

store = LocalFileStore("./cache/")

cached_embedder = CacheBackedEmbeddings.from_bytes_store(
    underlying_embeddings,
    store,
    namespace=underlying_embeddings.model
)
  • underlying_embeddings — 실제 임베딩을 계산하는 진짜 모델(OpenAI의 text-embedding-3-small).
  • store — 계산해 둔 벡터를 ./cache/ 폴더에 저장해 두는 캐시 창고.
  • namespace=...model — 캐시 키에 모델 이름을 붙여 다른 모델의 캐시와 섞이지 않게 하는 이름표.
⚠️ 실행하면 뜨는 SHA-1 경고 — 무시해도 됩니다 이 셀을 실행하면 Using default key encoder: SHA-1 is *not* collision-resistant... 라는 노란색 경고(UserWarning)가 뜹니다. 이는 캐시 키를 만드는 기본 해시 함수가 SHA-1이라는 안내일 뿐, 에러가 아니라 정보성 경고입니다. 일반적인 캐시 용도에서는 그대로 두어도 문제없습니다. (보안이 매우 중요하다면 key_encoder로 SHA-256 등을 지정할 수 있다는 힌트입니다.)

1. 기존 Chroma DB 불러오기

05장에서 만들어 둔 저장소를 다시 엽니다. 여기서 가장 중요한 포인트는 documents= 인자가 없다는 점입니다. 문서를 새로 넣는 게 아니라, 이미 저장돼 있는 데이터를 불러와 검색에만 쓰려는 것이기 때문입니다.

🔍 비유 — 새 책을 꽂는 게 아니라, 채워둔 책장을 다시 여는 것 documents=를 넘기는 것은 "이 책들을 책장에 새로 꽂아라"는 지시입니다. 그런데 이번에는 그 인자가 없습니다. 즉 "어제 책을 다 꽂아둔 그 책장을 그대로 다시 열어라"는 뜻이에요. persist_directory로 지정한 폴더에 이미 데이터가 있으면 그걸 그대로 로드하고, 비어 있으면 빈 책장을 새로 준비합니다. 그래서 이 코드만 실행해서는 새 문서가 저장되지 않습니다.
📥 코드
from langchain_chroma import Chroma

CHROMA_PATH = "./chroma_db"


db = Chroma(
    collection_name="rag_collection",
    embedding_function=cached_embedder,
    persist_directory=CHROMA_PATH,
    collection_metadata={"hnsw:space": "cosine"}  # 옵션: "cosine", "l2" (유클리드), "ip" (내적)
)

각 인자가 하는 일을 노트북 주석 그대로 자세히 풀어 보면 이렇습니다.

📥 코드 (주석으로 자세히 설명한 버전)
# 특징: documents= 인자가 없습니다.
# 즉, 새로운 문서를 추가하는 게 아니라 기존에 저장된 데이터를 불러와서 검색하기 위한 용도로 사용합니다.
db = Chroma(
    collection_name="rag_collection",
    embedding_function=cached_embedder,
    # embedding_function: 검색 시 사용자가 던지는 질문(Query)을 숫자로 바꿀 때 사용할 모델입니다.
    # cached_embedder를 사용하면 질문이 이전과 같을 경우 캐시된 값을 재사용합니다.

    persist_directory=CHROMA_PATH,
    # persist_directory: 벡터 데이터가 실제로 저장되어 있는 물리적 경로입니다.
    # 이 경로에 이미 데이터가 있다면 해당 데이터를 로드하고, 없다면 빈 데이터베이스를 초기화합니다.
    # (주의: documents 인자가 없으므로 이 코드 실행만으로는 새로운 문서가 저장되지 않습니다.)

    collection_metadata={"hnsw:space": "cosine"}  # 옵션: "cosine", "l2" (유클리드), "ip" (내적)

    # hnsw: ChromaDB가 내부적으로 사용하는 고속 검색 알고리즘(Hierarchical Navigable Small World)의 약자입니다.
    # space: 검색 공간에서 벡터 간의 '거리'를 측정하는 방식입니다.
    # "cosine"은 벡터 간의 각도를 측정하여 의미적 유사성을 계산하는 가장 일반적인 방식입니다.
)
🔍 비유 — hnsw:space는 "거리를 재는 자(尺) 고르기" 두 지점이 얼마나 가까운지 잴 때, 어떤 자로 재느냐에 따라 결과가 달라집니다. "cosine"은 두 벡터가 가리키는 방향(각도)이 얼마나 비슷한지 재는 자이고(크기는 무시), "l2"는 두 점 사이의 직선거리를 재는 자, "ip"는 내적으로 방향과 크기를 함께 보는 자입니다. 의미 검색에서는 문장 길이(크기)보다 "무슨 뜻을 향하는가(방향)"가 중요하므로 cosine을 가장 많이 씁니다.
📘 보충 — HNSW가 뭐길래 "고속" 검색일까?

DB에 문서가 수십만 개라면, 질문 벡터를 모든 문서와 하나하나 비교하는 건 너무 느립니다. HNSW(Hierarchical Navigable Small World)는 벡터들을 여러 층의 지름길 그물망으로 미리 엮어 두는 기법입니다.

🔍 비유 — 지하철 급행 노선 모든 역에 다 서는 완행으로 목적지까지 가면 오래 걸립니다. HNSW는 급행 노선(상위 층)으로 목적지 근처까지 빠르게 간 뒤, 완행(하위 층)으로 갈아타 정확한 이웃을 찾는 방식이에요. 덕분에 전부 뒤지지 않고도 거의 정확한 결과를 훨씬 빠르게 얻습니다.

우리가 collection_metadata에 넘긴 hnsw:space는 이 그물망이 거리를 어떤 기준으로 잴지를 정해주는 설정입니다.

2. similarity_search() — 가장 기본적인 검색

DB 객체에는 similarity_search()라는 가장 직관적인 검색 메서드가 있습니다. 질문 문자열을 넣으면, DB에 있는 문서들과 유사도를 계산해 가장 비슷한 순서로 결과를 돌려줍니다.

🔍 비유 — "이거랑 비슷한 거 찾아줘" 옷 가게에서 마음에 드는 셔츠를 들고 "이거랑 비슷한 거 보여주세요" 하면, 점원은 색·무늬·핏이 닮은 옷을 가장 비슷한 것부터 차례로 꺼내 옵니다. similarity_search(query)가 딱 이겁니다. 질문과 의미가 가까운 문서 조각을 유사도 높은 순서로 정렬해 돌려줍니다.
📥 코드
query = "Tesla 투자 비중이 얼마나 되나요?"
results = db.similarity_search(query)
# 벡터스토어에 있는 문서와 유사도를 계산하고, 유사도가 높은 순서대로 검색 결과를 반환한다

print(len(results))

print(f"검색된 문서 내용:\n{results[0].page_content}")

3. as_retriever() + score_threshold — 커트라인 검색

similarity_search()는 편하지만, "무조건 상위 몇 개"를 돌려줄 뿐 품질을 거르지는 못합니다. 별로 안 비슷한 문서라도 자리가 남으면 끼워서 돌려주죠. 이때 as_retriever()로 검색기를 만들면서 similarity_score_threshold 타입을 쓰면, 일정 점수를 넘는 문서만 통과시킬 수 있습니다.

🔍 비유 — 합격 커트라인 시험에서 "70점 이상만 합격"이라는 커트라인을 두면, 지원자가 아무리 많아도 기준을 못 넘으면 아무도 못 뽑습니다. score_threshold=0.4는 "유사도 0.4 이상인 문서만 통과"라는 커트라인입니다. 기준을 높게 잡을수록 더 확실히 관련된 문서만 남지만, 너무 높이면 합격자가 0명이 될 수도 있습니다.
📥 코드
# 검색기 생성
retriever = db.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.4}
    # score_threshold: 유사도 점수가 0.4 이상인 문서만 검색하겠다는 의미
    # 따라서 유사도 점수를 높이면 검색 결과가 없을 수도 있다.
)

results = retriever.invoke(query)

print(len(results))

print(results)

결과가 0개(빈 리스트 [])이고, No relevant docs were retrieved...라는 안내가 떴습니다. 이번 데이터·질문 조합에서는 어떤 문서도 유사도 0.4 커트라인을 넘지 못한 것이죠. 에러가 아니라 "기준에 맞는 게 없었다"는 정상적인 결과입니다.

⚠️ 함정 — threshold가 높으면 빈손이 될 수 있다 "정확도를 높이려고 threshold를 올렸는데 검색 결과가 아예 안 나온다"는 상황이 흔합니다. threshold는 낮게 시작해서 조금씩 올리며 적당한 지점을 찾는 게 요령입니다. 2번에서 similarity_search로는 문서가 잘 나왔는데 여기서 0개인 것도, 커트라인이 그만큼 빡빡했기 때문입니다.
📘 보충 — db.similarity_search() vs db.as_retriever()

둘 다 검색을 하지만 쓰임새가 다릅니다.

  • similarity_search() — 그 자리에서 바로 문서를 꺼내오는 일회성 함수 호출. 빠르게 확인할 때 편합니다.
  • as_retriever() — 검색 방식·옵션을 미리 세팅해 둔 재사용 가능한 "검색기 객체(Retriever)"를 만듭니다. .invoke(query)로 실행하죠.

Retriever는 LangChain의 다른 부품(체인·에이전트)에 그대로 끼워 넣을 수 있는 표준 규격이라, 실전 RAG 파이프라인에서는 대부분 as_retriever()를 씁니다.

4. as_retriever() + MMR — 다양성까지 챙기는 검색

일반 유사도 검색의 약점이 하나 있습니다. "가장 비슷한 것"만 뽑다 보니, 거의 똑같은 내용의 문서 조각이 3개 나란히 나오기도 합니다. 근거가 풍부해 보이지만 사실은 같은 말의 반복이죠. mmr(Maximal Marginal Relevance) 타입은 이 문제를 풀어줍니다.

🔍 비유 — 토론 패널을 다양하게 섭외하기 토론회 패널로 가장 실력 있는 전문가 3명을 뽑았는데, 알고 보니 셋 다 똑같은 주장을 하는 사람이라면 토론이 되질 않습니다. 좋은 섭외 담당자는 실력(관련성)도 보면서 서로 관점이 겹치지 않도록(다양성) 뽑죠. MMR이 바로 그 섭외 담당자입니다. "관련 있으면서도 서로 다른" 문서를 골라, LLM이 한쪽으로 치우치지 않게 도와줍니다.
일반 검색 vs MMR — 한 줄 그림
일반 검색: 유사도 Top-K → [A, A', A''] (비슷한 것만, 중복 많음)
MMR 검색 : 유사도 ↑ + 중복 제거 → [A, B, C] (관련 있고 다양함)
📥 코드
# 검색기 생성
retriever2 = db.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 3,}

)


results2 = retriever2.invoke(query)

print(len(results2))

print(results2[0].page_content)

유사도(거리) 측정 방법 정리

1번에서 hnsw:space로 골랐던 "거리를 재는 자"를 표로 정리하며 마무리합니다. 의미 검색에서는 대부분 코사인 유사도를 씁니다.

방법설명특징
코사인 유사도 (Cosine)
"cosine"		두 벡터 사이의 각도를 계산벡터의 크기는 무시하고 방향만 비교. 의미 검색에서 가장 많이 사용
유클리드 거리 (L2)
"l2"		두 점 사이의 직선거리 계산거리가 가까울수록 유사
내적 (Dot Product)
"ip"		한 벡터를 다른 벡터에 투영한 길이의 곱방향과 크기 모두 고려

📚 한 장 정리

오늘의 핵심 Retrieve는 "질문을 벡터로 바꿔 저장고에서 관련 문서를 꺼내오는" RAG의 심장이다. 그리고 어떻게 꺼낼지(검색 전략)는 search_type으로 골라 쓴다.
  • 기존 DB 불러오기 — documents= 없이 persist_directory만 주면, 이미 저장된 데이터를 다시 열어 검색에 쓴다(새 저장 아님).
  • 같은 임베더 사용 — 질문도 문서와 같은 임베딩 모델로 벡터화해야 의미 비교가 맞는다.
  • similarity_search() — "이거랑 비슷한 거." 유사도 높은 순 상위 k개(기본 4개)를 바로 꺼낸다.
  • score_threshold — 합격 커트라인. 점수를 넘는 문서만 통과. 너무 높이면 결과가 0개일 수 있다.
  • mmr — 토론 패널 섭외. 관련성 + 다양성을 함께 고려해 중복을 줄인다 → 편향 없는 답에 유리.
  • hnsw:space — 거리를 재는 자. 의미 검색은 보통 "cosine"(방향 비교).
