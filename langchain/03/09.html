09. Long-term Memory: Store 기본 CRUD

실습 노트북: 09.ipynb  ·  원문: docs/03.advanced-agent.md 3장 Memory  ·  난이도: 🟡 중급

이 자료는 실습 노트북(09.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 앞에서 배운 메모리(메시지 리스트)는 대화방 하나가 닫히면 사라졌습니다. 이번 장에서는 대화방이 바뀌어도, 앱을 껐다 켜도 유지되는 Long-term Memory(장기 기억) — 즉 Store라는 저장 공간에 데이터를 넣고(put) · 꺼내고(get) · 훑어보는(search) 가장 기본적인 CRUD를 비유와 함께 익힙니다.

🔍 비유 — 매번 새로 만나는 상담사 vs 나를 기억하는 단골 카페 지난 장의 "메시지 리스트 메모리"는 한 상담실 안에서만 유효한 기억입니다. 상담이 끝나 방을 나가면 그 대화는 통째로 사라지죠(이게 Short-term). 반면 단골 카페의 직원은 어제 앉았던 자리가 아니어도, 다른 지점에서 만나도 "오늘도 아이스 아메리카노 연하게 드릴까요?"라고 당신을 기억합니다. 이렇게 대화방(스레드)을 넘나들며 유지되는 기억이 바로 Long-term Memory = Store입니다.
이 장에서 배우는 것 LangGraph의 InMemoryStore를 만들어, 사용자 정보를 namespace(폴더) + key(파일명) 구조로 저장(put)하고, 특정 항목을 꺼내오고(get), 폴더 전체를 훑어봅니다(search). 여기서 만든 Store는 다음 노트북에서 Agent(모델)에게 통째로 주입되어 개인화 답변의 재료가 됩니다.

Short-term vs Long-term — 두 기억을 구분하기

구분저장 도구유지 범위비유
Short-term Checkpointer 한 대화 스레드(thread_id) 안에서만 상담실 하나 안에서만 통하는 기억
Long-term Store 여러 대화방 공통 (user_id/namespace 기반) 어느 지점에서 만나도 나를 아는 단골 카페

예를 들어 "이 사용자는 짧은 응답을 선호한다", "이전에 자기 이름이 Jay라고 말했다" 같은, 대화 하나로 끝나면 아까운 정보를 Store에 담아두면 다음에 다시 만났을 때도 써먹을 수 있습니다.

Store의 두 축 — namespace(폴더)와 key(파일명)

Store에 데이터를 넣을 때는 항상 어디에(namespace) · 무슨 이름으로(key) · 어떤 내용을(value) 이 세 가지를 함께 정해줍니다. 가장 직관적인 비유는 컴퓨터의 파일 시스템입니다.

🔍 비유 — 폴더와 파일 namespace는 폴더 경로입니다. 예를 들어 사용자_001 / 개인비서처럼요. 그 폴더 안에 key라는 파일 이름으로 실제 내용(value)을 저장합니다. memory_001.txt 같은 파일을 폴더에 넣는 셈이죠. 폴더 경로를 튜플(("user_001", "personal_assistant"))로 만드는 이유는 여러 사용자·여러 앱의 데이터가 서로 섞이거나 충돌하지 않게 칸막이를 치기 위해서입니다.
개념설명파일 시스템 비유예시
namespace 폴더 경로 (튜플로 구성 — 충돌 방지) 폴더 (디렉터리) ("user_001", "personal_assistant")
key 각 메모리 항목의 고유 식별자 파일 이름 "memory_001"
value 실제로 저장하는 내용 (딕셔너리) 파일 내용 {"facts": [...], "language": "Korean"}

이 장에서 다루는 3개의 메서드

메서드하는 일CRUD파일 시스템 비유
store.put(namespace, key, value)데이터 저장 (없으면 생성, 있으면 덮어쓰기)Create / Update폴더에 파일 저장하기
store.get(namespace, key)특정 key 하나를 콕 집어 조회Read파일 하나 열어보기
store.search(namespace)namespace 안의 모든 항목을 훑어보기Read (전체)폴더 열어 파일 목록 보기
⚠️ InMemoryStore는 "임시" 저장소입니다 이름 그대로 InMemoryStore는 데이터를 메모리(RAM)에만 담아둡니다. 화이트보드와 같아서, 프로그램을 끄면 적어둔 내용이 전부 지워집니다. 실제 서비스에서는 이 자리를 PostgreSQL·Redis 같은 진짜 DB(영구 노트)로 바꿔 끼웁니다. 배우기엔 화이트보드가 편하고, 인터페이스(put/get/search)는 DB로 바꿔도 똑같습니다.

0. 환경 준비

먼저 환경 변수를 불러오고 모델을 하나 선언합니다. 사실 이번 노트북에서 모델(model)은 아직 등장만 하고 직접 쓰이지는 않습니다. 이 장의 주인공은 모델이 아니라 Store이기 때문이에요. 모델과 Store가 실제로 손을 잡는 장면은 다음 노트북(10. 메모리 주입)에서 나옵니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent


# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")
💡 지금은 밑그림만 tool, create_agent도 함께 import 했지만 이번 장에선 쓰지 않습니다. "장기 기억을 가진 Agent를 만든다"는 큰 그림의 부품을 미리 꺼내 둔 것으로 보면 됩니다. 여기서는 순수하게 Store에 데이터를 넣고 빼는 연습에만 집중하세요.

1. Store 만들기 & namespace 정의

가장 먼저 빈 저장소를 하나 만들고, 데이터를 담을 폴더 경로(namespace)를 정합니다. 아직 아무것도 넣지 않았으니, 이름표만 붙인 빈 폴더를 준비하는 단계라고 생각하면 됩니다.

🔍 비유 — 새 서랍장과 라벨 붙이기 InMemoryStore()는 텅 빈 서랍장을 하나 새로 사는 것입니다. 그리고 namespace = (user_id, application_context)는 서랍 한 칸에 "user_001의 개인비서용"이라는 라벨을 붙이는 일이에요. 라벨을 두 단어(튜플)로 만든 덕분에, 나중에 user_002가 와도, 같은 사용자의 다른 앱이 와도 서랍이 또렷이 구분됩니다.
📥 코드
from langgraph.store.memory import InMemoryStore

# 1. Store 초기화
store = InMemoryStore()

user_id = "user_001"
application_context = "personal_assistant"

# 2. Namespace(폴더 경로) 설정
namespace = (user_id, application_context)
💡 namespace는 왜 튜플일까? ("user_001", "personal_assistant")처럼 여러 조각을 튜플로 이으면 계층 구조(폴더/하위폴더)가 생깁니다. user_001이라는 큰 서랍 안의 personal_assistant 칸, 이런 식이죠. 사용자별·앱별로 메모리를 깔끔하게 격리할 수 있어 다른 사용자의 정보가 섞여 나올 걱정이 없습니다.

2. store.put() — 데이터 저장 (Create)

이제 준비한 폴더에 실제 메모리를 저장해봅니다. put은 인자 세 개를 받습니다 — 어디에(namespace), 무슨 이름으로(key), 어떤 내용을(value 딕셔너리).

1namespace

저장할 폴더 경로 (어느 서랍에)

2key

이 항목의 고유 이름 (어떤 파일명으로)

3value

실제 내용 딕셔너리 (무엇을)

① 첫 번째 메모리 저장

📥 코드
# 3. 첫 번째 데이터 저장
store.put(
    namespace,
    "memory_001",  # 이 데이터의 고유 식별자 (Key)
    {
        "facts": [
            "사용자는 커피보다 차를 선호함",
            "사용자는 매일 아침 6시에 일어남",
        ],
        "language": "Korean",
    },
)

value는 자유로운 딕셔너리입니다. 여기서는 사실 목록(facts)과 선호 언어(language)를 담았지만, 형식이 정해져 있지 않아 원하는 구조로 자유롭게 넣을 수 있습니다.

② 두 번째 메모리 저장 — key를 꼭 다르게

⚠️ 같은 key로 저장하면 덮어쓰기(overwrite) put은 같은 파일명에 다시 저장하면 기존 내용을 지우고 새로 씁니다. 그래서 새 정보는 반드시 새 key("memory_002")로 저장해야 앞서 넣은 "memory_001"이 사라지지 않습니다. 같은 이름의 파일을 저장하면 이전 파일이 사라지는 것과 똑같은 원리예요.
📥 코드
# 4. 두 번째 데이터 저장
store.put(
    namespace,
    "memory_002",  # 이전 데이터가 덮어씌워지지 않도록 새로운 Key 지정
    {
        "facts": [
            "사용자는 그림 회화 작품을 좋아함",
            "빈센트 반 고흐의 작품을 특히 좋아함",
        ]
    },
)

이제 ("user_001", "personal_assistant") 폴더 안에는 memory_001, memory_002 두 개의 파일이 나란히 놓였습니다. 참고로 두 번째 value에는 language 없이 facts만 넣었는데, 앞서 말했듯 value의 구조는 항목마다 달라도 상관없습니다.

3. store.get() · store.search() — 조회 (Read)

저장했으니 이제 꺼내 볼 차례입니다. 꺼내는 방법은 두 가지입니다 — 파일 하나를 콕 집어 여는 get과, 폴더를 통째로 열어 안의 파일을 전부 훑는 search입니다.

🔍 비유 — 파일명으로 열기 vs 폴더 통째로 열기 get은 파일명을 정확히 알 때 "그 파일 하나만 딱 열어줘"라고 말하는 것입니다 (namespace + key 둘 다 필요). search는 파일명을 몰라도 "이 폴더 안에 뭐가 들어 있는지 전부 보여줘"라고 하는 것이죠 (namespace만 있으면 됨). 그래서 get은 항목 하나를, search는 목록(리스트)을 돌려줍니다.
💡 꺼낸 결과는 Item 객체 — 알맹이는 .value get/search가 돌려주는 것은 순수한 딕셔너리가 아니라 Item이라는 포장 상자입니다. 상자 겉면에는 key, namespace, 만든 시각(created_at), 수정 시각(updated_at) 같은 꼬리표(메타데이터)가 붙어 있고, 우리가 넣은 진짜 내용은 item.value 안에 들어 있습니다. 그래서 아래 코드도 item1.value처럼 .value로 알맹이를 꺼냅니다.
📥 코드
# 특정 Key 조회 (get)
item1 = store.get(namespace, "memory_001")
# print(item1)
print("1번 메모리:", item1.value)

item2 = store.get(namespace, "memory_002")
print("2번 메모리:", item2.value)

# Namespace 전체 검색 (search)
print("\n--- 전체 검색 결과 ---")
items = store.search(namespace)
# print(items)
for item in items:
    print(f"Key: {item.key} | Value: {item.value}")

출력을 세 덩어리로 나눠 읽어봅시다.

  • 1번·2번 메모리 — get으로 특정 key 하나씩 꺼내 .value(알맹이)만 깔끔하게 출력한 결과입니다.
  • 전체 검색 결과(리스트) — search가 돌려준 날것 그대로의 모습입니다. Item(...) 두 개가 리스트에 담겨 있고, 각 상자에 key·value·created_at 같은 꼬리표가 다 보입니다.
  • Key / Value 줄 — 그 리스트를 for로 하나씩 돌며 필요한 item.key와 item.value만 뽑아 보기 좋게 정리한 것입니다. 실제 코드에서 메모리를 활용할 때 쓰는 전형적인 패턴이에요.
💡 created_at · updated_at · score는? created_at/updated_at은 항목을 언제 만들고 고쳤는지 자동으로 붙는 시각 도장입니다. score는 의미 기반 검색(semantic search)을 했을 때의 유사도 점수 자리인데, 지금처럼 namespace 전체를 그냥 훑는 경우엔 관련 없어 None으로 나옵니다.

📚 한 장 정리

오늘의 핵심 Long-term Memory(Store)는 대화방을 넘나들며 유지되는 파일 시스템이다 — namespace(폴더) + key(파일명)로 정리하고, put(저장) · get(조회) · search(전체 훑기)로 다룬다.
  • Short-term vs Long-term — 스레드 안에서만 남는 Checkpointer vs 대화방을 넘나드는 Store(단골 카페의 기억).
  • 구조 = 폴더 + 파일 — namespace(튜플, 충돌 방지)가 폴더, key가 파일명, value(딕셔너리)가 내용.
  • put — 저장. 같은 key면 덮어쓰기되니 새 정보는 새 key로.
  • get — namespace + key로 항목 하나를 콕 집어 조회. 알맹이는 .value.
  • search — namespace만으로 폴더 안 전체 목록(Item 리스트)을 조회.
  • InMemoryStore는 임시(화이트보드) — 실서비스에선 PostgreSQL·Redis로 교체하되 인터페이스는 동일.
  • 다음 단계 — 여기서 만든 Store를 Agent(모델)에게 주입하면, 모델이 이 기억을 참고해 개인화된 답변을 한다.
