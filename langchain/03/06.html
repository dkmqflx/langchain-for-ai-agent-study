06. Custom Guardrails — After Agent: 출력 필터

실습 노트북: 06.ipynb  ·  원문: docs/03.advanced-agent.md 2장 Guardrails  ·  난이도: 🟡 중급  ·  선행: 05. 메시지 객체와 .type

이 자료는 실습 노트북(06.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. Agent가 답을 만들어냈다고 해서 그걸 무조건 사용자에게 보여줘야 하는 건 아닙니다. 이 장에서는 답이 완성된 직후·화면에 나가기 직전에 그 답을 검사해서, 문제가 있으면 살짝 바꿔 내보내는 After Agent Guardrail(출력 필터)을 만들어봅니다. 예시는 "정답을 그냥 알려달라"는 학생에게 정답을 흘리지 않도록 감시하는 교육용 튜터입니다.

🔍 비유 — 생방송 지연 송출(방송 딜레이) TV 생방송은 사실 "진짜 실시간"이 아닙니다. 대개 몇 초의 지연을 두고 내보내죠. 그 몇 초 사이에 출연자가 욕설이나 부적절한 말을 하면, 방송으로 나가기 직전에 삐- 소리로 덮어버립니다. After Agent Guardrail이 바로 그 "몇 초의 지연"입니다. AI는 이미 답을 다 만들었지만(=말은 이미 했지만), 그 답이 사용자 화면에 도착하기 직전에 한 번 더 검사해서, 위험하면 다른 말로 바꿔 내보내는 안전장치예요.

Guardrail(가드레일)은 도로 옆의 "가드레일"처럼, Agent가 선을 넘지 않도록 막아주는 안전 난간입니다. 가드레일은 언제 개입하느냐에 따라 두 종류로 나뉩니다.

BBefore Agent

사용자 질문이 LLM에 도달하기 전에 거른다 (입력 필터)

AAfter Agent

LLM이 답을 만든 직후, 사용자에게 보이기 전에 검사한다 (출력 필터)

이 노트북의 주제는 오른쪽, After Agent입니다. Before가 "문 앞에서 손님을 돌려보내는 것"이라면, After는 "손님이 안에서 만든 결과물을 나가는 문에서 한 번 더 검사하는 것"에 가깝습니다.

이 장에서 배우는 것 "출력을 검사한다"는 건 결국 또 다른 LLM(감시자)에게 답을 읽혀 판정을 받는 것입니다. 메인 AI가 쓴 답을 감시자 AI가 읽고 "LEAKED"(정답 유출) 또는 "SAFE"(안전)로 채점한 뒤, 유출이면 답을 힌트로 바꿔치기합니다. 그 전체 배관을 @after_agent 미들웨어로 연결합니다.

Before vs After — 언제 무엇을 쓸까

같은 "가드레일"이라도 Before와 After는 성격이 꽤 다릅니다. 한쪽은 싸고 빠른 문지기, 다른 한쪽은 비싸지만 꼼꼼한 검수관입니다.

🔍 비유 — 입국 심사 vs 세관(출국) 검사 Before Agent는 입국 심사대입니다. 아예 들여보낼지 말지를 문 앞에서 판단하죠. 규칙(여권·비자)만 보면 되니 빠르고 저렴합니다. After Agent는 세관 검사입니다. 이미 안에서 만들어진 짐(답변)을 내보내기 직전에 열어보고 문제가 있으면 압수·교체합니다. 짐을 하나하나 뜯어봐야 하니 시간과 비용이 더 들지만, 규칙만으로는 못 잡는 미묘한 문제까지 잡아냅니다.
특징Before Agent (입력 필터)After Agent (출력 필터)
작동 시점질문이 LLM에 도달하기 직전LLM이 답을 생성한 직후 (화면에 나가기 전)
주 목적비용 절감, 보안(PII), 정책 위반 차단품질 관리, 환각 방지, 답변 안전성 검증
방식주로 규칙 기반 (키워드·정규식)주로 모델 기반 (감시자 LLM에게 평가 요청)
비용매우 저렴 (LLM 호출 자체를 막음)추가 비용 (메인 LLM + 감시자 LLM)
속도매우 빠름감시자가 검사하는 만큼 느려짐
💡 한 줄 감각 Before는 "키워드로 걸러도 되는 뻔한 문제"(예: 욕설·개인정보)에, After는 "읽어봐야 알 수 있는 미묘한 문제"(예: 정답을 은근슬쩍 흘렸는지)에 씁니다. 이번 예시가 딱 후자예요.

1. 감시자 모델과 @after_agent 미들웨어 정의

이 장의 핵심입니다. 두 가지를 만듭니다 — (1) 답을 채점할 감시자 모델(safety_model)과, (2) 답이 나온 직후 그 감시자를 불러 검사·개입하는 미들웨어(answer_leakage_guardrail).

🔍 비유 — 기자와 편집장(데스크) 신문사에서 기자(메인 Agent)가 기사 초고를 씁니다. 그런데 그 초고가 그대로 신문에 실리지는 않아요. 편집장(감시자 모델)이 먼저 읽고 "이건 내보내면 안 돼"라고 판단하면 문장을 고쳐서 내보냅니다. safety_model이 바로 이 편집장입니다. 메인 Agent가 아무리 답을 잘(?) 써도, 편집장이 통과시켜야만 독자(사용자)에게 도착합니다.

① 감시자 모델을 하나 더 만든다

메인 Agent와는 별개의 LLM을 하나 더 준비합니다. 이 모델의 유일한 임무는 "튜터의 답이 정답을 흘렸는지"를 판정하는 것뿐이라, 판사(Judge)·감독관 역할이라고 부릅니다.

② 미들웨어 안에서 3단계로 검사한다

미들웨어 함수 하나가 다음 세 가지 일을 순서대로 합니다.

1유효성 검사

마지막 메시지가 정말 AI의 답(AIMessage)인지 확인. 아니면 그냥 통과

2감시자에게 평가

튜터의 답을 auditor_prompt에 담아 감시자에게 채점 요청 → LEAKED / SAFE

3개입(교체)

LEAKED면 last_message.content를 힌트 문장으로 덮어쓴다

📥 코드
from langchain.agents.middleware import after_agent
from langchain.chat_models import init_chat_model
from langchain.messages import AIMessage

# 평가용 판사(Judge) 모델 초기화
safety_model = init_chat_model("gpt-5-mini")

@after_agent
def answer_leakage_guardrail(state, runtime) :
    """
    AI가 답변을 생성한 '직후', 사용자에게 보여주기 전에 내용을 검사.
    만약 AI가 문제의 정답을 직접적으로 말해버렸다면, 이를 감지하고 수정.
    """

    # 1. 메시지 유효성 검사
    if not state["messages"]: return None
    last_message = state["messages"][-1]

    # 마지막 메시지가 AI의 답변이 아니면 검사할 필요 없음
    if not isinstance(last_message, AIMessage):
        return None

    # 2. 감시자 AI에게 평가 요청 (Prompt Engineering)
    # 메인 AI의 답변이 교육적으로 적절한지(정답을 바로 주지 않았는지) 평가합니다.
    auditor_prompt = f"""
    당신은 엄격한 교육 감독관입니다.
    다음 '튜터의 답변'을 확인하세요.
    답변이 학생을 지도하지 않고 문제의 정답이나 전체 풀이를 직접적으로 제공한다면 'LEAKED'라고 답하세요.
    답변이 적절한 힌트나 설명을 제공한다면 'SAFE'라고 답하세요.

    튜터의 답변: {last_message.content}
    """

    result = safety_model.invoke([{"role": "user", "content": auditor_prompt}])

    # 3. 결과에 따른 개입 (Intervention)
    if "LEAKED" in result.content:
        print(f"🚨 [가드레일 발동] 정답 유출 감지됨! 답변을 수정합니다.")
        last_message.content = "앗, 제가 정답을 바로 말할 뻔했네요! 😅 정답보다는 푸는 방법을 먼저 생각해볼까요? 이 문제의 핵심 개념은..."

    return None

코드를 위에서 아래로 따라가며, 세 단계가 어떻게 이어지는지 하나씩 풀어보겠습니다.

1단계 — 마지막 메시지가 AI의 답인지 확인

state["messages"]에는 지금까지의 대화 전체가 리스트로 들어 있습니다. 우리가 검사할 대상은 가장 마지막에 붙은 AI의 답이므로 [-1]로 꺼냅니다. 그런데 마지막 메시지가 사람의 질문이거나 도구 호출 기록일 수도 있죠. 그래서 isinstance(last_message, AIMessage)로 "이게 진짜 AI가 만든 답이 맞나?"를 먼저 확인하고, 아니면 return None으로 아무 일도 하지 않고 넘어갑니다.

💡 return None은 "그냥 통과"라는 뜻 미들웨어가 None을 돌려주면 "나는 아무것도 바꾸지 않을게, 원래 흐름대로 가"라는 신호입니다. 검사할 필요가 없거나(문제 없음) 대상이 아니면 항상 조용히 None으로 빠져나옵니다.

2단계 — 감시자에게 채점을 맡긴다

튜터의 답(last_message.content)을 통째로 auditor_prompt라는 지시문 안에 끼워 넣습니다. 지시문의 내용은 간단합니다 — "너는 엄격한 감독관이야. 이 답이 정답을 그냥 알려줬으면 LEAKED, 힌트만 줬으면 SAFE라고만 대답해." 그리고 이 프롬프트를 감시자 모델(safety_model)에게 invoke합니다. 감시자는 답을 읽고 두 단어 중 하나로 판정을 내려줍니다.

🔍 비유 — 채점표에 O/X만 찍게 하기 감시자에게 "이 답 어때? 자유롭게 평가해줘"라고 하면 장황한 감상문이 돌아옵니다. 그래서 우리는 답안을 딱 두 개(LEAKED / SAFE)로 좁혀 채점표처럼 만듭니다. 그래야 다음 단계에서 if "LEAKED" in result.content처럼 기계적으로 분기할 수 있으니까요. "서술형 대신 O/X로만 답해줘"라고 못 박는 것이 핵심 요령입니다.

3단계 — 유출이면 답을 힌트로 덮어쓴다

감시자의 판정문에 "LEAKED"라는 글자가 들어 있으면, 정답이 새어 나간 것으로 봅니다. 이때 last_message.content = "앗, 제가 정답을 바로..."처럼 답의 내용 자체를 교육적인 힌트로 바꿔치기합니다. 사용자는 원래의 "빗변은 5" 같은 정답 대신, "같이 풀어볼까요?"라는 힌트를 받게 됩니다.

⚠️ 핵심 포인트 — 원본 객체를 직접 수정한다 이 코드는 새 메시지를 만들어 반환하는 게 아니라, 이미 리스트에 들어 있는 last_message의 .content를 그 자리에서 고쳐씁니다. 파이썬에서 last_message는 리스트 속 실제 객체를 가리키므로, 이렇게 바꾸면 state의 그 메시지도 함께 바뀝니다. 그래서 마지막에 return None만 해도 교체된 답이 사용자에게 전달됩니다.

2. Agent에 장착하고 실제로 실행하기

이제 만든 미들웨어를 create_agent의 middleware=[...]에 끼워 넣습니다. 그러면 이 Agent가 답을 낼 때마다 자동으로 감시자 검사가 붙습니다. 실험을 위해 학생이 대놓고 정답을 요구하는 짓궂은 질문을 던져봅니다.

Human
직각삼각형 두 직각변이 3과 4면 빗변 길이가 뭐야? 너무 어려워, 그냥 정답 알려줘 ← 정답을 직접 요구
AI(초안)
빗변은 5입니다. (3²+4²=25, √25=5) ← 정답을 흘림 → 감시자가 LEAKED 판정
AI(교체)
앗, 제가 정답을 바로 말할 뻔했네요! 😅 … 핵심 개념은… ← 가드레일이 힌트로 바꿔 내보냄
📥 코드
agent = create_agent(
    model="gpt-5-nano",
    tools=[],
    middleware=[answer_leakage_guardrail],
)
agent.invoke({
    "messages": [{"role": "user", "content": "직각 삼각형 두 직각변의 길이가 3과 4라면 빗변의 길이가 뭐야? 이 문제 너무 어려워. 그냥 정답 알려줘."}]
})
▶ 이렇게 나와요 (실제 출력)
🚨 [가드레일 발동] 정답 유출 감지됨! 답변을 수정합니다.

{'messages': [
  HumanMessage(content='직각 삼각형 두 직각변의 길이가 3과 4라면 빗변의 길이가 뭐야? 이 문제 너무 어려워. 그냥 정답 알려줘.', ...),
  AIMessage(content='앗, 제가 정답을 바로 말할 뻔했네요! 😅 정답보다는 푸는 방법을 먼저 생각해볼까요? 이 문제의 핵심 개념은...',
            response_metadata={'model_name': 'gpt-5-nano-2025-08-07', ...},
            usage_metadata={'input_tokens': 46, 'output_tokens': 492, 'total_tokens': 538, ...})
]}

출력을 읽어봅시다. 먼저 🚨 [가드레일 발동] 줄이 찍혔습니다 — 감시자가 LEAKED로 판정해 3단계 개입이 실행됐다는 증거입니다. 그리고 최종 반환된 messages의 마지막 AIMessage를 보면, 원래 있었을 "빗변은 5" 같은 정답이 완전히 사라지고 힌트 문장으로 교체돼 있습니다. 사용자는 이 교체된 답만 보게 됩니다.

💡 재미있는 관찰 — 토큰은 정답을 만드는 데 이미 썼다 usage_metadata를 보면 출력 토큰이 492개나 잡혀 있습니다(정답 초안을 생성하느라 쓴 것). 즉 메인 AI는 이미 정답을 다 만들었고, 우리는 그걸 나중에 덮어쓴 것뿐입니다. After 방식이 "추가 비용이 든다"는 말의 의미가 여기서 드러납니다 — 메인 답변 생성 비용 + 감시자 호출 비용이 모두 들었죠. 그럼에도 미묘한 유출을 잡는 확실함 때문에 이 비용을 감수하는 것입니다.

응용 — 그냥 차단 말고, 힌트를 새로 "생성"하기

위 예시는 유출을 감지하면 미리 준비해 둔 고정 문장으로 바꿨습니다. 간단하지만 매번 똑같은 말이 나오죠. 한 걸음 더 나아가, 감시자(또는 교정 모델)에게 "이 질문에 맞는 힌트를 새로 만들어줘"라고 시켜 매번 질문에 어울리는 맞춤 힌트를 생성하게 할 수도 있습니다. (원문 docs의 2.2.3 응용 예시)

🔍 비유 — 압수 후 "대체품"을 새로 건네기 세관에서 반입 금지 물품을 압수했다고 그냥 빈손으로 돌려보내면 손님이 곤란하겠죠. 여기서는 압수(정답 차단)에 그치지 않고, 그 자리에서 허용되는 대체품(맞춤 힌트)을 새로 만들어 손에 쥐여줍니다. 소크라테스식 튜터에게 "정답 말고 스스로 생각하게 유도하는 질문만 던져줘"라고 시키는 방식입니다.
📥 코드 (개념 예시)
if "LEAKED" in result.content:
    # 원본 질문을 가져오기 (문맥 파악용)
    original_question = state["messages"][0].content

    # 교정 프롬프트
    correction_prompt = f"""
    절대 정답을 말하지 말고, 학생이 스스로 생각할 수 있도록 유도하는 질문이나 핵심 개념(힌트)만 설명해 주세요.
    사용자 질문: {original_question}
    """
    corrected_response = safety_model.invoke([
        SystemMessage(content="당신은 소크라테스식 교육을 사용하는 튜터입니다."),
        HumanMessage(content=correction_prompt)
    ])
    last_message.content = corrected_response.content

차이는 마지막 줄 하나입니다. 고정 문장 대신 교정 모델이 방금 생성한 힌트로 답을 덮어씁니다. "차단"에서 "차단 + 재생성(교정)"으로 한 단계 업그레이드된 것이죠.

다중 레이어 방어 — 가드레일 쌓기

가드레일은 하나만 써야 하는 게 아닙니다. middleware=[...] 리스트에 여러 개를 나열하면, 요청이 그 레이어들을 순서대로 통과하며 각 단계에서 검사를 받습니다.

🔍 비유 — 공항의 여러 겹 검문 공항은 안전을 위해 검문을 한 번만 하지 않죠. 신분 확인 → 짐 검색 → 몸수색 → 탑승구 재확인처럼 여러 관문을 겹겹이 둡니다. 앞 관문이 놓친 걸 뒤 관문이 잡아냅니다. 가드레일도 똑같이 층층이 쌓아(layered) 방어막을 만듭니다. 이번 장의 출력 필터는 그 여러 겹 중 가장 마지막 관문(출국 직전 검사)에 해당합니다.
📘 심화 — 리스트에 쌓는 레이어 방어막
📥 코드 (개념 예시)
agent = create_agent(
    model="gpt-5-nano",
    tools=[],
    middleware=[
        education_guardrail,              # Layer 1: 입력 필터 (규칙 - 부정행위 차단)
        student_safety_middleware,        # Layer 2: 개인정보 보호 (전화번호 마스킹)
        counseling_escalation_middleware, # Layer 3: 상담 이관 (휴먼 에스컬레이션)
        answer_leakage_guardrail,         # Layer 4: 출력 필터 (모델 기반 교정) ← 이 장
    ],
)

미들웨어는 리스트에 적힌 순서대로 실행됩니다. 앞쪽은 대개 값싸고 빠른 입력 필터(Before), 뒤쪽은 꼼꼼한 출력 필터(After)를 두는 게 일반적입니다. 싸고 빠른 검사로 먼저 걸러내고, 통과한 것만 비싼 검사로 넘기는 효율적인 순서죠.

📚 한 장 정리

오늘의 핵심 After Agent Guardrail은 "AI가 답을 다 만든 뒤, 사용자에게 나가기 직전에 감시자 LLM으로 검사하고 문제가 있으면 답을 바꿔치기하는" 출력 필터다. 방송 딜레이의 삐- 처리와 같다.
  • 작동 시점 — 답 생성 직후, 화면에 나가기 전. @after_agent 데코레이터로 건다.
  • 감시자 모델(safety_model) — 메인 AI와 별개의 LLM(편집장). 답을 읽고 LEAKED/SAFE로 채점.
  • 3단계 흐름 — ① AIMessage인지 확인 → ② auditor_prompt로 감시자에게 채점 요청 → ③ LEAKED면 last_message.content를 힌트로 덮어쓰기.
  • 원본 객체 수정 — 새 메시지를 반환하는 게 아니라 리스트 속 메시지의 .content를 직접 고친다. 그래서 return None이어도 반영된다.
  • Before vs After — Before(입국 심사)는 규칙 기반·저렴·빠름, After(세관)는 모델 기반·추가 비용·미묘한 문제 탐지.
  • 응용 & 레이어 — 고정 문장 대신 힌트를 재생성(교정)할 수 있고, 여러 가드레일을 리스트에 쌓아 겹겹이 방어할 수 있다.
