LangGraph 학습 후, 실무 프로젝트 3선

대상: LangGraph 01~05 + P1~P3를 마친 사람  ·  기간: 약 5~7주  ·  목적: AI Engineer 지원 포트폴리오 완성  ·  난이도: 🟢 → 🟡 → 🔴

LangGraph 과정에서 State · 조건부 엣지 · Checkpointer · Interrupt · Supervisor를 전부 노트북 안에서 다뤘습니다. 이 페이지는 그 그래프를 API 뒤에서 세션을 유지하고, 사람의 승인을 받고, 품질이 지표로 관리되는 서비스로 끌어올리는 프로젝트 3개(RAG 그래프 → Multi-Agent → Gateway)의 로드맵입니다. P1~P3는 버리지 않고 그대로 재료로 씁니다.

왜 이 3개인가

세 공고에서 LangGraph를 배운 뒤에야 답할 수 있는 요구만 추리면 아래 표가 됩니다. 카카오헬스케어는 LangGraph를 이름으로 명시하고(Multi-Agent · Workflow Orchestration), 토스플레이스는 Model Router · MCP Gateway · Long-term Memory를, 토스는 Agent 구조화와 평가를 요구합니다.

🏠 비유 — 방 하나 → 집 전체 → 단지 인프라 G1은 그래프 하나를 다룹니다(P1 위에서 노드·엣지·루프). G2는 그래프 여러 개를 다룹니다(G1을 부품으로 접어 넣고 총괄 Agent가 조율). G3는 그래프 바깥의 인프라를 다룹니다(모든 그래프의 LLM 호출이 지나는 관문). 방 하나 리모델링 → 방들을 잇는 집 설계 → 단지 전체의 전기·수도 순서라서, 각 프로젝트가 다음 프로젝트의 부품이 됩니다.
공고가 원하는 것쓰는 LangGraph 기능 · 한 줄 풀이공고 근거 → 프로젝트
RAG 정확도 고도화조건부 엣지 · Evaluator-Optimizer — 검색 결과를 채점해 부실하면 질문을 고쳐 다시 찾고, 답이 근거를 벗어나면 다시 쓰는 루프카카오 "검색 정확도를 끌어올리는 RAG 파이프라인" → G1
Multi-Agent · OrchestrationSupervisor · Subgraph · Command — 총괄 Agent가 요청을 보고 전문 Agent에게 넘기고(Handoff), 완성된 그래프를 부품(Subgraph)으로 끼움카카오 "Multi-Agent 구조 설계 · Sub-Agent" · 토스 "Agent 구조화" → G2
Human-in-the-loopInterrupt — 민감한 작업 직전에 그래프를 멈추고, 사람이 승인하면 그 지점부터 이어서 실행카카오 의료 도메인 = 사람 확인이 제품 요건 → G2
Long-term MemoryCheckpointer · Store — 대화 상태를 매 단계 DB에 저장해 재시작해도 세션이 이어지고(Checkpointer), 사용자 선호는 세션 밖에 따로 기억(Store)토스플레이스가 이름을 명시 → G2
Model Router · MCP Gateway라우팅을 상태 머신으로 · 폴백 엣지 — 요청마다 어느 모델을 쓸지 정하고 장애 시 우회. MCP는 외부 도구를 표준 규약으로 Agent에 꽂는 방식, Gateway는 그 도구들을 한곳에서 중개하는 관문토스플레이스 1순위 핵심 업무 → G3
SaaS + Self-hosted LLM(그래프가 아니라 서버 엔지니어링) — OpenAI·Anthropic 같은 외부 API와 내 서버에 띄운 모델(Ollama)을 같은 창구로 받음토스플레이스 "모두 연동" · 토스 "vLLM 등 Provider 운영" → G3
정량 평가 · 관측성P3 하네스 · Langfuse 재사용 — 그래프 노드별로 어느 경로를 탔는지 추적하고, 변경 전후 지표를 비교토스 "평가 기반을 플랫폼으로" · 카카오 "추적·로깅" → 전 프로젝트
⚠️ 새로 배울 것은 세 조각뿐입니다 ① Checkpointer를 SQLite/Postgres에 저장하기(몇 시간) ② MCP 연동 langchain-mcp-adapters(반나절) ③ Ollama로 로컬 모델 띄우기(한나절). 나머지는 전부 이미 배운 LangGraph 기능과 P1~P3의 조립입니다. "새 공부 1 : 조립·운영 9"이고, 그 비율이 곧 실무입니다.

프로젝트 로드맵

G1은 G2의 부품(검색 Sub-Agent)이 되고, G2에서 여러 곳으로 늘어난 LLM 호출이 "어느 모델을, 얼마에, 장애 땐 어디로?"라는 질문을 만들며, 그 답이 G3입니다. 앞 프로젝트가 뒤 프로젝트의 재료이므로 순서는 고정입니다.

G1
Self-Corrective RAG 워크플로우🟢 입문·복습 · 1~2주

P1의 직선 RAG를 그래프로 — 검색 채점 → 질의 재작성 루프 → 웹 폴백 → 답변 검증. P3로 before/after 측정.

G2
Supervisor Multi-Agent 서비스🟡 중급 · 2주

총괄 Agent + 전문 Sub-Agent(G1·P2 재사용) + 승인 API(Interrupt) + 장기 기억(Store). 카카오 공고 직격.

G3
LLM Gateway — Model Router + MCP Gateway🔴 심화·인프라 · 2~3주

SaaS + 로컬 모델을 정책으로 라우팅·폴백하는 독립 서버. G1·G2가 첫 사용자. 토스플레이스 1순위 직격.

G1 · Self-Corrective RAG 워크플로우

🟢 입문·복습 ⏱ 1~2주 복습: 02~03 StateGraph · Routing · Evaluator-Optimizer

무엇을 만드나

P1의 RAG는 한 번 검색해서 한 번 답하는 직선입니다. G1은 이것을 StateGraph로 다시 짜서, 검색 결과를 채점해 부실하면 질문을 고쳐 다시 찾고, 문서에 없으면 웹 검색으로 넘어가고, 답이 근거를 벗어나면 다시 쓰는 자기 교정 루프로 만듭니다. 03장의 Routing이 "관련성 낮음 → 재작성" 엣지로, Evaluator-Optimizer가 "답변 검증 → 재생성" 루프로, State가 재시도 횟수를 세는 가드로 — 노트북에서 장난감으로 배운 패턴이 실제 검색 품질 문제를 푸는 것을 처음 확인하는 프로젝트입니다. 효과는 P3 하네스로 P1(직선) vs G1(그래프)을 비교해 숫자로 남깁니다.

만드는 순서

  1. P1 검색기를 노드로 감싼 최소 그래프 retrieve → generate 검증: 같은 질문에 P1과 같은 수준의 답 + 그래프 시각화 이미지 저장
  2. grade_documents 노드(청크 관련성을 Structured Output으로 채점) + 조건부 엣지 → rewrite_query → 재검색 루프. State에 재시도 카운터와 상한 가드 검증: 무관한 질문을 넣으면 재작성 경로를 타고, 상한에 닿으면 무한 루프 없이 빠져나옴
  3. 웹 검색 폴백 노드 — 문서셋 밖 질문은 웹으로, 출처를 구분 표기 검증: 문서에 없는 질문에 웹 출처가 붙은 답이 옴
  4. check_hallucination 노드 — 답이 근거 청크를 벗어나면 재생성 검증: 근거 없는 답을 유도하는 질문에서 재생성이 발동한 로그 확인
  5. FastAPI POST /query + Langfuse 노드별 span 검증: 대시보드에서 질문 하나가 지나간 노드 경로가 트리로 보임
  6. P3 하네스로 P1 vs G1 측정 검증: faithfulness · context recall의 before/after 표 (예: 0.81 → 0.93)

새로 익히는 것

웹 검색 Tool (Tavily 등) 그래프를 FastAPI 뒤에서 서빙 StateGraph · 조건부 엣지 (복습) P1 검색기 · 평가셋, P3 하네스 (재사용)

G2 · Supervisor Multi-Agent 서비스

🟡 중급 ⏱ 2주 복습: 04 Memory · 05 Multi-Agent

무엇을 만드나

총괄(Supervisor) Agent가 요청을 보고 전문 Sub-Agent — 문서 검색(G1을 그대로 편입) · 업무 실행(P2 재사용) · 일반 응대 — 에게 넘기는 Multi-Agent 서비스입니다. 여기에 "서비스답게" 만드는 세 가지를 얹습니다. ① Checkpointer를 DB에 저장해 서버를 재시작해도 대화가 이어지고, ② 민감한 작업은 Interrupt로 멈춘 뒤 사람이 API로 승인해야 이어서 실행되며, ③ Store로 사용자 선호를 세션 밖에서 기억합니다. Supervisor가 올바른 Sub-Agent를 골랐는지는 P3에 라우팅 정확도 지표를 추가해 측정합니다.

도메인 팁 — 카카오헬스케어를 노린다면 "진료 기록 요약·검색·작성 보조"가 강력합니다. 기록 저장 전 반드시 사람이 승인하는 Interrupt 흐름이 의료의 실제 제품 요건과 겹치기 때문입니다. 토스 계열이라면 "매장 관리 비서"(주문 조회 = 검색, 공지 발송 = 승인 필요 작업)로 잡으세요.

만드는 순서

  1. Supervisor + Sub-Agent 3개 골격 — Command(goto=...)로 Handoff, G1은 Subgraph로, P2는 노드로 편입 검증: 질문 유형별로 다른 Sub-Agent가 응답하는 것이 trace에 보임
  2. Checkpointer 영속화 — SqliteSaver → PostgresSaver, thread_id로 세션 구분 검증: 서버를 재시작해도 같은 thread_id로 대화 맥락이 이어짐
  3. FastAPI POST /chat + SSE 스트리밍 검증: 토큰 단위 스트리밍 + Sub-Agent 전환 이벤트가 클라이언트에 표시
  4. Interrupt 승인 흐름 — 민감 도구 실행 전 정지 → GET /pending(대기 목록) · POST /approve(승인/거부/수정 후 재개) 검증: 민감 작업 요청 → 정지 → API 승인 → 이어서 실행 / 거부 → 취소
  5. Store 장기 기억 — 사용자 선호·이력을 스레드 밖에 저장 검증: 새 thread_id에서도 이전에 저장한 선호가 반영됨
  6. P3에 라우팅 정확도 평가셋 추가 (케이스 20~30개) 검증: Supervisor의 Sub-Agent 선택률이 숫자로 출력됨
  7. (선택) Time Travel 디버깅 — 잘못 분기한 시점의 checkpoint로 돌아가 다른 경로 재실행 검증: 과거 checkpoint에서 재개한 실행이 다른 Sub-Agent로 감

새로 익히는 것

SqliteSaver / PostgresSaver (영속화) Interrupt를 HTTP API로 (승인·재개 엔드포인트) 라우팅 정확도 지표 Supervisor · Subgraph · Command · Store (복습) G1 · P2 (Sub-Agent로 재사용)

G3 · LLM Gateway — Model Router + MCP Gateway

🔴 심화 · 인프라 관점 ⏱ 2~3주 복습: P2 Multi-LLM 스위칭

무엇을 만드나

P2의 Multi-LLM 스위칭(앱 안의 설정)을 독립 게이트웨이 서버로 꺼냅니다. OpenAI 호환 API 하나로 SaaS(OpenAI · Anthropic)와 로컬 모델(Ollama)을 받아, 요청 난이도에 따라 쉬운 요청은 저비용 모델, 어려운 요청은 고성능 모델로 보내고, 장애 시 다른 모델로 폴백하고, 요청별 비용을 기록합니다. 이 라우팅 파이프라인(분류 → 선택 → 호출 → 검증 → 폴백)을 LangGraph 상태 머신으로 짜고, 여러 MCP 서버의 도구를 한곳에서 중개하는 MCP Gateway를 얹습니다. 마지막으로 G1·G2가 이 게이트웨이를 지나게 바꾸면 "플랫폼을 만들고 다른 시스템이 썼다"는 서사가 완성되고, 토스플레이스 공고 첫 문장(Model Router · MCP Gateway · RAG · Long-term Memory를 플랫폼으로)의 네 컴포넌트를 G1·G2·G3로 전부 직접 만든 셈이 됩니다.

만드는 순서

  1. OpenAI 호환 POST /v1/chat/completions + OpenAI · Anthropic 어댑터 검증: 기존 OpenAI SDK 클라이언트가 base_url만 바꿔 그대로 동작
  2. Ollama 로컬 모델 연동 검증: 같은 엔드포인트로 로컬 모델 응답 수신, SaaS와 지연 비교 기록
  3. 라우팅 그래프 — 난이도·용도 분류 → 정책에 따라 모델 선택 검증: 쉬운 질문이 저비용 모델로 가는 결정이 trace에 남음
  4. 폴백·재시도 — Provider 오류·타임아웃 시 조건부 엣지로 2차 모델 전환, 사유 로깅 검증: 1차 Provider를 일부러 죽여도 2차로 전환돼 응답 성공 + 사유 로그
  5. 요청별 비용·지연·라우팅 결정 로깅 (Langfuse 집계) 검증: "전부 고성능 모델" 대비 비용 −N% 비교표 산출
  6. MCP Gateway — MCP 서버 2개 이상의 도구를 등록·목록화·중개 (langchain-mcp-adapters), 호출 감사 로그 검증: Agent가 게이트웨이 목록에서 도구를 발견·호출하고 로그가 남음
  7. G1 · G2를 게이트웨이 경유로 전환 검증: 두 프로젝트의 코드 변경이 base_url 설정뿐임을 diff로 확인
  8. (선택) P3 하네스로 라우팅 정책 A/B 검증: 저비용 라우팅 후에도 품질 지표가 임계값 이상

새로 익히는 것

Ollama (로컬 모델) langchain-mcp-adapters (MCP) OpenAI 호환 API 설계 vLLM (문서로만) FastAPI · Langfuse · LangGraph (재적용)
⚠️ vLLM은 스펙만, 실행은 Ollama로 vLLM은 GPU 서버가 필요해 로컬 실습에 맞지 않습니다. 실행 경험은 Ollama로 쌓고, vLLM은 PagedAttention · continuous batching 같은 구조를 문서로 정리해 "왜 프로덕션은 vLLM인가"를 말할 수 있으면 충분합니다.

다음 단계 — 지원 준비

G3까지 끝나면 여섯 프로젝트가 하나의 시스템이 됩니다 — 모든 LLM 호출은 G3를 지나고, 대화는 G2가 조율하고, 검색은 G1(원형은 P1)이, 업무 실행은 P2가, 품질은 P3가 맡습니다. 공고가 말하는 "AI 플랫폼"의 축소판입니다. 남은 일은 만든 것을 공고 언어로 옮기는 것이고, 위 표의 각 행이 그대로 이력서 한 줄이 됩니다.

토스플레이스 이력서 가이드는 어떤 문제 · 왜 중요했고 어떤 제약 · 어떤 판단 · 어떤 변화 네 가지를 요구합니다. G3가 이 형식에 가장 잘 맞습니다 — "여러 곳에 흩어진 LLM 호출(문제)을, 비용·장애 대응 제약 속에서(제약), 게이트웨이로 표준화하기로 판단하고(판단), 비용 N% 절감과 장애 시 자동 폴백을 달성(변화)".

  • 판단을 남기기 — 이번 라운드의 차별점은 코드가 아니라 판단입니다. "왜 Supervisor 방식인가", "왜 라우팅 기준이 난이도인가"를 README에 적어 두면 면접의 "정답 없는 문제" 질문에 그대로 씁니다.
  • 숫자로 말하기 — "faithfulness 0.81 → 0.93", "라우팅으로 비용 −40%", "라우팅 정확도 92%". P3 하네스가 모든 숫자의 출처입니다.
  • 장애와 consumer 서사 — 토스는 "치명적 장애 해결 경험"을 묻습니다. G3의 폴백 테스트(Provider 강제 다운 → 자동 전환)를 장애 시나리오로 기록하고, "G3를 만들어 G1·G2가 base_url 한 줄로 이관됐다"처럼 다른 팀이 쓰는 플랫폼의 언어로 쓰세요.
