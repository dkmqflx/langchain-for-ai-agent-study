02. RAG Load: PyMuPDF

실습 노트북: 02.ipynb  ·  원문: docs/04.rag.md 2.1.2 PyMuPDF  ·  난이도: 🟢 입문  ·  선행: 01. RAG Load: PDFPlumber

이 자료는 실습 노트북(02.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. RAG 파이프라인의 첫 단추인 Load(문서 불러오기)를, 앞 장의 PDFPlumber에 이어 이번에는 PyMuPDF라는 또 다른 PDF 로더로 다뤄봅니다. "같은 PDF를 왜 굳이 다른 로더로 읽을까?"라는 질문에 답하며, 표 추출과 풍부한 메타데이터라는 PyMuPDF의 강점을 비유와 예시로 천천히 풀어봅니다.

이 장에서 배우는 것 RAG의 다섯 단계(Load → Split → Embed → Store → Retrieve) 중 맨 앞 Load를 이어서 배웁니다. PDF에서 텍스트를 꺼내는 도구는 하나가 아닙니다. 이 장은 PyMuPDF 로더가 무엇이고, 앞서 배운 PDFPlumber와 무엇이 다른지, 그리고 그 결과물인 Document 객체와 metadata를 어떻게 확인하는지 알려줍니다.
⚠️ 실행 전 준비 코드를 직접 돌려보려면 langchain-community와 함께 pymupdf 패키지가 설치돼 있어야 하고, 노트북과 같은 폴더에 읽을 pdf-file.pdf가 있어야 합니다. 이 교재만 읽을 때는 필요 없습니다.

Load란 무엇인가 — Document 객체

본격적으로 PyMuPDF를 만나기 전에, RAG의 첫 단계인 Load가 정확히 무슨 일을 하는지 다시 짚어봅시다. Load는 PDF·CSV·웹페이지 같은 바깥 세상의 문서를, LangChain이 다룰 수 있는 표준 형식인 Document 객체로 바꿔 들여오는 단계입니다.

🔍 비유 — 수입 물품을 표준 택배 상자에 다시 담기 해외에서 온 물건들은 크기도, 포장도, 라벨 언어도 제각각입니다. 그대로는 우리 물류 창고에서 다루기 어렵죠. 그래서 통관을 거치면 모두 똑같은 규격의 택배 상자에 다시 담고, 겉면에 표준 송장을 붙입니다. Load가 바로 이 작업입니다. 어떤 소스에서 왔든 Document라는 똑같은 상자로 통일해주기 때문에, 뒤따르는 Split·Embed·Store 단계가 소스 종류를 신경 쓰지 않고 늘 똑같은 방식으로 처리할 수 있습니다.

Document 상자에는 딱 두 칸이 있습니다.

속성택배 상자에 비유하면담기는 내용
page_content상자 안의 내용물문서에서 뽑아낸 실제 텍스트
metadata겉면에 붙은 송장 라벨소스 경로 · 페이지 번호 · 총 페이지 · 생성일 등 부가 정보
💡 페이지 1장 = Document 1개 PDF 로더는 보통 PDF의 한 페이지를 Document 하나로 만듭니다. 그래서 3페이지짜리 PDF를 로드하면 Document가 3개 들어 있는 리스트가 돌아옵니다. 이 점은 잠시 뒤 실행 결과에서 직접 확인합니다.

PDFPlumber vs PyMuPDF — 왜 로더가 여러 개일까

앞 장에서는 PDFPlumber로 같은 PDF를 읽었습니다. 그런데 왜 또 다른 로더를 배울까요? PDF 안에는 그냥 줄글 텍스트만 있는 게 아니라 표, 이미지, 복잡한 레이아웃이 섞여 있고, 로더마다 이걸 얼마나 잘 뽑아내는지가 다르기 때문입니다.

🔍 비유 — 똑딱이 카메라 vs DSLR 스냅 사진을 빠르게 찍기엔 똑딱이 카메라(PDFPlumber)가 최고입니다. 가볍고 빠르고, 일상 텍스트를 담기엔 충분하죠. 하지만 세밀한 질감이나 표·수치가 빼곡한 장면을 정밀하게 담아야 한다면 DSLR(PyMuPDF)이 유리합니다. 렌즈가 좋아 표를 더 깔끔하게 잡아내고, 사진에 딸려오는 촬영 정보(EXIF)처럼 메타데이터도 더 풍부합니다. 둘 중 뭐가 "정답"인 게 아니라, 찍으려는 대상(문서 종류)에 맞춰 고르는 것입니다.

노트북에 정리된 두 로더의 비교표를 그대로 옮기면 다음과 같습니다.

항목PDFPlumberPyMuPDF
기반C 언어Python
속도매우 빠름빠름
표 추출보통우수
Metadata기본풍부 (format, title, author 등 추가 제공)
적합한 문서단순 텍스트 위주논문, 재무제표, 표가 많은 문서
💡 한 줄 선택 기준 빠른 처리 · 단순 텍스트라면 PDFPlumber, 표가 많거나 정밀 추출·풍부한 정보가 필요하면 PyMuPDF. 이번 노트북의 예제 PDF는 종목별 보유 비중이 담긴 ETF 보유내역 표(ARKK Holdings)라, 표에 강한 PyMuPDF가 잘 어울립니다.

PyMuPDFLoader로 불러오기

사용법은 앞 장의 PDFPlumber와 거의 판박이입니다. 로더 클래스 이름만 PyMuPDFLoader로 바뀔 뿐, 흐름은 똑같이 3단계입니다. 이게 바로 앞에서 말한 "표준 택배 상자"의 힘 — 로더를 갈아끼워도 우리 코드는 거의 그대로입니다.

1로더 준비

읽을 PDF 경로로 PyMuPDFLoader 객체를 만든다

2불러오기

loader.load()로 페이지별 Document 리스트를 얻는다

3확인

개수·내용·metadata를 print로 들여다본다

📥 코드
from langchain_community.document_loaders import PyMuPDFLoader


loader = PyMuPDFLoader("./pdf-file.pdf")


docs = loader.load()

print(docs) # 업로드한 파일이 총 3개의 페이지가 있기 때문에 총 3개의 Document 객체가 생성됨

print(len(docs))

print(docs[0].metadata)
  • PyMuPDFLoader("./pdf-file.pdf") — 어떤 PDF를 읽을지 경로만 알려주고 로더를 만듭니다(아직 읽진 않음).
  • loader.load() — 실제로 PDF를 펼쳐 읽어 페이지마다 Document 하나씩, docs 리스트로 돌려줍니다.
  • docs[0].metadata — 리스트의 첫 번째 페이지 Document에 붙은 송장(라벨)만 콕 집어 출력합니다.

이제 세 개의 print가 각각 무엇을 보여주는지 하나씩 살펴봅니다.

① print(docs) — Document 리스트 전체

리스트 안에 Document가 3개 들어 있습니다(PDF가 3페이지라서요). 각 Document는 metadata={...}와 page_content='...' 두 칸으로 이뤄져 있죠. 실제 출력은 표 내용이 통째로 담겨 매우 길기 때문에, 아래는 구조가 보이도록 본문을 줄여 표시한 것입니다.

▶ 이렇게 나와요 (실제 출력, 본문 일부 생략)
[Document(metadata={'producer': '', 'creator': '', 'creationdate': '2025-11-26T07:05:39+00:00', 'source': './pdf-file.pdf', 'file_path': './pdf-file.pdf', 'total_pages': 3, 'format': 'PDF 1.4', 'title': '', 'author': '', 'subject': '', 'keywords': 'HD:2025-11-26', 'moddate': '2025-11-26T07:05:39+00:00', 'trapped': '', 'modDate': "D:20251126070539+00'00'", 'creationDate': "D:20251126070539+00'00'", 'page': 0}, page_content='Holdings Data - ARKK\nAs of 11/26/2025\nARKK\nARK Innovation ETF\nCompany\nTicker\nCUSIP\nShares\nMarket Value ($)\nWeight (%)\n1\nTESLA INC\nTSLA\n88160R101\n2,204,438\n$924,541,297.20\n12.26%\n ...(1페이지 표 데이터가 길어 생략)... '),
 Document(metadata={..., 'page': 1}, page_content='Holdings Data - ARKK\n ...(2페이지 표 + 투자 위험 안내문)... '),
 Document(metadata={..., 'page': 2}, page_content='Holdings Data - ARKK\n ...(3페이지 저작권 안내문)... ')]
💡 읽는 법 대괄호 [ ... ]는 리스트, 그 안의 Document(...) 하나하나가 페이지 한 장입니다. metadata의 'page': 0 / 1 / 2가 각각 1·2·3페이지를 가리킵니다(번호는 0부터 시작). 내용물(page_content)에는 종목명·티커·주식 수·평가액이 줄바꿈(\n)으로 이어져 담겨 있습니다.

② print(len(docs)) — 몇 페이지였나

리스트에 든 Document 개수, 즉 페이지 수입니다. 예제 PDF가 3페이지이므로 3이 나옵니다.

▶ 이렇게 나와요
3

③ print(docs[0].metadata) — 첫 페이지의 송장

첫 번째 Document의 metadata(송장 라벨)만 따로 꺼내 본 것입니다. 여기서 PyMuPDF의 진가가 드러납니다 — 송장에 적힌 항목이 상당히 많죠.

▶ 이렇게 나와요
{'producer': '', 'creator': '', 'creationdate': '2025-11-26T07:05:39+00:00', 'source': './pdf-file.pdf', 'file_path': './pdf-file.pdf', 'total_pages': 3, 'format': 'PDF 1.4', 'title': '', 'author': '', 'subject': '', 'keywords': 'HD:2025-11-26', 'moddate': '2025-11-26T07:05:39+00:00', 'trapped': '', 'modDate': "D:20251126070539+00'00'", 'creationDate': "D:20251126070539+00'00'", 'page': 0}

더 풍부한 Metadata

방금 출력된 송장을 자세히 보면, PDFPlumber가 주던 기본 항목(source, page, total_pages, 생성일 등) 말고도 format, title, author, subject, producer 같은 문서 자체의 속성이 함께 담겨 있습니다.

🔍 비유 — 사진의 EXIF, 책의 판권 페이지 스마트폰으로 찍은 사진에는 우리 눈에 안 보여도 촬영 시각·기종·설정값(EXIF)이 숨어 있습니다. 책 맨 뒤 판권 페이지에는 지은이·출판사·발행일이 적혀 있죠. PyMuPDF의 metadata가 바로 이런 역할입니다. PDF 파일이 스스로에 대해 기록해 둔 정보를 더 알뜰히 긁어와, 나중에 "이 문서 누가 언제 어떤 형식으로 만들었지?"를 코드에서 바로 확인할 수 있게 해줍니다. (값이 비어 있는 칸은 원본 PDF에 그 정보가 애초에 안 적혀 있었다는 뜻입니다.)

metadata에 담긴 주요 항목을 정리하면 다음과 같습니다.

필드의미이 예제에서의 값
source / file_path원본 파일 경로./pdf-file.pdf
page페이지 번호(0부터)0 (첫 페이지)
total_pages전체 페이지 수3
formatPDF 버전/형식 PyMuPDF 추가PDF 1.4
title / author / subject제목·저자·주제 PyMuPDF 추가비어 있음(원본 미기재)
producer / creatorPDF를 만든 소프트웨어 PyMuPDF 추가비어 있음
keywords문서 키워드HD:2025-11-26
creationdate / moddate생성일 · 수정일2025-11-26T07:05:39+00:00
📘 보충 — 풍부한 metadata가 RAG에서 왜 쓸모 있을까?

metadata는 단순한 참고 정보가 아니라, 뒤 단계에서 실전 무기가 됩니다.

  • 출처 표기 — 답변을 만들 때 "이 정보는 pdf-file.pdf 3페이지에서 나왔어요"처럼 근거(source)를 함께 보여줄 수 있습니다.
  • 필터링 검색 — "특정 저자의 문서에서만", "특정 페이지 범위에서만" 검색하도록 metadata로 조건을 걸 수 있습니다.
  • 디버깅 — 이상한 답이 나왔을 때, 어떤 페이지·어떤 파일이 검색됐는지 metadata로 추적할 수 있습니다.
한 줄 요약 내용물(page_content)이 "무엇을 말하는가"라면, 송장(metadata)은 "어디서 왔는가"입니다. RAG에서는 둘 다 중요합니다.

📚 한 장 정리

오늘의 핵심 Load는 아무 문서나 Document라는 표준 상자로 바꾸는 단계이고, PyMuPDF는 그 상자를 만드는 여러 로더 중 표·메타데이터에 강한 선택지다.
  • Load = 표준 택배 상자 — 어떤 소스든 page_content(내용물)와 metadata(송장)를 가진 Document로 통일한다.
  • 페이지 1장 = Document 1개 — 3페이지 PDF → len(docs)는 3.
  • PyMuPDF = DSLR — PDFPlumber(똑딱이)보다 표 추출이 우수하고 metadata가 풍부하다. 논문·재무제표·표 많은 문서에 적합.
  • 사용법은 판박이 — PyMuPDFLoader(경로) → .load(). 로더만 갈아끼우면 나머지 코드는 그대로.
  • metadata는 무기 — format·title·author 등 문서 자체 정보까지 담겨, 출처 표기·필터 검색·디버깅에 쓰인다.
