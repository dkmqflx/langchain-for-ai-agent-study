3

검색 개선 ① Hybrid (BM25 + Dense)

랭체인 집중 복습(BM25) ⏱ 반나절
🎯 목표

키워드 검색(BM25)과 의미 검색(임베딩)을 앙상블해 검색 누락을 줄인다. 동시에 검색기를 mode 팩토리로 재구성해, 검색 전략을 문자열 하나로 갈아끼울 수 있게 만든다.

🧠 개념

임베딩 검색은 의미는 잘 잡지만 정확한 용어·수치·희귀 단어(조항 번호, 상품명, 고유명사)에 약합니다. BM25는 반대로 정확한 단어 일치에 강합니다. 둘을 EnsembleRetriever로 합치면 서로의 빈틈을 메웁니다 — 04에서 배운 Hybrid RAG. 그리고 get_retriever(mode) 팩토리로 만들어 두면, STEP 7에서 같은 골든셋으로 세 구성을 나란히 채점해 비교할 수 있습니다. 이 "구성요소를 조립·교체 가능하게 만드는" 감각이 토스 공고의 "RAG 구성 요소를 단독으로 설계하고 시스템 수준에서 통합"에 대응하는 훈련입니다.

🛠 할 일

rag.py의 기존 retriever = vs.as_retriever(...) 한 줄을 교체하는 작업입니다. 네 조각으로 나눠 보고, 맨 아래 전체 코드를 붙여 넣으세요.

🧭 네 조각 한눈에

① BM25용 원문 청크 준비  →  ② _build_retriever() — mode를 검색기로  →  ③ get_retriever() — 만든 검색기 재사용  →  ④ answer()에 mode 인자 추가

① BM25용 원문 청크 준비 — STEP 1의 함수를 다시 쓴다

여기서 STEP 1의 설계가 값을 합니다. BM25는 벡터를 쓰지 않습니다. "이 단어가 이 문서에 몇 번 나왔나"를 세는 방식이라 원문 텍스트가 그대로 필요해요. 그런데 Chroma에는 벡터가 들어 있죠. 그래서 ingest.py의 build_chunks()를 그대로 불러 씁니다 — STEP 1에서 이걸 함수로 빼 둔 이유가 바로 지금 드러나는 겁니다.

rag.py (STEP 2 코드에 이어서)
from langchain_community.retrievers import BM25Retriever    # 키워드(단어 일치) 기반 검색기
from langchain_classic.retrievers import EnsembleRetriever  # 검색기 여러 개를 합쳐 순위를 섞어 주는 도구
from ingest import build_chunks                             # STEP 1의 '청크 만들기' 함수를 그대로 재사용

# BM25는 벡터가 아니라 '원문에 그 단어가 몇 번 나오나'를 세는 방식이라 텍스트 청크가 그대로 필요하다.
# 그런데 Chroma에는 벡터만 들어 있으므로, PDF를 다시 읽어 청크를 만들어 둔다.
#
# 이 줄이 함수 '바깥'에 있는 게 중요하다 → 파일을 불러올 때 딱 한 번만 실행된다.
# answer() 안에 넣으면 질문할 때마다 PDF 전체를 다시 읽게 되어 몹시 느려진다.
chunks = build_chunks()

chunks = build_chunks()가 함수 바깥에 있는 게 중요합니다. 이러면 파일을 불러올 때 딱 한 번만 PDF를 읽습니다. answer() 안에 넣었다면 질문할 때마다 PDF 전체를 다시 읽어 몹시 느려집니다.

🤔 langchain_classic… 이거 레거시 아닌가요?

이름 때문에 오해하기 쉬운데, "구식 코드"가 아니라 "이사 간 옛 짐"입니다. LangChain 1.0에서 langchain 패키지를 에이전트 중심으로 비우고 다시 지으면서, 0.x 시절에 들어 있던 나머지(chains·memory·retrievers·evaluation 등)를 통째로 langchain-classic이라는 새 패키지로 옮겼습니다.

EnsembleRetriever는 v1 네이티브 대안이 아예 없습니다 — langchain_core에도 langchain_community에도 없고, 이 클래스가 정의된 파일은 langchain_classic/retrievers/ensemble.py 하나뿐입니다. deprecated 표시도, import 경고도 없고요. 내용물도 낡지 않았습니다: RRF(rank fusion)로 순위를 합치는 평범한 BaseRetriever라 .invoke()로 그대로 씁니다. STEP 4의 Reranker도, ingest.py의 CacheBackedEmbeddings도 같은 처지예요.

주의: 검색하다 보면 from langchain.retrievers import EnsembleRetriever라는 예제를 자주 만나는데, 그건 0.x 경로라 LangChain 1.x에서는 ModuleNotFoundError가 납니다(1.x의 langchain에는 retrievers 모듈이 없습니다). 옛 블로그 예제를 그대로 붙여 넣지 말고 설치된 버전 기준으로 경로를 확인하는 습관을 들이세요.

② _build_retriever() — 문자열 하나로 검색 전략 갈아끼우기

이 STEP의 진짜 핵심은 BM25가 아니라 이 함수의 모양입니다. "baseline"·"hybrid" 같은 문자열 하나로 검색기를 통째로 바꿀 수 있게 만드는 것 — 그래야 STEP 7에서 같은 질문으로 여러 구성을 나란히 채점할 수 있습니다.

rag.py (이어서)
def _build_retriever(mode: str):
    """mode 이름(문자열)을 받아 그에 해당하는 검색기 객체를 만들어 돌려준다."""
    dense = vs.as_retriever(search_kwargs={"k": 4})   # 의미(임베딩) 검색 — STEP 2에서 쓰던 그 검색기

    if mode == "baseline":
        return dense                                  # STEP 2 그대로: 의미 검색만 쓴다

    bm25 = BM25Retriever.from_documents(chunks)       # 청크들로 키워드 색인을 만든다
    bm25.k = 4                                        # BM25가 돌려줄 청크 수 (의미 검색과 똑같이 4개)

    if mode == "hybrid":
        # EnsembleRetriever = 두 검색기에게 각자 top-4를 뽑게 한 뒤,
        #                     weights 비율로 점수를 섞어 하나의 최종 순위를 만든다.
        # [0.4, 0.6] → 앞의 bm25에 40%, 뒤의 dense에 60% 비중.
        #   의미 검색이 평소 더 안정적이라 비중을 더 주고,
        #   BM25는 의미 검색이 놓치는 순간(조항번호·고유용어)을 메우는 보험 역할을 맡는다.
        return EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])

    # 오타 등으로 없는 이름이 들어오면 조용히 넘어가지 말고 즉시 에러를 내 알린다
    raise ValueError(f"unknown mode: {mode}")

EnsembleRetriever는 두 검색기에게 각자 top-4를 뽑게 한 뒤, weights로 점수를 섞어 최종 순위를 만듭니다. [0.4, 0.6]은 BM25 40%, 의미 검색 60%라는 뜻이고요. 의미 검색에 무게를 더 준 건 그게 평소에 더 안정적이기 때문이고, BM25는 의미 검색이 놓치는 순간을 메우는 보험에 가깝습니다.

이런 질문에서는누가 이기나이유
"제40조가 뭐야?" · "리볼빙 수수료율"BM25희귀한 단어·번호는 글자가 그대로 일치해야 찾힘. 임베딩은 이런 걸 뭉갬
"카드 잃어버리면 내가 물어내야 해?"의미 검색문서에 없는 말투로 물어봐도 뜻이 비슷한 조항을 찾아냄
🔢 결과가 4개가 아니라 6~8개로 나옵니다 — 정상입니다

앙상블은 두 검색기의 top-4를 합집합으로 합친 뒤 순위만 다시 매기는 방식이라, 겹치지 않은 청크는 그대로 남습니다. 두 검색기가 완전히 다른 걸 찾았다면 4+4=8개, 보통은 겹치는 게 있어 6~7개가 나와요. 그래서 answer()가 LLM에 넘기는 문맥도 baseline보다 길어지고 citations도 그만큼 늘어납니다. 이렇게 늘어난 후보를 다시 4개로 추려 내는 것이 바로 다음 STEP 4 Reranker(top_n=4)가 맡는 일입니다.

③ get_retriever() — 한 번 만든 검색기는 다시 쓰기

BM25Retriever.from_documents(chunks)는 호출할 때마다 색인을 처음부터 새로 만듭니다. 질문마다 이걸 반복하면 느려지니, 만들어 둔 검색기를 딕셔너리에 담아 두고 재사용합니다.

rag.py (이어서)
_retrievers = {}   # 이미 만들어 둔 검색기를 담는 보관함 — {mode 이름: 검색기 객체}

def get_retriever(mode: str = "hybrid"):
    """검색기를 돌려준다. 처음 요청받은 mode만 새로 만들고, 그다음부터는 보관함에서 꺼내 쓴다."""
    # BM25Retriever.from_documents()는 호출할 때마다 색인을 처음부터 새로 만들어 느리다.
    # 질문이 올 때마다 반복하지 않도록, 한 번 만든 것을 보관해 두고 재사용한다.
    if mode not in _retrievers:            # 보관함에 없으면 = 이 mode는 처음 쓰는 것
        _retrievers[mode] = _build_retriever(mode)   # 그때만 만들어 보관한다
    return _retrievers[mode]

# 참고: 이름 앞의 _ 는 파이썬에서 '바깥에서 직접 쓰지 마세요'라는 관례적 표시다.
#      바깥(main.py·evaluate.py)에 열어 둔 문은 get_retriever() 하나뿐이다.

처음 부를 때만 만들고 그다음부터는 꺼내 쓰는, "필요할 때 만들어 보관해 두기" 패턴입니다. _로 시작하는 이름은 파이썬에서 "바깥에서 직접 쓰지 마세요"라는 관례적 표시고요 — 바깥에서 쓸 문은 get_retriever() 하나만 열어 둔 겁니다.

④ answer()에 mode 인자 추가

고칠 곳은 딱 두 군데입니다. 함수 서명에 mode를 받고, 검색 한 줄을 get_retriever(mode)로 바꾸는 것. 나머지(프롬프트·생성·근거)는 하나도 안 바뀝니다 — 검색기를 부품으로 분리해 둔 덕분입니다.

rag.py (answer 교체)
# mode 인자가 추가됐다. 기본값이 있으므로 기존 호출부 answer("질문")은 그대로 동작한다.
def answer(question: str, mode: str = "hybrid"):
    # ← 바뀌는 건 이 한 줄뿐: 고정된 retriever 대신, mode에 해당하는 검색기를 꺼내 쓴다
    docs = get_retriever(mode).invoke(question)

    # 아래는 STEP 2와 완전히 같다. 검색기를 부품으로 떼어 놓은 덕분에 나머지는 손댈 필요가 없다.
    msg = PROMPT.invoke({"question": question, "context": format_context(docs)})
    resp = llm.invoke(msg)
    return {
        "answer": resp.content,
        "citations": [{"source": d.metadata.get("source"), "page": d.metadata.get("page")} for d in docs],
        "contexts": [d.page_content for d in docs],
    }

기본값을 "hybrid"로 둔 덕분에 기존 호출부(answer("질문"))는 그대로 동작합니다. STEP 5의 API도, STEP 7의 평가 스크립트도 이 인자 하나로 구성을 바꿔 부를 수 있게 됩니다.

📄 전체 코드 (rag.py에서 교체·추가할 부분)
rag.py (retriever → mode 팩토리로 교체)
# ═══════════════════════════════════════════════════════════════════
# STEP 3 · Hybrid 검색: 키워드 검색(BM25) + 의미 검색(임베딩)을 앙상블해 검색 누락을 줄인다.
# 임베딩은 '의미'에 강하나 정확한 용어·수치·희귀 단어(조항번호·상품명 등)에 약하고,
# BM25는 '정확한 단어 일치'에 강하다 → 둘을 합쳐 서로의 빈틈을 메운다.
#
# 동시에 검색기를 'mode 팩토리'로 재구성한다: baseline | hybrid  (STEP 4에서 rerank 추가)
# → STEP 7에서 같은 골든셋으로 세 구성을 나란히 채점해 비교하기 위한 뼈대.
# ═══════════════════════════════════════════════════════════════════
from langchain_community.retrievers import BM25Retriever
from langchain_classic.retrievers import EnsembleRetriever   # ImportError 시: from langchain.retrievers import EnsembleRetriever
from ingest import build_chunks                              # STEP 1의 청크 생성 함수 재사용(BM25는 원문 청크가 필요)

chunks = build_chunks()                # BM25용 원문 청크. 모듈 로드 시 1회만(매 요청 재호출은 느림)

def _build_retriever(mode: str):
    """mode 이름 → 검색기 객체. 검색 전략을 문자열 하나로 갈아끼우는 것이 이 리팩터링의 핵심."""
    dense = vs.as_retriever(search_kwargs={"k": 4})          # 의미(임베딩) 검색 — STEP 2에서 쓰던 것
    if mode == "baseline":
        return dense                                         # STEP 2 그대로: 의미 검색만
    bm25 = BM25Retriever.from_documents(chunks)              # 키워드(단어 빈도) 기반 검색기
    bm25.k = 4                                               # BM25가 돌려줄 청크 수
    if mode == "hybrid":
        # 두 검색기를 가중 앙상블: 각자 top-4를 뽑아 weights로 점수를 섞어 최종 순위를 만든다
        return EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])   # 0.4=BM25, 0.6=의미
    raise ValueError(f"unknown mode: {mode}")

_retrievers = {}                       # 만들어 둔 검색기 캐시(같은 mode를 매번 다시 만들지 않기)
def get_retriever(mode: str = "hybrid"):
    if mode not in _retrievers:
        _retrievers[mode] = _build_retriever(mode)
    return _retrievers[mode]

def answer(question: str, mode: str = "hybrid"):             # mode 인자 추가 — 기본은 hybrid
    """질문 하나를 받아 검색 → 생성 → 근거까지 끝낸 결과 dict를 돌려준다."""
    docs = get_retriever(mode).invoke(question)              # (1) 검색: mode에 해당하는 검색기로
    msg = PROMPT.invoke({"question": question, "context": format_context(docs)})
    resp = llm.invoke(msg)
    return {
        "answer": resp.content,
        "citations": [{"source": d.metadata.get("source"), "page": d.metadata.get("page")} for d in docs],
        "contexts": [d.page_content for d in docs],
    }
💡 팁 build_chunks()를 매 요청마다 부르면 느립니다. 지금은 학습이 목적이니 모듈 로드 시 한 번만 부르면 충분해요(위 코드처럼 파일 상단에서 1회). 성능 최적화는 STEP 8/README의 "개선 아이디어"로 남겨두세요.
✅ 검증 게이트
두 구성을 눈으로 비교 — 정확한 용어·조항 번호가 든 질문으로 baseline과 hybrid의 검색 결과를 나란히 출력해 보세요. 
uv run python - <<'EOF'
from rag import get_retriever
q = "내 문서의 정확한 용어·조항번호가 들어간 질문"   # 여러분의 문서 고유 용어로 바꾸세요
for mode in ["baseline", "hybrid"]:
    print(f"\n--- {mode}")
    for d in get_retriever(mode).invoke(q):
        print(d.metadata.get("page"), "|", d.page_content[:60].replace("\n", " "))
EOF
두 결과가 서로 다르고, 정확한 키워드가 든 질문에서 hybrid가 해당 용어가 포함된 청크를 더 안정적으로 상위에 올리면 통과. (몇 점이나 좋아졌는지의 정량 비교는 STEP 7에서 합니다. weights [0.4, 0.6]을 [0.5, 0.5], [0.3, 0.7]로 바꿔 결과가 어떻게 달라지는지 눈으로 실험해 봐도 좋습니다.)
🎓 배우는 것

EnsembleRetriever 조립 + retriever를 교체 가능한 부품으로 설계하는 랭체인 핵심 감각. 이 mode 팩토리가 STEP 7 비교 실험의 뼈대가 됩니다.
