07. Middleware: PII 개인정보 탐지

실습 노트북: 07.ipynb  ·  원문: docs/02.agent-basic.md 3장 Middleware  ·  난이도: 🟡 중급  ·  선행: 06. Human-in-the-Loop

이 자료는 실습 노트북(07.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 의료·금융·법률처럼 민감 정보를 다루는 Agent는, 사용자가 무심코 흘린 이메일·카드번호·전화번호가 LLM에까지 그대로 흘러가면 큰일 납니다. 이 장에서는 PIIMiddleware로 개인정보를 모델에 닿기 전에 자동으로 가려내는(masking) 방법을 — 내장 유형부터 정규식·함수로 직접 만든 커스텀 탐지기까지 — 비유와 함께 풀어봅니다.

🔍 비유 — 편지를 부치기 전 검은 매직펜으로 지우기 기밀문서를 외부에 공개할 때, 담당자는 이름·주민번호 같은 민감한 부분을 검은 매직펜으로 쓱쓱 칠해 못 읽게 만든 뒤 내보냅니다. PIIMiddleware가 바로 그 검열 담당자입니다. 사용자의 말이 모델에게 도착하기 전, 중간에서 가로채 개인정보만 골라 까맣게 칠하는 것이죠. 모델은 처음부터 지워진 버전만 받으므로, 개인정보를 아예 본 적조차 없게 됩니다.
이 장에서 배우는 것 "미들웨어(middleware)"는 사용자 입력 → 모델 → 도구 → 응답이라는 컨베이어 벨트 중간중간에 끼워 넣는 검사대입니다. 그중 PIIMiddleware는 개인정보 검사대예요. 이 장에서는 (1) 내장된 이메일·카드번호 탐지, (2) 정규식으로 만든 전화번호 탐지, (3) 함수로 만든 API Key 탐지 — 세 가지 방법을 순서대로 봅니다.

PII란 무엇인가

PII(Personally Identifiable Information, 개인 식별 정보)는 그 자체로 혹은 다른 정보와 합쳐져 특정 개인을 콕 집어낼 수 있는 정보를 말합니다. 이메일 주소, 신용카드 번호, 전화번호, IP 주소, 주민등록번호 같은 것들이죠. LangChain의 PIIMiddleware는 이런 정보를 자동으로 찾아냅니다.

💡 내장(Built-in) PII 유형 별도 설정 없이 이름만 지정하면 바로 잡아내는 유형들입니다 — email · credit_card · ip · mac_address · url 등. 여기 없는 형태(전화번호, API Key 등)는 뒤에서 배울 정규식·함수로 직접 만들어 붙일 수 있습니다.

처리 전략 4가지 — 찾은 다음 "어떻게" 가릴까

개인정보를 찾는 것과, 찾은 뒤 어떻게 처리할지는 별개의 선택입니다. 후자를 정하는 것이 strategy(전략) 옵션이에요. 네 가지가 있습니다.

🔍 비유 — 문서의 비밀번호를 가리는 네 가지 방법 비밀번호가 적힌 종이를 남에게 보여줘야 한다고 해봅시다. ① 통째로 검은 칠(redact) — "여기 뭔가 있었다"는 것만 남기고 내용은 완전 삭제. ② 일부만 별표(mask) — 카드 영수증처럼 뒤 4자리만 남기고 ****. ③ 아예 문 닫기(block) — "이런 건 못 보여줘"라며 처리를 중단. ④ 지문으로 바꾸기(hash) — 원본 대신 알아볼 수 없는 고유 코드로 치환. 상황에 맞는 강도를 골라 쓰는 것이죠.
전략 (strategy)설명예시
redact완전 마스킹 (통째로 가림)user@example.com → [REDACTED_EMAIL]
mask부분 마스킹 (뒷자리 일부만 남김)1234123443214321 → ************4321
block실행 중단 (에러 발생)API Key 감지 시 즉시 차단
hash해싱 처리 (원본 대신 해시값)원본 → a3f2...
⚠️ redact와 mask는 무엇이 다른가 redact는 정보가 있었다는 사실만 남기고 값은 전부 삭제합니다(이메일 → [REDACTED_EMAIL]). mask는 본인 확인용으로 뒷자리 일부는 남겨 둡니다(카드 → ************4321). "완전히 없애야 하나, 일부는 확인용으로 남겨야 하나"를 기준으로 고르면 됩니다.

적용 시점 (apply_to) — 컨베이어 벨트의 어디에 검사대를 둘까

검사대를 벨트의 어느 지점에 세울지도 고를 수 있습니다. 크게 세 곳입니다.

옵션검사 시점이럴 때
apply_to_input모델 호출 전 (사용자 입력)사용자가 흘린 개인정보가 모델에 닿기 전에 차단 — 가장 흔함
apply_to_output모델 호출 후 (모델 답변)모델이 실수로 개인정보를 뱉는 것을 방지
apply_to_tool_results도구 응답에 적용DB·API가 돌려준 결과 속 개인정보를 가림
🔍 비유 — 공항의 입국 심사대 apply_to_input=True는 입국장(모델) 입구에 세운 검색대입니다. 승객(사용자 메시지)이 안으로 들어오기 전에 위험물(개인정보)을 미리 걸러내죠. 그래서 이번 노트북 예제는 모두 apply_to_input=True를 씁니다 — 개인정보가 모델에 아예 도착하지 못하게 문 앞에서 막는 게 핵심이니까요.

0. 환경 준비 — 모델과 도구

먼저 말을 걸 모델과, Agent가 사용할 도구(tool) 하나를 준비합니다. 이번 장의 주인공은 도구가 아니라 그 사이에 끼워 넣을 PII 미들웨어이니, 도구는 간단한 예시용입니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool

# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-5-nano")
📥 코드
@tool
def save_book_info():
    """주어진 책 제목을 저장하는 도구"""
    # 실제로는 데이터베이스나 파일에 저장하는 로직이 들어감
    return f"책  정보가 저장되었습니다."
💡 도구는 지금은 조연입니다 save_book_info는 "책 정보를 저장한다"는 자리만 채워둔 껍데기 도구입니다. 실제로는 DB에 저장하는 코드가 들어가겠지만, 이 장에서 확인할 것은 사용자 입력이 모델에 닿기 전에 개인정보가 지워지는지이므로 도구 내부 로직은 중요하지 않습니다.

1. Built-in PII — 이메일 가리고, 카드번호 마스킹

이제 create_agent로 Agent를 만들면서 middleware 목록에 PIIMiddleware를 끼워 넣습니다. 미들웨어를 여러 개 나열하면 각각이 자기 담당 정보를 처리합니다. 여기서는 이메일은 통째로 가리고(redact), 카드번호는 뒷자리만 남기고 마스킹(mask)합니다.

📥 코드
from langchain.agents import create_agent
from langchain.agents.middleware import PIIMiddleware

agent = create_agent(
    model,
    tools=[save_book_info],
    middleware=[
        # 이메일은 완전히 가림 (redact)
        PIIMiddleware(pii_type="email", strategy="redact", apply_to_input=True),
        # 신용카드 번호는 마스킹 처리 (mask)
        PIIMiddleware(pii_type="credit_card", strategy="mask", apply_to_input=True),
    ],
)

이제 Agent에게 이메일과 카드번호가 섞인 메시지를 보내봅니다. 그리고 response["messages"][0].content — 즉 Agent가 실제로 받은 첫 메시지를 꺼내보면, 개인정보가 이미 지워져 있음을 눈으로 확인할 수 있습니다.

📥 코드
prompt = "안녕하세요. 이메일은 user123@example.com 입니다. 제 카드번호는 1234123443214321 입니다."
response = agent.invoke({"messages": [{"role": "user", "content": prompt}]})

# 에이전트가 실제로 넘겨받은(마스킹된) 메시지 확인
print(response)
print(response["messages"][0].content)
▶ 이렇게 나와요
안녕하세요. 이메일은 [REDACTED_EMAIL] 입니다. 제 카드번호는 ************4321 입니다.

원본 프롬프트에는 분명 user123@example.com과 1234123443214321이 들어 있었지만, Agent가 받은 첫 메시지에는 이미 지워진 값만 남아 있습니다. 변화를 표로 비교하면 이렇습니다.

이메일user123@example.com[REDACTED_EMAIL]redact

전체 흐름을 그림으로 보면, 개인정보는 모델에 도착하기도 전에 문 앞에서 걸러집니다.

이메일·카드번호가 그대로 담긴 원본 메시지

2PIIMiddleware

apply_to_input — 입력에서 탐지·마스킹

💡 왜 이게 중요한가 모델은 처음부터 민감 정보가 제거된 입력만 받습니다. 즉 개인정보가 LLM 서버로 전송되거나 로그에 남을 일이 없어집니다. "모델을 믿고 조심시키는" 것이 아니라, 아예 볼 수 없게 원천 차단하는 것이 핵심입니다.
⚠️ 참고 — 모델 답변은 원본 출력 그대로예요 실제 실행 결과를 보면, 마스킹된 입력을 받은 모델은 "카드번호 같은 민감 정보 공유는 위험하다"는 취지의 안내성 답변을 길게 내놓기도 합니다. 우리가 확인해야 할 것은 모델의 답변 내용이 아니라, messages[0].content가 이미 가려져 있다는 사실입니다.

2. Custom PII — 정규식으로 직접 패턴 정의

내장 유형에 없는 정보(예: 한국 휴대폰 번호)는 어떻게 잡을까요? PIIMiddleware의 detector 파라미터에 정규식(Regex) 문자열을 넘기면, 그 패턴에 맞는 텍스트를 개인정보로 간주해 처리합니다.

🔍 비유 — 특정 무늬만 걸러내는 체(sieve) 정규식은 "이런 모양의 글자만 통과시켜라"고 정해둔 특수 체입니다. 휴대폰 번호는 "010 뒤에 숫자 3~4개, 그리고 숫자 4개"라는 일정한 무늬를 가지죠. 이 무늬를 체에 새겨두면, 문장 속에서 그 무늬와 똑같이 생긴 부분만 쏙쏙 골라낼 수 있습니다. 사람이 일일이 찾는 게 아니라, 패턴으로 기계가 자동으로 걸러내는 것이죠.
📥 코드
# 휴대폰 번호(010-XXXX-XXXX)를 잡아내는 커스텀 정규식 패턴
phone_number_regex = r"\b(010)[-\s]?(\d{3,4})[-\s]?(\d{4})\b"

phone_masking_middleware = PIIMiddleware(
    pii_type="phone_number",
    detector=phone_number_regex,
    strategy="mask",
    apply_to_input=True,
)
📘 보충 — 정규식 \b(010)[-\s]?(\d{3,4})[-\s]?(\d{4})\b 뜯어보기
조각뜻
\b단어 경계 — 숫자 뭉치의 앞/뒤 딱 떨어지는 지점(엉뚱한 긴 숫자열의 일부를 잡지 않도록)
(010)정확히 010으로 시작
[-\s]?하이픈(-)이나 공백이 있어도 되고 없어도 됨 (? = 0개 또는 1개)
(\d{3,4})숫자(\d) 3~4개 — 국번(가운데 자리)
(\d{4})숫자 4개 — 마지막 자리

덕분에 010-1234-5678, 010 1234 5678, 01012345678처럼 구분자가 있든 없든 같은 번호를 모두 잡아낼 수 있습니다. 이 미들웨어를 Agent의 middleware 목록에 넣으면, 앞의 이메일·카드번호처럼 전화번호도 자동 마스킹됩니다.

3. Custom PII — 함수(function)로 직접 탐지하기

정규식 문자열만으로 부족할 때는, detector에 탐지 함수를 직접 넘길 수도 있습니다. 아래는 sk-로 시작하는 32자리 문자열을 API Key로 간주해 찾아내는 함수입니다.

🔍 비유 — 지명수배 몽타주를 든 형사 정규식 문자열이 "체"라면, 탐지 함수는 몽타주를 손에 쥔 형사입니다. 문장을 처음부터 끝까지 훑으면서(finditer), 몽타주(sk- + 32자리 무늬)와 일치하는 인물을 발견할 때마다 "어디에 있었는지(start·end)"와 "누구였는지(text)"를 수첩에 기록해 목록으로 넘겨줍니다. 미들웨어는 이 수첩을 받아, 해당 위치의 글자를 전략대로 처리하죠.
📥 코드
import re
# **re**는 파이썬의 내장 라이브러리로, **정규 표현식(Regular Expression)**을 다루기 위한 도구입니다.
# re: 복잡한 문자열 패턴을 찾기 위한 파이썬 기본 도구 상자.

def detect_api_key(content: str) -> list[dict[str, str | int]]:
    """'sk-'로 시작하는 32자리 문자열을 API 키로 간주하고 탐지합니다."""
    matches = []
    pattern = r"sk-[a-zA-Z0-9]{32}"
    for match in re.finditer(pattern, content):
        matches.append({
            "text": match.group(0), # 정규 표현식 패턴과 일치하는 전체 텍스트를 가져옵니다.
            "start": match.start(), # 일치하는 패턴이 시작되는 문자열 내의 인덱스(위치) 번호
            "end": match.end(),     # 일치하는 패턴이 끝나는 바로 다음 위치의 인덱스 번호입니다.
        })
    return matches
▶ 이렇게 나와요 (예상 출력)
>>> detect_api_key("sk-abcdefghij1234567890ABCDEFGH1234")
[{'text': 'sk-abcdefghij1234567890ABCDEFGH1234', 'start': 0, 'end': 35}]

함수는 찾은 항목마다 세 가지 정보를 담은 딕셔너리를 목록에 쌓아 돌려줍니다 — 일치한 문자열(text), 시작 위치(start), 끝 위치(end). 미들웨어는 이 start·end 위치를 보고 그 구간을 정확히 가립니다.

📘 보충 — 코드에 등장한 도구들

re.finditer(pattern, content)

문장(content) 안에서 패턴과 일치하는 부분을 처음부터 끝까지 하나씩 찾아 반복(iterate)하게 해줍니다. 일치할 때마다 match 객체를 하나씩 건네주는데, match.group(0)은 일치한 전체 텍스트, match.start()/match.end()는 그 텍스트의 시작·끝 위치(인덱스)입니다.

패턴 앞의 r"..." — Raw String(원시 문자열)

문자열 앞에 붙은 r은 "백슬래시(\)를 특수문자로 해석하지 말고 적힌 그대로 넘겨라"는 뜻입니다. 정규식은 \b, \d처럼 백슬래시를 규칙의 일부로 자주 쓰는데, 일반 문자열에서는 \n(줄바꿈)처럼 엉뚱하게 해석될 수 있기 때문입니다.

🔍 비유 — "있는 그대로 받아 적어" 받아쓰기를 시킬 때 r은 "내가 말하는 기호를 해석하지 말고 글자 그대로 적어"라는 지시입니다. 일반 문자열 "C:\Users\name"은 \U를 특수문자로 오해해 에러가 날 수 있지만, r"C:\Users\name"은 적힌 그대로의 경로로 인식합니다.
💡 이 함수를 미들웨어에 꽂으려면 원문 교재(docs/02.agent-basic.md)에서는 API Key처럼 유출되면 치명적인 값은 block 전략으로 아예 실행을 막습니다. 방금 만든 탐지기를 PIIMiddleware(pii_type="api_key", detector=detect_api_key, strategy="block", apply_to_input=True)처럼 넘기면, API Key가 감지되는 순간 처리가 중단됩니다.
🚫 API Key는 가리는 게 아니라 막아야 한다 이메일·카드번호는 마스킹해서 계속 진행해도 되지만, API Key가 프롬프트에 섞여 들어왔다는 것 자체가 사고 신호입니다. 한 번 유출되면 남의 계정으로 요금이 폭증할 수 있으니, 마스킹(mask)이 아니라 실행 중단(block)으로 강하게 대응하는 것이 정석입니다.

📚 한 장 정리

오늘의 핵심 PIIMiddleware는 개인정보를 모델에 닿기 전에 가로채 가리는 검열 담당자다. "무엇을 찾을지(내장 유형 · 정규식 · 함수)"와 "어떻게 가릴지(redact · mask · block · hash)"를 따로 골라 조합한다.
  • PII — 개인을 식별할 수 있는 정보(이메일·카드·전화·IP 등). 민감 정보 Agent엔 필수 방어막.
  • 4가지 전략 — redact(통째 가림) · mask(뒷자리만 남김) · block(실행 중단) · hash(해시 치환).
  • 적용 시점 — apply_to_input(모델 전) · apply_to_output(모델 후) · apply_to_tool_results(도구 응답). 보통 입구에서 막는 input.
  • Built-in — PIIMiddleware(pii_type="email"/"credit_card", ...)만으로 자동 탐지·마스킹.
  • Custom(정규식) — detector에 정규식 문자열을 넘겨 전화번호 등 원하는 무늬를 잡는다.
  • Custom(함수) — detector에 탐지 함수를 넘겨 text·start·end 목록을 돌려주면, API Key 같은 값을 block으로 강하게 차단한다.
