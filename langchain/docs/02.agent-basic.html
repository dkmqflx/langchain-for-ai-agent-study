02. Agent 기초 — Tool · Memory · Middleware · Structured Output

원문: docs/02.agent-basic.md  ·  난이도: 🟢 입문

이 자료는 langchain/02 폴더의 실습 노트북 8개(01~08)를 관통하는 핵심 개념을 압축한 강의 교재입니다. Agent가 실시간 정보에 접근하도록 돕는 Tool, 대화 맥락을 기억하는 Memory, Agent의 흐름을 세밀하게 제어하는 Middleware, 그리고 Agent의 답변을 정해진 데이터 구조로 강제하는 Structured Output까지 — Agent를 이루는 네 기둥을 순서대로 조립해 봅니다.

이 장에서 배우는 것 Agent는 Tool(손발) · Memory(기억) · Middleware(통제)가 맞물려 돌아가는 하나의 시스템입니다. 여기에 Structured Output을 더하면 Agent의 최종 답변까지 원하는 형태로 다룰 수 있습니다.

(복습) Agent란?

먼저 Agent의 정의부터 복습합니다.

Agent란 사용자의 입력(질문, 지시)에 대해 적절한 행동을 취하도록 추론(Reasoning)한 뒤 행동(Act)하는 주체(Executor)입니다.

Agent의 구성 요소

  • Model (LLM) — 추론과 의사결정을 담당하는 두뇌
  • Tools (함수) — 실제 행동(검색, 계산, API 호출 등)을 수행하는 손과 발
구분LLM 기반 애플리케이션LLM 기반 Agent
정의고정된 파이프라인LLM이 스스로 추론하고 행동하는 동적 시스템
행동 흐름입력 → LLM → 출력입력 → 추론 → 도구 선택/사용 → 판단 → 반복 → 최종 출력
결정 주체개발자가 미리 정한 구조LLM이 매번 스스로 판단

1.1 Tool 기초

1.1.1 Tool이 왜 필요한가?

LLM 모델은 학습 데이터의 시간적 한계(Knowledge Cutoff)가 있습니다. 예를 들어 gpt-5-nano의 학습 데이터는 특정 날짜까지만 포함됩니다.

따라서 "현재 한국 날씨 어때?" 처럼 실시간 정보를 묻는 질문에는 모델이 답변하지 못합니다.

▶ 실제 응답 (예상 출력)
content='실시간 날씨를 제 지식으로 바로 확인해 알려드리기 어렵습니다...'

이 문제를 해결하는 것이 바로 Tool입니다. 날씨 관련 요청이 들어오면 model이 날씨를 검색하는 tool을 호출하고, tool의 검색 결과를 참고해 model이 답변합니다.

🔍 비유 — 백과사전을 통째로 외운, 방에 갇힌 천재 LLM은 어마어마한 양의 책을 통째로 외운 천재입니다. 하지만 그 천재는 창문 없는 방에 갇혀 있고, 외운 책들은 전부 특정 날짜(학습 시점)까지만 담고 있어요. 그래서 "지금 서울 날씨 어때?", "오늘 환율은?" 같이 방 밖의 실시간 정보는 아무리 똑똑해도 알 수가 없습니다. Tool은 이 천재에게 쥐여 주는 전화기입니다. 모르는 걸 물어보면, 천재가 직접 전화를 걸어 확인한 뒤 대답해 줍니다.

1.1.2 Tool이란?

Tool은 모델(LLM)이 외부 시스템(API, DB, 파일 시스템 등)과 상호작용하기 위해 사용하는 요소입니다.

구성 요소 : ① 호출 가능한 함수(callable function) + ② 입력 스키마(input schema)

📌 Tool은 함수다!!! LLM이 "언제", "어떤 인자로" 호출할지 스스로 결정합니다.

1.1.3 Tool 작성법

Tool을 만드는 방법은 단 4단계입니다.

1함수 작성

파이썬 함수로 실제 로직을 구현

2타입 힌팅

입력·출력 타입을 명시 → LLM이 인자를 정확히 채울 수 있게 됨

3docstring

함수(Tool) 설명 → LLM이 이 Tool을 언제 쓸지 이해

4@tool 데코레이터

함수 위에 데코레이터를 붙여 Tool로 등록

📥 코드
from langchain.tools import tool

@tool
def get_weather(location: str) -> str:
    """특정 지역의 날씨 정보 제공"""
    return f"{location}의 날씨는 맑고, 영하 2도입니다"
💡 docstring의 역할 docstring이 LLM에게 "이 Tool을 어떤 상황에 써야 하는지" 알려주는 설명서 역할을 합니다. 설명이 정확할수록 LLM이 올바른 Tool을 선택합니다.
🔍 비유 — 공구함에 라벨 붙이기 Tool은 Agent가 든 공구함 속 공구들입니다. 그런데 라벨이 없으면 Agent(초보 조수)는 어떤 공구를 언제 써야 할지 모릅니다. 그래서 각 공구에 이름표(함수명), 사용 설명서(docstring), 규격표(타입 힌트)를 꼼꼼히 붙여 줍니다. 라벨이 정확할수록 조수는 상황에 딱 맞는 공구를 척척 골라 쓰죠. 라벨이 대충이면? 엉뚱한 공구를 집습니다.

1.1.4 Tool과 Model 연결 — Agent 생성

langchain.agents의 create_agent를 사용해 모델과 tools를 전달하면 Agent가 생성됩니다.

📥 코드
from langchain.agents import create_agent

agent = create_agent(model, tools=[get_weather])
🔍 비유 — 두뇌 + 손발 = 일할 줄 아는 직원 모델(model)은 생각만 하는 두뇌이고, Tool들은 손과 발입니다. 두뇌만 있으면 "서울은 아마 맑겠죠?" 하고 상상해서 말할 뿐이지만, 손발이 붙으면 직접 창밖(날씨 API)을 확인하고 사실을 말합니다. create_agent(model, tools=[...])는 바로 이 두뇌에 손발을 붙여 '일할 줄 아는 직원(Agent)'을 채용하는 것입니다.

1.1.5 Agent 실행

invoke() 메서드로 Agent를 실행합니다. 입력은 messages 키를 가진 딕셔너리이며, 최종 응답은 result["messages"][-1].content에서 꺼냅니다.

📥 코드
result = agent.invoke({
    "messages": [{"role": "user", "content": "서울 날씨 어때요?"}],
})

print(result["messages"][-1].content)
▶ 이렇게 나와요 (예상 출력)
서울 현재 날씨는 맑고 영하 2도예요. 상당히 추우니 외출 시 두꺼운 옷이나...

1.1.6 Agent 내부 동작 — messages 구조 해부

Agent를 실행하면 내부적으로 여러 메시지가 쌓입니다.

📥 코드
{
    "messages": [
        HumanMessage(content='서울 날씨 어때요?', ...),
        # Model이 content를 생성하지 않고, tool_calls로 get_weather 도구 호출
        AIMessage(content='', tool_calls=[{'name': 'get_weather', 'args': {'location': '서울'}}]),
        ToolMessage(content='서울의 날씨는 맑고, 영하 2도입니다', name='get_weather', ...),
        AIMessage(content='서울 현재 날씨는 맑고 영하 2도예요...'),
    ]
}
💡 핵심 Tool을 호출할지 말지, 어떤 Tool을 호출할지, 호출에 필요한 인자({'location': '서울'})는 누가 작성할까? → Agent 객체 속 AI Model이 스스로 결정합니다.

1.1.7 Agent 작동 순서 정리

"서울 날씨 어때요?" 질문 시 Agent 내부에서 일어나는 6단계 흐름입니다.

1Human

HumanMessage("서울 날씨 어때요?") 전달

2AI Model

"이건 get_weather를 호출해야겠군" 추론

3AI Model

AIMessage(tool_calls=[...]) 생성

4Tool

get_weather() 실행

5Tool

ToolMessage("...맑고 영하 2도...") 반환

6AI Model

Tool 결과를 참고해 최종 AIMessage 생성

1.2 Tool 응용 1 — 여러 Tool + System Message

더 많은 도구를 모델에게 쥐어주고, 이를 활용하도록 System Message를 부여해 봅니다.

📥 코드
from langchain.tools import tool
from langchain.agents import create_agent

@tool
def add(a: int, b: int) -> int:
    """`a`와 `b` 덧셈.
    Args:
        a: First int
        b: Second int
    """
    return a + b

@tool
def multiply(a: int, b: int) -> int:
    """`a`와 `b` 곱셈.
    Args:
        a: First int
        b: Second int
    """
    return a * b

@tool
def divide(a: int, b: int) -> float:
    """`a`와 `b` 나눗셈.
    Args:
        a: First int
        b: Second int
    """
    return a / b

tools = [add, multiply, divide]

# system_prompt: LLM이 확률 기반으로 답을 직접 내놓는 것을 방지하기 위해
# "반드시 tool을 사용하라"는 지시를 추가합니다.
agent = create_agent(
    model,
    tools=tools,
    system_prompt="당신은 계산기입니다. 반드시 도구를 사용하여 계산을 수행해야 합니다."
)
📝 왜 system_prompt가 필요한가 LLM은 간단한 산술 문제를 도구 없이도 답할 수 있습니다. 이를 방지하려면 system_prompt에 "반드시 Tool을 사용하라"는 지시를 명시해야 합니다.
🔍 비유 — "암산 금지, 계산기만 써!"라는 시험 규칙 똑똑한 학생에게 계산기를 쥐여 줘도, 쉬운 문제는 암산으로 후딱 풀어 버립니다. 만약 반드시 계산기 사용 과정을 남겨야 하는 시험이라면, 감독관이 "모든 계산은 계산기로, 암산 금지"라는 규칙을 미리 못 박아야 하죠. system_prompt가 바로 이 감독관의 규칙입니다.

"3 × 23 + 42를 계산해줘" 요청 시 Agent가 단계별로 추론하며 Tools를 호출하는 과정입니다.

1사용자 질문

"3 × 23 + 42를 계산해줘"

2[AI] 곱셈 필요 판단

multiply(3, 23)

3[Tool] multiply 결과

69

4[AI] 덧셈 필요 판단

add(42, 69)

5[Tool] add 결과

111

6[AI] 내부 reasoning

반복 시도

7[AI] 최종 답변

"정답은 111입니다."

1.3 Tool 응용 2 — 외부 API 연동

"현재 알라딘에서 베스트셀러 Top10 뭐야?" 처럼 실시간으로 업데이트되는 정보는 모델이 직접 답변하지 못합니다.

▶ 실제 응답 (예상 출력)
content='실시간으로 업데이트되는 정보라 제가 바로 현재 Top 10을 확인해 드리진 못해요...'

이를 해결하려면 알라딘 Open API를 호출하는 Tool을 만들면 됩니다.

1API Key 발급

알라딘 API Key 발급

2Tool 함수 작성

Tool 함수 내에서 requests.get(url, params=params)으로 API 호출

3Agent 장착

Agent에 해당 Tool을 장착 → 실시간 베스트셀러 정보 조회 가능

📥 코드
import requests
from langchain.tools import tool

@tool
def get_aladin_bestsellers(count: int = 10) -> list:
    """알라딘 API를 사용하여 현재 가장 인기 있는 베스트셀러 도서 목록을 가져옵니다."""
    url = "http://www.aladin.co.kr/ttb/api/ItemList.aspx"
    params = {
        "ttbkey": ALADIN_API_KEY,
        "QueryType": "Bestseller",
        "MaxResults": min(count, 50),
        "SearchTarget": "Book",
        "output": "js",
        "Version": "20131101"
    }
    response = requests.get(url, params=params)
    data = response.json()
    return [
        {"title": item.get("title"), "author": item.get("author")}
        for item in data.get("item", [])
    ]
💡 LLM의 Function Calling 사용자가 "5권 알려줘"라고 하면 LLM이 자동으로 count=5 인자를 추출해 get_aladin_bestsellers(count=5)를 호출합니다. 이것이 가능한 이유는 함수의 docstring과 타입 힌트를 LLM이 읽고 이해하기 때문입니다.
🔍 비유 — 도서관 사서에게 거는 전화 이 함수는 알라딘이라는 거대한 도서관에 전화를 거는 것과 같습니다. 전화를 걸 때는 정해진 양식으로 말해야 하죠 — "저는 회원번호 ○○(ttbkey)이고요, 베스트셀러(QueryType) 목록을 5개(MaxResults)만, 도서(SearchTarget) 기준으로 주세요." 사서(서버)는 이 요청을 알아듣고 목록을 돌려줍니다. @tool은 이 "전화 거는 절차"를 LLM이 스스로 다이얼링할 수 있게 포장해 준 것입니다.

2.1 Memory 기초

다중 턴 대화 시 대화 맥락을 고려한 Tool 호출을 위해 메모리 관리가 필요합니다.

메모리 종류

종류저장 방식용도
Short-term memoryCheckpointer를 통해 대화 스레드(세션) 저장대화 중 문맥 유지
Long-term memoryStore를 통해 장기 메모리 저장사용자 선호도, 과거 정보 유지
💡 예시로 감 잡기 ChatGPT의 대화 기록(왼쪽 사이드바)이 Short-term memory의 예시이고, "사용자에 대해 알아주세요" 설정이 Long-term memory의 예시입니다.
🔍 비유 — 통화 중 메모지 vs. 주소록 전화 통화 중에 상대가 부른 번호를 메모지에 잠깐 적어두는 것이 Short-term memory입니다. 통화(세션)가 이어지는 동안만 유효하죠. 반면 자주 연락하는 사람을 주소록에 영구 저장하는 것이 Long-term memory입니다. 이 장은 메모지(Checkpointer) 이야기이고, 주소록(Store)은 나중 장의 몫입니다.

2.1.1 Short-term Memory — InMemorySaver

Checkpointer는 스레드(대화 상태)를 저장할 저장소입니다. InMemorySaver()는 메모리 내에 대화를 저장하는 가장 기본적인 Checkpointer로, "기억용 수첩과 펜을 Agent에게 쥐여주기"와 같습니다.

📥 코드
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model,
    tools,
    checkpointer=InMemorySaver(),
)
🔍 비유 — 수첩과 펜을 손에 쥐여주기 기억을 못 하던 상담사에게 수첩과 펜을 하나 쥐여줬다고 상상해보세요. 이제 그는 손님이 한 말을 그때그때 수첩에 적어두고, 다음에 그 손님이 오면 수첩을 펼쳐 읽습니다. InMemorySaver()가 바로 이 수첩이고, checkpointer=로 넘기는 행위가 상담사(Agent)에게 그 수첩을 쥐여주는 것입니다.

2.1.2 thread_id로 대화 세션 구분

invoke() 호출 시 configurable 딕셔너리에 thread_id를 지정합니다. 같은 thread_id를 사용하면 이전 대화가 이어집니다.

📥 코드
# thread_id 1에 첫 번째 대화 저장
response = agent.invoke(
    {"messages": [{"role": "user", "content": "안녕하세요! 저는 Bloom ai의 Jay입니다."}]},
    {"configurable": {"thread_id": "1"}},
)
print(response["messages"][-1].content)

# 같은 thread_id로 이어서 대화
response = agent.invoke(
    {"messages": [{"role": "user", "content": "제 이름이 뭐라고 했죠?"}]},
    {"configurable": {"thread_id": "1"}},
)
print(response["messages"][-1].content)
▶ 이렇게 나와요 (예상 출력)
안녕하세요, Jay님! Bloom AI와 함께하게 되어 반갑습니다...

당신은 Jay라고 하셨습니다.

thread_id를 바꾸면 새로운 대화 스레드가 생성됩니다. 이전 대화 내용을 전혀 모르는 상태에서 시작합니다.

📥 코드
# thread_id를 2로 변경 → 새로운 대화 스레드
response = agent.invoke(
    {"messages": [{"role": "user", "content": "지금까지 무슨 얘기 나눴죠?"}]},
    {"configurable": {"thread_id": "2"}},
)
print(response["messages"][-1].content)
▶ 이렇게 나와요 (예상 출력)
지금까지의 대화 내용을 제가 직접 보지 못해 요약해 드리려면 두 가지가 필요합니다...
📌 thread_id = 대화방 번호 thread_id는 대화방 번호와 같습니다. 같은 번호면 이전 대화가 이어지고, 다른 번호면 완전히 새로운 대화가 시작됩니다.
🔍 비유 — 카카오톡 채팅방 thread_id는 메신저의 채팅방과 똑같습니다. "엄마와의 대화방"에 들어가면 어제 나눈 얘기가 그대로 이어져 있고, "친구와의 대화방"으로 옮기면 완전히 다른 맥락이 펼쳐지죠. 번호가 같으면 같은 방, 번호가 다르면 다른 방입니다.

3.1 Middleware 기초

Middleware는 Agent 내부에서 일어나는 일을 섬세하게 컨트롤하는 방법입니다. 기존의 단순한 request → model → tools → result 흐름에서 각 단계 사이에 훅(hook)을 끼워 넣을 수 있습니다. 

request
  ↓
before_agent
  ↓
before_model ←──────────────────┐
  ↓                             │
wrap_tool_call    wrap_model_call│
  (tools)           (model)     │
  ↓                             │
after_model ────────────────────┘
  ↓
after_agent
  ↓
result

즉 Middleware가 개입할 수 있는 지점은 before_agent / before_model / wrap_model_call / wrap_tool_call / after_model / after_agent 여섯 곳입니다.

Middleware의 주요 기능

  • Agent 내부 활동 모니터링 및 컨트롤 — 각 단계에서 로그 수집, 메트릭 기록
  • 프롬프트, tool 선택, 출력 포맷 수정 — 요청 전처리 및 응답 후처리
  • 가드레일 — 개인정보 감지(PII), 프롬프트 인젝션 방지, 욕설 필터링
🔍 비유 — 무대 뒤 스태프 Agent가 사용자와 대화하는 것을 연극 무대라고 해봅시다. 배우(AI 모델)는 무대 위에서 열심히 연기합니다. 그런데 무대 뒤에는 여러 스태프가 있어요 — 조명을 조절하고, 소품을 챙기고, 대본 진행을 점검하죠. 미들웨어가 바로 이 무대 뒤 스태프입니다. 배우와 관객(사용자) 사이에 슬쩍 끼어들어 요청과 응답을 다듬거나 보조하는 존재죠. 배우는 자기 연기에만 집중하고, 나머지 잔손질은 스태프가 알아서 해줍니다.

3.2 Middleware 종류

Middleware는 크게 두 종류로 나뉩니다.

종류설명
Built-in middlewareLangChain이 제공하는 내장 미들웨어
Custom middleware개발자가 직접 작성하는 미들웨어

from langchain.agents import create_agent
from langchain.agents.middleware import PIIMiddleware

agent = create_agent(
    model="gpt-5-nano",

    ],
)

3.3.1 LLM Tool Emulator — LLM 기반 Tool 흉내내기

LLM Tool Emulator는 실제 Tool 호출 대신 LLM이 Tool의 응답을 시뮬레이션하는 미들웨어입니다.

  • Tool 호출이 불가하거나 너무 비싼 경우
  • 프로토타입 단계에서 실제 API 없이 개발할 때 활용
📥 코드
from langchain.agents.middleware import LLMToolEmulator

agent = create_agent(
    model="gpt-5-nano",
    tools=[send_email_tool, read_email_tool],
    middleware=[
        LLMToolEmulator(model="gpt-5-nano"),  # 디폴트 모델: anthropic:claude-3-5-sonnet-latest
        # 특정 Tool만 설정도 가능
        # LLMToolEmulator(tools=["get_weather", "search_database"]),
    ],
)

실제 이메일 백엔드 없이도 send_email_tool, read_email_tool을 흉내 낸 응답을 생성합니다. 로그를 보면 실제 Tool이 아닌 LLM이 생성한 더미 응답이 ToolMessage로 돌아오는 것을 확인할 수 있습니다.

🔍 비유 — 영화 촬영장의 소품과 대역 은행 강도 장면을 찍는다고 진짜 돈을 털지는 않습니다. 가짜 지폐 다발을 쓰고, 위험한 장면은 배우 대신 대역(스턴트)이 뜁니다. 카메라에 담긴 화면은 "진짜처럼" 보이지만 실제로는 아무 은행도 털리지 않았죠. LLMToolEmulator가 바로 이 소품·대역입니다. Agent는 "이메일을 읽고 보냈다"고 그럴듯하게 연기하지만, 실제 메일함은 손끝 하나 대지 않습니다.

3.3.2 Todo List — 작업 단계 자동 계획

Todo List Middleware는 복잡한 요청을 처리할 때 Agent가 작업 단계를 스스로 계획하고 추적하도록 돕습니다.

📥 코드
from langchain.agents.middleware import LLMToolEmulator, TodoListMiddleware

agent = create_agent(
    model="gpt-5-nano",
    tools=[send_email_tool, read_email_tool],
    middleware=[
        LLMToolEmulator(model="gpt-5-nano"),
        TodoListMiddleware(),
    ],
)

"온 메일 다 확인한 뒤 요약해 보고해. 그 다음 답장 작성해 회신 보내줘." 같은 복잡한 요청 시 Agent가 write_todos Tool을 호출해 할 일 목록을 만들고, 단계별로 status를 in_progress → completed로 업데이트하며 진행합니다.

▶ 내부적으로 AI가 호출하는 write_todos 예시
{
    "todos": [
        {"content": "최신 이메일 3개 확인 및 요약", "status": "in_progress"},
        {"content": "주요 포인트 요약 작성", "status": "pending"},
        {"content": "개별 답장 초안 작성", "status": "pending"},
        {"content": "답장 발송", "status": "pending"},
        {"content": "발송 보고서 작성", "status": "pending"},
    ]
}
💡 복잡한 요청에만 작동 TodoListMiddleware는 복잡한 요청에만 작동합니다. 단순한 질문("안녕?")에는 AI가 굳이 할 일 목록을 만들 필요가 없다고 판단해 write_todos를 호출하지 않습니다.
🔍 비유 — 주방의 주문표(Order Ticket) 바쁜 식당 주방을 떠올려 보세요. 손님이 "스테이크는 미디엄으로, 파스타는 면 따로, 디저트는 마지막에"처럼 여러 요구가 섞인 주문을 하면, 요리사는 이걸 머릿속에만 담아두지 않습니다. 주문표(order ticket)를 뽑아 벽에 걸어두고 하나씩 완성될 때마다 줄을 그어 지우죠. TodoListMiddleware가 바로 이 주문표 시스템입니다. AI가 복잡한 요청을 받으면 스스로 주문표를 뽑아 걸고, 진행 상황을 하나씩 지워가며 관리합니다.

3.3.3 Human-in-the-loop — 사용자 개입

Human-in-the-loop Middleware는 작업 전 사용자의 의사를 묻는 미들웨어입니다. 이메일 발송, 결제 처리 등 부작용(Side Effect)이 크거나 되돌리기 어려운 작업에 적합합니다.

📥 코드
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver

# Human-in-the-loop는 반드시 checkpointer와 함께 사용해야 합니다.
checkpointer = InMemorySaver()

agent = create_agent(
    model,
    tools=[send_email_tool, read_email_tool],
    checkpointer=checkpointer,
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                # 이메일 보내기 전 사람의 판단 개입 (approve / edit / reject 중 선택)
                "send_email_tool": {"allowed_decisions": ["approve", "edit", "reject"]},
                # 이메일 읽기는 자동 승인 (사람 개입 없음)
                "read_email_tool": False,
            }
        ),
    ],
)

Agent가 send_email_tool을 호출하려는 순간, 실행이 일시정지(Interrupt)되고 __interrupt__ 키와 함께 결과가 반환됩니다. 사용자의 결정이 확인되면 같은 thread_id로 invoke를 다시 호출해 실행을 재개합니다.

📥 코드
# 첫 번째 invoke: 미들웨어가 send_email_tool 호출을 막고 __interrupt__ 반환
response = agent.invoke(
    {"messages": [{"role": "user", "content": "jasper@gmail.com에게 메일 보내줘"}]},
    {"configurable": {"thread_id": "HIL-1"}}
)
# response["__interrupt__"] 에 승인 대기 중인 도구 정보 담겨 있음

# 두 번째 invoke: 사용자 승인 후 실행 재개
response = agent.invoke(
    {"decision": "approve"},
    {"configurable": {"thread_id": "HIL-1"}}
)
📌 왜 checkpointer가 필요할까 HumanInTheLoopMiddleware가 InMemorySaver(Checkpointer)와 함께 사용되는 이유는, 멈췄던 지점의 상태(state)를 thread_id 기준으로 기억해야 나중에 재개할 수 있기 때문입니다. 2.1절의 "수첩과 펜" 비유 그대로 — 멈춘 페이지를 수첩에 적어 두었다가, 다시 그 페이지를 펼쳐 이어가는 것입니다.
🔍 비유 — 이체 버튼 앞의 "정말 보내시겠습니까?" 은행 앱에서 100만 원을 이체할 때, 앱은 곧바로 돈을 보내지 않습니다. "수취인 · 금액을 확인하세요" 창을 띄우고 당신이 확인 버튼을 누를 때까지 모든 걸 멈춘 채 기다립니다. 잘못 보내면 되돌릴 수 없으니까요. Human-in-the-Loop이 바로 이 확인 창입니다. AI가 위험한 도구를 실행하려는 순간, 미들웨어가 손을 들어 "잠깐! 사람 승인부터"라고 흐름을 붙잡습니다.

3.3.4 PII Detection — 개인정보 탐지

PII(Personally Identifiable Information) Middleware는 의료, 헬스 케어, 금융 등 민감 정보를 다루는 Agent 구축 시 필수적으로 활용됩니다.

Built-in PII 유형

email, credit_card, ip, mac_address, url 등

처리 전략 (strategy)

전략설명예시
block에러 발생 (실행 중단)—
redact완전 마스킹[REDACTED_EMAIL]
mask부분 마스킹************4321
hash해싱 처리a3f2...

적용 시점 (apply_to)

옵션시점
apply_to_inputmodel 호출 전
apply_to_outputmodel 호출 이후
apply_to_tool_resultstool의 응답 메시지에 대한 블록
📥 코드
from langchain.agents.middleware import PIIMiddleware

agent = create_agent(
    model,
    tools=[save_customer_feedback],
    middleware=[
        # 이메일 주소는 전부 마스킹 처리
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
        # 카드번호는 마지막 4자리만 남기고 나머지 마스킹 처리
        PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
        # API Key 형태(sk-로 시작하는 32자리)는 감지되면 실행 중단
        PIIMiddleware(
            "api_key",
            detector=r"sk-[a-zA-Z0-9]{32}",
            strategy="block",
            apply_to_input=True,
        ),
    ],
)
🔍 비유 — 편지를 부치기 전 검은 매직펜으로 지우기 기밀문서를 외부에 공개할 때, 담당자는 이름·주민번호 같은 민감한 부분을 검은 매직펜으로 쓱쓱 칠해 못 읽게 만든 뒤 내보냅니다. PIIMiddleware가 바로 그 검열 담당자입니다. 사용자의 말이 모델에게 도착하기 전, 중간에서 가로채 개인정보만 골라 까맣게 칠하는 것이죠. 모델은 처음부터 지워진 버전만 받으므로, 원본이 실수로 새어 나갈 일이 없습니다.

3.3.5 Summarization — 대화 요약

Summarization Middleware는 대화가 길어질 때 오래된 메시지를 자동으로 요약하여 토큰 사용량을 줄입니다.

파라미터설명
model요약 작업을 수행할 대상 LLM 모델 지정 (필수)
trigger메시지 개수나 토큰 수 등 요약 기능이 실행될 발동 조건 설정
keep요약 실행 후에도 문맥 유지를 위해 원본 그대로 남겨둘 최신 대화 범위
summary_prompt기본 템플릿 대신 구체적인 요약 스타일을 지시할 커스텀 프롬프트
trim_tokens_to_summarize요약 모델에 입력할 대화 내용이 너무 길지 않도록 제한하는 최대 토큰 수
🔍 비유 — 드라마의 "지난 줄거리" 코너 시즌이 길어진 드라마는 매 화 시작 전 "지난 줄거리" 코너로 오래된 회차를 몇 문장으로 압축해 보여주고, 최근 몇 회는 그대로 다시 보여줍니다. 그래야 시청자가 전체 맥락은 잃지 않으면서도 매번 처음부터 다 볼 필요가 없죠. SummarizationMiddleware가 하는 일이 정확히 이것입니다 — 오래된 대화(메시지)는 trigger 조건에 따라 요약본으로 압축하고, keep으로 지정한 최근 대화만 원문 그대로 남겨 토큰을 절약합니다.

3.4 Custom Middleware

Built-in 미들웨어로 해결이 안 되는 경우, 직접 미들웨어를 개발할 수 있습니다. Agent가 작동하는 특정 순간에 개입(hook)하는 로직을 직접 작성합니다.

구현 방식

방식설명적합한 경우
데코레이터 방식@before_agent, @after_model 등 단일 훅 함수에 데코레이터 적용단일 훅을 간단하게 구현할 때
클래스 방식미들웨어 베이스 클래스를 상속해 여러 메서드 구현여러 훅을 포함한 복잡한 미들웨어 구현 시

개입 가능한 훅 포인트: before_agent / before_model / wrap_model_call / wrap_tool_call / after_model / after_agent

4.1 Agent에서 Structured Output

Agent의 실행 결과를 자연어가 아닌 특정 포맷의 구조화된 데이터로 파싱할 수 있습니다.

케이스설명
case 1고객의 컴플레인 메일을 Agent가 답장 생성 → 일반 자연어 답변 생성
case 2Agent가 메일의 의도, 감정 상태, 요약, 다음 수행 업무 등을 분석 후 구조에 맞춰 데이터 생성 → 구조화된 답변 생성
🔍 비유 — 서술형 답안 vs OMR 카드 선생님이 학생에게 감상문을 받으면 사람이 한 줄 한 줄 읽어야 뜻을 압니다(자연어). 하지만 OMR 답안카드는 다릅니다 — "1번 보기, 2번 보기" 칸이 정해져 있어 기계가 그대로 채점할 수 있죠. Structured Output은 Agent에게 감상문 대신 OMR 카드를 쥐여주는 것입니다. "네 맘대로 문장 쓰지 말고, 이 칸들(의도·감정·요약·다음 조치)을 채워서 돌려줘"라고 시키면, 결과를 코드에서 바로 다룰 수 있는 데이터로 받게 됩니다.

4.2 Pydantic으로 출력 구조 정의

1장에서 배운 Pydantic을 사용해 Agent의 최종 출력 구조를 정의합니다.

📥 코드
from pydantic import BaseModel, Field
from typing import Literal

class EmailAnalysis(BaseModel):
    """이메일 내용을 분석한 결과 구조."""

    intent: Literal["complaint", "inquiry", "confirmation", "other"] = Field(
        description="이메일의 주요 의도 (예: complaint=불만, inquiry=문의, confirmation=확인, other=기타)"
    )
    sentiment: Literal["positive", "negative", "neutral"] = Field(
        description="이메일의 감정 상태"
    )
    summary: str = Field(description="이메일 내용 요약")
    next_action: str = Field(description="에이전트가 수행해야 할 다음 단계 (예: 회신, 확인, 무시 등)")
🔍 비유 — Literal은 자판기 버튼 summary는 아무 문장이나 써도 되는 주관식 칸입니다(str). 반면 intent는 Literal["complaint", "inquiry", "confirmation", "other"] — 즉 정해진 네 개의 버튼 중 하나만 누를 수 있는 자판기와 같습니다. Agent가 "아마 컴플레인 같기도 하고요…" 같은 애매한 답을 쓰지 못하고, 반드시 이 네 값 중 하나로만 답하게 강제합니다.

4.3 ToolStrategy로 Agent에 구조 적용

create_agent의 response_format 파라미터에 ToolStrategy(스키마클래스)를 전달하면 Agent의 최종 응답이 해당 구조로 강제됩니다.

📥 코드
from langchain.agents import create_agent
from langchain.agents.structured_output import ToolStrategy
from langchain.agents.middleware import LLMToolEmulator

agent = create_agent(
    model="gpt-5-nano",
    tools=[send_email_tool, read_email_tool],
    response_format=ToolStrategy(EmailAnalysis),  # ToolStrategy에 구조 전달
    middleware=[
        LLMToolEmulator(model="gpt-5-nano"),
    ],
)

response = agent.invoke({"messages": [{"role": "user", "content": "최근 온 메일을 읽고 분석해줘."}]})

# messages[-1].content 대신 structured_response 키로 바로 접근
analysis = response["structured_response"]
print(analysis.intent)
print(analysis.sentiment)
print(analysis.summary)
▶ 이렇게 나와요 (예상 출력)
'inquiry'
'neutral'
'고객이 환불을 요청하고 있습니다.'
💡 structured_response로 바로 접근 response_format=ToolStrategy(EmailAnalysis)를 사용하면 response["structured_response"]로 Pydantic 객체에 직접 접근할 수 있어, .content를 파싱하는 번거로움이 없습니다.
🔍 비유 — response_format은 "결재 서식 지정" 회사에서 보고를 올릴 때, 상사가 "자유 형식 말고 정해진 결재 서식에 맞춰 제출해"라고 하면 아무리 내용이 좋아도 그 서식대로 칸을 채워야 결재가 통과됩니다. response_format=ToolStrategy(EmailAnalysis)가 바로 그 "이 서식으로 제출해"라는 지시입니다. Agent가 도구를 쓰고 이런저런 추론을 하다가도, 마지막 제출물만큼은 반드시 이 서식(EmailAnalysis)에 맞춰 내놓아야 합니다.
🔍 비유 — .content는 봉투, structured_response는 정리된 표 response["messages"][-1].content는 손편지가 든 봉투를 받는 것과 같습니다 — 뜯어서 사람이 읽고 뜻을 해석해야 하죠. 반면 response["structured_response"]는 누군가 그 편지를 미리 읽고 항목별로 칸을 채워 넣은 표를 건네받는 것과 같습니다. "의도: 문의 / 감정: 중립 / 요약: … / 다음 조치: …" — 파싱이라는 번거로운 단계가 통째로 사라집니다.

📚 2장 정리

오늘의 핵심 Agent는 Tool(손발) · Memory(기억) · Middleware(통제)가 맞물려 돌아가는 시스템이고, Structured Output은 그 최종 답변까지 원하는 형태로 다듬어 준다.
  • Tool은 LLM이 외부 시스템과 상호작용하기 위한 함수다. @tool 데코레이터와 docstring으로 정의하고, create_agent로 모델에 연결한다.
  • Agent 내부 동작: LLM이 tool_calls를 결정 → Tool 실행 → ToolMessage 반환 → 최종 응답 생성의 6단계 흐름으로 작동한다.
  • Memory: InMemorySaver + thread_id로 Short-term memory를 구현한다. 같은 thread_id이면 대화가 이어지고, 다르면 새 세션이 시작된다.
  • Middleware: Agent 흐름의 각 단계에 개입해 모니터링, 프롬프트 수정, 가드레일 등을 추가한다.
    • LLM Tool Emulator: 실제 API 없이 Tool 응답을 시뮬레이션
    • Todo List: 복잡한 요청을 단계별 Todo로 관리
    • Human-in-the-loop: 위험한 Tool 실행 전 사람의 승인 필요
    • PII Detection: 개인정보 탐지 및 마스킹/차단
    • Summarization: 긴 대화를 자동 요약해 토큰 절약
  • Structured Output: ToolStrategy(PydanticClass)를 response_format에 전달해 Agent의 최종 응답을 구조화된 데이터로 받는다.
