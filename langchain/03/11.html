11. @tool 인자 결정·전달 원리

실습 노트북: 11.ipynb  ·  원문: docs/03.advanced-agent.md  ·  난이도: 🟡 중급  ·  선행: 10. Agent 메모리 주입

이 자료는 실습 노트북(11.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 에이전트에 도구(@tool)를 여러 개 붙이다 보면 이런 의문이 생깁니다 — "어떤 함수는 인자가 city 하나인데, 어떤 함수는 runtime이라는 낯선 인자가 붙어 있네? 이 값들은 대체 누가 채워 넣는 거지?" 이 노트북은 바로 그 답 — 도구 인자에는 'AI가 채우는 칸'과 '시스템이 자동으로 채우는 칸'이 섞여 있다 — 를 메모리 저장·조회 예제를 통해 풀어봅니다.

🔍 비유 — 병원 접수 서류 병원에서 서류를 작성할 때, 어떤 칸은 환자가 직접 손으로 씁니다 — "어디가 아프세요?", "이름이 뭐예요?". 반면 어떤 칸은 접수처 컴퓨터가 자동으로 찍어줍니다 — 접수 번호, 방문 시각, 진료 기록 ID. @tool 함수의 인자도 똑같이 두 종류입니다. AI(환자)가 대화에서 뽑아 채우는 인자가 있고, 시스템(접수처 컴퓨터)이 알아서 꽂아주는 인자가 있어요. 이 둘을 구분할 줄 알면 도구 함수의 시그니처가 갑자기 읽히기 시작합니다.
이 노트북에서 배우는 것 메모리를 저장하는 도구와 조회하는 도구를 만들어 에이전트에 붙입니다. 그 과정에서 (1) LLM이 도구 인자를 어떻게 스스로 채우는지, (2) runtime 같은 특수 인자는 왜 LLM이 건드리지 않는지, (3) 지난 10장의 "무조건 주입" 방식과 이번 "필요할 때만 호출" 방식이 토큰 비용에서 어떻게 갈리는지를 배웁니다.

0. 준비물 — Context · UserInfo · Store

먼저 모델과 기본 도구/에이전트 함수를 불러옵니다. 10장과 똑같이 시작하지만, 이번엔 도구가 주인공입니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent


# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")

다음으로, 이 노트북의 핵심 재료 세 가지를 정의합니다. 각자 역할이 뚜렷합니다.

1Context

"지금 누가 실행 중인가"를 담는 신분증 (user_id, app_name)

2UserInfo

LLM이 대화에서 뽑아낼 정보의 양식(칸 구조)

3Store

뽑아낸 정보를 실제로 쌓아둘 창고(메모리 저장소)

🔍 비유 — 택배 상자에 붙이는 3종 세트 Context는 보내는 사람 스티커(누구의 물건인지), UserInfo는 내용물 기재란(무엇을 어떤 칸에 적을지), Store는 물건이 실제로 쌓이는 창고입니다. 셋이 맞물려야 "누구의(Context) 어떤 정보를(UserInfo) 어디에(Store) 넣을지"가 결정됩니다.
📥 코드
from dataclasses import dataclass
from typing import TypedDict
from langgraph.store.memory import InMemoryStore

# 1. 실행 컨텍스트 정의 (누가 실행하는지 식별)
@dataclass
class Context:
    user_id: str
    app_name: str

# 2. LLM이 추출해야 할 정보의 구조를 정의
class UserInfo(TypedDict):
    personal_information : str
    preference: str
# LLM이 추출해야 할 정보의 구조를 정의 (사용자의 request로 부터 추출해야 할 정보의 구조를 정의)
# 즉, LLM이 request로 부터 정보를 추출한다음, 해당 정보를 Tool에 전달해야하는 경우 전달한다

# 3. 빈 Store 초기화
store = InMemoryStore()

여기서 눈여겨볼 점은 UserInfo를 TypedDict로 정의했다는 것입니다. 이 UserInfo가 잠시 뒤 저장 도구의 인자 타입으로 쓰이면서, LLM에게 "이 칸(personal_information, preference)에 맞춰 정보를 채워줘"라는 양식지 역할을 하게 됩니다. 그런데 왜 하필 TypedDict일까요? Pydantic과는 뭐가 다를까요? 노트북이 이 대목에서 짚어주는 내용을 보충 카드로 옮깁니다.

📘 보충 — TypedDict vs Pydantic, 뭐가 다를까?

둘의 가장 큰 차이는 딱 하나 — "실행 중에 데이터를 검증(Validation)하느냐, 안 하느냐"입니다.

🔍 비유 — 이름표 vs 검사원 TypedDict는 이름표입니다. "여기엔 age라는 칸이 있어"라고 알려주기만 할 뿐, 엉뚱한 값이 들어와도 막지 않습니다. Pydantic은 검사원입니다. "이 칸은 반드시 정수여야 해!"라며 실제로 검사하고, 틀리면 바로 퇴짜(에러)를 놓습니다.
특징TypedDict (파이썬 내장)Pydantic (외부 라이브러리)
실행 시 검증안 함 (타입이 틀려도 에러 없음)함 (틀리면 즉시 에러)
타입 변환안 함 ("10"은 문자열 그대로)함 ("10" → 정수 10으로 변환)
정체단순한 딕셔너리(dict)새로운 객체(Object)
속도매우 빠름 (검증이 없으므로)상대적으로 느림 (검증 과정 존재)

① TypedDict — 검사 안 함

from typing import TypedDict

class User(TypedDict):
    age: int

# 에러가 안 납니다! (타입 힌트일 뿐이라서)
user = User(age="스무살")
print(user["age"])  # "스무살" (문자열 그대로 출력됨)

② Pydantic — 엄격하게 검사함

from pydantic import BaseModel

class User(BaseModel):
    age: int

user1 = User(age="20")     # "20"을 정수 20으로 자동 변환 (성공)
user2 = User(age="스무살")  # 정수로 못 바꿔서 ValidationError! (실패)
💡 언제 뭘 쓰나 속도가 중요하고 값을 가볍게 받아 넘기기만 할 땐 TypedDict, 데이터 정확성이 중요하고 LLM이 뱉은 불안정한 값을 안전하게 정제하고 싶을 땐 Pydantic. 최근 LangChain은 LLM 응답 구조화에 Pydantic을 더 권장하는 추세입니다(LLM이 가끔 이상한 값을 주니까요). 이 노트북은 학습용으로 가벼운 TypedDict를 씁니다.

1. 도구 두 개 만들기 — get_user_info · save_user_info

이제 에이전트에게 쥐여줄 도구 두 개를 만듭니다. 하나는 정보를 꺼내는(조회) 도구, 다른 하나는 정보를 넣는(저장) 도구입니다. 두 함수의 인자 구성이 다르다는 점을 미리 마음에 담아두세요 — 바로 다음 절의 핵심 주제입니다.

① 조회 도구 — get_user_info(runtime)

"내 정보 보여줘"에 답하는 도구입니다. 사용자가 따로 넘겨줄 데이터는 없습니다. 다만 "지금 질문한 사람이 누구인지(user_id)"를 알아야 창고에서 그 사람 것만 꺼낼 수 있죠. 그 정보는 runtime이라는 인자를 통해 얻습니다.

📥 코드
import uuid
from langchain_core.runnables import RunnableConfig
from langchain.tools import tool, ToolRuntime

# --- 조회 도구 ---
@tool
def get_user_info(runtime) -> str:
    """
    현재 사용자의 정보 조회 (시스템 내부용 도구)
    """
    user_id = runtime.context.user_id
    app = runtime.context.app_name

    # 해당 네임스페이스의 모든 메모리 검색
    memories = runtime.store.search((user_id, app))

    if not memories:
        return "기록된 정보 없음"

    results = []
    for item in memories:
        # 저장된 데이터 구조(UserInfo)에 맞춰 필드 확인
        data = item.value
        print('data', data)
        if "personal_information" in data: # 딕셔너리 key 중에 personal_information이 있으면
            results.append(f"- 개인정보: {data['personal_information']}")
        if "preference" in data:
            results.append(f"- 선호도: {data['preference']}")

    return "\n".join(results) if results else "데이터 형식 불일치로 읽을 수 없음"

runtime.context에서 user_id·app_name을 꺼내 runtime.store.search(...)로 그 사람의 메모리만 조회합니다. context와 store가 모두 runtime 하나에 매달려 있는 게 보이죠.

② 저장 도구 — save_user_info(user_info, runtime)

"내 이름은 Alice야, 차를 좋아해" 같은 말에서 정보를 뽑아 창고에 넣는 도구입니다. 조회 도구와 달리 인자가 두 개입니다 — 무엇을 저장할지(user_info)와, 누구의 창고에 넣을지(runtime).

📥 코드
from langchain.tools import ToolRuntime

# --- 저장 도구 ---
@tool
def save_user_info(user_info: UserInfo, runtime: ToolRuntime) -> str:
    """
    사용자의 정보를 저장하거나 업데이트
    """
    # 1. 실행 컨텍스트에서 user_id 가져오기
    user_id = runtime.context.user_id
    app = runtime.context.app_name
    store = runtime.store

    # 2. Store에 데이터 저장 (UUID를 생성하여 계속 누적)
    memory_key = str(uuid.uuid4())
    store.put((user_id, app), memory_key, user_info)

    return f"정보가 안전하게 저장되었습니다. (ID: {memory_key})"
⚠️ 두 도구의 미묘한 차이 — 타입 힌트 자세히 보면 저장 도구는 runtime: ToolRuntime이라고 타입을 명시했지만, 조회 도구는 그냥 runtime(힌트 없음)입니다. 특수 인자는 ToolRuntime 타입을 붙여주는 것이 정석입니다. 그래야 프레임워크가 "이건 시스템이 주입할 인자"라고 확실히 알아보고 LLM에게 보이는 설명서에서 숨겨줍니다. (실제로 뒤의 실행 결과를 보면, 힌트 없는 조회 도구에서는 LLM이 runtime 칸을 채우려 시도한 흔적 'runtime': {}이 남습니다.)

2. 인자는 누가 채우나 — AI vs 시스템

두 도구의 인자를 나란히 놓고 보면 규칙이 보입니다. @tool 함수가 받을 수 있는 인자는 크게 두 부류로 나뉩니다.

부류누가 채우나예시정체
일반 인자 AI(LLM) — 대화에서 값을 추출 user_info, city, query 함수 실행에 필요한 데이터
특수 인자
(주입, Injected)		 시스템(Runtime) — 자동 주입 runtime, config, tool_call_id 함수 실행에 필요한 환경 정보
🔍 비유 — 식당 서버와 주방 손님이 서버에게 "김치찌개 하나요"라고 주문 내용을 말합니다 — 이건 손님(AI)이 채우는 값입니다. 하지만 주방으로 넘어가는 주문표에는 테이블 번호, 주문 시각도 함께 찍혀 있죠. 이건 손님이 말한 게 아니라 포스(POS) 시스템이 자동으로 붙인 겁니다. user_info는 손님이 말한 주문, runtime은 시스템이 찍어준 테이블 번호예요.

그래서 두 함수의 인자 개수가 다른 이유가 자연스럽게 설명됩니다.

  • save_user_info — "무엇을 저장할지" 알아야 하니 user_info(AI가 채움)가 필요하고, "누구의 창고에 넣을지" 알아야 하니 runtime(시스템이 채움)도 필요합니다. → 인자 2개
  • get_user_info — 사용자가 줄 데이터는 따로 없습니다("그냥 내 정보 보여줘"). 하지만 "누구의 정보인지"는 알아야 하니 runtime만 있으면 충분합니다. → 인자 1개

3. @tool 인자 결정·전달 원리

그렇다면 AI는 대체 어떻게 "이 인자에 이 값을 넣어야지"라고 판단할까요? 결론부터 말하면, LLM은 함수의 이름, 설명(docstring), 인자의 타입 힌트 — 이 세 가지를 설명서(스키마)처럼 읽고 스스로 값을 정합니다.

🔍 비유 — 라벨만 보고 채우는 서류 낯선 신청서를 받아도 우리는 칸 옆의 라벨을 보고 채웁니다 — "이름" 칸엔 이름을, "생년월일" 칸엔 날짜를요. LLM도 똑같습니다. @tool이 함수의 이름·docstring·타입 힌트를 라벨로 만들어 건네주면, LLM은 그 라벨을 읽고 대화 속에서 알맞은 값을 뽑아 채웁니다. 그래서 docstring과 타입 힌트를 잘 써두는 것이 곧 "AI가 실수 없이 인자를 채우게 만드는 법"입니다.

① 일반 인자가 있는 경우 (AI가 채움)

예를 들어 이런 날씨 도구가 있다고 해봅시다.

📥 코드
@tool
def get_weather(city: str) -> str:
    """특정 도시의 현재 날씨를 가져옵니다."""
    return f"{city}의 날씨는 맑고 22도입니다."

사용자가 "서울 날씨 어때?"라고 물으면, LLM은 docstring("특정 도시의 현재 날씨")과 타입 힌트(city: str)를 보고 "city 칸에 도시 이름을 넣어야겠구나"라고 이해합니다. 그리고 내부적으로 {"city": "Seoul"}이라는 JSON을 만들어내고, LangChain이 이를 get_weather(city="Seoul") 호출로 바꿔줍니다.

▶ 이렇게 흘러갑니다
1스키마 읽기

LLM이 이름·docstring·타입 힌트를 설명서로 받음

2값 추출

대화에서 뽑아 {"city":"Seoul"} JSON 생성

3주입

프레임워크가 특수 인자(runtime)를 자동으로 끼움

4함수 호출

실제 파이썬 함수가 두 값을 받아 실행

② 특수 인자가 있는 경우 (시스템이 채움)

get_user_info(runtime)의 runtime에 무엇이 들어갈지는 LLM이 정하지 않습니다. 프레임워크의 '인자 주입(Injection)' 규칙이 정합니다.

  • LLM은 이 인자의 존재를 모릅니다. @tool이 LLM에게 보내는 도구 설명서에서 runtime 같은 특수 인자는 자동으로 제외됩니다(그래서 LLM이 값을 지어낼 필요가 없죠).
  • 시스템이 자동 주입합니다. LangGraph/LangChain이 도구를 실행하는 순간, 인자 이름/타입이 runtime인 것을 보고 자신이 관리하는 실행 객체(Context·Store 등)를 알아서 끼워 넣어 호출합니다.
💡 한 줄 정리 일반 인자(city, user_info)는 AI가 채우고, 특수 인자(runtime, config, tool_call_id)는 시스템이 자동으로 채웁니다. 도구는 이 둘을 조합해 자기 일을 수행합니다.

4. 에이전트 조립 & 실행

두 도구를 에이전트에 붙입니다. 중요한 건 store=store로 창고를 연결하고, context_schema=Context로 "실행마다 신분증(Context)을 받겠다"고 선언하는 부분입니다. 이 두 줄 덕분에 도구 안의 runtime.store·runtime.context가 실제 값으로 채워집니다.

📥 코드
from langchain.agents import create_agent

agent = create_agent(
    model="gpt-5-nano",
    tools=[get_user_info, save_user_info],
    store=store,         # 에이전트에 store 연결
    context_schema=Context
)

① 저장 실행 — 정보를 뽑아 창고에 넣기

"내 이름은 이제 'Alice'야. 커피보단 차를 좋아해"라고 말을 겁니다. invoke의 두 번째 인자로 context=Context(...)를 넘겨 신분증을 함께 건네는 점을 보세요.

📥 코드
response1 = agent.invoke(
    {"messages": [{"role": "user", "content": "내 이름은 이제 'Alice'야. 커피보단 차를 좋아해"}]},
    context=Context(user_id="user_001", app_name="personal_assistant")
)
print(response1)
print(response1["messages"][-1].content)

LLM은 이 문장에서 정보를 추출해 스스로 저장 도구를 호출합니다. 아래 실행 결과의 tool_calls를 보면, LLM이 user_info 칸을 {'personal_information': 'Alice', 'preference': 'tea'}로 알아서 채워 넣은 것을 확인할 수 있습니다. (runtime은 목록에 없죠 — 시스템 몫이니까요.)

▶ 이렇게 나와요 (실행 결과 · 핵심만 발췌)
# AIMessage 안의 tool_calls — LLM이 채운 인자
tool_calls=[{
  'name': 'save_user_info',
  'args': {'user_info': {'personal_information': 'Alice', 'preference': 'tea'}},
  'id': 'call_vlCcCQM4PaUlH0k8bHvnxL8M',
  'type': 'tool_call'
}]

# ToolMessage — 저장 도구가 돌려준 결과
정보가 안전하게 저장되었습니다. (ID: 4cd9b24e-0d70-4bfa-ae7a-6ed1dc2519cf)

# 최종 답변 (response1["messages"][-1].content)
좋아요, Alice! 앞으로 그렇게 부를게요. 커피 대신 차를 선호하신다니 기억해둘게요. ...

② 조회 실행 — 창고에서 꺼내오기

이번엔 "나에 대해 아는 정보 말해줘"라고 묻습니다. LLM은 "이건 저장된 정보를 봐야겠네"라고 판단해 조회 도구를 호출합니다.

📥 코드
response2 = agent.invoke(
    {"messages": [{"role": "user", "content": "나에 대해 아는 정보 말해줘"}]},
    context=Context(user_id="user_001", app_name="personal_assistant")
)
print(response2)
print(response2["messages"][-1].content)
▶ 이렇게 나와요 (실행 결과 · 핵심만 발췌)
# 도구 내부의 print('data', data) 가 찍은 로그 — 창고에 쌓인 것들
data {'personal_information': 'Alice', 'preference': 'tea'}
data {'personal_information': 'Name: Alice', 'preference': 'tea over coffee'}
data {'personal_information': 'name: Alice', 'preference': 'prefers tea to coffee'}

# tool_calls — 힌트 없는 runtime이라 LLM이 빈 값을 채우려 한 흔적
tool_calls=[{'name': 'get_user_info', 'args': {'runtime': {}}, ... }]

# ToolMessage — 조회 도구가 돌려준 결과
- 개인정보: Alice
- 선호도: tea
- 개인정보: Name: Alice
- 선호도: tea over coffee
- 개인정보: name: Alice
- 선호도: prefers tea to coffee

# 최종 답변 (response2["messages"][-1].content)
지금까지 저장된 정보는 다음과 같습니다.
- 이름: Alice
- 선호도: 차를 선호(커피보다 차를 더 좋아함)
⚠️ 왜 정보가 세 번이나 쌓였을까? 저장 도구는 매번 새 UUID로 계속 누적(put)합니다 — 기존 값을 덮어쓰지 않아요. 그래서 같은 사람 정보가 표현만 조금씩 다르게 세 벌 쌓였습니다. 또한 args에 'runtime': {}가 보이는 건, 조회 도구가 runtime에 ToolRuntime 힌트를 안 붙여 LLM에게 완전히 숨겨지지 못한 흔적입니다. 실전에서는 타입 힌트를 붙이고, 중복 저장은 갱신(update) 로직으로 다듬는 것이 좋습니다.

5. Push vs Pull — 10장 방식과 11장 방식

지난 10장과 이번 11장은 같은 목표(과거 기억 활용)를 다른 방식으로 이룹니다. 핵심 차이는 "누가, 언제 정보를 가져오느냐"이고, 그 차이가 토큰 비용으로 직결됩니다.

🔍 비유 — 시험장에 들고 가는 교재 10장(Push)은 시험 볼 때 모든 교과서를 통째로 들고 들어가는 방식입니다 — 필요 없는 과목 책까지 매번 다 펼쳐 놓으니 무겁고 비효율적이죠. 11장(Pull)은 시험을 보다가 모르는 게 나왔을 때만 필요한 페이지를 찾아보는 방식입니다. 평소엔 책을 안 펼치니 훨씬 가볍고 경제적입니다.

10장 방식 — 미들웨어가 무조건 주입 (Push)

LLM이 물어보기도 전에, 미들웨어(before_agent 훅)가 과거 기억을 꺼내 프롬프트 맨 앞에 미리 붙여 보냅니다. 문제는 "오늘 날씨 어때?"처럼 사용자 정보가 전혀 필요 없는 대화에서도 매번 과거 기억을 통째로 실어 보낸다는 것. 대화가 길고 기억이 많아질수록 매 요청마다 수천 토큰을 낭비합니다.

11장 방식 — 모델이 필요할 때만 호출 (Pull)

LLM에게 get_user_info라는 도구를 쥐여주고 스스로 판단하게 합니다. "안녕"엔 도구 없이 그냥 답하고(토큰 절약), "내가 좋아하는 음료로 추천해줘"처럼 취향을 알아야 하는 순간에만 도구를 호출해 정보를 가져옵니다.

비교 항목10장 (미들웨어 주입 · Push)11장 (도구 호출 · Pull)
주도권시스템(미들웨어)이 강제 주입LLM(모델)이 스스로 판단해 요청
토큰 사용매 요청마다 과거 기억 전체 포함 (비효율)필요한 순간에만 도구 결과 포함 (효율적)
구현 방식before_agent 훅에서 state 수정@tool 정의 후 에이전트에 등록
비유교과서를 통째로 들고 시험장에모르는 게 나오면 필요한 페이지만
💡 그래서 결론은 11장 방식은 LLM에게 "기억을 조회할 수 있는 능력(도구)"을 부여한 것입니다. 덕분에 에이전트가 "자기 마음대로 도구를 호출하는" 것처럼 보이는데, 그건 사실 모델의 자율적 판단에 의한 정보 조회입니다 — 훨씬 경제적이고 똑똑하죠.

📚 한 장 정리

오늘의 핵심 @tool 함수의 인자에는 'AI가 대화에서 뽑아 채우는 칸'과 '시스템이 실행 환경에서 자동으로 꽂아주는 칸'이 섞여 있다. 이 둘을 구분하면 도구 시그니처가 읽힌다.
  • 일반 인자(AI가 채움) — user_info, city 등. LLM이 이름·docstring·타입 힌트를 설명서로 읽고 값을 추출해 JSON으로 만든다.
  • 특수 인자(시스템이 채움) — runtime, config, tool_call_id. LLM 설명서에서 제외되고, 프레임워크가 실행 시 자동 주입한다.
  • 정석 — 특수 인자엔 runtime: ToolRuntime처럼 타입 힌트를 명시해 확실히 숨기고 주입되게 한다.
  • TypedDict vs Pydantic — 이름표(검증 안 함) vs 검사원(검증 함). 정확성이 중요하면 Pydantic.
  • Push(10) vs Pull(11) — 무조건 주입은 매번 토큰 낭비, 도구 호출은 필요할 때만 가져와 경제적. "교과서 통째로 vs 필요한 페이지만".
