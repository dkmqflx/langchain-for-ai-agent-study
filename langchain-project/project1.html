04 RAG에서 배운 Load→Split→Embed→Store→Retrieve를 재조립해, 문서에 질문하면 근거(citation)와 함께 답하는 RAG를 FastAPI API로 서빙하고, RAGAS로 검색 품질을 정량 측정한 뒤 Hybrid + Reranker로 개선합니다. STEP 0부터 STEP 9까지 순서대로 따라가면, 마지막에 돌아가는 서비스 + before/after 지표표 + 포트폴리오 README가 남습니다.

1

문서 인제스천 — Load → Split → Embed → Store

복습(04 RAG) ⏱ 반나절
🎯 목표

PDF들을 청크로 쪼개 임베딩해 Chroma에 저장하는 인덱싱 스크립트를 완성한다.

🧠 개념

RAG의 "사전 준비" 단계입니다. Split은 검색 단위를 정하고(너무 크면 노이즈, 너무 작으면 맥락 상실), Embed는 의미를 벡터로 바꿉니다. CacheBackedEmbeddings로 같은 청크를 재임베딩하지 않아 비용·시간을 아낍니다(04에서 배운 그대로).

🛠 할 일
ingest.py
# ═══════════════════════════════════════════════════════════════════
# STEP 1 · 인제스천(indexing): 원본 PDF를 '검색 가능한 벡터'로 바꿔 저장한다.
# 파이프라인  Load(읽기) → Split(쪼개기) → Embed(벡터화) → Store(저장)
# 이 스크립트를 한 번 실행해 두면, 이후 rag.py는 저장된 벡터DB에서 '검색'만 하면 된다.
#
# 아래 import가 각각 파이프라인의 어느 단계를 맡는지:
#   PyMuPDFLoader                        → Load  : PDF를 페이지별 Document로 읽기
#   RecursiveCharacterTextSplitter       → Split : 긴 텍스트를 청크로 분할
#   OpenAIEmbeddings                     → Embed : 텍스트를 의미 벡터로 변환
#   CacheBackedEmbeddings/LocalFileStore → Embed : 임베딩 캐시(재계산·재과금 방지)
#   Chroma                               → Store : 벡터 저장 + 유사도 검색(벡터DB)
# ═══════════════════════════════════════════════════════════════════
from pathlib import Path
from dotenv import load_dotenv
from langchain_community.document_loaders import PyMuPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_classic.embeddings import CacheBackedEmbeddings
from langchain_classic.storage import LocalFileStore
from langchain_chroma import Chroma

load_dotenv()                    # .env를 읽어 환경변수로 등록 → OpenAI 임베딩 호출에 쓸 API 키가 준비됨
DOCS_DIR = Path("data")          # 원본 PDF들이 들어 있는 폴더
PERSIST_DIR = "chroma_db"        # 벡터DB를 저장할 폴더(디스크에 남아 다음 실행에서 그대로 재사용)
COLLECTION = "p1_docs"           # 벡터DB 안에서 이 문서 묶음을 가리키는 이름표(테이블 이름 같은 것)

def build_chunks():
    """data/의 모든 PDF를 읽어 '청크(검색 단위 조각)' 리스트로 반환한다.  (Load → Split)

    청크 = 검색의 기본 단위가 되는 문서 조각. 검색은 문서 전체가 아니라 이 조각
    단위로 이뤄지므로, '어떻게 쪼개는가'가 검색 품질을 크게 좌우한다.
    """
    docs = []
    for pdf in sorted(DOCS_DIR.glob("*.pdf")):   # data/의 모든 .pdf를 이름순으로 하나씩 순회
        # PyMuPDFLoader(...).load() → PDF 1개를 '페이지별 Document' 리스트로 변환.
        # 각 Document.metadata에 source(파일 경로)·page(쪽 번호)가 자동으로 담긴다
        # → 이 값이 나중에 답변의 '근거(citation: 어느 문서 몇 쪽)'로 그대로 쓰인다.
        docs.extend(PyMuPDFLoader(str(pdf)).load())
    # chunk_size=1000  : 청크 하나의 최대 길이(글자). 크면 관련 없는 내용까지 섞여 노이즈↑, 작으면 문맥이 끊김
    # chunk_overlap=150: 이웃한 청크를 150자 겹치게 → 경계에서 문장이 잘려 뜻이 사라지는 것을 완화
    splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=150)
    return splitter.split_documents(docs)        # 페이지 Document들을 청크 단위 Document로 다시 쪼개 반환

def get_embeddings():
    """청크를 벡터로 바꿀 임베딩기를 만든다. 단, 캐시를 씌워 같은 청크의 중복 계산을 막는다.  (Embed)"""
    base = OpenAIEmbeddings(model="text-embedding-3-small")   # 실제 벡터를 만드는 OpenAI 임베딩 모델(가볍고 저렴한 소형)
    store = LocalFileStore("./cache/embeddings")             # 임베딩 결과(벡터)를 저장해 둘 로컬 캐시 폴더
    # 같은 청크는 다시 임베딩하지 않고 캐시에서 꺼내 씀 → 스크립트를 재실행해도 비용·시간 절약
    # namespace=base.model : 모델이 다르면 벡터도 다르므로 캐시를 '모델 이름'별로 분리(캐시 섞임 방지)
    return CacheBackedEmbeddings.from_bytes_store(base, store, namespace=base.model)

def main():
    chunks = build_chunks()             # (1) PDF들을 읽어 청크로 분할
    print(f"청크 수: {len(chunks)}")     # 몇 조각으로 나뉘었는지 확인(0이면 PDF가 비었거나 스캔본=텍스트 없음 의심)
    # (2) 각 청크를 임베딩해 Chroma에 저장. persist_directory를 주면 디스크에 영구 저장되어 재사용 가능
    Chroma.from_documents(
        documents=chunks,               # 저장할 청크(Document) 목록
        embedding=get_embeddings(),     # 각 청크를 벡터로 바꿀 임베딩기(위에서 만든 캐시 버전)
        collection_name=COLLECTION,     # 저장할 컬렉션 이름 → 검색할 때 같은 이름으로 접근
        persist_directory=PERSIST_DIR,  # 저장 위치(폴더). 지정하면 메모리가 아닌 디스크에 남음
    )
    print(f"저장 완료 -> {PERSIST_DIR} (collection={COLLECTION})")

if __name__ == "__main__":   # 이 파일을 직접 실행할 때만 main() 호출(다른 파일에서 import하면 실행 안 됨)
    main()

실행: uv run python ingest.py

✅ 검증 게이트 실행 후 청크 수: N(N>0)이 찍히고 chroma_db/ 폴더가 생기면 통과. 추가로 아래 한 줄 검색이 관련 있어 보이는 청크를 돌려주는지 확인하세요. 
uv run python -c "from langchain_chroma import Chroma; from langchain_openai import OpenAIEmbeddings; \
vs=Chroma(collection_name='p1_docs', persist_directory='chroma_db', embedding_function=OpenAIEmbeddings(model='text-embedding-3-small')); \
[print(d.metadata.get('source'), d.metadata.get('page'), d.page_content[:60]) for d in vs.similarity_search('가장 궁금한 주제 키워드', k=3)]"

인덱싱 파이프라인을 모듈로. build_chunks()를 함수로 뺀 이유는 STEP 6의 BM25가 같은 청크를 재사용하기 때문 — 재사용 가능한 설계 감각.

2

검색 + 생성 + 근거(Citation)

복습 + Citation 신규 ⏱ 반나절
🎯 목표

질문을 받아 검색 → 생성 → 근거 반환까지 하는 answer() 함수를 완성한다.

🧠 개념

RAG의 핵심 원칙: 모델은 검색된 문맥으로만 답한다(환각 억제). 그리고 실무 RAG는 반드시 "이 답의 근거가 어느 문서 몇 페이지냐"를 함께 줘야 신뢰할 수 있습니다 — 특히 의료 도메인에서 필수. 그래서 metadata의 source·page를 답변과 함께 반환합니다.

🛠 할 일
rag.py
# ═══════════════════════════════════════════════════════════════════
# STEP 2 · 검색 + 생성 + 근거(Citation): 질문 → 관련 청크 검색 → LLM이 그 문맥으로만 답변.
# 핵심 원칙  (1) 모델은 검색된 CONTEXT만 근거로 답한다(환각 억제)
#           (2) 답과 함께 '어느 문서 몇 쪽'(source·page)을 근거로 돌려준다
# 이 answer()가 이후 서빙(STEP 3)·평가(STEP 5)·하이브리드(STEP 6)의 공통 진입점이 된다.
# ═══════════════════════════════════════════════════════════════════
from dotenv import load_dotenv
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain.chat_models import init_chat_model          # 문자열 하나로 챗 모델을 만드는 헬퍼
from langchain_core.prompts import ChatPromptTemplate      # system/human 메시지 템플릿

load_dotenv()                                              # .env의 OPENAI_API_KEY 로드
emb = OpenAIEmbeddings(model="text-embedding-3-small")     # STEP 1과 '같은' 임베딩 모델이어야 검색이 맞는다
# 이미 인덱싱된 벡터DB를 연다(새로 저장하지 않고 읽기 전용). collection·경로는 STEP 1과 동일하게
vs = Chroma(collection_name="p1_docs", persist_directory="chroma_db", embedding_function=emb)
retriever = vs.as_retriever(search_kwargs={"k": 4})        # 질문당 가장 유사한 청크 4개를 가져오는 검색기
llm = init_chat_model("gpt-5-mini")                        # 답변을 생성할 LLM

# 프롬프트: system=규칙(문서 밖 내용은 지어내지 말 것 = 환각 억제), human=질문 + 검색된 문맥
PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "너는 제공된 CONTEXT만 근거로 답한다. "
     "CONTEXT에 근거가 없으면 '문서에서 찾을 수 없습니다'라고 답하고 추측하지 마라. "
     "답변 끝에 사용한 근거 번호를 [1][2]처럼 표기하라."),
    ("human", "질문: {question}\n\nCONTEXT:\n{context}"),   # {question}·{context}는 invoke 때 채워짐
])

def format_context(docs):
    """검색된 청크들을 '[번호] (source, page) + 본문' 형태의 한 문자열로 합친다.

    번호를 매겨두면 LLM이 답변 끝에 [1][2]로 어떤 근거를 썼는지 가리킬 수 있다.
    """
    return "\n\n".join(
        f"[{i+1}] (source={d.metadata.get('source')}, page={d.metadata.get('page')})\n{d.page_content}"
        for i, d in enumerate(docs)                        # i=0,1,2... 각 청크에 번호 부여
    )

def answer(question: str):
    """질문 하나를 받아 검색 → 생성 → 근거까지 끝낸 결과 dict를 돌려준다."""
    docs = retriever.invoke(question)                      # (1) 검색: 질문과 유사한 청크 4개
    msg = PROMPT.invoke({"question": question, "context": format_context(docs)})  # (2) 프롬프트에 질문·문맥 주입
    resp = llm.invoke(msg)                                 # (3) 생성: LLM이 문맥 기반으로 답변
    return {
        "answer": resp.content,                            # 최종 답변 텍스트
        # 근거 목록: 답이 어느 파일 몇 쪽에서 왔는지 (신뢰성의 핵심)
        "citations": [{"source": d.metadata.get("source"), "page": d.metadata.get("page")} for d in docs],
        "contexts": [d.page_content for d in docs],   # 검색된 원문들 → STEP 5 RAGAS 평가에서 사용
    }

if __name__ == "__main__":
    import json
    # 직접 실행하면 질문 하나를 넣어 결과를 보기 좋게 출력(한글 안 깨지게 ensure_ascii=False)
    print(json.dumps(answer("가장 궁금한 질문"), ensure_ascii=False, indent=2))

실행: uv run python rag.py

FastAPI로 서빙

신규 ⏱ 반나절
🎯 목표

answer()를 HTTP API로 노출한다. 이 순간 "노트북 코드"가 "서비스"가 됩니다.

🧠 개념

FastAPI는 파이썬 함수를 타입이 검증되는 HTTP 엔드포인트로 바꿔줍니다. pydantic 모델로 요청/응답 스키마를 정의하면, 잘못된 입력은 자동으로 거부되고 응답 형태가 문서화됩니다. 토스 "실험→서빙→운영", 카카오 "서비스에 탑재 가능한 형태"의 첫걸음입니다.

🛠 할 일
main.py
# ═══════════════════════════════════════════════════════════════════
# STEP 3 · FastAPI 서빙: STEP 2의 answer()를 HTTP API(POST /query)로 노출한다.
# pydantic 모델로 요청/응답 '스키마'를 선언 → 잘못된 입력은 자동 거부, /docs에 문서가 자동 생성.
# 이 순간 '노트북 코드'가 '서비스'가 된다.
# ═══════════════════════════════════════════════════════════════════
from fastapi import FastAPI
from pydantic import BaseModel          # 요청/응답의 형태(스키마)를 선언하는 클래스
from rag import answer                  # STEP 2에서 만든 핵심 함수 그대로 재사용

app = FastAPI(title="P1 RAG Search Service")   # 앱 객체. title은 /docs 문서 제목에 표시됨

class QueryIn(BaseModel):               # 요청 본문 스키마: question(문자열) 하나를 받는다
    question: str

class Citation(BaseModel):              # 근거 1건의 스키마
    source: str | None = None           # 파일 경로 (없을 수 있어 None 허용)
    page: int | None = None             # 쪽 번호

class QueryOut(BaseModel):              # 응답 스키마: 답변 + 근거 목록
    answer: str
    citations: list[Citation]

@app.get("/health")                     # 헬스체크: 서버가 살아있는지 확인하는 운영 기본 엔드포인트
def health():
    return {"status": "ok"}

@app.post("/query", response_model=QueryOut)   # POST /query. 응답을 QueryOut 형태로 검증·문서화
def query(body: QueryIn):               # body는 요청 JSON이 QueryIn으로 자동 파싱·검증된 결과
    result = answer(body.question)      # RAG 실행(검색 + 생성 + 근거)
    return {"answer": result["answer"], "citations": result["citations"]}   # contexts는 응답에서 제외

  -H "Content-Type: application/json" \
  -d '{"question": "문서에 있는 내용을 물어보세요"}'

Langfuse로 관측성 붙이기

신규 ⏱ 1~2시간
🎯 목표

모든 질의의 검색·생성·토큰·비용·지연을 Langfuse 대시보드에서 눈으로 본다.

🧠 개념

RAG가 틀린 답을 하면 "검색이 잘못됐나, 생성이 잘못됐나"를 알아야 고칩니다. 관측성(Observability)은 그 판단 근거입니다. Langfuse는 LangChain 콜백 한 줄로 실행을 trace(추적 트리)로 남깁니다. 카카오가 공고에 이름을 명시한 도구예요.

🛠 할 일

1) cloud.langfuse.com에서 무료 프로젝트를 만들고 키 2개를 .env에 채웁니다(STEP 0의 빈칸).

2) rag.py에 콜백 핸들러를 추가하고, 검색·생성 호출에 전달합니다.

rag.py (수정)
# ═══════════════════════════════════════════════════════════════════
# STEP 4 · 관측성(Langfuse): 모든 질의의 검색·생성·토큰·비용·지연을 대시보드로 추적한다.
# 방법은 간단 — LangChain 호출에 '콜백 핸들러'를 config로 넘기면 실행이 trace(추적 트리)로 남는다.
# 사전 준비: .env의 LANGFUSE_PUBLIC_KEY·SECRET_KEY를 채워둘 것(STEP 0의 빈칸).
# ═══════════════════════════════════════════════════════════════════
from langfuse.langchain import CallbackHandler   # langfuse v3~v4: 콜백은 langfuse.langchain 에 있음
# (v2를 쓰면: from langfuse.callback import CallbackHandler)

langfuse_handler = CallbackHandler()             # Langfuse로 로그를 보내는 콜백(키는 .env에서 자동으로 읽음)

def answer(question: str):
    cfg = {"callbacks": [langfuse_handler]}       # 이 config를 붙인 호출만 Langfuse에 기록된다
    docs = retriever.invoke(question, config=cfg) # 검색도 config 전달 → trace에 'retriever' 노드로 남음
    msg = PROMPT.invoke({"question": question, "context": format_context(docs)})
    resp = llm.invoke(msg, config=cfg)            # 생성도 config 전달 → 'LLM' 노드 + 토큰·지연 기록
    return {
        "answer": resp.content,
        "citations": [{"source": d.metadata.get("source"), "page": d.metadata.get("page")} for d in docs],
        "contexts": [d.page_content for d in docs],
    }
💡 팁 CallbackHandler import 경로는 langfuse 버전에 민감합니다. 설치된 버전은 uv run python -c "import langfuse; print(langfuse.__version__)"로 확인하고, v3면 langfuse.langchain, v2면 langfuse.callback을 쓰세요.
✅ 검증 게이트 /query를 몇 번 호출한 뒤 Langfuse 대시보드 Traces에서 각 요청이 retriever → LLM 트리로 보이고 토큰·지연이 찍히면 통과.
🎓 배우는 것

LLM 앱의 관측성 — 실무에서 "왜 이 답이 나왔는지"를 사후 추적하는 능력. 비용·지연 모니터링의 출발점.

골든 평가셋 + RAGAS 베이스라인

신규 · 핵심 ⏱ 반나절~1일
🎯 목표

"잘 되는 것 같다"를 숫자로 바꾼다. 현재 시스템의 baseline 점수를 확보한다.

🧠 개념

개선하려면 먼저 측정해야 합니다. RAGAS의 대표 지표 4개:

지표무엇을 재나낮으면 원인
faithfulness답이 검색 문맥에 충실한가(환각 여부)생성 프롬프트 문제
answer_relevancy답이 질문에 맞는가생성/질문 이해 문제
context_precision검색된 문맥이 군더더기 없이 관련 있나검색 노이즈 → Reranker(STEP7)
context_recall정답 근거를 검색이 빠짐없이 가져왔나검색 누락 → Hybrid(STEP6)
🛠 할 일

1) 문서에서 답할 수 있는 질문–정답 쌍으로 골든셋을 만듭니다. 처음엔 5개로 시작해 20~50개까지 늘리세요.

eval_data.json
[
  {"question": "질문 1?", "ground_truth": "문서 기준 정답 1"},
  {"question": "질문 2?", "ground_truth": "문서 기준 정답 2"}
]

2) answer()를 골든셋 전체에 돌려 RAGAS로 채점합니다.

evaluate.py
# ═══════════════════════════════════════════════════════════════════
# STEP 5 · RAGAS 평가: '잘 되는 것 같다'를 숫자로 바꾼다.
# 골든셋(eval_data.json의 질문·정답)에 answer()를 돌려, 4개 지표로 채점한다:
#   faithfulness(환각 여부) · answer_relevancy(질문 적합) · context_precision(문맥 정확) · context_recall(누락 없음)
# 실행:  uv run python evaluate.py baseline   (뒤에서 hybrid/rerank 태그로 재평가해 비교)
# ═══════════════════════════════════════════════════════════════════
import json, sys
from datasets import Dataset                                   # RAGAS에 넣을 표(데이터셋) 형식
from ragas import evaluate                                     # 채점 실행 함수
from ragas.metrics import faithfulness, answer_relevancy, context_precision, context_recall  # 지표 4종
from ragas.llms import LangchainLLMWrapper                     # RAGAS가 LangChain LLM을 쓰게 감싸는 어댑터
from ragas.embeddings import LangchainEmbeddingsWrapper        # RAGAS가 쓸 임베딩 어댑터
from langchain.chat_models import init_chat_model
from langchain_openai import OpenAIEmbeddings
from rag import answer                                         # 평가 대상: 우리 RAG 파이프라인

rows = json.load(open("eval_data.json", encoding="utf-8"))     # 골든셋 로드: [{question, ground_truth}, ...]
records = []
for r in rows:                                                 # 질문마다 실제로 RAG를 돌려 채점용 행을 만든다
    out = answer(r["question"])
    records.append({
        "question": r["question"],                             # 질문
        "answer": out["answer"],                               # 우리 시스템이 낸 답
        "contexts": out["contexts"],                           # 검색된 문맥(정확/누락 지표 계산에 필요)
        "ground_truth": r["ground_truth"],                     # 사람이 만든 정답(기준)
    })

result = evaluate(                                             # 4개 지표로 일괄 채점
    Dataset.from_list(records),
    metrics=[faithfulness, answer_relevancy, context_precision, context_recall],
    llm=LangchainLLMWrapper(init_chat_model("gpt-5-mini")),                       # 채점을 수행하는 심판 LLM
    embeddings=LangchainEmbeddingsWrapper(OpenAIEmbeddings(model="text-embedding-3-small")),  # 유사도 계산용 임베딩
)
print(result)                                                 # 지표 평균을 화면에 출력
tag = sys.argv[1] if len(sys.argv) > 1 else "baseline"      # 실행 인자로 결과 태그 지정(없으면 baseline)
result.to_pandas().to_csv(f"eval_{tag}.csv", index=False)     # 문항별 상세 점수를 CSV로 저장 → 설정 간 비교

실행: uv run python evaluate.py baseline

💡 팁 RAGAS는 버전에 따라 evaluate() 인자/데이터 형식이 다를 수 있어요. 컬럼 이름은 question · answer · contexts · ground_truth가 기본이며, 에러가 나면 설치된 RAGAS 문서의 "EvaluationDataset" 예시에 맞춰 records 형식만 바꾸면 됩니다.
✅ 검증 게이트 4개 지표가 숫자로 출력되고 eval_baseline.csv가 생기면 통과. 이 숫자가 앞으로의 기준선입니다 — 잘 적어두세요.
🎓 배우는 것

정량 평가 언어(recall/precision/faithfulness)와 평가셋 설계 — 두 공고 모두의 핵심 요구. "지표 없이 개선 없다"를 체득.

검색 개선 ① Hybrid (BM25 + Dense)

복습(BM25) + 실험 ⏱ 반나절
🎯 목표

키워드 검색(BM25)과 의미 검색(임베딩)을 앙상블해 context_recall을 끌어올린다.

🧠 개념

임베딩 검색은 의미는 잘 잡지만 정확한 용어·수치·희귀 단어(약물명, 코드, 고유명사)에 약합니다. BM25는 반대로 정확한 단어 일치에 강합니다. 둘을 EnsembleRetriever로 합치면 서로의 빈틈을 메웁니다 — 04에서 배운 Hybrid RAG.

🛠 할 일

rag.py의 retriever를 하이브리드로 교체합니다. BM25는 원문 청크가 필요하므로 STEP 1의 build_chunks()를 재사용합니다.

rag.py (retriever 교체)
# ═══════════════════════════════════════════════════════════════════
# STEP 6 · Hybrid 검색: 키워드 검색(BM25) + 의미 검색(임베딩)을 앙상블해 검색 누락을 줄인다.
# 임베딩은 '의미'에 강하나 정확한 용어·수치·희귀 단어(약물명·조항번호 등)에 약하고,
# BM25는 '정확한 단어 일치'에 강하다 → 둘을 합쳐 서로의 빈틈을 메운다. 목표 지표: context_recall↑
# rag.py의 기존 retriever 정의를 아래 코드로 '교체'한다.
# ═══════════════════════════════════════════════════════════════════
from langchain_community.retrievers import BM25Retriever
from langchain_classic.retrievers import EnsembleRetriever   # ImportError 시: from langchain.retrievers import EnsembleRetriever
from ingest import build_chunks                              # STEP 1의 청크 생성 함수 재사용(BM25는 원문 청크가 필요)

chunks = build_chunks()                 # 원문 청크(모듈 로드 시 1회만 — 매 요청 재호출은 느림)
bm25 = BM25Retriever.from_documents(chunks)   # 키워드(단어 빈도) 기반 검색기
bm25.k = 4                              # BM25가 돌려줄 청크 수
dense = vs.as_retriever(search_kwargs={"k": 4})   # 기존 임베딩(의미) 검색기

# 두 검색기를 가중 앙상블: 각자 top-4를 뽑아 점수를 weights로 섞어 최종 순위를 만든다
retriever = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])   # 0.4=BM25, 0.6=의미. 값을 바꿔 실험

7

검색 개선 ② Reranker (2-stage retrieval)

신규 ⏱ 반나절
🎯 목표

후보를 넉넉히 뽑은 뒤 Cross-Encoder로 재정렬해 context_precision을 끌어올린다.

🧠 개념

검색은 빠르지만 정밀도가 낮고, Cross-Encoder(질문·문서를 함께 보는 모델)는 느리지만 정밀합니다. 그래서 1단계로 top-10을 빠르게 검색 → 2단계로 rerank해 상위 4개만 남기는 것이 실무 표준(2-stage retrieval). 노이즈 청크가 걸러져 생성 품질이 오릅니다.

🛠 할 일
rag.py (reranker 적용)
# ═══════════════════════════════════════════════════════════════════
# STEP 7 · Reranker(2-stage retrieval): 후보를 넉넉히 뽑은 뒤 정밀 모델로 재정렬한다.
# 1단계(빠름): 하이브리드로 top-10을 넓게 검색  →  2단계(정밀): Cross-Encoder가 질문·문서를
