LangGraph 학습 전, 실무 프로젝트 3선

목표: AI Engineer  ·  타깃: 토스 · 카카오헬스케어  ·  스택: FastAPI Langfuse RAGAS  ·  난이도: 🟢 → 🟡 → 🔴

LangChain 학습(01 입문 · 02 Agent 기초 · 03 Advanced Agent · 04 RAG)을 마친 상태에서, LangGraph로 넘어가기 전에 실무에서 마주칠 프로젝트 3개를 직접 만들어 보는 로드맵입니다. 세 프로젝트는 각각 RAG · Agent · 평가·관측성을 하나씩 총정리하며, 난이도가 오르는 순서로 배치됩니다. Multi-Agent는 이 셋을 재료로 LangGraph의 첫 프로젝트로 이어집니다.

🎯 핵심 전략 — "튜토리얼"과 "실무 프로젝트"의 차이를 만든다 LangChain은 AI 로직을 만드는 도구입니다. 하지만 두 공고가 공통으로 요구하는 것은 그걸 서비스로 띄우고(FastAPI) · 정량 평가하고(RAGAS) · 실행을 추적하는(Langfuse) 능력입니다. 그래서 3개 프로젝트 모두 이 세 가지를 얇게 얹습니다. 이 층이 있어야 "튜토리얼을 따라 했다"가 아니라 "실험 → 서빙 → 운영 → 개선을 해봤다"는 이력서 문장이 나옵니다.

왜 이 3개인가 — 공고 요구 → 학습 갭 → 프로젝트

두 공고를 한 줄로 요약하면 이렇습니다.

  • 토스 AI Platform — RAG · Agent를 재사용 가능한 플랫폼으로 만들고, 정량 평가하고, 실험→서빙→운영하는 팀. (Multi-LLM Provider 운영, ML 시스템 설계 면접)
  • 카카오헬스케어 AI — 의료 도메인에서 RAG 정확도 · Multi-Agent · Workflow Orchestration을 제품화하는 팀. (LangChain/LangGraph, Tool Calling, Langfuse 추적, 프롬프트/평가 명시)

P1 · 프로덕션급 RAG 문서 검색 서비스

🟢 입문·복습 ⏱ 1~2주 토스: 재사용 RAG 컴포넌트 · 정량 평가 카카오: 검색 정확도 고도화
📋 단계별 실행 가이드 STEP 0 → STEP 9를 순서대로 따라가면 프로젝트도 학습도 완성됩니다 → project1.html 열기

🎯 목표

도메인 문서 컬렉션에 질문하면 근거(citation)와 함께 답하는 RAG를 FastAPI API로 서빙하고, 검색·답변 품질을 RAGAS로 정량 측정한 뒤 Hybrid 검색 + Reranker로 개선해 "before/after 지표 표"를 남기는 것이 목표입니다. 모든 질의는 Langfuse로 추적합니다.

📁 도메인 선택 카카오헬스케어를 노린다면 공개 의료 문서(질병관리청 가이드라인, 논문 초록, 의약품 설명서 등)로, 토스를 노린다면 "어떤 문서셋에도 꽂아 쓰는 재사용 컴포넌트" 관점으로 잡으면 공고 서사가 살아납니다.

🧩 핵심 기능

  • 문서 인제스천 파이프라인: Load → Split → Embed → Store 이미 학습
  • POST /query — 질문 → 관련 청크 검색 → 답변 생성 → 근거 청크 + 출처 반환
  • Hybrid 검색 (BM25 키워드 + 임베딩 벡터) + Reranker(Cross-encoder/Cohere)로 상위 문서 재정렬
  • 평가셋(질문–정답 20~50개) 기반 RAGAS: faithfulness · answer relevancy · context precision · context recall
  • 개선 실험 비교표: baseline vs +hybrid vs +rerank

🛠 기술 스택

LangChain (loader/splitter/embeddings/retriever) Chroma / pgvector FastAPI RAGAS Langfuse rank_bm25 / Cohere Rerank

✅ 마일스톤 (각 단계 = 검증 가능한 산출물)

  1. 도메인 문서셋 선택 → 인제스천 스크립트 작성 (Load~Store) 검증: 저장된 청크 수 출력 + 임의 질의로 유사 청크 top-k 확인
  2. FastAPI /query 엔드포인트 — retrieve → generate → 근거·출처 반환 검증: curl로 질문 전송 시 답변 + citation 배열이 함께 오는지 확인
  3. Langfuse 연동 — 모든 질의를 trace로 기록 검증: Langfuse 대시보드에서 retrieval/generation span·지연·토큰 확인
  4. 평가셋(20~50 Q/A) 구축 + RAGAS 베이스라인 측정 검증: 4개 지표 점수표가 숫자로 출력됨
  5. Hybrid + Reranker 적용 후 재측정 검증: baseline 대비 context recall / faithfulness 상승을 표로 비교
  6. (선택) chunk size · top-k 스윕 실험 검증: 파라미터별 지표 로그 + 최적값 선택 근거 기록
🎓 학습 성과 RAG를 "돌아가는 것"에서 "측정하고 개선하는 것"으로. 검색 품질 지표 언어(recall/precision/faithfulness)를 갖추고, 서빙·추적의 기본기를 확보합니다. → 이력서: "context recall 0.72 → 0.89로 개선" 같은 정량 문장.
🔗 LangGraph 연결 이 RAG를 나중에 그래프의 "검색 노드"로 넣으면, 검색 결과가 부실할 때 재검색하는 Corrective RAG / Self-RAG로 확장됩니다. P1이 그 노드의 원형입니다.

P2 · 관측 가능한 Agent API 서비스

🟡 중급 ⏱ 1~2주 토스: Agent 시스템 · Multi-LLM · 정량 평가 카카오: Tool Calling · Langfuse 추적 · 프롬프트 평가

🎯 목표

Tool · Memory · Guardrails를 갖춘 실용 Agent(리서치/업무 비서)를 FastAPI로 서빙하고, Langfuse로 전 실행(추론·Tool 호출·토큰·비용·지연)을 추적하며, OpenAI ↔ Anthropic을 설정으로 스위칭하고, 프롬프트 A/B를 정량 평가합니다.

🧩 핵심 기능

  • Agent 코어: 이미 배운 Tool + Memory + Guardrails + Structured Output 조립 이미 학습
  • 실용 도구 2~4개: 웹 검색 · 계산 · 날짜 · 사내 문서 검색 = P1 재사용
  • POST /chat — 세션 메모리 유지(멀티턴), 가능하면 SSE 스트리밍
  • Multi-LLM Provider 추상화: 환경설정으로 OpenAI/Anthropic 교체
  • Langfuse 트레이싱: Tool 호출별 span, 토큰/비용, Guardrail 차단 로그
  • 프롬프트 평가 하네스: 케이스 10~20개에 대해 프롬프트 A vs B를 LLM-as-judge로 채점

🛠 기술 스택

LangChain Agent (tool/memory/middleware/guardrails) FastAPI Langfuse OpenAI + Anthropic 동시 지원 LLM-as-judge 평가 스크립트

✅ 마일스톤

  1. Agent 코어 (tools + memory + guardrails) 구성 검증: 로컬에서 멀티턴 대화 + Tool 호출이 동작
  2. FastAPI /chat + 세션 메모리 검증: 두 번째 요청이 첫 요청의 맥락을 기억하는지 확인
  3. Langfuse 연동 검증: 대시보드에서 Tool 호출/토큰/비용 span이 트리로 보임
  4. Multi-LLM Provider 스위칭 검증: 같은 질문을 OpenAI/Anthropic으로 각각 실행, 응답·비용 비교
  5. 프롬프트 평가 하네스 (LLM-as-judge, 케이스 10~20개) 검증: 프롬프트 A/B의 정확도·형식준수 점수표 출력
  6. (선택) Guardrail 위반/거부 케이스 로깅 검증: Langfuse에서 차단된 요청이 사유와 함께 기록
🎓 학습 성과 Agent를 운영 관점(추적·비용·프롬프트 품질)으로 다룹니다. P1을 Tool로 재사용하며 "시스템을 조립하는" 감각을 얻고, Multi-LLM 운영 경험(토스 우대사항)을 확보합니다.
🔗 LangGraph 연결 하나의 Agent에 도구가 늘고 역할이 섞이면 "차라리 역할별로 Agent를 쪼개 조율하고 싶다"는 지점이 옵니다. 그게 바로 P3의 출발점입니다.

P3 · LLM/Agent 평가·관측성 하네스

🔴 심화 · 인프라 관점 ⏱ 2주 토스: 정량 평가 기반을 "플랫폼으로 제공" 카카오: 평가 체계 구축 · 반복 개선

🎯 목표

P1(RAG)과 P2(Agent)를 대상 시스템(system under test)으로 삼아, 프롬프트·모델·검색 파라미터를 바꿀 때마다 품질이 오르내리는지 자동으로 측정·비교·회귀 감지하는 평가 파이프라인을 만듭니다. 평가 결과는 Langfuse에 점수·데이터셋으로 남기고, 실행마다 리포트를 자동 생성합니다. 토스가 공고에 명시한 "정량 평가 기반을 만들고 플랫폼으로 제공"을 정면으로 겨냥합니다.

💡 왜 이게 "3번째 프로젝트"로 강력한가 P1·P2는 평가를 부속 단계로만 씁니다. P3는 평가 자체를 주인공으로 세워, "만드는 능력"과 구별되는 "품질을 지표로 관리하는 능력"을 증명합니다. 이 하네스는 이후 LangGraph로 만들 모든 것의 품질 게이트로 그대로 재사용됩니다.

🧩 핵심 기능

  • 골든 평가셋 관리: 질문–기대답·기대근거를 버전 관리 (RAG용 / Agent용 분리)
  • 평가 러너: 한 번 실행으로 P1/P2를 호출해 지표 자동 산출 (RAGAS 지표 · Agent task success · Tool 선택 정확도 · 형식 준수)
  • LLM-as-judge 정성 평가 + judge 신뢰도 점검 (사람이 라벨한 소수 케이스와의 일치율)
  • 실험 비교 · 회귀 감지: 설정 A vs B, "이번 변경이 지난 베이스라인보다 떨어졌는가"
  • 관측성 통합: Langfuse에 score 기록, trace ↔ eval 연결, 비용·지연도 지표화
  • 자동 리포트: 실행마다 지표표 + 회귀 하이라이트를 담은 리포트 생성

🛠 기술 스택

RAGAS LLM-as-judge (자체 스크립트) Langfuse (datasets · scores · traces) pandas (집계·리포트) pytest / CI 훅 (선택) OpenTelemetry (선택 · 카카오 우대)

✅ 마일스톤

  1. 골든 평가셋 v1 구축 (RAG용·Agent용, 각 20~50 케이스) 검증: 케이스 스키마 검증 + 버전 태그 부여
  2. 평가 러너 — P1/P2를 호출해 지표 자동 산출 검증: 한 번 실행에 지표 표가 숫자로 출력됨
  3. LLM-as-judge 정성 평가 + judge 신뢰도 점검 검증: judge 점수와 내가 손으로 라벨한 소수 케이스의 일치율 확인
  4. 실험 비교(A/B) + 회귀 감지 검증: 일부러 나쁜 프롬프트를 넣으면 회귀로 잡히는지 확인
  5. Langfuse 통합 (score·dataset 기록, trace 연결) 검증: 대시보드에서 실행별 점수 추이·비용이 보임
  6. 자동 리포트 생성 검증: 실행 시 지표표 + 회귀 하이라이트 리포트 파일이 생성됨
  7. (선택) CI에 평가 붙이기 검증: 커밋 시 임계값 미달이면 경고/실패
🎓 학습 성과 "만든다"에서 "품질을 지표로 관리한다"로. 평가셋 설계 · judge 신뢰도 · 회귀 평가 · 관측성 운영을 확보하고, 토스의 "평가 플랫폼" 서사와 카카오 우대사항(평가 데이터셋·반복 개선)을 정면으로 충족합니다.
🔗 LangGraph 연결 이 하네스는 LangGraph로 넘어간 뒤에도 그대로 재사용됩니다. LangGraph로 만든 Multi-Agent·워크플로우의 품질을 똑같이 측정하는 "품질 게이트"가 되어, 앞으로 만들 모든 것의 회귀를 막아 줍니다.

다음 단계 — LangGraph로 자연스럽게 넘어가기

LangGraph 학습의 첫 프로젝트는 Multi-Agent 오케스트레이터로 잡으세요. Multi-Agent는 두 공고 모두가 원하지만(카카오는 LangGraph를 명시), 그 제자리가 LangGraph이기 때문에 "LangGraph 이전"이 아니라 "LangGraph의 첫 결과물"로 만드는 게 맞습니다. 이때 이번에 만든 3개가 그대로 재료가 됩니다.

이번에 만든 것LangGraph 단계에서의 역할
P1 RAG 검색 서비스그래프의 "검색 노드" → Corrective / Self-RAG로 확장
P2 Agent APIMulti-Agent의 Sub-Agent(노드)로 편입
P3 평가·관측성 하네스LangGraph 워크플로우의 품질 게이트로 그대로 재사용
신규 Multi-Agent 오케스트레이터Supervisor·Sub-Agent를 StateGraph·조건부 엣지로 구현

Multi-Agent를 LangGraph로 처음부터 만들면, 아래를 "손으로 짤 필요 없이" 프레임워크가 제공한다는 걸 바로 체감합니다.
