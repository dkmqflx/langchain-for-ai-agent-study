5-4. Subgraph — 그래프를 통째로 노드에 접어 넣기

실습 노트북: 3.ipynb · # Subgraph / # State 분리 절  ·  대상 범위: add_node("이름", 컴파일된_그래프) · graph.invoke() · State 공유 / 분리  ·  난이도: 🟡 중급

5-3에서 노드가 다음 노드를 직접 지목하는 법을 배웠습니다 — Command(goto="booking"). 이번 장에서는 그 지목당하는 대상이 노드 하나가 아니라 그래프 통째가 됩니다. add_node("kitchen", kitchen_subgraph) — 컴파일된 그래프를 노드 자리에 그냥 꽂아 넣는 겁니다. 겉보기엔 네모 한 칸인데 현미경으로 확대하면 그 안에 또 그래프가 들어 있는 구조, 이게 Subgraph입니다. 멀티 에이전트란 결국 "에이전트 하나 = 서브그래프 하나"로 쌓아 올린 건물이고, 이번 장이 그 벽돌을 만드는 법입니다.

이 장에서 배우는 것

서브그래프를 붙이는 방법은 딱 두 가지입니다. 그리고 그 둘을 가르는 기준도 딱 하나예요 — 부모와 자식이 State(공책)를 같이 쓰느냐, 따로 쓰느냐.

  1. State를 공유할 때 → add_node("kitchen", kitchen_subgraph). 컴파일된 그래프를 노드 자리에 그대로 넣습니다. 값은 알아서 흘러 들어가고 알아서 흘러 나옵니다.
  2. State를 분리할 때 → 평범한 함수 노드를 하나 만들고, 그 안에서 child_graph.invoke({...})로 API 부르듯 호출합니다. 값은 우리가 직접 옮겨 담아야 합니다.

나머지는 전부 이 둘의 부속 설명입니다 — 왜 자식 그래프를 먼저 만들어야 하는지, 왜 자식은 checkpointer를 받지 않는지, 왜 State를 굳이 쪼개는지.

선행 지식: 5-1의 interrupt() · Command(resume=) · checkpointer · thread_id, 5-3의 Command(goto=) · with_structured_output(). 전부 그대로 다시 씁니다.

1. Subgraph란 — 하나의 Agent가 너무 많은 일을 하고 있다

지금까지 우리가 만든 그래프는 노드를 옆으로 계속 늘리는 방식이었습니다. 노드가 5개일 땐 괜찮습니다. 그런데 50개가 되면 어떻게 될까요? 한 파일에 함수 50개가 늘어서 있고, State에는 필드 40개가 붙어 있고, 엣지가 어디서 어디로 가는지 아무도 모르는 상태가 됩니다.

🔍 비유 — 1인 식당 vs 주방이 따로 있는 식당

지금까지는 1인 식당이었습니다. 사장 혼자 주문받고, 재료 확인하고, 요리하고, 서빙하고, 계산까지 합니다. 메뉴가 3개일 땐 굴러갑니다.

메뉴가 30개가 되는 순간 이 방식은 무너집니다. 그래서 진짜 식당은 홀과 주방을 나눕니다. 홀 직원은 "주방에 주문 넣었다"까지만 알면 되고, 주방 안에서 재료팀과 조리팀이 어떻게 움직이는지는 알 필요가 없습니다.

Subgraph는 이 "주방"을 만드는 문법입니다. 홀 그래프 입장에서 주방은 네모 한 칸이지만, 그 칸을 열어 보면 안에 또 그래프가 돌고 있습니다.

정의 — 다른 그래프를 Node로 사용하는 그래프

정의는 한 줄이면 끝납니다. 노드 자리에 그래프를 넣은 것, 그게 서브그래프입니다. 요청이 들어와서 노드 A가 노드 B에게 일을 넘겼는데, 그 B를 현미경으로 확대해 봤더니 또 하나의 그래프였던 상황이죠. 그리고 그 안에 든 그래프가 또 자기 노드로 다른 그래프를 품을 수도 있습니다. 이게 5-3 첫머리에서 봤던 Hierarchical(계층형) 구조의 정체입니다.

쓰는 이유 3가지 — 여행 예약 시스템으로 보기

슬라이드에 적힌 세 가지 용도를 하나의 예시로 한꺼번에 이해해 보죠. "여행을 통째로 예약해 주는 에이전트"를 만든다고 해 봅시다. 여행이니까 호텔 예약, 항공권 예약, 식당 예약이 다 필요합니다.

1멀티 에이전트

호텔 / 항공 / 식당 에이전트를 각각 서브그래프로 만들고, 위에서 하나로 묶는다

2재사용성

식당 예약 서브그래프를 나중에 배달 앱 에이전트에 그대로 갖다 붙인다

3분산 개발

호텔은 A팀, 항공은 B팀, 식당은 C팀이 따로 만들고 마지막에 연결만 한다

세 번째가 특히 현실적입니다. 팀 A·B·C가 서로의 코드를 볼 필요 없이 각자 만들고, 마지막에 add_node 세 줄로 붙이면 끝입니다. 그리고 C팀이 만든 식당 예약 에이전트는, 나중에 회사가 배달 서비스를 에이전트로 만들겠다고 할 때 다시 짤 필요 없이 그대로 꺼내 쓸 수 있습니다. 모듈로 만들어 뒀기 때문이죠.

주요 문법 2가지 — 미리 알아 둘 것

서브그래프에서 기억해야 할 두 줄

2. 만들 것 — 오마카세 예약에 "주방"을 붙인다

5-3에서 만든 오마카세 예약 에이전트를 그대로 이어받습니다. 메뉴를 추천하고, 사람에게 물어보고, 대답에 따라 goto로 갈라지는 그 구조 그대로예요. 딱 하나만 바뀝니다 — 고객이 "네, 그걸로 주세요"라고 했을 때 가는 곳이 노드가 아니라 주방 그래프 통째입니다.

설계도 읽기 — 세 갈래와 그 안의 두 칸

recommender

A코스(15만) 또는 B코스(8만)를 제안합니다. 직전 메시지에 "비싸"·"부담"이 들어 있으면 B코스로 내려갑니다.

confirm

interrupt()로 멈춰서 사람에게 묻고, 대답을 LLM이 confirm / change / cancel로 분류합니다. 그리고 Command(goto=...)로 셋 중 하나로 보냅니다.

kitchen ★

여기가 이번 장의 주인공. 노드처럼 보이지만 안에 check_stock → assign_chef 두 칸짜리 그래프가 들어 있습니다.

cancel

"그냥 안 할래요"인 경우. 상태만 cancelled로 바꾸고 끝냅니다.

주방 안쪽은 단순한 일직선입니다. 재료가 있는지 확인하고(check_stock), 쉐프를 배정하고 예상 시간을 계산하면(assign_chef) 끝이에요. 주방 그래프가 하는 일이 단순한 건 일부러 그런 겁니다. 이 장의 주제는 주방 안에서 무슨 일이 벌어지느냐가 아니라 주방을 어떻게 노드로 접어 넣느냐니까요.

⚠️ 만드는 순서 — 반드시 자식 그래프부터

순서를 지키지 않으면 코드가 아예 돌아가지 않습니다

자식(주방) 그래프를 먼저 만들고 컴파일한 다음, 부모 그래프를 만듭니다. 이유는 단순합니다 — 부모를 조립할 때 add_node("kitchen", kitchen_subgraph)라고 쓰는데, 이때 kitchen_subgraph라는 변수가 이미 존재해야 하기 때문이에요. 순서를 바꾸면 NameError가 납니다.

3. 구현 — STEP 1. State 정의

from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class ReservationState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    menu: str           # 지금 제안 중인 메뉴          ← 부모가 작성
    price: int          # 그 메뉴의 가격               ← 부모가 작성
    status: str         # 진행 상태                    ← 부모·자식 둘 다 건드림
    chef_name: str      # 배정된 쉐프                  ← 자식(주방)이 작성
    cooking_time: str   # 예상 소요 시간               ← 자식(주방)이 작성

이 절의 핵심은 필드가 6개라는 게 아니라, 이 공책 하나를 부모와 자식이 같이 쓴다는 점입니다. menu는 부모가 적고 자식이 읽습니다. chef_name은 자식이 적고 부모가 읽습니다. 서로 값을 넘겨 주는 코드는 한 줄도 없는데 값이 오갑니다.

🔍 비유 — 주방에 걸린 주문표 한 장

홀 직원이 주문표에 "A코스"라고 적어서 주방 벽에 겁니다. 주방은 그 주문표를 보고 요리를 시작하고, 같은 종이 아래쪽에 "담당: 지로, 40분"이라고 적어 둡니다.

홀 직원이 나중에 그 종이를 보면 주방이 적은 내용까지 그대로 읽을 수 있습니다. 종이가 한 장이니까요. 이게 State 공유형 서브그래프입니다.

(5장에서는 이 종이를 두 장으로 찢습니다. 그때부터는 값을 손으로 옮겨 적어야 해요.)

price 필드는 없어도 됩니다

price는 "A코스 15만 원"처럼 가격을 따로 들고 있으려고 넣은 필드일 뿐, 서브그래프 문법과는 아무 상관이 없습니다. 설계하기 나름이에요.

STEP 2. 주방 노드 2개 — 자식 그래프의 부품

① check_ingredients — 재료 재고 확인

# 주방만의 별도 워크플로우를 정의
def check_ingredients(state: ReservationState):
    print(f"\n   🍳 [주방/재료팀] '{state['menu']}' 재료 재고 확인 중...")
    # (로직 생략: 무조건 재료가 있다고 가정)
    return {"status": "ok"}

진짜 재고 시스템을 붙이는 건 이 장의 관심사가 아니라서, 무조건 ok를 반환하도록 뒀습니다. 대신 state['menu']를 읽고 있다는 점을 보세요. 이 값을 적은 건 부모 그래프의 recommender 노드입니다. State를 공유하니까 자식이 그냥 꺼내 읽을 수 있는 거예요.

② assign_chef — 쉐프 배정과 소요 시간

def assign_chef(state: ReservationState):
    menu = state['menu']
    if "오마카세" in menu:
        chef = "Master Jiro"
        time = "40분"
    else:
        chef = "Chef Kim"
        time = "20분"

    print(f"   👨‍🍳 [주방/인사팀] {chef} 쉐프 배정 완료 (예상 소요: {time})")
    return {"chef_name": chef, "cooking_time": time, "status": "cooking"}

비싼 오마카세면 마스터 지로에게 40분, 아니면 쉐프 킴에게 20분. 그리고 세 개의 필드를 한꺼번에 반환합니다. 이 중 chef_name과 cooking_time은 지금까지 아무도 손대지 않았던 빈 칸이었고, 주방이 처음으로 채워 넣는 값입니다. 이 두 값이 나중에 부모 쪽 결과에 그대로 나타나는지가 4장에서 확인할 포인트입니다.

STEP 3. 주방 그래프 조립 — 여기서 한 번 컴파일 ★

kitchen_builder = StateGraph(ReservationState)

kitchen_builder.add_node("check_stock", check_ingredients)
kitchen_builder.add_node("assign_chef", assign_chef)

kitchen_builder.add_edge(START, "check_stock")
kitchen_builder.add_edge("check_stock", "assign_chef")
kitchen_builder.add_edge("assign_chef", END)
# 주방 그래프 컴파일 (이 자체가 하나의 노드처럼 쓰임)
kitchen_subgraph = kitchen_builder.compile()
▶ 출력 — kitchen_subgraph
__start__ → check_stock → assign_chef → __end__   (일직선 그래프)

여기까지는 아무 새로운 것도 없습니다. 그래서 오히려 중요합니다 — 서브그래프는 "특별한 종류의 그래프"가 아니라, 그냥 평범하게 만든 그래프를 노드 자리에 꽂는 것이거든요. 이미 만들어 둔 아무 그래프나 서브그래프가 될 수 있습니다. 재사용성이라는 장점이 여기서 나옵니다.

왜 여기서는 checkpointer를 넣지 않나

compile()에 괄호가 비어 있는 걸 보세요. 우리 그래프는 interrupt()로 멈췄다가 다시 이어 가야 하니까 당연히 checkpointer가 필요한데도, 자식 그래프에는 넣지 않습니다.

부모가 가진 걸 자식이 물려받기 때문입니다

부모 그래프를 compile(checkpointer=checkpointer)로 컴파일하는 순간, 그 안에 등록된 서브그래프에도 같은 checkpointer가 자동으로 전파됩니다.

그러니 자식은 빈손으로 두고, 부모에게만 한 번 쥐여 주면 됩니다.

🔍 비유 — 회사 하나에 회계 장부 하나

주방이 따로 장부를 쓰지 않습니다. 식당 전체의 장부 한 권에 주방 지출도 같이 기록되죠.

주방이 자기 장부를 따로 만들면 어떻게 될까요? 같은 지출이 두 군데에 적히거나, 어느 쪽이 진짜인지 알 수 없게 됩니다. 그래서 장부는 사장(부모 그래프)이 한 권만 관리합니다.

STEP 4. recommender 노드 — 부모 그래프의 시작

여기서부터는 부모 그래프입니다. 먼저 모델을 하나 준비해 둡니다. 뒤에 나올 confirm 노드에서 씁니다. 

from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")
# [부서 1] 메뉴 추천
def menu_recommender(state: ReservationState):
    last_msg = state["messages"][-1].content if state["messages"] else ""

    if "비싸" in last_msg or "부담" in last_msg:
        proposal = "B코스 (런치 스페셜)"
        price = 80000
        msg = f"🍣 부담 없는 '{proposal} ({price:,}원)'은 어떠신가요?"
    else:
        proposal = "A코스 (쉐프 오마카세)"
        price = 150000
        msg = f"🍣 시그니처 '{proposal} ({price:,}원)'를 추천합니다."

    return {"menu": proposal, "price": price, "messages": [msg]}

판단 기준은 딱 두 단어입니다 — 직전 메시지에 "비싸"나 "부담"이 있으면 싼 코스로 내려갑니다. 맨 처음에는 messages가 비어 있으니 last_msg가 빈 문자열이 되고, 자연스럽게 else로 빠져 A코스부터 제안합니다.

이 노드가 되돌아오는 자리이기도 합니다

고객이 "너무 비싸요"라고 하면 confirm 노드가 goto="recommender"로 여기로 다시 보냅니다. 그때는 messages의 마지막이 "아니요.. 너무 비싸요."이므로 "비싸"에 걸려 B코스가 나오죠. 같은 함수인데 두 번째 방문에서 다른 답을 내놓는 구조입니다.

STEP 5. confirm 노드 — 사람에게 묻고, 세 갈래로 보낸다

먼저 LLM이 아무 말이나 하지 못하도록 답변 형식을 고정합니다. 5-3에서 실습으로 봤던 그 방식입니다.

from typing import Literal
from pydantic import BaseModel, Field

class UserIntent(BaseModel):
    action: Literal["confirm", "change", "cancel"] = Field(description="확정, 변경, 취소 판단")

intent_analyzer = model.with_structured_output(UserIntent)

이렇게 만들어 두면 intent_analyzer.invoke(...)의 결과는 문장이 아니라 action 속성을 가진 객체로 돌아옵니다. 그래서 아래 코드에서 analysis.action으로 꺼내 쓸 수 있고, 값은 반드시 셋 중 하나입니다. 

# [부서 2] Agentic Router
def customer_confirm_node(state: ReservationState):
    menu = state['menu']
    price = state['price']

    print(f"\n🛑 [System]: 고객 의사 확인 중 (Interrupt)")

    # 1. 멈추고 사람의 대답을 기다립니다.
    user_input = interrupt(f"'{menu}' ({price:,}원)으로 하시겠습니까?")
    print(f"▶️ [User Input]: \"{user_input}\"")

    # 2. LLM 의도 분석
    analysis = intent_analyzer.invoke(f"제안: {menu}, 답변: {user_input}")
    print(f"🧠 [AI Router]: 의도='{analysis.action}'")

    # 3. 분류된 의도에 따라 Command(goto=...)로 런타임 라우팅을 수행합니다.
    if analysis.action == "confirm":
        # [핵심] 여기서 'kitchen'으로 보내면, 노드가 아닌 연결된 Subgraph가 통째로 실행됩니다.
        return Command(
            update={"messages": [HumanMessage(content=user_input)]},
            goto="kitchen"
        )
    elif analysis.action == "change":
        return Command(
            update={"messages": [HumanMessage(content=user_input)]},
            goto="recommender"
        )
    else:
        return Command(
            update={"messages": [HumanMessage(content=user_input)]},
            goto="cancel"
        )

노드 하나가 세 가지 일을 합니다 — 멈추고(interrupt), 알아듣고(LLM), 보냅니다(goto). 전부 5-1·5-3에서 이미 본 문법이에요.

⚠️ 여기서 놓치기 쉬운 것 — goto="kitchen"의 "kitchen"은 무엇인가

지금 이 코드를 쓰는 시점에는 kitchen이라는 노드가 아직 존재하지 않습니다. STEP 7에서 parent_builder.add_node("kitchen", kitchen_subgraph)로 서브그래프를 등록할 때 붙일 이름을 미리 적어 둔 거예요.

즉 goto에 적는 건 "그래프 이름"이 아니라 "등록할 때 준 노드 이름"입니다. 등록 이름을 "주방"으로 바꾸면 여기도 goto="주방"이 됩니다.

🔍 비유 — 문패에 적힌 이름으로 부른다

서류를 "주방으로 보내"라고 적을 때, 우리는 주방에 몇 명이 있고 어떤 순서로 일하는지 몰라도 됩니다. 문 앞에 붙은 문패 이름만 정확하면 서류는 도착합니다.

goto="kitchen"이 딱 그겁니다. 부모는 "kitchen"이라는 문패까지만 알고, 그 문 안에서 check_stock → assign_chef가 돈다는 건 알 필요가 없습니다.

이 줄을 앞의 세 줄과 나란히 놓고 보세요

add_node("cancel", cancel_node) — 두 번째 자리에 함수가 들어갔습니다.
add_node("kitchen", kitchen_subgraph) — 두 번째 자리에 컴파일된 그래프가 들어갔습니다.

문법 모양이 완전히 똑같습니다. LangGraph 입장에서 "노드"는 그냥 State를 받아 State 조각을 돌려주는 무언가일 뿐이고, 함수든 그래프든 그 조건만 만족하면 노드가 될 수 있습니다.

엣지는 3개만

# 최소한의 정적 엣지만 연결 (나머지는 Command goto가 동적으로 처리)
parent_builder.add_edge(START, "recommender")
parent_builder.add_edge("recommender", "confirm")

confirm에서 나가는 엣지가 하나도 없다는 걸 보세요. confirm이 어디로 갈지는 실행 중에 goto가 정하기 때문입니다 — 5-3에서 배운 그대로예요.

마지막 줄 add_edge("kitchen", END)는 주방 그래프가 자기 END에 도달한 뒤 부모 그래프에서 어디로 갈지를 정합니다. 여기서는 바로 전체 종료입니다.

⚠️ END가 두 겹이라는 점을 헷갈리지 마세요

주방 그래프 안에도 add_edge("assign_chef", END)가 있었습니다. 그건 주방 그래프의 END고, 거기 도달하면 "주방 노드가 끝났다"는 뜻일 뿐 전체가 끝나는 게 아닙니다.

주방을 빠져나온 다음 어디로 갈지는 부모 그래프의 엣지가 결정합니다. 만약 add_edge("kitchen", "결제")라고 썼다면 주방 다음에 결제 노드로 갔겠죠.

그런데 디버깅할 때는 주방 안이 궁금할 수 있습니다. 평소처럼 app.get_state(config)를 부르면 부모의 State만 보이는데, subgraphs=True를 주면 자식 그래프 내부 상태까지 함께 조회됩니다.

🔍 비유 — 매장 CCTV를 주방까지 확장하는 스위치

기본 get_state(config)는 홀 CCTV만 보여 줍니다. 주방 문 앞까지가 화면 끝이에요.

subgraphs=True는 주방 안 카메라까지 켜는 스위치입니다. 평소엔 필요 없지만, "왜 40분이 아니라 20분이 나왔지?"를 추적할 땐 이 스위치가 필요합니다.

5. State 분리 — 공책을 두 장으로 찢는다

앞 절의 그래프를 다시 떠올려 보세요. 부모의 menu_recommender도 ReservationState를 받고, 자식의 assign_chef도 ReservationState를 받습니다. 공책 한 권을 온 식당이 돌려 쓰고 있는 것이죠. 값이 저절로 오가서 편했지만, 바꿔 말하면 아무나 아무 칸이나 다 볼 수 있다는 뜻이기도 합니다.

분리하는 두 가지 이유

🔍 비유 — 여행 예약 에이전트에 외부 회사가 합류한다면

1장에서 든 여행 예약 시스템으로 돌아가 봅시다. 호텔·항공 예약 서브그래프는 부킹닷컴이 만들고, 식당 예약 서브그래프는 배달 앱 회사가 만들어서 합류했다고 해 보죠.

공책이 한 권이면, 부킹닷컴이 만든 그래프가 돌면서 적은 항공권 가격·좌석 등급·제휴 수수료 같은 값이 전부 그 공책에 남습니다. 그리고 배달 앱 쪽 그래프도 같은 공책을 받으니 그걸 다 읽을 수 있습니다. 보여 주고 싶지 않은 정보가 자동으로 새는 구조예요.

공책을 따로 쓰면 이 문제가 사라집니다. 부킹닷컴 그래프는 자기 공책만 들고 일하고, 넘겨줄 값만 손으로 건네받고 손으로 돌려줍니다.

보안 / 프라이버시 서브그래프가 남의 영역 값까지 전부 읽을 수 있습니다. 서드파티가 만든 에이전트를 붙일 때는 사실상 정보를 통째로 넘기는 셈이 됩니다.
State 비대화 방지 항공(편명·좌석·상태), 호텔(객실·체크인), 식당(가게 ID·주소·가격)… 모든 하위 시스템의 필드가 State 하나에 다 붙습니다. 나중엔 어떤 노드가 어떤 필드를 쓰는지 아무도 모르게 됩니다.

STEP 1. 자식 그래프 — 배달업체만의 공책

from typing_extensions import TypedDict

# 배송 모듈만의 완전히 독립적인 State
class DeliveryState(TypedDict):
    address: str           # 어디로 배달할지        ← 부모에게서 받음
    package_info: str      # 무엇을 배달할지        ← 부모에게서 받음
    delivery_status: str   # 지금 어디까지 왔는지   ← 자식이 직접 갱신

앞의 두 개는 부모가 넘겨 주는 값, 마지막 하나는 자식이 스스로 채우는 값입니다. 이 3개가 배달업체와 주고받는 계약서의 전부예요.

노드 2개

def pickup_package(state: DeliveryState):
    print(f"\n   🛵 [배달업체] 픽업 완료! (물품: {state['package_info']})")
    return {"delivery_status": "picked_up"}


def deliver_to_customer(state: DeliveryState):
    print(f"   Hit [배달업체] {state['address']}로 배송 중... 띵동! 배달 완료.")
    return {"delivery_status": "delivered"}

단계를 지날 때마다 delivery_status가 picked_up → delivered로 바뀝니다. 배달 앱에서 보이는 그 상태 표시와 같은 거예요.

그래프 조립

delivery_builder = StateGraph(DeliveryState)

delivery_builder.add_node("pickup", pickup_package)
delivery_builder.add_node("deliver", deliver_to_customer)

delivery_builder.add_edge(START, "pickup")
delivery_builder.add_edge("pickup", "deliver")
delivery_builder.add_edge("deliver", END)

# 하위 그래프 컴파일 (이 자체가 하나의 노드처럼 쓰임)
delivery_graph = delivery_builder.compile()

class RestaurantState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    menu: str               # 주문 메뉴          → 자식에게 넘겨줄 값

DeliveryState와 필드 이름이 하나도 겹치지 않는다는 걸 보세요. 부모는 menu·customer_address라고 부르고, 자식은 package_info·address라고 부릅니다. 서로 다른 회사가 각자 만든 양식이니 당연한 일이고, 바로 그래서 값이 저절로 흘러갈 수가 없습니다.

① cook_food — 조리 노드

def cook_food(state: RestaurantState):

② call_delivery_service — 브릿지 노드 ★

이 절에서 딱 하나만 기억한다면 이 노드입니다

State가 분리되면 add_node("배달", delivery_graph)를 쓸 수 없습니다. 필드 이름이 다르니 LangGraph가 무엇을 무엇에 넣어야 할지 알 방법이 없거든요.

대신 평범한 함수 노드를 하나 만들고, 그 안에서 delivery_graph.invoke(...)로 직접 호출합니다. 이 함수를 브릿지(Bridge) 노드라고 부릅니다.

# 외부 그래프를 호출하는 '브릿지(Bridge)' 노드
def call_delivery_service(state):
    print("\n📞 [매니저] 배달 업체 호출 중...")

    # 1. 내 공책(Parent)의 정보를 -> 외부 업체 양식(Child)으로 변환 (Mapping)
    delivery_input = {
        "address": state["customer_address"],
        "package_info": state["menu"],
        "delivery_status": "pending"
    }

    # 2. 함수 안에서 그래프를 실행 (API 호출하듯이)
    delivery_result = delivery_graph.invoke(delivery_input)

    # 3. 결과를 받아서 내 공책에 기록
    final_status = delivery_result['delivery_status']

    # 자식이 반환한 delivery_status를 부모의 final_status 키에 맞춰 업데이트합니다.
    return {"final_status": final_status}
🔍 비유 — 택배 접수증을 대신 써 주는 직원

식당 매니저가 배달 업체 앱을 열어 접수증을 작성합니다. 우리 주문서에는 "메뉴: 특선 초밥 세트"라고 적혀 있지만, 업체 앱의 칸 이름은 "물품"이에요. 매니저가 옮겨 적습니다.

접수하면 기사님이 알아서 픽업하고 배달합니다. 매니저는 그 과정에 개입하지 않아요.

다 끝나면 앱에 "배송 완료"가 뜨고, 매니저는 그 상태만 우리 장부에 옮겨 적습니다. 기사님이 어느 길로 갔는지, 몇 건을 같이 돌았는지는 우리 장부에 남지 않습니다.

브릿지 노드가 하는 일 — 항상 이 3단계
단계코드하는 일
① 포장 delivery_input = {...} 자식의 필드 이름을 키로 삼아 딕셔너리를 만듭니다. 키는 자식 것, 값은 부모 것 — "address": state["customer_address"]
② 호출 delivery_graph.invoke(delivery_input) 자식 그래프가 독립적으로 처음부터 끝까지 실행되고, 최종 State를 통째로 반환합니다
③ 개봉 result['delivery_status'] → return {"final_status": ...} 돌아온 State에서 필요한 값만 꺼내 부모 필드 이름으로 다시 담아 반환
invoke()가 반환하는 건 "최종 State"입니다

delivery_graph.invoke(...)의 결과는 자식 그래프가 END에 도달했을 때의 State 전체예요. 그러니까 {'address': '...', 'package_info': '...', 'delivery_status': 'delivered'} 이런 딕셔너리가 통째로 옵니다.

거기서 우리가 필요한 delivery_status 하나만 꺼내 쓰는 거고, 나머지는 버립니다. 무엇을 가져올지 우리가 고른다는 게 분리형의 특징입니다.

자주 걸리는 함정 7가지

  1. 자식 그래프를 먼저 만들어야 한다 — add_node("kitchen", kitchen_subgraph)를 쓰는 시점에 kitchen_subgraph 변수가 이미 있어야 합니다. 순서를 바꾸면 NameError입니다.
  2. 등록하는 건 builder가 아니라 compile()의 결과다 — add_node("kitchen", kitchen_builder)가 아니라 add_node("kitchen", kitchen_subgraph). 컴파일해야 실행 가능한 그래프가 됩니다.
  3. ⚠️ 자식에는 checkpointer를 주지 않는다 — 부모를 컴파일할 때 준 것이 자식에게 전파됩니다. 자식 compile()의 괄호는 비워 두세요.
  4. goto="kitchen"의 문자열은 "등록할 때 준 노드 이름"이다 — 그래프 변수 이름(kitchen_subgraph)이 아닙니다. add_node의 첫 번째 인자와 글자가 정확히 같아야 합니다.
  5. END가 두 겹이다 — 자식 안의 END는 "자식이 끝났다"일 뿐입니다. 그다음 어디로 갈지는 부모의 add_edge("kitchen", ...)가 정합니다. 이 엣지를 빼먹으면 거기서 멈춥니다.
  6. ⚠️ State가 다르면 add_node가 통하지 않는다 — 필드 이름이 다른 State끼리는 값이 자동으로 넘어갈 수 없습니다. 이때는 브릿지 노드 + invoke()가 유일한 방법입니다.
  7. 브릿지 노드에서 키 이름을 헷갈리지 말 것 — delivery_input의 키는 자식 필드 이름, 값은 부모에서 꺼낸 것입니다. {"address": state["customer_address"]} — 왼쪽이 자식, 오른쪽이 부모. 반대로 쓰면 KeyError가 나거나, 더 나쁘게는 빈 값이 조용히 흘러갑니다.

# ★ [정답] ★
def exchange_bridge_node(state: TravelState):
    # 1. 내 공책(Parent)에서 정보 꺼내기
    my_request = state['request_amount']

    # 2. 외부 업체 공책(Child) 양식에 맞춰 데이터 포장 (Mapping)
    # Parent의 'request_amount' -> Child의 'usd_amount'

    print(f"✈️ [가이드] 은행에서 {exchanged_money}원을 받아왔습니다.")

실습 2 — "AI 뉴스레터 편집국" (State 공유형 + Human-in-the-loop)

요구사항

Parent(편집국)는 전체 흐름과 인간 편집장과의 소통을 담당하고, Subgraph(제작팀)는 검색(Researcher)과 집필(Writer)을 담당합니다.

  1. 사용자가 주제를 입력한다
  2. 제작팀 Subgraph가 작동해 초안을 만든다
  3. 편집장에게 interrupt가 걸린다 — 초안을 보여 주고 승인을 요청
  4. 승인이면 발행하고 종료
  5. 거절이면 피드백을 받아 다시 제작팀 Subgraph로 돌려보낸다 (Command 사용)
  6. 제작팀은 피드백을 반영해 원고를 수정한다 (State 유지)

5번이 이 문제의 핵심입니다. goto="content_team"으로 서브그래프를 다시 실행시키는 것이고, 이번 장 본문에서 goto="recommender"로 되돌아갔던 것과 구조가 같습니다. 다만 돌아가는 대상이 노드가 아니라 그래프 통째죠.

① State 공유형 — 오마카세 예약 + 주방 서브그래프

from langchain.chat_models import init_chat_model
from langchain.messages import AnyMessage, HumanMessage
from typing_extensions import TypedDict, Annotated
from typing import Literal
from pydantic import BaseModel, Field
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver

model = init_chat_model("gpt-5-nano")

# ── State (부모·자식 공용) ────────────────────────────────
class ReservationState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    menu: str
    price: int
    status: str
    chef_name: str
    cooking_time: str

# ── Child Graph (주방) ────────────────────────────────────
def check_ingredients(state: ReservationState):
    print(f"\n   🍳 [주방/재료팀] '{state['menu']}' 재료 재고 확인 중...")
    return {"status": "ok"}

def assign_chef(state: ReservationState):
    menu = state['menu']
    if "오마카세" in menu:
        chef, time = "Master Jiro", "40분"
    else:
        chef, time = "Chef Kim", "20분"
    print(f"   👨‍🍳 [주방/인사팀] {chef} 쉐프 배정 완료 (예상 소요: {time})")
    return {"chef_name": chef, "cooking_time": time, "status": "cooking"}

kitchen_builder = StateGraph(ReservationState)
kitchen_builder.add_node("check_stock", check_ingredients)
kitchen_builder.add_node("assign_chef", assign_chef)
kitchen_builder.add_edge(START, "check_stock")
kitchen_builder.add_edge("check_stock", "assign_chef")
kitchen_builder.add_edge("assign_chef", END)

kitchen_subgraph = kitchen_builder.compile()   # ← checkpointer 없음

# ── Parent Graph (홀) ─────────────────────────────────────
def menu_recommender(state: ReservationState):
    last_msg = state["messages"][-1].content if state["messages"] else ""
    if "비싸" in last_msg or "부담" in last_msg:
        proposal, price = "B코스 (런치 스페셜)", 80000
        msg = f"🍣 부담 없는 '{proposal} ({price:,}원)'은 어떠신가요?"
    else:
        proposal, price = "A코스 (쉐프 오마카세)", 150000
        msg = f"🍣 시그니처 '{proposal} ({price:,}원)'를 추천합니다."
    return {"menu": proposal, "price": price, "messages": [msg]}

class UserIntent(BaseModel):
    action: Literal["confirm", "change", "cancel"] = Field(description="확정, 변경, 취소 판단")

intent_analyzer = model.with_structured_output(UserIntent)

def customer_confirm_node(state: ReservationState):
    menu, price = state['menu'], state['price']
    print(f"\n🛑 [System]: 고객 의사 확인 중 (Interrupt)")
    user_input = interrupt(f"'{menu}' ({price:,}원)으로 하시겠습니까?")
    print(f"▶️ [User Input]: \"{user_input}\"")

    analysis = intent_analyzer.invoke(f"제안: {menu}, 답변: {user_input}")
    print(f"🧠 [AI Router]: 의도='{analysis.action}'")

    if analysis.action == "confirm":
        return Command(update={"messages": [HumanMessage(content=user_input)]}, goto="kitchen")
    elif analysis.action == "change":
        return Command(update={"messages": [HumanMessage(content=user_input)]}, goto="recommender")
    else:
        return Command(update={"messages": [HumanMessage(content=user_input)]}, goto="cancel")

def cancel_node(state: ReservationState):
    print(f"\n👋 [카운터]: 예약 종료.")
    return {"status": "cancelled"}

parent_builder = StateGraph(ReservationState)
parent_builder.add_node("recommender", menu_recommender)
parent_builder.add_node("confirm", customer_confirm_node)
parent_builder.add_node("cancel", cancel_node)
parent_builder.add_node("kitchen", kitchen_subgraph)      # ★ 그래프를 노드로

parent_builder.add_edge(START, "recommender")
parent_builder.add_edge("recommender", "confirm")
parent_builder.add_edge("kitchen", END)

checkpointer = InMemorySaver()
app = parent_builder.compile(checkpointer=checkpointer)   # ★ 여기서만 checkpointer

# ── 실행 ──────────────────────────────────────────────────
config = {"configurable": {"thread_id": "subgraph-demo-1"}}
app.invoke({"messages": []}, config=config)
result = app.invoke(Command(resume="좋아요, 그걸로 주세요."), config=config)

② State 분리형 — 레스토랑 + 외부 배달업체

from typing_extensions import TypedDict, Annotated
from langchain.messages import AnyMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

# ── Child: 배달업체만의 State ─────────────────────────────
class DeliveryState(TypedDict):
    address: str
    package_info: str
    delivery_status: str

def pickup_package(state: DeliveryState):
    print(f"\n   🛵 [배달업체] 픽업 완료! (물품: {state['package_info']})")
    return {"delivery_status": "picked_up"}

def deliver_to_customer(state: DeliveryState):
    print(f"   Hit [배달업체] {state['address']}로 배송 중... 띵동! 배달 완료.")
    return {"delivery_status": "delivered"}

delivery_builder = StateGraph(DeliveryState)
delivery_builder.add_node("pickup", pickup_package)
delivery_builder.add_node("deliver", deliver_to_customer)
delivery_builder.add_edge(START, "pickup")
delivery_builder.add_edge("pickup", "deliver")
delivery_builder.add_edge("deliver", END)

delivery_graph = delivery_builder.compile()

# ── Parent: 식당만의 State ────────────────────────────────
class RestaurantState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    menu: str
    customer_address: str
    final_status: str

def cook_food(state: RestaurantState):
    print(f"\n👨‍🍳 [주방] '{state['menu']}' 조리 완료! 포장했습니다.")
    return {"messages": ["조리 완료"]}

# ★ 브릿지 노드 — 포장 → 호출 → 개봉
def call_delivery_service(state):
    print("\n📞 [매니저] 배달 업체 호출 중...")

    delivery_input = {                                  # ① 포장 (키=자식, 값=부모)
        "address": state["customer_address"],
        "package_info": state["menu"],
        "delivery_status": "pending"
    }

    delivery_result = delivery_graph.invoke(delivery_input)   # ② 호출

    final_status = delivery_result['delivery_status']         # ③ 개봉
    return {"final_status": final_status}

parent_builder = StateGraph(RestaurantState)
parent_builder.add_node("kitchen", cook_food)
parent_builder.add_node("delivery_manager", call_delivery_service)
parent_builder.add_edge(START, "kitchen")
parent_builder.add_edge("kitchen", "delivery_manager")
parent_builder.add_edge("delivery_manager", END)

app = parent_builder.compile()

# ── 실행 ──────────────────────────────────────────────────
result = app.invoke({
    "menu": "특선 초밥 세트",
    "customer_address": "서울시 강남구 역삼동 123",
    "messages": []
})

📚 한 장 정리

Subgraph — 딱 이것만 기억하면 됩니다
질문답
Subgraph가 뭔가다른 그래프를 노드로 사용하는 그래프. 노드를 확대했더니 또 그래프인 상황
왜 쓰나멀티 에이전트 · 재사용성 · 분산 개발. 거대해지는 시스템을 모듈로 쪼개기 위해
만드는 순서자식 먼저, 부모 나중. 부모가 등록할 때 자식 변수가 이미 있어야 함
붙이는 법 (State 공유)add_node("kitchen", kitchen_subgraph) — 컴파일된 그래프를 그대로
붙이는 법 (State 분리)브릿지 노드 안에서 child.invoke({...}) — 포장 → 호출 → 개봉
checkpointer부모에게만. 자식에게 자동 전파됨
내부 상태 조회get_state(config, subgraphs=True)
  • 서브그래프는 특별한 그래프가 아니다 — 평범하게 만들어 컴파일한 그래프를 노드 자리에 꽂았을 뿐입니다. 이미 만들어 둔 어떤 그래프든 서브그래프가 될 수 있습니다.
  • add_node의 두 번째 인자에 함수도 그래프도 들어간다 — LangGraph에게 노드란 State를 받아 State 조각을 돌려주는 무언가일 뿐이고, 그래프도 그 조건을 만족합니다.
  • State를 공유하면 값이 저절로 오간다 — 부모가 적은 menu를 자식이 읽고, 자식이 적은 chef_name이 부모 결과에 그대로 남습니다. 옮기는 코드는 한 줄도 없습니다.
  • 편한 만큼 다 보인다 — 자식은 부모 State를 전부 볼 수 있습니다. 서드파티 모듈이라면 이게 곧 정보 유출이 됩니다.
  • State를 분리하면 자동은 끝나고 수동이 시작된다 — 필드 이름이 다르니 자동으로 흘러갈 수 없습니다. 브릿지 노드가 딕셔너리로 옮겨 담고 → invoke()하고 → 결과에서 필요한 것만 꺼냅니다.
  • ⚠️ 자식은 checkpointer를 받지 않는다 — 부모가 컴파일할 때 준 것이 자동 전파됩니다. 자식 compile()의 괄호는 비워 둘 것.
  • ⚠️ goto에 적는 건 등록 이름이다 — goto="kitchen"의 "kitchen"은 add_node의 첫 번째 인자이지 그래프 변수 이름이 아닙니다.
  • ⚠️ END는 두 겹이다 — 자식의 END는 "자식이 끝났다"일 뿐입니다. 그다음 행선지는 부모의 add_edge("kitchen", ...)가 정합니다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

식당 홀에서 주방 문을 바라보는 장면을 떠올리세요. 홀 직원에게 주방은 문 하나입니다. 주문표를 넣으면 음식이 나옵니다. 안에서 재료팀과 조리팀이 어떤 순서로 움직이는지는 알 필요도 없고 알 수도 없습니다.

그리고 이 문 안쪽과 바깥쪽이 같은 주문표를 쓰느냐가 두 방식을 가릅니다. 같은 종이를 쓰면 add_node 한 줄이면 되고, 종이를 나누면 매니저가 접수증을 대신 써 주는 절차(브릿지 노드)가 하나 더 붙습니다.

그리고 지금 "주방"이라고 부른 그 문 안에, 다음 장부터는 에이전트가 들어갑니다.
