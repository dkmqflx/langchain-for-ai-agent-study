3-2. 기초 아키텍처 패턴 — Routing

실습 노트북: 1-2.ipynb  ·  대상 범위: 기초 아키텍처 패턴 세 번째 — Routing  ·  난이도: 🟢 입문~초급

앞 문서에서 노드를 일렬로 줄 세우고(Chaining), 부챗살로 펼쳐(Parallelization) 봤습니다. 이번에 배울 Routing은 기초 아키텍처의 마지막 조각입니다. 한 문장으로 요약하면 이렇습니다 — 여러 전문가를 미리 만들어 두고, 들어온 일감을 보고 그중 하나에게만 토스한다. 실습으로는 고객 문의를 알아서 담당 부서로 넘겨주는 상담 서비스를 만듭니다.

이 장에서 배우는 것

새 문법은 사실상 두 개뿐입니다. 하나는 2강에서 이미 써 본 add_conditional_edges, 다른 하나는 LangChain에서 배웠던 with_structured_output입니다.

그런데 이번 장의 진짜 주제는 문법이 아니라 "약속"입니다. 라우터가 뱉는 값과 분기 함수가 기대하는 값이 사전에 딱 맞아떨어지도록 강제하는 법 — 이것이 라우팅 그래프가 흔들리지 않고 도는 유일한 비결입니다.

1. Routing — 상황을 보고 갈 길을 고른다

Routing 그래프는 맨 앞에 "라우터 노드(Router Node)"가 한 명 서 있는 구조입니다. 이 노드는 실제 일을 하지 않습니다. 오직 하나만 결정하죠 — "이 일은 아래 작업자 중 누구에게 넘겨야 하는가?"

그리고 라우터가 내놓은 그 결정값에 따라 조건부 함수가 작동하면서, 아래에 늘어선 전문가 노드 중 딱 하나만 실행됩니다. 나머지 노드들은 그날 아무 일도 하지 않고 그냥 서 있습니다.

실선과 점선 — 병렬 처리와 딱 하나 다른 점

앞 문서의 Parallelization 그림과 지금 Routing 그림을 나란히 놓으면 모양이 거의 똑같습니다. 위에 노드 하나, 아래에 작업자 여럿. 그런데 선의 종류가 다릅니다.

구분ParallelizationRouting
상위 → 하위 연결선실선 (add_edge)점선 (add_conditional_edges)
실행되는 작업자전원 예외 없이 다 돈다선택된 1명 나머지는 쉰다
상위 노드의 역할딱히 없음 (START에서 바로 갈라짐)누구에게 줄지 판단하는 게 전부
LLM 호출 횟수작업자 수만큼 (3명이면 3번)라우터 1번 + 전문가 1번 = 2번
🔍 비유 — 회람 vs 이관

Parallelization은 사내 회람입니다. 공문 하나를 전 부서에 똑같이 돌리고 각 부서 의견을 모아 종합하죠. 누가 답할지는 고민할 필요가 없습니다. 다 답하니까요.

Routing은 이관(移管)입니다. 민원이 들어오면 접수 창구가 내용을 읽고 "이건 세무과 건이네요" 하고 한 부서에만 넘깁니다. 노무과와 법무과는 이 민원의 존재조차 모릅니다.

💡 "하나만"이 아니라 "몇 개만"도 가능합니다

조건부 함수는 노드 이름 하나가 아니라 이름의 리스트를 반환할 수도 있습니다. 그러면 그 여러 노드가 동시에 실행되죠. 예를 들어 "이 업무를 끝내려면 검색 API와 RAG 둘 다 필요하겠다"는 판단이 나오면 두 노드를 함께 호출하는 식입니다.

핵심은 개수가 아니라 "전부 가느냐(실선), 골라서 가느냐(점선)"입니다.

언제 쓰는가 — 대표 사례 세 가지

슬라이드의 한 줄 정의는 이렇습니다 — "입력의 종류가 다양해서, 하나의 프로세스로 처리하기엔 너무 복잡하거나 비효율적일 때." 이 문장이 구체적으로 어떤 상황을 가리키는지 세 가지로 나눠 봅시다.

① 전문화가 필요할 때 (Specialization)

가장 흔한 경우입니다. 하나의 노드에 "너는 환불도 처리하고, 기술 지원도 하고, 제품 안내도 해"라고 전부 맡기는 대신, 각각의 전문가를 미리 만들어 두는 것이죠.

LangGraph 용어로 말하면 노드마다 페르소나(persona)를 따로 심어 둔다는 뜻입니다. 환불 담당 노드의 프롬프트는 "당신은 결제 및 환불 전문가입니다"로 시작하고, 기술 지원 노드는 "당신은 IT 엔지니어입니다"로 시작합니다. 같은 모델이지만 어떤 옷을 입혀 부르느냐에 따라 답변의 결이 완전히 달라집니다.

🔍 비유 — 노무사 · 세무사 · 변호사

회사에 노무사, 세무사, 변호사가 한 명씩 있다고 해봅시다. 어떤 프로젝트 건이 들어왔을 때 노무사와 세무사는 각자 자기 관점에서 검토가 필요하지만, 변호사는 굳이 볼 필요가 없다고 판단되면 — 라우터는 변호사를 아예 부르지 않습니다.

이게 회람(병렬)과의 차이입니다. 회람이었으면 변호사도 읽고 의견을 냈겠죠. 비용도 시간도 낭비고요.

② 도구(Tool) 선택이 명확해야 할 때

노드마다 연결된 도구가 다를 때도 라우팅이 답입니다. 개인 비서 Agent를 예로 들면 —

노드연결된 도구이런 요청이 오면
A 노드검색 API"오늘 서울 날씨 어때?"
B 노드캘린더 조회 API"내일 오후 일정 있나?"
C 노드RAG (사내 문서 검색)"작년 휴가 규정이 어떻게 되지?"

들어온 업무를 완료하기 위해 "나는 검색과 RAG를 호출해야겠다"고 라우터가 판단하면, 해당 도구가 붙어 있는 노드로 길을 열어주는 겁니다.

③ 모델 최적화 및 비용 절감

이건 지난 LangChain 강의에서도 비슷하게 구현해 본 적이 있는 패턴입니다. 노드마다 서로 다른 언어 모델을 붙여 두는 거죠.

💰 노드별로 모델 등급을 다르게
노드 A → gpt-5        (가장 비싸고 똑똑함)   ← 복잡한 추론·코드 생성
노드 B → gpt-5-mini   (중간)                 ← 일반적인 질의응답
노드 C → gpt-5-nano   (가장 저렴함)          ← 인사말, 단순 분류, 짧은 응답

그다음 라우터 노드가 질문의 난이도를 보고 판단합니다. "이 정도 질문이면 nano로 충분하겠다." 그 판단 결과에 따라 해당 노드만 호출하면, 품질은 지키면서 비용은 확 낮출 수 있습니다.

🔍 비유 — 병원 응급실의 트리아지(triage)

응급실에 환자가 들어오면 제일 먼저 만나는 사람은 의사가 아니라 분류 간호사입니다. 이 사람이 하는 일은 치료가 아니라 "이 환자는 어느 진료과, 어느 등급인가"를 정하는 것뿐이죠.

가벼운 찰과상 환자에게 외과 과장님을 붙이지 않습니다. 낭비니까요. 라우터 노드가 정확히 이 분류 간호사입니다. 싸고 빠른 모델을 쓰면 딱 좋은 자리이기도 하고요. (실습에서도 라우터와 전문가 모두 gpt-5-nano를 씁니다.)

2. 기획 — 고객 응대 서비스

2강부터 반복해 온 순서 그대로입니다. 요구사항 → 그래프 → State. 코드는 그다음입니다.

1요구사항

고객 문의를 성격에 맞는 전문가에게 전달

2그래프 구성

라우터 1 + 전문가 4, 조건부 엣지로 연결

3State 설계

질문 · 분류 결과 · 답변 세 칸

기획 2 · 그래프 구성

전문가는 네 명입니다. 각각 결제/환불 · 기술 지원 · 배송 · 일반 상담을 맡습니다. 마지막 일반 상담(general)은 "셋 다 아닐 때 가는 곳"이라는 점을 기억해 두세요. 나중에 조건부 함수를 짤 때 이 노드가 안전망 역할을 합니다.

기획 3 · State 설계 — 칸이 세 개면 충분하다

2강의 원칙을 다시 꺼냅니다. "다음 노드 혹은 다다음 노드가 읽어야 하는 값이라면 State에 담는다." 이 기준으로 그래프를 따라가며 필요한 칸을 세어 봅시다.

필드누가 쓰나누가 읽나왜 필요한가
query 사용자 (invoke 입력) router_node + 전문가 노드 라우터가 읽고 분류하고, 선택된 전문가도 읽고 답변한다
category router_node 조건부 함수 이 값을 보고 어느 노드로 갈지 결정한다
response 선택된 전문가 노드 사용자 (최종 반환) 최종 답변이 담기는 자리
💡 query는 두 번 읽힙니다

Chaining에서는 각 칸이 앞 노드 → 뒷 노드로 한 번씩만 배턴처럼 넘어갔습니다. 그런데 여기서 query는 라우터도 읽고, 그다음 전문가도 읽습니다.

이상한 게 아닙니다. State는 모든 노드가 함께 보는 공용 공책이니까요. 한 번 적힌 값은 누구든 몇 번이든 읽을 수 있습니다.

STEP 1. Model 정의

기획이 끝났으니 코딩입니다. 순서는 늘 같습니다 — ①모델 → ②State → ③Node → ④그래프 → ⑤실행.

📥 코드
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")

이번엔 temperature를 건드리지 않았습니다. 앞 문서의 농담 생성기는 뻔하면 재미없는 일이라 1.0을 줬지만, 고객 상담은 정반대입니다. 분류는 정확해야 하고 답변은 안정적이어야 하니 기본값 그대로가 맞습니다.

STEP 2. State 정의

📥 코드
from typing import TypedDict

class SupportState(TypedDict):
    query: str          # 고객 질문
    category: str       # 라우터가 분류한 카테고리
    response: str       # 전문가의 답변

리듀서는 하나도 없습니다. 그리고 그게 맞습니다 — 각 칸은 한 노드가 딱 한 번만 채우고 끝이니까요. 특히 response는 네 전문가가 같은 칸을 쓰지만, 한 번의 실행에서는 그중 한 명만 돌기 때문에 충돌이 일어나지 않습니다.

💡 병렬이었으면 response는 터졌을 겁니다

앞 문서에서 "워커 셋이 같은 칸에 쓰면 에러가 난다"고 배웠죠. 여기 response도 네 노드가 공유하는 칸입니다. 그런데 왜 괜찮을까요?

같은 스텝에 두 명 이상이 쓰지 않기 때문입니다. 라우팅은 애초에 한 명만 실행하니까요. "같은 칸이라서 문제"가 아니라 "동시에 써서 문제"였던 겁니다. 이 구분이 헷갈리면 리듀서를 언제 붙일지 계속 헷갈립니다.

🔑 여기서 한 가지 문제 — category에 뭐가 들어올지 어떻게 믿나

State는 다 만들었는데, 코딩을 더 진행하기 전에 반드시 짚고 넘어가야 할 게 하나 있습니다. 바로 category 칸입니다.

계획대로라면 라우터 노드가 이 칸을 채우고, 조건부 함수가 그 값을 읽어서 분기합니다. 그런데 라우터는 결국 언어 모델입니다. 언어 모델에게 "이 문의가 어느 부서 건인지 알려줘"라고 물으면 뭐라고 답할까요?

❌ 그냥 물어봤을 때 — 매번 다른 모양의 대답
"결제 관련 문의로 보입니다."
"billing"
"이 건은 결제/환불 부서에서 처리하는 것이 적절합니다."
"청구 부서"
"Billing Department"

전부 의미상으로는 정답입니다. 그런데 이걸 받아서 분기하는 코드는 이렇게 생겼죠.

💥 그 결과 — 조건문이 전부 빗나간다
if category == 'billing':          # "결제 관련 문의로 보입니다." != 'billing'  → False
    return 'billing_expert'
elif category == 'technical':      # → False
    return 'technical_expert'
elif category == 'shipping':       # → False
    return 'shipping_expert'
else:
    return 'general_expert'        # ← 결제 문의인데 매번 여기로 떨어짐

에러도 안 납니다. 그냥 조용히 전부 일반 상담원에게 흘러갈 뿐이죠. 전문가를 넷이나 만들어 놓고 한 명만 계속 일하는 그래프가 됩니다. 이런 버그는 발견하기가 제일 어렵습니다.

🚫 문제의 본질 — "약속되지 않은 값"

라우터 노드의 리턴값과 조건부 함수가 비교하는 문자열이 사전에 약속되어 있어야 분기가 제대로 됩니다.

즉 라우터가 낼 수 있는 답을 미리 정해진 몇 개로 제한(constrain)해야 합니다. "아무렇게나 답하지 말고, 이 네 개 중에서만 골라"라고 강제할 방법이 필요한 거죠.

(복습) 그 방법은 LangChain에서 이미 배웠습니다 — Structured Outputs

LangChain 강의에서 "답변을 특정 형태로 파싱해야 할 때" 쓰는 문법으로 Structured Outputs를 배웠습니다. 절차는 두 단계였죠.

1스키마(class) 생성

어떤 필드를, 어떤 타입으로, 무슨 기준으로 채울지 정의

2모델에 결합

model.with_structured_output(스키마)로 새 모델 객체를 만듦

🔍 비유 — 서술형 답안지 vs 객관식 답안지

모델에게 그냥 물어보는 건 백지에 서술형으로 쓰라는 것과 같습니다. 내용은 훌륭하겠지만 채점 프로그램은 못 읽습니다.

with_structured_output은 OMR 카드를 쥐여주는 것입니다. "1번부터 4번 중 하나에 마킹해." 이렇게 하면 기계가 100% 읽을 수 있는 답이 나옵니다. 뒤에 오는 조건부 함수가 바로 그 채점 기계고요.

RouteDecision 스키마 — 답을 네 개로 못 박기

이제 우리 상황에 맞는 스키마를 만들 차례입니다. 필드는 딱 하나(category)면 충분합니다. 라우터에게 시킬 일이 그것뿐이니까요.

📥 코드
from typing import Literal
from pydantic import BaseModel, Field

class RouteDecision(BaseModel):
    category: Literal['billing', 'technical', 'shipping', 'general'] = Field(
        description='고객 문의 내용을 분석하여 적절한 부서를 선택하세요'
    )

세 부분으로 나눠서 뜯어봅시다.

Literal['billing', 'technical', 'shipping', 'general'] — 선택지를 못 박는 타입

str이라고 쓰면 "문자열이면 뭐든 OK"라는 뜻입니다. Literal[...]은 "이 네 개 중 하나여야만 함"이라는 뜻이죠. 이 정보가 모델에게 그대로 전달되기 때문에, 모델은 네 값 외의 답을 낼 수 없습니다.

💡 값 이름은 마음대로 지어도 됩니다 — 단, 하나만 맞추면

'billing' 대신 'node_a', 'A', '결제'로 지어도 전혀 문제없습니다.

다만 여기서는 앞으로 만들 노드의 기능에 맞춰 이름을 붙였습니다. 나중에 조건부 함수를 읽을 때 if category == 'billing' 한 줄만 보고도 무슨 뜻인지 바로 이해되기 때문입니다. 미래의 나를 위한 배려죠.

Field(description=...) — 모델이 실제로 읽는 지시문

description은 사람을 위한 주석이 아닙니다. 이 문장은 스키마와 함께 모델에게 그대로 전달돼서, 모델이 어떤 기준으로 이 칸을 채울지 판단하는 근거가 됩니다.

그래서 "고객 문의 내용을 분석하여 적절한 부서를 선택하세요"라고 적었습니다. 여기가 사실상 라우터의 시스템 프롬프트인 셈입니다. 분류가 자꾸 엉뚱하게 나온다면 제일 먼저 손볼 곳이 이 문장입니다.

⚠️ 분류 정확도를 올리는 가장 싼 방법

description에 각 카테고리의 판단 기준을 예시와 함께 적어주면 정확도가 확 올라갑니다.

예: "billing은 요금·결제·환불, technical은 오류·API·설치 문제, shipping은 배송·주문 조회, 그 외 인사말이나 분류가 애매한 경우는 general을 선택하세요."

모델을 더 비싼 걸로 바꾸기 전에 이 문장부터 다듬으세요. 비용 0원짜리 개선입니다.

BaseModel — pydantic이 타입을 지켜준다

class RouteDecision(BaseModel)은 pydantic의 데이터 스키마입니다. 혹시 모델이 규칙을 어기고 이상한 값을 내면 pydantic 단계에서 걸러집니다. 이중 안전장치인 셈이죠 — 모델에게 제한을 알려주고, 결과도 검증하고.

router_llm — 스키마가 결합된 모델 객체

📥 코드
router_llm = model.with_structured_output(RouteDecision)

한 줄이지만 여기서 완전히 새로운 객체가 하나 생깁니다. 원래 model은 그대로 남아 있고, RouteDecision이라는 답안지가 물려 있는 또 다른 모델이 만들어지는 거죠.

구분modelrouter_llm
.invoke()의 반환 타입AIMessage 객체RouteDecision 객체
본문 꺼내는 법msg.contentdecision.category
답의 자유도무엇이든 줄글로네 값 중 하나
실습에서 쓰는 곳전문가 노드 4개라우터 노드 1개
⚠️ .content를 쓰면 에러가 납니다

router_llm.invoke(...)의 결과에는 .content가 없습니다. AIMessage가 아니라 RouteDecision이라는 파이썬 객체가 나오기 때문이죠.

그래서 접근 방법도 다릅니다. State는 딕셔너리라 state["query"]처럼 대괄호를 쓰지만, decision은 객체라 decision.category처럼 점(.)을 씁니다. 이 둘을 뒤집어 쓰는 실수가 정말 흔합니다.

STEP 3. Node 정의 — 관제탑 하나 + 전문가 넷

노드의 계약은 언제나 같습니다. ①state를 인자로 받고, ②State 양식에 맞는 딕셔너리를 반환한다. 다섯 노드 모두 이 계약을 따릅니다.

① router_node — 일하지 않고 결정만 하는 노드

📥 코드
# [Manager] router 노드
def router_node(state: SupportState):
    query = state["query"]
    print(f"\n--- [Router] 문의 분석 중: '{query}' ---")

    decision = router_llm.invoke(query)  # LLM이 문맥을 읽고 카테고리를 결정함 (Rule-based가 아님!)

    print(f"   -> 분류 결과: {decision.category.upper()} 부서로 연결합니다.")
    return {"category": decision.category}

네 줄짜리 노드입니다. State에서 query를 꺼내 → router_llm에 넘기고 → .category만 뽑아 → category 칸에 담아 반환. 답변을 만들지도, 프롬프트를 길게 쓰지도 않습니다. 오직 분류만 합니다.

주석의 "Rule-based가 아님!"이 왜 중요한가

전통적인 방식이라면 이 분류를 키워드 매칭으로 했을 겁니다.

🕰️ 옛날 방식 — 키워드 규칙
if '환불' in query or '결제' in query:
    category = 'billing'
elif '에러' in query or '오류' in query:
    category = 'technical'
# ...

이 방식은 "지난달 요금이 두 번 빠져나갔어요" 같은 문장에서 무너집니다. '환불'도 '결제'도 없기 때문이죠. 그런데 사람이 읽으면 명백히 결제 문제입니다.

LLM 라우터는 키워드가 아니라 문맥을 읽습니다. "요금이 두 번 빠져나갔다 = 중복 청구 = 결제 부서"라는 추론을 하는 거죠. 실제로 실습에서 이 문장은 정확히 billing으로 분류됩니다.

🔍 비유 — ARS와 사람 상담원

Rule-based 라우팅은 ARS입니다. "요금 문의는 1번, 고장 신고는 2번..." 고객이 미리 정해진 단어를 정확히 말해야만 작동하죠. 조금이라도 다르게 말하면 "다시 말씀해 주세요"를 무한 반복합니다.

LLM 라우팅은 사람 상담원입니다. 고객이 두서없이 상황을 설명해도 "아, 중복 결제 건이시군요" 하고 알아듣고 담당자에게 넘깁니다. 이 차이 하나 때문에 라우터 자리에 LLM을 세우는 겁니다.

💡 print는 장식이 아닙니다

라우팅 그래프에서 제일 궁금한 건 언제나 "얘가 어디로 갔지?"입니다. 그런데 조건부 엣지는 실행되지 않은 노드에 대해 아무 흔적도 남기지 않습니다.

그래서 라우터에 분류 결과를 찍고, 전문가 노드마다 자기 이름을 찍어두면 로그만 봐도 경로가 한눈에 보입니다. 라우팅 디버깅의 90%는 이 print 두 줄로 끝납니다.

② 전문가 노드 4종 — 같은 모델, 다른 페르소나

📥 코드
# [Expert A] 결제/환불 담당
def billing_expert(state: SupportState):
    print("--- [Billing Expert] 결제 전문가가 답변 작성 중 ---")
    prompt = f"당신은 결제 및 환불 전문가입니다. 다음 문의에 대해 정중하게 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

# [Expert B] 기술 지원 담당
def technical_expert(state: SupportState):
    print("--- [Tech Expert] 기술 지원 엔지니어가 분석 중 ---")
    prompt = f"당신은 IT 엔지니어입니다. 다음 기술 문제에 대해 해결책을 제시하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

# [Expert C] 배송 담당
def shipping_expert(state: SupportState):
    print("--- [Shipping Expert] 물류 담당자가 배송 조회 중 ---")
    prompt = f"당신은 배송 관리자입니다. 다음 배송 문의에 대해 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

# [Expert D] 일반 상담
def general_expert(state: SupportState):
    print("--- [General] 일반 상담원이 답변 중 ---")
    msg = model.invoke(f"다음 문의에 친절하게 답변하세요: {state['query']}")
    return {"response": msg.content}

네 함수를 나란히 놓고 보면 다른 부분이 딱 두 군데입니다 — 페르소나 문장과 print 라벨. 나머지는 완전히 동일하죠. 모델도 같은 model 하나를 공유합니다.

🔍 비유 — 배우 한 명, 배역 네 개

전문가가 넷이라고 해서 모델을 네 개 만든 게 아닙니다. 같은 배우에게 매번 다른 배역을 주는 것에 가깝습니다.

"당신은 결제 전문가입니다"라고 말하는 순간 모델의 어휘와 말투가 그쪽으로 쏠립니다. "당신은 IT 엔지니어입니다"라고 하면 갑자기 체크리스트와 원인 분석을 쏟아내죠. 실습 결과에서 이 차이가 눈으로 확인될 만큼 뚜렷하게 나타납니다.

💡 여기서 노드마다 다른 모델을 붙이면 — 그게 ③번 사례입니다

앞에서 이야기한 비용 절감 라우팅이 궁금하셨다면, 손댈 곳은 바로 이 네 함수입니다.

technical_expert만 model_pro = init_chat_model("gpt-5")를 쓰게 하고 나머지는 gpt-5-nano를 그대로 쓰면 — 어려운 기술 문의에만 비싼 모델이 투입되는 비용 최적화 그래프가 됩니다. 그래프 구조는 한 줄도 안 바꾸고요.

STEP 4. 그래프 생성

노드가 다 준비됐으니 조립할 차례입니다. 먼저 노드 등록과 확실한 엣지(START → 라우터)부터 긋습니다.

📥 코드
workflow = StateGraph(SupportState)

# 노드 등록
workflow.add_node("router_node", router_node)
workflow.add_node("billing_expert", billing_expert)
workflow.add_node("technical_expert", technical_expert)
workflow.add_node("shipping_expert", shipping_expert)
workflow.add_node("general_expert", general_expert)

# 엣지 연결
workflow.add_edge(START, "router_node")

노드는 다섯 개, 그런데 엣지는 아직 한 줄뿐입니다. START에서 라우터로 가는 길만 확실하고, 그 아래는 실행해 봐야 아는 길이니까요. 바로 그 "실행해 봐야 아는 부분"을 이제 만듭니다.

조건부 함수 route_to_expert — 갈림길의 판단 기준

📥 코드
# 조건부 엣지를 위한 함수
def route_to_expert(state: SupportState):
    category = state['category']

    if category == 'billing':
        return 'billing_expert'
    elif category == 'technical':
        return 'technical_expert'
    elif category == 'shipping':
        return 'shipping_expert'
    else:
        return 'general_expert'

State 속 category를 읽어서, 갈 노드의 이름을 문자열로 반환합니다. 그게 전부입니다.

⚠️ 이 함수는 노드가 아닙니다

생김새가 노드와 비슷해서 헷갈리기 쉬운데, 결정적 차이가 있습니다 — 노드는 딕셔너리를 반환해서 State를 바꾸고, 조건부 함수는 문자열을 반환해서 길을 정합니다.

그래서 add_node로 등록하지 않습니다. 그래프 그림에도 안 나옵니다. 화살표 위에 붙은 이정표 같은 존재죠.

반환값을 왜 'billing'이 아니라 'billing_expert'로 맞췄나

return 'billing'처럼 카테고리 값을 그대로 돌려줘도 동작은 합니다. 다만 그러면 add_conditional_edges에서 "billing이라는 답이 나오면 billing_expert로 가라"는 매핑 딕셔너리를 따로 적어줘야 합니다.

비교 — 두 가지 스타일
# 스타일 A) 반환값 = 노드 이름  → 리스트만 넘기면 끝  ★ 실습에서 쓰는 방식
return 'billing_expert'
workflow.add_conditional_edges('router_node', route_to_expert,
                               ['billing_expert', 'technical_expert', ...])

# 스타일 B) 반환값 = 카테고리   → 매핑 딕셔너리가 필요함
return 'billing'
workflow.add_conditional_edges('router_node', route_to_expert,
                               {'billing': 'billing_expert',
                                'technical': 'technical_expert', ...})

2강에서 이야기했던 그 요령입니다. 조건부 함수의 반환값을 등록한 노드 이름과 똑같이 맞춰두면 코드가 짧아지고, 연결 실수도 줄어듭니다.

else가 있어서 안전하다

마지막이 elif category == 'general'이 아니라 else인 게 포인트입니다. 앞의 세 조건에 안 걸리면 무조건 general_expert로 갑니다.

Literal 덕분에 값은 네 개 중 하나로 보장되지만, 혹시라도 예상 못 한 값이 들어와도 그래프가 멈추지 않게 하는 안전망이죠. 라우팅 함수에는 항상 else로 기본 경로를 하나 두세요.

add_conditional_edges — 점선 네 개를 한 번에 긋기

📥 코드
workflow.add_conditional_edges(
    'router_node',
    route_to_expert,
    ['billing_expert', 'technical_expert', 'shipping_expert', 'general_expert']
)

인자 세 개를 문장으로 읽으면 이렇습니다.

인자값뜻
1. 출발점'router_node'이 노드가 끝나면
2. 판단 로직route_to_expert이 함수를 돌려서
3. 도착 후보[네 개의 노드 이름]이 넷 중 하나로 간다
💡 세 번째 인자는 왜 필요한가 — 사실 "그림"을 위한 것

세 번째 인자를 생략해도 실행에는 지장이 없습니다. 조건부 함수가 반환하는 이름으로 알아서 찾아가니까요.

그런데 생략하면 LangGraph는 "이 라우터가 어디로 갈 수 있는지"를 미리 알 수 없습니다. 그래서 그래프 그림에 점선이 안 그려지거나 이상하게 그려집니다.

명시적으로 적어두면 그림도 정확해지고, 오타도 조기에 잡힙니다. 적는 습관을 들이세요.

마지막 — 전문가들을 END로 모으기

📥 코드
workflow.add_edge('billing_expert', END)
workflow.add_edge('technical_expert', END)
workflow.add_edge('shipping_expert', END)
workflow.add_edge('general_expert', END)

app = workflow.compile()

네 줄 모두 조건부가 아닌 그냥 add_edge입니다. 어느 전문가가 일하게 되든, 일이 끝나면 무조건 END이기 때문이죠. 고를 것이 없으니 실선입니다.

⚠️ 병렬 처리의 Fan-in과 모양은 같지만 의미가 다릅니다

앞 문서에서 워커 셋 → Aggregator로 모을 때도 화살표가 이렇게 모였죠. 하지만 거기서 Aggregator는 세 명이 전부 도착할 때까지 기다렸습니다.

여기 END는 기다리지 않습니다. 애초에 도착하는 노드가 한 명뿐이니까요. 화살표 개수가 아니라 "몇 개가 실제로 실행되는가"가 대기 여부를 결정합니다.

STEP 5. 실행 — 세 가지 문의를 던져보기

이제 성격이 다른 문의 세 개를 넣어 정말로 다른 전문가에게 가는지 확인합니다. 실행할 때 넣는 딕셔너리는 State 양식을 따라야 하므로 query 칸을 채워서 보냅니다.

케이스 1 — 결제 문의

📥 코드
app.invoke({"query": "지난달 요금이 두 번 빠져나갔어요. 확인해주세요."})
📤 실행 로그
--- [Router] 문의 분석 중: '지난달 요금이 두 번 빠져나갔어요. 확인해주세요.' ---
   -> 분류 결과: BILLING 부서로 연결합니다.
--- [Billing Expert] 결제 전문가가 답변 작성 중 ---

로그가 딱 두 줄이라는 데 주목하세요. 라우터 한 번, 전문가 한 번. technical·shipping·general은 아예 실행되지 않았습니다. 병렬이었다면 네 줄이 전부 찍혔겠죠.

📤 최종 반환값 (일부 발췌)
{'query': '지난달 요금이 두 번 빠져나갔어요. 확인해주세요.',
 'category': 'billing',
 'response': '안녕하세요. 불편을 겪게 해드려 정말 죄송합니다. 지난달 요금이 두 번 청구된 건
             신속하게 확인하고 환불 조치를 도와드리겠습니다.

             조사를 정확히 진행하기 위해 아래 정보를 알려주시면 ...
             - 계정에 등록된 이메일 주소나 사용자 ID
             - 두 번 청구된 날짜와 대략적인 시간 범위
             - 각 건의 청구 금액 ...'}

사과 → 필요 정보 요청 → 처리 절차 및 소요 기간 안내. 전형적인 결제 담당자의 화법입니다. "당신은 결제 및 환불 전문가입니다" 한 문장이 만든 차이죠.

케이스 2 — 기술 문의

📥 코드
app.invoke({"query": "API 연결할 때 404 에러가 자꾸 떠요."})
📤 실행 로그
--- [Router] 문의 분석 중: 'API 연결할 때 404 에러가 자꾸 떠요.' ---
   -> 분류 결과: TECHNICAL 부서로 연결합니다.
--- [Tech Expert] 기술 지원 엔지니어가 분석 중 ---
📤 최종 반환값 (일부 발췌)
{'query': 'API 연결할 때 404 에러가 자꾸 떠요.',
 'category': 'technical',
 'response': '404는 "해당 자원(path)이 서버에 없다"는 뜻이므로 ...

             2) 실전 체크리스트
             - 요청 URL 확인 (버전 경로 /v1, /v2 가 맞는가? 대소문자, 트레일링 슬래시)
             - 경로 구성 요소 점검 (동적 파라미터 id, URL 인코딩)
             - HTTP 메서드 확인
             - 인증/권한 여부 점검
             - 환경 차이 확인 (prod vs stage) ...'}

말투가 완전히 달라졌습니다. 사과 대신 원인 가설 → 체크리스트가 나오죠. 같은 gpt-5-nano인데도 이 정도 차이가 납니다. 페르소나 분리의 실질적인 효과가 여기서 드러납니다.

케이스 3 — 배송 문의

📥 코드
app.invoke({"query": "주문한 노트북 언제 도착하나요?"})
📤 실행 로그
--- [Router] 문의 분석 중: '주문한 노트북 언제 도착하나요?' ---
   -> 분류 결과: SHIPPING 부서로 연결합니다.
--- [Shipping Expert] 물류 담당자가 배송 조회 중 ---
📤 최종 반환값 (일부 발췌)
{'query': '주문한 노트북 언제 도착하나요?',
 'category': 'shipping',
 'response': '도와드리겠습니다. 정확한 도착일(ETA)을 알려면 주문 정보가 필요합니다.

             필요 정보
             - 주문번호
             - 운송장 번호(tracking number) 또는 배송 방법
             - 수령인 이름 ...'}
💡 "노트북"이라는 단어에 속지 않았습니다

"노트북"은 IT 제품입니다. 단순 키워드 매칭이었다면 technical로 잘못 분류될 여지가 충분했죠.

그런데 라우터는 "주문한 ~ 언제 도착하나요"라는 문장 전체의 의도를 읽고 배송 건으로 판단했습니다. 이게 LLM 라우터를 쓰는 이유입니다.

State(공책)가 채워지는 과정 — 케이스 1 기준

START

{'query': '지난달 요금이 두 번 빠져나갔어요...'}
category·response 두 칸은 비어 있음

router_node

query를 읽음 → router_llm 호출 → category 칸에 'billing' 기록
답변은 아직 한 글자도 없음

route_to_expert

(노드가 아님 · State를 바꾸지 않음)
category == 'billing' → 문자열 'billing_expert' 반환 → 길만 정함

billing_expert

query를 다시 읽음 → 결제 전문가 프롬프트로 모델 호출 → response 칸을 채움
"안녕하세요. 불편을 겪게 해드려 정말 죄송합니다..."

(나머지 3개 노드)

실행되지 않음. LLM 호출도, 비용도, 시간도 0

END

세 칸이 모두 찬 State 전체가 반환됨 — query · category · response

🔍 비유 — 민원 접수증 한 장이 돌아다닌다

State는 민원실 접수증입니다. 고객이 [민원 내용] 칸을 채워 제출하면, 접수 담당자가 [담당 부서] 칸에 "결제팀"이라고 도장을 찍고, 결제팀 직원이 [처리 결과] 칸을 채워 돌려주죠.

종이는 처음부터 끝까지 한 장입니다. 여러 사람이 자기 칸만 채워 나갈 뿐이죠. 그래서 마지막에 받아 보면 "무슨 질문이었고, 어디로 갔고, 뭐라고 답했는지"가 전부 남아 있습니다.

기초 패턴 세 가지 한자리에 놓고 비교

이번 장으로 기초 아키텍처 패턴 3종이 모두 끝났습니다. 한 표로 정리하면 이렇습니다.

💡 판단 기준은 질문 두 개면 끝납니다

Q1. 작업자들이 서로의 결과물을 봐야 하는가?
→ 그렇다면 Chaining (줄 세우기)

Q2. (안 봐도 된다면) 작업자를 전부 써야 하는가?
→ 전부 필요하면 Parallelization (펼치기)
→ 그중 골라야 하면 Routing (갈림길)

실무 그래프는 이 셋을 구간마다 섞어서 씁니다. 예를 들어 ①라우팅으로 담당 결정 → ②그 담당이 자료를 병렬 수집 → ③초안·검수 체인처럼요.

전체 코드 한눈에 보기

# ══ STEP 1. Model ═════════════════════════════════════
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END

model = init_chat_model("gpt-5-nano")

# ══ STEP 2. State ═════════════════════════════════════
from typing import TypedDict

class SupportState(TypedDict):
    query: str          # 고객 질문
    category: str       # 라우터가 분류한 카테고리
    response: str       # 전문가의 답변

# ══ 라우터의 답을 4개로 못 박는 스키마 ═══════════════════
from typing import Literal
from pydantic import BaseModel, Field

class RouteDecision(BaseModel):
    category: Literal['billing', 'technical', 'shipping', 'general'] = Field(
        description='고객 문의 내용을 분석하여 적절한 부서를 선택하세요'
    )

router_llm = model.with_structured_output(RouteDecision)   # ★ 이 한 줄이 라우팅의 안전벨트

# ══ STEP 3. Node ══════════════════════════════════════
# [Manager] 분류만 하고 답변은 하지 않는 노드
def router_node(state: SupportState):
    query = state["query"]
    print(f"\n--- [Router] 문의 분석 중: '{query}' ---")
    decision = router_llm.invoke(query)        # ★ 반환 타입은 AIMessage가 아니라 RouteDecision
    print(f"   -> 분류 결과: {decision.category.upper()} 부서로 연결합니다.")
    return {"category": decision.category}     # ★ 점(.)으로 접근

# [Expert A~D] 페르소나만 다르고 구조는 동일
def billing_expert(state: SupportState):
    print("--- [Billing Expert] 결제 전문가가 답변 작성 중 ---")
    prompt = f"당신은 결제 및 환불 전문가입니다. 다음 문의에 대해 정중하게 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

def technical_expert(state: SupportState):
    print("--- [Tech Expert] 기술 지원 엔지니어가 분석 중 ---")
    prompt = f"당신은 IT 엔지니어입니다. 다음 기술 문제에 대해 해결책을 제시하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

def shipping_expert(state: SupportState):
    print("--- [Shipping Expert] 물류 담당자가 배송 조회 중 ---")
    prompt = f"당신은 배송 관리자입니다. 다음 배송 문의에 대해 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

def general_expert(state: SupportState):
    print("--- [General] 일반 상담원이 답변 중 ---")
    msg = model.invoke(f"다음 문의에 친절하게 답변하세요: {state['query']}")
    return {"response": msg.content}

# ══ STEP 4. Graph ═════════════════════════════════════
workflow = StateGraph(SupportState)

workflow.add_node("router_node", router_node)
workflow.add_node("billing_expert", billing_expert)
workflow.add_node("technical_expert", technical_expert)
workflow.add_node("shipping_expert", shipping_expert)
workflow.add_node("general_expert", general_expert)

workflow.add_edge(START, "router_node")        # 실선 — 무조건 라우터부터

# 조건부 함수: State를 읽고 '갈 노드의 이름'을 문자열로 반환
def route_to_expert(state: SupportState):
    category = state['category']
    if category == 'billing':
        return 'billing_expert'
    elif category == 'technical':
        return 'technical_expert'
    elif category == 'shipping':
        return 'shipping_expert'
    else:                                      # ★ 안전망
        return 'general_expert'

# 점선 — 넷 중 하나로만 간다
workflow.add_conditional_edges(
    'router_node',
    route_to_expert,
    ['billing_expert', 'technical_expert', 'shipping_expert', 'general_expert']
)

# 실선 — 누가 일했든 끝나면 END
workflow.add_edge('billing_expert', END)
workflow.add_edge('technical_expert', END)
workflow.add_edge('shipping_expert', END)
workflow.add_edge('general_expert', END)

app = workflow.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
app.invoke({"query": "지난달 요금이 두 번 빠져나갔어요. 확인해주세요."})   # → billing
app.invoke({"query": "API 연결할 때 404 에러가 자꾸 떠요."})              # → technical
app.invoke({"query": "주문한 노트북 언제 도착하나요?"})                    # → shipping

자주 걸리는 함정 6가지

🕳️ 라우팅에서 실제로 밟게 되는 지뢰

1. 라우터를 그냥 model로 호출한다

router_llm이 아니라 model.invoke(query)를 쓰면 줄글 답변이 나옵니다. 그러면 조건문이 전부 빗나가서 에러 없이 조용히 general_expert로만 흘러갑니다. "분류가 다 general로 나온다"면 제일 먼저 이 줄을 의심하세요.

2. decision.content라고 쓴다

router_llm.invoke()는 AIMessage가 아니라 RouteDecision 객체를 반환합니다. .content는 존재하지 않습니다. decision.category가 맞습니다. State는 대괄호(state["query"]), 스키마 객체는 점(decision.category)으로 기억하세요.

3. 조건부 함수의 반환값과 노드 이름이 어긋난다

add_node("billing_expert", ...)로 등록해놓고 조건부 함수가 return 'billing'을 하면 "그런 노드 없다"는 에러가 납니다. 등록한 이름과 반환값을 똑같이 맞추는 게 가장 안전합니다.

4. 조건부 함수를 add_node로 등록한다

route_to_expert는 노드가 아닙니다. 노드는 딕셔너리를 반환해 State를 바꾸고, 조건부 함수는 문자열을 반환해 길을 정합니다. 등록하면 문자열을 State로 병합하려다 엉뚱한 에러가 납니다.

5. 전문가 → END 엣지를 빠뜨린다

네 개를 복사하다 보면 하나를 빼먹기 쉽습니다. 그러면 평소엔 멀쩡하다가 그 부서로 분류된 문의에서만 그래프가 이상하게 끝나죠. 가장 재현하기 어려운 종류의 버그입니다. 컴파일 후 그래프 그림에서 END로 들어오는 화살표 개수를 세어보세요.

6. description을 대충 쓰고 모델 탓을 한다

분류가 자꾸 틀린다면 모델이 아니라 Field(description=...)부터 보세요. 이 문장이 라우터의 유일한 판단 기준입니다. 카테고리별 예시를 한 줄씩 추가하는 것만으로 정확도가 눈에 띄게 올라갑니다.

💡 디버깅 요령 — 라우팅만 따로 떼어 테스트하세요

그래프 전체를 돌리면 전문가 답변 생성까지 기다려야 해서 확인이 느립니다.

router_llm.invoke("어떤 문의")만 단독으로 여러 번 호출해 보세요. 분류가 안정적인지 몇 초 만에 확인할 수 있습니다. 라우팅 그래프의 품질은 사실상 이 한 줄이 결정합니다.

📚 한 장 정리

오늘의 핵심 한 문장

라우터가 반환할 값을 미리 약속된 몇 개로 제한해야 조건부 함수가 그 약속에 따라 안정적으로 분기할 수 있다 — 그 제한을 거는 문법이 with_structured_output이다.

  • Routing이란 — 앞에 선 라우터 노드가 일감을 보고 아래 전문가 중 누구에게 줄지만 결정하는 구조. 나머지 노드는 실행되지 않는다.
  • 병렬과의 결정적 차이는 선의 종류 — 실선(add_edge) = 전원 실행, 점선(add_conditional_edges) = 골라서 실행. 그림만 봐도 어떤 문법인지 읽힌다.
  • 쓰는 신호 3가지 —
    • ①전문화 — 노드마다 페르소나를 심는다 (환불 / 기술 / 배송 / 일반)
    • ②도구 선택 — 노드마다 붙은 도구가 다르다 (검색 API / 캘린더 / RAG)
    • ③비용 절감 — 노드마다 모델 등급을 다르게 (gpt-5 / mini / nano)
  • State는 세 칸 — query(입력) · category(라우터의 결정) · response(전문가의 답). query는 라우터와 전문가가 두 번 읽고, response는 네 노드가 공유하지만 동시에 쓰지 않아 리듀서가 필요 없다.
  • 이 장의 심장 — Literal + with_structured_output
    • 그냥 물어보면 모델은 매번 다른 모양의 문장으로 답한다 → 조건문이 전부 빗나간다
    • Literal['billing', 'technical', 'shipping', 'general']로 선택지를 못 박고
    • Field(description=...)에 판단 기준을 적어주고
    • model.with_structured_output(스키마)로 답안지를 물린 모델을 만든다
    • 반환값은 AIMessage가 아니므로 .content가 아니라 .category
  • 조건부 함수는 노드가 아니다 — 딕셔너리가 아니라 문자열(갈 노드의 이름)을 반환한다. 반환값을 등록한 노드 이름과 똑같이 맞추면 add_conditional_edges에 리스트만 넘기면 된다. 그리고 마지막은 항상 else로 기본 경로를 둔다.
  • LLM 라우터는 키워드가 아니라 문맥을 읽는다 — "지난달 요금이 두 번 빠져나갔어요"에 '결제'라는 단어가 없어도 billing으로, "주문한 노트북 언제 도착하나요"는 '노트북'이 IT 제품이어도 shipping으로 간다. Rule-based로는 불가능한 판단이다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

민원실 접수 창구를 떠올리세요. 접수 담당자는 민원을 처리하지 않습니다. 읽고, [담당 부서] 칸에 도장을 찍고, 넘길 뿐이죠.

그런데 이 도장이 "결제팀", "청구 부서", "아마 결제 쪽일 듯"처럼 매번 다르게 찍히면 뒤에서 서류를 분류하는 사람이 일을 못 합니다.

그래서 도장은 네 개만 만들어 두고 그중 하나를 찍게 합니다. 그 도장통이 바로 Literal이고, 도장통을 손에 쥐여주는 행위가 with_structured_output입니다.

다음 예고 — 응용 아키텍처 패턴

이것으로 기초 아키텍처 패턴 세 가지(Prompt Chaining · Parallelization · Routing)가 모두 끝났습니다. 다음은 이 부품들을 조합한 응용 패턴 두 가지입니다.

지금까지와 무엇이 달라지나

Evaluator-Optimizer — 평가자가 "퇴짜"를 놓으면 생성자로 되돌아가는 루프입니다. 지금까지의 그래프는 전부 앞으로만 흘렀지만, 처음으로 뒤로 가는 화살표가 등장합니다.

Orchestrator-Worker — 지휘자가 일을 몇 조각으로 쪼갤지 실행 중에 정하고 그 개수만큼 워커를 만들어 뿌립니다. 오늘까지가 "미리 그려둔 도면대로 흐르는 구조"였다면, 다음은 "도면을 실행 중에 그리는 구조"입니다.
