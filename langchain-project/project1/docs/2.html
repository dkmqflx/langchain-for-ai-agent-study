검색 + 생성 + 근거(Citation)

복습 + Citation 신규 ⏱ 반나절
🎯 목표

질문을 받아 검색 → 생성 → 근거 반환까지 하는 answer() 함수를 완성한다.

🧠 개념

RAG의 핵심 원칙: 모델은 검색된 문맥으로만 답한다(환각 억제). 그리고 실무 RAG는 반드시 "이 답의 근거가 어느 문서 몇 페이지냐"를 함께 줘야 신뢰할 수 있습니다 — 금융 약관·의료처럼 정확성이 생명인 도메인에서 필수. 그래서 metadata의 source·page를 답변과 함께 반환합니다.

🛠 할 일

만들 파일은 rag.py 하나입니다. 먼저 다섯 조각으로 나눠 각 조각이 무슨 일을 하는지 보고, 맨 아래에 이어 붙인 전체 코드를 그대로 복사하면 됩니다. (조각 코드에는 설명이 본문에 있으니 주석을 뺐고, 전체 코드에는 주석이 다 들어 있습니다.)

🧭 다섯 조각 한눈에

① 저장해 둔 벡터DB 열기  →  ② 환각을 막는 프롬프트 짜기  →  ③ 검색된 청크에 번호표 붙이기  →  ④ 검색·생성·근거를 한 함수로 묶기  →  ⑤ 직접 실행해 보기

① 준비 — 이미 만들어 둔 벡터DB를 "열기"

STEP 1이 쓰기였다면 STEP 2는 읽기입니다. PDF를 다시 읽거나 임베딩을 다시 하지 않고, chroma_db 폴더에 저장해 둔 벡터를 그대로 엽니다. 여기서 만드는 건 부품 네 개예요 — 질문을 벡터로 바꿀 임베딩기, 창고(벡터DB), 창고에서 꺼내오는 검색기, 답을 쓸 LLM.

rag.py
import sys                                             # 터미널에서 준 인자(질문)를 읽기 위해 사용
from dotenv import load_dotenv                         # .env 파일을 읽어오는 도구
from langchain_chroma import Chroma                    # STEP 1에서 만들어 둔 벡터DB를 여는 도구
from langchain_openai import OpenAIEmbeddings          # 질문을 벡터로 바꿀 임베딩 모델
from langchain.chat_models import init_chat_model      # 모델 이름 문자열 하나로 챗 모델을 만들어 주는 헬퍼
from langchain_core.prompts import ChatPromptTemplate  # system/human 메시지 양식을 만드는 도구

load_dotenv()                                          # .env의 OPENAI_API_KEY를 환경변수로 등록

# 검색이란 '질문도 청크와 똑같은 방식으로 벡터화해서' 거리를 재는 일이다.
# 따라서 STEP 1에서 저장할 때 쓴 모델과 반드시 같아야 한다.
# 다르면 좌표계가 달라져 엉뚱한 청크가 걸리는데, 에러는 안 나고 결과만 조용히 나빠진다.
emb = OpenAIEmbeddings(model="text-embedding-3-small")

# 이미 만들어 둔 벡터DB를 '연다'(새로 저장하는 게 아니다).
# collection_name·persist_directory는 STEP 1에서 저장할 때 쓴 값과 같아야 한다. 다르면 빈 DB가 열린다.
vs = Chroma(collection_name="p1_docs", persist_directory="chroma_db", embedding_function=emb)

# as_retriever = 벡터DB를 '질문을 넣으면 관련 청크를 돌려주는 물건'으로 감싼다.
# k=4 → 질문 하나당 가장 유사한 청크를 4개 가져온다. (크면 문맥은 풍부해지지만 노이즈·비용↑)
retriever = vs.as_retriever(search_kwargs={"k": 4})

llm = init_chat_model("gpt-5-mini", reasoning_effort="low")   # 검색된 문맥을 읽고 답변 문장을 만들어 낼 LLM

as_retriever()가 하는 일은 "벡터DB"를 "질문을 넣으면 관련 청크를 주는 물건"으로 감싸는 것입니다. k=4는 매번 4개를 가져오라는 뜻이고요. 이 숫자가 크면 문맥이 풍부해지는 대신 노이즈와 비용이 늘고, 작으면 정답 조각을 놓칠 수 있어 STEP 8에서 튜닝 대상이 됩니다.

⚠️ 임베딩 모델은 STEP 1과 반드시 같아야 합니다

검색은 질문도 똑같은 방식으로 벡터로 바꿔서 저장된 청크 벡터와 거리를 재는 일입니다. STEP 1에서 text-embedding-3-small로 저장해 놓고 여기서 다른 모델을 쓰면 좌표계가 달라져 엉뚱한 청크가 걸립니다. 에러도 안 나고 결과만 조용히 나빠져서 찾기 어려운 유형의 버그예요. collection_name·persist_directory도 STEP 1과 같은 값이어야 합니다.

② 프롬프트 — 환각을 막는 "규칙"을 문장으로 못 박기

RAG의 안전장치는 대부분 프롬프트 몇 줄에 들어 있습니다. system은 모델이 지켜야 할 규칙, human은 실제 질문과 검색된 문맥입니다.

rag.py (이어서)
# ChatPromptTemplate = LLM에게 보낼 '메시지 양식'. 두 종류를 넣는다.
#   system → 모델이 지켜야 할 규칙 (대화 내내 적용되는 지시사항)
#   human  → 사용자가 실제로 보내는 내용 (질문 + 검색된 문맥)
PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     # 규칙 1 — 모델이 원래 알고 있던 지식이 아니라 '검색된 CONTEXT'만 근거로 답하게 한다.
     #          우리가 원하는 건 일반 상식이 아니라 '이 문서에 뭐라고 쓰여 있는지'이기 때문.
     "너는 제공된 CONTEXT만 근거로 답한다. "
     # 규칙 2 — 모르면 모른다고 말할 '출구'를 열어 준다.
     #          이 문장이 없으면 모델은 어떻게든 그럴듯한 답을 지어낸다(환각).
     "CONTEXT에 근거가 없으면 '문서에서 찾을 수 없습니다'라고 답하고 추측하지 마라. "
     # 규칙 3 — 아래 format_context()가 붙여 줄 번호표를 답변에서 인용하게 한다.
     "답변 끝에 사용한 근거 번호를 [1][2]처럼 표기하라."),

    # {question}·{context}는 아직 값이 없는 '빈칸'이다. 나중에 invoke 할 때 실제 값이 채워진다.
    # \n 은 줄바꿈 → 질문과 CONTEXT가 한 덩어리로 붙지 않게 띄워 준다.
    ("human", "질문: {question}\n\nCONTEXT:\n{context}"),
])

규칙은 세 개인데, 각각 하는 일이 다릅니다.

  • "CONTEXT만 근거로" — 모델이 원래 알고 있던 지식으로 답하지 못하게 막습니다. 우리가 원하는 건 일반 상식이 아니라 이 약관에 뭐라고 쓰여 있는지니까요.
  • "없으면 '문서에서 찾을 수 없습니다'" — 모르면 모른다고 말할 출구를 열어 주는 겁니다. 이 문장이 없으면 모델은 어떻게든 그럴듯한 답을 지어냅니다.
  • "근거 번호를 [1][2]처럼" — 아래 ③에서 붙일 번호표를 쓰라는 지시입니다. (자세한 건 맨 아래 citation 설계에서)

{question}·{context}는 아직 빈칸입니다. 지금은 양식만 만들어 둔 것이고, 실제 값은 ④에서 채워집니다.

③ format_context() — 청크에 번호표 붙여 한 덩어리로

검색기는 Document 객체 리스트를 주는데, LLM은 문자열만 먹습니다. 그래서 사이에 변환기가 필요해요. 이때 그냥 이어 붙이지 않고 번호와 출처를 같이 적는 게 포인트입니다.

rag.py (이어서)
def format_context(docs):
    """검색된 청크 여러 개를 '[번호] (출처) 본문' 형태의 문자열 하나로 합친다."""
    # 검색기는 Document '객체 리스트'를 주지만 LLM은 '문자열'만 받는다 → 그 사이를 잇는 변환기.
    # "\n\n".join(...) = 각 조각 사이에 빈 줄을 하나 넣어 긴 문자열 하나로 이어 붙인다.
    return "\n\n".join(
        # f"..." 는 f-string: 중괄호 {} 안의 값을 문자열 중간에 끼워 넣는 문법이다.
        #   i+1                       → 1부터 시작하는 번호 (i는 0부터라서 +1). 이게 답변의 [1][2]가 된다
        #   d.metadata.get('source')  → STEP 1에서 자동으로 담긴 파일 경로
        #   d.metadata.get('page')    → 쪽 번호. .get()을 쓰면 값이 없을 때 에러 대신 None이 나온다
        #   d.page_content            → 청크의 실제 본문 텍스트
        f"[{i+1}] (source={d.metadata.get('source')}, page={d.metadata.get('page')})\n{d.page_content}"
        for i, d in enumerate(docs)   # enumerate = 리스트를 돌면서 (순번, 항목)을 함께 꺼내 준다
    )

결과는 이렇게 생긴 문자열 하나입니다.

[1] (source=data/03_신용카드개인회원표준약관_SC제일은행.pdf, page=25)
제40조 (카드의 분실ㆍ도난신고와 보상) ① 회원은 카드를 분실하거나 ...

[2] (source=data/03_신용카드개인회원표준약관_SC제일은행.pdf, page=26)
제41조 (위·변조카드 사용 등에 대한 책임) ① 다음 각 호에 따른 ...

번호를 매겨 두면 모델이 답변에서 [1], [2]로 어떤 근거를 썼는지 콕 집어 가리킬 수 있습니다. 번호가 없으면 "세 번째로 주신 그거요"라고밖에 말할 수 없어요.

④ answer() — 검색 → 생성 → 근거를 한 함수로

이 프로젝트의 심장입니다. STEP 5(서빙)·STEP 7(평가)이 전부 이 함수 하나를 부릅니다.

rag.py (이어서)
def answer(question: str):
    """질문 하나를 받아 검색 → 생성 → 근거까지 끝낸 결과를 dict로 돌려준다."""

    # (1) 검색 — 벡터DB에서 질문과 의미가 가까운 청크 4개를 꺼낸다. 결과는 Document 리스트.
    docs = retriever.invoke(question)

    # (2) 조립 — 양식의 빈칸({question}·{context})에 실제 값을 채워 '보낼 메시지'를 완성한다.
    #     여기서는 아직 LLM을 부르지 않는다. 문자열을 만드는 것뿐이라 즉시 끝나고 비용도 없다.
    msg = PROMPT.invoke({"question": question, "context": format_context(docs)})

    # (3) 생성 — 여기서 처음으로 OpenAI 서버에 요청이 나간다. 시간과 비용이 드는 유일한 줄.
    resp = llm.invoke(msg)

    return {
        # resp는 객체이므로 .content로 글자만 꺼낸다
        "answer": resp.content,
        # 근거 목록 — 답이 어느 파일 몇 쪽에서 왔는지. 화면에 '출처 보기'를 그리거나 사람이 확인할 때 쓴다.
        # [ ... for d in docs ] 는 리스트 컴프리헨션: docs를 돌면서 새 리스트를 만드는 문법.
        "citations": [{"source": d.metadata.get("source"), "page": d.metadata.get("page")} for d in docs],
        # 검색된 원문 전체 — 사람에게 보여줄 용도가 아니라 STEP 7 RAGAS가 '검색이 잘 됐나'를 채점할 때 쓴다
        "contexts": [d.page_content for d in docs],
    }
🔌 invoke가 세 번 나오는데, 왜죠?

invoke는 "LLM을 호출한다"는 뜻이 아닙니다. "이 부품에 입력을 넣고 결과를 받아라"라는, 랭체인 모든 부품이 공통으로 가진 실행 버튼 이름이에요. 부품이 다르니 하는 일도 완전히 다릅니다.

  • retriever.invoke(질문) → Document 4개 · 벡터DB에서 꺼내옴
  • PROMPT.invoke(딕셔너리) → 메시지 묶음 · 빈칸에 값을 끼우는 문자열 조립일 뿐, 네트워크를 타지 않고 공짜
  • llm.invoke(메시지 묶음) → AIMessage · 여기서 처음으로 OpenAI 서버에 요청이 나감(유료·수 초)

편지에 비유하면 PROMPT.invoke는 양식에 내용을 채워 편지를 완성하는 것, llm.invoke는 그 편지를 부치고 답장을 받는 것입니다. 이름을 통일해 둔 덕분에 chain = PROMPT | llm처럼 레고처럼 이어 붙일 수도 있는데, 여기서는 중간에 무엇이 흘러가는지 눈으로 보려고 일부러 나눠 썼습니다. RAG가 이상하게 답할 때 원인은 십중팔구 모델이 아니라 모델에게 넘어간 문맥이라, 이 지점을 열어두는 게 유리합니다.

반환하는 dict의 세 항목은 읽는 사람이 각각 다릅니다.

항목담기는 것누가 쓰나
answer최종 답변 텍스트사람이 읽음
citations출처 주소만 (source · page)화면·API STEP 5
contexts검색된 원문 전체RAGAS 평가기 STEP 7

⑤ 직접 실행해 보기

마지막은 이 파일을 직접 돌렸을 때만 실행되는 부분입니다. 기본 질문은 여러분 문서에 실제로 있는 내용으로 바꾸세요. 인자를 받게 해두면 아래 검증 게이트의 "문서에 없는 질문"도 파일을 고치지 않고 확인할 수 있습니다.

rag.py (이어서)
DEFAULT_QUESTION = "신용카드 회원의 카드 분실·도난 시 책임은 어떻게 되나요?"

if __name__ == "__main__":
    import json
    question = sys.argv[1] if len(sys.argv) > 1 else DEFAULT_QUESTION
    print(json.dumps(answer(question), ensure_ascii=False, indent=2))
📄 전체 코드 (위 다섯 조각을 이어 붙인 것)
rag.py
# ═══════════════════════════════════════════════════════════════════
# STEP 2 · 검색 + 생성 + 근거(Citation): 질문 → 관련 청크 검색 → LLM이 그 문맥으로만 답변.
# 핵심 원칙  (1) 모델은 검색된 CONTEXT만 근거로 답한다(환각 억제)
#           (2) 답과 함께 '어느 문서 몇 쪽'(source·page)을 근거로 돌려준다
# 이 answer()가 이후 하이브리드(STEP 3)·서빙(STEP 5)·평가(STEP 7)의 공통 진입점이 된다.
#
# STEP 1(ingest.py)은 '쓰기'였다면 여기는 '읽기'다 — 이미 저장된 벡터DB를 열어 검색만 한다.
# ═══════════════════════════════════════════════════════════════════
import sys
from dotenv import load_dotenv
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain.chat_models import init_chat_model          # 문자열 하나로 챗 모델을 만드는 헬퍼
from langchain_core.prompts import ChatPromptTemplate      # system/human 메시지 템플릿

load_dotenv()                                              # .env의 OPENAI_API_KEY 로드
# 검색은 '질문도 같은 방식으로 벡터화해서' 청크 벡터와 비교하는 것 → STEP 1에서 저장할 때 쓴
# 임베딩 모델과 반드시 같아야 한다. 다르면 좌표계가 달라져 엉뚱한 청크가 걸린다.
emb = OpenAIEmbeddings(model="text-embedding-3-small")
# 이미 인덱싱된 벡터DB를 연다(새로 저장하지 않고 읽기 전용). collection·경로는 STEP 1과 동일하게
vs = Chroma(collection_name="p1_docs", persist_directory="chroma_db", embedding_function=emb)
retriever = vs.as_retriever(search_kwargs={"k": 4})        # 질문당 가장 유사한 청크 4개를 가져오는 검색기
llm = init_chat_model("gpt-5-mini", reasoning_effort="low")   # 답변을 생성할 LLM

# 프롬프트: system=규칙(문서 밖 내용은 지어내지 말 것 = 환각 억제), human=질문 + 검색된 문맥
PROMPT = ChatPromptTemplate.from_messages([
    ("system",
     "너는 제공된 CONTEXT만 근거로 답한다. "
     "CONTEXT에 근거가 없으면 '문서에서 찾을 수 없습니다'라고 답하고 추측하지 마라. "
     "답변 끝에 사용한 근거 번호를 [1][2]처럼 표기하라."),
    ("human", "질문: {question}\n\nCONTEXT:\n{context}"),   # {question}·{context}는 invoke 때 채워짐
])

def format_context(docs):
    """검색된 청크들을 '[번호] (source, page) + 본문' 형태의 한 문자열로 합친다.

    LLM에게는 Document 객체가 아니라 '하나의 긴 문자열'로 문맥을 넘겨야 한다.
    이때 번호를 매겨두면 LLM이 답변 끝에 [1][2]로 어떤 근거를 썼는지 가리킬 수 있다.
    """
    return "\n\n".join(
        f"[{i+1}] (source={d.metadata.get('source')}, page={d.metadata.get('page')})\n{d.page_content}"
        for i, d in enumerate(docs)                        # i=0,1,2... 각 청크에 번호 부여
    )

def answer(question: str):
    """질문 하나를 받아 검색 → 생성 → 근거까지 끝낸 결과 dict를 돌려준다."""
    docs = retriever.invoke(question)                      # (1) 검색: 질문과 유사한 청크 4개
    msg = PROMPT.invoke({"question": question, "context": format_context(docs)})  # (2) 프롬프트에 질문·문맥 주입
    resp = llm.invoke(msg)                                 # (3) 생성: LLM이 문맥 기반으로 답변
    return {
        "answer": resp.content,                            # 최종 답변 텍스트
        # 근거 목록: 답이 어느 파일 몇 쪽에서 왔는지 (신뢰성의 핵심)
        "citations": [{"source": d.metadata.get("source"), "page": d.metadata.get("page")} for d in docs],
        "contexts": [d.page_content for d in docs],   # 검색된 원문들 → STEP 7 RAGAS 평가에서 사용
    }

# 검증 게이트용 기본 질문: 신용카드표준약관 제40·41조에 실제로 있는 내용
DEFAULT_QUESTION = "신용카드 회원의 카드 분실·도난 시 책임은 어떻게 되나요?"

if __name__ == "__main__":
    import json
    # 인자를 주면 그 질문으로 실행 → 검증 게이트의 '문서에 없는 질문'도 파일 수정 없이 확인 가능
    #   uv run python rag.py "문서에 없는 질문"
    question = sys.argv[1] if len(sys.argv) > 1 else DEFAULT_QUESTION
    # 결과를 보기 좋게 출력(한글 안 깨지게 ensure_ascii=False)
    print(json.dumps(answer(question), ensure_ascii=False, indent=2))

실행: uv run python rag.py  /  다른 질문으로: uv run python rag.py "문서에 없는 질문"

✅ 검증 게이트 문서에 있는 내용을 물으면 답변 + citations(source·page)가 나오고, 문서에 없는 내용을 물으면 "문서에서 찾을 수 없습니다"가 나오면 통과. (환각을 막는지 반드시 두 경우 다 확인하세요.)
🎓 배우는 것

RAG 체인을 함수로 캡슐화 + citation 설계 + 프롬프트로 환각 억제. 이 answer()가 이후 서빙·평가·하이브리드의 공통 진입점이 됩니다.

📌 더 알아보기 — "citation 설계"가 뭔가요?

위 "🎓 배우는 것"에 나온 citation 설계는 말이 거창하지만, 한 문장으로 줄이면 "답변에 근거를 어떻게 딸려 보낼지 미리 정해두는 것"입니다.

📚 비유 — 교과서의 각주

"조선의 인구는 약 1,000만 명이었다 3)" 라고 쓰인 교과서를 떠올려 보세요. 문장 뒤의 3) 번호와, 페이지 아래의 "3) 세종실록 21권, 45쪽"이 한 쌍으로 있어야 독자가 "정말인가?" 하고 직접 펴서 확인할 수 있습니다. 둘 중 하나만 있으면 소용이 없죠. RAG의 citation도 똑같습니다 — 답변 속 번호와 그 번호가 가리키는 출처 목록, 이 두 개를 만들어 주는 게 전부입니다.

왜 필요한가 — 근거 없는 답은 못 쓴다

citation 없이 RAG를 만들면 결과는 줄글 한 덩어리입니다. "카드를 분실하면 신고일로부터 60일 전까지 소급해 보상받을 수 있습니다." — 맞는 말 같지만, 이게 약관에 실제로 있는 문장인지 모델이 그럴듯하게 지어낸 문장인지 사용자는 알 방법이 없습니다. 금융 약관·의료처럼 틀리면 안 되는 도메인에서는 이런 답을 그대로 쓸 수 없어요. 뒤에 "03_신용카드표준약관 25쪽"이 붙어야 비로소 확인 가능한 답이 됩니다.

설계할 곳이 네 군데 있습니다

근거는 저절로 붙지 않습니다. 아래 네 곳에서 하나씩 챙겨야 하고, 한 군데라도 빠지면 근거가 끊깁니다.

단계 무엇을 하나 코드 위치 빠뜨리면
① 남기기 청크에 source(파일)·page(쪽)를 붙여 저장 ingest.py — PyMuPDFLoader가 자동으로 넣어줌 나중에 근거를 만들 방법이 아예 없음 — STEP 1을 다시 해야 함
② 번호 붙이기 검색된 청크마다 [1] [2] [3] [4] 번호표를 달아 LLM에 넘김 rag.py — format_context() 모델이 "세 번째로 주신 그거요"라고밖에 못 가리킴
③ 쓰라고 시키기 "답변 끝에 근거 번호를 [1][2]처럼 표기하라"를 system에 명시 rag.py — PROMPT 번호를 줘도 모델이 안 씀
④ 따로 빼기 출처를 citations 리스트로 답변 텍스트와 분리해 반환 rag.py — answer()의 return STEP 5에서 API가 답변 문자열을 정규식으로 뜯어야 함

실제로 어떻게 도는지 — 눈으로 보기

②에서 format_context()가 만들어 LLM에게 넘기는 문자열은 이렇게 생겼습니다. (번호표를 붙이는 부분)

[1] (source=data/03_신용카드개인회원표준약관_SC제일은행.pdf, page=25)
제40조 (카드의 분실ㆍ도난신고와 보상) ① 회원은 카드를 분실하거나 도난당한 경우 즉시 은행 또는 ...

[2] (source=data/03_신용카드개인회원표준약관_SC제일은행.pdf, page=26)
제41조 (위·변조카드 사용 등에 대한 책임) ① 다음 각 호에 따른 카드의 사용으로 생기는 책임은 ...

그러면 모델은 ③의 지시에 따라 문장마다 번호를 달아 답합니다.

회원은 분실·도난 시 즉시 은행에 신고해야 하며, 신고 접수일로부터 소급하여
60일 이내의 제3자 부정사용액에 대해 보상을 신청할 수 있습니다. [1]
위·변조된 카드 사용으로 생긴 책임은 원칙적으로 은행에 있습니다. [2]

마지막으로 ④가 답변과 출처를 분리해서 돌려줍니다.

{
  "answer": "회원은 분실·도난 시 즉시 ... [1] ... 은행에 있습니다. [2]",
  "citations": [
    {"source": "data/03_신용카드개인회원표준약관_SC제일은행.pdf", "page": 25},
    {"source": "data/03_신용카드개인회원표준약관_SC제일은행.pdf", "page": 26}
  ]
}

정리하면 answer는 사람이 읽는 것, citations는 프로그램이 읽는 것입니다. 이렇게 나눠 뒀기 때문에 STEP 5에서 FastAPI가 그대로 JSON으로 내보낼 수 있고, 화면에서는 "📄 출처 보기 · 25쪽" 같은 버튼을 만들 수 있습니다. 만약 출처가 답변 문자열 안에만 있었다면, 화면을 만들 때마다 글자를 파싱해서 긁어내야 했을 거예요.

⚠️ 헷갈리기 쉬운 점 — citations는 "실제 인용"이 아니라 "후보"입니다

지금 코드의 citations에는 검색된 4개가 전부 들어갑니다. 모델이 답에 실제로 쓴 건 그중 2개뿐일 수도 있어요 — 진짜 쓰인 건 답변 본문의 [1][2] 번호입니다. 둘을 정확히 맞추려면 모델에게 "쓴 번호"를 구조화된 출력으로 따로 받아 걸러내야 하는데, 이 프로젝트는 단순한 쪽을 택했습니다. 근거가 조금 넉넉하게 딸려 오는 건 확인에 방해가 되지 않으니까요.

citations와 contexts는 왜 따로 있나요?

answer()가 돌려주는 dict에는 비슷해 보이는 항목이 둘 있는데, 읽는 사람이 다릅니다.

항목 담기는 것 누가 쓰나 목적
citations 출처 주소만 (source · page) 사용자 · 화면 STEP 5 "이 답 어디서 나왔어?"를 확인시켜 주기
contexts 검색된 원문 전체 RAGAS 평가기 STEP 7 "검색이 제대로 됐나"를 기계가 채점하기
💡 보너스 — citation은 "검색 품질 디버깅 도구"이기도 합니다

문서에 분명히 있는 내용을 물었는데 "문서에서 찾을 수 없습니다"가 나올 때가 있습니다. 이건 대개 LLM 잘못이 아니라, 검색이 엉뚱한 청크를 가져온 것입니다. 이때 citations를 출력해 보면 바로 판별됩니다 — 질문과 상관없는 페이지가 올라와 있으면 검색 문제 확정이죠. (실제로 "통장 분실 시 어떻게 하나요?"를 물었더니 예금거래기본약관의 입금·수수료 조항이 딸려온 적이 있습니다.) 바로 이래서 STEP 3에서 키워드 검색(Hybrid)을, STEP 4에서 재정렬(Reranker)을 붙입니다. 근거를 보여주는 장치가, 동시에 다음 단계가 왜 필요한지도 알려주는 셈입니다.
