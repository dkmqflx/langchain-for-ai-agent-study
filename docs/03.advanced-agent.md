1. state (상태)

- LangGraph에서 state는 그래프 내의 노드들이 공유하는 공통 메모리입니다.

- 그래프가 실행되는 동안 각 노드는 이 상태를 읽고 수정하며 다음 단계로 전달합니다.

- 의미: 현재 워크플로우가 가지고 있는 데이터의 스냅샷입니다.

- 출력된 값 분석:

  ```js
   state {'messages': [HumanMessage(content='안녕하세요, 내 이름은 무엇인가요', ...)]}
  ```

  - messages: 현재 상태에 저장된 메시지 리스트입니다.

  - HumanMessage: 사용자가 입력한 메시지 객체입니다.

  - content='안녕하세요, 내 이름은 무엇인가요': 사용자가 실제로 던진 질문 내용입니다.

  - 이 출력은 현재 그래프의 상태에 사용자의 질문이 담긴 메시지 리스트가 하나 존재함을 보여줍니다.

2. runtime (런타임)

- runtime은 그래프가 실행되는 동안 유지되는 실행 환경 정보(Configuration)를 담고 있습니다.

- state가 "무엇을 처리하는가"에 집중한다면, runtime은 "어떤 환경에서 처리하는가"를 나타냅니다.

- 출력된 값 분석:

  ```js
    runtime Runtime(context=Context(user_name='John Doe'), store=None, ...)
  ```

  - `context=Context(user_name='John Doe')`: 가장 중요한 부분입니다. 코드에서 config를 통해 주입한 외부 변수입니다.

  - 에이전트는 state에는 없지만 이 runtime.context를 통해 "현재 대화 중인 사용자가 John Doe구나"라는 사실을 알 수 있습니다.

  - `store=None`: 상태를 영구적으로 저장하기 위한 외부 저장소(BaseStore)가 설정되지 않았음을 의미합니다.

  - `stream_writer`: 스트리밍 출력을 처리하기 위한 내부 함수 포인터입니다.

- Checkpointer (Short-term): 특정 **thread_id (채팅방)**에 종속된 데이터. (예: 세션 데이터)

- Store (Long-term): user_id (사용자 전체) 혹은 시스템 전체에 공유되는 데이터. (예: 사용자 프로필, 선호도 설정)

- PostgresSaver를 써서 DB에 저장하더라도, 그것이 **"특정 대화방의 기록"**을 저장하는 것이라면 랭체인 아키텍처상
  Short-term memory로 분류합니다. 그 이유를 로우레벨 원리로 설명해 드릴게요.

- 1. Short-term Memory (Checkpointer)

  - "한 대화의 맥락을 이어가기 위한 기억"

  - 저장 내용: messages (대화 내역), node (현재 실행 단계), config 등.

  - 키워드: thread_id.

  - 원리: 에이전트가 "그거 아까 말한 대로 처리해줘"라고 했을 때, "아까"가 무엇인지 알려주기 위한 기억입니다.

  - 왜 Short-term인가?: 대화가 길어져서 요약(Summarization)되거나 삭제되면 사라질 수 있는 '휘발성 맥락'이기 때문입니다. 비록 DB(PostgresSaver)에 저장해서 1년 뒤에 꺼내볼 수 있더라도, 에이전트 입장에서는 해당 채팅방을 벗어나면 참조하지 않는 정보이므로 '단기 기억'입니다.

- 2. Long-term Memory (Store)

  - "대화방이 바뀌어도 유지되는 사용자에 대한 지식"

  - 저장 내용: "이 유저는 TypeScript를 좋아함", "이 유저는 이메일을 보낼 때 항상 끝에 '드림'을 붙임", "유저의 생일은 5월 4일임".

  - 키워드: user_id 또는 namespace.

  - 원리: 에이전트가 여러 개의 채팅방(thread_id 1번, 2번, 3번)을 가지고 있어도, 어느 방에서든 공통적으로 알고 있어야 하는 유저에 대한 정보입니다.

  - 왜 Long-term인가?: 특정 대화의 맥락(Context)이 끝나더라도 시스템이 "학습"하여 계속 가지고 있는 지식이기 때문입니다.
