08. RAG 응용: Hybrid Search (BM25 + 벡터)

실습 노트북: 08.ipynb  ·  원문: docs/04.rag.md 3장 RAG 응용  ·  난이도: 🟡 중급  ·  선행: 07. 캐시 임베더로 저장·검색

이 자료는 실습 노트북(08.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 지금까지 우리는 문서를 벡터(의미)로 바꿔 검색했습니다. 그런데 벡터 검색이 의외로 약한 구석이 있어요 — 바로 "정확한 단어"를 찾는 일입니다. 이 장에서는 옛날부터 검색엔진이 써 온 BM25(키워드 검색)를 벡터 검색과 한 팀으로 묶는 Hybrid Search를 배웁니다. 그리고 한국어에서 꼭 필요한 형태소 분석(kiwipiepy)까지 함께 다룹니다.

🔍 비유 — 도서관의 두 사서 큰 도서관에 성격이 다른 사서 두 명이 있다고 해봅시다. 한 명은 색인 카드 사서입니다. "혈압"이라고 말하면 제목·본문에 정확히 그 단어가 든 책을 번개같이 찾아줍니다. 대신 "고혈압 관리법"을 물으면 "관리"라는 글자가 없는 좋은 책은 놓치죠. 다른 한 명은 주제 전문 사서입니다. 단어가 달라도 뜻이 통하면 "혈압 조절", "심혈관 건강" 책까지 척척 골라줍니다. 대신 "BM25 논문"처럼 정확한 고유명사는 가끔 엉뚱한 걸 집어옵니다. Hybrid Search는 이 두 사서를 동시에 부르는 것입니다. 색인 카드 사서(BM25)와 주제 전문 사서(벡터 검색)의 추천을 합치면, 어느 한쪽만 쓸 때보다 훨씬 든든하죠.
이 장에서 배우는 것 "검색"에는 두 갈래가 있습니다 — 단어를 그대로 맞추는 키워드 검색(BM25)과 뜻으로 맞추는 의미 검색(벡터). 이 장은 그중 BM25를 LangChain에서 다루는 법과, 한국어에서 BM25가 제대로 작동하도록 형태소 분석기를 끼우는 법, 그리고 둘을 Hybrid로 합치는 큰 그림을 배웁니다.

BM25 vs 벡터 검색 — 무엇이 다른가

BM25(Best Matching 25)는 단어의 빈도를 세어 점수를 매기는 전통적인 키워드 검색 알고리즘입니다. ElasticSearch·Lucene 같은 검색엔진의 기본 알고리즘으로 수십 년간 검증된 방식이죠. 핵심 아이디어는 딱 두 가지입니다.

  • TF(Term Frequency, 단어 빈도) — 찾는 단어가 그 문서에 자주 나올수록 관련성이 높다.
  • IDF(Inverse Document Frequency, 역문서 빈도) — 그 단어가 온 문서에 흔하면(예: "그리고") 점수를 깎고, 희귀할수록 점수를 올린다. 즉 흔한 단어보다 특이한 단어의 매칭을 더 값지게 본다.
🔍 비유 — 형광펜으로 밑줄 긋기 BM25는 문서를 읽으며 내가 찾는 단어에 형광펜을 긋는 사람과 같습니다. 밑줄이 많이 그어진 문서일수록 점수가 높죠(TF). 다만 "은/는/이/가"처럼 아무 데나 나오는 흔한 단어는 형광펜을 그어봐야 의미가 없으니 무시하고(IDF), "브로드컴", "형태소"처럼 특이한 단어가 겹칠 때 크게 반응합니다. 뜻은 전혀 이해하지 않고 오직 글자만 본다는 게 벡터 검색과의 결정적 차이예요.
방식기준장점단점
BM25키워드 빈도 기반정확한 단어 매칭에 강함, 빠름, 학습 불필요의미(문맥) 이해 불가
Vector Search의미(Semantic) 기반문맥·의미적 유사성 파악고유명사·정확한 키워드 매칭에 약할 수 있음
HybridBM25 + Vector 결합두 방식의 장점을 모두 활용구성 복잡도가 올라감
💡 왜 굳이 둘을 합칠까? 벡터 검색은 "저혈압 대처" 같은 의미 질문에 강하지만, 제품 코드 "GPT-4o-mini", 사람 이름 같은 정확한 문자열은 종종 놓칩니다. 반대로 BM25는 그런 정확한 단어는 귀신같이 잡지만 뜻은 못 봅니다. 서로의 약점을 정확히 메워주기 때문에 실무 RAG에서 Hybrid가 강력한 겁니다.

1. BM25Retriever 첫걸음 — 문자열로 만들어 보기

LangChain에는 BM25를 바로 쓸 수 있는 BM25Retriever가 있습니다. langchain_community 패키지에 들어 있어요.

📥 코드
from langchain_community.retrievers import BM25Retriever

가장 간단한 시작은 문자열 리스트를 그대로 검색 대상으로 넘기는 것입니다. from_texts()는 평범한 문자열 리스트를 BM25가 검색할 수 있는 데이터셋으로 바꿔줍니다.

🔍 비유 — 색인 카드 만들기 from_texts()는 도서관 사서가 책마다 색인 카드를 한 장씩 만들어 서랍에 정리해 두는 일과 같습니다. 이 정리(인덱싱)를 미리 해 두었기 때문에, 나중에 invoke("foo")라고 물으면 서랍을 순식간에 뒤져 "foo"가 든 카드부터 순서대로 꺼내줄 수 있는 거예요.
📥 코드
# LangChain의 BM25Retriever를 사용하여 텍스트 데이터에서 관련성 높은 문서를 검색하는 간단한 예제

# 텍스트 리스트 준비
retriever = BM25Retriever.from_texts(["foo", "bar", "world", "hello", "foo bar"])
# BM25Retriever.from_texts(): 단순 문자열 리스트를 검색 가능한 데이터셋으로 변환합니다.

# 'foo'와 가장 연관성 높은 문서 검색
result = retriever.invoke("foo")
# retriever.invoke("foo"): "foo"라는 쿼리와 가장 유사한(BM25 알고리즘 기준) 문서를 찾아 반환합니다.

print(result)
▶ 이렇게 나와요
[Document(metadata={}, page_content='foo'), Document(metadata={}, page_content='foo bar'), Document(metadata={}, page_content='hello'), Document(metadata={}, page_content='world')]

결과를 읽어봅시다. "foo"를 물었더니 "foo"와 "foo bar"가 맨 앞에 왔습니다 — 찾는 단어가 들어 있으니 당연하죠. 반면 단어가 전혀 겹치지 않는 "bar"는 결과에 아예 빠지고, "hello"·"world"는 관련성이 낮아 뒤로 밀렸습니다. 반환 타입이 그냥 문자열이 아니라 Document 객체 리스트라는 점도 눈여겨보세요 — 앞 장에서 다룬 그 표준 데이터 단위 그대로입니다.

💡 순위(랭킹)가 핵심 BM25 검색기는 단순히 "포함 여부"만 알려주는 게 아니라 점수순으로 정렬해서 돌려줍니다. 그래서 결과 리스트의 맨 앞이 가장 관련성 높은 문서입니다. RAG에서는 보통 이 상위 몇 개만 LLM에게 넘깁니다.

2. Document로 검색 — 그리고 한국어의 벽

문자열 대신 LangChain의 표준 데이터 단위인 Document 객체로도 검색기를 만들 수 있습니다. from_documents()를 쓰면 됩니다. 여기서 한국어의 함정이 하나 드러납니다.

📥 코드
from langchain_core.documents import Document

# LangChain의 표준 데이터 단위인 Document 객체를 사용하여 검색기를 만듭니다.
retriever = BM25Retriever.from_documents([
    Document(page_content="사과는"),
    Document(page_content="사과합니다."),
    Document(page_content="사과 팝니다."),
])

result = retriever.invoke("사과드립니다.")

print(result)
▶ 이렇게 나와요
[Document(metadata={}, page_content='사과 팝니다.'), Document(metadata={}, page_content='사과합니다.'), Document(metadata={}, page_content='사과는')]

우리가 물은 것은 "사과드립니다."(사과=apology의 의미)입니다. 사람이라면 뜻이 가장 가까운 "사과합니다."를 1등으로 꼽겠죠. 그런데 결과 1등은 엉뚱하게도 "사과 팝니다."(사과=fruit)가 나왔습니다. 왜 이런 일이 벌어질까요?

⚠️ BM25는 "글자 덩어리"를 통째로 본다 BM25는 기본적으로 공백 단위로 단어를 쪼갭니다. 그래서 이 문서들을 이렇게 인식해요 — "사과는", "사과합니다.", "사과 팝니다.". 마지막 문서만 "사과"라는 독립된 토큰을 가지고 있고, 나머지는 "사과는" / "사과합니다."처럼 조사·어미가 딱 붙은 다른 단어로 취급됩니다. 질문의 "사과드립니다." 역시 통째로 하나의 낯선 단어라, 정확히 "사과" 토큰을 가진 "사과 팝니다."가 어부지리로 1등이 된 겁니다.
🔍 비유 — 띄어쓰기만 아는 외국인 한국어를 띄어쓰기로만 배운 외국인을 떠올려 보세요. 그에게 "사과는", "사과합니다", "사과 팝니다"는 전부 완전히 다른 단어로 들립니다. "사과"라는 공통 뿌리가 있다는 걸 모르니까요. 한국어는 교착어 — 하나의 어근에 조사·어미가 끝없이 달라붙는 언어라서, 단순 띄어쓰기 분리로는 검색이 헛돌 수밖에 없습니다. 해결책은 단어를 뿌리와 꼬리로 제대로 쪼개주는 전문가, 바로 형태소 분석기입니다.

3. Kiwi 형태소 분석기로 한국어 쪼개기

형태소(morpheme)는 뜻을 가진 가장 작은 말의 단위입니다. "사과드립니다"를 형태소로 쪼개면 사과 + 드리 + ㅂ니다가 되죠. kiwipiepy는 이 작업을 아주 빠르게 해주는 한국어 형태소 분석기입니다. BM25에 이걸 물려주면, 검색기가 드디어 "사과"라는 뿌리를 알아보게 됩니다.

📥 코드
from kiwipiepy import Kiwi


# 1. Kiwi 형태소 분석기 준비
kiwi = Kiwi()

# 전처리 함수 정의 (명사, 동사, 형용사 등 의미 있는 품사만 추출하거나 전체를 추출)
def korean_tokenizer(text):
    # kiwi.tokenize()는 토큰 정보를 반환하므로, 거기서 단어 형태(form)만 추출
    return [token.form for token in kiwi.tokenize(text)]


print(korean_tokenizer("사과드립니다."))
▶ 이렇게 나와요
Quantization is not supported for ArchType::neon. Fall back to non-quantized model.

['사과', '드리', 'ᆸ니다', '.']

드디어 "사과드립니다."가 ['사과', '드리', 'ᆸ니다', '.']로 잘게 쪼개졌습니다. 맨 앞에 "사과"라는 독립 토큰이 생긴 게 보이죠? 이제 이 토크나이저를 검색기에 끼우면, 질문이든 문서든 똑같은 방식으로 "사과" 조각을 뽑아내 서로 매칭할 수 있게 됩니다.

💡 코드 뜯어보기 — token.form kiwi.tokenize()는 각 토큰마다 표면형(form)·품사(tag)·위치 등 풍부한 정보를 담은 객체를 돌려줍니다. 우리는 검색용 단어만 필요하므로 token.form(실제 글자 형태)만 뽑아 리스트로 만들었습니다. 주석에 적혀 있듯, 필요하면 여기서 명사·동사 같은 특정 품사만 골라 노이즈를 더 줄일 수도 있습니다.
⚠️ 저 빨간 경고 메시지는 에러가 아닙니다 Quantization is not supported for ArchType::neon...는 Kiwi가 ARM(애플 실리콘) 환경에서 최적화(양자화) 모델 대신 일반 모델로 대체해 돌아간다는 안내일 뿐입니다. 결과에는 아무 영향이 없으니 그냥 무시해도 됩니다.
📘 보충 — 'ᆸ니다'는 왜 이렇게 생겼나요?

결과의 세 번째 조각 'ᆸ니다'는 앞에 자음 ㅂ이 홀로 붙은 낯선 모양입니다. 이는 "드리 + ㅂ니다"에서 어미 "-ㅂ니다"의 첫 자음이 받침(종성)으로 결합하는 한국어 특성을 형태소 분석기가 낱개 자모(옛한글 자모 영역의 종성 ㅂ)로 분리해 표기한 결과입니다.

검색 관점에서 중요한 건 이런 어미 조각이 아니라 맨 앞의 "사과"라는 내용 단어입니다. 어미·조사는 여러 문서에 흔하게 나타나 IDF가 낮으므로(2번 문단 참고) 점수에 거의 영향을 주지 않아요.

4. 형태소 분석기를 BM25에 주입 — preprocess_func

이제 만든 korean_tokenizer를 BM25Retriever에 끼워봅시다. 방법은 간단합니다 — from_documents()의 preprocess_func 인자에 함수를 넘기면 됩니다. 그러면 검색기는 문서를 인덱싱할 때도, 질문을 받을 때도 이 함수로 먼저 단어를 쪼갠 뒤 매칭합니다.

🔍 비유 — 통역사를 붙여 주기 preprocess_func는 검색기에게 전담 통역사를 붙여 주는 것과 같습니다. 문서가 들어오든 질문이 들어오든, 통역사(형태소 분석기)가 먼저 "사과", "형태소", "분석"처럼 알맹이 단어로 번역해 준 다음에 BM25에게 넘깁니다. 양쪽을 같은 언어(같은 토큰 규칙)로 맞춰 주기 때문에 비로소 제대로 된 매칭이 됩니다.

먼저 검색 대상이 될 한국어 문서 4개를 준비합니다.

📥 코드
# 2. 문서 데이터
docs = [
    Document(page_content="RAG 시스템을 구축할 때는 검색기의 성능이 매우 중요합니다."),
    Document(page_content="한국어는 교착어이므로 형태소 분석이 필수적입니다."),
    Document(page_content="BM25는 키워드 기반의 희소 검색(Sparse Retrieval) 알고리즘입니다."),
    Document(page_content="벡터 검색은 문맥을 잘 파악하지만 고유명사 검색에 약할 수 있습니다."),
]

이제 preprocess_func에 토크나이저를 주입해 검색기를 만들고, 질문을 던져 봅니다.

📥 코드
# 3. BM25 검색기 생성 (preprocess_func에 한국어 토크나이저 주입)
retriever2 = BM25Retriever.from_documents(
    docs,
    preprocess_func=korean_tokenizer
)

result3 = retriever2.invoke("형태소 분석은 왜 해야하나요?")
print(f"검색 결과: {result3[0].page_content}")
▶ 이렇게 나와요
검색 결과: 한국어는 교착어이므로 형태소 분석이 필수적입니다.

성공입니다! 질문 "형태소 분석은 왜 해야하나요?"가 ['형태소', '분석', ...]로 쪼개지고, 문서 "한국어는 교착어이므로 형태소 분석이 필수적입니다." 역시 같은 방식으로 쪼개졌기 때문에 "형태소", "분석" 토큰이 정확히 겹쳐 1등으로 뽑혔습니다. 2번에서 형태소 분석 없이 헛돌던 것과 비교하면, 토크나이저 한 줄이 만든 차이가 극적이죠.

💡 핵심 한 줄 한국어에서 BM25를 쓸 때 가장 중요한 준비물이 바로 이 preprocess_func입니다. 이걸 빼먹으면 검색기가 조사·어미에 발이 걸려 엉뚱한 답을 내놓습니다. "한국어 BM25 = 형태소 분석 필수"로 외워두세요.

5. 진짜 Hybrid로 — 두 검색기를 한 팀으로

여기까지 우리는 Hybrid의 절반, 즉 BM25 검색기를 완성했습니다. 나머지 절반인 벡터 검색기는 이미 06·07장에서 만들어 봤죠(Chroma의 as_retriever()). Hybrid Search는 이 둘을 나란히 세워 결과를 합치는 것입니다.

1키워드 팀

BM25Retriever — 정확한 단어 매칭 담당

2의미 팀

벡터 Retriever — 문맥·뜻 매칭 담당

3결과 합치기

두 결과를 가중치로 섞어 최종 순위 산출

🔍 비유 — 두 심사위원의 합산 점수 오디션에 심사위원이 두 명 있습니다. 한 명은 가사 정확도(BM25)를, 다른 한 명은 감정 전달(벡터)을 봅니다. 최종 순위는 두 점수를 가중치로 합산해 정하죠. 어느 한 심사위원만 믿으면 편향되지만, 둘의 점수를 합치면 더 공정하고 튼튼한 순위가 나옵니다. Hybrid Search가 바로 이 합산 채점입니다.
📘 보충 — 결합은 보통 EnsembleRetriever로 (다음 단계 개념)

LangChain에서는 여러 검색기를 묶어주는 EnsembleRetriever가 있습니다. 아래는 이 노트북에는 없지만, 위에서 만든 BM25 검색기를 벡터 검색기와 합쳐 진짜 Hybrid로 확장할 때 쓰는 대표 패턴입니다(개념 예시).

📥 코드 (개념 예시 — 노트북 외 확장)
from langchain.retrievers import EnsembleRetriever

# bm25_retriever : preprocess_func로 만든 BM25 검색기 (위 4번)
# vector_retriever: Chroma 등에서 만든 벡터 검색기 (06·07장)
hybrid_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.5, 0.5],   # 두 검색기 결과를 어떤 비중으로 섞을지
)

result = hybrid_retriever.invoke("형태소 분석은 왜 해야하나요?")

weights로 키워드 vs 의미의 비중을 조절합니다. 고유명사·코드가 많은 데이터라면 BM25 비중을, 자연어 질의가 많다면 벡터 비중을 높이는 식으로 도메인에 맞춰 튜닝합니다.

⚠️ 위 5번 코드는 이 노트북에 없는 "다음 단계" 예시입니다 08.ipynb가 실제로 실행하는 것은 BM25 검색기(1~4번)까지입니다. EnsembleRetriever 부분은 배운 조각을 어떻게 이어붙이는지 큰 그림을 보여주려 덧붙인 개념 코드예요. 실행하려면 bm25_retriever·vector_retriever를 실제로 준비해야 합니다.

📚 한 장 정리

오늘의 핵심 검색은 "단어를 맞추는 것(BM25)"과 "뜻을 맞추는 것(벡터)" 두 갈래가 있고, Hybrid Search는 이 둘을 한 팀으로 묶어 서로의 약점을 메운다. 그리고 한국어에서는 형태소 분석기가 있어야 BM25가 비로소 제대로 작동한다.
  • BM25 — 단어 빈도(TF)와 희귀도(IDF)로 점수를 매기는 전통 키워드 검색. 뜻은 모르고 글자만 본다.
  • BM25Retriever — from_texts()·from_documents()로 만들고 invoke()로 점수순 정렬 결과를 받는다.
  • 한국어의 벽 — 기본 BM25는 공백으로만 쪼개서 "사과합니다/사과 팝니다"를 헷갈린다(교착어 문제).
  • Kiwi 형태소 분석 — kiwi.tokenize() + token.form으로 "사과"라는 뿌리를 뽑아낸다.
  • preprocess_func 주입 — 문서와 질문을 같은 토큰 규칙으로 맞춰, 한국어 검색을 극적으로 개선한다.
  • Hybrid 완성 — EnsembleRetriever로 BM25 + 벡터를 가중치로 결합하면 키워드와 의미를 모두 잡는다.
