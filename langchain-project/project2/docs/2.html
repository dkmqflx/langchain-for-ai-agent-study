Agent 코어 ② — P1의 RAG를 Tool로 장착

🟢 랭체인 집중 ⏱ 1~2시간
🎯 목표

P1의 POST /query를 부르는 도구를 만들어 Agent에 꽂고, 약관 질문에는 이 도구를, 일반 질문에는 다른 도구를 고르게 만든다.

⚠️ P1 서버가 켜져 있어야 합니다

터미널 A에서 cd ~/Documents/langchain-study/langchain-project/project1 && uv run uvicorn main:app --reload. P1이 없다면 이 STEP을 건너뛰고 STEP 3으로 가도 됩니다.

🧠 개념

"항상 검색"에서 "필요할 때만 검색"으로

P1의 RAG는 질문이 뭐든 무조건 벡터DB를 뒤졌습니다. 코드가 그렇게 생겼으니까요. "안녕하세요"라고 인사해도 약관을 검색했고, "1+1은?"이라고 물어도 약관을 검색했습니다. 검색은 공짜가 아닙니다 — 임베딩 API 호출, 리랭커 모델 실행, 그리고 쓸데없는 청크가 프롬프트에 실려 답변까지 흐려집니다.

같은 RAG를 도구로 바꾸면 이 판단이 LLM에게 넘어갑니다. "이 질문은 우리 문서에 답이 있을 법한가?"를 매번 따져 보고, 아니면 안 부릅니다. P1 코드는 한 줄도 안 고쳤는데 동작이 달라진 겁니다 — 바뀐 건 그걸 호출하는 쪽의 구조뿐이에요.

P1 — RAG 체인P2 — RAG 도구
검색 시점항상LLM이 필요하다고 판단할 때만
"안녕하세요"약관 검색 후 "문서에서 찾을 수 없습니다"검색 없이 바로 인사 응답
검색 횟수질문당 정확히 1번0번일 수도, 여러 번일 수도
다른 정보와 조합불가 — 약관 밖은 못 봄약관 + 웹검색 + 계산을 한 답변에 섞을 수 있음
판단 주체개발자(코드)LLM(docstring을 읽고)

그래서 이 STEP의 진짜 난이도는 docstring에 있다

도구를 만드는 코드는 15줄이면 끝납니다. 어려운 건 "언제 이 도구를 쓸지"를 LLM에게 이해시키는 문장이에요. 도구가 네 개가 되는 순간 web_search와 search_internal_docs가 서로 헷갈리기 시작하거든요. 둘 다 "찾아본다"는 도구니까요.

docstring결과
"""문서를 검색한다.""" ❌ 어떤 문서인지 없음 → 웹 검색과 구분이 안 돼 아무 질문에나 부른다
"""사내 문서를 검색한다.""" △ 나아졌지만 "사내 문서에 뭐가 들었는지"를 모르니 여전히 헛다리를 짚는다
무엇이 들었는지 + 어떤 질문에 쓰는지 + 언제 쓰면 안 되는지 ✅ 약관 질문에만 정확히 걸린다
🗂 비유 — 신입에게 넘기는 인수인계서

"저 캐비닛 참고하세요"라고만 하면 신입은 아무 때나 캐비닛을 열어 봅니다. "저 캐비닛엔 우리 회사 금융 약관 4종이 들어 있어요. 조항이나 수수료 규정을 물어보면 거기서 찾고, 바깥 뉴스는 거기 없으니 인터넷을 보세요." 이렇게 말해 줘야 제대로 씁니다. docstring은 딱 이 인수인계서예요. 그리고 "거기 없는 것"까지 알려 주는 게 절반입니다.

🛠 할 일

① tools.py에 네 번째 도구 추가

파일 맨 위 import와 맨 아래 도구, 두 군데를 고칩니다.

tools.py — 맨 위에 추가
import os
import requests                     # P1의 HTTP 창구를 두드리는 도구
from dotenv import load_dotenv

load_dotenv()                       # ← STEP 1엔 없던 줄. 왜 여기 필요한지는 아래 경고 참고

# P1 서버 주소. 코드에 박지 않고 .env에서 읽는다 →
# 나중에 P1을 다른 서버에 올려도 이 코드는 그대로 두고 설정만 바꾸면 된다.
P1_API_URL = os.getenv("P1_API_URL", "http://localhost:8000")
🚨 load_dotenv()를 tools.py에도 넣어야 하는 이유 — 임포트 순서의 함정

agent.py에 이미 load_dotenv()가 있는데 왜 또 쓸까요? 실행 순서 때문입니다. 파이썬은 from tools import ... 줄을 만나는 순간 tools.py를 통째로 먼저 실행합니다. 그때 agent.py의 load_dotenv()는 아직 실행 전이에요. 

agent.py 실행 시작
  ├─ from tools import ...   → tools.py 전체 실행
  │    └─ P1_API_URL = os.getenv("P1_API_URL")   ← .env가 아직 안 읽혔다! → None → 기본값
  └─ load_dotenv()                                ← 이제야 읽는다. 하지만 이미 늦었다

지금은 기본값이 우연히 맞아서 티가 안 나지만, P1 주소를 바꾸는 순간 "분명 .env를 고쳤는데 안 먹네"로 30분을 씁니다. load_dotenv()는 여러 번 불러도 안전하니, 환경변수를 읽는 파일마다 각자 부르는 게 안전합니다.

tools.py — 맨 아래에 추가
# ── 도구 4 · 사내 문서 검색 (P1 RAG 서비스 호출) ──────────────────
# P1의 코드를 import 하지 않고 HTTP로 부른다. P2는 Chroma도 리랭커 모델도 몰라도 되고,
# P1이 죽어도 P2는 살아 있다. 두 서비스를 나눠 얻는 이득이 이 함수 하나에 압축돼 있다.
@tool
def search_internal_docs(question: str) -> str:
    """사내 문서에서 근거와 함께 답을 찾는다.

    보유 문서: 예금거래기본약관, 전자금융거래기본약관, 신용카드 개인회원 표준약관,
    은행여신거래기본약관(가계용), 금융소비자의 소리 자료.

    약관·조항·수수료·책임 범위·해지 절차처럼 "우리 문서에 뭐라고 적혀 있는가"를
    묻는 질문에 사용한다. 일반 상식이나 최신 뉴스에는 사용하지 않는다(그건 web_search).

    Args:
        question: 사용자의 질문을 한 문장으로 전달한다. 대명사("그거", "거기")는
            앞 대화를 참고해 구체적인 말로 바꿔서 넘긴다.
    """
    try:
        r = requests.post(
            f"{P1_API_URL}/query",
            json={"question": question, "mode": "rerank"},   # P1이 만든 최고 성능 구성
            timeout=60,          # 리랭커는 느리다. 첫 호출은 모델 다운로드까지 겹쳐 더 걸린다
        )
        r.raise_for_status()     # 4xx·5xx면 여기서 예외 → 아래 except로 간다
    except requests.exceptions.RequestException as e:
        # P1이 꺼져 있어도 Agent는 죽지 않는다. '실패했다'는 사실을 LLM에게 보고할 뿐이다.
        # 뒷문장이 중요하다 — LLM에게 '그럼 어떻게 하라'까지 알려 줘야 엉뚱하게 지어내지 않는다.
        return (f"사내 문서 검색 서비스에 연결할 수 없습니다({e}). "
                "이 질문은 사내 문서로 확인할 수 없다고 사용자에게 알려라.")

    data = r.json()

    # 근거 정리: 같은 페이지에서 여러 청크가 걸리는 일이 흔해 중복을 걷어낸다.
    # (dict.fromkeys는 순서를 지키면서 중복만 없애는 관용구다)
    cites = list(dict.fromkeys(
        f"{c.get('source')} p.{c.get('page')}" for c in data.get("citations", [])
    ))

    # 답변과 근거를 한 문자열로 합쳐 돌려준다.
    # 근거를 같이 넘겨야 Agent가 최종 답변에 "「신용카드 표준약관」 40쪽에 따르면..." 처럼 인용할 수 있다.
    return f"{data['answer']}\n\n[근거] " + " / ".join(cites)

② agent.py — 도구 등록 + 규칙 한 줄

도구를 목록에 넣고, 시스템 프롬프트에 "어느 도구를 먼저 보라"는 우선순위를 적습니다. 도구가 넷이 되면 설명만으로는 경합이 생기기 시작해서, 프롬프트에서 한 번 더 정리해 주는 게 효과가 큽니다.

agent.py — 고치는 두 군데
from tools import get_today, calculate, web_search, search_internal_docs   # ← 추가

SYSTEM_PROMPT = """너는 정확성을 최우선으로 하는 업무 비서다.

규칙:
1. 오늘 날짜·현재 시각이 필요하면 반드시 get_today를 호출한다. 날짜를 추측하지 않는다.
2. 숫자 계산은 반드시 calculate를 호출한다. 암산하지 않는다.
3. 약관·규정·계약 조건에 관한 질문은 web_search보다 search_internal_docs를 먼저 쓴다.
   우리 문서에 있는 내용을 인터넷에서 찾으면 틀린 답이 나온다.
4. search_internal_docs의 결과를 쓸 때는 답변에 [근거]의 문서명과 쪽수를 반드시 적는다.
5. 최신 정보가 필요하면 web_search를 호출하고, 답변에 출처 URL을 함께 적는다.
6. 도구로도 확인할 수 없는 내용은 모른다고 말한다. 지어내지 않는다."""

agent = create_agent(
    model="openai:gpt-5-mini",
    tools=[get_today, calculate, web_search, search_internal_docs],   # ← 추가
    system_prompt=SYSTEM_PROMPT,
)
💡 규칙 3번이 하는 일 — "일반적으로 신용카드 분실 시에는…"을 막는다

이 줄이 없으면 Agent는 약관 질문에도 web_search를 부르곤 합니다. 그리고 인터넷에서 찾은 다른 회사의 약관으로 그럴듯하게 답합니다. 문장은 매끄럽지만 우리 약관과 다른 내용이죠. 이런 오류는 "틀렸다"가 눈에 잘 안 띄어서 가장 위험합니다. STEP 8의 평가 케이스에 expect_tool(어떤 도구를 썼어야 하는가) 항목을 넣는 이유가 정확히 이것입니다.

✅ 검증 게이트

네 가지 모두 확인합니다. 특히 4번은 P1 서버를 일부러 끄고 해 보세요.

# 1) 약관 질문 → search_internal_docs 를 부르고, 답변에 문서명·쪽수가 있는가
uv run python agent.py "신용카드를 분실하면 회원 책임은 어디까지야?"

# 2) 일반 상식 → 사내 문서를 부르지 '않는가'
uv run python agent.py "파이썬에서 리스트와 튜플의 차이가 뭐야?"

# 3) 도구 두 개를 섞는가
uv run python agent.py "카드 연회비 관련 조항 찾아보고, 연회비가 15000원이면 5년치는 얼마야?"
#    → search_internal_docs · calculate 가 둘 다 호출돼야 한다

# 4) P1이 꺼져 있어도 Agent가 죽지 않는가  ← 터미널 A에서 Ctrl+C 로 P1을 끄고 실행
uv run python agent.py "신용카드 분실 시 책임은?"
#    → 500 에러가 아니라 "사내 문서를 확인할 수 없다"는 답변이 나와야 한다

4번을 통과했다면 서비스를 분리한 값을 제대로 받은 것입니다. P1이 죽어도 P2는 나머지 도구로 계속 일하니까요. 확인했으면 P1을 다시 켜 두세요.

⚠️ 첫 호출이 유독 느리다면

P1의 rerank 모드는 Cross-Encoder 모델을 씁니다. 그 서버에서 처음 한 번은 모델을 내려받느라 수십 초가 걸릴 수 있어요. timeout=60을 넉넉히 잡아 둔 이유입니다. 그래도 넘친다면 P1을 curl로 한 번 미리 깨워 두거나, 도구에서 "mode": "hybrid"로 바꿔 리랭커를 건너뛰세요.

🎓 배우는 것

서비스를 도구로 감싸 조립하는 방법. 같은 RAG라도 "체인으로 부르느냐, 도구로 부르느냐"에 따라 동작이 달라진다는 것. 그리고 서비스 경계에서 반드시 해야 하는 일 — 타임아웃 정하기, 실패를 예외 대신 메시지로 바꾸기, 실패했을 때 LLM이 취할 행동까지 알려 주기. 여기에 임포트 순서와 load_dotenv()라는, 한 번 겪으면 잊지 못할 함정도 하나 더.
