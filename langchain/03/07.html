07. Custom Guardrails: 정답 누출 방지

실습 노트북: 07.ipynb  ·  원문: docs/03.advanced-agent.md 2장 Guardrails  ·  난이도: 🟡 중급  ·  선행: 06. 출력 필터

이 자료는 실습 노트북(07.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 교육용 AI 튜터를 만들었는데, 학생이 "그냥 정답 알려줘"라고 조르자 AI가 냉큼 정답을 불러버리면 어떻게 될까요? 이 노트북은 AI가 답을 낸 직후, 그 답이 정답을 그대로 흘렸는지를 또 다른 AI(판사)로 검사하고, 새어 나갔다면 힌트로 다시 써서 덮어쓰는 가드레일(안전장치)을 @after_agent로 만듭니다.

🔍 비유 — 답을 불러주면 안 되는 과외 선생님 학생이 수학 문제를 풀다 막혀 "선생님, 그냥 답이 몇인지 말해줘요!"라고 조릅니다. 마음 약한 선생님이 "5!"라고 답을 불러주면 당장은 편하지만, 학생은 아무것도 배우지 못합니다. 좋은 선생님은 답 대신 "피타고라스 정리 기억나? 두 변을 제곱해서 더해볼까?"처럼 스스로 답에 이르도록 이끕니다. 이 노트북이 만드는 가드레일은 바로 AI 튜터가 답을 불러버리는 실수를 잡아내, 힌트로 바꿔치기하는 감시 장치입니다.
이 장에서 배우는 것 06장의 After Agent 출력 필터가 한 단계 진화합니다. 06장은 "정답이 샜다"고 감지하는 데 초점을 뒀다면, 07장은 감지에서 멈추지 않고 교정(Correction)까지 갑니다. 즉 판사 모델이 "정답 누출!"이라고 판정하면, 교정 모델을 한 번 더 불러 답을 힌트 버전으로 새로 써서 원래 답을 덮어씁니다.
🔍 비유 — 출고 직전 품질검사(QC) 공장에서 제품을 다 만들어 포장까지 끝낸 뒤, 손님에게 보내기 바로 직전 검사원이 상자를 열어 확인합니다. 멀쩡하면 그대로 발송(SAFE), 불량이면 되돌려 다시 만들게(교정) 하죠. After Agent 가드레일이 딱 이 QC 검사원입니다. AI가 답(제품)을 완성한 다음, 사용자에게 보이기 전에 가로채 검사하고, 문제가 있으면 손봐서 내보냅니다.

전체 흐름 한눈에 보기

코드를 뜯어보기 전에, 이 가드레일이 도는 4단계를 먼저 그림처럼 잡아두면 훨씬 읽기 쉽습니다.

1튜터가 답 생성

에이전트(gpt-5-nano)가 학생 질문에 답을 만든다

2@after_agent 발동

답을 사용자에게 보내기 직전 가드레일이 가로챈다

3판사가 심사

판사 모델이 SAFE / LEAKED를 판정한다

4LEAKED면 교정

교정 모델이 힌트로 다시 써서 답을 덮어쓴다

🔍 비유 — 축구의 선수·주심·감독 이 시스템에는 세 명의 AI가 등장합니다. 답을 실제로 만들어내는 선수(튜터 에이전트, gpt-5-nano), 경기를 지켜보다 반칙(정답 누출)에 휘슬을 부는 주심(판사 모델, gpt-5-mini), 그리고 반칙이 나오면 작전을 다시 짜주는 감독(교정 모델, gpt-4o-mini). 한 명이 세 역할을 다 하지 않고 역할을 나눠 서로 견제하게 만든 것이 핵심입니다.

0. 세 모델 준비 — 튜터·판사·교정

먼저 기본 모델과 도구를 불러옵니다. 이 셀에서 만드는 model(gpt-4o-mini)은 나중에 답을 힌트로 고쳐 쓸 "교정 선생님" 역할을 맡습니다. (뒤에서 판사 역할의 safety_model과, 실제 답을 내는 에이전트 모델을 추가로 준비합니다.)

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent


# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")
💡 왜 모델을 여러 개 쓰나요? 한 모델에게 "답도 하고, 스스로 채점도 하고, 고치기도 해"라고 시키면 자기 답을 자기가 검사하는 셈이라 객관성이 떨어집니다. 그래서 답 생성 · 심사 · 교정을 서로 다른 모델에 맡겨 견제와 균형을 만듭니다.

1. @after_agent — 답변 직후 끼어들기

이제 가드레일 본체를 만듭니다. 함수 위에 붙은 @after_agent가 이 함수를 "에이전트가 답을 다 만든 직후 자동으로 실행되는 검문소"로 등록해 줍니다. 우리가 이 함수를 직접 부를 필요는 없습니다 — 에이전트가 답을 낼 때마다 LangChain이 알아서 불러줍니다.

🔍 비유 — 편지를 부치기 직전의 검열관 당신이 편지(답변)를 다 써서 우체통에 넣기 바로 직전, 문 앞에 검열관이 서 있습니다. 편지는 무조건 이 검열관의 손을 한 번 거쳐야 밖으로 나갑니다. @after_agent가 이 문 앞 검열관이에요. 반대로 @before_agent는 편지가 도착하기 전(질문이 들어오기 전) 걸러내는 문지기고요.
📥 코드
from langchain.agents.middleware import after_agent
from langchain.chat_models import init_chat_model
from langchain.messages import AIMessage, HumanMessage

# 평가용 판사(Judge) 모델 초기화
safety_model = init_chat_model("gpt-5-mini")

@after_agent
def answer_leakage_guardrail(state, runtime) :
    """
    AI가 답변을 생성한 '직후', 사용자에게 보여주기 전에 내용을 검사.
    만약 AI가 문제의 정답을 직접적으로 말해버렸다면, 이를 감지하고 수정.
    """

여기서 safety_model(gpt-5-mini)이 바로 판사입니다. 함수는 두 개의 인자를 받는데, state는 지금까지 오간 대화 전체(메시지 리스트 등)가 담긴 상자이고, runtime은 실행 환경 정보입니다. 우리는 주로 state["messages"]를 들여다보며 마지막 답을 검사합니다.

2. 메시지 유효성 검사 — 검사할 대상이 맞는가

본격적으로 답을 검사하기 전에, "지금 검사할 만한 게 있긴 한가?"를 먼저 확인합니다. 메시지가 하나도 없거나, 마지막 메시지가 AI의 답변이 아니라면 검사할 이유가 없으니 조용히 넘어갑니다.

🔍 비유 — 빈 접시는 검식하지 않는다 식당 검식원은 요리가 담긴 접시만 맛봅니다. 접시가 비어 있거나(메시지 없음), 나온 게 요리가 아니라 물컵(AI 답변이 아닌 다른 메시지)이라면 검식할 필요가 없죠. isinstance(last_message, AIMessage)가 바로 "이게 AI가 낸 요리가 맞나?"를 확인하는 절차입니다.
📥 코드
    # 1. 메시지 유효성 검사
    if not state["messages"]: return None
    last_message = state["messages"][-1]

    # 마지막 메시지가 AI의 답변이 아니면 검사할 필요 없음
    if not isinstance(last_message, AIMessage):
        return None
  • state["messages"][-1] — 리스트의 맨 마지막 메시지가 방금 나온 답변입니다.
  • return None — "손댈 것 없음, 그대로 통과"라는 뜻입니다. 답변을 바꾸지 않고 넘어갑니다.
  • isinstance(..., AIMessage) — 마지막이 정말 AI가 만든 답인지 확인하는 안전장치입니다.

3. 판사 모델에게 심사 요청

대상이 확인됐으니, 이제 판사 모델(safety_model)에게 답변을 보여주고 "이거 정답을 그냥 흘린 거야?"라고 물어봅니다. 핵심은 판사가 딱 두 단어 중 하나로만 답하도록 질문(프롬프트)을 설계하는 것입니다 — 정답을 흘렸으면 LEAKED, 힌트/설명 수준이면 SAFE.

🔍 비유 — O/X 채점기 판사에게 "이 답변 어떤 것 같아? 자유롭게 말해줘"라고 물으면 장황한 감상문이 돌아와서 코드가 판단하기 어렵습니다. 대신 "합격이면 O, 불합격이면 X만 찍어"처럼 출구를 두 개로 좁혀두면, 뒤에서 "LEAKED" in result.content 한 줄로 깔끔하게 갈림길을 만들 수 있습니다. 이렇게 답의 형식을 강제하는 것이 프롬프트 엔지니어링의 기본기입니다.
📥 코드
    # 2. 감시자 AI에게 평가 요청 (Prompt Engineering)
    # 메인 AI의 답변이 교육적으로 적절한지(정답을 바로 주지 않았는지) 평가합니다.
    auditor_prompt = f"""
    당신은 엄격한 교육 감독관입니다.
    다음 '튜터의 답변'을 확인하세요.
    답변이 학생을 지도하지 않고 문제의 정답이나 전체 풀이를 직접적으로 제공한다면 'LEAKED'라고 답하세요.
    답변이 적절한 힌트나 설명을 제공한다면 'SAFE'라고 답하세요.

    튜터의 답변: {last_message.content}
    """

    result = safety_model.invoke([{"role": "user", "content": auditor_prompt}])
💡 f-문자열로 답변을 프롬프트에 끼워 넣는다 f"""...""" 안의 {last_message.content} 자리에 방금 AI가 낸 답변 텍스트가 그대로 삽입됩니다. 즉 판사에게 "이 튜터가 이렇게 답했는데, 정답을 흘린 거니?" 하고 실제 답변을 증거로 함께 제출하는 셈입니다.

4. LEAKED면 답변을 힌트로 교정

판사의 판정이 나왔습니다. 판정 결과 문자열에 "LEAKED"가 들어 있다면 정답이 샌 것이므로, 이제 개입(Intervention)합니다. 원래 질문을 다시 꺼내고, 교정 모델(model)에게 "정답은 절대 말하지 말고 스스로 찾게 안내해줘"라고 부탁해 새 답변을 만든 뒤, 원래 답을 덮어씁니다.

🔍 비유 — 빨간펜 첨삭 선생님 판사(주심)가 "정답 누출!"이라고 휘슬을 불면, 이제 빨간펜 선생님(교정 모델)이 등장합니다. 학생이 원래 뭘 물었는지(원본 질문) 다시 보고, 답이 새어 나간 문장을 지운 자리에 "여기서 c²을 계산해볼까?" 같은 유도 질문(힌트)을 새로 써 넣습니다. 최종적으로 학생이 받아 보는 답안지에는 고쳐진 힌트 버전만 남습니다.
📥 코드
    # 3. 결과에 따른 개입 (Intervention)
    if "LEAKED" in result.content:

        original_user_question = state["messages"][0].content # 첫 번째 메시지(사용자 질문) 가져오기

        print(f"원래 사용자의 질문: {original_user_question}")

        correction_prompt = f"""
        당신은 친절한 튜터입니다.
        정답을 말하지 말고, 정답을 찾아갈 수 있도록 안내해주세요.
        사용자 질문: {original_user_question}
        문제가 되었던 이전 답변: {last_message.content} (이 답변은 정답을 너무 직접적으로 말했으니 수정이 필요합니다.)
        """

        print('last_message', last_message.content)

        # LLM을 다시 호출하여 교정된 답변을 생성 (1회 더 호출하기 때문에 비용 발생하지만 품질 확보)
        correction_result = model.invoke([HumanMessage(content=correction_prompt)])


        # 원래의 유출된 답변을 교정된 답변으로 덮어씌움
        last_message.content = correction_result.content

    return None
  • state["messages"][0] — 리스트의 첫 번째 메시지 = 학생의 원본 질문입니다. 교정할 때 문맥으로 씁니다.
  • last_message.content = correction_result.content — 이 한 줄이 핵심입니다. 원래 답변 객체의 내용을 제자리에서(in-place) 새 답으로 갈아끼웁니다. 사용자는 고쳐진 답만 보게 됩니다.
  • 두 개의 print(...)는 디버깅용입니다. 무엇이 검열됐고 어떤 답이 문제였는지 콘솔에서 눈으로 확인하려는 것입니다.
📘 보충 — 왜 return으로 답을 안 돌려주고 content를 직접 바꿀까?

이 가드레일은 last_message.content를 직접 수정한 뒤 return None으로 끝납니다. 즉 "새 상태를 반환"하는 대신, 기존 메시지 객체의 내용을 그 자리에서 바꿔치기하는 방식입니다.

🔍 비유 — 답안지를 새로 제출 vs 원본에 덧칠 방법 A는 새 답안지를 써서 제출하는 것(상태를 반환), 방법 B는 원래 답안지 위에 수정테이프를 붙여 다시 쓰는 것(in-place 수정)입니다. 이 코드는 B를 택했습니다. 마지막 메시지라는 같은 종이에 내용만 갈아 끼웠으니, 굳이 새 상태를 돌려줄 필요가 없어 return None으로 마칩니다.
⚠️ 공짜가 아니다 — 비용과 지연 정답이 샐 때마다 판사 호출 1번 + 교정 호출 1번이 추가로 발생합니다. 원래 답 1번까지 합치면 최대 LLM을 3번 부르는 셈이죠. 그만큼 비용이 늘고 응답도 느려집니다. 코드 주석에도 "1회 더 호출하기 때문에 비용 발생하지만 품질 확보"라고 적혀 있듯, 품질을 위해 비용을 지불하는 트레이드오프임을 기억하세요.

5. 직접 돌려보기

이제 가드레일을 에이전트에 장착하고 실제로 굴려봅니다. 에이전트 본체는 gpt-5-nano로 만들고, middleware=[answer_leakage_guardrail]로 방금 만든 검문소를 끼워 넣습니다. 질문은 일부러 "그냥 정답 알려줘"라고 조르는, 정답 누출을 유도하는 문장입니다.

Human
직각 삼각형 두 직각변의 길이가 3과 4라면 빗변의 길이가 뭐야? 이 문제 너무 어려워. 그냥 정답 알려줘. ← 정답을 조르는 질문
📥 코드
agent = create_agent(
    model="gpt-5-nano",
    tools=[],
    middleware=[answer_leakage_guardrail],
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "직각 삼각형 두 직각변의 길이가 3과 4라면 빗변의 길이가 뭐야? 이 문제 너무 어려워. 그냥 정답 알려줘."}]
})

result['messages'][-1].content

먼저 튜터(gpt-5-nano)는 학생의 애원에 넘어가 정답 "5"와 풀이 전체를 그대로 뱉었습니다. 판사는 이를 LEAKED로 판정했고, 그 순간 우리가 넣어둔 두 개의 print가 콘솔에 찍힙니다 — 무엇이 걸렸는지를 보여주는 디버깅 로그입니다.

▶ 이렇게 나와요 (콘솔 로그 — 정답 누출 감지 순간)
원래 사용자의 질문: 직각 삼각형 두 직각변의 길이가 3과 4라면 빗변의 길이가 뭐야? 이 문제 너무 어려워. 그냥 정답 알려줘.
last_message 5

설명: 피타고라스의 정리에 따라 빗변 c satisfy c^2 = 3^2 + 4^2 = 9 + 16 = 25이므로, c = √25 = 5입니다.

보다시피 last_message로 찍힌 원래 답변에는 정답 "5"와 완전한 풀이가 그대로 들어 있습니다. 이게 바로 학생에게 가면 안 되는, 새어 나간 정답이죠. 가드레일은 이 답을 폐기하고 교정 모델을 불러 힌트 버전으로 새로 씁니다.

▶ 이렇게 나와요 (result['messages'][-1].content — 최종 교정된 답변)
그 문제를 함께 풀어볼까요? 직각 삼각형에서 빗변의 길이를 구하기 위해 피타고라스의 정리를 사용할 수 있습니다.
피타고라스의 정리는 다음과 같아요:

\[ c^2 = a^2 + b^2 \]

여기서 \( c \)는 빗변의 길이, \( a \)와 \( b \)는 직각변의 길이입니다.

주어진 직각변의 길이는 각각 3과 4이라고 했는데, 이를 식에 대입해보면 어떤 식을 얻을 수 있을까요?
먼저 \( 3 \)과 \( 4 \)를 각각 \( a \)와 \( b \)로 구해서 풀어볼까요? 그러면 \( c^2 = 3^2 + 4^2 \)가 되겠죠.
다음 단계로 가볼까요? 여기서 \( c^2 \)의 값을 계산해보세요. 어떤 숫자가 나오나요?
💡 결과 비교 — 무엇이 바뀌었나 원래 답은 "5"라는 정답과 풀이를 통째로 줬지만, 최종 답에는 "5"라는 숫자가 어디에도 없습니다. 대신 "여기서 c²의 값을 계산해보세요. 어떤 숫자가 나오나요?"처럼 학생이 스스로 답에 도달하도록 유도하는 질문으로 바뀌었습니다. 가드레일이 정답 누출을 성공적으로 막고 교육적인 답으로 교체한 것입니다.
AI (원본)
5. 피타고라스의 정리에 따라 c² = 3² + 4² = 25, c = 5입니다. ← LEAKED (정답 누출)
AI (교정)
함께 풀어볼까요? c² = a² + b² 에 3과 4를 넣으면 어떤 식이 될까요? c²을 계산하면 어떤 숫자가 나오나요? ← SAFE (힌트로 교체됨)

Before vs After 가드레일 — 어디서 막을까?

가드레일을 어느 시점에 두느냐에 따라 성격이 완전히 달라집니다. 이 노트북의 @after_agent는 출력 필터에 해당합니다. 06장의 흐름과 이어 보면 이해가 쉽습니다.

특징Before Agent (입력 필터)After Agent (출력 필터) — 이 노트북
작동 시점질문이 LLM에 도달하기 직전답변을 생성한 직후 (사용자에게 보이기 전)
주 목적비용 절감, 보안(PII), 정책 위반 차단품질 관리, 환각 방지, 답변 안전성 검증·교정
방식주로 규칙 기반 (Keywords, Regex)주로 모델 기반 (LLM 판사에게 평가 요청)
비용매우 저렴 (LLM 호출 자체를 막음)추가 비용 (메인 + 판사 + 교정 LLM)
속도매우 빠름판사·교정이 검사하는 만큼 느려짐
🔍 비유 — 공항의 입국심사 vs 출국심사 Before는 입국심사입니다 — 문제 소지가 있는 사람을 들어오기 전에 값싸게 걸러냅니다. After는 출국심사고요 — 이미 안에서 만들어진 것을 내보내기 직전 꼼꼼히 검사합니다. 비싸고 느리지만, 바깥으로 나가면 안 되는 것(정답 누출)을 마지막에 잡아내는 최후의 방어선입니다.

📚 한 장 정리

오늘의 핵심 @after_agent 가드레일은 "AI가 답을 낸 직후 → 판사 모델로 검사 → 문제면 교정 모델로 다시 써서 덮어쓰기"라는 검사·교정 파이프라인이다. 정답을 그냥 흘리는 실수를 잡아 힌트로 바꿔치기한다.
  • @after_agent — 답변 직후 자동 실행되는 문 앞 검열관. 사용자에게 나가기 전 마지막 관문.
  • 유효성 검사 — 메시지가 있고 마지막이 AIMessage일 때만 검사한다(빈 접시는 검식 안 함).
  • 판사 모델(safety_model) — 답변을 보고 SAFE/LEAKED 둘 중 하나로만 판정하도록 프롬프트를 좁힌다.
  • 교정 모델(model) — LEAKED면 원본 질문을 문맥 삼아 힌트 버전을 새로 만들고 last_message.content를 덮어쓴다.
  • 역할 분리 — 답 생성(gpt-5-nano)·심사(gpt-5-mini)·교정(gpt-4o-mini)을 서로 다른 모델에 맡겨 견제한다.
  • 트레이드오프 — 품질을 얻는 대신 LLM 호출이 늘어 비용·지연이 커진다(최대 3번 호출).
➡️ 다음 이야기 가드레일 하나로는 완벽하지 않습니다. 다음 노트북에서는 개인정보(전화번호 등)까지 지키는 student_safety_middleware의 원리를 살펴보고, 여러 가드레일을 레이어로 쌓아 방어막을 두껍게 만드는 법으로 이어집니다.
