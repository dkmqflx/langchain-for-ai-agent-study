04. Custom Middleware — 멤버십 기반 모델 선택

실습 노트북: 04.ipynb  ·  원문: docs/03.advanced-agent.md 1.5 Wrap-style  ·  난이도: 🟡 중급  ·  선행: 03. 동적 모델 선택

이 자료는 실습 노트북(04.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 이번 노트북의 목표는 딱 하나 — 로그인한 사용자의 멤버십 등급(is_premium)에 따라 서로 다른 모델을 제공하는 Agent를 만드는 것입니다. 프리미엄 회원에게는 강력한 gpt-5를, 일반 회원에게는 가볍고 저렴한 gpt-5-nano를 자동으로 골라주는 Wrap-style 미들웨어를 비유와 함께 천천히 풀어봅니다.

🔍 비유 — 항공사 좌석 등급 같은 비행기(같은 서비스)를 타더라도 이코노미 승객과 퍼스트클래스 승객은 대접이 다릅니다. 항공사는 손님이 탑승하기 직전에 항공권(멤버십 등급)을 확인하고 그에 맞는 좌석으로 안내하죠. 이 노트북에서 만들 Agent도 똑같습니다. 사용자가 말을 거는 순간 그 사람의 회원 카드(is_premium)를 확인하고, VIP라면 강력한 모델을, 일반 회원이라면 가벼운 모델을 배정합니다.
이 노트북에서 배우는 것 "사용자마다 다른 모델을 쓴다"를 코드로 옮기려면 두 가지가 필요합니다. ① 그 사용자가 누구이고 어떤 등급인지 알려주는 Context(회원 카드), ② 모델 호출 직전에 그 카드를 확인해 모델을 바꿔치기하는 미들웨어(도어맨). 이 둘을 조립하는 법을 배웁니다.
is_premium선택되는 모델의미
Truegpt-5강력한 모델 (프리미엄 회원 대접)
Falsegpt-5-nano기본 모델 (비용 절약)
⚠️ 03과 헷갈리지 마세요 바로 앞 노트북(03. 동적 모델 선택)은 사용자 메시지의 길이를 보고 모델을 골랐습니다. 이번 04는 외부에서 주입된 회원 정보(is_premium)를 보고 모델을 고릅니다. "무엇을 근거로 모델을 바꾸느냐"가 다른 것이지, 미들웨어를 만드는 뼈대는 똑같습니다. (자세한 비교는 아래 표에서 다룹니다.)

0. 환경 준비 — 기본 모델 만들기

먼저 필요한 도구들을 가져오고 .env에서 API 키를 불러온 뒤, 기본 모델을 하나 만듭니다. 여기서 만든 model은 말하자면 "기본값"일 뿐, 실제로 어떤 모델이 쓰일지는 뒤에서 만들 미들웨어가 상황에 따라 다시 결정합니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent


# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")
💡 import는 왜 미리 다 해둘까 tool과 create_agent는 이 셀에서 당장 쓰이진 않습니다. 이후 미들웨어를 실제 Agent에 조립할 때 필요하기 때문에 미리 불러두는 것뿐이에요. (조립하는 모습은 아래 보충에서 확인합니다.)

1. Context 정의 — 회원 카드 만들기

Context는 대화가 시작될 때 Agent에게 딱 한 번 건네주는 "회원 카드"입니다. 이 카드에는 사용자가 누구인지(user_id)와 프리미엄 회원인지(is_premium)가 적혀 있습니다. Agent가 실행되는 동안 이 정보는 변하지 않습니다 — 그래서 "사용자 ID나 권한 같은 고정 정보"를 담기에 딱 맞습니다.

🔍 비유 — 입장할 때 내미는 회원 카드 헬스장이나 라운지에 들어갈 때 우리는 입구에서 회원 카드를 한 번 내밉니다. 카드에는 "이 사람은 누구", "VIP인지 아닌지"가 적혀 있죠. 일단 들어가고 나면 운동하는 내내 그 카드 내용이 바뀌지 않습니다. Context가 바로 그 회원 카드입니다. 대화(입장) 시작 시 한 번 건네지고, 대화가 끝날 때까지 고정된 신원 정보로 계속 참조됩니다.
📥 코드
# 예시 코드
from dataclasses import dataclass

@dataclass
class Context:
    user_id: str
    is_premium: bool = False  # 프리미엄 여부 (기본값 False)
💡 @dataclass가 하는 일 @dataclass는 __init__(생성자) 같은 반복 코드를 자동으로 만들어 주는 데코레이터입니다. 덕분에 Context(user_id="user_001", is_premium=True)처럼 바로 값을 채워 카드를 발급할 수 있습니다. is_premium=False는 기본값이라 생략하면 자동으로 "일반 회원"으로 취급됩니다.

2. membership_model_selector — 회원 등급을 확인하는 미들웨어

이제 이 노트북의 핵심입니다. @wrap_model_call로 미들웨어를 만들면, 모델이 호출되기 직전에 요청을 가로채서(intercept) 원하는 대로 손볼 수 있습니다. 우리는 이 지점에서 회원 카드를 꺼내 보고, 등급에 맞는 모델로 바꿔치기할 겁니다.

🔍 비유 — 클럽 입구의 도어맨 @wrap_model_call 미들웨어는 모델로 들어가는 문 앞에 선 도어맨입니다. 손님(요청)이 안으로 들어가기 직전에 도어맨이 잠깐 멈춰 세우고 회원 카드(is_premium)를 확인합니다. VIP면 "VIP룸(gpt-5)으로 안내", 일반이면 "일반석(gpt-5-nano)으로 안내"라고 행선지 표를 바꿔 붙인 뒤 손님을 통과시키죠. 도어맨은 손님을 막는 게 아니라, 맞는 방으로 다시 안내하는 역할입니다.

미들웨어 안에서 벌어지는 일은 정확히 5단계입니다.

1카드 확인

request.runtime.context.is_premium으로 등급을 읽는다

2모델 결정

등급에 따라 gpt-5 / gpt-5-nano 이름을 고른다

3모델 생성

init_chat_model로 새 모델 객체를 만든다

4요청 수정

request.override(model=...)로 모델 칸만 바꾼 사본을 만든다

5넘기기

handler(new_request)로 수정된 요청을 실행 단계로 넘긴다

📥 코드
from langchain.agents.middleware import wrap_model_call
# 예시 코드
@wrap_model_call
def membership_model_selector(request, handler):
    # 1. 런타임 컨텍스트에서 멤버십 정보 확인
    is_premium = request.runtime.context.is_premium

    # 2. 조건에 따른 모델 이름 결정
    if is_premium:
        model_name = "gpt-5"
    else:
        model_name = "gpt-5-nano"

    # 3. 새로운 모델 객체 생성
    new_model = init_chat_model(model_name)

    # 4. 기존 요청의 모델을 새로운 모델로 덮어쓰기 (override)
    new_request = request.override(model=new_model)

    # 5. 수정된 요청으로 실행 계속 진행
    return handler(new_request)

한 줄씩 뜯어보기

① request.runtime.context.is_premium — 회원 카드를 꺼내 보는 대목입니다. request는 "이 모델로 이 메시지를 처리해줘"라는 주문서이고, 그 안의 runtime.context가 바로 우리가 1단계에서 정의한 회원 카드(Context)입니다. 여기서 .is_premium을 읽어 등급을 확인합니다.

② ~ ③ 모델 이름을 정하고 만들기 — is_premium이 True면 "gpt-5", 아니면 "gpt-5-nano". 정해진 이름으로 init_chat_model을 호출해 실제 모델 객체를 새로 만듭니다.

🔍 비유 — 주문서의 한 칸만 고쳐 넘기기 request.override(model=new_model)는 주문서를 통째로 새로 쓰는 게 아니라, 원본 주문서를 복사한 뒤 "모델" 칸 하나만 새 값으로 고친 사본을 만드는 것입니다 (메시지·도구·설정 등 나머지 칸은 그대로 유지). 그리고 handler(new_request)는 그 고쳐진 주문서를 실제 요리사(모델 호출 담당)에게 넘기는 행동이에요. 도어맨이 행선지만 바꿔 손님을 들여보내는 것과 똑같습니다.

④ ~ ⑤ handler가 진짜 실행자 — handler는 "이 요청으로 모델을 실제 호출하는 다음 단계"입니다. 미들웨어는 요청을 손보기만 하고, 진짜 실행은 handler에게 맡깁니다. 그래서 return handler(new_request)로 바꿔치기한 요청을 넘기면, 그 사용자에게 맞는 모델로 답변이 생성됩니다.

▶ 이렇게 동작해요 (예상 동작)
# is_premium=True 인 사용자가 말을 걸면
#   → membership_model_selector가 "gpt-5" 로 교체 → 강력한 모델이 답변

# is_premium=False (또는 생략) 인 사용자가 말을 걸면
#   → membership_model_selector가 "gpt-5-nano" 로 교체 → 가벼운 모델이 답변
⚠️ override는 원본을 바꾸지 않습니다 request.override(...)는 원본 request를 직접 수정하지 않고 새 사본을 돌려줍니다. 그래서 반드시 new_request = request.override(...)처럼 결과를 받아서 그걸 handler에 넘겨야 합니다. request.override(...)만 호출하고 결과를 안 받으면 모델이 바뀌지 않아요.

03 vs 04 — 무엇이 달라졌나

두 노트북 모두 @wrap_model_call로 모델을 동적으로 바꾸는 미들웨어입니다. 뼈대(요청 가로채기 → 모델 결정 → override → handler)는 완전히 같습니다. 다른 건 딱 하나 — "무엇을 근거로 모델을 고르느냐"입니다.

구분03 dynamic_model_selector04 membership_model_selector
판단 기준사용자 메시지의 길이사용자의 멤버십 등급(is_premium)
정보 출처request.messages
(요청 안에 이미 있는 정보)		request.runtime.context
(외부에서 주입한 Context 정보)
비유손님이 주문한 '양'을 보고 결정손님의 '회원 등급'을 보고 결정
공통점request.override(model=...)로 모델을 갈아끼운 뒤 handler로 넘긴다
💡 runtime.context는 "바깥세상과 이어진 통로" 메시지 길이는 요청 안에 이미 들어 있어 곧바로 잴 수 있습니다. 하지만 회원 등급은 요청 안에 없습니다 — 그건 로그인 시스템이나 DB가 알고 있는 정보죠. 그래서 우리가 바깥에서 Context에 담아 주입하고, 미들웨어는 request.runtime.context라는 통로를 통해 그 정보를 읽습니다. 이것이 "외부 정보로 Agent 동작을 바꾸는" 컨텍스트 엔지니어링의 기본기입니다.

Agent에 실제로 연결하기 보충

노트북에는 미들웨어를 정의하는 부분까지만 나옵니다. 그렇다면 이 도어맨을 실제 문 앞에 세우고, 회원 카드는 어떻게 건네줄까요? create_agent에 미들웨어와 Context 스키마를 등록하고, invoke할 때 실제 회원 카드(Context 인스턴스)를 함께 넘겨 주면 됩니다.

📘 보충 — 미들웨어를 Agent에 조립하는 전체 흐름 (노트북 이후 단계)

아래 코드는 노트북 셀에는 없지만, 앞에서 만든 조각들이 실제로 어떻게 맞물리는지 보여주는 예시입니다.

📥 코드 (예시)
from langchain.agents import create_agent

# 1) 미들웨어와 Context 스키마를 Agent에 등록
agent = create_agent(
    model="gpt-4o-mini",                   # 기본 모델 (미들웨어가 상황에 맞게 교체함)
    tools=[],
    middleware=[membership_model_selector],
    context_schema=Context,                # 회원 카드 양식 등록
)

# 2) 프리미엄 회원 → 미들웨어가 gpt-5 로 교체
agent.invoke(
    {"messages": [{"role": "user", "content": "안녕하세요"}]},
    context=Context(user_id="user_001", is_premium=True),
)

# 3) 일반 회원 → 미들웨어가 gpt-5-nano 로 교체
agent.invoke(
    {"messages": [{"role": "user", "content": "안녕하세요"}]},
    context=Context(user_id="user_002", is_premium=False),
)
🔍 비유 — 문·도어맨·회원 카드의 조립 context_schema=Context는 "우리 가게는 이런 양식의 회원 카드를 받습니다"라고 문에 붙여두는 것, middleware=[membership_model_selector]는 도어맨을 문 앞에 세우는 것, 그리고 invoke(..., context=Context(...))는 손님이 입장하며 실제 회원 카드를 내미는 순간입니다. 이 셋이 맞물려야 도어맨이 카드를 확인하고 방을 배정할 수 있습니다.
실전에서는 is_premium=True를 코드에 직접 쓰는 대신, Context(user_id="...", is_premium=DB에서_조회한_결과)처럼 로그인·결제 DB에서 조회한 값을 넣습니다. 코드 로직은 그대로 두고 카드 내용만 사용자마다 달라지는 셈이죠.

📚 한 장 정리

오늘의 핵심 외부에서 주입한 회원 정보(Context.is_premium)를 미들웨어가 request.runtime.context로 읽어 사용자 등급에 맞는 모델로 갈아끼운다. 프리미엄은 gpt-5, 일반은 gpt-5-nano.
  • Context = 회원 카드 — @dataclass로 user_id·is_premium 같은 고정 신원 정보를 담는다.
  • @wrap_model_call = 도어맨 — 모델 호출 직전에 요청을 가로채 원하는 대로 손볼 수 있다.
  • 5단계 흐름 — 카드 확인 → 모델 결정 → 모델 생성 → override(model=...) → handler로 넘기기.
  • override는 사본을 만든다 — 원본을 바꾸지 않으니 new_request = request.override(...)로 결과를 받아 handler에 넘겨야 한다.
  • 03과의 차이 — 판단 근거가 메시지 길이(요청 내부)가 아니라 멤버십(외부 주입 Context)이라는 점뿐. 미들웨어 뼈대는 동일.
  • 조립 — create_agent(middleware=[...], context_schema=Context)로 세팅하고, invoke(..., context=Context(...))로 실제 카드를 건넨다.
