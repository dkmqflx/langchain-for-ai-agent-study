— "평가가 없으면 변경은 도박"을 두세 문장으로

프롬프트 한 줄, 검색 설정 하나를 바꿀 때마다 "나아졌나?"를 질문 두세 개로 확인하던 상태에서 출발합니다. 그 방식은 내가 고친 부분만 보게 되고, 다른 곳이 나빠진 건 배포 뒤에야 압니다. 그래서 고정된 시험지와 자동 판정이 필요했다 — 이게 문제 정의입니다.

# P3 · LLM/Agent 평가·관측성 하네스

## 문제 정의
프롬프트나 검색 설정을 바꿀 때마다 질문 두세 개로 "나아졌나"를 확인하는 방식은 고친 곳만 보게 되고,
다른 곳의 회귀는 배포 뒤에 드러난다. P1(RAG)·P2(Agent)를 시험 대상으로, 고정된 시험지와 자동 판정으로
"이번 변경이 지난 baseline보다 나빠졌는가"에 명령 한 번으로 답하는 하네스를 만들었다.

## 아키텍처
골든셋(datasets/, 버전 태그) → 러너(runner.py) → 시험 대상(P1 /query · P2 /chat, HTTP만)
→ 지표 3층(결정론 · RAGAS · LLM-as-judge) → runs/<시험지>__<라벨>__<시각>/ → compare.py(임계값 판정)
→ 리포트(reports/) · 게이트(pytest, baselines/ 대비)

손잡이: `--param`(시험 대상 설정) · `THRESHOLDS`(지표별 임계값) · `baselines/`(승격은 폴더 복사)
Langfuse: 시험지 = dataset, 케이스 = item(id 동일), 실행 = run, 지표 = score

시험 대상을 import하지 않고 HTTP로만 호출해, 창구가 있는 서비스라면 무엇이든 같은 시험지로 채점된다.

## 실행
```bash
# 터미널 A·B: P1(8000) · P2(8001) 먼저
uv sync
uv run python runner.py --target rag   --dataset rag_v1   --label rerank --param mode=rerank --ragas --judge
uv run python runner.py --target agent --dataset agent_v1 --label prompt-A --judge
uv run python compare.py baselines/rag_v1 runs/<실행>
uv run pytest -q
```

## 한계와 다음
- 케이스 15~20개 — 케이스 하나가 0.05~0.07을 움직인다 → 50개 이상 + smoke/full 분리
- 같은 설정의 흔들림 ±0.0x(3회 측정) → 3회 평균으로 판정
- judge가 시험 대상과 같은 계열 → 다른 계열 심판, 라벨 30개로 κ
- P3 trace ↔ P2 trace는 세션 id로만 연결 → 헤더 전파
- CI는 로컬 gate.sh — P1의 인덱스·모델 로딩 때문에 → 아티팩트 캐시 + 야간 workflow

## 배운 점
- (평가 하네스를 만들며 시험 대상 설계에 대해 깨달은 것 한 줄 — 예: "P1에 contexts 옵션이 없었다면 RAGAS 셋 중 셋을 못 쟀다. 서비스는 평가를 염두에 두고 창구를 열어야 한다")
- (judge를 사람 라벨로 검증하며 깨달은 것 한 줄)
- (임계값을 정하며 깨달은 것 한 줄)
✅ 검증
  • 처음 보는 사람이 돌릴 수 있다 — README만 보고 서버 둘을 띄우고 runner → compare → pytest를 실행할 수 있다
  • 표 셋에 실제 숫자가 있다 — x가 하나도 안 남아 있고, 각 표 아래 해석이 한 줄씩 있다
  • 한계 칸에 측정치가 있다 — 흔들림 폭과 judge 후함/박함이 "느낌"이 아니라 숫자로 적혀 있다
  • 커밋 히스토리가 순서를 말한다 — 시험지 → 러너 → 지표 → 비교 → 게이트 순서의 커밋과, baseline 승격 커밋이 있다
🎓 한 줄 정리

P3의 결과물은 점수가 아니라 "회귀를 잡아냈다"는 기록이다. 그 기록이 있어야 다음 단계에서 무엇을 바꾸든 안심하고 바꿀 수 있다.

이력서 문장 셋

  • 토스플레이스 · 토스 — "RAG·Agent 서비스에 대한 골든셋 기반 회귀 평가 하네스를 구축해, 검색 구성 변경 시 context recall 0.70→0.58 하락을 배포 전에 자동 감지"
  • 토스 (평가 플랫폼) — "LLM-as-judge를 사람 라벨 대비 ±1 일치율 0.9로 검증하고, 지표를 Langfuse dataset run·score로 적재해 실행 간 비교를 대시보드화"
  • 카카오헬스케어 — "평가 대상을 HTTP 경계로 분리해 어떤 서비스든 같은 시험지로 채점되는 구조 — 이후 LangGraph 기반 서비스의 품질 게이트로 재사용"

다음 단계에서 P3가 하는 일

LangGraph 프로젝트 3선의 G1(Self-Corrective RAG)은 P1을 그래프로 다시 만드는 프로젝트입니다. G1이 완성되면 targets.py에 ask_g1()을 더하고 같은 rag_v1으로 두 실행을 비교합니다 — "그래프로 바꿨더니 recall +0.15"가 그때의 표입니다. G2(Supervisor)에서는 agent_v1에 라우팅 케이스를 더해(v2) 라우팅 정확도를 잽니다. P3는 버리는 연습작이 아니라 앞으로 만드는 모든 것의 검문소입니다.
