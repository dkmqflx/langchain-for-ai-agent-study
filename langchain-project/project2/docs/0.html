🎯 목표

project2/를 혼자서도 도는 프로젝트로 세우고, P1 서버와 말이 통하는지까지 확인합니다. 코드는 아직 한 줄도 안 씁니다. 빈 캔버스를 제대로 준비하는 게 이번 목표예요.

🧠 개념 — 딱 하나만

P1과 폴더를 나눕니다. 창구 하나로만 만나게

P2가 필요한 건 P1의 검색 결과뿐입니다. Chroma DB도, 리랭커 모델도, PDF 파서도 필요 없어요. 그런데 같은 폴더에 섞어 두면 그 짐을 전부 같이 지게 됩니다 — 패키지 버전이 하나만 어긋나도 둘이 함께 막히고요.

그래서 HTTP라는 얇은 창구로만 만나게 합니다. P2가 P1에 대해 아는 건 주소 하나와 JSON 모양뿐입니다. 지금 폴더를 나누는 이 결정이, STEP 2에서 "왜 import가 아니라 requests인가"의 답이 됩니다.

📞 비유 — 옆 건물 자료실에 전화 걸기

우리 사무실(P2)은 서고를 통째로 들여놓지 않습니다. 필요할 때 자료실(P1)에 전화해서 필요한 것만 묻습니다. 그러니 사무실은 책장 없이도 일할 수 있고, 자료실이 다른 건물로 이사해도 전화번호만 바꾸면 됩니다. 자료실이 오늘 문을 닫았다면? 사무실은 그 일만 못 할 뿐, 나머지 일은 계속합니다.

그 전화번호가 .env의 P1_API_URL입니다. 이 값을 코드가 아니라 설정에 두는 이유가 정확히 "이사할 수 있어서"예요.

🛠 할 일 — 다섯 조각

하나씩 보고, 아래 전체 명령어를 그대로 복사해 써도 됩니다.

①

P2 전용 파이썬 환경

— 폴더는 이미 있다. 환경만 새로 깐다
터미널 B — P2 작업용
# 이 가이드가 들어 있는 폴더로 이동 (docs/의 부모)
cd ~/Documents/langchain-study/langchain-project/project2

# 지금 폴더(.)를 파이썬 프로젝트로 초기화한다. P1 때와 같은 명령이다:
#   pyproject.toml   → 이 프로젝트가 쓰는 패키지 목록
#   .python-version  → 쓸 파이썬 버전
#   .gitignore       → 깃에 올리지 않을 파일 목록 (.env 등)
#   .venv/           → P2 전용 파이썬 환경 (P1과 섞이지 않는 칸막이)
uv init .

환경을 나눠야 "P2는 무슨 패키지로 도는가"가 pyproject.toml 하나에 정확히 드러납니다. STEP 9에서 남에게 보여 줄 때, 이 파일이 곧 이 프로젝트의 부품 목록이 돼요.

②

의존성 — 세 묶음으로 나눠서

— 어느 패키지가 어느 STEP 것인지 알고 넘어간다
터미널 B
# 1묶음 · Agent 코어 (STEP 1~4)
#   langgraph → checkpointer(InMemorySaver)가 여기 들어 있다. langchain이 내부적으로 쓰지만
#               우리가 직접 import 하므로 명시적으로 적는다('쓰는 쪽이 선언'이 원칙)
#   ddgs      → DuckDuckGo 검색. API 키가 필요 없어 바로 쓸 수 있다
#   requests  → STEP 2에서 P1의 창구를 두드릴 때 쓴다
uv add langchain langchain-openai langgraph python-dotenv ddgs requests

# 2묶음 · 서빙 · 관측 (STEP 5~6)
#   "uvicorn[standard]" 의 따옴표는 필수 — 없으면 셸이 [ ]를 파일이름 패턴으로 읽는다
uv add fastapi "uvicorn[standard]" langfuse

# 3묶음 · Multi-LLM · 평가 (STEP 7~8)
uv add langchain-google-genai pandas
패키지쓰이는 곳역할
langchain · langchain-openai1~4create_agent·@tool·미들웨어 + OpenAI 모델 연결
langgraph3InMemorySaver — 대화 세션을 저장하는 checkpointer
ddgs1DuckDuckGo 웹 검색 (API 키 불필요)
requests2P1의 POST /query 호출
python-dotenv전체.env의 키를 환경변수로 로드
fastapi · uvicorn5HTTP API 서버

langchain-google-genai7Gemini 모델 연결 (Multi-LLM의 두 번째 축)
pandas8평가 결과 집계·비교표 출력

나중에 ImportError가 나면 이 표를 보세요. "아 이건 STEP 7용이었지" 하고 바로 짚입니다.

④

.env — 키와 주소

— P1에서 쓰던 파일을 복사해 오고 두 줄 더한다
.env
OPENAI_API_KEY=sk-...

# P1에서 쓰던 값 그대로 복사
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_BASE_URL=https://cloud.langfuse.com

# STEP 2 — P1 서버 주소. 코드에 박지 않고 설정으로 빼 둔다
#          (나중에 P1을 다른 서버에 올려도 이 한 줄만 바꾸면 된다)
P1_API_URL=http://localhost:8000

# STEP 7 — Gemini. langchain-google-genai가 찾는 이름은 GOOGLE_API_KEY다.
#          학습용 .env에 GEMINI_API_KEY로 있다면 같은 값을 이 이름으로도 넣어 준다.
GOOGLE_API_KEY=AIza...

Langfuse 키는 P1에서 발급받은 같은 값을 씁니다. 그래야 한 프로젝트에 P1·P2 기록이 함께 쌓여서, 나중에 "이 대화에서 P1 검색이 몇 번 일어났나"를 한 화면에서 볼 수 있어요. .gitignore에 .env가 들어 있는지도 확인해 두세요 — uv init이 보통 넣어 줍니다.

🎓 한 줄 정리

서비스를 나눈다는 건 폴더를 나누는 게 아니라, 서로 아는 것을 주소 하나로 줄이는 것이다. 환경·의존성·키를 각자 갖고, 통신은 코드가 아니라 설정(P1_API_URL)에 둔다.

더 알아보기 — 환경변수 이름 / P1 없이 진행하기

라이브러리마다 찾는 이름이 정해져 있습니다

키를 .env에 분명히 넣었는데 "API key not found"가 나는 경우, 값이 아니라 변수 이름이 원인일 때가 많습니다. 라이브러리는 자기가 정해 둔 이름만 찾거든요 — langchain-google-genai는 GOOGLE_API_KEY를 봅니다. 학습용 .env에 GEMINI_API_KEY로 적어 두었다면, 같은 값을 GOOGLE_API_KEY라는 이름으로도 넣어 주면 됩니다.

"키가 없다"는 메시지를 보면 키가 정말 없는 건지, 이름이 다른 건지부터 확인하세요. 아래처럼 한 줄로 볼 수 있습니다. 

uv run python -c "import os; from dotenv import load_dotenv; load_dotenv(); print(sorted(k for k in os.environ if 'KEY' in k))"

P1이 아직 없다면

STEP 2만 건너뛰면 됩니다. 도구 세 종(날짜·계산·웹검색)만으로도 메모리·가드레일·서빙·관측·Multi-LLM·평가는 전부 그대로 학습할 수 있어요. 나중에 P1이 준비되면 tools.py에 도구 하나를 더하고 create_agent의 목록에 이름 하나를 추가하면 끝입니다. 그게 능력을 도구 단위로 쪼개 둔 값입니다 — 새 능력이 생겨도 나머지 코드는 그대로예요.
