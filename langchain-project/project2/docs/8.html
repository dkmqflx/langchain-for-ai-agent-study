8

프롬프트 A/B 평가 하네스 (LLM-as-judge)

서비스화 층 이 프로젝트의 하이라이트 ⏱ 3~4시간
🎯 목표

케이스 10~20개로 프롬프트 A와 B를 자동 채점해, "이 프롬프트 수정이 실제로 나아졌는가"를 표에 있는 숫자로 증명한다.

🧠 개념 ①

프롬프트 수정은 항상 나아 보입니다

프롬프트를 고치고, 질문 두세 개 던져 보고, "오 훨씬 낫네" 하고 배포한 적 있으신가요? 문제는 그 판단이 거의 언제나 틀린 방식으로 만들어진다는 겁니다.

  • 표본이 두세 개입니다. 그것도 내가 방금 고친 부분이 잘 드러나는 질문들로만 골랐죠.
  • 내가 고친 걸 압니다. 사람은 자기가 손댄 쪽을 더 좋게 읽습니다. 눈을 가리지 않은 실험이에요.
  • 망가진 곳은 안 봅니다. 한 곳을 좋게 만든 프롬프트가 다른 곳을 부수는 일은 아주 흔한데, 그 "다른 곳"을 질문하지 않았습니다.
🏃 비유 — 스톱워치 없는 훈련

자세를 바꾸고 나서 "오늘 훨씬 가볍게 뛴 것 같은데?"는 데이터가 아닙니다. 컨디션 좋은 날엔 뭘 해도 가볍거든요. 매번 같은 코스에서 스톱워치로 재야 자세 변경이 효과가 있었는지 알 수 있습니다.

eval_cases.json이 그 고정된 코스이고, 채점 하네스가 스톱워치입니다. 코스를 고정해 두는 게 핵심이에요 — 매번 다른 질문으로 재면 아무것도 비교할 수 없습니다.

🧠 개념 ②

세 가지를 따로 잽니다 — 그리고 두 개는 공짜입니다

"답변 품질"을 뭉뚱그려 LLM에게 채점시키는 건 비싸고, 흔들리고, 왜 그 점수인지 알기 어렵습니다. 코드로 정확히 셀 수 있는 것부터 분리해 내세요.

무엇을어떻게비용재는 것
① 도구 선택 정확도 expect_tool vs 실제 used_tools 0원 약관 질문에 문서검색을 썼는가. 인사에 도구를 안 썼는가
② 형식 준수 sources가 비었나 · blocked가 기대와 같나 0원 근거를 달았는가. 막아야 할 걸 막았는가
③ 답변 품질 LLM-as-judge (1~5점) 호출 1회 내용이 기준(rubric)에 맞는가. 사람만 판단할 수 있던 것
💡 STEP 4에서 본 원칙이 그대로 다시 나옵니다

가드레일에서 "싸고 확실한 검사를 앞에"라고 했었죠. 채점도 똑같습니다. ①·②는 공짜인 데다 결과가 흔들리지 않습니다 — 몇 번을 돌려도 같은 답이 나와요. ③만 LLM에게 맡깁니다. 이렇게 나눠 두면 점수가 떨어졌을 때 "도구를 잘못 골라서인지, 근거를 안 달아서인지, 내용이 부실해서인지"가 바로 보입니다. 하나로 뭉친 점수는 떨어져도 왜 떨어졌는지 알려 주지 않습니다.

LLM-as-judge — 채점 기준을 프롬프트로 준 채점자

별게 아닙니다. "이 기준으로 이 답변을 1~5점으로 매겨 줘"라고 다른 LLM에게 부탁하는 것이에요. 다만 채점자를 제대로 세우려면 세 가지를 지켜야 합니다.

  • 기준을 케이스마다 준다. "좋은 답인가?"는 채점 기준이 아닙니다. "무엇이 들어 있어야 하는가"를 적어야 해요.
  • 점수의 뜻을 못 박는다. 척도 설명이 없으면 판단이 흔들리고, 대체로 뭉뚱그려 중간 점수만 나옵니다.
  • 이유를 함께 쓰게 한다. 이유를 적게 하면 채점이 더 정확해지고, 우리도 점수를 검증할 수 있습니다.
⚠️ 채점자는 자기 답에 후합니다 (self-preference bias)

같은 모델이 답도 쓰고 채점도 하면, 자기 문체로 쓰인 답에 점수를 더 줍니다. 사람도 그러죠. 그래서 가능하면 채점자와 피평가자를 다른 모델로 두는 게 좋습니다 — STEP 7에서 provider를 갈아끼울 수 있게 만들어 뒀으니 어렵지 않습니다.

그리고 더 근본적인 질문 — "이 채점자를 믿어도 되나?" 이건 사람이 직접 매긴 소수 케이스와 judge 점수의 일치율을 재서 확인합니다. 그 작업이 P3의 주제이고, 여기서는 씨앗만 뿌려 둡니다: 돌려 본 뒤 케이스 3~5개는 직접 읽고 "나라면 몇 점?"을 적어 보세요.

B에서 열 군데를 고치고 점수가 올랐다면, 어느 수정 덕분인지 알 수 없습니다. 위 B는 두 군데(근거 형식 구체화 · 도구 미사용 규칙)만 건드렸고, 그래서 결과를 해석할 수 있어요. 더 엄밀하게 하려면 하나씩만 바꾼 C, D를 만들어 붙이면 됩니다 — 하네스가 있으니 케이스는 그대로 재사용됩니다.

② agent.py — 프롬프트를 요청마다 갈아끼울 구멍 내기

평가하려면 같은 Agent를 프롬프트만 바꿔 돌려야 합니다. STEP 7에서 모델을 갈아끼운 방식을 그대로 씁니다 — Context에 칸을 하나 늘리고 미들웨어를 하나 더 다는 게 전부예요.

agent.py — 추가·수정
@dataclass
class Context:
    provider: str | None = None
    system_prompt: str | None = None      # ← 추가


@wrap_model_call
def override_prompt(request, handler):
    """요청에 시스템 프롬프트가 지정돼 있으면 그것으로 갈아끼운다(평가·실험용)."""
    sp = getattr(request.runtime.context, "system_prompt", None)
    if sp:
        request = request.override(system_prompt=sp)
    return handler(request)


# create_agent의 middleware 목록에 override_prompt 추가
# ask()에도 인자를 하나 늘린다:
def ask(message: str, session_id: str = "default",
        provider: str | None = None, system_prompt: str | None = None) -> dict:
    ...
        result = agent.invoke(
            {"messages": [{"role": "user", "content": message}]},
            {"configurable": {"thread_id": session_id}, "callbacks": [langfuse_handler]},
            context=Context(provider=provider, system_prompt=system_prompt),   # ← 수정
        )
    ...
🎛 미들웨어 하나 = 실험 축 하나

이제 모델과 프롬프트를 요청 단위로 바꿀 수 있게 됐습니다. 손잡이 두 개가 생긴 셈이고, 조합해서 "A×openai / A×gemini / B×openai / B×gemini"를 재는 것도 가능하죠. 실험 가능한 시스템이란 결국 이런 손잡이가 밖으로 나와 있는 시스템입니다. 코드를 고쳐야만 바뀌는 값은 실험할 수 없어요.

③ eval_cases.json — 고정된 코스 만들기

여기가 이 STEP에서 가장 오래 걸리고, 가장 값진 부분입니다. 코드는 복사하면 되지만 케이스는 여러분의 문서에서 직접 만들어야 하니까요. 10~20개를 목표로 하되, 골고루 담는 게 개수보다 중요합니다.

종류개수왜 필요한가

④ evaluate.py — 채점 하네스

evaluate.py
# ═══════════════════════════════════════════════════════════════════
# STEP 8 · 프롬프트 A/B 채점: 같은 케이스를 프롬프트별로 돌려 세 가지를 잰다.
#   ① 도구 선택 정확도 (코드로 계산 · 공짜)
#   ② 형식 준수        (코드로 계산 · 공짜)
#   ③ 답변 품질        (LLM-as-judge · 케이스당 호출 1회)
#
# 실행: uv run python evaluate.py
# ═══════════════════════════════════════════════════════════════════
import json

import pandas as pd
from dotenv import load_dotenv
from pydantic import BaseModel, Field
from langchain.chat_models import init_chat_model
from langfuse import get_client

from agent import ask
from prompts import PROMPTS

load_dotenv()
langfuse = get_client()


# ── 채점자(judge) 준비 ────────────────────────────────────────────
class Judgement(BaseModel):
    """채점 결과의 형식. 점수만 받지 않고 이유까지 받는다."""
    score: int = Field(description="1~5점", ge=1, le=5)
    reason: str = Field(description="그 점수를 준 이유 한 문장")

# with_structured_output = '이 형식으로만 답하라'고 모델을 묶는 것.
# 채점 결과를 문자열에서 파싱할 필요가 없어진다.
#
# 채점자는 피평가 모델과 다르게 두는 편이 낫다(자기 답에 후한 경향).
# 여기서는 학습 편의상 같은 계열을 쓰되, gemini로 바꿔 보고 점수가 달라지는지 확인해 보세요.
judge = init_chat_model("openai:gpt-5-mini").with_structured_output(Judgement)

JUDGE_TEMPLATE = """너는 엄격한 채점자다. 아래 답변을 채점 기준에 따라 1~5점으로 평가하라.

[질문]
{question}

[채점 기준]
{rubric}

[답변]
{answer}

[제시된 근거]
{sources}

점수 척도 — 반드시 이 기준을 따르라:
5 = 기준을 완전히 충족하고, 근거가 적절하다
4 = 기준을 충족하나 사소한 누락이 있다
3 = 절반쯤 맞다. 중요한 내용이 빠졌다
2 = 대체로 빗나갔다. 일부만 관련 있다
1 = 완전히 틀렸거나, 문서에 없는 내용을 지어냈다

지어낸 내용이 하나라도 있으면 다른 게 아무리 좋아도 1점이다."""


def judge_answer(case: dict, result: dict) -> Judgement:
    prompt = JUDGE_TEMPLATE.format(
        question=case["question"],
        rubric=case["rubric"],
        answer=result["answer"],
        sources=result["sources"] or "(없음)",
    )
    return judge.invoke(prompt)


# ── 케이스 하나 채점 ──────────────────────────────────────────────
def run_case(case: dict, label: str, system_prompt: str) -> dict:
    # 세션을 케이스마다 다르게 준다. 같으면 앞 케이스의 대화가 뒤 케이스에 섞여
    # '2번 문제를 1번 답을 보고 푸는' 꼴이 된다 — 채점이 통째로 무의미해진다.
    result = ask(
        case["question"],
        session_id=f"eval-{label}-{case['id']}",
        system_prompt=system_prompt,
    )

    # ① 도구 선택: 기대한 도구를 썼는가. 기대가 없으면(None) '아무 도구도 안 썼는가'
    expect = case.get("expect_tool")
    used = result["used_tools"]
    tool_ok = (expect in used) if expect else (len(used) == 0)

    # ② 형식 준수: 근거를 요구한 케이스에서 sources가 채워졌는가 + 차단 여부가 기대와 같은가
    sources_ok = bool(result["sources"]) if case.get("expect_sources") else True
    block_ok = result["blocked"] == case.get("expect_blocked", False)
    format_ok = sources_ok and block_ok

    # ③ 답변 품질: 차단이 기대된 케이스는 내용 채점을 하지 않는다.
    #    막는 게 정답인 질문의 '답변 내용'을 채점하는 건 말이 안 되고, 호출만 낭비다.
    if case.get("expect_blocked"):
        score, reason = (5 if block_ok else 1), "차단 케이스(내용 채점 생략)"
    else:
        verdict = judge_answer(case, result)
        score, reason = verdict.score, verdict.reason

    return {
        "id": case["id"], "prompt": label,
        "tool_ok": tool_ok, "format_ok": format_ok, "score": score,
        "expect_tool": expect, "used_tools": ",".join(used) or "-",
        "blocked": result["blocked"], "reason": reason,
    }


# ── 전체 실행 ────────────────────────────────────────────────────
def main():
    cases = json.load(open("eval_cases.json", encoding="utf-8"))
    rows = []

    for label, system_prompt in PROMPTS.items():
        print(f"\n=== 프롬프트 {label} · {len(cases)}개 케이스 ===")
        for case in cases:
            row = run_case(case, label, system_prompt)
            rows.append(row)
            mark = "✅" if (row["tool_ok"] and row["format_ok"]) else "❌"
            print(f"  {mark} {row['id']:10s} 도구={row['used_tools']:24s} 품질={row['score']}")

    df = pd.DataFrame(rows)
    df.to_csv("eval_results.csv", index=False, encoding="utf-8-sig")   # 케이스별 원본 기록

    # 프롬프트별 요약. mean()은 True를 1로 세므로 tool_ok의 평균이 곧 정확도다.
    summary = df.groupby("prompt").agg(
        도구선택_정확도=("tool_ok", "mean"),
        형식준수율=("format_ok", "mean"),
        답변품질_평균=("score", "mean"),
    ).round(3)

    print("\n" + "=" * 52)
    print(summary.to_string())
    print("=" * 52)

    # 어느 케이스에서 갈렸는지 — 요약표보다 이쪽이 훨씬 쓸모 있다
    pivot = df.pivot(index="id", columns="prompt", values="score")
    diff = pivot[pivot["A"] != pivot["B"]]
    if not diff.empty:
        print("\n[A와 B의 점수가 갈린 케이스]")
        print(diff.to_string())

    langfuse.flush()   # 스크립트가 끝나기 전에 기록을 모두 전송한다 (STEP 6 경고 참고)


if __name__ == "__main__":
    main()

# prompt    A    B
# id
# none-01   3    5
# web-01    4    3

통과 조건은 "점수가 올랐다"가 아닙니다. 아래 셋입니다.

  • 표가 숫자로 나온다 — 세 지표가 프롬프트별로 출력됨
  • 갈린 케이스를 설명할 수 있다 — eval_results.csv에서 그 케이스의 reason을 읽고 "왜 이렇게 됐는지" 한 문장으로 말할 수 있어야 한다
  • 차단 케이스가 A·B 둘 다 통과한다 — 프롬프트를 고쳤는데 가드레일이 뚫렸다면 즉시 고쳐야 한다
🚨 B가 졌다면? 그게 정상이고, 그게 수확입니다

"규칙을 더 자세히 썼는데 점수가 떨어졌다"는 흔한 일입니다. 규칙 7번("애매하면 자문하라")이 필요한 도구까지 주저하게 만들었을 수도 있죠. 그럼 그 케이스의 reason을 읽고 7번만 다시 손봐서 C를 만들어 돌리면 됩니다.

여기서 진짜로 얻은 것은 "B가 더 낫다"가 아니라 "이제 알 수 있게 됐다"입니다. 하네스가 없었다면 B를 배포하고 몇 주 뒤에야 뭔가 이상하다고 느꼈을 테니까요. 이력서에 쓸 문장도 점수 자체가 아니라 이쪽입니다 — "프롬프트 변경의 영향을 15개 케이스로 자동 채점해, 배포 전에 회귀를 잡는 체계를 만들었다."

⚠️ 비용과 시간 — 한 번 돌리면 얼마나 드나

케이스 15개 × 프롬프트 2개 = 30번의 Agent 실행 + 채점 호출 약 26번. Agent 실행 하나가 모델을 2~3번 부르니 대략 110회 안팎이고, 사내 문서 케이스는 P1까지 부르므로 전체 5~15분 걸립니다. 처음엔 케이스 3개로 줄여 돌려서 하네스가 제대로 도는지부터 확인하세요 — 15개를 다 돌리고 나서 버그를 발견하는 것만큼 아까운 게 없습니다.

🎓 배우는 것

"나아졌다"를 증명하는 방법. 고정된 케이스셋(코스)을 만들고, 잴 수 있는 것을 층으로 나누고, 판단이 필요한 것만 LLM에게 맡기는 설계. 그리고 실험 가능한 시스템의 조건 — 바꾸고 싶은 것(모델·프롬프트)이 코드 바깥으로 나와 있어야 한다는 것.
