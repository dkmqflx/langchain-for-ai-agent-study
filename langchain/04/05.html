05. RAG Store: Chroma DB

실습 노트북: 05.ipynb  ·  원문: docs/04.rag.md 2.4 Store  ·  난이도: 🟢 입문  ·  선행: 04. 캐시 임베더

이 자료는 실습 노트북(05.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. RAG 파이프라인의 네 번째 단계 Store — 임베딩한 벡터를 Vector DB에 파일로 영구 저장하는 단계를 다룹니다. 오늘의 주인공은 Chroma DB입니다. 문서를 저장하고, 질문 하나로 가장 비슷한 조각을 꺼내오는 RAG의 핵심 흐름까지 비유와 함께 천천히 짚어봅니다.

이 장에서 배우는 것 RAG는 Load → Split → Embed → Store → Retrieve 다섯 단계로 흐릅니다. 앞 장(04)에서 문서를 숫자(벡터)로 바꾸는 Embed까지 왔습니다. 이번 장은 그 벡터를 어딘가에 잘 보관(Store)하고, 나중에 질문으로 찾아 꺼내는(Retrieve의 맛보기) 방법입니다.
1Load

PDF 등 원문 불러오기

2Split

긴 문서를 조각(청크)으로 분할

3Embed

각 조각을 벡터(숫자)로 변환

4Store

벡터를 Vector DB에 저장 ← 오늘

5Retrieve

질문과 비슷한 조각 검색

🔍 비유 — 정리 안 된 책 더미 vs 도서관 임베딩만 끝낸 상태는 바닥에 쌓인 책 더미와 같습니다. 분명 있긴 한데, 필요한 책을 찾으려면 하나하나 뒤져야 하죠. Store는 이 책들을 도서관 서고에 분류해 꽂아 두는 일입니다. 한 번 잘 꽂아 두면, 나중에 "테슬라 이야기 나온 책"이라고 말만 해도 사서(similarity_search)가 곧바로 찾아줍니다. 그리고 이 서고는 파일이라, 도서관 문을 닫았다 다시 열어도(프로그램 재시작) 책이 그대로 남아 있습니다.
⚠️ 실행 전 준비 임베딩 단계에서 OpenAI를 호출하므로, 직접 돌려보려면 프로젝트 루트에 .env 파일과 그 안의 OPENAI_API_KEY가 필요합니다. 또 예제는 같은 폴더에 pdf-file.pdf가 있다고 가정합니다. 이 교재만 읽을 때는 필요 없습니다.

1. 재료 준비 — 캐시 임베더 만들기

벡터를 저장하려면 먼저 "문서를 벡터로 바꿔 줄 임베딩 모델"이 있어야 합니다. 04장에서 배운 캐시 임베더(CacheBackedEmbeddings)를 그대로 씁니다. 한 번 계산한 벡터를 ./cache/ 폴더에 기억해 두었다가, 같은 문장이 또 오면 API를 다시 부르지 않고 재사용하는 알뜰한 임베더죠.

🔍 비유 — 계산 결과를 적어 두는 계산기 매번 똑같은 문장을 임베딩(계산)하면 돈과 시간이 듭니다. 캐시 임베더는 한 번 계산한 답을 노트에 적어 두었다가, 같은 문제가 또 나오면 노트만 펼쳐 보는 계산기입니다. Store 실습에서도 문서 임베딩 비용을 아끼려고 이 임베더를 재료로 씁니다.
📥 코드
from langchain_openai import OpenAIEmbeddings
from langchain_classic.embeddings import CacheBackedEmbeddings
from langchain_classic.storage import LocalFileStore

underlying_embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

store = LocalFileStore("./cache/")

cached_embedder = CacheBackedEmbeddings.from_bytes_store(
    underlying_embeddings,
    store,
    namespace=underlying_embeddings.model
)
💡 이름이 겹쳐도 괜찮아요 여기서 만든 store는 임베딩 결과를 캐싱하는 저장소(LocalFileStore)입니다. 이번 장 제목의 "Store"(Vector DB)와는 다른 개념이에요. 하나는 계산 결과 캐시, 하나는 검색용 벡터 창고입니다.

2. 문서 로드 · 분할하기

저장할 내용물을 준비할 차례입니다. PDF를 불러와서(Load), 300자 단위 조각으로 쪼갭니다(Split). 이렇게 만들어진 조각 리스트 recursive_docs가 곧 Vector DB에 넣을 재료가 됩니다.

📥 코드
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_community.document_loaders import PDFPlumberLoader


loader = PDFPlumberLoader("./pdf-file.pdf")

docs = loader.load()


text_splitter = RecursiveCharacterTextSplitter(chunk_size=300, chunk_overlap=0)

recursive_docs = text_splitter.split_documents(docs)

vectorstore = InMemoryVectorStore.from_documents(
    documents=recursive_docs,
    embedding=cached_embedder
)
🔍 비유 — 화이트보드 vs 노트 마지막 줄의 InMemoryVectorStore는 화이트보드입니다 — 지금은 편하게 쓸 수 있지만, 프로그램을 끄면(교실을 나가면) 싹 지워집니다. 메모리(RAM) 위에만 있으니까요. 다음 단계에서 만날 Chroma는 노트입니다 — 파일로 남아서 나중에 다시 펼쳐 볼 수 있습니다. 이 셀은 "메모리 방식도 있다"를 보여 주는 대조군이고, 진짜 저장은 다음 단계의 Chroma가 담당합니다.
💡 왜 300자로 쪼갤까 문서가 너무 길면 검색 정확도도, LLM에 넣을 때의 효율도 떨어집니다. 그래서 의미 단위로 잘게 나눠 두는 것이죠. chunk_overlap=0은 조각끼리 겹치는 부분을 두지 않는다는 뜻입니다. (분할의 상세는 03장 참고)

3. Chroma DB에 저장하기

드디어 오늘의 핵심입니다. Chroma.from_documents(...) 한 번이면 "조각들을 임베딩해서 → Vector DB에 저장"까지 한꺼번에 처리됩니다. 게다가 Chroma는 그 결과를 ./chroma_db 폴더에 파일로 남기기 때문에, 프로그램을 재시작해도 데이터가 사라지지 않습니다.

🔍 비유 — 창고에 라벨 붙여 넣기 from_documents는 이삿짐센터 직원과 같습니다. 상자(문서 조각)를 받아 내용을 스캔(임베딩)하고, 창고(persist_directory)의 지정된 선반(collection_name)에 차곡차곡 넣어 둡니다. 한 번 넣어 두면, 나중에 창고 주소만 알려 줘도 그대로 다시 꺼내 볼 수 있죠.
📥 코드
from langchain_chroma import Chroma

# 1. DB 경로 설정
CHROMA_PATH = "./chroma_db"

# 2. Store 생성
db = Chroma.from_documents(
    documents=recursive_docs,
    embedding=cached_embedder,
    persist_directory=CHROMA_PATH,
    collection_name="rag_collection")

핵심 파라미터 4가지

파라미터뜻비유
documents저장할 문서 조각 리스트 (신규 저장 시에만 사용)창고에 넣을 상자들
embedding조각을 벡터로 바꿔 줄 임베딩 모델내용을 읽어 주는 스캐너
persist_directoryDB를 파일로 저장할 폴더 경로창고 주소
collection_nameDB 안의 테이블(선반) 이름 (선택)창고 속 선반 이름표
💡 collection_name이 왜 필요할까 하나의 Chroma DB 안에 여러 "컬렉션"을 둘 수 있습니다. 관계형 DB의 테이블처럼요. 예를 들어 "news_2024", "reports_2025"처럼 주제별로 선반을 나눠 두면 나중에 원하는 선반만 골라 검색할 수 있어 관리가 편해집니다.
📘 보충 — 이미 만들어 둔 Chroma DB 다시 불러오기

Chroma는 파일로 저장되므로, 한 번 만든 뒤에는 다시 임베딩할 필요 없이 경로만 알려 주고 불러올 수 있습니다. 이때는 documents=를 넘기지 않고, from_documents 대신 Chroma(...) 생성자를 씁니다.

📥 코드
# 기존 DB 불러오기 (새 문서 추가 없이 검색만)
db = Chroma(
    collection_name="rag_collection",
    embedding_function=cached_embedder,
    persist_directory=CHROMA_PATH,
)
⚠️ 인자 이름이 살짝 달라요 저장할 때는 embedding=이지만, 기존 DB를 불러올 때는 embedding_function=입니다. 불러온 뒤에도 질문을 벡터로 바꿔야 검색이 되기 때문에, 임베딩 모델을 다시 알려 주는 거예요.

4. similarity_search로 검색해 보기

저장했으니 이제 꺼내 볼 차례입니다. db.similarity_search(query, k=1)는 질문과 가장 비슷한 문서 조각을 k개 찾아 줍니다. 여기서는 k=1이라 딱 1개만 가져옵니다.

🔍 비유 — 사서에게 물어보기 도서관 사서에게 "테슬라 투자 비중이 궁금해요"라고 말하면, 사서는 서고를 훑어 가장 관련 깊은 책 한 권을 뽑아 건네줍니다. similarity_search가 바로 이 사서예요. 정확히 같은 단어가 아니어도, 의미가 가까운 조각을 벡터 거리(유사도)로 찾아냅니다.
📥 코드
query = "Tesla 투자 비중이 얼마나 되나요?"
results = db.similarity_search(query, k=1)
# 벡터스토어에 있는 문서와 유사도를 계산하고, 유사도가 높은 순서대로 검색 결과를 반환한다

print(len(results))

print(f"검색된 문서 내용:\n{results[0].page_content}")

💡 바로 이 흐름이 RAG의 심장 질문 → 유사한 문서 검색 → 그 내용을 프롬프트에 얹어 LLM에게 전달. 모델이 스스로 아는 지식이 아니라 우리가 찾아 준 근거로 답하게 만드는 것 — 이것이 RAG(검색 증강 생성)입니다.

5. 질문(Query)은 왜 쪼개지 않을까?

여기서 자연스러운 궁금증이 생깁니다. "문서는 300자로 잘게 쪼갰는데, 질문도 쪼개야 하나?" 정답은 아니오입니다. 질문은 통째로 임베딩합니다. 그 이유를 단계별로 짚어 볼게요.

🔍 비유 — 완성된 한 문장의 뜻 "테슬라 투자 비중이 / 얼마나 되나요?"처럼 질문을 반토막 내면, 각 조각은 원래의 의도를 잃어버립니다. "얼마나 되나요?"만 떼어 놓으면 무엇을 묻는지 알 수 없죠. 질문은 그 자체로 하나의 완성된 뜻이라, 쪼개지 않고 통째로 숫자로 바꿔야 의미가 온전히 보존됩니다.

① 질문 처리 과정

db.similarity_search(query, k=1) 한 줄 뒤에서는 이런 일이 벌어집니다.

  1. 임베딩 (청킹 X): "Tesla 투자 비중이 얼마나 되나요?"라는 문장 전체를 통째로 벡터로 변환합니다. 질문은 보통 짧아서 쪼갤 필요가 없습니다.
  2. 유사도 비교: 질문 벡터와, 이미 저장돼 있는 수많은 문서 조각들의 벡터를 수학적으로 비교합니다.
  3. 결과 추출 (k=1): 질문과 가장 비슷하게 생긴 조각 1개를 골라냅니다.

② 문서와 질문의 차이

대상쪼개나?이유
문서(Documents)✅ 쪼갠다너무 길어서 LLM이 한 번에 못 읽음 → 잘게 나눠 저장
질문(Query)❌ 통째로질문 자체가 하나의 완성된 의도 → 쪼개면 뜻이 깨짐

③ "자동으로" 일어나는 일들

사용자가 db.similarity_search 한 줄만 썼을 때, LangChain이 배후에서 알아서 해 주는 일입니다.

  • query를 임베딩 모델(OpenAI 등)로 보내 벡터로 변환
  • 받아온 벡터를 벡터 스토어의 데이터와 비교
  • 가장 유사한 순서대로 정렬해 상위 k개를 반환
💡 요약 질문은 쪼개지 않고 통째로 임베딩 · 비교는 질문 벡터 vs 저장된 청크 벡터들 · 결과는 유사도 최상위 k개. 이것이 RAG의 첫 단계인 검색(Retrieval)의 실체입니다. (검색기를 더 세밀하게 다루는 법은 다음 06장에서 이어집니다.)

📚 한 장 정리

오늘의 핵심 Store = 임베딩한 벡터를 Vector DB에 파일로 저장하는 단계. Chroma에 저장해 두면 프로그램을 껐다 켜도 남고, similarity_search 한 줄로 질문에 가장 가까운 조각을 꺼낼 수 있다.
  • Store의 위치 — RAG 5단계(Load → Split → Embed → Store → Retrieve) 중 네 번째, "벡터를 서고에 꽂는" 단계.
  • Chroma DB — 벡터를 ./chroma_db 폴더에 파일로 영구 저장. 재시작해도 데이터가 유지된다(노트, 화이트보드 아님).
  • Chroma.from_documents(...) — 조각 임베딩 + 저장을 한 번에. 핵심 인자는 documents · embedding · persist_directory · collection_name.
  • 다시 불러오기 — documents 없이 Chroma(...) 생성자로 경로만 지정. 이때 임베딩은 embedding_function=.
  • similarity_search(query, k) — 질문과 가장 비슷한 조각 k개 반환. 이 내용을 프롬프트에 얹는 게 RAG의 심장.
  • 질문은 통째로 — 문서는 쪼개 저장하지만, 질문은 완성된 의도라 쪼개지 않고 통째로 임베딩한다.
