🎯 목표

독립 실행되는 project2/ 환경을 만들고, P1 서버와 통신이 되는지까지 확인해 "빈 캔버스"를 준비한다.

🧠 개념

P1과 같은 폴더에 섞지 않고 별도 프로젝트로 나누는 이유가 이 STEP의 핵심입니다. P2는 P1의 검색 결과만 필요할 뿐, P1의 무거운 짐(Chroma DB·리랭커 모델·PDF 파서)까지 짊어질 이유가 없습니다. 두 서비스가 HTTP라는 얇은 창구로만 만나면, 각자 가볍게 뜨고 각자 고쳐도 서로 안 깨집니다. 지금 폴더를 나누는 이 결정이 STEP 2에서 "왜 import가 아니라 requests인가"의 답이 됩니다.

🛠 할 일

다섯 조각으로 나눠 하나씩 보고, 맨 아래에 이어 붙인 전체 명령어를 그대로 복사해 쓰면 됩니다.

① 가상환경 만들기

이 가이드가 들어 있는 project2/ 폴더에서 시작합니다. 폴더는 이미 있으니 만들 필요는 없고, 그 안에 이 프로젝트 전용 파이썬 환경만 새로 깔면 됩니다. P1과 환경을 나눠야 "P2는 무슨 패키지로 도는가"가 pyproject.toml 하나로 정확히 드러납니다.

터미널 B — P2 작업용
# 이 가이드가 들어 있는 폴더로 이동 (docs/의 부모)
cd ~/Documents/langchain-study/langchain-project/project2

# 지금 폴더(.)를 파이썬 프로젝트로 초기화한다. P1 때와 같은 명령이다:
#   pyproject.toml   → 이 프로젝트가 쓰는 패키지 목록
#   .python-version  → 쓸 파이썬 버전
#   .gitignore       → 깃에 올리지 않을 파일 목록 (.env 등)
#   .venv/           → P2 전용 파이썬 환경 (P1과 섞이지 않는 칸막이)
uv init .

② 의존성 설치 — 필요한 시점별로 세 묶음

한 번에 다 깔지만, 어느 패키지가 어느 STEP에서 쓰이는지 알고 넘어가세요. 나중에 ImportError가 났을 때 "아 이건 STEP 7용이었지" 하고 바로 짚을 수 있습니다.

터미널 B
# 1묶음 · Agent 코어 (STEP 1~4에서 사용)
#   langgraph → checkpointer(InMemorySaver)가 여기 들어 있다. langchain이 내부적으로 쓰지만
#               우리가 직접 import 하므로 명시적으로 적어 둔다(의존성은 '쓰는 쪽이 선언'이 원칙)
#   ddgs      → DuckDuckGo 검색. API 키가 필요 없어 바로 쓸 수 있다
#   requests  → STEP 2에서 P1의 HTTP 창구를 두드릴 때 쓴다
uv add langchain langchain-openai langgraph python-dotenv ddgs requests

# 2묶음 · 서빙 · 관측 (STEP 5~6에서 사용)
#   "uvicorn[standard]" 의 따옴표는 필수 — 없으면 셸이 [ ]를 파일이름 패턴으로 오해한다
uv add fastapi "uvicorn[standard]" langfuse

# 3묶음 · Multi-LLM · 평가 (STEP 7~8에서 사용)
uv add langchain-google-genai pandas
패키지쓰이는 곳역할
langchain · langchain-openai1~4create_agent·@tool·미들웨어 + OpenAI 모델 연결
langgraph3InMemorySaver — 대화 세션을 저장하는 checkpointer
ddgs1DuckDuckGo 웹 검색 (API 키 불필요)
requests2P1의 POST /query 호출
python-dotenv전체.env의 키를 환경변수로 로드
fastapi · uvicorn5HTTP API 서버
langfuse6도구 호출·토큰·비용·지연 추적 대시보드
langchain-google-genai7Gemini 모델 연결 (Multi-LLM의 두 번째 축)
pandas8평가 결과 집계·비교표 출력

③ 폴더 구조 잡기 — 파일 하나가 STEP 하나

지금은 빈 파일만 만들어 두고 STEP마다 채웁니다. P1과 달리 data/·chroma_db/가 없다는 점에 주목하세요 — 문서와 벡터DB는 전부 P1이 들고 있고, P2는 그걸 물어보기만 합니다. P2가 이렇게 가벼운 것 자체가 서비스를 분리한 대가로 얻은 이득입니다.

④ .env — 키 준비

P1에서 쓰던 .env를 그대로 복사해 오고, 두 줄만 더합니다. Langfuse 키는 이미 P1에서 발급받았으니 같은 값을 그대로 쓰면 됩니다 — 같은 Langfuse 프로젝트에 P1·P2 트레이스가 함께 쌓여서, 나중에 "이 대화에서 P1 검색이 몇 번 일어났나"를 한 화면에서 볼 수 있습니다.

.env
OPENAI_API_KEY=sk-...

# P1에서 쓰던 값 그대로 복사
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_BASE_URL=https://cloud.langfuse.com

# STEP 2 — P1 서버 주소. 코드에 박지 않고 설정으로 빼 둔다
#          (나중에 P1을 다른 서버에 올려도 이 한 줄만 바꾸면 된다)
P1_API_URL=http://localhost:8000

# STEP 7 — Gemini. 학습용 .env에는 GEMINI_API_KEY로 저장돼 있을 텐데,
#          langchain-google-genai가 찾는 이름은 GOOGLE_API_KEY다. 같은 값을 이 이름으로 넣어 준다.
GOOGLE_API_KEY=AIza...
⚠️ 키 이름이 안 맞아 생기는 흔한 사고

Gemini 키를 분명히 .env에 넣었는데 STEP 7에서 "API key not found"가 나는 일이 자주 있습니다. 원인은 대개 변수 이름이에요 — 라이브러리는 정해진 이름(GOOGLE_API_KEY)만 찾습니다. "키가 없다"는 에러를 보면 키가 진짜 없는 건지, 이름이 다른 건지부터 확인하는 습관을 들이세요.

.gitignore에 .env가 있는지도 꼭 확인하세요. uv init이 보통 넣어 주지만, 없으면 직접 한 줄 추가합니다.

⑤ P1 서버 띄우고 연결 확인

STEP 2부터 P1이 필요합니다. 터미널을 두 개 씁니다 — 하나는 P1 서버를 계속 띄워 두는 용도, 다른 하나는 P2를 만드는 용도. 이 "서버 여러 개를 동시에 띄워 두고 서로 부르게 하는" 감각 자체가 실무 환경 그대로입니다.

터미널 A — P1 전용 (닫지 말고 계속 켜 둠)
cd ~/Documents/langchain-study/langchain-project/project1
uv run uvicorn main:app --reload
터미널 B — 연결 확인
# P1이 살아 있는지 물어본다. {"status":"ok"} 가 나오면 성공
curl http://localhost:8000/health
💡 P1이 없어도 STEP 3부터는 진행됩니다

P1을 아직 안 만들었다면 STEP 2만 건너뛰세요. 도구 3종(날짜·계산·웹검색)만으로도 메모리·가드레일·서빙·관측·Multi-LLM·평가는 전부 그대로 학습할 수 있습니다. 나중에 P1이 준비되면 tools.py에 도구 하나만 추가하면 됩니다 — 그게 도구 구조의 장점이에요.

📄 전체 명령어 (①~③ 한 번에)

cd ~/Documents/langchain-study/langchain-project/project2

# Agent 코어 (STEP 1~4)

uv run python -c "import langchain, langgraph, ddgs, fastapi, langfuse; print('ok')"
# → ok

# 2) P1 서버와 통신이 되는가  (STEP 2를 건너뛸 거라면 이건 생략 가능)
curl http://localhost:8000/health
# → {"status":"ok"}
