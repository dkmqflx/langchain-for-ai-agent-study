3

검색 개선 ① Hybrid (BM25 + Dense)

랭체인 집중 복습(BM25) ⏱ 반나절
🎯 목표

키워드 검색(BM25)과 의미 검색(임베딩)을 앙상블해 검색 누락을 줄인다. 동시에 검색기를 mode 팩토리로 재구성해, 검색 전략을 문자열 하나로 갈아끼울 수 있게 만든다.

🧠 개념

임베딩 검색은 의미는 잘 잡지만 정확한 용어·수치·희귀 단어(조항 번호, 상품명, 고유명사)에 약합니다. BM25는 반대로 정확한 단어 일치에 강합니다. 둘을 EnsembleRetriever로 합치면 서로의 빈틈을 메웁니다 — 04에서 배운 Hybrid RAG. 그리고 get_retriever(mode) 팩토리로 만들어 두면, STEP 7에서 같은 골든셋으로 세 구성을 나란히 채점해 비교할 수 있습니다. 이 "구성요소를 조립·교체 가능하게 만드는" 감각이 토스 공고의 "RAG 구성 요소를 단독으로 설계하고 시스템 수준에서 통합"에 대응하는 훈련입니다.

🛠 할 일

rag.py의 기존 retriever = vs.as_retriever(...) 한 줄을 아래 구조로 교체하고, answer()에 mode 인자를 추가합니다. BM25는 원문 청크가 필요하므로 STEP 1의 build_chunks()를 재사용합니다.

rag.py (retriever → mode 팩토리로 교체)
# ═══════════════════════════════════════════════════════════════════
# STEP 3 · Hybrid 검색: 키워드 검색(BM25) + 의미 검색(임베딩)을 앙상블해 검색 누락을 줄인다.
# 임베딩은 '의미'에 강하나 정확한 용어·수치·희귀 단어(조항번호·상품명 등)에 약하고,
# BM25는 '정확한 단어 일치'에 강하다 → 둘을 합쳐 서로의 빈틈을 메운다.
#
# 동시에 검색기를 'mode 팩토리'로 재구성한다: baseline | hybrid  (STEP 4에서 rerank 추가)
# → STEP 7에서 같은 골든셋으로 세 구성을 나란히 채점해 비교하기 위한 뼈대.
# ═══════════════════════════════════════════════════════════════════
from langchain_community.retrievers import BM25Retriever
from langchain_classic.retrievers import EnsembleRetriever   # ImportError 시: from langchain.retrievers import EnsembleRetriever
from ingest import build_chunks                              # STEP 1의 청크 생성 함수 재사용(BM25는 원문 청크가 필요)

chunks = build_chunks()                # BM25용 원문 청크. 모듈 로드 시 1회만(매 요청 재호출은 느림)

def _build_retriever(mode: str):
    """mode 이름 → 검색기 객체. 검색 전략을 문자열 하나로 갈아끼우는 것이 이 리팩터링의 핵심."""
    dense = vs.as_retriever(search_kwargs={"k": 4})          # 의미(임베딩) 검색 — STEP 2에서 쓰던 것
    if mode == "baseline":
        return dense                                         # STEP 2 그대로: 의미 검색만
    bm25 = BM25Retriever.from_documents(chunks)              # 키워드(단어 빈도) 기반 검색기
    bm25.k = 4                                               # BM25가 돌려줄 청크 수
    if mode == "hybrid":
        # 두 검색기를 가중 앙상블: 각자 top-4를 뽑아 weights로 점수를 섞어 최종 순위를 만든다
        return EnsembleRetriever(retrievers=[bm25, dense], weights=[0.4, 0.6])   # 0.4=BM25, 0.6=의미
    raise ValueError(f"unknown mode: {mode}")

_retrievers = {}                       # 만들어 둔 검색기 캐시(같은 mode를 매번 다시 만들지 않기)
def get_retriever(mode: str = "hybrid"):
    if mode not in _retrievers:
        _retrievers[mode] = _build_retriever(mode)
    return _retrievers[mode]

def answer(question: str, mode: str = "hybrid"):             # mode 인자 추가 — 기본은 hybrid
    """질문 하나를 받아 검색 → 생성 → 근거까지 끝낸 결과 dict를 돌려준다."""
    docs = get_retriever(mode).invoke(question)              # (1) 검색: mode에 해당하는 검색기로
    msg = PROMPT.invoke({"question": question, "context": format_context(docs)})
    resp = llm.invoke(msg)
    return {
        "answer": resp.content,
        "citations": [{"source": d.metadata.get("source"), "page": d.metadata.get("page")} for d in docs],
        "contexts": [d.page_content for d in docs],
    }
💡 팁 build_chunks()를 매 요청마다 부르면 느립니다. 지금은 학습이 목적이니 모듈 로드 시 한 번만 부르면 충분해요(위 코드처럼 파일 상단에서 1회). 성능 최적화는 STEP 8/README의 "개선 아이디어"로 남겨두세요.
✅ 검증 게이트
두 구성을 눈으로 비교 — 정확한 용어·조항 번호가 든 질문으로 baseline과 hybrid의 검색 결과를 나란히 출력해 보세요. 
uv run python - <<'EOF'
from rag import get_retriever
q = "내 문서의 정확한 용어·조항번호가 들어간 질문"   # 여러분의 문서 고유 용어로 바꾸세요
for mode in ["baseline", "hybrid"]:
    print(f"\n--- {mode}")
    for d in get_retriever(mode).invoke(q):
        print(d.metadata.get("page"), "|", d.page_content[:60].replace("\n", " "))
EOF
두 결과가 서로 다르고, 정확한 키워드가 든 질문에서 hybrid가 해당 용어가 포함된 청크를 더 안정적으로 상위에 올리면 통과. (몇 점이나 좋아졌는지의 정량 비교는 STEP 7에서 합니다. weights [0.4, 0.6]을 [0.5, 0.5], [0.3, 0.7]로 바꿔 결과가 어떻게 달라지는지 눈으로 실험해 봐도 좋습니다.)
🎓 배우는 것

EnsembleRetriever 조립 + retriever를 교체 가능한 부품으로 설계하는 랭체인 핵심 감각. 이 mode 팩토리가 STEP 7 비교 실험의 뼈대가 됩니다.
