3-2. 기초 아키텍처 패턴 — Routing

실습 노트북: 1-2.ipynb  ·  대상 범위: 기초 아키텍처 패턴 세 번째 — Routing  ·  난이도: 🟢 입문~초급

기초 아키텍처의 마지막 조각, Routing입니다. 한 문장으로 — 여러 전문가를 미리 만들어 두고, 들어온 일감을 보고 그중 하나에게만 토스한다. 실습으로는 고객 문의를 알아서 담당 부서로 넘겨주는 상담 서비스를 만듭니다.

이 장에서 배우는 것

새 문법은 add_conditional_edges와 with_structured_output 둘뿐입니다. 진짜 주제는 문법이 아니라 "약속" — 라우터가 뱉는 값과 분기 함수가 기대하는 값이 사전에 딱 맞아떨어지도록 강제하는 법입니다.

1. Routing — 상황을 보고 갈 길을 고른다

Routing 그래프는 맨 앞에 "라우터 노드(Router Node)"가 한 명 서 있는 구조입니다. 이 노드는 실제 일을 하지 않고 "이 일은 아래 작업자 중 누구에게 넘겨야 하는가?"만 결정합니다. 그 결정값에 따라 전문가 노드 중 딱 하나만 실행되고, 나머지는 그날 아무 일도 하지 않습니다.

실선과 점선 — 병렬 처리와 딱 하나 다른 점

앞 문서의 Parallelization 그림과 모양이 거의 같지만 선의 종류가 다릅니다. 병렬은 실선이라 전원이 돌고, 라우팅은 점선이라 골라서 돕니다.

구분ParallelizationRouting
상위 → 하위 연결선실선 (add_edge)점선 (add_conditional_edges)
실행되는 작업자전원 예외 없이 다 돈다선택된 1명 나머지는 쉰다
상위 노드의 역할딱히 없음 (START에서 바로 갈라짐)누구에게 줄지 판단하는 게 전부
LLM 호출 횟수작업자 수만큼 (3명이면 3번)라우터 1번 + 전문가 1번 = 2번
🔍 비유 — 회람 vs 이관

Parallelization은 사내 회람 — 공문을 전 부서에 돌리고 의견을 모읍니다. Routing은 이관(移管) — 접수 창구가 민원을 읽고 "이건 세무과 건이네요" 하고 한 부서에만 넘깁니다. 다른 부서는 이 민원의 존재조차 모릅니다.

💡 "하나만"이 아니라 "몇 개만"도 가능합니다

조건부 함수는 노드 이름 리스트를 반환해 여러 노드를 동시에 실행시킬 수도 있습니다. 핵심은 개수가 아니라 "전부 가느냐(실선), 골라서 가느냐(점선)"입니다.

언제 쓰는가 — 대표 사례 세 가지

한 줄 정의 — "입력의 종류가 다양해서, 하나의 프로세스로 처리하기엔 너무 복잡하거나 비효율적일 때." 구체적으로 세 가지 상황입니다.

① 전문화가 필요할 때 (Specialization)

하나의 노드에 환불·기술 지원·제품 안내를 전부 맡기는 대신 전문가를 미리 나눠 두는 것, 즉 노드마다 페르소나(persona)를 따로 심어 두는 것입니다. 같은 모델이라도 "당신은 결제 및 환불 전문가입니다"로 시작하느냐 "당신은 IT 엔지니어입니다"로 시작하느냐에 따라 답변의 결이 완전히 달라집니다.

② 도구(Tool) 선택이 명확해야 할 때

노드마다 연결된 도구가 다를 때도 라우팅이 답입니다. 개인 비서 Agent라면 —

노드연결된 도구이런 요청이 오면
A 노드검색 API"오늘 서울 날씨 어때?"
B 노드캘린더 조회 API"내일 오후 일정 있나?"
C 노드RAG (사내 문서 검색)"작년 휴가 규정이 어떻게 되지?"

③ 모델 최적화 및 비용 절감

노드마다 서로 다른 등급의 언어 모델을 붙여 두는 패턴입니다.

💰 노드별로 모델 등급을 다르게
노드 A → gpt-5        (가장 비싸고 똑똑함)   ← 복잡한 추론·코드 생성
노드 B → gpt-5-mini   (중간)                 ← 일반적인 질의응답
노드 C → gpt-5-nano   (가장 저렴함)          ← 인사말, 단순 분류, 짧은 응답

라우터가 질문의 난이도를 보고 "이 정도면 nano로 충분"이라 판단해 해당 노드만 호출하면, 품질은 지키면서 비용을 확 낮출 수 있습니다.

🔍 비유 — 병원 응급실의 트리아지(triage)

응급실에서 환자를 제일 먼저 만나는 사람은 의사가 아니라 분류 간호사입니다. 치료는 하지 않고 "어느 진료과, 어느 등급인가"만 정하죠. 가벼운 찰과상에 외과 과장님을 붙이지 않듯, 라우터가 정확히 이 역할입니다. 싸고 빠른 모델이 어울리는 자리이기도 합니다. (실습에서도 전부 gpt-5-nano를 씁니다.)

2. 기획 — 고객 응대 서비스

2강에서 배운 기획 순서 그대로 요구사항 → 그래프 → State 순으로 정리하고 코드로 갑니다.

1요구사항

고객 문의를 성격에 맞는 전문가에게 전달

2그래프 구성

라우터 1 + 전문가 4, 조건부 엣지로 연결

3State 설계

질문 · 분류 결과 · 답변 세 칸

기획 2 · 그래프 구성

전문가는 결제/환불 · 기술 지원 · 배송 · 일반 상담 네 명입니다. 일반 상담(general)은 "셋 다 아닐 때 가는 곳" — 조건부 함수에서 안전망 역할을 하니 기억해 두세요.

기획 3 · State 설계 — 칸이 세 개면 충분하다

기준은 2강의 원칙 그대로 — "다음 노드가 읽어야 하는 값이라면 State에 담는다."

필드누가 쓰나누가 읽나왜 필요한가
query 사용자 (invoke 입력) router_node + 전문가 노드 라우터가 읽고 분류하고, 선택된 전문가도 읽고 답변한다
category router_node 조건부 함수 이 값을 보고 어느 노드로 갈지 결정한다
response 선택된 전문가 노드 사용자 (최종 반환) 최종 답변이 담기는 자리
💡 query는 두 번 읽힙니다

State는 모든 노드가 함께 보는 공용 공책이라, 한 번 적힌 값은 라우터도 읽고 전문가도 읽습니다. 몇 번이든 읽을 수 있습니다.

STEP 1. Model 정의

📥 코드
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")

이번엔 temperature를 건드리지 않습니다. 분류는 정확해야 하고 답변은 안정적이어야 하니 기본값 그대로가 맞습니다.

STEP 2. State 정의

📥 코드
from typing import TypedDict

class SupportState(TypedDict):
    query: str          # 고객 질문
    category: str       # 라우터가 분류한 카테고리
    response: str       # 전문가의 답변
💡 response는 네 노드가 공유하는데 왜 리듀서가 없나

1-1에서 "워커 셋이 같은 칸에 동시에 쓰면 에러"라고 배웠지만, 라우팅은 한 번의 실행에서 한 명만 돌기 때문에 충돌이 없습니다. "같은 칸이라서 문제"가 아니라 "동시에 써서 문제"였던 겁니다.

🔑 여기서 한 가지 문제 — category에 뭐가 들어올지 어떻게 믿나

라우터는 결국 언어 모델입니다. "이 문의가 어느 부서 건인지 알려줘"라고 그냥 물으면 —

❌ 그냥 물어봤을 때 — 매번 다른 모양의 대답
"결제 관련 문의로 보입니다."
"billing"
"이 건은 결제/환불 부서에서 처리하는 것이 적절합니다."
"청구 부서"
"Billing Department"

전부 의미상 정답이지만, 이걸 받는 분기 코드는 이렇게 생겼습니다.

💥 그 결과 — 조건문이 전부 빗나간다
if category == 'billing':          # "결제 관련 문의로 보입니다." != 'billing'  → False
    return 'billing_expert'
elif category == 'technical':      # → False
    return 'technical_expert'
elif category == 'shipping':       # → False
    return 'shipping_expert'
else:
    return 'general_expert'        # ← 결제 문의인데 매번 여기로 떨어짐
🚫 문제의 본질 — "약속되지 않은 값"

에러도 안 나고 조용히 전부 일반 상담원에게 흘러갑니다 — 발견하기 제일 어려운 종류의 버그입니다. 해결하려면 라우터가 낼 수 있는 답을 미리 정해진 몇 개로 제한(constrain)해야 합니다.

(복습) 그 방법은 LangChain에서 이미 배웠습니다 — Structured Outputs

LangChain 강의에서 배운 Structured Outputs가 정확히 이 도구입니다. 절차는 두 단계 — ①스키마(class) 생성 → ②model.with_structured_output(스키마)로 결합. 스키마를 물린 모델은 줄글 대신 정해진 필드에, 정해진 타입으로 답을 채워 돌려줍니다.

🔍 비유 — 서술형 답안지 vs OMR 카드

그냥 물어보는 건 백지에 서술형으로 쓰라는 것 — 내용은 훌륭해도 채점 프로그램은 못 읽습니다. with_structured_output은 OMR 카드를 쥐여주는 것입니다. 뒤에 오는 조건부 함수가 바로 그 채점 기계고요.

RouteDecision 스키마 — 답을 네 개로 못 박기

우리 상황에 맞는 스키마입니다. 라우터에게 시킬 일은 분류뿐이니 필드는 category 하나면 충분합니다.

📥 코드
from typing import Literal
from pydantic import BaseModel, Field

class RouteDecision(BaseModel):
    category: Literal['billing', 'technical', 'shipping', 'general'] = Field(
        description='고객 문의 내용을 분석하여 적절한 부서를 선택하세요'
    )

세 부분으로 나눠 봅니다.

Literal['billing', 'technical', 'shipping', 'general'] — 선택지를 못 박는 타입

str은 "문자열이면 뭐든 OK", Literal[...]은 "이 네 개 중 하나여야만 함". 이 정보가 모델에게 그대로 전달되므로 모델은 네 값 외의 답을 낼 수 없습니다. 값 이름은 마음대로 지어도 되지만, 앞으로 만들 노드 이름에 맞춰 두면 나중에 조건부 함수를 읽을 때 바로 이해됩니다.

Field(description=...) — 모델이 실제로 읽는 지시문

description은 사람용 주석이 아니라 스키마와 함께 모델에게 전달되는 판단 기준입니다. 사실상 라우터의 시스템 프롬프트이므로, 분류가 엉뚱하게 나오면 제일 먼저 손볼 곳이 이 문장입니다.

⚠️ 분류 정확도를 올리는 가장 싼 방법

description에 각 카테고리의 판단 기준을 예시와 함께 적어주세요. 예: "billing은 요금·결제·환불, technical은 오류·API·설치 문제, shipping은 배송·주문 조회, 그 외는 general." 모델을 바꾸기 전에 이 문장부터 다듬으세요. 비용 0원짜리 개선입니다.

BaseModel — pydantic이 타입을 지켜준다

혹시 모델이 규칙을 어기고 이상한 값을 내면 pydantic 단계에서 걸러집니다. 모델에게 제한을 알려주고, 결과도 검증하는 이중 안전장치입니다.

router_llm — 스키마가 결합된 모델 객체

📥 코드
router_llm = model.with_structured_output(RouteDecision)

원래 model은 그대로 남고, RouteDecision이라는 답안지가 물린 별도의 모델 객체가 하나 더 생깁니다.

구분modelrouter_llm
.invoke()의 반환 타입AIMessage 객체RouteDecision 객체
본문 꺼내는 법msg.contentdecision.category
답의 자유도무엇이든 줄글로네 값 중 하나
실습에서 쓰는 곳전문가 노드 4개라우터 노드 1개
⚠️ .content를 쓰면 에러가 납니다

router_llm.invoke(...)의 결과는 AIMessage가 아니라 RouteDecision 객체라 .content가 없습니다. State는 딕셔너리라 state["query"]처럼 대괄호, decision은 객체라 decision.category처럼 점(.) — 이 둘을 뒤집어 쓰는 실수가 정말 흔합니다.

STEP 3. Node 정의 — 관제탑 하나 + 전문가 넷

노드의 계약은 언제나 같습니다 — state를 받고, State 양식에 맞는 딕셔너리를 반환한다.

① router_node — 일하지 않고 결정만 하는 노드

📥 코드
# [Manager] router 노드
def router_node(state: SupportState):
    query = state["query"]
    print(f"\n--- [Router] 문의 분석 중: '{query}' ---")

    decision = router_llm.invoke(query)  # LLM이 문맥을 읽고 카테고리를 결정함 (Rule-based가 아님!)

    print(f"   -> 분류 결과: {decision.category.upper()} 부서로 연결합니다.")
    return {"category": decision.category}

query를 꺼내 → router_llm에 넘기고 → .category만 뽑아 → 반환. 답변을 만들지 않고 오직 분류만 합니다.

주석의 "Rule-based가 아님!"이 왜 중요한가

전통적인 방식이라면 이 분류를 키워드 매칭으로 했을 겁니다.

🕰️ 옛날 방식 — 키워드 규칙
if '환불' in query or '결제' in query:
    category = 'billing'
elif '에러' in query or '오류' in query:
    category = 'technical'
# ...

이 방식은 "지난달 요금이 두 번 빠져나갔어요"에서 무너집니다 — '환불'도 '결제'도 없으니까요. LLM 라우터는 키워드가 아니라 문맥을 읽어 "요금이 두 번 빠져나갔다 = 중복 청구 = 결제 부서"라는 추론을 합니다.

🔍 비유 — ARS와 사람 상담원

Rule-based 라우팅은 ARS — 고객이 미리 정해진 단어를 정확히 말해야만 작동합니다. LLM 라우팅은 사람 상담원 — 두서없이 설명해도 "아, 중복 결제 건이시군요" 하고 알아듣고 담당자에게 넘깁니다. 이 차이 때문에 라우터 자리에 LLM을 세웁니다.

💡 print는 장식이 아닙니다

조건부 엣지는 실행되지 않은 노드에 대해 아무 흔적도 남기지 않으므로, 라우터에 분류 결과를, 전문가 노드에 자기 이름을 찍어두면 로그만으로 경로가 보입니다. 라우팅 디버깅의 90%는 이 print 두 줄로 끝납니다.

② 전문가 노드 4종 — 같은 모델, 다른 페르소나

📥 코드
# [Expert A] 결제/환불 담당
def billing_expert(state: SupportState):
    print("--- [Billing Expert] 결제 전문가가 답변 작성 중 ---")
    prompt = f"당신은 결제 및 환불 전문가입니다. 다음 문의에 대해 정중하게 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

# [Expert B] 기술 지원 담당
def technical_expert(state: SupportState):
    print("--- [Tech Expert] 기술 지원 엔지니어가 분석 중 ---")
    prompt = f"당신은 IT 엔지니어입니다. 다음 기술 문제에 대해 해결책을 제시하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

# [Expert C] 배송 담당
def shipping_expert(state: SupportState):
    print("--- [Shipping Expert] 물류 담당자가 배송 조회 중 ---")
    prompt = f"당신은 배송 관리자입니다. 다음 배송 문의에 대해 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

# [Expert D] 일반 상담
def general_expert(state: SupportState):
    print("--- [General] 일반 상담원이 답변 중 ---")
    msg = model.invoke(f"다음 문의에 친절하게 답변하세요: {state['query']}")
    return {"response": msg.content}

네 함수의 차이는 페르소나 문장과 print 라벨 딱 두 군데뿐이고, 모델도 같은 model 하나를 공유합니다. 배우 한 명에게 매번 다른 배역을 주는 셈입니다.

💡 노드마다 다른 모델을 붙이면 — 그게 ③번 사례입니다

technical_expert만 model_pro = init_chat_model("gpt-5")를 쓰게 하면 어려운 기술 문의에만 비싼 모델이 투입되는 비용 최적화 그래프가 됩니다. 그래프 구조는 한 줄도 안 바꾸고요.

STEP 4. 그래프 생성

먼저 노드 등록과 확실한 엣지(START → 라우터)부터 긋습니다.

📥 코드
workflow = StateGraph(SupportState)

# 노드 등록
workflow.add_node("router_node", router_node)
workflow.add_node("billing_expert", billing_expert)
workflow.add_node("technical_expert", technical_expert)
workflow.add_node("shipping_expert", shipping_expert)
workflow.add_node("general_expert", general_expert)

# 엣지 연결
workflow.add_edge(START, "router_node")

노드는 다섯 개인데 엣지는 한 줄 — 라우터 아래는 실행해 봐야 아는 길이라서입니다. 이제 그 부분을 만듭니다.

조건부 함수 route_to_expert — 갈림길의 판단 기준

📥 코드
# 조건부 엣지를 위한 함수
def route_to_expert(state: SupportState):
    category = state['category']

    if category == 'billing':
        return 'billing_expert'
    elif category == 'technical':
        return 'technical_expert'
    elif category == 'shipping':
        return 'shipping_expert'
    else:
        return 'general_expert'
⚠️ 이 함수는 노드가 아닙니다

노드는 딕셔너리를 반환해 State를 바꾸고, 조건부 함수는 문자열을 반환해 길을 정합니다. 그래서 add_node로 등록하지 않고, 그래프 그림에도 안 나옵니다. 화살표 위에 붙은 이정표 같은 존재입니다.

반환값을 왜 'billing'이 아니라 'billing_expert'로 맞췄나

비교 — 두 가지 스타일
# 스타일 A) 반환값 = 노드 이름  → 리스트만 넘기면 끝  ★ 실습에서 쓰는 방식
return 'billing_expert'
workflow.add_conditional_edges('router_node', route_to_expert,
                               ['billing_expert', 'technical_expert', ...])

# 스타일 B) 반환값 = 카테고리   → 매핑 딕셔너리가 필요함
return 'billing'
workflow.add_conditional_edges('router_node', route_to_expert,
                               {'billing': 'billing_expert',
                                'technical': 'technical_expert', ...})

조건부 함수의 반환값을 등록한 노드 이름과 똑같이 맞춰두면 코드가 짧아지고 연결 실수도 줄어듭니다. 그리고 마지막이 elif가 아니라 else인 것도 포인트 — 예상 못 한 값이 들어와도 그래프가 멈추지 않는 안전망입니다. 라우팅 함수에는 항상 else로 기본 경로를 두세요.

add_conditional_edges — 점선 네 개를 한 번에 긋기

📥 코드
workflow.add_conditional_edges(
    'router_node',
    route_to_expert,
    ['billing_expert', 'technical_expert', 'shipping_expert', 'general_expert']
)

인자 세 개를 문장으로 읽으면 — "router_node가 끝나면, route_to_expert를 돌려서, 이 넷 중 하나로 간다."

💡 세 번째 인자는 왜 필요한가 — 사실 "그림"을 위한 것

생략해도 실행은 되지만, LangGraph가 라우터의 행선지를 미리 알 수 없어 그래프 그림에 점선이 제대로 그려지지 않습니다. 명시하면 그림도 정확해지고 오타도 조기에 잡힙니다.

마지막 — 전문가들을 END로 모으기

📥 코드
workflow.add_edge('billing_expert', END)
workflow.add_edge('technical_expert', END)
workflow.add_edge('shipping_expert', END)
workflow.add_edge('general_expert', END)

app = workflow.compile()

어느 전문가가 일하든 끝나면 무조건 END라 고를 것이 없으니 실선입니다. 모양은 병렬의 Fan-in과 같지만, 여기 END는 기다리지 않습니다 — 도착하는 노드가 한 명뿐이니까요.

📥 코드
app
📤 출력 — 기획서와 같은 모양인지 눈으로 확인
              __start__
                  │           (실선)
             router_node
        ┌────┬─────┴─────┬────┐   (점선 = 조건부)
   billing  general  shipping  technical
        └────┴─────┬─────┴────┘   (실선)
                __end__

키워드 매칭이었다면 IT 제품인 "노트북" 때문에 technical로 갈 뻔했지만, 라우터는 "주문한 ~ 언제 도착하나요"라는 문장 전체의 의도를 읽고 배송 건으로 판단했습니다. 이게 LLM 라우터를 쓰는 이유입니다.

State(공책)가 채워지는 과정 — 케이스 1 기준

START

{'query': '지난달 요금이 두 번 빠져나갔어요...'}
category·response 두 칸은 비어 있음

router_node

query를 읽음 → router_llm 호출 → category 칸에 'billing' 기록
답변은 아직 한 글자도 없음

route_to_expert

(노드가 아님 · State를 바꾸지 않음)
category == 'billing' → 문자열 'billing_expert' 반환 → 길만 정함

"안녕하세요. 불편을 겪게 해드려 정말 죄송합니다..."

(나머지 3개 노드)

END

세 칸이 모두 찬 State 전체가 반환됨 — query · category · response

🔍 비유 — 민원 접수증 한 장이 돌아다닌다

State는 민원실 접수증입니다. 고객이 [민원 내용] 칸을 채워 제출하면, 접수 담당자가 [담당 부서] 칸에 도장을 찍고, 결제팀 직원이 [처리 결과] 칸을 채워 돌려주죠. 종이는 처음부터 끝까지 한 장 — 여러 사람이 자기 칸만 채워 나갈 뿐입니다.

전체 코드 한눈에 보기

# ══ STEP 1. Model ═════════════════════════════════════
from langchain.chat_models import init_chat_model
from langgraph.graph import StateGraph, START, END

model = init_chat_model("gpt-5-nano")

# ══ STEP 2. State ═════════════════════════════════════
from typing import TypedDict

class SupportState(TypedDict):
    query: str          # 고객 질문
    category: str       # 라우터가 분류한 카테고리
    response: str       # 전문가의 답변

# ══ 라우터의 답을 4개로 못 박는 스키마 ═══════════════════
from typing import Literal
from pydantic import BaseModel, Field

class RouteDecision(BaseModel):
    category: Literal['billing', 'technical', 'shipping', 'general'] = Field(
        description='고객 문의 내용을 분석하여 적절한 부서를 선택하세요'
    )

router_llm = model.with_structured_output(RouteDecision)   # ★ 이 한 줄이 라우팅의 안전벨트

# ══ STEP 3. Node ══════════════════════════════════════
# [Manager] 분류만 하고 답변은 하지 않는 노드
def router_node(state: SupportState):
    query = state["query"]
    print(f"\n--- [Router] 문의 분석 중: '{query}' ---")
    decision = router_llm.invoke(query)        # ★ 반환 타입은 AIMessage가 아니라 RouteDecision
    print(f"   -> 분류 결과: {decision.category.upper()} 부서로 연결합니다.")
    return {"category": decision.category}     # ★ 점(.)으로 접근

# [Expert A~D] 페르소나만 다르고 구조는 동일
def billing_expert(state: SupportState):
    print("--- [Billing Expert] 결제 전문가가 답변 작성 중 ---")
    prompt = f"당신은 결제 및 환불 전문가입니다. 다음 문의에 대해 정중하게 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

def technical_expert(state: SupportState):
    print("--- [Tech Expert] 기술 지원 엔지니어가 분석 중 ---")
    prompt = f"당신은 IT 엔지니어입니다. 다음 기술 문제에 대해 해결책을 제시하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

def shipping_expert(state: SupportState):
    print("--- [Shipping Expert] 물류 담당자가 배송 조회 중 ---")
    prompt = f"당신은 배송 관리자입니다. 다음 배송 문의에 대해 답변하세요: {state['query']}"
    msg = model.invoke(prompt)
    return {"response": msg.content}

def general_expert(state: SupportState):
    print("--- [General] 일반 상담원이 답변 중 ---")
    msg = model.invoke(f"다음 문의에 친절하게 답변하세요: {state['query']}")
    return {"response": msg.content}

# ══ STEP 4. Graph ═════════════════════════════════════
workflow = StateGraph(SupportState)

workflow.add_node("router_node", router_node)
workflow.add_node("billing_expert", billing_expert)
workflow.add_node("technical_expert", technical_expert)
workflow.add_node("shipping_expert", shipping_expert)
workflow.add_node("general_expert", general_expert)

workflow.add_edge(START, "router_node")        # 실선 — 무조건 라우터부터

# 조건부 함수: State를 읽고 '갈 노드의 이름'을 문자열로 반환
def route_to_expert(state: SupportState):
    category = state['category']
    if category == 'billing':
        return 'billing_expert'
    elif category == 'technical':
        return 'technical_expert'
    elif category == 'shipping':
        return 'shipping_expert'
    else:                                      # ★ 안전망
        return 'general_expert'

# 점선 — 넷 중 하나로만 간다
workflow.add_conditional_edges(
    'router_node',
    route_to_expert,
    ['billing_expert', 'technical_expert', 'shipping_expert', 'general_expert']
)

# 실선 — 누가 일했든 끝나면 END
workflow.add_edge('billing_expert', END)
workflow.add_edge('technical_expert', END)
workflow.add_edge('shipping_expert', END)
workflow.add_edge('general_expert', END)

app = workflow.compile()

# ══ STEP 5. Run ═══════════════════════════════════════
app.invoke({"query": "지난달 요금이 두 번 빠져나갔어요. 확인해주세요."})   # → billing
app.invoke({"query": "API 연결할 때 404 에러가 자꾸 떠요."})              # → technical
app.invoke({"query": "주문한 노트북 언제 도착하나요?"})                    # → shipping

자주 걸리는 함정 6가지

🕳️ 라우팅에서 실제로 밟게 되는 지뢰

1. 라우터를 그냥 model로 호출한다

router_llm이 아니라 model.invoke(query)를 쓰면 줄글 답변이 나와 조건문이 전부 빗나가고, 에러 없이 조용히 general_expert로만 흘러갑니다. "분류가 다 general로 나온다"면 제일 먼저 이 줄을 의심하세요.

2. decision.content라고 쓴다

router_llm.invoke()는 RouteDecision 객체를 반환하므로 .content가 없습니다. decision.category가 맞습니다. State는 대괄호, 스키마 객체는 점(.)으로 기억하세요.

3. 조건부 함수의 반환값과 노드 이름이 어긋난다

add_node("billing_expert", ...)로 등록해놓고 return 'billing'을 하면 "그런 노드 없다"는 에러가 납니다. 등록한 이름과 반환값을 똑같이 맞추는 게 가장 안전합니다.

4. 조건부 함수를 add_node로 등록한다

route_to_expert는 노드가 아닙니다. 등록하면 문자열을 State로 병합하려다 엉뚱한 에러가 납니다.

5. 전문가 → END 엣지를 빠뜨린다

네 개를 복사하다 하나를 빼먹으면 그 부서로 분류된 문의에서만 그래프가 이상하게 끝납니다 — 가장 재현하기 어려운 종류의 버그입니다. 컴파일 후 그래프 그림에서 END로 들어오는 화살표 개수를 세어보세요.

6. description을 대충 쓰고 모델 탓을 한다

분류가 자꾸 틀리면 Field(description=...)부터 보세요. 이 문장이 라우터의 유일한 판단 기준입니다. 카테고리별 예시 한 줄씩으로 정확도가 눈에 띄게 올라갑니다.

💡 디버깅 요령 — 라우팅만 따로 떼어 테스트하세요

router_llm.invoke("어떤 문의")만 단독으로 여러 번 호출하면 분류가 안정적인지 몇 초 만에 확인할 수 있습니다. 라우팅 그래프의 품질은 사실상 이 한 줄이 결정합니다.

📚 한 장 정리

오늘의 핵심 한 문장

라우터가 반환할 값을 미리 약속된 몇 개로 제한해야 조건부 함수가 그 약속에 따라 안정적으로 분기할 수 있다 — 그 제한을 거는 문법이 with_structured_output이다.

  • Routing이란 — 라우터 노드가 누구에게 줄지만 결정하고, 전문가 중 선택된 하나만 실행되는 구조.
  • 병렬과의 결정적 차이는 선의 종류 — 실선(add_edge) = 전원 실행, 점선(add_conditional_edges) = 골라서 실행.
  • 쓰는 신호 3가지 — ①전문화(노드마다 페르소나) · ②도구 선택(노드마다 다른 도구) · ③비용 절감(노드마다 다른 모델 등급).
  • State는 세 칸 — query(입력) · category(라우터의 결정) · response(전문가의 답). response는 네 노드가 공유하지만 동시에 쓰지 않아 리듀서가 필요 없다.
  • 이 장의 심장 — Literal + with_structured_output — Literal[...]로 선택지를 못 박고, Field(description=...)에 판단 기준을 적고, with_structured_output으로 답안지를 물린다. 반환값은 AIMessage가 아니므로 .content가 아니라 .category.
  • 조건부 함수는 노드가 아니다 — 문자열(갈 노드의 이름)을 반환한다. 반환값을 노드 이름과 맞추고, 마지막은 항상 else로 기본 경로를 둔다.
  • LLM 라우터는 키워드가 아니라 문맥을 읽는다 — '결제'라는 단어가 없어도 billing으로, '노트북'이 있어도 shipping으로. Rule-based로는 불가능한 판단이다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

민원실 접수 창구의 도장이 매번 "결제팀", "청구 부서", "아마 결제 쪽일 듯"처럼 다르게 찍히면 뒤에서 분류하는 사람이 일을 못 합니다. 그래서 도장 네 개만 만들어 두고 그중 하나만 찍게 합니다 — 그 도장통이 Literal이고, 도장통을 쥐여주는 행위가 with_structured_output입니다.
