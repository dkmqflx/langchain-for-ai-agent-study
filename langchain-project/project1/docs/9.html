① 문제 정의 — "왜 만들었나"를 한 문단

읽는 사람이 가장 먼저 알고 싶은 건 어떻게 만들었나가 아니라 왜 이게 필요한가입니다. "RAG를 공부하려고 만들었다"는 튜토리얼이고, "약관은 조항이 길고 흩어져 있어 사람이 찾기 어렵고, 틀리면 분쟁이 되므로 근거가 함께 나와야 한다"는 문제 해결입니다. 같은 코드라도 이 한 문단이 인상을 가릅니다.

② 아키텍처 — 데이터가 흐르는 순서대로

기술 이름을 나열하지 말고 흐름으로 적으세요. Load→Split→Embed→Store → mode 팩토리 → 생성(+citation) → FastAPI처럼요. 읽는 사람이 어디를 갈아끼울 수 있는 구조인지 알아볼 수 있으면 성공입니다. 관측(Langfuse)과 평가(RAGAS)는 특정 단계가 아니라 전체를 가로지르는 층이라 따로 적습니다.

③ 결과 — 이 프로젝트의 핵심

여기가 튜토리얼과 갈리는 지점입니다. STEP 7에서 만든 세 구성 비교표를 그대로 붙이세요. "검색 품질을 개선했다"는 누구나 쓸 수 있지만, "context_recall 0.72 → 0.89"는 실제로 측정한 사람만 쓸 수 있습니다.

💡 안 오른 지표도 그대로 쓰세요

모든 칸이 올라간 표는 오히려 의심스럽습니다(보통 recall과 precision은 반대로 움직이니까요). 내려간 숫자를 적고 "왜 그런지, 그럼에도 왜 이 설정을 골랐는지"를 한 줄 붙이는 편이 훨씬 신뢰를 줍니다. STEP 8에서 이미 그 판단을 해뒀다면 그대로 옮기면 됩니다.

④ 실행 방법 — 처음 보는 사람이 그대로 따라 되게

내 컴퓨터에서만 되는 프로젝트는 없는 것과 같습니다. .env에 무엇이 필요한지, data/에 뭘 넣어야 하는지까지 적으세요. 빈 폴더에서 이 순서대로 따라 해보는 것이 가장 확실한 점검입니다 — 보통 "당연해서 안 적은 한 줄"에서 막힙니다.

⑤ 배운 점 · 개선 아이디어 — 다음에 뭘 할지 아는 사람

못 한 것을 적는 칸입니다. 감추는 게 아니라 "한계를 알고 있다"를 보여주는 자리예요. 지금 이 프로젝트라면 예컨대 이런 것들이 있습니다 — build_chunks()를 실행할 때마다 부르는 대신 캐싱하기, 인제스천을 여러 번 돌려도 중복이 안 쌓이게 만들기, 스캔본 PDF를 위한 OCR 붙이기. 마지막으로 "코퍼스만 바꾸면 다른 도메인에 그대로 재사용된다"는 한 줄은 꼭 넣으세요 — 범용 부품을 만들었다는 뜻이니까요.

# P1 · RAG 문서 검색 서비스

## 문제 정의
- (어떤 도메인 문서에 대한 정확한 QA가 왜 필요한지)

## 아키텍처
- Load→Split→Embed→Store → mode 팩토리(baseline/hybrid/rerank) → 생성(+citation) → FastAPI
- 관측: Langfuse / 평가: RAGAS

## 결과 (정량)
| 설정 | faithfulness | context_precision | context_recall |
|---|---|---|---|
| baseline | 0.xx | 0.xx | 0.xx |
| + hybrid | 0.xx | 0.xx | 0.xx |
| + hybrid + rerank | 0.xx | 0.xx | 0.xx |

## 실행 방법
1. uv sync
2. data/ 에 PDF 넣기 → uv run python ingest.py
3. uv run uvicorn main:app --reload

## 배운 점 / 개선 아이디어
- (검색 품질을 무엇으로, 얼마나 개선했는지 / 다음에 할 것)
- 코퍼스만 교체하면 다른 도메인(의료·사내 문서 등)에 그대로 재사용 가능
📝 이력서 3문장 템플릿 (토스 가이드 반영: 목적→접근→정량결과)

"목적 — (내 도메인) 문서에 대한 정확한 근거 기반 QA가 필요했다. 접근 — LangChain으로 검색기를 baseline→Hybrid→Reranker로 교체 가능하게 설계하고, FastAPI로 서빙, RAGAS로 세 구성을 정량 비교했다. 결과 — context_recall 0.72 → 0.89, faithfulness 0.81 → 0.93으로 향상했고 Langfuse로 전 과정을 추적했다."

✅ 최종 검증 게이트 (= 완성 정의) 맨 위 Definition of Done의 5개 항목에 모두 ✅. 그러면 Project 1은 완성이고, 아래 실무 감각이 손에 남습니다: 검색기 조립·교체 설계 · RAG 서빙 · 관측성 · 정량 평가.
