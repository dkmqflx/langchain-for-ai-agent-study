LangGraph 학습 전, 실무 프로젝트 3선

대상: LangChain 01~04를 마친 사람  ·  기간: 약 5~6주  ·  목적: AI Engineer 지원 포트폴리오  ·  난이도: 🟢 → 🟡 → 🔴

LangChain 기초 과정(01 입문 · 02 Agent 기초 · 03 Advanced Agent · 04 RAG)을 마치면 "돌아가는 데모"는 만들 수 있습니다. 이 페이지는 그 데모를 서비스로 띄우고, 품질을 숫자로 재고, 실행을 추적하는 수준까지 끌어올리는 프로젝트 3개(RAG → Agent → 평가)의 로드맵입니다. 세 개가 끝나면 LangGraph로 넘어갑니다.

왜 이 3개인가

지원하려는 세 공고(토스플레이스 · 토스 · 카카오헬스케어)는 표현만 다를 뿐 같은 것을 묻습니다. "AI 로직을 만들 줄 아느냐"가 아니라, 만든 것을 서비스에 올리고(서빙), 품질을 지표로 관리하고(평가), 안에서 무슨 일이 벌어지는지 볼 수 있느냐(관측성)입니다. LangChain 과정에서 배운 것은 앞쪽 "만들기"이고, 뒤쪽 세 가지는 아직 비어 있습니다.

🍳 비유 레시피대로 한 접시를 만드는 법(LangChain)은 배웠지만, 식당을 열려면 주문 창구(FastAPI), 손님 평가표(RAGAS·LLM-as-judge), 주방 CCTV(Langfuse)가 필요합니다. 세 프로젝트는 이 셋을 하나씩 붙이는 연습입니다.

⚠️ 새 프레임워크 공부가 아닙니다 뼈대는 전부 이미 배운 LangChain(Tool · Memory · Guardrails · RAG)이고, 위 도구는 그걸 감싸는 얇은 층입니다. 각각 반나절이면 익힙니다. Multi-Agent는 일부러 뺐습니다 — 그 제자리는 LangGraph이기 때문입니다.

프로젝트 로드맵

각 프로젝트는 LangChain 과정의 한 챕터를 총정리하면서 위 도구를 얹습니다. P1은 04 RAG, P2는 02·03 Agent를 각각 "돌아가는 것 → 측정·운영되는 것"으로 승격시키고, P3는 그 둘을 시험 대상으로 삼는 평가 인프라를 만듭니다. P3가 P1·P2를 필요로 하므로 순서는 고정입니다.

P1
프로덕션급 RAG 문서 검색 서비스🟢 입문·복습 · 1~2주

내 문서에 질문하면 근거와 함께 답하는 API. 검색 품질을 세 구성으로 비교해 숫자로 개선한다.

P2
관측 가능한 Agent API 서비스🟡 중급 · 1~2주

도구·메모리·가드레일을 갖춘 Agent를 API로. 실행 전체를 추적하고, LLM을 갈아 끼우고, 프롬프트를 채점한다.

P3
LLM/Agent 평가·관측성 하네스🔴 심화·인프라 · 2주

P1·P2를 시험 대상으로, 설정을 바꿀 때마다 품질을 자동 측정하고 나빠지면 잡아내는 회귀 테스트 인프라.

P1 · 프로덕션급 RAG 문서 검색 서비스

🟢 입문·복습 ⏱ 1~2주 복습 챕터: 04 RAG
📋 단계별 가이드 실제 코드는 STEP 0 → 9 순서로 따라가면 됩니다 → Project 1 가이드 열기

무엇을 만드나

PDF 같은 문서 묶음에 질문하면 답변과 함께 근거 문단·출처를 돌려주는 검색 서비스입니다. 04 RAG에서 만든 Load → Split → Embed → Store → Retrieve 파이프라인이 뼈대이고, 여기에 세 가지를 더합니다. 검색기를 Hybrid(키워드+벡터) → Reranker로 두 번 개선하고, FastAPI로 API를 열고, RAGAS로 baseline · hybrid · rerank 세 구성을 같은 평가셋에서 비교합니다. 끝나면 "context recall 0.72 → 0.89"처럼 before/after 지표 표가 손에 남습니다.

문서 선택 팁 — 카카오헬스케어를 노린다면 공개 의료 문서(질병관리청 가이드라인, 의약품 설명서 등), 토스라면 "어떤 문서셋에도 꽂아 쓰는 재사용 컴포넌트" 관점으로 잡으면 공고 서사가 살아납니다.

만드는 순서 (가이드 STEP과 동일)

  1. STEP 1문서 인제스천 — Load → Split → Embed → Chroma 저장 검증: 저장된 청크 수 출력 + 임의 질의로 유사 청크 top-k 확인
  2. STEP 2검색 + 생성 + 근거 — 질문 → 관련 청크 → 답변 + citation 검증: 답변과 근거 청크·출처가 함께 나옴
  3. STEP 3~4검색 개선 — Hybrid(BM25 + 벡터) → Cross-Encoder Reranker로 상위 문서 재정렬 검증: 같은 질문에 상위 문서 순서가 달라지는 것을 눈으로 확인
  4. STEP 5FastAPI POST /query 서빙 검증: curl로 질문을 보내면 답변 + citation 배열이 JSON으로 옴
  5. STEP 6Langfuse 연동 — 요청 1건 = 트레이스 1건 검증: 대시보드에서 retrieval / generation span과 토큰·지연이 보임
  6. STEP 7골든 평가셋(20~50 Q/A) + RAGAS로 세 구성 비교 검증: faithfulness · answer relevancy · context precision · recall 표에서 rerank가 baseline보다 상승
  7. STEP 8~9(선택) chunk size · top-k 튜닝, README 정리 검증: 파라미터별 지표 로그와 최적값 선택 근거가 README에 남음

새로 익히는 것

FastAPI Langfuse RAGAS rank_bm25 · Cross-Encoder Reranker LangChain loader / splitter / retriever (복습) Chroma (복습)

P2 · 관측 가능한 Agent API 서비스

🟡 중급 ⏱ 1~2주 복습 챕터: 02 · 03 Agent
📋 단계별 가이드 실제 코드는 STEP 0 → 9 순서로 따라가면 됩니다 → Project 2 가이드 열기

무엇을 만드나

웹 검색 · 계산 · 날짜 · P1 문서 검색 네 가지 도구를 가진 업무 비서 Agent를 FastAPI로 서빙합니다. 세션마다 대화를 기억하고(Memory), 위험한 입력은 막고(Guardrails), 답은 정해진 형식으로 내놓습니다(Structured Output) — 전부 02·03에서 배운 조각들의 조립입니다. 그 위에 P1과 다른 세 가지를 얹습니다. Langfuse로 Tool 호출 하나하나까지 추적하고, OpenAI ↔ Anthropic을 설정으로 갈아 끼우고, 프롬프트 A와 B 중 어느 쪽이 나은지 LLM-as-judge로 채점합니다. P1을 도구로 재사용하면서 "시스템을 조립한다"는 감각이 생깁니다.

만드는 순서 (가이드 STEP과 동일)

  1. STEP 1~2Agent 코어 — 도구 3종 + 첫 Agent, 그리고 P1의 RAG를 네 번째 도구로 장착 검증: 질문 종류에 따라 알맞은 도구를 고르는 것이 로그에 보임
  2. STEP 3Memory — 세션별 멀티턴 대화 검증: 두 번째 요청이 첫 요청의 맥락을 기억함
  3. STEP 4Guardrails + Structured Output 검증: 금지 입력은 차단되고, 응답은 정해진 스키마로 옴
  4. STEP 5FastAPI POST /chat (+ SSE 스트리밍) 검증: curl로 같은 thread_id를 보내면 멀티턴이 이어짐
  5. STEP 6Langfuse 연동 검증: 대시보드에 Tool 호출 / 토큰 / 비용 span이 트리로 보임
  6. STEP 7Multi-LLM Provider 추상화 검증: 같은 질문을 OpenAI · Anthropic으로 각각 실행해 응답·비용 비교
  7. STEP 8프롬프트 A/B 평가 하네스 (LLM-as-judge, 케이스 10~20개) 검증: 프롬프트 A/B의 정확도 · 형식 준수 점수표 출력
  8. STEP 9README 정리 검증: 문제 정의 · 아키텍처 · 점수표 · 배운 점이 README에 남음

새로 익히는 것

Multi-LLM Provider 추상화 LLM-as-judge 평가 스크립트 SSE 스트리밍 FastAPI · Langfuse (P1에서 익힌 것 재적용) LangChain Agent / Memory / Middleware (복습)

P3 · LLM/Agent 평가·관측성 하네스

🔴 심화 · 인프라 관점 ⏱ 2주 단계별 가이드 준비 중

무엇을 만드나

P1(RAG)과 P2(Agent)를 시험 대상(system under test)으로 놓고, 프롬프트·모델·검색 설정을 바꿀 때마다 한 번의 실행으로 지표를 뽑고 지난 결과와 비교해 나빠졌으면 알려 주는 평가 파이프라인입니다. P1·P2에서 평가는 마지막 한 단계였지만, P3에서는 평가 자체가 주인공입니다. "만드는 능력"과 구별되는 "품질을 지표로 관리하는 능력"을 증명하는 프로젝트라서 세 개 중 가장 강력하고, 토스 공고의 "정량 평가 기반을 플랫폼으로 제공"에 정면으로 대응합니다.

🧪 비유 일반 코드에 테스트 스위트와 CI가 있듯, LLM 앱에도 "이번 변경으로 답변 품질이 떨어지지 않았나"를 자동으로 묻는 회귀 테스트를 두는 것입니다. 한 번 만들어 두면 이후 LangGraph로 만드는 모든 것의 품질 게이트로 그대로 씁니다.

만드는 순서

  1. 골든 평가셋 v1 — 질문 · 기대 답 · 기대 근거를 RAG용 / Agent용으로 나눠 버전 관리 (각 20~50 케이스) 검증: 케이스 스키마 검증 통과 + 버전 태그 부여
  2. 평가 러너 — P1/P2를 호출해 RAGAS 지표 · task success · Tool 선택 정확도 · 형식 준수를 자동 산출 검증: 명령 한 번에 지표 표가 숫자로 출력됨
  3. LLM-as-judge 정성 평가 + judge 신뢰도 점검 검증: 내가 손으로 라벨한 소수 케이스와 judge 점수의 일치율 확인
  4. 실험 비교(A/B) + 회귀 감지 — "이번 변경이 지난 베이스라인보다 떨어졌는가" 검증: 일부러 나쁜 프롬프트를 넣으면 회귀로 잡힘
  5. Langfuse 통합 — dataset · score 기록, trace ↔ eval 연결, 비용·지연도 지표화 검증: 대시보드에서 실행별 점수 추이와 비용이 보임
  6. 자동 리포트 — 실행마다 지표 표 + 회귀 하이라이트 파일 생성 검증: 실행 후 리포트 파일이 생김
  7. (선택) CI에 평가 붙이기 검증: 커밋 시 임계값 미달이면 경고 / 실패

새로 익히는 것

평가셋 설계 · 버전 관리 judge 신뢰도 검증 회귀 평가 설계 Langfuse datasets · scores pandas 집계 · 리포트 pytest / CI 훅 (선택) OpenTelemetry (선택 · 카카오 우대)

이력서·면접용 서술 팁

토스 이력서 가이드는 "어떤 기술을 썼는지"보다 어떤 목적의 과제였고, 무엇으로, 어떻게 해결했는지를 원합니다. 각 프로젝트를 목적 → 접근 → 정량 결과(before/after) 세 문장으로 정리하세요.

  • 숫자로 말하기 — "잘 됐다"가 아니라 "context recall 0.72 → 0.89", "프롬프트 B가 정확도 +14%p". RAGAS · Langfuse 지표가 근거가 됩니다.
  • 과정을 남기기 — baseline → 개선 순서의 커밋 히스토리와, 문제 정의 · 아키텍처 · 지표 표 · 배운 점을 담은 README가 "실험→개선을 해봤다"의 증거입니다.
  • 공고별 한 줄 맞춤 — 카카오는 P1을 의료 문서로 돌려 "의료 정보 검색 정확도" 서사를, 토스플레이스는 P2의 Multi-LLM 스위칭을 "Model Router를 축소판부터 단계적으로 키웠다"로 서술하세요.
