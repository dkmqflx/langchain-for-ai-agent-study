10. Long-term Memory — Agent 메모리 주입

실습 노트북: 10.ipynb  ·  원문: docs/03.advanced-agent.md  ·  난이도: 🟡 중급  ·  선행: 09. Store 기본 CRUD

이 자료는 실습 노트북(10.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 09번에서는 Store라는 창고에 기억을 넣고 꺼내는 법(CRUD)만 배웠습니다. 하지만 창고에 기억을 넣어둔다고 Agent가 저절로 그걸 참고하지는 않습니다. 이번 노트북의 핵심은 "창고에 있는 장기기억을 매 대화마다 Agent의 눈앞에 자동으로 갖다 놓는" 연결 고리 — 바로 미들웨어(middleware) 방식의 메모리 주입입니다.

🔍 비유 — 냉장고에 재료는 있는데 요리사가 안 본다 09번에서 우리는 냉장고(Store)에 좋은 재료(사용자 정보)를 차곡차곡 넣어뒀습니다. 그런데 요리사(LLM)는 냉장고 문을 열어볼 생각을 안 합니다. 눈앞에 놓인 주문서만 보고 요리하죠. 그래서 누군가가 매번 주문이 들어올 때마다 냉장고를 열어 재료를 꺼내 조리대 위에 올려줘야 합니다. 이번 노트북의 inject_memory 미들웨어가 바로 그 재료 담당 스태프예요.
이 노트북에서 배우는 것 Store에 저장된 장기기억을, LLM을 호출하기 직전에 가로채서 system_prompt(감독의 지시문)에 슬쩍 끼워 넣는 방법을 배웁니다. 그러면 LLM은 마치 사용자를 오래 알고 지낸 것처럼 "당신은 커피보다 차를 좋아하시죠"라고 답할 수 있습니다.

단기기억(09까지) vs 장기기억(이번 장)

구분단기기억 (Short-term)장기기억 (Long-term)
담기는 곳메시지 리스트 (한 대화 세션)Store (세션이 끝나도 유지)
수명대화가 끝나면 사라짐사용자를 지칭하는 열쇠(namespace)만 알면 언제든 다시 꺼냄
비유회의 중 눈앞의 화이트보드사물함에 넣어둔 개인 노트
이번 장의 관심사—이 노트를 매번 Agent에게 자동으로 펼쳐 보여주기

전체 그림 — 3단계 조립

코드가 여러 셀로 나뉘어 있어 복잡해 보이지만, 실제로 하는 일은 부품 3개를 만들어 하나로 조립하는 것이 전부입니다. 먼저 큰 그림을 머릿속에 넣어두면, 아래 코드들이 각각 어느 부품인지 훨씬 잘 보입니다.

1Store 채우기

사용자 정보(facts)를 namespace라는 열쇠로 창고에 저장

2Context 정의

"지금 대화 상대가 누구인지"(user_id)를 담는 명찰을 설계

3미들웨어 장착

매 호출마다 Store를 뒤져 system_prompt에 기억을 주입

🔍 비유 — 단골 카페의 3요소 단골손님을 알아보는 카페를 만든다고 해봅시다. ① 고객 카드(Store)에 "이 손님은 연하게, 두유로"라고 적어두고, ② 손님이 오면 멤버십 앱(Context)으로 누구인지 식별하고, ③ 매니저(미들웨어)가 그 카드를 찾아 바리스타(LLM)에게 "이분은 연하게, 두유예요" 하고 귀띔합니다. 이 셋이 맞물릴 때 비로소 "어서오세요, 늘 드시던 걸로 드릴까요?"가 가능해집니다.

0. 환경 준비 — 모델 선언

늘 그랬듯 먼저 말을 걸 상대(모델)를 하나 준비합니다. 이 셀 자체는 특별할 게 없습니다 — 진짜 주인공은 뒤에 나올 Store · Context · 미들웨어입니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent


# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")
💡 여기서 만든 model은 사실 이번 장에서 직접 쓰이진 않습니다 뒤에서 create_agent를 부를 때 모델을 "gpt-5-nano" 문자열로 다시 지정하기 때문이에요. 즉 이 셀은 "환경 로드(load_dotenv)"가 핵심 목적이라고 봐도 됩니다. API 키가 없으면 그 뒤 코드가 실행되지 않습니다.

1. Store 채우기 — 기억 심어두기

09번의 복습 파트입니다. 장기기억을 저장할 창고(Store)를 만들고, 사용자에 대한 사실들을 넣어둡니다. 나중에 Agent가 이 창고를 뒤져 기억을 꺼내게 됩니다.

① Store 만들고 namespace 정하기

🔍 비유 — namespace는 사물함 번호 Store는 거대한 사물함 벽입니다. 여기에 아무 데나 물건을 넣으면 나중에 못 찾겠죠. 그래서 (user_id, application_context)라는 사물함 주소를 정합니다 — 예를 들어 ("user_001", "personal_assistant")는 "1번 사용자의 개인비서 서랍"이라는 뜻입니다. 이 주소(namespace)를 알아야만 그 사람의 기억을 정확히 꺼낼 수 있습니다.
📥 코드
from langgraph.store.memory import InMemoryStore

# 1. Store 초기화
store = InMemoryStore()

user_id = "user_001"
application_context = "personal_assistant"

# 2. Namespace(폴더 경로) 설정
namespace = (user_id, application_context)

InMemoryStore는 이름 그대로 메모리(RAM) 위에만 존재하는 창고입니다. 프로그램을 껐다 켜면 내용이 사라지죠. 학습·실습용으로는 완벽하고, 실제 서비스에서는 DB로 뒷받침되는 영속 Store로 교체하면 됩니다. namespace는 파이썬 튜플이라는 점도 눈여겨보세요 — 뒤에서 그대로 재사용됩니다.

② 기억(facts) 저장하기 — put

이제 이 서랍에 사용자에 대한 사실들을 넣습니다. store.put(namespace, key, value) 형태이며, key는 각 기억의 고유 이름표입니다.

📥 코드
# 3. 첫 번째 데이터 저장
store.put(
    namespace,
    "memory_001",  # 이 데이터의 고유 식별자 (Key)
    {
        "facts": [
            "사용자는 커피보다 차를 선호함",
            "사용자는 매일 아침 6시에 일어남",
        ],
        "language": "Korean",
    },
)
📥 코드
# 4. 두 번째 데이터 저장
store.put(
    namespace,
    "memory_002",  # 이전 데이터가 덮어씌워지지 않도록 새로운 Key 지정
    {
        "facts": [
            "사용자는 그림 회화 작품을 좋아함",
            "빈센트 반 고흐의 작품을 특히 좋아함",
        ]
    },
)
⚠️ key가 같으면 덮어쓰기(overwrite)됩니다 만약 두 번째 저장에도 "memory_001"을 그대로 썼다면, 첫 번째 기억은 흔적도 없이 사라지고 두 번째 것으로 교체됩니다. 기억을 쌓고 싶다면 memory_002처럼 새 key를 줘야 합니다. 사물함 한 칸에 계속 덮어쓰지 말고, 새 칸을 쓰라는 뜻이죠.

③ 잘 들어갔는지 확인 — get · search

저장이 잘 됐는지 두 가지 방법으로 확인합니다. get은 key를 콕 집어 하나만 꺼내고(사물함 특정 칸 열기), search는 namespace 전체를 훑어 그 서랍의 모든 기억을 가져옵니다(서랍 통째로 열기).

📥 코드
# 특정 Key 조회 (get)
item1 = store.get(namespace, "memory_001")
# print(item1)
print("1번 메모리:", item1.value)

item2 = store.get(namespace, "memory_002")
print("2번 메모리:", item2.value)

# Namespace 전체 검색 (search)
print("\n--- 전체 검색 결과 ---")
items = store.search(namespace)
# print(items)
for item in items:
    print(f"Key: {item.key} | Value: {item.value}")

📘 보충 — get이 돌려주는 Item 객체

store.get(...)의 반환값은 딕셔너리가 아니라 Item이라는 포장 상자입니다. 우리가 넣은 실제 값은 그 안의 .value에 들어 있죠. 그래서 item1.value로 꺼냅니다. 상자에는 값 말고도 .key(이름표), .namespace(어느 서랍인지), .created_at/.updated_at(저장 시각) 같은 택배 송장 정보도 함께 붙어 있습니다. 뒤 미들웨어에서 이 .value를 파고들게 됩니다.

2. Context 정의 — "지금 대화 상대가 누구인가"

Store에는 user_001, user_002 등 여러 사람의 기억이 섞여 들어갈 수 있습니다. 그렇다면 Agent가 답할 때 어느 서랍을 열어야 할지 어떻게 알까요? 바로 이 정보를 담는 그릇이 Context입니다.

🔍 비유 — Context는 방문객 명찰 회사에 손님이 오면 방문객 명찰에 "누구를 만나러 왔는지"를 적어 목에 겁니다. 안내 직원은 그 명찰만 보고 올바른 부서로 안내하죠. Context가 바로 이 명찰입니다. 매 대화마다 "지금 나는 user_001의 personal_assistant를 쓰는 중"이라는 명찰을 Agent에 걸어주면, 미들웨어가 그 명찰을 읽고 정확히 그 사람의 서랍을 엽니다.
📥 코드
from dataclasses import dataclass

@dataclass
class Context:
    user_id: str
    app_name: str

@dataclass는 "이 클래스는 데이터를 담는 용도일 뿐"이라고 파이썬에게 알려주는 간편 장치입니다. 복잡한 생성자를 손으로 안 써도 Context(user_id="user_001", app_name="personal_assistant")처럼 바로 만들 수 있죠. 여기서 정한 user_id와 app_name 두 칸이, 잠시 뒤 namespace를 조립하는 재료가 됩니다.

⚠️ 필드 이름을 잘 봐두세요 1단계에서 서랍을 만들 땐 변수 이름이 application_context였지만, Context에서는 같은 개념을 app_name이라고 부릅니다. 변수 이름은 달라도 담기는 값("personal_assistant")은 같아야 미들웨어가 올바른 서랍을 찾습니다.

3. inject_memory 미들웨어 — Store를 system_prompt에 주입

드디어 이 노트북의 심장부입니다. 미들웨어(middleware)는 Agent가 LLM을 호출하는 흐름 중간에 끼어들어 요청을 살짝 바꾸는 장치입니다. 여기서는 @wrap_model_call을 써서 "LLM을 부르기 직전에 Store를 뒤져 기억을 꺼내고, 그걸 system_prompt에 끼워 넣어라"라고 지시합니다.

🔍 비유 — 회의실에 들어가기 직전, 비서의 귓속말 사장(LLM)이 손님을 만나러 회의실 문 앞에 섰습니다. 바로 그 순간, 비서(@wrap_model_call)가 다가와 "이분은 커피보다 차를 좋아하시고, 반 고흐 팬이세요"라고 귓속말로 브리핑합니다. 사장은 그 브리핑을 머릿속에 넣은 채 문을 열고 들어가 자연스럽게 응대하죠. @wrap_model_call은 "모델 호출을 감싸는(wrap)" 미들웨어라서, 이렇게 호출 직전에 끼어들 수 있습니다.
📥 코드
from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
from typing import Callable


@wrap_model_call
def inject_memory(request: ModelRequest, handler: Callable) -> ModelResponse:
    current_user = request.runtime.context.user_id
    current_app = request.runtime.context.app_name
    memories = request.runtime.store.search((current_user, current_app))

    memory_content = "기록된 정보 없음"

    if memories:
        # 검색된 메모리들을 텍스트로 변환
        extracted_facts = []
        for item in memories:
            # print('item', item)
            if "facts" in item.value:
                extracted_facts.extend(item.value["facts"])
                # print('extracted_facts', extracted_facts)
        memory_content = "\n- ".join(extracted_facts)
        # print('memory_content', memory_content)

    system_message = f"사용자 관련 장기 메모리 :\n- {memory_content}"
    request = request.override(system_prompt=system_message)
    return handler(request)

이 함수가 한 줄씩 무슨 일을 하는지 천천히 따라가 봅시다.

코드하는 일 (비유)
request.runtime.context.user_id 손님의 명찰에서 "누구인지"를 읽는다 (2단계 Context에서 걸어준 값)
request.runtime.store.search((current_user, current_app)) 그 명찰로 서랍 주소(namespace)를 조립해 창고를 통째로 검색
extracted_facts.extend(item.value["facts"]) 꺼낸 기억 상자들에서 facts 리스트만 골라 한 바구니에 쏟아 모으기
"\n- ".join(extracted_facts) 모은 사실들을 줄바꿈 + 불릿(-)으로 이어 붙여 읽기 좋은 목록 문장으로
request.override(system_prompt=...) 완성된 브리핑을 감독 지시문(system_prompt)에 덮어씌우기
return handler(request) 바뀐 요청을 들고 진짜 LLM 호출을 이어서 진행
💡 handler(request)가 핵심 마무리입니다 미들웨어는 요청을 가로채 손질만 할 뿐, 실제 LLM 호출은 handler에게 넘겨야 합니다. 비유하자면 비서가 귓속말(브리핑)을 마친 뒤 "이제 들어가셔도 됩니다"라고 문을 열어주는 동작이에요. 이걸 빠뜨리면 사장은 회의실 문 앞에 계속 서 있게 됩니다(응답이 안 나옴).
📘 보충 — facts가 없는 기억은 자동으로 건너뜁니다

if "facts" in item.value: 조건이 있는 이유를 볼까요? 우리가 저장한 memory_001에는 facts 말고 language 같은 다른 칸도 있었습니다. 만약 어떤 기억 상자에 아예 facts 키가 없다면, item.value["facts"]를 꺼내려다 에러가 날 수 있죠. 그래서 "이 상자에 facts가 있을 때만 꺼내라"고 안전장치를 둔 것입니다. 실제 실행에서는 memory_001·memory_002의 facts가 모두 모여 아래 브리핑 문장이 완성됩니다.

▶ 이렇게 만들어집니다 (내부에서 완성되는 memory_content)
사용자는 커피보다 차를 선호함
- 사용자는 매일 아침 6시에 일어남
- 사용자는 그림 회화 작품을 좋아함
- 빈센트 반 고흐의 작품을 특히 좋아함

즉 최종적으로 LLM에게 전달되는 system_prompt는 아래처럼 됩니다. LLM 입장에서는 이 지시문을 미리 읽고 대화를 시작하니, 사용자를 "기억하는" 것처럼 보이는 거죠.

4. Agent 조립 & 실행

부품 3개(Store · Context · 미들웨어)가 준비됐으니, 이제 create_agent 한 방으로 조립합니다. 세 개의 인자가 각각 어느 부품을 꽂는 자리인지 보세요.

📥 코드
from langchain.agents import create_agent

agent = create_agent(
    model="gpt-5-nano",
    store=store,          # store 연결
    context_schema=Context,
    middleware=[inject_memory]  # 미들웨어 장착
)

response = agent.invoke(
    {"messages": [{"role": "user", "content": "나에 대해 알고있는 정보 알려줘"}]},
    context=Context(user_id="user_001", app_name="personal_assistant")
    # user_id가 002로 바뀌면 사용자 정보를 알 수 없다고 답변한다
)
print(response["messages"][-1].content)
인자꽂는 부품역할
store=store1단계 창고미들웨어가 뒤질 기억 저장소를 Agent에 연결
context_schema=Context2단계 명찰 양식이 Agent는 어떤 명찰을 받을 수 있는지 알려줌
middleware=[inject_memory]3단계 비서매 호출 직전에 끼어들 미들웨어 장착
context=Context(...)이번 손님 명찰invoke할 때 실제 값을 담아 명찰을 걺
▶ 이렇게 나와요
다음이 현재 제가 기억하고 있는 당신에 관한 정보입니다.

- 커피보다 차를 선호합니다.
- 매일 아침 6시에 일어납니다.
- 그림 회화 작품을 좋아합니다.
- 특히 빈센트 반 고흐의 작품을 좋아합니다.

원하신다면 이 정보를 바탕으로 개인화된 제안이나 대화를 더 자세하게 맞춰드릴 수 있어요. 예를 들어
차 추천, 6시 기상 루틴 아이디어, 반 고흐 테마의 미술관 전시 소식이나 작품 해설 등도 제공해 드릴 수 있습니다.
새로운 선호나 추가하고 싶은 정보가 있다면 알려주시면 업데이트하겠습니다.

우리는 프롬프트에 사용자 정보를 직접 적지 않았습니다. "나에 대해 알려줘"라고만 물었죠. 그런데도 LLM이 차·기상 시간·반 고흐를 정확히 짚어낸 이유는, 미들웨어가 system_prompt에 몰래 브리핑을 넣어줬기 때문입니다. Store에 심어둔 장기기억이 실제 답변으로 살아난 순간이에요.

자주 겪는 함정 — 명찰(user_id)이 어긋나면?

코드 주석에도 적혀 있듯, invoke할 때 user_id를 "user_002"로 바꾸면 어떻게 될까요? 미들웨어는 ("user_002", "personal_assistant") 서랍을 열려고 합니다. 하지만 우리는 그 서랍에 아무것도 넣은 적이 없죠.

🔍 비유 — 남의 사물함 열쇠 1번 손님의 노트는 1번 사물함에만 들어 있습니다. 그런데 2번 사물함 열쇠로 문을 열면? 당연히 텅 비어 있죠. 미들웨어의 search는 빈 결과를 받고, memory_content는 초기값 "기록된 정보 없음" 그대로 남습니다. 그래서 LLM은 "당신에 대해 기록된 정보가 없다"고 답하게 됩니다.
⚠️ 핵심 규칙 저장할 때의 namespace와 꺼낼 때 조립되는 namespace가 정확히 일치해야 기억이 연결됩니다. 기억이 안 불려온다면 십중팔구 user_id나 app_name 값이 저장 시점과 어긋난 것입니다. 오타 하나가 "기억상실"을 만듭니다.

📚 한 장 정리

오늘의 핵심 장기기억은 Store에 넣어두는 것만으로 끝나지 않는다. 매 호출 직전에 꺼내 system_prompt에 주입하는 미들웨어가 있어야 비로소 Agent가 그 기억을 "쓴다".
  • Store — 세션이 끝나도 남는 장기기억 창고. put으로 넣고 get/search로 꺼낸다(09번 복습).
  • namespace — (user_id, app_name) 튜플 = 사물함 주소. 저장·조회 시 정확히 일치해야 한다.
  • Context — "지금 대화 상대가 누구인가"를 담는 방문객 명찰. invoke 때 context=로 걸어준다.
  • @wrap_model_call 미들웨어 — 회의 직전 비서의 귓속말. Store 검색 → request.override(system_prompt=...) → handler(request)로 마무리.
  • 조립 — create_agent(store=, context_schema=, middleware=[...])로 세 부품을 하나로 꽂는다.
  • 함정 — user_id가 어긋나면 빈 서랍을 열게 되어 "기록된 정보 없음"이 된다.
