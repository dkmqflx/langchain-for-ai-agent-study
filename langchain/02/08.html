08. Structured Output — 구조화된 답변 생성

실습 노트북: 08.ipynb  ·  원문: docs/02.agent-basic.md 4장 Structured Output  ·  난이도: 🟡 중급  ·  선행: 07. PII 탐지

이 자료는 실습 노트북(08.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 지금까지 Agent의 답은 늘 사람이 읽는 자연어 문장이었습니다. 그런데 그 답을 코드가 다시 다뤄야 할 때 — 예를 들어 "이 고객 메일은 불만인가 문의인가?"를 자동으로 분류해 DB에 넣어야 할 때 — 문장은 다루기 까다롭습니다. 이 장에서는 Agent의 최종 답을 정해진 칸이 있는 데이터(Pydantic 객체)로 받아내는 Structured Output을, 고객 이메일 분석 Agent를 만들며 배웁니다.

🔍 비유 — 서술형 답안 vs OMR 카드 선생님이 학생에게 감상문을 받으면 사람이 한 줄 한 줄 읽어야 뜻을 압니다(자연어). 하지만 OMR 답안카드는 다릅니다 — "1번 보기, 2번 보기" 칸이 정해져 있어 기계가 그대로 채점할 수 있죠. Structured Output은 Agent에게 감상문 대신 OMR 카드를 쥐여주는 것입니다. "네 맘대로 문장 쓰지 말고, 이 칸들(의도·감정·요약·다음 조치)을 채워서 돌려줘"라고 시키면, 돌아온 답을 코드가 파싱 없이 바로 읽어 다음 작업으로 넘길 수 있습니다.
이 장에서 배우는 것 Agent의 최종 응답을 자연어 문자열로 받는 대신, 우리가 미리 정의한 구조(스키마)에 맞춘 데이터로 받는 법을 배웁니다. 핵심은 딱 두 가지 — ① Pydantic 클래스로 "칸"을 정의하고, ② create_agent(response_format=ToolStrategy(클래스))로 그 칸을 강제하는 것입니다.

같은 Agent라도 답을 어디서 꺼내는가가 달라집니다. 두 경우를 나란히 비교해 봅시다.

케이스답을 꺼내는 곳돌아오는 형태
일반 Agentresponse["messages"][-1].content자연어 문자열 (사람이 읽는 문단)
Structured Output Agentresponse["structured_response"]Pydantic 객체 (칸이 채워진 데이터)

적용 방법 — 딱 3단계

1양식 정의

Pydantic 클래스로 어떤 칸(의도·감정·요약…)이 필요한지 스키마를 만든다

2Agent에 씌우기

create_agent(response_format=ToolStrategy(클래스))로 최종 출력을 강제한다

3객체로 꺼내기

response["structured_response"]로 채워진 객체를 바로 받는다

⚠️ 실행 전 준비 코드를 직접 돌려보려면 프로젝트 루트에 .env 파일이 있고 그 안에 OPENAI_API_KEY 같은 API 키가 들어 있어야 합니다. 이 교재만 읽을 때는 필요 없습니다.

0. 모델과 도구 준비

먼저 말을 걸 모델을 만들고, 이 Agent가 쓸 도구(Tool) 두 개를 준비합니다. 우리가 만들 것은 고객 이메일 분석 Agent라서, "메일을 읽는 도구"와 "메일을 보내는 도구"가 필요합니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent

# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-5-nano")

다음은 도구 두 개입니다. 아직 진짜 메일 서버는 없지만, 실습이므로 정해진 문자열을 돌려주는 프로토타입으로 만듭니다. @tool 데코레이터와 함수의 docstring이 곧 LLM에게 주는 "이 도구는 이런 일을 해"라는 설명서입니다.

📥 코드
from langchain.tools import tool
from typing import Dict, List

@tool
def send_email_tool(to: str, subject: str, body: str) -> str:
    """지정한 이메일 주소로 메일을 보내는 도구(프로토타입)."""
    return f"✅ 이메일이 성공적으로 전송되었습니다.\n수신자: {to}\n제목: {subject}\n내용: {body[:50]}..."

@tool
def read_email_tool(limit: int = 1) -> List[Dict[str, str]]:
    """가상의 고객 이메일을 조회하는 도구."""
    return f"✅ 이메일이 성공적으로 조회되었습니다."
🔍 비유 — 리허설용 소품 전화기 연극 무대에 놓인 전화기는 진짜 통화가 되지 않아도, 배우가 "여보세요" 연기를 하기엔 충분합니다. 여기 두 도구도 마찬가지예요 — 실제 SMTP 서버에 연결하지 않고 정해진 응답만 돌려주는 소품입니다. 우리의 관심사는 "메일이 진짜 가느냐"가 아니라, Agent가 이 도구들을 거쳐 만든 최종 답을 어떻게 구조화하느냐이기 때문이죠.

1. Pydantic으로 출력 구조 정의

이제 이 장의 OMR 카드를 직접 그릴 차례입니다. Agent가 이메일을 분석한 결과를 담을 네 개의 칸을 Pydantic 클래스로 정의합니다.

📥 코드
from pydantic import BaseModel, Field
from typing import Literal

class EmailAnalysis(BaseModel):
    """이메일 내용을 분석한 결과 구조."""

    intent: Literal["complaint", "inquiry", "confirmation", "other"] = Field(
        description="이메일의 주요 의도 (complaint=불만, inquiry=문의, confirmation=확인, other=기타)"
    )
    sentiment: Literal["positive", "negative", "neutral"] = Field(
        description="고객의 감정 상태"
    )
    summary: str = Field(
        description="이메일의 핵심 내용을 1~2문장으로 짧게 요약"
    )
    next_action: str = Field(
        description="담당자가 취해야 할 다음 단계 (예: 환불 부서 이관, 매뉴얼 링크 발송 등)"
    )

여기엔 두 가지 중요한 장치가 있습니다. 하나는 Literal 타입, 다른 하나는 Field(description=...)입니다. 하나씩 감을 잡아봅시다.

🔍 비유 — Literal은 자판기 버튼 summary는 아무 문장이나 써도 되는 주관식 칸입니다(str). 반면 intent는 Literal["complaint", "inquiry", "confirmation", "other"] — 즉 정해진 네 개의 버튼 중 하나만 누를 수 있는 자판기와 같습니다. Agent가 "아마 컴플레인 같기도 하고요…" 같은 애매한 답을 쓰지 못하고, 반드시 이 네 값 중 하나로만 답하도록 선택지를 좁혀 줍니다. 덕분에 뒤에서 if intent == "complaint": 같은 코드 분기를 마음 놓고 짤 수 있죠.

Field(description="...")의 설명문은 LLM에게 주는 힌트입니다. 각 칸 옆에 붙은 작성 안내문이라고 보면 됩니다. LLM은 이 설명을 읽고 "아, 이 칸에는 감정 상태를 넣어야 하는구나", "이 칸에는 다음에 할 일을 적으면 되는구나"를 판단해 값을 채웁니다. 설명이 친절할수록 채워지는 값의 품질도 좋아집니다.

📘 보충 — 왜 굳이 Literal로 값을 가두나?

만약 intent를 그냥 str로 두면 어떻게 될까요? 어떤 날은 "complaint", 어떤 날은 "불만", 또 어떤 날은 "customer complaint"처럼 제각각의 표현이 돌아올 수 있습니다. 그러면 이 값을 받아 처리하는 코드가 매번 깨지겠죠.

Literal로 허용값을 못 박아두면, LLM의 자유분방함을 우리가 정한 울타리 안에 가둘 수 있습니다. 이것이 구조화 출력의 진짜 힘입니다 — 답의 "형태"뿐 아니라 "값의 범위"까지 통제하는 것.

한 줄 요약 Literal = 객관식 보기(정해진 값만) · str = 주관식(자유 서술). 분류·상태처럼 값이 정해진 칸은 Literal, 요약·설명처럼 자유로운 칸은 str.

2. ToolStrategy로 Agent에 적용

양식(스키마)을 그렸으니, 이제 Agent에게 "최종 답은 반드시 이 양식에 맞춰라"라고 지시할 차례입니다. 방법은 create_agent에 response_format=ToolStrategy(EmailAnalysis)를 넘기는 것 하나입니다.

📥 코드
from langchain.agents import create_agent
from langchain.agents.middleware import LLMToolEmulator
from langchain.agents.structured_output import ToolStrategy
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")
tools = [send_email_tool, read_email_tool]

agent = create_agent(
    model=model,
    tools=tools,
    # 핵심: 최종 산출물의 규격을 EmailAnalysis 스키마로 강제합니다.
    response_format=ToolStrategy(EmailAnalysis),
    middleware=[
        # 이메일 도구가 실제 백엔드에 없더라도 가상으로 동작하게 해주는 실습용 미들웨어
        LLMToolEmulator(model="gpt-5-nano"),
    ],
)
🔍 비유 — response_format은 "결재 서식 지정" 회사에서 보고를 올릴 때, 상사가 "자유 형식 말고 정해진 결재 서식에 맞춰 제출해"라고 하면 아무리 내용이 좋아도 그 서식대로 칸을 채워야 결재가 통과됩니다. response_format=ToolStrategy(EmailAnalysis)가 바로 그 "이 서식으로 제출해"라는 지시입니다. Agent가 도구를 쓰고 이런저런 추론을 하다가도, 마지막 제출물만큼은 반드시 EmailAnalysis 양식에 맞춰 내놓게 되는 것이죠.
💡 LLMToolEmulator는 여기서 조연입니다 middleware=[LLMToolEmulator(...)]는 이 장의 주제가 아니라, 진짜 메일 서버 없이도 도구가 가상으로 동작하도록 흉내 내주는 실습용 장치입니다(자세한 내용은 04. Tool Emulator 노트북). 마치 모의고사처럼, 실제 시스템을 붙이지 않고도 Agent 흐름 전체를 시연할 수 있게 해줍니다. 이 장의 진짜 주인공은 어디까지나 response_format=ToolStrategy(EmailAnalysis) 한 줄입니다.

3. 실행과 structured_response

준비가 끝났습니다. 이제 사용자 지시를 담아 agent.invoke(...)를 호출합니다. 아래 대화 흐름을 머릿속에 그려 보세요.

Human
최근 온 메일을 읽고, 고객의 의도와 감정, 요약, 그리고 필요한 다음 조치를 분석해줘 ← 사용자 지시
AI
read_email_tool 호출 → 고객 메일 확인 ← 도구 사용
AI
분석 결과를 EmailAnalysis 양식에 맞춰 제출 ← 구조화된 최종 답
📥 코드
# 사용자 지시사항 전달 및 에이전트 실행
response = agent.invoke(
    {
        "messages": [
            {
                "role": "user",
                "content": "최근 온 메일을 읽고, 고객의 의도와 감정, 요약, 그리고 필요한 다음 조치를 분석해줘.",
            }
        ]
    }
)
print(response['messages'][-1].content)

# messages 배열을 뒤지는 대신, structured_response 키로 바로 접근합니다.
analysis = response["structured_response"]
print(analysis)

출력의 두 번째 줄이 바로 print(analysis)의 결과 — 채워진 EmailAnalysis 객체입니다. intent='inquiry', sentiment='neutral'처럼 우리가 정의한 네 칸이 모두 값으로 채워져 돌아왔죠. 여기서 진짜 중요한 건, 이 값들을 문자열에서 정규식으로 긁어낸 게 아니라 이미 나뉜 칸에서 바로 꺼낼 수 있다는 점입니다.

🔍 비유 — .content는 봉투, structured_response는 정리된 표 response["messages"][-1].content는 손편지가 든 봉투를 받는 것과 같습니다 — 뜯어서 사람이 읽고 뜻을 해석해야 하죠. 반면 response["structured_response"]는 누군가 그 편지를 미리 읽고 항목별로 칸을 채워 넣은 표를 건네받는 것과 같습니다. "의도: 문의 / 감정: 중립 / 요약: … / 다음 조치: …" — 파싱이라는 번거로운 단계가 통째로 사라집니다.

그래서 실제 코드에서는 analysis.intent, analysis.sentiment처럼 점(.)으로 각 칸에 바로 접근할 수 있습니다. 예를 들어 "불만(complaint)이고 감정이 부정(negative)이면 즉시 관리자에게 알림"같은 자동화 로직을, 문장 해석 없이 곧바로 짤 수 있습니다.

📥 코드 (활용 예 — 개념 설명용)
# structured_response 덕분에 이런 분기를 문장 파싱 없이 바로 짤 수 있다.
if analysis.intent == "complaint" and analysis.sentiment == "negative":
    print("⚠️ 긴급 불만 메일 → 관리자에게 즉시 에스컬레이션")
else:
    print(f"다음 조치: {analysis.next_action}")
💡 핵심 한 줄 Structured Output은 결국 "LLM의 답을 코드가 곧바로 쓸 수 있는 데이터로 받는 기술"입니다. Agent의 똑똑함(도구 사용·추론)은 그대로 두고, 그 결과를 담는 그릇만 문장 → 객체로 바꾼 것이죠.

📚 한 장 정리

오늘의 핵심 Agent에게 감상문 대신 OMR 카드를 쥐여주면, 돌아온 답을 코드가 파싱 없이 바로 다룰 수 있다. 그 방법은 Pydantic으로 칸을 정의하고 response_format=ToolStrategy(클래스)로 강제하는 것.
  • 일반 Agent — 답은 response["messages"][-1].content의 자연어 문자열. 사람이 읽기 좋지만 코드가 다루긴 번거롭다.
  • Structured Output Agent — 답은 response["structured_response"]의 Pydantic 객체. .intent처럼 점으로 바로 꺼낸다.
  • ① Pydantic 스키마 — 필요한 칸을 클래스로 정의. Field(description=...)은 LLM에게 주는 작성 안내문.
  • Literal = 자판기 버튼 — 값을 정해진 보기로 가둬, 분류·상태 칸이 제멋대로 표현되지 않게 한다.
  • ② ToolStrategy — create_agent(response_format=ToolStrategy(클래스))로 최종 제출 서식을 강제한다.
  • LLMToolEmulator는 조연 — 진짜 서버 없이 도구를 흉내 내는 실습용 장치일 뿐, 구조화의 주역은 response_format이다.
