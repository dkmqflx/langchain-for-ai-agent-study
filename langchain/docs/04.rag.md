## 1장. RAG 개요

### 1.1 LLM의 한계

<img src='../images/04.rag/02.png'>

LLM은 강력하지만 두 가지 근본적인 한계가 있습니다.

1. **유한한 컨텍스트** : 한 번에 모든 데이터를 입력받을 수 없습니다.
2. **정적인 지식** : 학습 데이터가 특정 시점에 고정되어 있습니다. (Knowledge Cutoff)

> 💡 예를 들어 `gpt-5-nano-2025-08-07` 모델은 2025년 8월 7일 이후의 정보를 알지 못합니다.

---

### 1.2 RAG란?

<img src='../images/04.rag/03.png'>

**RAG** 는 **Retrieval-Augmented Generation** 의 약자로, **검색(Retrieval)** 을 통해 LLM의 생성(Generation)을 **증강(Augmented)** 하는 기술입니다.

<img src='../images/04.rag/04.png'>

#### RAG의 작동 방식

```
사용자 질문(Question)
  ↓
관련 문서 검색 (RETRIEVE)
  ↓
프롬프트에 검색 결과 추가 (PROMPT)
  ↓
LLM이 검색된 정보를 바탕으로 답변 생성
  ↓
최종 답변 (Answer)
```

LLM이 학습 데이터에 없는 정보도 **외부 문서를 실시간으로 검색해 참고**함으로써 정확하고 최신의 답변을 생성할 수 있습니다.

---

### 1.3 RAG 시스템 구축 순서

<img src='../images/04.rag/05.png'>

RAG 시스템은 **사전 준비(인덱싱)** 와 **런타임(검색·생성)** 두 단계로 나뉩니다.

#### 사전 준비 (인덱싱)

| 단계 | 설명 |
| :---: | :--- |
| **Load** | 다양한 소스(PDF, CSV 등)를 Document 객체로 변환 |
| **Split** | Document를 작은 Chunk(말뭉치)로 분할 |
| **Embed** | 각 Chunk를 고정 길이의 숫자 벡터로 변환 |
| **Store** | 벡터를 Vector DB에 저장 |

#### 런타임 (검색·생성)

| 단계 | 설명 |
| :---: | :--- |
| **Retrieve** | 사용자 질문을 임베딩 → Vector DB에서 유사 문서 검색 |
| **Generate** | 검색된 문서를 프롬프트에 추가해 LLM이 답변 생성 |

## 2장. RAG 시스템 구축

### 2.1 Load — 문서 로딩

<img src='../images/04.rag/06.png'>

**Load** 는 RAG 시스템 구축의 **첫 번째 단계**입니다.  
다양한 데이터 소스(PDF, CSV, Google Drive 등)를 LangChain에서 작업할 수 있는 **Document 객체**로 변환합니다.

각 Document 객체는 두 가지 핵심 속성을 가집니다.

| 속성 | 설명 |
| :--- | :--- |
| `page_content` | 문서의 실제 텍스트 내용 |
| `metadata` | 소스 경로, 페이지 번호, 생성일 등 부가 정보 |

---

#### 2.1.1 PDFPlumber

<img src='../images/04.rag/07.png'>

- **C 언어 기반** → 매우 빠름
- 대량의 문서, **단순 텍스트 추출**에 유리

```python
from langchain_community.document_loaders import PDFPlumberLoader

loader = PDFPlumberLoader("./pdf-file.pdf")
docs = loader.load()

print(len(docs))  # 페이지 수
print(docs[0])    # 첫 번째 페이지 Document 객체
```

<img src='../images/04.rag/08.png'>

```python
import pprint
```

### 2.2 Split — 청크 분할

<img src='../images/04.rag/11.png'>

**Split** 은 RAG 시스템 구축의 **두 번째 단계**입니다.  
Load한 Document 객체를 **작은 말뭉치(Chunk)** 로 쪼갭니다.

#### 왜 쪼개야 할까?

LLM의 **Context Window 사이즈 한계** 때문입니다. 전체 문서를 한 번에 넣을 수 없으므로, 관련된 부분만 잘라서 LLM에게 전달해야 합니다.

---

#### 2.2.1 RecursiveCharacterTextSplitter — 재귀적 문자 텍스트 분할기

<img src='../images/04.rag/13.png'>

**가장 많이 사용되는 텍스트 분할기**입니다. **큰 단위에서 작은 단위로 순차적으로 내려가며 쪼개는 방식**으로, 문맥을 최대한 보존합니다.

분할 우선순위 (기본값):

| 순서 | 구분자 | 의미 |
| :---: | :--- | :--- |
| 1 | `\n\n` | 문단 바꿈 (가장 큰 단위) |
| 2 | `\n` | 줄 바꿈 |
| 3 | ` ` | 공백/띄어쓰기 |
| 4 | `""` | 글자 단위 (가장 작은 단위) |

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

docs = loader.load()

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=300,      # 각 청크의 최대 글자 수
    chunk_overlap=0,     # 청크 간 겹치는 글자 수 (문맥 연결용)
    separators=["\n\n", "\n", " ", ""]  # 기본 우선순위
)

recursive_docs = text_splitter.split_documents(docs)
```

> 📝 `split_texts` 는 문자열을, `split_documents` 는 **Document 객체 리스트**를 청킹할 때 사용합니다.

<img src='../images/04.rag/15.png'>

`chunk_size=100` 으로 설정하면 본문이 여러 개의 Chunk로 나뉘어, 각각 100자 이하의 텍스트가 담긴 청크 목록이 생성됩니다.

---

#### 2.2.2 청킹 전략 참고

<img src='../images/04.rag/17.png'>

AWS Bedrock이 지원하는 다양한 청킹 전략 참고:

| 전략 | 설명 |
| :--- | :--- |
| **기본 청킹** | 약 300 토큰 크기로 자동 분할 |
| **고정 크기 청킹** | 설정한 고정 토큰 크기로 분할 |

| **청킹 없음** | 이미 사전 처리된 문서에 적합 |

### 2.3 Embed — 임베딩 (벡터화)

<img src='../images/04.rag/18.png'>

**Embed** 는 RAG 시스템 구축의 **세 번째 단계**입니다.  
Split한 각 Chunk를 **고정 길이의 숫자 배열(벡터)로 변환**합니다. 이후 유사도 검색을 위해 필요합니다.

---

#### 2.3.1 임베딩/벡터라이징이란?

<img src='../images/04.rag/19.png'>

텍스트, 이미지 등을 **컴퓨터가 이해하고 계산할 수 있는 숫자들로 바꾸는 과정**입니다.

```
"anatine amigos" → [-0.027, -0.001, -0.020, ..., -0.023]
"porcine pals"   → [-0.011, -0.011,  0.032, ..., -0.011]
```

<img src='../images/04.rag/20.png'>

> 💡 **FIFA 선수 데이터 비유**: 메시와 호날두처럼 비슷한 특성을 가진 선수들은 임베딩 벡터도 유사하게 나옵니다. 이와 같은 원리로 **유사한 의미의 텍스트는 유사한 벡터값**을 갖습니다.

---

#### 2.3.2 OpenAI Embedding 모델

<img src='../images/04.rag/21.png'>

```python
from langchain_openai import OpenAIEmbeddings
from langchain_core.vectorstores import InMemoryVectorStore

# 1. 임베딩 모델 객체 생성
embeddings = OpenAIEmbeddings(model="text-embedding-3-large")

text = "랭체인이 뭔가요?"

# 2. 임베딩 결과를 Vector Store에 저장
vectorstore = InMemoryVectorStore.from_texts(
    [text],
    embedding=embeddings,
)
```

---

#### 2.3.3 CacheBackedEmbeddings — 임베딩 캐싱

<img src='../images/04.rag/22.png'>

임베딩 API 호출은 비용이 발생합니다. **한 번 임베딩한 텍스트 결과를 로컬 파일에 저장해두고, 똑같은 텍스트가 들어오면 API 호출 대신 저장된 파일을 사용**합니다.

```python
from langchain_openai import OpenAIEmbeddings
from langchain_classic.embeddings import CacheBackedEmbeddings
from langchain_classic.storage import LocalFileStore

# 1. 실제 계산을 담당할 핵심 임베딩 모델
underlying_embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

# 2. 캐시 데이터를 저장할 물리적 위치
store = LocalFileStore("./cache/")

# 3. 캐시 지원 임베딩 래퍼(Wrapper) 생성
cached_embedder = CacheBackedEmbeddings.from_bytes_store(
    underlying_embeddings,   # 실제 계산을 수행할 모델 객체
    store,                   # 결과를 저장하고 불러올 저장소 객체
    namespace=underlying_embeddings.model  # 충돌 방지용 이름표
)
```

> 📌 같은 텍스트를 두 번 임베딩하면 첫 번째는 API를 호출하지만, 두 번째는 캐시에서 즉시 반환합니다. 비용과 시간 모두 절약됩니다.

### 2.4 Store — Vector Store 저장

<img src='../images/04.rag/23.png'>

**Store** 는 RAG 시스템 구축의 **네 번째 단계**입니다.  
임베딩한 결과(벡터)를 Vector Database에 저장합니다.

> 💡 주요 Vector DB: **Chroma**, **FAISS**, **MongoDB** 등

---

#### 2.4.1 Chroma DB

<img src='../images/04.rag/24.png'>

**Chroma** 는 벡터로 전환한 데이터를 **파일 형태로 저장**합니다. 프로그램을 껐다 켜도 데이터가 보존됩니다.

```python
from langchain_chroma import Chroma

# 1. DB 경로 설정
CHROMA_PATH = "./chroma_db"

# 2. Store 생성 (Split한 문서를 임베딩해서 저장)
db = Chroma.from_documents(
    documents=recursive_docs,         # Split한 문서 리스트
    embedding=cached_embedder,        # 임베딩 모델
    persist_directory=CHROMA_PATH,    # 데이터를 저장할 폴더 경로
    collection_name="rag_collection"  # (선택) DB 내의 테이블 이름 같은 개념
)
```

기존 Chroma DB를 불러올 때는 `documents=` 인자 없이 경로만 지정합니다.

```python
# 기존 DB 불러오기 (새 문서 추가 없이 검색만)
db = Chroma(
    collection_name="rag_collection",
    embedding_function=cached_embedder,
    persist_directory=CHROMA_PATH,
)
```

### 2.5 Retrieve — 검색

<img src='../images/04.rag/25.png'>

**Retrieve** 는 사용자의 질문을 임베딩해 Vector Store에서 **유사한 문서를 검색**하는 단계입니다.

#### 유사도 측정 방법

| 방법 | 설명 | 특징 |
| :--- | :--- | :--- |
| **코사인 유사도** (Cosine Similarity) | 두 벡터 사이의 각도 계산 | 벡터의 크기는 무시, **방향**만 비교. 가장 많이 사용 |
| **유클리드 거리** (Euclidean Distance) | 두 점 사이의 직선거리(L2 Distance) 계산 | 거리가 가까울수록 유사 |
| **내적** (Dot Product) | 한 벡터를 다른 벡터에 투영했을 때의 길이 곱 | 방향과 크기 모두 고려 |

---

#### 2.5.1 검색기 생성 — `as_retriever()`

<img src='../images/04.rag/26.png'>

`as_retriever()` 메서드로 Vector Store 기반 검색기를 생성하고, `invoke()`로 실행합니다.

```python
# ① 유사도 점수 임계값 방식 (threshold)
retriever = db.as_retriever(
    search_type="similarity_score_threshold",
    search_kwargs={"score_threshold": 0.4}  # 유사도 0.4 이상인 문서만 반환
)
results = retriever.invoke("ARKK의 Tesla 투자 비중은?")

# ② MMR 방식 (다양성 고려)
retriever = db.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 5}  # 상위 5개 반환
)
```

---

#### 2.5.2 MMR (Maximal Marginal Relevance)

<img src='../images/04.rag/27.png'>

일반 유사도 검색은 "가장 비슷한 것"만 찾기 때문에 **똑같은 내용의 문장만 3개** 나올 수 있습니다.

**MMR** 은 **"관련 있으면서도 서로 다른(다양한)"** 내용을 찾아줍니다.

```
일반 검색: 유사도 Top-K → [A, A', A''] (비슷한 것만)
MMR 검색 : 유사도 ↑ + 중복 제거 → [A, B, C] (다양한 내용)
```

> 📌 RAG 품질 향상에 MMR이 효과적인 이유: 동일 내용의 문서가 반복되면 LLM이 편향된 답변을 생성할 수 있습니다.

## 3장. RAG 응용

### 3.1 Agentic RAG

<img src='../images/04.rag/29.png'>

RAG 아키텍처는 시스템의 요구사항에 따라 다양한 방식으로 구현할 수 있습니다.

#### 2-Step RAG (기본)

```
사용자 질문 → 관련 문서 검색 → 답변 생성 → 사용자에게 반환
```

고정된 단순 파이프라인. 항상 검색을 수행합니다.

#### Agentic RAG

```
사용자 입력 / 질문
  ↓
에이전트(LLM)
  ↓
외부 정보가 필요한가?
  → Yes → 도구로 검색 → 답변이 충분한가?
                           → Yes → 최종 답변 생성 → 사용자에게 반환
                           → No  → (반복)
  → No  → 최종 답변 생성 → 사용자에게 반환
```

LLM이 **스스로 검색 필요 여부를 판단**하고, 충분한 정보가 쌓일 때까지 반복 검색합니다.

> 💡 **2-Step RAG vs Agentic RAG**
>
> | 구분 | 2-Step RAG | Agentic RAG |
> | :--- | :--- | :--- |
> | 검색 여부 | 항상 검색 | 필요할 때만 검색 |
> | 검색 횟수 | 1회 고정 | 충분할 때까지 반복 |
> | 제어 주체 | 개발자 설계 | LLM이 스스로 판단 |
> | 복잡도 | 낮음 | 높음 |

---

### 3.2 Hybrid RAG

<img src='../images/04.rag/30.png'>

**Hybrid RAG** 는 여러 검색 방식과 LLM 추론을 결합한 고급 아키텍처입니다.

```
사용자 질문
  ↓
쿼리 향상 (전처리)
  ↓
문서 검색
  ↓
정보가 충분한가?
  → Yes → 답변 생성 → 답변 품질이 괜찮은가?
                        → Yes → 최적의 답변 반환 → 사용자
                        → No  → 다른 접근 방식 시도?
                                  → Yes → (반복)
                                  → No  → 쿼리 수정 → (재검색)
  → No  → 쿼리 수정 → (재검색)
```

**RAG 검색**과 **LLM 추론**이 상호작용하며 답변 품질을 높입니다.

> 📌 **Hybrid Search** — BM25(키워드 기반) + 벡터 유사도 검색을 결합하면 더 정확한 문서를 찾을 수 있습니다.
> - **BM25**: 전통적인 키워드 빈도 기반 검색 알고리즘 (ElasticSearch 기본 알고리즘)
> - **Vector Search**: 의미(Semantic) 기반 유사도 검색
> - 두 방식을 결합하면 키워드 매칭과 의미적 유사성을 모두 활용할 수 있습니다.

## 📚 4장 정리

- **RAG** 는 LLM의 두 가지 한계(유한한 컨텍스트, 정적인 지식)를 외부 문서 검색으로 보완하는 기술이다.
- **RAG 파이프라인**: Load → Split → Embed → Store → Retrieve
  - **Load**: PDFPlumber(빠름, 텍스트), PyMUPDF(표, 정밀)로 Document 객체 생성
  - **Split**: `RecursiveCharacterTextSplitter`로 `\n\n → \n → 공백 → 글자` 순으로 청크 분할
  - **Embed**: `OpenAIEmbeddings` + `CacheBackedEmbeddings`로 비용 절약하며 벡터화
  - **Store**: `Chroma DB`로 파일에 영구 저장
  - **Retrieve**: `as_retriever()`로 검색기 생성, `score_threshold` 또는 **MMR**로 다양성 있는 검색
- **Agentic RAG**: LLM이 검색 필요 여부를 스스로 판단하고 반복 검색
- **Hybrid RAG**: BM25 키워드 검색 + 벡터 유사도 검색 결합으로 정확도 향상
