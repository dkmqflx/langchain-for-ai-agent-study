01. Tool 기초

실습 노트북: 02/01.ipynb  ·  원문: docs/02.agent-basic.md 1장 Agents  ·  난이도: 🟢 입문

이 자료는 실습 노트북(02/01.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 지금까지의 모델은 혼자 말만 하는 두뇌였습니다. 이번 장에서는 그 두뇌에게 손과 발(Tool)을 달아 줍니다. LLM이 스스로 "지금은 도구를 써야겠다"고 판단하고, 실제 함수를 호출해 그 결과를 받아 답하는 Agent를 비유와 예시로 천천히 만들어봅니다.

개요 · Tool은 왜 필요한가

🔍 비유 — 백과사전을 통째로 외운, 방에 갇힌 천재 LLM은 어마어마한 양의 책을 통째로 외운 천재입니다. 하지만 그 천재는 창문 없는 방에 갇혀 있고, 외운 책들은 전부 특정 날짜(학습 시점)까지만 담고 있어요. 그래서 "지금 서울 날씨 어때?", "오늘 환율은?" 같이 방 밖의 실시간 정보는 아무리 똑똑해도 알 수가 없습니다. Tool은 이 천재에게 쥐여 주는 전화기입니다. 모르는 걸 물어보면, 천재가 직접 전화를 걸어 바깥세상(날씨 서버, DB, API)에 확인한 뒤 그 답을 참고해 대답하는 거죠.

Tool이란 LLM이 외부 시스템(API, DB, 파일 시스템 등)과 상호작용하기 위해 사용하는 함수입니다. LLM 모델은 학습 데이터의 시간적 한계(Knowledge Cutoff)가 있어서, 학습이 끝난 시점 이후의 일이나 실시간으로 변하는 정보(날씨·주가·최신 뉴스)는 스스로 알지 못합니다. Tool을 붙이면 바로 이 한계를 넘어설 수 있습니다.

이 노트북에서 배우는 것 ① Tool을 만드는 법(@tool), ② Tool과 모델을 묶어 Agent를 만드는 법(create_agent), ③ Agent를 실행했을 때 내부에서 메시지가 어떻게 쌓이는지, 그리고 ④ 여러 Tool과 System Message로 계산기 Agent를 만들어 다단계 추론을 눈으로 확인합니다.
⚠️ 실행 전 준비 코드를 직접 돌려보려면 프로젝트 루트에 .env 파일이 있고 그 안에 OPENAI_API_KEY가 들어 있어야 합니다. 이 교재만 읽을 때는 필요 없습니다.

0. 모델 준비

먼저 앞 장들과 똑같이 "말을 걸 두뇌(모델)" 하나를 준비합니다. 여기에 이번 장의 새 손님인 @tool과 create_agent를 함께 불러옵니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent


# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")
  • tool — 평범한 파이썬 함수를 LLM이 호출할 수 있는 Tool로 승격시키는 데코레이터입니다.
  • create_agent — 모델(두뇌)과 Tool들(손발)을 하나로 조립해 Agent를 만들어 주는 함수입니다.

Tool 작성법 — 4단계

Tool을 만드는 건 생각보다 간단합니다. 평범한 파이썬 함수에 딱 세 가지 표식을 붙이는 것이 전부예요.

🔍 비유 — 공구함에 라벨 붙이기 Tool은 Agent가 든 공구함 속 공구들입니다. 그런데 라벨이 없으면 Agent(초보 조수)는 어떤 공구를 언제 써야 할지 모릅니다. 그래서 각 공구에 이름표(함수명), 사용 설명서(docstring), 규격표(타입 힌트)를 꼼꼼히 붙여 줍니다. 라벨이 정확할수록 조수는 상황에 딱 맞는 공구를 척척 골라 쓰죠. 라벨이 대충이면? 엉뚱한 공구를 집습니다.
단계할 일왜 필요한가
1. 함수 작성파이썬 함수로 실제 로직 구현Tool의 알맹이(실제 동작)
2. 타입 힌팅입력·출력 타입 명시 (location: str -> str)LLM이 인자를 정확히 채우게 도와줌
3. docstring함수가 무엇을 하는지 설명LLM이 이 Tool을 언제 쓸지 이해
4. @tool함수 위에 데코레이터 추가일반 함수 → Tool로 승격
💡 docstring이 곧 사용설명서 docstring은 LLM에게 "이 Tool은 이런 상황에 써라"고 알려주는 설명서 역할을 합니다. 설명이 정확할수록 LLM이 올바른 Tool을 고릅니다. 반대로 설명이 모호하면, 써야 할 상황에 안 쓰거나 엉뚱한 도구를 부릅니다.

1. 첫 Tool — 날씨 도구 만들기

위 4단계를 그대로 적용해, "특정 위치의 현재 날씨를 알려주는" Tool을 하나 만들어 봅니다. 실제 서비스라면 이 안에서 날씨 API를 호출하겠지만, 지금은 구조를 익히는 게 목적이라 고정된 예시 문자열을 돌려주도록 했습니다.

📥 코드
# 현재 날씨를 알려주는 tool 함수 예시
@tool
def get_current_weather(location: str) -> str:
  """
  주어진 위치(location)의 현재 날씨 정보를 반환합니다.
  실제 구현에서는 외부 API 호출이 필요합니다.
  """
  # 예시 응답 (실제 구현 시 API 연동 필요)
  return f"{location}의 현재 날씨는 맑음, 22도입니다."
  • 함수 이름 get_current_weather — "현재 날씨를 가져온다"는 의도가 이름에 드러납니다.
  • 타입 힌트 location: str → LLM이 "이 도구엔 문자열 위치를 넣어야 하는구나"를 알게 됩니다.
  • docstring — "주어진 위치의 현재 날씨 정보를 반환" → LLM이 날씨 질문에 이 도구를 고르게 만드는 단서입니다.
💡 여기서 중요한 오해 풀기 우리가 이 함수를 직접 부르지 않습니다. 우리는 그냥 도구를 만들어 등록만 해 둘 뿐, "언제, 어떤 location 값으로 이 함수를 부를지"는 LLM이 스스로 결정합니다. 이게 일반 함수와 Tool의 결정적 차이예요.

2. Agent 생성 — 도구와 두뇌 연결

Tool 하나만으로는 아무 일도 일어나지 않습니다. 이 도구를 모델(두뇌)에 쥐여 줘야 비로소 "필요하면 알아서 도구를 쓰는" 존재가 됩니다. 이 조립을 create_agent가 해 줍니다.

🔍 비유 — 두뇌 + 손발 = 일할 줄 아는 직원 모델(model)은 생각만 하는 두뇌이고, Tool들은 손과 발입니다. 두뇌만 있으면 "서울은 아마 맑겠죠?" 하고 상상해서 말할 뿐이지만, 손발이 붙으면 직접 창밖(날씨 API)을 확인하고 사실을 말합니다. create_agent(model, tools=[...])는 바로 이 두뇌에 손발을 붙여 '일할 줄 아는 직원(Agent)'을 채용하는 것입니다.
📥 코드
# 에이전트 생성
agent_with_weather = create_agent(
    model=model,
    tools=[get_current_weather],)

tools에는 도구를 리스트로 넘깁니다(지금은 하나뿐이지만 곧 여러 개를 넣습니다). 이렇게 만든 agent_with_weather는 이제 질문을 받으면 스스로 "이건 get_current_weather를 불러야겠다"고 판단할 수 있습니다.

3. Agent 실행 & messages 해부

Agent는 invoke()로 실행합니다. 입력은 messages 키를 가진 딕셔너리이고, 최종 답변은 result["messages"][-1].content(리스트의 맨 마지막 메시지)에서 꺼냅니다.

📥 코드
result = agent_with_weather.invoke({"messages": [
  {"role": "user", "content": "서울 날씨 어때"},
]})

print("Agent의 응답:", result)
print(result['messages'][-1].content)

여기서 중요한 사실 하나 — Agent를 한 번 실행하면, 내부에서는 메시지가 하나가 아니라 여러 개 순서대로 쌓입니다. "질문 → 도구 호출 결정 → 도구 실행 결과 → 최종 답변"의 흐름이 그대로 기록되죠.

순서메시지 타입내용
1HumanMessage사용자 질문 ("서울 날씨 어때")
2AIMessageTool 호출 결정 (content='', tool_calls=[...])
3ToolMessageTool 실행 결과
4AIMessage최종 자연어 답변

이 4개의 메시지를 말풍선으로 그려 보면 다음과 같습니다.

Human
서울 날씨 어때 ← 사용자 질문
AI
content='' · tool_calls=[get_current_weather(location='서울')] ← 말 대신 "도구 부르자!"고 결정
Tool
서울의 현재 날씨는 맑음, 22도입니다. ← 함수가 실제로 실행된 결과
AI
서울의 현재 날씨는 맑고, 기온은 22도입니다. ← 도구 결과를 다듬은 최종 답변
💡 2번 메시지의 content가 비어 있는 이유 두 번째 AIMessage는 사람에게 하는 말이 아니라, "이 도구를 이 인자로 불러 줘"라는 기계에게 보내는 지시입니다. 그래서 사람이 읽을 content는 비어 있고(''), 대신 tool_calls 칸에 어떤 함수를 어떤 인자로 부를지가 담깁니다. 여기서 {'location': '서울'}이라는 인자를 LLM이 스스로 뽑아냈다는 점이 핵심입니다.
▶ 이렇게 나와요 (핵심만 추려 표시)
Agent의 응답: {'messages': [
  HumanMessage(content='서울 날씨 어때', ...),
  AIMessage(content='', tool_calls=[{'name': 'get_current_weather',
                                     'args': {'location': '서울'},
                                     'id': 'call_ao1P...', 'type': 'tool_call'}], ...),
  ToolMessage(content='서울의 현재 날씨는 맑음, 22도입니다.',
              name='get_current_weather', ...),
  AIMessage(content='서울의 현재 날씨는 맑고, 기온은 22도입니다.', ...)
]}
서울의 현재 날씨는 맑고, 기온은 22도입니다.

맨 마지막 줄이 result['messages'][-1].content로 꺼낸 최종 답변입니다. 실제 출력에는 토큰 사용량·모델 이름 같은 메타데이터가 잔뜩 붙지만, 흐름을 이해하는 데엔 위 뼈대만 보면 충분합니다.

📘 보충 — "누가 도구를 부르기로 결정하나?"

Tool을 호출할지 말지, 어떤 Tool을 부를지, 그리고 {'location': '서울'} 같은 인자를 무엇으로 채울지 — 이 모든 걸 결정하는 건 개발자가 미리 짜 둔 if문이 아니라 Agent 속 AI 모델 자신입니다.

그래서 같은 코드라도 질문이 "부산 날씨는?"으로 바뀌면 모델은 알아서 {'location': '부산'}으로 인자를 바꿔 도구를 부릅니다. 고정된 파이프라인이 아니라, 매번 스스로 판단하는 동적 시스템 — 이것이 일반 LLM 앱과 Agent의 차이입니다.

4. 응용 — 여러 Tool + System Message로 계산기 Agent

이제 도구를 여러 개 장착하고, System Message로 Agent의 행동 방침까지 정해 봅니다. 사칙연산 도구 세 개(더하기·나누기·곱하기)를 만들어 "계산기 Agent"를 꾸며 보겠습니다.

📥 코드
# 사칙연산 tool 함수 정의
@tool
def add(a: int, b: int) -> float:
  """두 수의 합을 반환합니다."""
  return a + b

@tool
def divide(a: float, b: float) -> float:
  """a를 b로 나눈 값을 반환합니다. (b가 0이면 예외 발생)"""
  if b == 0:
    raise ValueError("0으로 나눌 수 없습니다.")
  return a / b

@tool
def multiply(a: float, b: float) -> float:
  """두 수의 곱을 반환합니다."""
  return a * b

세 함수 모두 타입 힌트 + docstring + @tool이라는 같은 공식을 따릅니다. 특히 divide는 0으로 나누면 예외를 던지도록 방어 코드를 넣었습니다.

⚠️ 함정 — LLM은 도구를 "안 쓰고" 답할 수 있다 LLM은 확률 기반으로 추론합니다. 그래서 32 + 5 * 100 같은 간단한 계산은 "굳이 도구 안 써도 내가 알지" 하며 도구를 무시하고 직접 답해 버릴 수 있습니다. 우리가 "반드시 도구로 계산하는 계산기"를 원한다면, 이 습관을 명시적으로 막아야 합니다.
🔍 비유 — "암산 금지, 계산기만 써!"라는 시험 규칙 똑똑한 학생에게 계산기를 쥐여 줘도, 쉬운 문제는 암산으로 후딱 풀어 버립니다. 만약 반드시 계산기 사용 과정을 남겨야 하는 시험이라면, 감독관이 "모든 계산은 계산기로, 암산 금지"라는 규칙을 미리 못 박아야 하죠. system_prompt가 바로 이 감독관의 규칙입니다.
📥 코드
# AI는 확률 기반으로 추론하는데, tool를 사용하지 않고도 답을 할 수 있다고 판단하게 되면 tools를 사용하지 않을 수 있다
# 이런 경우를 방지하려면, system 메시지에 반드시 tool를 사용하도록 지시하는 내용을 추가해야 합니다.
agent_with_calculator = create_agent(
    model=model,
    tools=[add, divide, multiply],
    system_prompt="당신은 계산기입니다. 반드시 도구를 사용하여 계산을 수행해야 합니다. 절대 도구를 사용하지 않고 대답하지 마세요.")


result = agent_with_calculator.invoke({"messages": [
  {"role": "user", "content": "32 + 5 * 100를 계산해줘."},
]})

print("Agent의 응답:", result)
💡 system_prompt = Agent의 헌법 System Message는 대화 맨 앞에 깔리는 변하지 않는 행동 규칙입니다. 여기서는 "너는 계산기다 · 반드시 도구를 써라 · 절대 암산으로 답하지 마라"라는 세 문장으로 Agent가 매번 도구를 거치도록 강제했습니다.

5. 다단계 추론 관찰

32 + 5 * 100은 사람도 곱셈을 먼저, 덧셈을 나중에 하죠(연산자 우선순위). 놀랍게도 Agent도 이 순서를 스스로 지켜 도구를 단계별로 나눠 호출합니다. 한 번에 답을 뱉는 게 아니라, 도구 호출 → 결과 확인 → 다음 도구 호출을 반복하는 것이죠.

1질문 접수

"32 + 5 * 100를 계산해줘"

2곱셈 먼저

multiply(5, 100) → 500

3덧셈 다음

add(32, 500) → 532

4최종 답변

"결과는 532입니다."

result["messages"]를 출력하면 각 단계마다 AIMessage(tool_calls=...) → ToolMessage(content=...)가 번갈아 쌓이는 흐름을 직접 볼 수 있습니다.

▶ 이렇게 나와요 (핵심만 추려 표시)
Agent의 응답: {'messages': [
  HumanMessage(content='32 + 5 * 100를 계산해줘.', ...),
  AIMessage(content='', tool_calls=[multiply(a=5, b=100), ...]),   # 곱셈 먼저
  ToolMessage(content='500.0', name='multiply', ...),
  AIMessage(content='', tool_calls=[add(a=32, b=500)]),            # 그 다음 덧셈
  ToolMessage(content='532', name='add', ...),
  AIMessage(content='32 + 5 * 100의 결과는 532입니다.', ...)        # 최종 답변
]}
📘 보충 — 실제 실행은 조금 더 어수선할 수 있어요

위 흐름은 핵심만 추린 이상적인 그림입니다. 실제로 gpt-4o-mini로 돌려 보면, 첫 단계에서 multiply(5, 100)과 함께 add(32, 0) 같은 불필요한 도구 호출을 한꺼번에 시도하기도 합니다(모델이 여러 수를 병렬로 처리해 보려는 시도).

그래도 걱정 없습니다 — Agent는 중간 결과를 보고 스스로 다음 판단을 이어가며 결국 add(32, 500) → 532라는 올바른 최종 답에 도달합니다. "추론 → 행동 → 관찰 → 다시 추론"을 반복하는 것이 Agent의 본질이라, 경로가 매번 똑같지 않을 수 있다는 점만 기억하세요.

📚 한 장 정리

오늘의 핵심 Tool은 함수다. LLM(두뇌)에 Tool(손발)을 붙이면, "언제·어떤 인자로 도구를 부를지"를 스스로 판단하는 Agent가 된다.
  • Tool은 왜? — LLM은 학습 시점 이후·실시간 정보를 모른다(Knowledge Cutoff). Tool은 바깥세상과 잇는 전화기.
  • 작성 4단계 — 함수 작성 → 타입 힌트 → docstring → @tool. docstring이 곧 "언제 쓸지" 설명서.
  • create_agent(model, tools=[...]) — 두뇌(모델)에 손발(도구)을 붙여 Agent 채용.
  • 실행 흐름 — invoke 한 번에 HumanMessage → AIMessage(tool_calls) → ToolMessage → AIMessage가 쌓인다. 최종 답은 messages[-1].content.
  • 도구를 강제하려면 — LLM은 쉬운 문제를 도구 없이 답할 수 있다. system_prompt로 "반드시 도구 사용"을 못 박는다.
  • 다단계 추론 — 복잡한 요청은 도구 호출 → 결과 관찰 → 다음 도구 호출을 반복하며 스스로 풀어간다.
