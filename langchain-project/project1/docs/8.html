8

파라미터 튜닝 & 실험 정리 (선택)

선택 · 심화 ⏱ 반나절
🎯 목표

지금까지의 실험을 정리하고, 몇 개 파라미터를 바꿔 최적 설정을 근거와 함께 고른다.

🛠 할 일

이 STEP에는 새로 짤 코드가 없습니다. 이미 만든 것의 숫자만 바꿔가며 점수를 남기는 단계예요. 세 조각으로 나눠 보고, 맨 아래 기록표 템플릿을 채워 나가세요.

🧭 세 조각 한눈에

① 무엇을 바꿔볼지 고르기  →  ② 한 번에 하나씩 바꿔 채점하기  →  ③ 표로 모아 근거와 함께 결정하기

① 무엇을 바꿔볼까 — 손잡이는 네 개

지금까지 나온 숫자들은 대부분 "일단 이 값으로 시작하자"였습니다. 이제 근거를 만들 차례예요. 각 손잡이는 어느 지표를 움직이는지가 다릅니다.

손잡이어디에올리면주로 움직이는 지표
chunk_size
500·1000·1500		 ingest.py 문맥은 풍부해지되 관계없는 내용이 함께 딸려옴 올리면 context_precision↓ · 내리면 context_recall↓
k (검색 개수)
3·4·6		 rag.py 정답을 놓칠 확률은 줄고 노이즈와 비용은 늚 context_recall↑ · context_precision↓
rerank top_n
3·4·6		 rag.py LLM에게 더 많은 근거를 주지만 희석됨 faithfulness · context_precision
hybrid weights
[0.3,0.7]·[0.5,0.5]		 rag.py BM25 쪽을 키우면 용어·조항번호 질문에 강해짐 context_recall (질문 유형에 따라)
⚠️ chunk_size를 바꿨다면 반드시 다시 인덱싱하세요

이 값은 벡터DB에 이미 저장된 청크의 모양을 정하는 값이라, 코드만 고치면 아무 일도 일어나지 않습니다. uv run python ingest.py를 다시 돌려야 반영됩니다. (ingest.py가 저장 전에 기존 컬렉션을 비우므로 chroma_db/를 손으로 지울 필요는 없습니다. 다만 청크 텍스트가 달라져 캐시가 안 먹으므로, 이때만은 임베딩 비용이 다시 듭니다.) 나머지 세 개는 검색 시점의 값이라 재인덱싱 없이 바로 반영돼요.

② 한 번에 하나씩만 바꾸기

두 개를 동시에 바꾸면 무엇 때문에 좋아졌는지 알 수 없습니다. 하나 바꾸고 → 채점하고 → 기록하고 → 되돌리거나 유지하고, 이 순서를 지키세요. evaluate.py는 eval_<mode>.csv로 저장하니 그대로 두면 덮어써집니다. 실행 직후 이름을 바꿔 보관하세요.

터미널
# 1) 설정을 '하나만' 바꾼다 (예: rag.py에서 k=4 → 6)
#    두 개를 동시에 바꾸면 무엇 덕분에 좋아졌는지 알 수 없게 된다.

# 2) 채점한다
uv run python evaluate.py rerank

# 3) 결과 파일 이름을 바꿔 보관한다.
#    evaluate.py는 항상 eval_rerank.csv로 저장하므로, 그냥 두면 다음 실험이 덮어써 버린다.
#    mv = 이름 바꾸기(이동). 파일명에 '무엇을 바꿨는지'를 적어 두면 나중에 찾기 쉽다.
mv eval_rerank.csv exp_k6_rerank.csv

# 4) 커밋한다. 메시지에 '바꾼 값 + 점수 변화'를 함께 적는 것이 요령 —
#    이러면 git log가 그대로 실험 노트가 되고, STEP 9에서 README를 쓸 때 로그만 훑으면 된다.
#    -am = 수정된 파일을 모두 담아(-a) 메시지와 함께(-m) 커밋
git commit -am "실험: k=4 -> 6 (context_recall 0.71 -> 0.78, precision 0.66 -> 0.59)"

커밋 메시지에 바꾼 값과 점수 변화를 같이 적어 두는 것이 요령입니다. 이러면 git log가 그대로 실험 노트가 되고, STEP 9에서 README를 쓸 때 기억을 더듬는 대신 로그만 훑으면 됩니다.

③ 표로 모아 "왜 이 설정인지" 한 문단

최종 산출물은 표 하나와 문단 하나입니다. 여기서 중요한 건 모든 지표가 함께 오르는 설정은 거의 없다는 점이에요. 보통 recall과 precision은 서로 반대로 움직입니다. 그래서 "다 좋은 설정"이 아니라 "우리 서비스는 어느 쪽이 더 중요한가"를 정하고 고르는 겁니다 — 약관 QA라면 근거를 빠뜨리지 않는 쪽(recall)에 무게를 두는 식으로요. 그 판단을 문장으로 적는 것이 이 STEP의 진짜 결과물입니다.

최종 선택: ___ — 이유: _______________ (예: "exp1을 택했다. precision이 0.07 떨어졌지만 recall이 0.07 올랐고, 약관 QA에서는 근거를 빠뜨리는 쪽이 더 치명적이라고 판단했다.")

✅ 검증 게이트 3가지 이상 설정의 지표를 한 표에 모으고, 최종 설정을 숫자 근거로 선택한 문장이 있으면 통과.
