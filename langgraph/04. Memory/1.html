4-1. Short-term Memory — Checkpointer와 State History

실습 노트북: 1.ipynb  ·  대상 범위: 4강 Memory 첫 번째 — 단기 메모리 저장과 그 기록 열어보기  ·  난이도: 🟢 입문~중급

3강까지 만든 그래프는 전부 한 번 쓰고 잊어버리는 기계였습니다. 이번 장에서는 그 그래프에 기억을 붙입니다. 새로 배울 문법은 딱 세 개 — compile(checkpointer=...), get_state(), get_state_history(). 이 셋만으로 에이전트가 지금 무엇을 어떻게 기억하고 있는지를 통째로 열어볼 수 있게 됩니다.

이 장에서 배우는 것

전반부는 기억을 저장하는 법 — LangChain에서 해봤던 InMemorySaver와 thread_id를 LangGraph 문법으로 옮기는 것뿐이라 금방 끝납니다. 후반부가 진짜 알맹이입니다. 저장된 기억을 자동차 블랙박스 돌려보듯 한 장면씩 되감아 보는 것이고, 이 되감기가 다음 장 Time Travel의 준비 운동입니다.

4강 지도 — 왜 이번 강의는 빠르게 지나가나

4강의 목차는 지난 LangChain 강의와 같습니다 — 단기 메모리를 먼저, 장기 메모리를 나중에. 다만 진행은 훨씬 빠릅니다. 메모리는 LangChain에서 배운 문법을 새 그릇에 옮겨 담는 일에 가깝기 때문입니다.

복습 → LangGraph 문법 → State History → Time Travel

순수하게 새로 배우는 것은 타임 트래블처럼 "LangGraph에서만 되는 것들"이고, 이번 문서는 그중 단기 메모리와 State History까지를 다룹니다.

1. Short-term Memory 복습 — 수첩 하나와 고객 카드 하나

슬라이드의 두 줄이 4강 전체의 뼈대입니다.

구분Short-term memory (단기)Long-term memory (장기)
담당 부품CheckpointerStore
저장 단위대화 스레드(세션) 하나사용자 하나
유효 범위그 채팅방 안에서만모든 채팅방에 걸쳐
ChatGPT로 치면지금 열어둔 대화창의 스크롤개인 맞춤 설정 (닉네임 · 직업 · 나에 대한 정보)
다루는 곳이번 문서4강 후반부
🔍 비유 — 단골 미용실의 수첩과 고객 카드

단기 메모리는 오늘 상담하면서 적는 수첩입니다. "앞머리는 눈썹 위로, 옆은 좀 남기고" — 오늘 오간 말이 순서대로 적혀 있어 대화가 이어지지만, 그 수첩은 오늘 이 자리에만 놓여 있습니다. 장기 메모리는 카운터의 고객 카드입니다. "모발이 얇음, 파마 알러지 있음" — 몇 달 뒤 다른 자리에 앉아도 따라옵니다. ChatGPT에서 새 대화를 열면 앞 대화는 사라지지만 개인 맞춤 설정은 어느 방에서든 반영되는, 정확히 그 차이입니다.

LangChain에서는 이렇게 했다 — 에이전트에게 수첩과 펜을 쥐여주기

두 가지만 짚습니다. 첫째, Checkpointer는 대화 상태를 담아둘 "저장소"이고 InMemorySaver는 그중 가장 간단한, 메모리(RAM)에 담아두는 구현체입니다. 둘째, import 경로가 이미 langgraph입니다 — 메모리는 원래부터 LangGraph의 기능이었고 LangChain이 빌려 쓴 것이죠. 이번 장이 빠르게 진행되는 이유입니다.

thread_id — 대화방마다 붙는 번호표

invoke에 들어가는 것은 두 덩어리 — 이번에 할 말(messages)과 어느 방에서 할 말인지(thread_id)입니다. 같은 thread_id로 호출하면 대화가 이어지고, 번호를 바꾸면 새 방이 열립니다.

🔍 비유 — 병원 차트 번호

병원에서 "3번 차트요"라고 하면 그 차트가 나오고, 의사는 지난 처방을 보고 이어서 진료합니다. "4번 차트요"라고 하면 다른 사람의 차트가 나오죠. Checkpointer는 차트 보관함, thread_id는 차트 번호입니다. 보관함을 달아주는 것과 번호를 대는 것은 별개의 동작 — 이 구분이 뒤에서 계속 쓰입니다.

2. Checkpointer — LangGraph에서는 어디에 넣나

LangChain에서는 create_agent(...)라는 완성품 함수에 checkpointer=를 끼워 넣으면 됐지만, LangGraph에서는 StateGraph로 그래프를 직접 조립합니다. 그러면 수첩은 어디서 쥐여줄까요? 답은 맨 마지막, compile()할 때입니다.

컴파일은 "조립 끝, 실행 가능한 물건으로 만들어줘"라는 신호입니다. 바로 그 순간에 checkpointer를 함께 넘기면 단기 메모리가 지원되는 그래프가 만들어집니다.

🔍 비유 — 출고 직전에 블랙박스를 장착한다

엔진을 얹고(add_node), 배선을 연결하는(add_edge) 조립 공정은 주행 기록과 무관합니다. 출고 직전(compile)에 블랙박스를 달면, 차의 구조는 그대로인데 이제부터 어디를 어떻게 달렸는지가 전부 기록되죠. 4장 State History가 바로 그 블랙박스를 돌려보는 일입니다 — 블랙박스를 안 단 차는 돌려볼 영상이 없습니다.

딱 한 줄만 다르다 — 실행 방법은 완전히 같다

차이는 딱 한 군데, 체크포인터를 넘기는 위치뿐입니다.

단계LangChainLangGraph
수첩 만들기 memory = InMemorySaver()  — 완전히 동일
수첩 쥐여주기 create_agent(model, tools, checkpointer=memory)
에이전트 생성 시		 workflow.compile(checkpointer=memory)
컴파일 시
호출하기 app.invoke(input, config={'configurable': {'thread_id': '1'}})  — 완전히 동일
💡 한 문장으로 기억하세요

"단기 메모리는 compile할 때 붙이고, invoke할 때 지목한다." 붙이는 건 그래프 전체에 한 번, 지목은 호출할 때마다입니다. "체크포인터는 넣었는데 왜 기억을 못 하지?"는 십중팔구 config를 빼먹은 경우입니다.

STEP 1. Model 정의

순서는 늘 같습니다 — ①모델 → ②State → ③Node → ④그래프 → ⑤실행. 이번 그래프는 도구도 분기도 없는 노드 하나짜리 챗봇입니다. 메모리만 도드라져 보이게 나머지를 일부러 걷어냈습니다.

📥 코드
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")

STEP 2. State 정의

📥 코드
from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages
from langchain.messages import HumanMessage, SystemMessage

class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

2강의 그 messages 필드 그대로, add_messages 리듀서 덕에 새 메시지가 덮어쓰지 않고 뒤에 쌓입니다.

⚠️ 흔한 오해 — "리듀서가 있으면 기억하는 것 아닌가?"

add_messages가 쌓아주는 건 딱 한 번의 invoke 안에서입니다. invoke가 끝나면 그 State는 사라지고, 다음 invoke는 빈 State에서 시작해요. 리듀서는 "한 판 안에서의 누적", 체크포인터는 "판과 판 사이의 보존" — 층이 다르고, 둘 다 있어야 대화가 이어집니다.

STEP 3. Node 정의

📥 코드
def chatbot_node(state: ChatState):
    return {"messages": [model.invoke(state["messages"])]}

한 줄짜리 노드 — State의 메시지를 통째로 모델에게 주고, 답변을 리스트로 감싸 반환합니다. 여기서 기억의 실체가 드러납니다. 모델은 아무것도 기억하지 못하고 매번 state["messages"]를 통째로 다시 읽을 뿐이에요. "기억한다"는 건 "지난 대화를 매번 다시 읽혀준다"는 뜻이고, 체크포인터는 그 읽어줄 원고를 보관해주는 장치입니다.

STEP 4. 그래프 생성 — 그리고 체크포인터 장착

📥 코드 · 조립
from langgraph.graph import StateGraph, START, END

workflow = StateGraph(ChatState)

workflow.add_node("chatbot", chatbot_node)

workflow.add_edge(START, "chatbot")
workflow.add_edge("chatbot", END)

START → chatbot → END — 여기까지는 조립 공정. 이제 블랙박스를 달 차례입니다.

📥 코드 · 수첩 만들기
# InMemorySaver 객체 import
from langgraph.checkpoint.memory import InMemorySaver

memory = InMemorySaver()
📥 코드 · 컴파일하며 장착
app = workflow.compile(checkpointer=memory)

끝입니다. 이 그래프는 이제 대화를 기억합니다.

⚠️ 그래프 그림에는 아무 변화가 없습니다

시각화하면 여전히 __start__ → chatbot → __end__입니다. 체크포인터는 그래프의 구조가 아니라 실행 환경이라 — 블랙박스를 달았다고 차의 설계도가 바뀌지 않듯 — 그림으로는 확인할 수 없고, 실제로 대화를 시켜봐야 압니다. 그게 STEP 5입니다.

STEP 5. 실행 — 정말 기억하는지 확인하기

시나리오는 세 번의 호출 — ①이름을 알려주고 → ②같은 방에서 되묻고 → ③다른 방에서 똑같이 되묻기. ②는 맞히고 ③은 못 맞혀야 "방 단위로 기억한다"가 증명됩니다.

📥 코드 · 방 번호표 만들기
config_1 = {'configurable': {'thread_id': '1'}}

모양은 딕셔너리 안에 딕셔너리 — 바깥 키는 반드시 'configurable'. 이 두 겹을 헷갈리는 게 이 장에서 가장 흔한 오타입니다.

① 첫 대화 — 이름을 알려준다

📥 코드
from langchain.messages import HumanMessage

input_msg1 = {"messages": [HumanMessage(content="안녕? 내 이름은 Jay야.")]}
response1 = app.invoke(input_msg1, config=config_1)

config=config_1이 붙었다는 것 하나만 다릅니다.

📤 response1 (길어서 요약)
{'messages': [
  HumanMessage(content='안녕? 내 이름은 Jay야.', ...),
  AIMessage(content='안녕하세요, Jay님! 만나서 반가워요. 오늘은 어떤 도움을 드릴까요? ...', ...)
]}

마지막 답변만 보고 싶다면 이렇게 꺼냅니다.

📥 코드
response1['messages'][-1].content
📤 출력
'안녕하세요, Jay님! 만나서 반가워요. 오늘은 어떤 도움을 드릴까요? 관심 있는 주제나 하고 싶은 일,
알고 싶은 게 있으면 말씀해 주세요. 공부, 코딩, 글쓰기, 여행 팁 등 뭐든 함께 이야기해볼게요.'

② 같은 스레드에서 되묻기 — 기억한다

📥 코드
input_msg2 = {"messages": [HumanMessage(content="내 이름이 뭐라고?")]}
response2 = app.invoke(input_msg2, config=config_1)   # ★ 같은 config_1

새로 넣은 메시지는 "내 이름이 뭐라고?" 한 줄뿐인데, 반환값을 보면 —

📤 response2 (길어서 요약)
{'messages': [
  HumanMessage(content='안녕? 내 이름은 Jay야.', ...),               ← 지난 턴에 저장돼 있던 것
  AIMessage(content='안녕하세요, Jay님! 만나서 반가워요. ...', ...),   ← 지난 턴에 저장돼 있던 것
  HumanMessage(content='내 이름이 뭐라고?', ...),                     ← 이번에 새로 넣은 것
  AIMessage(content='당신의 이름은 Jay예요. 세션 동안 Jay로 부를게요. ...', ...)
]}

앞의 두 메시지가 되살아나 있습니다. 체크포인터가 thread_id: '1' 서랍에서 지난 대화를 꺼내 앞에 붙여줬고, 모델은 네 줄짜리 대화 전체를 읽고 답을 만들었습니다.

📤 response2['messages'][-1].content
'당신의 이름은 Jay예요. 세션 동안 Jay로 부를게요. 다른 이름으로 불리고 싶으면 알려 주세요.'

③ 스레드를 바꾸면 — 깨끗하게 잊는다

이제 반대로 — 번호표만 2번으로 바꾸고, 질문은 똑같이 던져봅니다.

📥 코드
config_2 = {"configurable": {"thread_id": "2"}}   # ★ 방 번호만 2로

input_msg3 = {"messages": [HumanMessage(content="내 이름이 뭐라고?")]}
response3 = app.invoke(input_msg3, config=config_2)

response3['messages'][-1].content
📤 출력
'제가 당신의 이름을 알 수 없어요. 지금 알려주시면 그 이름으로 불러드릴게요.
원하시는 호칭이나 닉네임이 있으면 그것으로도 부를 수 있어요. 어떤 이름으로 부를까요?'

모른다고 합니다. 모델도 그래프도 체크포인터도 그대로인데 번호표 하나 바뀌었다고 완전한 초면이 됐죠.

💡 이 세 번의 호출이 증명한 것

기억은 그래프가 아니라 스레드에 붙는다. 실제 챗봇 서비스에서 사용자마다, 대화창마다 thread_id를 다르게 발급하면 서로의 대화가 섞이지 않습니다. 반대로 잘못 관리하면 A 사용자의 대화가 B에게 보이는 사고가 나죠. thread_id는 단순한 문자열이지만 사실상 경계선입니다.

⚠️ InMemorySaver는 프로그램이 꺼지면 사라집니다

이름 그대로 메모리(RAM)에만 담아두니 런타임을 재시작하면 모든 대화가 증발합니다. 실습용으로는 이게 제일 편하고, 실서비스에서는 DB 기반 체크포인터로 바꿔 끼웁니다. 교체 자리는 compile(checkpointer=...) 한 줄 — 수첩을 서류함으로 바꾸는 것일 뿐, 나머지 코드는 그대로입니다. (공식 문서 — Persistence)

4. State History — 에이전트 속 블랙박스를 돌려보자

지금까지는 결과만 봤습니다. 이제 상자를 열어 START에서 END까지 가는 동안 각 지점에서 에이전트가 어떤 기억을 들고 있었는지를 한 장면씩 돌려봅니다. 자동차 블랙박스를 돌려보는 것과 같은 동작이라 문법 이름도 State History입니다.

잠깐 복습 — State는 "작업자가 쓰는 공책"이었다

2강에서 잡아둔 정의 — State는 공책, Node는 작업자, Edge는 선 — 를 그대로 이어서 생각하면, 노드라는 작업자가 일할 때마다 공책에 뭔가를 적습니다.

  • 사용자의 질문이 들어오면 → messages 칸에 HumanMessage가 적히고
  • LLM이 도구를 부르기로 하면 → 그 결정이 AIMessage로 적히고
  • 도구 노드가 실행되면 → 결과가 ToolMessage로 적히고
  • END에 도달하면 → 그때까지 적힌 공책을 통째로 반환합니다

State History를 돌려본다는 건 각 작업자가 공책에 무엇을 적었는지 순서대로 확인하는 일입니다. 공책의 매 페이지를 찍어둔 사진 한 장이 StateSnapshot이고, 들여다보는 메서드는 두 개 — 하나는 마지막 한 장만, 하나는 전부.

1get_state(config)

현재 시점의 스냅샷 한 장

2get_state_history(config)

과거부터 현재까지 전부 (역순)

① get_state — 블랙박스의 마지막 한 장면

📥 코드
current_state = app.get_state(config_1)   # ★ 조회할 때도 '어느 방인지'가 필요하다
current_state
📤 출력 (길어서 줄바꿈해 옮김)

  values={'messages': [HumanMessage(content='안녕? 내 이름은 Jay야.', ...),

StateSnapshot의 네 칸 — 하나씩 뜯어보기

① values — 그 시점의 공책 내용

말 그대로 그 시점의 State 딕셔너리 — messages에 휴먼 → AI → 휴먼 → AI 네 개가 순서대로, 아까 response2로 봤던 값 그대로 들어 있습니다.

📥 코드 · 마지막 대화만 꺼내기
# 현재 스텝
current_state.values['messages'][-1].content
📤 출력
'당신의 이름은 Jay야. 앞으로 Jay라고 부르면 될까?'

② next — 다음에 실행될 노드

이 시점에서 그래프를 재개하면 누가 일하게 되는지. 지금은 END까지 끝난 상태라 비어 있습니다.

📥 코드
# 다음 실행할 노드
current_state.next
📤 출력
()

이 칸은 나중에 interrupt와 멀티 에이전트에서 "어디서 멈춰 있는지" 알려주는 표지판으로 크게 쓰입니다. 비어 있지 않다는 건 "아직 할 일이 남아 있다"는 뜻입니다.

③ config — 이 장면의 좌표

📥 코드
current_state.config
📤 출력
{'configurable': {'thread_id': '1',
                  'checkpoint_ns': '',
                  'checkpoint_id': '1f18f1bc-3b00-6994-8004-52293e85e0f7'}}

우리가 넣어준 thread_id: '1' 옆에 처음 보는 값 — LangGraph가 자동 발급한 고유 식별자 checkpoint_id가 붙어 있습니다. 같은 노드가 여러 번 호출될 수 있으니 "에이전트 노드가 일한 시점"이라는 말만으로는 부족해서, 저장되는 매 시점마다 고유 번호를 찍어두는 것입니다.

🔍 비유 — 게임의 세이브 슬롯

thread_id는 "어떤 캐릭터의 플레이인가", checkpoint_id는 "그 플레이의 몇 번 세이브 파일인가"입니다. 캐릭터만 고르면 가장 최근 세이브로 이어서 하게 되죠 — 지금까지 우리가 한 일입니다. 슬롯 번호까지 찍어서 부르면 "그 시점"으로 돌아갈 수 있고, 그게 다음 장 Time Travel입니다. checkpoint_id는 긴 문자열로 보이지만 사실은 과거로 가는 좌표예요.

④ metadata와 parent_config — 이력 추적용

metadata={'source': 'loop', 'step': 4, 'parents': {}} — source는 "루프를 돌다가 저장됨", step은 "네 번째 단계에서 저장됨". parent_config는 직전 스냅샷의 좌표로, 스냅샷들이 부모-자식 사슬로 연결되어 있습니다. 지금은 source와 step만 눈에 익혀두세요 — 바로 다음 절에서 이 두 값으로 순서를 읽습니다.

② get_state_history — 영상 전체를 되감기

쓰는 법은 get_state와 똑같이 config를 넣으면 되는데, 반환값이 제너레이터라서 list()로 감싸주는 습관을 들이는 게 좋습니다.

📥 코드
history = list(app.get_state_history(config_1))
⚠️ 순서에 주의 — history[0]이 가장 최근입니다

시간의 역순으로 반환됩니다 — Index 0이 "대화가 모두 끝난 상태"(최근), Index 5가 "아무 대화도 없는 초기 상태"(태초). 맨 앞이 방금, 맨 뒤가 태초로 기억하세요. 블랙박스는 보통 "방금 무슨 일이 있었지?"를 보려고 돌리니, 뒤에서부터 재생하는 게 자연스럽습니다.

스냅샷을 통째로 출력하면 지저분하니 필요한 칸만 뽑아 출력하는 반복문을 돌려봅시다.

for i, snapshot in enumerate(history):

    # 해당 시점의 대화 내용

    print(f" - Metadata: {snapshot.metadata}") # 단계 정보 (step, source 등)

💡 규칙 두 개만 잡으면 스냅샷은 다 읽힙니다

규칙 1 — source가 'input'이면 새 요청이 들어온 순간, 'loop'면 그래프가 한 걸음 나아간 순간. invoke를 두 번 했으니 'input'도 두 번(step -1, step 2) 나왔죠. 규칙 2 — next가 비어 있으면 그 턴이 끝난 것, 차 있으면 그 노드가 다음 차례. Time Travel이 가능한 이유가 이겁니다 — 스냅샷에는 "그때의 데이터"뿐 아니라 "그때 이어서 할 일"까지 들어 있습니다.

노드 하나짜리 예제에서도 스냅샷이 여섯 장 나왔으니, 도구와 분기가 붙으면 훨씬 촘촘해집니다. 그래서 State History가 LangGraph의 디버깅 도구로 쓰입니다 — "왜 이런 답이 나왔지?" 싶을 때 결과가 아니라 과정을 열어볼 수 있으니까요.

자주 걸리는 함정 6가지

🕳️ 메모리에서 실제로 밟게 되는 지뢰

1. compile()에 체크포인터를 안 넘긴다

memory = InMemorySaver()까지 써놓고 workflow.compile()을 그냥 호출 — 수첩을 만들어놓고 쥐여주지 않은 것. 에러 없이 조용히 아무것도 기억하지 못해서 제일 찾기 어려운 부류입니다.

2. invoke에 config를 빼먹는다

체크포인터를 붙인 그래프는 thread_id를 반드시 요구합니다 — 어느 서랍에 넣을지 모르니까요. 빼먹으면 실행 자체가 막힙니다.

3. configurable 키를 빠뜨리거나 오타를 낸다

{'thread_id': '1'}처럼 한 겹으로 쓰는 실수가 정말 흔합니다. 올바른 모양은 {'configurable': {'thread_id': '1'}} — 딕셔너리 안에 딕셔너리입니다.

4. 이전 대화를 직접 다시 넣어준다

지난 메시지를 messages에 손으로 다시 넣으면 체크포인터가 꺼내온 것 위에 또 쌓여 대화가 두 벌이 됩니다. 새 메시지만 넣으세요 — 앞의 것은 체크포인터가 알아서 붙여줍니다.

5. get_state_history의 순서를 거꾸로 안다

history[0]이 최신, 마지막 원소가 가장 옛날 — 일반 로그와 반대입니다. "블랙박스는 뒤에서부터 돌린다"로 기억하세요. 제너레이터라서 list()로 감싸야 인덱스 접근이 됩니다.

6. InMemorySaver를 실서비스에 쓴다

프로세스가 죽으면 전부 사라져 재배포 순간 모든 사용자의 대화가 초기화됩니다. 실서비스로 갈 때 compile(checkpointer=...) 한 줄만 교체하면 됩니다.

💡 디버깅 요령 — 기억이 되는지 3초 만에 확인하는 법

이름 알려주기 → 이름 되묻기가 가장 빠른 테스트입니다. 그래도 이상하면 app.get_state(config).values['messages']의 길이를 찍어보세요. 턴마다 2씩 늘어야 정상 — 늘 2에서 멈추면 저장이 안 되는 것, 4, 8, 16처럼 뛰면 대화를 중복으로 넣고 있는 것입니다.

전체 코드 한눈에 보기

# ══ STEP 1. Model ═════════════════════════════════════
from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")

# ══ STEP 2. State ═════════════════════════════════════
from langchain.messages import AnyMessage, HumanMessage, SystemMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]   # ★ 한 판 안에서의 누적

# ══ STEP 3. Node ══════════════════════════════════════
def chatbot_node(state: ChatState):
    return {"messages": [model.invoke(state["messages"])]}

# ══ STEP 4. Graph ═════════════════════════════════════
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

workflow = StateGraph(ChatState)
workflow.add_node("chatbot", chatbot_node)
workflow.add_edge(START, "chatbot")
workflow.add_edge("chatbot", END)

memory = InMemorySaver()                          # ★ 수첩 만들기
app = workflow.compile(checkpointer=memory)       # ★ 컴파일할 때 쥐여주기 = 판과 판 사이의 보존

# ══ STEP 5. Run ═══════════════════════════════════════
config_1 = {'configurable': {'thread_id': '1'}}   # ★ 두 겹 딕셔너리

input_msg1 = {"messages": [HumanMessage(content="안녕? 내 이름은 Jay야.")]}
response1 = app.invoke(input_msg1, config=config_1)
print(response1['messages'][-1].content)

input_msg2 = {"messages": [HumanMessage(content="내 이름이 뭐라고?")]}
response2 = app.invoke(input_msg2, config=config_1)   # ★ 같은 방 → 기억함
print(response2['messages'][-1].content)

config_2 = {"configurable": {"thread_id": "2"}}
input_msg3 = {"messages": [HumanMessage(content="내 이름이 뭐라고?")]}
response3 = app.invoke(input_msg3, config=config_2)   # ★ 다른 방 → 못 기억함
print(response3['messages'][-1].content)

# ══ State History ═════════════════════════════════════
# ① 현재 시점 스냅샷 한 장
current_state = app.get_state(config_1)
current_state.values['messages'][-1].content   # 그 시점의 공책
current_state.next                             # 다음에 실행될 노드
current_state.config                           # thread_id + checkpoint_id (= 시점 좌표)

# ② 과거부터 현재까지 전부 (역순, 제너레이터이므로 list로 감싸기)
history = list(app.get_state_history(config_1))

for i, snapshot in enumerate(history):
    print(f"\n[Snapshot {i}]")
    print(f" - Created At: {snapshot.created_at}")
    msgs = snapshot.values.get("messages", [])
    if msgs:
        last_msg = msgs[-1]
        sender = "AI" if last_msg.type == "ai" else "User"
        print(f" - 마지막 대화: [{sender}] {last_msg.content}")
    else:
        print(" - (대화 시작 전 초기 상태)")
    print(f" - Next: {snapshot.next}")
    print(f" - Metadata: {snapshot.metadata}")

📚 한 장 정리

오늘의 핵심 한 문장

기억은 compile할 때 붙이고(checkpointer), invoke할 때 지목하며(thread_id), get_state_history로 되감아 볼 수 있다.

  • 메모리는 두 종류 — 단기(Checkpointer)는 대화 스레드 단위, 장기(Store)는 사용자 단위. ChatGPT로 치면 대화창의 스크롤 vs 개인 맞춤 설정.
  • LangChain과 딱 한 군데만 다르다 — create_agent(..., checkpointer=memory) 대신 workflow.compile(checkpointer=memory). 호출 방법(config)은 동일.
  • thread_id는 방 번호표 — {'configurable': {'thread_id': '1'}}, 딕셔너리 두 겹. 기억은 그래프가 아니라 스레드에 붙는다.
  • 리듀서와 체크포인터는 층이 다르다 — add_messages는 한 번의 invoke 안에서의 누적, 체크포인터는 invoke 사이의 보존. 둘 다 있어야 대화가 된다.
  • 두 메서드 — get_state(config)는 현재 스냅샷 한 개, get_state_history(config)는 전부(시간 역순, list()로 감싸기). get_state는 곧 history[0].
  • StateSnapshot의 네 칸 — values(그 시점의 공책), next(다음 실행될 노드, 비면 턴 종료), config(thread_id+checkpoint_id = Time Travel의 좌표), metadata(source·step으로 이력 추적).
  • InMemorySaver는 휘발성 — 실습엔 최적, 실서비스엔 DB 기반 체크포인터. 교체 지점은 compile 한 줄.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

블랙박스를 단 자동차. 조립 공정(add_node·add_edge)과 블랙박스 장착(compile)은 별개고, 주행 기록은 차량 번호(thread_id)별로 나뉩니다. 영상을 돌려보면(get_state_history) 최신 장면부터 거꾸로 재생되고, 매 장면에 찍힌 타임코드(checkpoint_id)가 다음 장의 입장권입니다.

다음 — 과거로 돌아가 사건을 바꾸기

재료는 다 모았습니다. checkpoint_id가 돌아갈 좌표, next가 그 시점에서 다시 시작될 지점입니다. 특히 Snapshot 1 — "질문은 들어왔지만 챗봇이 아직 답하지 않은 상태"를 기억해두세요. 에이전트가 엉뚱한 결정을 내리려는 순간으로 돌아가 그 결정을 갈아끼우는 것 — 그게 다음 장 Time Travel에서 할 일입니다.
