04. 캐시 임베더 (CacheBackedEmbeddings)

실습 노트북: 04.ipynb  ·  원문: docs/04.rag.md 2.3 Embed  ·  난이도: 🟢 입문  ·  선행: 03. RAG Split

이 자료는 실습 노트북(04.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. RAG를 만들다 보면 같은 문서를 몇 번이고 다시 임베딩하게 됩니다. 그런데 임베딩은 API 호출마다 돈이 나가고 시간이 걸리죠. 이 장에서는 "한 번 계산한 임베딩 결과를 하드디스크에 저장해두고 재사용"하는 캐시 임베더(CacheBackedEmbeddings)를 비유와 실험으로 익힙니다.

🔍 비유 — 유료 번역가 vs 내 번역 공책 "How are you?"를 한국어로 바꿔야 할 때, 매번 유료 번역가(OpenAI 임베딩 API)에게 돈을 내고 맡길 수도 있습니다. 하지만 똑똑한 사람은 한 번 번역한 문장을 공책에 적어둡니다. 다음에 똑같은 "How are you?"가 오면 번역가를 부르지 않고 공책을 펼쳐 즉시 답을 베낍니다. 돈도 안 들고 훨씬 빠르죠. 캐시 임베더가 바로 이 번역 공책입니다.
이 장에서 배우는 것 임베딩 자체는 이미 앞에서 다뤘습니다. 여기서는 "임베딩 과정의 중복을 없애 비용·시간을 아끼는 법"에 집중합니다. 핵심은 딱 하나 — 이미 계산한 텍스트는 다시 계산하지 않고 파일에서 꺼내 쓴다는 것입니다.
구분캐시 없음캐시 있음 (CacheBackedEmbeddings)
같은 문장 100번 임베딩OpenAI에 100번 요청 (돈 100번)1번만 요청, 나머지 99번은 파일에서 로드 (돈 1번)
코드 재실행 (문서 그대로)전부 다시 임베딩전부 캐시에서 즉시 로드 (API 호출 0)
속도매번 네트워크 왕복내 컴퓨터 파일 읽기 (훨씬 빠름)
⚠️ 실행 전 준비 직접 돌려보려면 .env에 OPENAI_API_KEY가 있어야 하고, 같은 폴더에 pdf-file.pdf가 필요합니다. 임베딩 결과 파일은 ./cache/ 폴더에 쌓입니다. 이 교재만 읽을 때는 필요 없습니다.

1. 임베딩 복습 — 텍스트를 숫자로 바꾸기

캐싱 이야기를 하기 전에, 임베딩이 뭐였는지 한 번만 짚고 갑니다. 임베딩은 "인공지능" 같은 텍스트를 컴퓨터가 계산할 수 있는 숫자 배열(벡터)로 바꾸는 작업입니다.

🔍 비유 — 의미 지도 위의 GPS 좌표 거대한 의미 지도가 있다고 상상해보세요. 이 지도 위에서 뜻이 비슷한 단어들은 서로 가까이 모여 있습니다. "강아지"와 "개"는 바로 옆 동네, "자동차"는 저 멀리 다른 구역에 있죠. 임베딩은 어떤 텍스트가 이 지도의 어디쯤에 있는지를 나타내는 GPS 좌표(숫자 목록)를 찍어주는 일입니다. 좌표가 가까우면 의미가 비슷하다 — 이것이 나중에 "유사한 문서 검색"의 원리가 됩니다.
📥 코드
from langchain_openai import OpenAIEmbeddings

# 임베딩 모델 객체 생성 (가성비가 좋은 small 모델 사용)
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

# 텍스트 임베딩 수행
query_result = embeddings.embed_query('인공지능')

print(f"벡터의 길이(차원 수): {len(query_result)}")
print(f"변환된 벡터의 앞부분 5개 값: {query_result[:5]}")
▶ 이렇게 나와요
벡터의 길이(차원 수): 1536
변환된 벡터의 앞부분 5개 값: [-0.01385547686368227, 0.0200613122433424, 0.007972599007189274, 0.007269692607223988, -0.01721169427037239]

"인공지능"이라는 짧은 단어 하나가 1536개의 숫자로 변환됐습니다. 이 1536개의 숫자가 곧 의미 지도 위의 좌표입니다. 사람 눈에는 의미 없는 소수점 나열이지만, 컴퓨터는 이 좌표들 사이의 거리를 계산해 "누가 누구와 비슷한지"를 판단합니다.

💡 embed_query vs embed_documents embed_query는 문장 하나를 벡터로 바꾸고, embed_documents는 여러 문장(리스트)을 한 번에 벡터로 바꿉니다. RAG에서 문서 청크 수백 개를 처리할 때는 뒤에 나올 embed_documents를 씁니다. 바로 여기에 캐싱이 큰 힘을 발휘하죠.

2. 캐시 임베더 만들기 — from_bytes_store

이제 본론입니다. 방금 만든 임베딩 모델을 그대로 쓰지 않고, "캐시 껍데기(Wrapper)"로 한 번 감싸줍니다. 감싸는 데 필요한 재료는 딱 두 가지 — 실제 계산을 할 임베딩 모델과, 결과를 저장할 창고입니다.

🔍 비유 — 번역가 앞에 앉은 비서 캐시 임베더는 번역가(OpenAI) 앞에 비서 한 명을 앉혀두는 것과 같습니다. 문장이 들어오면 비서가 먼저 서랍(./cache/)을 뒤져 "이거 예전에 번역한 적 있나?" 확인합니다. 있으면 서랍에서 꺼내 바로 주고, 없을 때만 번역가에게 넘깁니다. 그리고 번역가가 새로 준 결과도 서랍에 차곡차곡 보관해둡니다. 우리는 이 비서(cached_embedder)하고만 대화하면 되고, 비서가 알아서 돈을 아껴줍니다.
📥 코드
from langchain_openai import OpenAIEmbeddings
from langchain_classic.embeddings import CacheBackedEmbeddings
from langchain_classic.storage import LocalFileStore

underlying_embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

store = LocalFileStore("./cache/")

# 시를 사용할 **준비(설정)**만 마친 상태이기 때문에,
# 실제로 임베딩 작업을 수행하는 명령을 내리기 전까지는
# ./cache/ 폴더에 아무런 파일도 생성되지 않습니다.

cached_embedder = CacheBackedEmbeddings.from_bytes_store(
    underlying_embeddings,
    store,
    namespace=underlying_embeddings.model
)

세 개의 주인공을 순서대로 뜯어봅니다.

1underlying_embeddings

실제 계산을 담당하는 진짜 임베딩 모델 (OpenAI). 비서 뒤의 "번역가".

2store

결과를 저장하고 꺼내올 창고. LocalFileStore("./cache/") = 내 컴퓨터의 폴더.

3namespace

모델별로 결과를 구분하는 이름표. 데이터가 섞이지 않게 하는 서랍 라벨.

🔍 비유 — namespace는 서랍에 붙이는 이름표 같은 문장이라도 어떤 임베딩 모델로 계산했느냐에 따라 결과 숫자가 완전히 달라집니다. text-embedding-3-small이 매긴 좌표와 text-embedding-3-large가 매긴 좌표는 서로 딴 세상이죠. 그래서 namespace로 "이 칸은 small 전용", "저 칸은 large 전용"이라고 이름표를 붙여 엉뚱한 결과를 꺼내 쓰는 사고를 막습니다. 여기서는 모델 이름(underlying_embeddings.model)을 그대로 이름표로 씁니다.
⚠️ 아직은 "설정"만 끝난 상태 이 셀을 실행해도 ./cache/ 폴더에는 아무 파일도 생기지 않습니다. 비서를 고용하고 서랍을 준비했을 뿐, 아직 번역 주문(임베딩 실행)을 넣지 않았기 때문이죠. 실제 파일은 뒤에서 embed_documents나 벡터 스토어 저장을 실행하는 순간부터 만들어집니다.

3. 캐시가 진짜 통할까 — 속도 실험

말로만 "빨라진다"고 하면 믿기 어렵죠. 똑같은 텍스트 10개를 두 번 연속 임베딩해보고, 각각 걸린 시간을 재봅니다. 1차는 캐시가 만들어지는 시점, 2차는 그 캐시를 꺼내 쓰는 시점입니다.

📥 코드
import time

# 테스트할 텍스트 리스트
test_texts = ["안녕하세요 " + str(i) for i in range(10)]

# --- 1. 첫 번째 실행 (캐시가 생성되는 시점) ---
print("1차 실행 시작 (OpenAI 호출 예상)...")
start_time = time.time()

# 임베딩 수행
cached_embedder.embed_documents(test_texts)

end_time = time.time()
print(f"1차 실행 소요 시간: {end_time - start_time:.4f}초")
print("-" * 30)

# --- 2. 두 번째 실행 (캐시를 사용하는 시점) ---
print("2차 실행 시작 (로컬 캐시 사용 예상)...")
start_time = time.time()

# 똑같은 텍스트로 다시 임베딩 수행
cached_embedder.embed_documents(test_texts)

end_time = time.time()
print(f"2차 실행 소요 시간: {end_time - start_time:.4f}초")
▶ 이렇게 나와요
1차 실행 시작 (OpenAI 호출 예상)...
1차 실행 소요 시간: 0.0107초
------------------------------
2차 실행 시작 (로컬 캐시 사용 예상)...

두 번째 실행이 첫 번째의 절반 이하 시간으로 끝났습니다. 똑같은 문장을 다시 임베딩했는데 번역가(OpenAI)에게 가지 않고 서랍(캐시)에서 바로 꺼내왔기 때문입니다.

💡 "1차도 0.01초밖에 안 걸렸는데요?" 맞습니다. 이 실험에서는 1차마저 매우 빨랐죠. 이 노트북은 예전에 이미 같은 텍스트를 임베딩한 적이 있어서 1차 실행 때 이미 캐시가 데워져 있던(warm) 상태였기 때문입니다. 정말로 캐시가 텅 빈 진짜 첫 실행(cold start)이라면 1차는 네트워크 왕복 때문에 수백 밀리초~수 초까지 걸립니다. 그때 2차와의 격차는 훨씬 극적으로 벌어집니다. 핵심은 숫자의 절대값이 아니라 "2차가 언제나 더 빠르다"는 사실입니다.

4. 실전 — PDF를 쪼개서 임베딩 + 캐싱

장난감 텍스트 말고 진짜 문서로 가봅니다. 앞 장(03. RAG Split)에서 배운 대로 PDF를 불러와 작은 청크(Chunk)로 쪼갠 뒤, 그 청크들을 벡터 스토어에 담습니다. 이때 임베딩 모델 자리에 방금 만든 cached_embedder를 그대로 끼워넣는 것이 전부입니다.

📥 코드
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_community.document_loaders import PDFPlumberLoader


loader = PDFPlumberLoader("./pdf-file.pdf")

docs = loader.load()


text_splitter = RecursiveCharacterTextSplitter(chunk_size=300, chunk_overlap=0)

recursive_docs = text_splitter.split_documents(docs)

vectorstore = InMemoryVectorStore.from_documents(
    documents=recursive_docs,
    embedding=cached_embedder
)

# cache 폴더를 보면 파일이 생성된 것 확인할 수 있다
# 해당 파일은 임베딩 결과를 저장하는 파일로, recursive_docs의 page_content를 임베딩 한 결과를 저장하는 파일이다
# 파일 이름은 임베딩 모델의 이름과 page_content의 해시값으로 구성된다
# 띠리사 page_content와 똑같은 입력이 들어오면, 해싱을 한 다음
# 동일한 파일이 있는지 찾고, 만약 같은게 있다면 임베딩 모델에 입력이 전달되는 것이 아니라
# 찾은 폴더의 파일을 읽어서 임베딩 결과를 반환하는 것이다

이 셀을 실행하는 순간, 드디어 ./cache/ 폴더에 파일들이 우르르 생겨납니다. 청크 하나당 파일 하나씩, 그 청크의 임베딩 결과가 저장되는 것이죠. 그런데 파일 이름이 어떻게 정해질까요?

🔍 비유 — 문장마다 찍히는 지문(Hash) 사람마다 지문이 다르듯, 캐시 임베더는 각 청크의 전체 텍스트를 해시(Hash)라는 고유한 지문 문자열로 바꿉니다. 글자가 하나라도 다르면 지문이 완전히 달라지고, 100% 똑같아야만 지문도 똑같습니다. 파일 이름 = 이름표(모델명) + 지문(해시값). 새 청크가 오면 먼저 지문을 찍어보고, 같은 지문의 파일이 서랍에 있으면 번역가를 부르지 않고 그 파일을 읽어 결과를 돌려줍니다.

캐싱의 단위는 "단어"가 아니라 "청크 덩어리"

한 가지 꼭 짚을 점 — 캐시는 단어 단위가 아니라 청크(조각) 전체 텍스트를 기준으로 작동합니다.

상황청크 A청크 B캐시 판단
내용이 완전히 동일"제1장 개요""제1장 개요"✅ 같은 지문 → B는 캐시에서 로드
단어 일부만 겹침"사과는 맛있다.""사과는 빨갛다."❌ 다른 지문 → 둘 다 각각 임베딩

"사과는"이라는 단어가 둘 다 들어있어도, 전체 텍스트가 다르면 완전히 다른 데이터로 취급합니다. 즉 캐시가 통하려면 청크 덩어리 전체가 100% 일치해야 합니다.

💡 진짜 위력은 "코드를 다시 실행할 때" 개발 중에는 검색 로직을 고치느라 코드를 수십 번 재실행합니다. 캐시가 없으면 그때마다 청크 수백 개를 전부 다시 임베딩해야 하죠(매번 API 비용 발생). 캐시가 있으면 PDF 내용이 그대로인 한 모든 청크를 서랍에서 즉시 로드합니다 — API 호출 0번, 비용 0원. 이것이 RAG 개발에서 캐시 임베더를 거의 필수 최적화로 쓰는 이유입니다.

5. 일부만 바뀌면? — 똑똑한 부분 재사용

"그럼 PDF를 조금 수정하면 전부 다시 임베딩해야 하나요?" 아닙니다. 여기가 캐시 임베더의 가장 영리한 부분입니다. 바뀐 조각만 새로 계산하고, 안 바뀐 나머지는 그대로 캐시에서 꺼내옵니다.

🔍 비유 — 책 한 페이지만 새로 번역하기 100쪽짜리 책을 통째로 번역해 공책에 정리해뒀다고 합시다. 나중에 5쪽의 오타 한 글자만 고쳤다면, 멀쩡한 나머지 99쪽까지 처음부터 다시 번역할 이유가 없죠. 고쳐진 5쪽 부분만 새로 번역하고 나머지는 공책에서 그대로 씁니다. 청크마다 지문(해시)이 독립적이라, 한 조각이 바뀌어도 다른 조각의 지문은 그대로거든요.

PDF 10쪽 → 청크 100개로 쪼갠 경우를 예로 들면 이렇게 흘러갑니다.

1첫 실행

청크 100개 전부 임베딩해서 ./cache/에 저장.

25쪽 오타 수정

PDF에서 한 글자만 고침.

3안 바뀐 90개

지문 동일 → 캐시에서 즉시 로드 (비용 0).

4바뀐 10개

지문 변경 → OpenAI 호출해 새로 임베딩 (비용 발생).

⚠️ 함정 — 청크가 "밀려나면" 캐시가 깨질 수 있다 주의할 게 하나 있습니다. PDF 앞부분에 내용을 추가하면 뒤쪽 텍스트가 통째로 밀리면서 쪼개지는 지점이 달라질 수 있습니다. 예전엔 "A / B"로 갈리던 게 이번엔 "AB /"로 갈리면 텍스트 내용 자체가 달라진 것이라 지문도 바뀌고, 결국 다시 임베딩하게 됩니다. 다행히 RecursiveCharacterTextSplitter는 최대한 의미 단위로 쪼개려 하므로, 운이 좋으면 뒤쪽 청크가 이전과 똑같이 갈려 캐시를 계속 활용할 수 있습니다.

6. 검색으로 마무리 — 이게 바로 RAG

임베딩과 캐싱까지 끝냈으니, 이제 실제로 질문을 던져 비슷한 문서를 찾아봅니다. 벡터 스토어에 similarity_search로 질문을 넣으면, 질문을 임베딩한 좌표와 가장 가까운 청크를 유사도 높은 순서로 돌려줍니다.

🔍 비유 — 도서관 사서에게 "이런 느낌의 책"을 묻기 벡터 스토어는 청크들을 의미 지도 위 좌표대로 정리해둔 특수 도서관입니다. "테슬라 투자 비중?"이라고 물으면, 사서는 그 질문도 좌표로 바꾼 뒤 가장 가까운 자리에 꽂힌 책(청크)을 순식간에 집어옵니다. 키워드가 정확히 일치하지 않아도 "의미가 비슷한" 문서를 찾아준다는 게 핵심이에요.
📥 코드
query = "Tesla 투자 비중이 얼마나 되나요?"
results = vectorstore.similarity_search(query)
# 벡터스토어에 있는 문서와 유사도를 계산하고, 유사도가 높은 순서대로 검색 결과를 반환한다

print(f"검색된 문서 내용:\n{results[0].page_content}")
# 가장 유사한 문서의 내용을 반환한다
# 이 내용을 LLM에게 전달해서 답변을 생성할 수 있다

둘 다 "빠르게·저렴하게"를 돕지만 담당 구역이 다릅니다. 헷갈리기 쉬우니 한 번 정리하고 갑니다.

📚 한 장 정리

오늘의 핵심 캐시 임베더는 "한 번 계산한 임베딩은 하드디스크에 저장해두고, 똑같은 텍스트가 오면 다시 계산하지 않고 꺼내 쓰는" 비용·시간 절약 장치다. RAG 개발의 사실상 필수 최적화.
  • 왜 쓰나 — 임베딩 API는 호출마다 돈이 나가고 시간이 걸린다. 중복 계산을 없애 둘 다 아낀다.
  • 만드는 법 — CacheBackedEmbeddings.from_bytes_store(모델, 저장소, namespace=...)로 기존 임베딩 모델을 감싼다.
  • namespace — 서랍 이름표. 모델별로 결과를 분리해 엉뚱한 캐시를 꺼내 쓰는 사고를 막는다.
  • 캐싱 단위 — 단어가 아니라 청크 전체 텍스트. 지문(해시)이 100% 일치할 때만 재사용.
  • 부분 수정 — 바뀐 청크만 새로 계산하고 나머지는 캐시 재사용. 단, 청크가 밀려 재분할되면 캐시가 깨질 수 있다.
  • 캐시 임베더 vs 벡터 스토어 — 전자는 계산 비용, 후자는 검색 속도를 담당. 둘이 합쳐져 RAG가 된다.
