8

파라미터 튜닝 & 실험 정리 (선택)

선택 · 심화 ⏱ 반나절
🎯 목표

지금까지 코드에 박아 둔 숫자들은 대부분 "일단 이 값으로 시작하자"였습니다. chunk_size=1000도, k=4도, [0.4, 0.6]도요. 이 STEP은 그 숫자들에 근거를 붙이는 단계입니다 — 몇 개를 바꿔가며 STEP 7의 채점기로 점수를 남기고, 최종 설정을 "왜 이걸 골랐는지" 숫자와 함께 설명할 수 있게 만듭니다.

새로 짤 코드는 없습니다. 이미 만든 것의 숫자만 바꿔가며 점수를 기록하는 단계예요.

🧠 개념
⚠️ 가장 흔한 오해부터 — "손잡이를 잘 맞추면 네 지표가 다 오른다"

그런 설정은 거의 없습니다. 특히 context_recall과 context_precision은 대체로 서로 반대로 움직입니다. 하나를 올리면 다른 하나가 내려가요. 이걸 모르고 표를 보면 "손잡이마다 오르는 지표 내리는 지표가 제각각이네…" 하고 길을 잃게 됩니다. 그 반대 관계 하나만 이해하면 이 STEP 전체가 풀립니다.

🎣 왜 반대로 움직이나 — 그물 비유

검색은 그물을 던져 물고기를 건지는 일입니다. 그물을 크게 던지면 목표 물고기는 확실히 잡히지만 쓰레기도 잔뜩 딸려 올라옵니다. 그물을 작게 던지면 건진 게 다 쓸모 있지만 한 마리를 놓칠 위험이 커지죠.

context_recall은 "필요한 걸 빠짐없이 건졌나", context_precision은 "건진 것 중 쓸모 있는 게 얼마나 되나"입니다. 그물 크기 하나로 두 값이 동시에 반대 방향으로 움직이는 게 보이시나요.

숫자로 보면 더 분명합니다. 정답 근거가 12조와 15조 두 군데에 흩어져 있는 질문이라고 해 보죠.

질문: "환불 기한과 배송비 부담 주체는?"      정답 근거 = [12조] [15조] 두 개

k=2 → 검색 결과 [12조] [교환]
      건진 근거 1/2  →  recall 0.50      건진 것 중 쓸모 1/2  →  precision 0.50

k=6 → 검색 결과 [12조] [교환] [면책] [15조] [해지] [보험료]
      건진 근거 2/2  →  recall 1.00 ↑    건진 것 중 쓸모 2/6  →  precision 0.33 ↓
                        ~~~~~~~~~~~                              ~~~~~~~~~~~~~
                        올랐지만                                 대신 떨어졌다

(RAGAS의 실제 context_precision은 순위까지 반영하는 조금 더 복잡한 식이라 딱 2/6이 나오지는 않습니다. 방향과 직관만 이렇게 잡아 두면 충분해요.)

💡 그래서 이 STEP의 결과물은 "최고 점수"가 아닙니다

다 좋은 설정을 찾는 게임이 아니라, "우리 서비스는 어느 쪽을 포기할 것인가"를 정하는 게임입니다. 약관 QA라면 관련 없는 조항이 하나 섞이는 것보다 필요한 조항을 빠뜨리는 쪽이 훨씬 치명적이니 recall에 무게를 두는 식으로요. 그 판단을 문장으로 적어 두는 것이 이 STEP의 진짜 산출물이고, 면접에서 "감이 아니라 지표로 정했다"는 이야기가 되는 부분입니다.

🛠 할 일

세 조각으로 나눠 보고, 맨 아래 기록표 템플릿을 채워 나가세요.

🧭 세 조각 한눈에

① 무엇을 바꿔볼지 고르기  →  ② 한 번에 하나씩 바꿔 채점하기  →  ③ 표로 모아 근거와 함께 결정하기

① 무엇을 바꿔볼까 — 손잡이는 네 개, 축은 두 개

손잡이를 네 개로 외우면 어렵습니다. 축이 두 개라고 보면 훨씬 간단해요.

축 1 · "얼마나 크게 건질까" — chunk_size, k, top_n 셋은 모두 그물 크기를 조절하는 같은 축입니다. 올리면 recall↑ precision↓, 내리면 그 반대. 조절하는 지점만 다를 뿐이에요 — chunk_size는 한 조각을 얼마나 크게 자를까, k는 몇 조각을 건질까, top_n은 건진 것 중 몇 개를 LLM에게 줄까.

축 2 · "어떤 방식으로 건질까" — weights 하나뿐입니다. 양이 아니라 검색 방식의 배합을 바꾸는 손잡이라, 위 셋과 성격이 다릅니다.

손잡이어디에올리면주로 움직이는 지표
chunk_size
500·1000·1500		 ingest.py 41행
재인덱싱 필요		 문맥은 풍부해지되 관계없는 내용이 함께 딸려옴 올리면 context_precision↓ · 내리면 context_recall↓
k (검색 개수)

rerank 모드는 120~121행(10)		 정답을 놓칠 확률은 줄고 노이즈와 비용은 늚 context_recall↑ · context_precision↓

🔎 k와 top_n이 헷갈린다면 — 채용 과정 비유

rerank 모드는 2단계 검색이었죠(STEP 4). k는 서류에서 몇 명을 부를까(현재 10명), top_n은 면접 후 몇 명을 뽑을까(현재 4명)입니다. k를 줄이면 애초에 후보에 없어서 놓치고, top_n을 늘리면 애매한 후보까지 합격시켜 LLM 책상이 어수선해집니다. faithfulness가 top_n 쪽에 붙어 있는 이유가 이거예요 — 근거가 희석되면 모델이 엉뚱한 데서 답을 끌어옵니다.

⚠️ chunk_size를 바꿨다면 반드시 다시 인덱싱하세요

나머지 셋은 사서에게 주는 지시라 말만 바꾸면 다음 질문부터 바로 반영됩니다. 그런데 chunk_size는 책을 애초에 몇 쪽씩 잘라 서가에 꽂았느냐예요 — 벡터DB에 이미 저장된 청크의 모양을 정하는 값이라, 코드만 고치면 아무 일도 일어나지 않습니다. uv run python ingest.py를 다시 돌려 서가를 새로 만들어야 반영돼요.

(ingest.py가 저장 전에 기존 컬렉션을 비우므로 chroma_db/를 손으로 지울 필요는 없습니다. 다만 청크 텍스트가 달라져 캐시가 안 먹으므로, 이때만은 임베딩 비용이 다시 듭니다.)

② 한 번에 하나씩만 바꾸기

규칙은 하나입니다 — 두 개를 동시에 바꾸면 무엇 덕분에 좋아졌는지 영영 알 수 없습니다. 하나 바꾸고 → 채점하고 → 파일 이름 바꿔 보관하고 → 되돌린 뒤 다음 손잡이로. 이 순서를 지키세요.

⚠️ 결과 파일은 매번 이름을 바꿔야 합니다

evaluate.py는 항상 eval_<mode>.csv라는 같은 이름으로 저장합니다. 그냥 두면 다음 실험이 덮어써 버려서, 세 번 돌려도 파일은 마지막 것 하나만 남아요.

터미널
# 0) 기준선부터 확보한다. 비교 대상이 없으면 '올랐다'고 말할 수가 없다.
#    (지금 코드 그대로: chunk 1000 · k4 · top_n4 · weights [0.4, 0.6])
uv run python evaluate.py rerank
mv eval_rerank.csv exp_base.csv

# 1) 설정을 '하나만' 바꾼다 — 예: rag.py 99·105행의 k를 4 → 6
#    두 개를 동시에 바꾸면 무엇 덕분에 좋아졌는지 알 수 없게 된다.

# 2) 같은 골든셋 · 같은 mode로 다시 채점한다 (비교하려면 나머지 조건이 같아야 한다)
uv run python evaluate.py rerank

# 3) 결과 파일 이름을 바꿔 보관한다.
#    mv = 이름 바꾸기(이동). 파일명에 '무엇을 바꿨는지'를 적어 두면 나중에 찾기 쉽다.
mv eval_rerank.csv exp_k6.csv

# 4) 커밋한다. 메시지에 '바꾼 값 + 점수 변화'를 함께 적는 것이 요령 —
#    이러면 git log가 그대로 실험 노트가 되고, STEP 9에서 README를 쓸 때 로그만 훑으면 된다.
#    -am = 수정된 파일을 모두 담아(-a) 메시지와 함께(-m) 커밋
git commit -am "실험: k=4 -> 6 (context_recall 0.71 -> 0.78, precision 0.66 -> 0.59)"

# 5) k를 4로 '되돌린' 뒤 다음 손잡이로 넘어간다.
#    되돌리지 않으면 다음 실험이 'k=6 + 새 변경' 두 개를 동시에 바꾼 셈이 된다.
💡 평균이 아니라 CSV를 열어 보세요

화면에 찍히는 건 지표 평균이라 왜 떨어졌는지는 알려주지 않습니다. evaluate.py가 남기는 CSV에는 문항별 점수가 들어 있어요. 점수가 흔들렸다면 어떤 질문이 깎아먹었는지를 여기서 찾으세요 — "조항 번호가 든 질문만 유독 낮다" 같은 게 보이면 다음에 어느 손잡이를 돌릴지가 저절로 정해집니다.

③ 표로 모아 "왜 이 설정인지" 한 문단

최종 산출물은 표 하나와 문단 하나입니다. 표는 무엇을 얻고 무엇을 잃었는지를 보여주고, 문단은 그래서 왜 이걸 택했는지를 말합니다. 표만 있으면 "실험은 했는데 결론이 없는" 상태이고, 이 STEP은 문단이 있어야 끝납니다.

이유를 쓸 때는 잃은 것을 먼저 인정하고, 그럼에도 택한 근거를 대는 형태가 가장 설득력 있습니다. 아래 문장을 그대로 흉내 내 보세요. 

"exp1(k=6)을 택했다.
 precision이 0.66 → 0.59로 떨어졌지만 recall이 0.71 → 0.78로 올랐다.
 약관 QA에서는 관련 없는 조항이 하나 섞이는 것보다
 필요한 조항을 빠뜨리는 쪽이 훨씬 치명적이라고 판단했다."

  └ 잃은 것 → 얻은 것 → 서비스 성격상 어느 쪽이 중요한지  (이 세 마디면 충분하다)
✅ 검증 게이트 3가지 이상 설정의 지표를 한 표에 모으고, 최종 설정을 숫자 근거로 선택한 문장이 있으면 통과.
🏭 참고 · 실무에서는 어떤 순서로 하나

이 STEP은 손잡이 네 개를 다뤘지만, 실제 서비스에서 RAG 품질을 올릴 때 숫자 튜닝은 맨 마지막에 오는 일입니다. 순서를 거꾸로 잡으면 — 표가 깨진 채로 인덱싱해 놓고 k만 6으로 올리면 — 깨진 조각을 더 많이 건지는 것뿐이에요. 위에서부터 점검하고, 위쪽이 정리된 다음에 이 STEP으로 내려오세요.

순서무엇을구체적으로효과 크기
1 측정 장치부터
STEP 7		 골든셋 + 채점기. 이게 없으면 아래 전부가 감(感)이라, 좋아졌다는 말을 할 수가 없습니다. 전제 조건
2 원본이 제대로 들어갔나
STEP 1 · Load		 파싱된 텍스트를 눈으로 열어 보세요. 표가 한 줄로 뭉개지거나, 머리말·쪽번호가 문장 사이에 끼거나, 스캔 PDF라 글자가 아예 안 잡히는 일이 실무에선 아주 흔합니다. 여기가 깨지면 아래는 전부 무의미합니다. 가장 큼
3 어떻게 자를까
STEP 1 · Split		 글자 수로 1000자씩 자르는 대신 조항·제목 단위로 자르기. 약관·매뉴얼처럼 구조가 뚜렷한 문서라면 chunk_size 숫자를 조이는 것보다 훨씬 크게 움직입니다. 큼
4 질문을 손보기
검색 직전		 사용자의 짧고 애매한 질문("환불 언제까지?")을 검색 전에 다시 쓰거나(query rewriting) 여러 개로 늘려(multi-query) 던지기. 질문이 나쁘면 검색기가 아무리 좋아도 못 건집니다. 중간
5 프롬프트
STEP 2		 "문맥에 없으면 모른다고 답하라", 인용 형식 강제 같은 지시. faithfulness는 검색보다 여기서 더 크게 움직이는 경우가 많습니다. 중간
6 숫자 손잡이
← 이 STEP		 chunk_size·k·top_n·weights. 위가 다 정리된 뒤 마지막 몇 %를 짜내는 단계입니다. 작음

그러니 이 STEP에서 진짜 가져갈 것은 k=6이라는 결론이 아니라 측정 없이는 아무것도 주장하지 않는 습관입니다. 실무에서 쓰는 문장도 대개 "k를 6으로 올렸다"가 아니라 "표 파싱을 고치고 조항 단위 청킹으로 바꿨더니 recall 0.71 → 0.85, 비용은 그대로"에 가깝습니다.

💰 실무 기록표에는 칼럼이 두 개 더 붙습니다

top_n을 4 → 8로 올리면 지표는 조금 오를지 몰라도 매 질문마다 LLM에 들어가는 토큰이 두 배가 되고, 응답이 느려지고, 청구서가 커집니다. 그래서 실제 회의에서는 "recall 0.03 오르는데 비용 2배면 안 한다"는 결론이 자주 나와요. 실무 표에는 지표 옆에 쿼리당 비용과 p95 응답시간이 함께 적히고, 그 두 숫자는 STEP 6의 Langfuse에서 그대로 볼 수 있습니다.

🔁 골든셋은 "만들어 두는 것"이 아니라 자랍니다

STEP 7에서는 15문항을 손으로 먼저 만들었지만 실무 순서는 반대입니다 — 일단 배포하고, Langfuse 트레이스에서 이상한 답이 나간 질문을 발견할 때마다 골든셋에 한 줄씩 추가해요. 그러면 골든셋이 실패에서 자라는 회귀 테스트 모음이 됩니다. 여기에 채점기를 CI에 걸어 두면, 누가 프롬프트를 "개선"했을 때 특정 유형만 조용히 망가지는 사고를 배포 전에 잡을 수 있습니다.

🎓 배우는 것

실험 관리와 의사결정 — 변수 하나만 바꿔 비교하는 습관, 그리고 트레이드오프를 인정하고 근거로 선택하는 서사. "감이 아니라 지표로 정했다"는 이력서·면접용 이야기가 여기서 나옵니다.
