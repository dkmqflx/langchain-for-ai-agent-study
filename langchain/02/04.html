04. Tool Emulator — 실제 도구 없이 LLM으로 결과 모킹하기

실습 노트북: 04.ipynb  ·  원문: docs/02.agent-basic.md 3.3.1 LLM Tool Emulator  ·  난이도: 🟢 입문  ·  선행: 03. Memory

이 자료는 실습 노트북(04.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 도구(Tool)를 만들다 보면 "아직 진짜로 실행하기는 부담스러운" 순간이 옵니다 — 실제로 이메일이 발송되거나, 유료 API가 호출되거나, DB가 바뀌면 곤란하니까요. 이럴 때 LLMToolEmulator는 도구를 진짜로 돌리지 않고, LLM이 "그럴듯한 결과를 지어내(모킹)" 대신 채워줍니다. 실제 백엔드 없이도 Agent의 전체 흐름을 리허설해 볼 수 있게 해주는 도구예요.

🔍 비유 — 영화 촬영장의 소품과 대역 은행 강도 장면을 찍는다고 진짜 돈을 털지는 않습니다. 가짜 지폐 다발을 쓰고, 위험한 장면은 배우 대신 대역(스턴트)이 뜁니다. 카메라에 담긴 화면은 "진짜처럼" 보이지만 실제로는 아무 은행도 털리지 않았죠. LLMToolEmulator가 바로 이 소품·대역입니다. Agent는 "이메일을 읽고 보냈다"고 그럴듯하게 연기하지만, 실제 메일함은 손끝 하나 대지 않습니다.
이 장에서 배우는 것 LangChain의 Agent에는 미들웨어(middleware)라는, 실행 과정에 끼워 넣는 부품이 있습니다. 그중 LLMToolEmulator는 "도구 호출을 가로채서 진짜 실행 대신 LLM의 가짜 응답으로 바꿔치기"하는 미들웨어입니다. 이 장에서는 도구 2개를 만들고, 그 위에 에뮬레이터를 씌워 진짜로는 아무것도 실행되지 않는 리허설을 돌려봅니다.

왜 도구를 "흉내"낼까?

3번 노트북까지는 도구를 만들면 실제로 그 코드가 실행됐습니다. 하지만 개발 초기에는 "실제 실행"이 오히려 걸림돌이 될 때가 많습니다. 원문 교재는 두 가지 대표 상황을 듭니다.

  • 도구 호출이 불가능하거나 너무 비쌀 때 — 아직 실제 API가 없거나, 한 번 부를 때마다 요금이 나가는 경우.
  • 프로토타입 단계에서 실제 백엔드 없이 개발할 때 — 이메일 서버·결제 시스템을 붙이기 전에 흐름부터 확인하고 싶을 때.
🔍 비유 — 우주비행사 훈련 시뮬레이터 우주비행사는 훈련할 때 진짜 우주선을 쏘아 올리지 않습니다. 진짜와 똑같이 생긴 조종석 시뮬레이터에서 버튼을 누르고 절차를 몸에 익히죠. 진짜 로켓은 비싸고, 위험하고, 한 번 쓰면 되돌릴 수 없으니까요. LLMToolEmulator도 같은 목적입니다 — 진짜 도구를 쏘아 올리기 전에, 버튼 배치(도구 이름·인자)와 절차(Agent 흐름)가 맞는지 안전하게 리허설합니다.
⚠️ "흉내낸 결과"는 사실이 아니다 에뮬레이터가 돌려주는 값은 LLM이 지어낸 가짜(mock) 데이터입니다. 진짜 메일함을 읽은 것도, 진짜로 메일을 보낸 것도 아니에요. 그래서 결과의 내용을 사실로 믿으면 안 됩니다. "흐름이 맞게 굴러가는지" 확인하는 리허설용이라는 점을 꼭 기억하세요.

0. 환경 준비

앞 장들과 똑같이 모델 하나를 준비합니다. 다만 이번엔 이 모델이 두 가지 역할을 겸합니다 — 질문에 답하고 도구를 고르는 "두뇌" 역할, 그리고 뒤에서 도구 결과를 대신 지어내는 "대역 배우" 역할이죠.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent

# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-4o-mini")

새로 등장한 create_agent는 모델 + 도구 + 미들웨어를 하나로 묶어 스스로 판단하고 도구를 호출하는 Agent를 만들어 주는 함수입니다. 뒤에서 바로 씁니다.

1. 흉내낼 도구 2개 정의 — send_email_tool · read_email_tool

먼저 Agent가 쓸 도구 두 개를 만듭니다. 하나는 메일을 보내는 도구, 하나는 메일을 읽는 도구입니다. docstring("""...""")에 "(프로토타입)"이라고 적힌 게 힌트예요 — 속은 아직 텅 빈 껍데기라는 뜻입니다.

🔍 비유 — 모델하우스(견본주택) 아파트 분양 전에 짓는 모델하우스를 떠올려 보세요. 문·싱크대·조명이 다 달려 있어 진짜 집처럼 보이지만, 사실 수도관도 전기도 연결돼 있지 않은 껍데기입니다. 여기 두 도구가 딱 그렇습니다. 함수 이름·인자·설명(간판)은 완벽하게 갖췄지만, 안의 return은 대충 채운 임시값이라 실제 메일 서버와는 아무 연결이 없습니다.
📥 코드
from typing import List, Dict
from langchain.tools import tool

@tool
def send_email_tool(to: str, subject: str, body: str) -> str:
    """지정한 주소로 이메일을 보내는 도구(프로토타입)."""
    return f"Email sent. to={to}, subject={subject}"

@tool
def read_email_tool(limit: int = 3) -> List[Dict[str, str]]:
    """최근 받은 이메일을 조회하는 도구(프로토타입)."""
    return [{"from": "hr@example.com", "subject": "정책 안내", "body": "..."}][:limit]

두 함수 모두 진짜 일은 하나도 하지 않습니다. send_email_tool은 그냥 "보냈다"는 문자열을 되돌려줄 뿐이고, read_email_tool은 고정된 가짜 메일 한 통(hr@example.com / "정책 안내")을 되돌려줄 뿐이죠. 뒤에서 에뮬레이터를 씌우면 이 임시 return조차 실제로는 실행되지 않습니다 — 이 점을 뒤 "결과 뜯어보기"에서 눈으로 확인하게 됩니다.

📘 보충 — @tool 데코레이터가 하는 일

함수 위에 붙인 @tool은 평범한 파이썬 함수를 Agent가 호출할 수 있는 도구로 등록해 줍니다. 이때 LLM은 함수의 이름(read_email_tool), 인자와 타입 힌트(limit: int = 3), 그리고 docstring("최근 받은 이메일을 조회하는 도구")을 읽고 "언제 이 도구를 써야 하는지"를 판단합니다.

💡 그래서 에뮬레이터가 가능하다 에뮬레이터는 함수의 속(내용물)이 아니라 겉(이름·인자·설명·반환 타입)만 보고 그럴듯한 결과를 지어냅니다. 모델하우스의 간판과 도면만 보고 "이런 집이겠구나" 상상해서 방문객에게 설명하는 것과 같아요.

2. LLMToolEmulator 씌우기

이제 핵심입니다. create_agent에 middleware=[LLMToolEmulator(...)]를 넣어주면, Agent가 도구를 부르는 순간 에뮬레이터가 중간에서 가로채 실제 실행 대신 LLM의 가짜 응답으로 바꿔치기합니다.

🔍 비유 — 무대 뒤 대역 배우 주연 배우가 "위험한 액션 장면"에 들어가려는 순간, 감독이 "컷! 여기부터 대역"이라고 외칩니다. 그러면 똑같은 옷을 입은 대역(에뮬레이터)이 대신 뛰고, 관객(사용자)은 이어 붙은 화면만 보고 주연이 다 한 줄 압니다. middleware=[LLMToolEmulator(...)]가 바로 그 "컷! 대역 투입" 지시예요. 도구가 실행될 자리마다 대역이 들어가 결과를 대신 연기합니다.
📥 코드
from langchain.agents.middleware import LLMToolEmulator


LLMToolEmulator

agent = create_agent(
    model=model,
    tools=[send_email_tool, read_email_tool],
    # tool emulator: 실제 도구 호출 대신 LLM으로 시뮬레이션, 즉, 도구가 만든 결과를 모킹하는것. gemini-2.5-flash 모델 사용
    middleware=[LLMToolEmulator(model="gpt-4o-mini")],
    )

# # 이메일 읽기 예시
result = agent.invoke({"messages": [
  {"role": "user", "content": "최근 도착한 이메일을 읽고 답장해줘"}]},
  {"configurable": {"thread_id": 1}})

print("=== 이메일 읽고 쓰기 결과 ===")
print(result)
print(result['messages'][-1].content)

포인트 세 가지만 짚고 넘어가겠습니다.

  • tools=[send_email_tool, read_email_tool] — Agent에게 쓸 수 있는 도구 목록을 알려줍니다.
  • middleware=[LLMToolEmulator(model="gpt-4o-mini")] — "이 도구들은 진짜 실행하지 말고 gpt-4o-mini가 결과를 지어내라"고 지시합니다.
  • agent.invoke({"messages": [...]}) — 3번 노트북에서 배운 메시지 리스트를 그대로 Agent에 던집니다. 여기선 user 역할 한 줄만 넣었어요.
⚠️ 주석과 실제 코드가 다르다 코드 주석에는 "gemini-2.5-flash 모델 사용"이라고 적혀 있지만, 실제 인자는 model="gpt-4o-mini"입니다. 옛 주석이 남은 것이니 실제로 동작하는 것은 gpt-4o-mini라고 읽으면 됩니다. (에뮬레이터에 넘긴 모델이 곧 "대역 배우"가 됩니다.)
📘 보충 — 두 개의 선택적 인자: model과 tools

LLMToolEmulator는 인자 없이 LLMToolEmulator()로도 쓸 수 있고, 이땐 기본 모델(anthropic:claude-3-5-sonnet-latest)이 대역을 맡습니다. 여기선 model="gpt-4o-mini"로 대역 배우를 직접 지정한 것이죠.

또, 도구 일부만 흉내내게 할 수도 있습니다. 예를 들어 LLMToolEmulator(tools=["read_email_tool"])처럼 이름을 지정하면 지정한 도구만 대역이 뛰고 나머지는 진짜로 실행됩니다. 아무것도 지정하지 않으면 등록된 모든 도구가 흉내내기 대상이 됩니다(이 노트북이 그 경우).

📘 보충 — thread_id는 왜 넣었을까?

두 번째 인자 {"configurable": {"thread_id": 1}}는 3번 노트북의 메모리 이야기와 이어집니다. thread_id는 "이 대화의 방 번호" 같은 것으로, 같은 번호로 다시 호출하면 그 방의 대화를 이어갈 수 있게 해주는 열쇠입니다. 이 예제에서는 한 번만 호출하므로 큰 역할은 없지만, Agent가 대화 단위로 상태를 구분한다는 감만 잡아두면 충분합니다.

3. 실행 결과 뜯어보기

"최근 도착한 이메일을 읽고 답장해줘" 한 줄을 던졌을 뿐인데, Agent는 스스로 ① 메일을 읽고 → ② 답장을 작성해 → ③ 발송하는 여러 단계를 알아서 밟았습니다. 그런데 그 중간 결과들이 전부 대역(LLM)이 지어낸 것이라는 게 이 장의 핵심입니다.

최종 답변 (result['messages'][-1].content)

▶ 이렇게 나와요
=== 이메일 읽고 쓰기 결과 ===
제가 최근 도착한 이메일에 답장을 보냈습니다:

1. Mike Johnson에게 "회의 알림"에 대한 답장했습니다.
2. Sara Brown에게 "프로젝트 업데이트"에 대한 답장했습니다.

모두 성공적으로 발송되었습니다! 다른 도움이 필요하시면 말씀해 주세요.

감쪽같죠? 마치 진짜로 메일을 읽고 답장까지 보낸 것처럼 보고합니다. 하지만 Mike Johnson도, Sara Brown도 실제로는 존재하지 않는 사람입니다 — 전부 대역 LLM이 지어낸 등장인물이에요. 이걸 print(result)로 찍은 메시지 전체 기록을 보면 확실히 드러납니다.

메시지 기록을 대화로 펼쳐보면

최근 도착한 이메일을 읽고 답장해줘 ← 우리가 던진 요청
AI
(내용 없음) → read_email_tool(limit=3) 호출 결정
Tool
[{"from": "mike.johnson@email.com", "subject": "Meeting Reminder", ...}, {"from": "sara.brown@email.com", ...}, {"from": "newsletter@techupdates.com", ...}] ← 대역이 지어낸 가짜 메일 목록
AI
(내용 없음) → send_email_tool 2번 호출 (Mike·Sara에게 답장)

🚨 결정적 증거 — Tool 결과가 우리 코드와 다르다 우리가 정의한 read_email_tool은 분명 hr@example.com / "정책 안내" 한 통을 돌려주도록 짰습니다. 그런데 실제 ToolMessage에는 mike.johnson@email.com, sara.brown@email.com 같은 전혀 다른 값이 담겨 나왔습니다. send_email_tool도 마찬가지예요 — 우리 코드는 "Email sent. to=..., subject=..."를 돌려주게 짰는데, 결과는 "Email sent successfully to ... with subject ..."라는 다른 문장입니다. 즉 우리 함수의 return은 단 한 번도 실행되지 않았고, 전부 대역 LLM이 즉흥으로 지어낸 겁니다. 이것이 "에뮬레이터가 진짜로 도구를 실행하지 않는다"는 가장 확실한 증거입니다.
💡 왜 AI 메시지에 content가 비어 있을까? 중간의 AI 메시지들은 content=''로 텍스트가 비어 있습니다. 대신 tool_calls에 "어떤 도구를 어떤 인자로 부를지"가 담겨 있죠. LLM이 말을 하는 대신 도구를 호출하기로 결정한 순간에는 이렇게 내용이 비고 도구 호출만 실립니다. 도구 결과(Tool 메시지)를 받아 할 말이 생겼을 때 비로소 마지막 AI 메시지에 텍스트가 채워집니다.

실행 흐름 한눈에

요청 한 줄이 최종 보고까지 이어지는 과정을 단계로 그려보면 이렇습니다. ③·⑤가 대역이 끼어드는 지점입니다.

1요청 투입

"이메일 읽고 답장해줘"를 Agent에 전달

2도구 선택

LLM이 read_email_tool을 부르기로 결정

3🎭 대역 투입

에뮬레이터가 가로채 가짜 메일 목록을 지어냄

4답장 작성·발송 결정

LLM이 send_email_tool을 2번 호출

5🎭 대역 투입

에뮬레이터가 "발송 성공" 메시지를 지어냄

LLM이 결과를 요약해 사용자에게 답변

💡 진짜 도구였다면? 에뮬레이터가 없었다면 ③에서 우리 read_email_tool이 실제로 실행돼 hr@example.com 한 통이 돌아오고, ⑤에서 진짜로 메일이 발송됐을 겁니다. 에뮬레이터는 이 ③·⑤ 지점만 "대역"으로 바꿔 나머지 흐름은 그대로 두는 것이죠.

진짜 도구 vs 흉내 도구

구분진짜 도구 실행 (에뮬레이터 없음)흉내 도구 (LLMToolEmulator)
도구 안의 return실제로 실행됨실행 안 됨 (LLM이 대신 지어냄)
결과의 정확성진짜 데이터가짜(mock) 데이터 — 사실 아님
부작용(메일 발송 등)실제로 일어남일어나지 않음 (안전)
비용·외부 API실제 요금·호출 발생대역 LLM 호출 비용만
주로 언제실제 서비스 운영프로토타입·리허설·테스트
🔍 비유 — 리허설과 본공연 연극 리허설에서는 조명·동선·대사 타이밍을 마음껏 맞춰봅니다. 실수해도 관객이 없으니 괜찮죠. 본공연은 실수가 곧 사고입니다. 에뮬레이터는 리허설 무대예요 — 흐름이 완성되면 에뮬레이터를 떼고 진짜 도구를 연결해 본공연(실서비스)으로 올리면 됩니다.

📚 한 장 정리

오늘의 핵심 LLMToolEmulator는 도구를 진짜로 실행하지 않고, LLM이 결과를 지어내(모킹) 대신 채우는 미들웨어다. 실제 백엔드 없이 Agent 흐름을 안전하게 리허설하기 위한 장치다.
  • 왜 쓰나 — 도구가 없거나 비싸거나 위험할 때, 프로토타입 단계에서 흐름만 먼저 확인하려고.
  • 어떻게 쓰나 — create_agent(..., middleware=[LLMToolEmulator(model="...")]) 한 줄이면 등록된 도구가 전부 대역으로 바뀐다.
  • 일부만 흉내 — LLMToolEmulator(tools=["도구이름"])로 특정 도구만 대역 처리, 나머지는 진짜 실행.
  • 결정적 특징 — 도구 함수의 return은 실행되지 않는다. 결과 ToolMessage가 우리 코드와 다른 값이면 그게 증거다.
  • 주의 — 돌려받은 값은 가짜 데이터다. 내용을 사실로 믿지 말고, 흐름 검증용으로만 쓴다.
  • 비유로 한 방에 — 소품과 대역(영화), 조종석 시뮬레이터(우주비행), 모델하우스(부동산), 리허설(연극).
➡️ 다음 이야기 에뮬레이터도 미들웨어의 하나였습니다. 다음 노트북에서는 또 다른 미들웨어 — 복잡한 요청을 만나면 Agent가 스스로 할 일 목록(TodoList)을 세우고 단계별로 처리하게 돕는 TodoListMiddleware를 만나봅니다.
