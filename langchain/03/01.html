01. Hooks & Middleware 가이드

실습 노트북: 01.ipynb  ·  원문: docs/03.advanced-agent.md 1장 Advanced Agent  ·  난이도: 🟡 중급

이 자료는 실습 노트북(01.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 기본 Agent를 넘어서 실행 흐름 중간에 끼어들어 Agent를 정교하게 제어하는 두 가지 장치 — 미들웨어(Middleware)와 훅(Hook) — 을 배웁니다. "모델이 답을 만들기 직전에 로그를 남기고 싶다", "사용자 이름을 몰래 프롬프트에 끼워 넣고 싶다" 같은 일이 어떻게 가능한지, 비유와 실제 실행 결과로 천천히 풀어봅니다.

이 장에서 배우는 것 Agent는 "질문을 받아 → 모델을 부르고 → 도구를 쓰고 → 답을 낸다"는 흐름(파이프라인)으로 움직입니다. 이 흐름의 중간중간에 우리 코드를 끼워 넣는 것이 이 장의 전부입니다. 끼워 넣는 기능 조각을 미들웨어, 끼워 넣는 지점을 훅이라고 부릅니다.

가장 먼저 잡아야 할 감은 미들웨어와 훅의 관계입니다. 어렵게 느껴지지만, 한 문장으로 줄이면 "무엇을(미들웨어) 언제(훅) 실행할까"입니다.

🔍 비유 — 공장 라인의 센서 Agent 시스템을 거대한 공장 라인이라고 생각해 보세요. 라인 위에는 여러 기계(노드)가 있습니다 — LLM을 돌리는 기계, 도구를 실행하는 기계 등. 각 기계 바로 앞에는 센서를 꽂을 수 있는 장착 지점(훅)이 미리 마련되어 있습니다. 우리는 거기에 원하는 센서 기기(미들웨어)를 쓱 꽂기만 하면 됩니다. 훅이 없다면 공장 내부 배선을 통째로 뜯어고쳐야 하지만, 지점이 미리 있으니 우리는 기능만 만들어 끼워 넣으면 되는 것이죠.
용어정체대답하는 질문예
미들웨어 (Middleware)실행할 코드(기능 단위)무엇을?log_before_model 함수
훅 (Hook)미들웨어가 걸리는 실행 지점언제?@before_model 데코레이터

즉 미들웨어는 훅이라는 갈고리에 걸어 두는 실제 작업 도구입니다. "이 기능(log_before_model)을 저 지점(@before_model)에 걸어 줘"라고 등록하는 것이 우리가 할 일의 전부예요.

⚠️ 실행 전 준비 코드를 직접 돌려보려면 프로젝트 루트에 .env 파일이 있고 그 안에 OPENAI_API_KEY 같은 API 키가 들어 있어야 합니다. 이 교재만 읽을 때는 필요 없습니다.

Runtime & State — 미들웨어가 들여다보는 두 상자

미들웨어 함수를 열어 보면 state, runtime, request 같은 인자가 등장합니다. 이 이름들이 낯설면 미들웨어가 통째로 어렵게 느껴지니, 딱 두 개만 먼저 잡고 갑시다 — Runtime과 State입니다.

🔍 비유 — 요리사의 주방(Runtime) vs 지금까지 만든 요리(State) Runtime은 요리사가 일하는 주방 환경입니다 — 손님이 누구인지 적힌 주문서(Context), 단골손님 취향을 적어 둔 메모 노트(Store), 홀에 상황을 알리는 인터폰(Stream writer). 요리 중에 바뀌지 않는 바깥 환경이죠. 반면 State는 요리사가 지금까지 실제로 만들어 낸 결과물입니다 — 완성된 접시들(messages), 중간 재료(tool_results). 요리가 진행될수록 계속 늘어나는 안쪽 산출물이에요.
큰 구분구성 요소설명
Runtime
(바깥 환경)		Context사용자 ID, DB 연결 URL처럼 실행 중 변하지 않는 정보
Store사용자 이름·선호도 같은 장기 메모리
Stream writer내부 작동 로그 등 실시간 이벤트 출력
State
(내부 산출물)		messages모델이 Runtime을 참조해 만든 대화 결과물
tool_results도구가 만들어 낸 정보 모음
💡 한 줄 정리 State가 Agent 내부 흐름(대화·도구 결과)을 다룬다면, Runtime은 그 바깥 환경(사용자 정보·저장소·스트림)을 다룹니다. 이 장의 예제에서 우리가 넣어 줄 "사용자 이름"은 대화 중 변하지 않는 정보이므로 Runtime의 Context에 담깁니다.

dataclass — Context를 담는 깔끔한 그릇

방금 Context에 "사용자 이름"을 담는다고 했죠. 그 Context를 정의할 때 파이썬의 dataclass를 씁니다. dataclass는 데이터를 담는 클래스를 아주 쉽고 깔끔하게 만들어 주는 도구예요(파이썬 3.7부터 내장).

🔍 비유 — 서식 자동 완성기 보통 클래스를 만들려면 "값을 받는 생성자(__init__)", "예쁘게 출력하는 법(__repr__)", "두 개가 같은지 비교하는 법(__eq__)"을 매번 손으로 적어야 합니다. @dataclass는 "어떤 칸이 필요한지"만 적으면 나머지 지루한 서식을 자동으로 채워 주는 문서 자동 완성기입니다. 우리는 user_name: str 한 줄만 쓰면, 파이썬이 "아, 이건 user_name을 받는 생성자가 필요하겠구나" 하고 알아서 만들어 줍니다.
📥 코드
from dataclasses import dataclass

@dataclass
class Context:
  user_name: str

@dataclass 데코레이터만 붙였을 뿐인데, 이 클래스는 아래 세 가지를 공짜로 얻습니다.

자동 생성 메서드하는 일
__init__인스턴스를 만들 때 값을 받는 생성자 (예: Context(user_name="Jay"))
__repr__print(ctx) 시 Context(user_name='Jay')처럼 보기 좋게 출력 (일반 클래스는 메모리 주소가 나옴)
__eq__== 비교를 주소가 아니라 데이터 내용 기준으로 수행
💡 왜 여기서 쓰나? LangChain의 Context는 사용자 이름·설정값처럼 단순한 데이터의 묶음인 경우가 많습니다. 복잡한 로직보다 데이터 그 자체를 안전하게 전달하는 게 목적이라, 코드가 짧고 읽기 쉬운 dataclass를 쓰는 것이 관례입니다.

방법 1 — Node-style Hook (@before_model)

이제 진짜 미들웨어를 만들어 봅니다. 첫 번째 방식은 Node-style Hook입니다. 입력 파라미터로 state와 runtime을 받고, 흐름의 특정 지점(before/after)에서 순차적으로 실행됩니다.

🔍 비유 — 라인 옆에 선 검수원(관찰자) Node-style은 공장 라인 옆에 서서 지나가는 물건을 지켜보는 검수원과 같습니다. 물건이 기계에 들어가기 직전(before_model)에 "번호 잘 찍혔나" 살펴보고, 이상 없으면 로그를 적고 그냥 흘려보냅니다. 물건 자체를 붙잡거나 바꾸는 게 주 임무가 아니라, 들여다보고 기록·검사하는 데 특화돼 있죠. 그래서 공식 문서도 로깅·검증·상태 갱신에 이 방식을 추천합니다 — 노드 내부의 상세한 맥락에 바로 접근할 수 있으니까요.

아래는 모델이 호출되기 직전에 상태와 런타임을 그대로 찍어 보는 미들웨어입니다.

📥 코드 — @before_model 미들웨어 정의
from langchain.agents.middleware import before_model

@before_model
def log_before_model(state, runtime) :
    print(f"(step1)before_model_state : \n{state}")
    print(f"(step2)before_model_runtime : \n{runtime}")
    print(f"(step3)사용자 이름 : {runtime.context.user_name}")
    return None
  • @before_model이 훅(지점) — "모델 호출 직전에 걸어 줘"라는 뜻.
  • log_before_model이 미들웨어(기능) — 실제로 로그를 남기는 코드.
  • state로는 현재까지의 메시지를, runtime.context.user_name으로는 우리가 넣어 준 사용자 이름을 꺼냅니다.
  • return None — 상태를 바꾸지 않고 그대로 흘려보낸다는 뜻(관찰만 함).

이제 이 미들웨어를 Agent에 장착합니다. 핵심은 context_schema=Context를 넘겨 주는 것 — 이래야 미들웨어가 runtime.context로 우리 데이터를 볼 수 있습니다.

📥 코드 — Agent에 미들웨어 장착
agent = create_agent(
    model="gpt-5-mini",
    tools=[],
    middleware=[log_before_model],
    context_schema=Context,
)
⚠️ @before_model은 매번 실행됩니다 @before_model은 모델이 호출될 때마다 실행됩니다(도구를 쓴 뒤 모델을 다시 부를 때도 반복). 반면 @before_agent는 Agent 실행 전체에서 딱 한 번만 실행됩니다. 로그가 여러 번 찍힌다면 이 차이 때문이에요.

실습 ① — 미들웨어로 내부 엿보기

이제 Agent를 호출합니다. 이때 context=Context(user_name="Jay")로 사용자 이름을 주입합니다.

📥 코드
agent.invoke(
    {"messages": [{"role": "user", "content": "제 이름이 뭐죠?"}]},
    context=Context(user_name="Jay"),
)

미들웨어가 모델 호출 직전에 끼어들어, 아래처럼 내부 상태를 그대로 출력합니다.

▶ 이렇게 나와요
(step1)before_model_state :
{'messages': [HumanMessage(content='제 이름이 뭐죠?', additional_kwargs={}, response_metadata={}, id='2ec93f0a-...')]}
(step2)before_model_runtime :
Runtime(context=Context(user_name='Jay'), store=None, stream_writer=<function Pregel.stream.<locals>.stream_writer at 0x113a5b1a0>, previous=None)
(step3)사용자 이름 : Jay

state 안에는 사용자 메시지가, runtime 안에는 우리가 넣은 Context(user_name='Jay')가 그대로 들어 있습니다. 그래서 runtime.context.user_name으로 "Jay"를 정확히 꺼냈죠.

🚨 함정 — "이름을 봤는데 왜 답을 못 하지?" 미들웨어는 사용자 이름 "Jay"를 분명히 읽었습니다. 그런데 정작 모델의 최종 답변은 이렇습니다:

"모르겠어요 — 이 채팅에선 아직 이름을 알려주지 않으셨어요…"

왜일까요? Node-style은 옆에서 지켜보며 로그만 남겼을 뿐, 그 이름을 모델에게 건네주지는 않았기 때문입니다. 검수원이 물건 번호를 노트에 적었다고 해서, 그 번호가 물건 자체에 새겨지는 건 아니니까요. "관찰"과 "개입(변형)"은 다릅니다. 이 아쉬움을 해결하는 것이 바로 다음에 나올 Wrap-style입니다.
📘 보충 — Node-style Hook은 어디에 쓰나 (공식 권장 용도)
용도설명
Validation (검증)입력 데이터가 비즈니스 로직에 들어가기 직전에 이상 없는지 검사
Logging (로깅)노드 내부에서 벌어지는 상세한 작업 단계를 기록
State Updates (상태 갱신)실행 결과에 따라 즉시 상태를 바꿔야 할 때

공통점은 모두 "흐름을 크게 틀지 않고, 특정 지점에서 곁들이는 작업"이라는 점입니다. 데코레이터로는 @before_agent, @before_model, @after_model, @after_agent가 있습니다.

방법 2 — Wrap-style Hook (@wrap_model_call)

두 번째 방식은 Wrap-style Hook입니다. 이름 그대로 실행을 감싸서(wrap), 모델이나 도구가 호출될 때 그 실행과 제어를 통째로 가로챕니다(intercept). 입력 파라미터는 request(요청 꾸러미)와 handler(실제 실행 함수)입니다.

🔍 비유 — 물건을 붙잡는 문지기 Node-style이 "옆에서 지켜보는 검수원"이었다면, Wrap-style은 기계 앞을 막고 선 문지기입니다. 들어가는 물건(request)을 손에 쥐고, 라벨을 바꿔 붙이거나(변형) · 아예 기계를 거치지 않고 되돌려 보내거나(건너뛰기) · 실패하면 몇 번이고 다시 밀어 넣을(재시도) 수 있습니다. "실제로 기계를 돌려라"라고 버튼을 눌러 주는 행위가 handler(request)이고, 그 버튼을 누를지·언제 누를지·몇 번 누를지를 문지기가 결정하는 것이죠.

Wrap-style이 가진 세 가지 힘은, 실제 기계(모델·도구)를 몇 번 돌리느냐로 나누면 한눈에 들어옵니다.

패턴실행 횟수무엇을 하나예시
① 단락 실행
(Short-circuit)		0번handler를 아예 부르지 않고 결과를 바로 반환캐싱(같은 질문이면 저장된 답 즉시 반환), Emulation(가짜 데이터 반환)
② 정상 흐름
(Normal flow)		1번평범하게 한 번 실행하되 입력·출력을 가공Transformation(들어가기 전 인자 보안 처리, 복잡한 JSON을 읽기 쉬운 텍스트로 변환)
③ 반복 실행
(Retry logic)		여러 번실패하면 성공할 때까지 다시 시도Retries(네트워크 오류 시 미들웨어 레벨에서 3번 더 재시도)
💡 두 종류의 Wrap 감싸는 대상에 따라 두 가지가 있습니다. wrap_model_call은 각 모델 호출 주변에서, wrap_tool_call은 각 도구 호출 주변에서 작동합니다. 이 노트북에서는 wrap_model_call을 다룹니다.

예시 — 메시지 길이에 따라 모델을 바꿔 끼우기

Wrap-style의 "가로채서 바꾸기"를 보여 주는 대표 예시입니다. 사용자 메시지가 짧으면 값싼 모델, 길면 강력한 모델을 쓰도록 request.model 자체를 교체합니다. 비싼 GPT-5를 항상 쓰는 대신, 상황에 맞게 골라 써서 비용을 아끼는 실전 패턴이죠.

📥 코드
from langchain.agents.middleware import wrap_model_call
from langchain_openai import ChatOpenAI

# 작성 예시
@wrap_model_call
def dynamic_model_selector(request, handler):
    # 최근 사용자의 입력 메시지 추출
    last_msg = request.messages[-1].content if request.messages else ""
    msg_len = len(last_msg)

    # 길이에 따라 모델 선택
    if msg_len < 10:
        model_name = "gpt-5-nano"
    elif msg_len < 30:
        model_name = "gpt-5-mini"
    else:
        model_name = "gpt-5"

    # request.model을 새로운 모델로 교체
    new_model = ChatOpenAI(model_name=model_name)
    new_request = request.override(model=new_model)

    # 수정된 요청으로 LLM 호출
    return handler(new_request)
  • request.messages[-1]로 가장 최근 메시지를 꺼내 길이를 잽니다.
  • request.override(model=new_model)로 요청 안의 모델을 바꿔 끼웁니다. 원본을 건드리지 않고 새 요청을 만든다는 점이 포인트.
  • 마지막에 handler(new_request) — 바뀐 요청으로 실제 모델을 호출합니다.

실습 ② — 사용자 이름을 시스템 프롬프트에 주입하기

드디어 아까 실습 ①의 아쉬움을 해결할 차례입니다. Node-style은 이름을 "봤지만" 모델에 못 넘겼죠. Wrap-style로는 이름을 시스템 프롬프트에 직접 끼워 넣어 모델이 알게 만들 수 있습니다.

🔍 비유 — 모델에게 직접 떠먹여 주기 request는 모델에게 전달할 정보가 다 든 보따리입니다. 이 보따리 안 책상(runtime) 위에 놓인 신분증(context.user_name)을 꺼내, "사용자의 이름은 Jay Pak입니다"라는 쪽지(시스템 프롬프트)로 만들어 보따리에 다시 넣어 모델에게 건넵니다. Node-style이 신분증을 힐끗 보고 노트에만 적었다면, Wrap-style은 그 정보를 모델 입에 직접 떠먹여 주는 셈이에요.
📥 코드 — 요청을 가로채 시스템 프롬프트 덮어쓰기
from typing import Callable
from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse
from langchain.messages import HumanMessage, SystemMessage

@wrap_model_call
def inject_user_name(request: ModelRequest, handler: Callable[[ModelRequest], ModelResponse]) -> ModelResponse:
    print(f"request : \n{request}")

    # 1. request 보따리 안의 책상(runtime)에서 신분증 정보 추출
    user_name = request.runtime.context.user_name

    if user_name:
        system_message = f"사용자의 이름은 {user_name}입니다"
        # 2. request.override()를 사용해 시스템 프롬프트 덮어쓰기 (모델에게 직접 떠먹여 주기)
        request = request.override(system_prompt=system_message)

    # 3. 조작된 request를 handler를 통해 모델로 전송
    return handler(request)

이제 이 미들웨어를 장착한 Agent를 만들고, 아까와 똑같은 질문을 던져 봅니다.

📥 코드
from langchain.agents import create_agent

agent = create_agent(
    model="gpt-5-mini",
    tools=[],
    middleware=[inject_user_name],
    context_schema=Context,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "제 이름이 뭐죠?"}]},
    context=Context(user_name="Jay Pak"),
)
print(result["messages"][-1].content)

먼저 print(f"request : ...")가 가로챈 요청 꾸러미를 통째로 보여 줍니다. 그 안에 우리 Context가 실려 있는 게 보이죠.

두 주인공 다시 보기 — handler와 request

Wrap-style을 다룰 때 계속 나온 handler와 request, 이 둘의 정체를 확실히 정리하고 갑시다.

1. handler 란?

handler는 "실제 모델(LLM) 호출을 실행하는 함수"이자 "다음 단계로 넘겨주는 함수"입니다. @wrap_model_call 미들웨어는 모델 호출을 가로챈 상태이므로, handler를 직접 불러 줘야만 비로소 진짜 LLM이 실행됩니다. (문지기가 버튼을 눌러 줘야 기계가 돈다고 했죠.)

📥 코드 — 가로채기의 전형적인 3단 구조
@wrap_model_call
def wrap_model_call_hook(request, handler):
    # 1. 모델 호출 전 처리 (예: 프롬프트 수정)

    # 2. 실제 모델 호출 실행 (handler 호출 필수!)
    result = handler(request)

    # 3. 모델 호출 후 처리 (예: 결과 가공)
    return result
⚠️ handler를 안 부르면? handler(request)를 빼먹으면 실제 모델이 영영 호출되지 않습니다. 단, 이걸 일부러 안 부르는 게 앞서 본 단락 실행(캐싱·Emulation)입니다 — "실수로 빼먹기"와 "의도적으로 건너뛰기"는 코드가 같아도 의도가 다르다는 점만 기억하세요.

2. request 란?

request는 "모델이나 도구를 호출하는 데 필요한 모든 정보를 담은 데이터 꾸러미(보따리)"입니다. 프롬프트·파라미터·설정값이 모두 여기 들어 있습니다. 실습 ②의 출력에서 봤듯, 주요 칸은 이렇습니다.

필드담긴 것
model어떤 모델을 쓸지 (예: ChatOpenAI)
system_prompt시스템 프롬프트 (없으면 None)
messages대화 메시지 목록
tools / tool_choice사용 가능한 도구 · 강제 선택할 도구
response_format출력 포맷 (예: JSON schema)
state / runtime실행 상태(메시지 기록) · 실행 환경(context·store·stream)
model_settings모델 설정 (온도, 토큰 제한 등)
💡 request.override(...)의 정체 우리가 계속 쓴 request.override(model=...), request.override(system_prompt=...)는 이 꾸러미의 특정 칸만 바꾼 새 요청을 만들어 주는 메서드입니다. 원본을 직접 뜯어고치지 않고 바뀐 사본을 만들어 넘기므로 안전합니다.

📚 한 장 정리

오늘의 핵심 미들웨어는 "무엇을", 훅은 "언제". 그리고 관찰만 할 거면 Node-style, 흐름을 가로채 바꿀 거면 Wrap-style.
  • 미들웨어 vs 훅 — 미들웨어(기능)를 훅(지점)이라는 갈고리에 걸어서 쓴다.
  • Runtime vs State — Runtime은 바깥 환경(context·store·stream, 주방), State는 내부 산출물(messages·tool_results, 만든 요리).
  • dataclass — Context를 담는 그릇. @dataclass 한 줄로 __init__·__repr__·__eq__를 공짜로 얻는다.
  • Node-style(state, runtime) — 옆에서 지켜보는 검수원. 로깅·검증·상태 갱신에 적합. 이름을 봤지만 모델에 못 넘겨 "모르겠어요".
  • Wrap-style(request, handler) — 앞을 막는 문지기. 단락 실행(0번)·정상 흐름(1번)·재시도(여러 번). 이름을 주입해 "Jay Pak님입니다".
  • handler·request — handler(request)를 불러야 진짜 모델이 돈다. request.override(...)로 꾸러미의 특정 칸만 바꾼 새 요청을 만든다.
