8

프롬프트 A/B 평가 하네스 (LLM-as-judge)

서비스화 층 이 프로젝트의 하이라이트 ⏱ 3~4시간
🎯 목표

프롬프트를 한 줄 고쳤습니다. 나아졌을까요?

지금까지 우리가 확인한 방법은 질문 두세 개를 던져 보는 것이었습니다. 그런데 이 방법은 거의 항상 "좋아졌다"는 답을 줍니다. 내가 고친 부분이 잘 드러나는 질문을 무의식중에 고르게 되고, 내가 고쳤다는 걸 알고 답을 읽으니까요.

이번 STEP에서는 질문 10~20개를 파일에 고정해 두고, 프롬프트 A와 B로 각각 전부 돌린 뒤, 자동으로 채점해 표 한 장을 얻습니다. 끝나고 손에 남는 건 이겁니다. 

        도구선택_정확도  형식준수율  답변품질_평균
prompt
A               0.800     0.667        4.100
B               0.933     1.000        4.200

이 표를 만드는 장치를 평가 하네스(evaluation harness)라고 부릅니다. 하네스는 장비를 붙들어 고정하는 벨트예요 — 한 번 만들어 두면 그다음부터는 프롬프트를 고칠 때마다 같은 조건으로 다시 잽니다. 이번에 만드는 건 표 한 장이 아니라 표를 계속 뽑아 주는 장치입니다.

🧠 개념 — 딱 하나만

같은 코스에서 같은 스톱워치로 재야 비교가 된다

🏃 비유 — 달리기 기록

새 러닝화가 더 빠른지 알고 싶다고 해 봅시다. 오늘은 한강에서, 다음 주엔 동네 언덕에서 뛰고 "오늘이 더 가벼웠어"라고 말하면 그건 신발 이야기가 아니라 코스 이야기입니다. 같은 코스를 정해 두고, 같은 스톱워치로 재야 비로소 신발을 비교한 게 됩니다.

프롬프트도 똑같습니다. 그래서 두 가지를 고정합니다.

  • 코스 = eval_cases.json — 질문 목록과, 질문마다 "무엇이 맞는 답인지"를 미리 적어 둔 파일
  • 스톱워치 = 채점 규칙 — 매번 똑같은 기준으로 점수를 매기는 코드

이 둘을 만들어 놓고 프롬프트만 바꿔 가며 돌리는 것, 그게 이번 STEP의 전부입니다.

📋 eval_cases.json질문 N개 + 기대하는 것
(고정된 코스)
→
🤖 Agent 실행프롬프트 A로 N번
프롬프트 B로 N번
→
📏 점수 3가지도구 선택 · 형식 · 답변 품질
(스톱워치)
→
📊 표A vs B
갈린 케이스 목록

점수는 셋으로 나눠서 잰다

답변 하나를 놓고 "몇 점?"이라고 물으면 뭉뚱그린 숫자 하나가 나옵니다. 그 숫자가 떨어졌을 때 왜 떨어졌는지는 알 수 없어요. 그래서 세 가지를 따로 잽니다. 그중 둘은 코드로 셀 수 있으니 공짜고, 사람의 판단이 필요한 하나만 LLM에게 맡깁니다.

점수어떻게 재나비용이게 낮으면
① 도구 선택기대한 도구가 used_tools에 있나0원약관 질문에 웹을 뒤졌거나, 인사에 도구를 불렀다
② 형식 준수sources가 채워졌나 · blocked가 기대와 같나0원근거를 안 달았거나, 막아야 할 걸 안 막았다
③ 답변 품질다른 LLM에게 "이 기준으로 1~5점" 부탁호출 1회도구도 형식도 맞는데 내용이 부실하다

③이 LLM-as-judge입니다. 이름은 거창하지만 하는 일은 단순해요 — 채점 기준(rubric)을 케이스마다 미리 적어 두고, 그 기준과 Agent의 답변을 함께 채점자 모델에게 넘겨 점수와 이유를 받아 옵니다. 지금까지 사람이 눈으로 읽어야만 판단할 수 있던 "내용이 맞나?"를 자동으로 만드는 것이죠.

셋으로 나눠 두면 점수가 움직였을 때 원인이 바로 보입니다. "①은 그대로인데 ②만 떨어졌다"면 도구는 잘 골랐는데 근거를 안 달았다는 뜻이고, 고쳐야 할 곳은 프롬프트의 근거 관련 규칙 한 줄입니다.

🧩 출발점 — 채점기가 볼 것은 이미 준비돼 있다

새로 만들 채점 코드가 무엇을 읽는지부터 봅시다. STEP 7까지 만들어 온 ask()는 질문 하나를 처리하고 칸이 다섯 개인 dict를 돌려줍니다. 

>>> from agent import ask
>>> ask("신용카드를 분실하면 회원의 책임은 어디까지인가요?", session_id="tmp")

{
  "answer":     "분실 신고를 접수한 시점을 기준으로 책임 범위가 달라집니다. 신고 이후 발생한 ...",
  "sources":    ["03_신용카드개인회원표준약관_SC제일은행 p.12"],
  "confident":  True,
  "used_tools": ["search_internal_docs"],
  "blocked":    False,
}

이 다섯 칸이 곧 채점 재료입니다. 앞 STEP들이 하나씩 만들어 둔 것이고, 여기서 값을 합니다.

칸만든 곳이번 STEP에서 쓰는 곳
used_toolsSTEP 6 · 7점수 ① — 기대한 도구를 썼는지 대조
sourcesSTEP 4 (ChatReply)점수 ② — 근거를 달았는지 확인
blockedSTEP 4 (가드레일)점수 ② — 막혀야 할 게 막혔는지 확인
answerSTEP 4점수 ③ — 채점자 모델에게 넘길 본문
confidentSTEP 4(이번엔 안 씀 — 케이스를 늘릴 때 쓸 여지)

답변을 그냥 문자열 하나로 돌려줬다면 지금 이 채점은 불가능했을 겁니다. 근거가 있는지 보려고 본문을 정규식으로 뒤져야 했을 테니까요. STEP 4에서 답변에 칸을 만들어 둔 이유가 여기서 드러납니다 — 칸이 있어야 셀 수 있고, 셀 수 있어야 비교할 수 있습니다.

🛠 할 일 — 파일 넷

만들 것은 넷입니다. 앞의 셋은 짧고, 시간은 대부분 ③(케이스 쓰기)과 ④(채점기)에 들어갑니다.

① prompts.py비교할 프롬프트 A와 B
② agent.py 수정프롬프트를 요청마다
갈아끼울 구멍
③ eval_cases.json질문 + 기대 (코스)
④ evaluate.py돌리고 채점하고
표로 만드는 스크립트
①

prompts.py — 비교할 두 프롬프트

— B는 A에서 딱 두 군데만 바꾼다

A는 지금 서비스가 쓰고 있는 프롬프트 그대로여야 합니다. 지금 상태가 기준점이니까요. 복사해 두면 나중에 agent.py만 고쳤을 때 A가 옛날 것이 되므로, 복사하지 않고 가져다 씁니다. 

# prompts.py
# [가설] B는 A보다 (1) 근거(sources)를 더 자주 채우고, (2) 불필요한 도구 호출을 줄인다.
#        → '형식 준수율'과 '도구 선택 정확도'가 오를 것이다. 답변 품질은 비슷할 것이다.

from agent import SYSTEM_PROMPT as SYSTEM_A     # A = 지금 서비스가 쓰는 프롬프트 그대로

SYSTEM_B = """너는 정확성을 최우선으로 하는 업무 비서다.

규칙:
1. 오늘 날짜·현재 시각이 필요하면 반드시 get_today를 호출한다. 날짜를 추측하지 않는다.
2. 숫자 계산은 반드시 calculate를 호출한다. 암산하지 않는다.
3. 약관·규정·계약 조건에 관한 질문은 web_search보다 search_internal_docs를 먼저 쓴다.
   우리 문서에 있는 내용을 인터넷에서 찾으면 틀린 답이 나온다.
4. 도구를 사용했다면 sources에 근거를 반드시 담는다.                          ←─ 바꾼 곳 (1)
   사내 문서는 "문서명 p.쪽수", 웹은 전체 URL 형식으로 적는다. 빈 목록으로 두지 않는다.
5. 최신 정보가 필요하면 web_search를 호출하고, 답변에 출처 URL을 함께 적는다.
6. 도구로도 확인할 수 없는 내용은 모른다고 말하고 confident를 false로 둔다. 지어내지 않는다.
7. 인사, 잡담, 너 자신에 대한 질문에는 도구를 호출하지 않는다.                 ←─ 바꾼 곳 (2)
   도구를 부를지 애매하면 '이 질문에 답하려면 내가 모르는 사실이 필요한가?'를 먼저 자문한다."""

PROMPTS = {"A": SYSTEM_A, "B": SYSTEM_B}        # 채점기는 이 딕셔너리를 훑는다

참고로 A(= agent.py의 SYSTEM_PROMPT)에서 이 두 자리는 이렇게 돼 있습니다.

4. search_internal_docs의 결과를 쓸 때는 답변에 [근거]의 문서명과 쪽수를 반드시 적는다.
   → B: "답변에 적는다"가 아니라 "sources 칸에 담는다"로, 그리고 형식까지 지정

(7번 없음)
   → B: 도구를 안 써도 되는 질문을 다루는 규칙을 새로 추가

코드를 쓰기 전에 맨 위에 가설 한 줄을 적습니다. "무엇을 왜 바꿨고, 그래서 어느 숫자가 오를 것이다"까지요. 이걸 안 적으면 나중에 표를 받아 들고도 "그래서 이게 좋아진 건가?"를 판단할 기준이 없습니다.

B가 두 군데만 고친 이유도 같습니다. 열 군데를 고치고 점수가 올랐다면 어느 수정 덕분인지 알 수 없어서, 다음에 무엇을 더 하면 좋을지도 알 수 없습니다. 한 번에 조금만 바꾸고 여러 번 재는 쪽이 결국 빠릅니다.

②

agent.py — 프롬프트를 요청마다 갈아끼울 구멍

— STEP 7에서 모델을 바꾼 것과 완전히 같은 모양

지금 SYSTEM_PROMPT는 create_agent(...)에 한 번 박혀 있습니다. 그대로 두면 A로 한 번 돌리고, 파일을 고치고, B로 또 돌려야 하죠. 그러면 두 실행 사이에 코드가 달라지므로 "같은 코스"라는 전제가 깨집니다. 한 번의 실행 안에서 A와 B를 둘 다 돌리려면 프롬프트가 인자여야 합니다.

고칠 곳은 세 군데입니다. STEP 7에서 provider를 뚫은 것과 자리도, 모양도 같아요. 

# agent.py

@dataclass
class Context:
    provider: str | None = None
    system_prompt: str | None = None       # ①  상자에 칸 하나 추가


@wrap_model_call                           # ②  모델 호출 직전에 끼어드는 훅 하나 추가
def override_prompt(request, handler):
    """요청에 시스템 프롬프트가 지정돼 있으면 그것으로 갈아끼운다(평가·실험용)."""
    sp = getattr(request.runtime.context, "system_prompt", None)
    if sp:
        request = request.override(system_prompt=sp)
    return handler(request)


agent = create_agent(
    ...
    middleware=[
        input_guardrail,
        select_provider,
        override_prompt,                   # ②  미들웨어 목록에도 등록
        PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
        ...
    ],
)


def ask(message, session_id="default", provider=None, system_prompt=None):   # ③ 인자 추가
    ...
        context=Context(provider=provider, system_prompt=system_prompt),     # ③ 상자에 담아 전달
evaluate.pyask(질문, system_prompt=SYSTEM_B)
→
Context 상자system_prompt="...규칙 7..."
→
override_prompt상자에 값이 있네
→ 요청의 프롬프트를 교체
→
모델 호출B 프롬프트로 답한다

system_prompt를 안 넘기면 None이라 if sp:가 거짓이 되고, 아무 일도 일어나지 않습니다. 즉 평소 요청은 지금까지와 똑같이 돌아가고, 평가할 때만 이 구멍을 씁니다.

이제 손잡이가 둘입니다 — 모델(provider)과 프롬프트(system_prompt). 둘 다 코드 밖에서 지정할 수 있으니, "A를 gemini로" 같은 조합도 코드를 고치지 않고 잴 수 있습니다. 실험할 수 있는 시스템이란 이런 모양입니다.

③

eval_cases.json — 코스 만들기

— 제일 오래 걸리고, 제일 오래 남는 부분

케이스 하나는 질문 하나와, 그 질문에 대해 우리가 기대하는 것입니다. 칸은 여섯 개예요. 

{
  "id": "doc-01",
  "question": "신용카드를 분실하면 회원의 책임은 어디까지인가요?",
  "expect_tool": "search_internal_docs",
  "expect_sources": true,
  "expect_blocked": false,
  "rubric": "분실 신고 시점을 기준으로 책임 범위가 달라진다는 점을 약관 근거와 함께 설명해야 한다."
}
칸쓰이는 점수의미
id—케이스 이름표. 나중에 "어느 케이스에서 갈렸나"를 이 이름으로 본다
question—Agent에게 던질 질문. 매번 이 문장 그대로 던진다
expect_tool①써야 하는 도구 이름. 아무 도구도 안 써야 하면 null
expect_sources②근거를 달아야 하는 질문인가
expect_blocked②가드레일에 막혀야 하는 질문인가
rubric③채점자에게 줄 채점 기준

rubric은 모범답안이 아니라 "무엇이 들어 있어야 하는가"

rubric에 모범답안을 적으면 채점자는 표현이 다르다는 이유로 점수를 깎습니다. 우리가 보고 싶은 건 표현이 아니라 내용이죠. 그래서 채점자가 답변을 읽으며 있다/없다로 확인할 수 있는 문장을 적습니다. 

"rubric": "분실 신고 시점을 기준으로 책임 범위가 달라진다는 점을 약관 근거와 함께 설명해야 한다."
          → 채점자가 확인할 것: (1) 신고 시점 언급  (2) 책임 범위가 달라진다는 설명  (3) 근거 제시

"rubric": "전자금융거래기본약관의 손해배상·면책 조항을 근거로 설명해야 한다.
           조건 없이 '무조건 보상된다'고 하면 감점."
          → 있어야 할 것뿐 아니라 '있으면 안 되는 것'도 적을 수 있다

"잘 설명해야 한다" 같은 문장은 확인할 대상이 없어서 채점자가 매번 다른 점수를 줍니다. 기준이 흔들리면 A와 B의 차이도 묻힙니다.

개수보다 종류를 골고루

케이스 15개를 사내 문서 질문으로만 채우면, 모든 질문에 문서 검색을 부르는 Agent가 만점을 받습니다. 코스는 우리 서비스에 실제로 들어올 질문의 축소판이어야 해요.

종류개수이 줄이 없으면 놓치는 것
사내 문서 질문5~6주력 기능. 답이 data/의 약관에 있으니 채점 기준을 정확히 쓸 수 있다

evaluate.py — 채점기

— 파일 하나. 아래에서 한 조각씩 쌓아 올린다

먼저 파일 전체의 모양입니다. 위에서부터 이 네 덩어리로 되어 있고, 아래에서 순서대로 하나씩 만듭니다.

evaluate.py ├── ④-1 준비 import · 채점자 모델 · Judgement 형식 · 채점 프롬프트 ├── ④-2 judge_answer() 답변 하나를 채점자에게 넘겨 1~5점을 받는다 ├── ④-3~6 run_case() 케이스 하나를 돌리고 → 세 점수를 매겨 → 표 한 줄로 만든다 └── ④-7 main() 전부 돌리고 → 표로 모으고 → 요약과 비교를 찍는다

중요한 건 ④-3부터 ④-6까지가 전부 run_case() 함수 하나라는 점입니다. 길어서 조각내 보고 있을 뿐이에요. 조각들이 어떻게 이어지는지는 마지막의 "전체 코드 한 번에 보기"에서 확인할 수 있습니다.

④-1 · 준비 — 채점자에게 "점수와 이유"를 정해진 모양으로 받는다
import json

import pandas as pd
from dotenv import load_dotenv
from pydantic import BaseModel, Field
from langchain.chat_models import init_chat_model
from langfuse import get_client

from agent import ask               # 우리 Agent를 부르는 창구
from prompts import PROMPTS         # {"A": ..., "B": ...}

load_dotenv()
langfuse = get_client()


class Judgement(BaseModel):
    """채점 결과의 형식. 점수만 받지 않고 이유까지 받는다."""
    score: int = Field(description="1~5점", ge=1, le=5)
    reason: str = Field(description="그 점수를 준 이유 한 문장")


judge = init_chat_model("openai:gpt-5-mini").with_structured_output(Judgement)

마지막 줄이 채점자입니다. .with_structured_output(Judgement)는 STEP 4에서 ChatReply로 한 것과 같은 일이에요 — "답을 아무렇게나 쓰지 말고 이 칸에 맞춰 채워라"라고 모델을 묶어 둡니다. 그래서 judge.invoke(...)는 문자열이 아니라 Judgement 객체를 돌려주고, .score·.reason으로 바로 꺼내 쓸 수 있습니다.

점수만 받지 않고 이유를 함께 받는 이유는 두 가지입니다. 나중에 우리가 "왜 이 점수인지" 읽어야 하고, 이유를 쓰게 하면 채점자가 답변을 실제로 들여다보게 되어 점수가 덜 흔들립니다.

채점자에게 보낼 프롬프트는 이렇게 생겼습니다.

JUDGE_TEMPLATE = """너는 엄격한 채점자다. 아래 답변을 채점 기준에 따라 1~5점으로 평가하라.

[질문]
{question}

[채점 기준]
{rubric}

[답변]
{answer}

[제시된 근거]
{sources}

점수 척도 — 반드시 이 기준을 따르라:
5 = 기준을 완전히 충족하고, 근거가 적절하다
4 = 기준을 충족하나 사소한 누락이 있다
3 = 절반쯤 맞다. 중요한 내용이 빠졌다
2 = 대체로 빗나갔다. 일부만 관련 있다
1 = 완전히 틀렸거나, 문서에 없는 내용을 지어냈다

지어낸 내용이 하나라도 있으면 다른 게 아무리 좋아도 1점이다."""

척도의 뜻을 못 박아 두는 게 핵심입니다. "1~5점으로 평가하라"고만 하면 채점자는 대부분 3~4점만 주고, 그러면 A와 B가 아무리 달라도 평균이 붙어 버려 비교가 안 됩니다. 각 점수의 의미를 적어 두면 점수가 흩어지고, 차이가 보입니다.

④-2 · judge_answer() — 답변 하나를 채점받는다
def judge_answer(case: dict, result: dict) -> Judgement:
    prompt = JUDGE_TEMPLATE.format(
        question=case["question"],
        rubric=case["rubric"],
        answer=result["answer"],
        sources=result["sources"] or "(없음)",   # 빈 목록이면 '(없음)'이라고 명시해 준다
    )
    return judge.invoke(prompt)

case는 eval_cases.json에서 읽은 케이스 하나, result는 ask()가 돌려준 dict입니다. 둘을 템플릿의 빈칸에 끼워 넣어 채점자에게 보내면 이런 게 돌아옵니다. 

Judgement(score=4, reason="신고 시점 기준으로 책임이 달라진다는 점은 설명했으나 근거 문서명이 없다")

sources가 빈 목록일 때 "(없음)"으로 바꿔 넘기는 건, 빈 대괄호 []만 보내면 채점자가 근거가 없다는 사실을 흘려보내기 쉬워서입니다.

④-3 · run_case() 시작 — 케이스 하나를 돌린다
def run_case(case: dict, label: str, system_prompt: str) -> dict:
    result = ask(
        case["question"],
        session_id=f"eval-{label}-{case['id']}",   # 케이스마다 다른 세션
        system_prompt=system_prompt,               # ②에서 뚫어 둔 구멍
    )

인자 셋의 뜻은 이렇습니다. case는 케이스 하나, label은 "A"나 "B", system_prompt는 그 라벨에 해당하는 프롬프트 본문입니다.

session_id를 케이스마다 다르게 주는 게 중요합니다. STEP 3에서 만든 메모리는 같은 세션이면 앞 대화를 이어받게 돼 있어요. 전부 같은 세션으로 돌리면 5번째 케이스를 채점할 때 앞의 네 질문이 대화에 섞여 있게 되고, 그건 우리가 재려던 상황이 아닙니다. f"eval-{label}-{case['id']}"는 eval-B-doc-01 같은 이름을 만들어 주니, 케이스마다도 프롬프트마다도 세션이 갈립니다.

덤으로 이 이름은 Langfuse에도 세션 이름으로 남습니다(STEP 6). 나중에 대시보드에서 eval-로 걸러 평가 실행만 따로 볼 수 있어요.

④-4 · 점수 ① 도구 선택 — 코드로 센다
    expect = case.get("expect_tool")
    used = result["used_tools"]
    tool_ok = (expect in used) if expect else (len(used) == 0)

마지막 줄이 조건에 따라 두 갈래로 갈립니다. 풀어 쓰면 이렇습니다.

if expect:                        # 써야 하는 도구가 지정된 케이스
    tool_ok = expect in used      #   → 그 도구가 사용 목록에 들어 있나
else:                             # expect_tool이 null인 케이스
    tool_ok = len(used) == 0      #   → 아무 도구도 안 썼나

실제 값을 넣어 보면 이렇게 됩니다.

케이스expect_tool실제 used_toolstool_ok왜
doc-01search_internal_docs["search_internal_docs"]✅ True기대한 도구를 썼다
doc-01search_internal_docs["web_search"]❌ False사내 문서 대신 웹을 뒤졌다
doc-01search_internal_docs["get_today", "search_internal_docs"]✅ True다른 도구를 곁들여도 통과
none-01null[]✅ True인사에 도구를 안 불렀다
none-01null["web_search"]❌ False안 불러도 될 도구를 불렀다

==가 아니라 in을 쓴 게 셋째 줄의 이유입니다. 오늘 날짜를 확인한 뒤 약관을 찾아보는 건 잘못된 판단이 아니니까요. 여기서 재려는 건 "군더더기 없이 딱 하나만 불렀나"가 아니라 "필요한 도구를 골라냈나"입니다.

④-5 · 점수 ② 형식 준수 — 근거와 차단 여부
    sources_ok = bool(result["sources"]) if case.get("expect_sources") else True
    block_ok = result["blocked"] == case.get("expect_blocked", False)
    format_ok = sources_ok and block_ok

첫 줄 — 근거를 요구한 케이스(expect_sources: true)에서만 sources가 채워졌는지 봅니다. bool([])은 False, bool(["약관 p.12"])은 True라서 목록이 비었는지를 그대로 판정합니다. 요구하지 않은 케이스는 True로 통과시켜요 — "안녕하세요"에 근거가 없다고 감점하면 안 되니까요.

둘째 줄 — 차단 여부는 양방향으로 맞아야 합니다. 막아야 할 질문이 통과한 것도 틀린 거지만, 평범한 질문이 막힌 것도 똑같이 틀린 겁니다. 그래서 크거나 작거나가 아니라 ==로 "기대와 같은가"를 봅니다. .get("expect_blocked", False)는 그 칸을 안 적은 케이스를 "안 막혀야 함"으로 취급한다는 뜻입니다.

block-01trueTrue✅ True프롬프트 탈취 시도를 막았다
block-01trueFalse❌ False가드레일이 뚫렸다
doc-01falseTrue❌ False정상 질문을 막아 버렸다
④-6 · 점수 ③ 답변 품질 + 표 한 줄로 만들기
    if case.get("expect_blocked"):
        score, reason = (5 if block_ok else 1), "차단 케이스(내용 채점 생략)"
    else:
        verdict = judge_answer(case, result)
        score, reason = verdict.score, verdict.reason

    return {
        "id": case["id"], "prompt": label,
        "tool_ok": tool_ok, "format_ok": format_ok, "score": score,
        "expect_tool": expect, "used_tools": ",".join(used) or "-",
        "blocked": result["blocked"], "reason": reason,
    }

차단이 기대되는 케이스는 채점자를 부르지 않습니다. 돌아온 답이 "시스템 설정에 관한 요청은 처리할 수 없습니다"인데, 이 문장의 '내용'을 채점할 건 없으니까요. 대신 막는 데 성공했으면 5점, 뚫렸으면 1점을 넣습니다. 점수를 아예 비워 두면 가드레일이 뚫려도 품질 평균이 꿈쩍하지 않아서, 표만 보고는 눈치채지 못하게 됩니다. 덤으로 채점 호출도 케이스 수만큼 아낍니다.

마지막 return이 이 함수의 결과물, 즉 표 한 줄입니다. 실제로는 이런 dict가 나옵니다. 

{"id": "doc-01", "prompt": "B", "tool_ok": True, "format_ok": True, "score": 5,
 "expect_tool": "search_internal_docs", "used_tools": "search_internal_docs",
 "blocked": False, "reason": "신고 시점 기준과 약관 근거를 모두 제시함"}

used_tools를 ",".join(used)로 문자열로 만드는 건 표의 한 칸에 들어가야 해서입니다. 아무것도 안 썼으면 빈 문자열이 되는데, 그러면 표에서 안 보이니 or "-"로 대시를 넣습니다.

정리하면 케이스 하나 = 표 한 줄입니다. 케이스 8개를 프롬프트 2개로 돌리면 16줄이 나옵니다.

④-7 · main() — 전부 돌리고, 표로 모으고, 비교한다

남은 건 run_case()를 반복해 부르고 결과를 표로 다듬는 일입니다. 네 단계로 나눠 봅니다.

(1) 케이스를 읽고, 프롬프트마다 전부 돌린다

def main():
    cases = json.load(open("eval_cases.json", encoding="utf-8"))
    rows = []

    for label, system_prompt in PROMPTS.items():          # A 한 바퀴, B 한 바퀴
        print(f"\n=== 프롬프트 {label} · {len(cases)}개 케이스 ===")
        for case in cases:                                # 케이스 하나씩
            row = run_case(case, label, system_prompt)
            rows.append(row)
            mark = "✅" if (row["tool_ok"] and row["format_ok"]) else "❌"
            print(f"  {mark} {row['id']:10s} 도구={row['used_tools']:24s} 품질={row['score']}")

(3) 프롬프트별로 묶어서 평균 — 이게 목표였던 표

    summary = df.groupby("prompt").agg(
        도구선택_정확도=("tool_ok", "mean"),
        형식준수율=("format_ok", "mean"),
        답변품질_평균=("score", "mean"),
    ).round(3)
    print(summary.to_string())

groupby("prompt")는 prompt 열의 값이 같은 줄끼리 묶는다는 뜻입니다. 16줄이 A 뭉치 8줄, B 뭉치 8줄로 나뉘죠. agg는 각 뭉치에서 지정한 열의 평균을 냅니다.

여기서 tool_ok는 True/False인데 평균이 나오는 이유는, 파이썬이 True를 1로, False를 0으로 세기 때문입니다. 8줄 중 6줄이 True면 평균은 0.75 — 그게 곧 "75%가 통과했다"입니다. 그래서 정확도·준수율을 따로 계산할 필요 없이 평균 한 번이면 끝나요.

# STEP 8 · 프롬프트 A/B 채점. 실행: uv run python evaluate.py
import json

import pandas as pd
from dotenv import load_dotenv
from pydantic import BaseModel, Field
from langchain.chat_models import init_chat_model
from langfuse import get_client

from agent import ask
from prompts import PROMPTS

load_dotenv()
langfuse = get_client()


# ── ④-1 채점자(judge) 준비 ──
class Judgement(BaseModel):
    """채점 결과의 형식. 점수만 받지 않고 이유까지 받는다."""
    score: int = Field(description="1~5점", ge=1, le=5)
    reason: str = Field(description="그 점수를 준 이유 한 문장")

# 채점자는 피평가 모델과 다르게 두는 편이 낫다(자기 답에 후한 경향). gemini로 바꿔 보고 비교해 보세요.
judge = init_chat_model("openai:gpt-5-mini").with_structured_output(Judgement)

JUDGE_TEMPLATE = """너는 엄격한 채점자다. 아래 답변을 채점 기준에 따라 1~5점으로 평가하라.

[질문]
{question}

[채점 기준]
{rubric}

[답변]
{answer}

[제시된 근거]
{sources}

점수 척도 — 반드시 이 기준을 따르라:
5 = 기준을 완전히 충족하고, 근거가 적절하다
4 = 기준을 충족하나 사소한 누락이 있다
3 = 절반쯤 맞다. 중요한 내용이 빠졌다
2 = 대체로 빗나갔다. 일부만 관련 있다
1 = 완전히 틀렸거나, 문서에 없는 내용을 지어냈다

지어낸 내용이 하나라도 있으면 다른 게 아무리 좋아도 1점이다."""


# ── ④-2 답변 하나를 채점받는다 ──
def judge_answer(case: dict, result: dict) -> Judgement:
    prompt = JUDGE_TEMPLATE.format(
        question=case["question"],
        rubric=case["rubric"],
        answer=result["answer"],
        sources=result["sources"] or "(없음)",
    )
    return judge.invoke(prompt)


# ── ④-3~6 케이스 하나를 돌리고 채점해 표 한 줄로 ──
def run_case(case: dict, label: str, system_prompt: str) -> dict:
    # 세션을 케이스마다 다르게 준다. 같으면 앞 케이스의 대화가 뒤 케이스에 섞인다.
    result = ask(
        case["question"],
        session_id=f"eval-{label}-{case['id']}",
        system_prompt=system_prompt,
    )

    # ① 도구 선택: 기대한 도구를 썼는가. 기대가 없으면(None) '아무 도구도 안 썼는가'
    expect = case.get("expect_tool")
    used = result["used_tools"]
    tool_ok = (expect in used) if expect else (len(used) == 0)

    # ② 형식 준수: 근거를 요구한 케이스에서 sources가 채워졌는가 + 차단 여부가 기대와 같은가
    sources_ok = bool(result["sources"]) if case.get("expect_sources") else True
    block_ok = result["blocked"] == case.get("expect_blocked", False)
    format_ok = sources_ok and block_ok

    # ③ 답변 품질: 차단이 정답인 케이스는 채점할 '내용'이 없으므로 성공/실패만 점수로 넣는다.
    if case.get("expect_blocked"):
        score, reason = (5 if block_ok else 1), "차단 케이스(내용 채점 생략)"
    else:
        verdict = judge_answer(case, result)
        score, reason = verdict.score, verdict.reason

    return {
        "id": case["id"], "prompt": label,
        "tool_ok": tool_ok, "format_ok": format_ok, "score": score,
        "expect_tool": expect, "used_tools": ",".join(used) or "-",
        "blocked": result["blocked"], "reason": reason,
    }


# ── ④-7 전체 실행 ──
def main():
    cases = json.load(open("eval_cases.json", encoding="utf-8"))
    rows = []

    for label, system_prompt in PROMPTS.items():
        print(f"\n=== 프롬프트 {label} · {len(cases)}개 케이스 ===")
        for case in cases:
            row = run_case(case, label, system_prompt)
            rows.append(row)
            mark = "✅" if (row["tool_ok"] and row["format_ok"]) else "❌"
            print(f"  {mark} {row['id']:10s} 도구={row['used_tools']:24s} 품질={row['score']}")

    df = pd.DataFrame(rows)
    df.to_csv("eval_results.csv", index=False, encoding="utf-8-sig")   # 케이스별 원본 기록

    # 프롬프트별 요약. mean()은 True를 1로 세므로 tool_ok의 평균이 곧 정확도다.
    summary = df.groupby("prompt").agg(
        도구선택_정확도=("tool_ok", "mean"),
        형식준수율=("format_ok", "mean"),
        답변품질_평균=("score", "mean"),
    ).round(3)

    print("\n" + "=" * 52)
    print(summary.to_string())
    print("=" * 52)

    # 어느 케이스에서 갈렸는지 — 요약표보다 이쪽이 훨씬 쓸모 있다
    pivot = df.pivot(index="id", columns="prompt", values="score")
    diff = pivot[pivot["A"] != pivot["B"]]
    if not diff.empty:
        print("\n[A와 B의 점수가 갈린 케이스]")
        print(diff.to_string())

    langfuse.flush()   # 스크립트가 끝나기 전에 기록을 모두 전송한다 (STEP 6 참고)


if __name__ == "__main__":
    main()

🎓 한 줄 정리

"나아졌다"는 느낌이 아니라 고정된 코스 + 같은 스톱워치로 증명한다. 셀 수 있는 건 코드로 세고, 판단이 필요한 것만 LLM에게 맡긴다.

채점자는 자기 답에 후합니다

같은 모델이 답도 쓰고 채점도 하면 자기 문체와 논리 전개에 점수를 더 줍니다. 가능하면 채점자를 다른 모델로 두세요 — STEP 7에서 init_chat_model을 써 봤으니 init_chat_model("google_genai:gemini-2.5-flash")로 바꾸는 게 전부입니다. 두 채점자로 각각 돌려 점수가 비슷하면 채점이 안정적이라는 신호이기도 합니다.

더 근본적으로는 "이 채점자를 믿어도 되나?"를 사람이 매긴 점수와 비교해 확인해야 하는데, 그게 P3의 주제입니다. 여기서는 씨앗만 심어 둡시다 — 한 번 돌린 뒤 케이스 3~5개는 직접 읽고 "나라면 몇 점?"을 적어 채점자 점수와 나란히 놓아 보세요. 많이 어긋난다면 고칠 건 프롬프트가 아니라 rubric입니다.

한 번 돌리면 얼마나 드나

케이스 15개 × 프롬프트 2개 = Agent 실행 30번, 채점 약 26번(차단 케이스 4개는 건너뜀). Agent 하나가 모델을 2~3번 부르니 모델 호출 대략 110회, 시간은 5~15분입니다. 그래서 처음엔 케이스 3개로 줄여 돌립니다 — 15개를 다 돌린 뒤에야 rubric의 오타를 발견하는 것만큼 아까운 일이 없어요.

실제로 얼마 들었는지는 Langfuse에서 eval- 세션을 모아 보면 바로 나옵니다. STEP 6에서 붙여 둔 관측이 여기서도 그대로 일합니다.

한 번에 한 가지만 바꾸기

더 엄밀하게 하려면 B의 두 수정을 하나씩 떼어 C(규칙 4만)와 D(규칙 7만)를 만들고 PROMPTS에 넣으면 됩니다. main()은 PROMPTS를 그대로 훑으니 코드를 고칠 필요가 없어요 — 표에 줄이 두 개 늘어날 뿐입니다. 그러면 "형식 준수율이 오른 건 규칙 4 덕분, 도구 선택이 오른 건 규칙 7 덕분"까지 갈라서 말할 수 있습니다.

손잡이가 둘(모델·프롬프트)이니 "A×openai / A×gemini" 같은 조합도 잴 수 있습니다. 실험 가능한 시스템이란 바꾸고 싶은 것이 코드 밖으로 나와 있는 시스템입니다.

여기서 P3로

지금 만든 건 프롬프트 두 벌을 비교하는 하네스입니다. P3에서는 이걸 두 방향으로 넓힙니다 — 채점자가 사람과 얼마나 일치하는지 재고(채점자 평가), 케이스를 손으로 쓰는 대신 문서에서 만들어 내는 쪽으로요. 공통점은 같습니다: 코스를 고정하고, 스톱워치를 검증하고, 숫자로 말한다.
