4-3. Store (Long-term Memory) — 스레드를 넘어 사람을 기억하기

실습 노트북: 3.ipynb  ·  대상 범위: 4강 Memory 세 번째 — 장기 메모리 Store와 LangGraph의 설계 철학  ·  난이도: 🟢 입문~중급

앞의 두 장에서 만든 기억은 전부 대화방 하나에 묶여 있었습니다. thread_id를 바꾸는 순간 에이전트는 완전한 초면이 됐죠. 이번 장에서는 그 벽을 넘습니다. 대화방이 바뀌어도, 며칠 뒤에 다시 와도 따라오는 기억 — 장기 메모리(Long-term Memory), 그리고 그것을 담는 그릇 Store입니다. LangChain에서 이미 배운 개념이라 문법은 거의 그대로예요. 다만 Store가 놓이는 자리가 딱 하나 다릅니다. 그리고 그 "자리 하나"가 LangGraph라는 프레임워크의 설계 철학 전체를 요약합니다.

이 장에서 배우는 것

전반부는 LangChain 복습입니다. namespace·key·put·get·search — 이미 아는 것들이라 빠르게 훑고 지나갑니다.

중반부가 실습입니다. 같은 에이전트를 두 가지 방식으로 만들어 봅니다. 먼저 "기억해"라는 단어가 들어오면 저장하는 키워드 트리거 방식, 그다음 LLM이 스스로 판단해서 저장 도구를 호출하는 도구화 방식이죠. 뒤쪽이 훨씬 실전에 가깝습니다.

후반부는 설계 철학입니다. "왜 LangGraph는 Store를 Runtime 안에 두지 않고 밖으로 꺼냈을까?" — 이 질문에 답하면 왜 LangGraph 코드가 LangChain보다 길어지는지도 함께 설명됩니다.

1. 복습 — LangChain에서는 장기 메모리를 이렇게 다뤘다

슬라이드를 다시 보면 Runtime 아래에 세 개가 매달려 있습니다. Context(사용자 ID나 DB 접속 URL처럼 실행 도중 변하지 않는 값), Store(사용자의 이름·선호처럼 계속 남겨둘 기억), Stream writer(실시간 로그 출력). 이번 장의 주인공은 그중 Store입니다.

🔍 비유 — 미용실 이야기를 이어서

1장에서 단기 메모리는 오늘 상담하며 적는 수첩, 장기 메모리는 카운터의 고객 카드라고 했습니다. 이번 장은 그 고객 카드 쪽 이야기예요.

그런데 고객 카드는 그냥 책상 위에 굴러다니지 않죠. 카운터 뒤 캐비닛에 들어 있고, 캐비닛은 고객별 서랍으로 나뉘어 있고, 서랍 안에는 카드가 여러 장 꽂혀 있습니다.

캐비닛 = Store, 서랍 = namespace, 카드 한 장 = key, 카드에 적힌 내용 = value. 이 네 단어면 이번 장의 절반은 끝납니다.

Store — 폴더와 파일 이름

비유가 아주 정직합니다. namespace는 폴더고 key는 그 폴더 안의 파일 이름입니다. 우리가 이번 실습에서 쓸 namespace는 ('jay', 'profile')인데, 이건 jay/profile/ 폴더라고 읽으면 됩니다. 그 안에 memory_001, a3f9-... 같은 파일들이 쌓이는 것이고요.

namespace는 왜 튜플인가

폴더 경로는 계층이기 때문입니다. ('jay', 'profile')은 "jay라는 사람의 → profile 카테고리"라는 두 단계 경로예요. ('jay', 'schedule'), ('jay', 'memo')처럼 카테고리를 늘려도 사용자별로 안 섞입니다.

그리고 튜플은 수정할 수 없는(immutable) 자료형이라 키로 쓰기에 안전합니다. 리스트로 넘기면 안 되고, 반드시 튜플이어야 한다고 기억해 두세요.

InMemoryStore는 이름 그대로 메모리(RAM) 위에 만드는 임시 저장소입니다. 프로세스가 죽으면 같이 사라져요. 실습용이라는 뜻이죠. 실제 서비스에서는 PostgreSQL이나 Redis 같은 진짜 DB로 교체합니다. 다행히 교체 지점은 이 두 줄뿐이라, 나머지 코드는 하나도 안 바뀝니다.

메서드 세 개 — put · get · search

쓰기는 put 하나고, 읽기는 두 가지가 있습니다. 파일 하나를 콕 집어 열 것인가, 폴더를 통째로 열 것인가의 차이예요.

메서드필요한 것돌아오는 것비유
put(ns, key, value) 폴더 + 파일명 + 내용 없음 (저장만) 파일 저장
get(ns, key) 폴더 + 파일명 Item 하나 → .value 파일 하나 열기
search(ns) 폴더만 Item 리스트 폴더 통째로 열기
왜 실전에서는 search를 쓰나

get을 쓰려면 파일 이름을 미리 알고 있어야 합니다. 그런데 기억은 언제 몇 개가 쌓일지 모르잖아요. 그래서 저장할 때는 uuid로 겹치지 않는 이름을 자동 생성해 두고, 읽을 때는 폴더를 통째로 훑는(search) 방식이 자연스럽습니다. 이번 실습도 정확히 그 조합입니다.

저장만으로는 아무 일도 안 일어난다 — 주입

기억을 저장하는 일과 그 기억을 쓰는 일은 별개입니다. 고객 카드를 캐비닛에 잘 넣어놨어도, 손님이 왔을 때 카드를 꺼내 읽지 않으면 없는 것과 같죠. LangChain에서는 그 "꺼내 읽기"를 미들웨어가 담당했습니다.

코드가 하는 일은 딱 네 단계입니다. ① runtime.context에서 누구의 기억인지 알아내고, ② runtime.store.search(...)로 그 사람의 기억을 전부 꺼내고, ③ for 문으로 돌면서 텍스트 한 덩어리로 합치고, ④ 그걸 시스템 프롬프트로 덮어쓴 뒤 handler에 넘깁니다.

이 네 단계는 LangGraph에서도 그대로입니다

정말입니다. 바뀌는 건 ①과 ②를 "어디서 꺼내오느냐"뿐이에요. ③, ④는 문장 하나 안 바뀝니다. 그러니 지금부터 볼 LangGraph 코드가 낯설게 느껴진다면, ①·② 두 줄만 비교해 보세요.

2. LangGraph의 Store — 물건은 같고, 자리가 다르다

LangChain에서 Store는 Runtime이라는 상자 안에 들어 있는 부품이었습니다. 그래서 꺼내려면 request.runtime.store처럼 상자를 열고 안으로 파고들어야 했죠.

LangGraph는 그 상자를 아예 안 씁니다. Store를 밖으로 꺼내 놓고, 필요한 노드에게 직접 건네줍니다. "왜 굳이?"라는 질문이 당연히 떠오를 텐데, 그 답은 5장 설계 철학에서 하겠습니다. 지금은 문법부터 봅시다.

① 그래프에 장착 — compile(store=...)

1장에서 체크포인터를 compile에 넘겼던 것 기억하시죠. Store도 정확히 같은 자리입니다. 인자 이름만 store로 하나 더 붙는 거예요. 그래프의 모양(노드·엣지)은 전혀 바뀌지 않습니다. 

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore

checkpointer = InMemorySaver()   # 단기 — 대화 스레드별 수첩
store = InMemoryStore()          # 장기 — 사용자별 고객 카드 캐비닛

app = workflow.compile(checkpointer=checkpointer, store=store)
🔍 비유 — 가게를 여는 준비

add_node·add_edge는 가게 동선을 짜는 일입니다 — 손님이 어디로 들어와서 어디를 거쳐 나가는지.

compile은 개업 직전에 비품을 들이는 일이고요. 상담 수첩(체크포인터)과 고객 카드 캐비닛(스토어)을 카운터에 놓는 겁니다. 비품을 놓는다고 동선이 바뀌지는 않죠. 그래서 app을 그려봐도 그림은 그대로입니다.

② 노드가 직접 받는다 — BaseStore

지금까지 우리가 만든 노드는 인자가 state 하나였습니다. 여기에 둘이 더 붙습니다.

1state

공책. 지금까지 오간 메시지가 담긴 그래프의 상태. 늘 첫 번째 자리.

2config

작업 지시서. thread_id·user_id가 들어 있다. LangChain의 Context 역할.

3store

캐비닛 열쇠. 장기 메모리 저장소 그 자체. 타입은 BaseStore.

이 셋은 우리가 넣어주는 게 아닙니다. LangGraph가 노드 함수의 파라미터를 보고 알아서 채워 넣습니다. store라는 이름의 파라미터가 있으면, compile(store=...)에 넘겼던 그 객체가 그대로 들어옵니다. 안 쓸 거면 그냥 안 적으면 됩니다.

BaseStore는 무엇인가 — "저장소 표준 규격"

store: BaseStore에서 BaseStore는 타입 힌트입니다. 없어도 코드는 돌아갑니다. 그런데 왜 적을까요?

콘센트 규격을 생각해 보세요. 220V 콘센트라는 규격이 있으니까 선풍기든 노트북 충전기든 플러그 모양만 맞으면 꽂힙니다. BaseStore는 "이 자리에 들어올 물건은 put·get·search를 갖고 있다"는 규격 선언이에요.

덕분에 실습에선 InMemoryStore, 실서비스에선 DB 기반 스토어를 꽂아도 노드 코드는 한 글자도 안 바뀝니다. 게다가 에디터가 store.까지 치면 메서드를 자동완성해 주죠.

③ 한눈에 비교 — 딱 두 줄만 다르다

하는 일LangChainLangGraph
저장소 장착 create_agent(..., store=store) workflow.compile(store=store)
주입 지점 미들웨어 (@wrap_model_call) 노드 함수 본문
사용자 식별 request.runtime.context.user_id config['configurable']['user_id']
저장소 접근 request.runtime.store.search(ns) store.search(ns)

메서드 이름 put · get · search — 완전히 동일

표를 세로로 훑어보면 LangGraph 쪽이 전부 짧습니다. request.runtime.이라는 껍데기가 통째로 사라졌기 때문이에요. 대신 함수 시그니처가 길어졌죠. 숨어 있던 정보를 문 앞으로 끄집어낸 것 — 이게 LangGraph의 방식입니다.

🔍 비유 — 만능 공구함 vs 작업 지시서

LangChain 방식은 작업자에게 만능 공구함(request) 하나를 통째로 쥐여주는 것입니다. 필요한 건 다 그 안에 있어요. 편하죠. 대신 "이 작업자가 창고를 건드리나?"를 알려면 작업 내용을 처음부터 끝까지 읽어봐야 합니다.

LangGraph 방식은 작업 지시서 첫 줄에 못을 박습니다 — "이 작업은 도면(state), 작업 지시(config), 자재 창고 열쇠(store)를 씁니다." 쓸 게 늘어나 번거롭지만, 노드가 서른 개로 불어나도 첫 줄만 훑으면 창고를 건드리는 노드를 골라낼 수 있습니다.

3. 구현 ① — "기억해"라고 말하면 저장하는 에이전트

이제 코드를 씁니다. 만들 것은 노드 하나짜리 아주 단순한 에이전트예요. 사용자 메시지에 "기억해"라는 단어가 들어 있으면 Store에 저장하고, 답변할 때는 매번 Store를 읽어서 참고합니다.

STEP 1. Model 정의

from langchain.chat_models import init_chat_model

model = init_chat_model("gpt-5-nano")

늘 하던 그대로입니다. 넘어갑시다.

STEP 2. State 정의

from langchain.messages import AnyMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

필드가 messages 하나뿐인 가장 단순한 상태입니다. 여기서 잠깐 짚고 갈 게 있어요 — 장기 메모리를 State에 넣지 않았다는 점입니다.

왜 기억을 State에 안 넣나

State는 "이번 대화방에서 벌어지는 일"을 담는 공책입니다. thread_id가 바뀌면 공책도 새것으로 바뀌죠.

그런데 장기 메모리는 방을 넘어 따라와야 합니다. 공책에 적으면 방을 바꾸는 순간 같이 사라져 버려요. 그래서 장기 메모리는 State 바깥, 즉 Store에 둡니다. State는 대화, Store는 사람 — 이렇게 나눠 기억하세요.

STEP 3. Node 정의 — 읽고, 쓰고, 주입한다

import uuid
from langgraph.store.base import BaseStore
from langchain.messages import SystemMessage

def memory_agent_node(state: ChatState, config, store: BaseStore):

    # 1. 설정에서 user_id 가져오기 (누구의 기억인가?)
    user_id = config['configurable']['user_id']

    # 2. 기억 공간(Namespace) 정의: (사용자ID, 카테고리)
    namespace = (user_id, 'profile')

    # [WRITE] 기억 저장 로직 (간단한 키워드 트리거)
    last_message = state["messages"][-1]
    if "기억해" in last_message.content:
        # store.put(namespace, key, value)
        # key는 고유해야 하므로 uuid 사용
        memory_id = str(uuid.uuid4())
        store.put(
            namespace,
            memory_id,
            {
                'content' : last_message.content
            }
        )

    # [READ] 기억 조회 로직
    memories = store.search(namespace)

    # 기억이 있으면 문자열로 병합
    if memories:
        memory_text = "\n".join([f"- {m.value['content']}" for m in memories])
        system_msg = f"""
        당신은 사용자의 정보를 기억하는 비서입니다.

        [장기 기억 저장소]
        {memory_text}

        위 기억을 참고하여 답변하세요.
        """
    else:
        system_msg = "당신은 도움이 되는 비서입니다. 아직 사용자에 대해 아는 것이 없습니다."

    # 3. LLM 호출 (시스템 메시지 + 대화 내역)
    # SystemMessage를 맨 앞에 끼워넣어서 Context 주입
    prompt = [SystemMessage(content=system_msg)] + state["messages"]

    return {"messages": [model.invoke(prompt)]}

길어 보이지만 하는 일은 네 덩어리입니다. 하나씩 뜯어봅시다.

① 누구?

config['configurable']['user_id']로 사용자를 특정합니다. LangChain에서 request.runtime.context.user_id였던 자리예요. 이 값이 없으면 어느 서랍을 열지 알 수 없습니다.

② 어느 서랍?

(user_id, 'profile') 튜플로 네임스페이스를 만듭니다. 'profile'은 우리가 정한 카테고리 이름이라 마음대로 바꿔도 됩니다. 다만 쓸 때와 읽을 때가 같아야 합니다.

③ 쓰기 [WRITE]

마지막 메시지에 "기억해"가 들어 있으면 put. 파일 이름은 uuid4()로 매번 새로 뽑아 겹치지 않게 합니다. 조건이 안 맞으면 그냥 건너뜁니다.

④ 읽기 + 주입

search로 서랍을 통째로 꺼내고, for 문으로 돌며 목록 형태의 문자열로 합칩니다. 그걸 SystemMessage에 담아 대화 맨 앞에 끼워 넣고 LLM을 호출합니다.

③과 ④의 순서가 중요합니다. 먼저 저장하고, 그다음 읽습니다. 덕분에 "이거 기억해"라고 말한 바로 그 턴에도 방금 저장한 내용이 답변에 반영됩니다. 순서를 뒤집으면 한 턴씩 늦게 반영돼요.

⚠️ 가장 많이 틀리는 곳 — 쓸 때의 키와 읽을 때의 키

코드에서 같은 단어가 두 번 등장합니다. 눈에 잘 안 띄지만 여기가 제일 잘 깨지는 지점이에요.

store.put(namespace, memory_id, {'content': last_message.content})
#                                 ~~~~~~~~~

# 읽을 때 — 그래서 꺼낼 때도 'content'로 꺼내야 한다
memory_text = "\n".join([f"- {m.value['content']}" for m in memories])

키가 안 맞으면 KeyError

put에서는 {'content': ...}로 넣어놓고 읽을 때 m.value['data']로 꺼내면 그런 키 없다며 터집니다.

더 고약한 건, 저장이 한 건도 없을 때는 for 문이 안 돌아서 에러도 안 난다는 점이에요. 기억이 하나 쌓인 다음 두 번째 실행에서야 터집니다. 잠시 후 4장 도구화 버전에서는 이 키가 'data'로 바뀝니다. 그때 다시 짚겠습니다.

🔍 비유 — 라벨을 붙였으면 그 라벨로 찾아라

고객 카드에 "메모"라고 항목 이름을 써서 넣어놓고, 나중에 "비고" 칸을 찾으면 당연히 못 찾습니다. value의 키는 내가 정하는 라벨 이름이고, 정한 사람이 지켜야 하는 약속입니다.

4. 구현 ② — 기억을 도구로 만들어 자동화하기

앞의 방식에는 명백한 구멍이 있습니다. "기억해"라는 단어에만 반응한다는 것이죠.

  • "내 이름은 Jay야" → 저장 안 됨. 중요한 정보인데도 키워드가 없으니까.
  • "이 노래 좀 기억해뒀다가 나중에 틀어줘" → 저장됨. 프로필과 상관없는데도 키워드가 있으니까.
  • 사용자가 "기억해줘"라고 쓰면 "기억해"가 포함돼 통과하지만, "외워둬"는 그냥 지나갑니다.

if 문으로 단어를 늘려가는 건 답이 아닙니다. 우리에겐 문맥을 판단할 줄 아는 LLM이 있으니까요. "저장할지 말지"라는 판단 자체를 LLM에게 넘기는 것 — 그게 도구화입니다.

🔍 비유 — 단어에 반응시키기 vs 알아서 적게 하기

키워드 방식은 신입에게 "손님이 '기억해'라고 말하면 카드에 적어"라고 시키는 것입니다. 정확히 그 단어가 나올 때만 적겠죠.

도구화는 "손님 정보 중 남겨둘 만한 게 나오면 카드에 적어. 인사말은 적지 말고"라고 기준만 알려주고 판단을 맡기는 것입니다. 손님이 '기억해'라고 말하지 않아도 이름과 사는 곳은 알아서 적히게 됩니다.

STEP 1. 기억 버튼 만들기 — @tool

from langchain.tools import tool

# 1. 도구(Tool) 정의: AI에게 쥐어줄 '기억 버튼'
@tool
def save_profile(info: str):
    """
    사용자에 대한 중요한 정보(이름, 취미, 특징 등)를 저장할 때 사용합니다.
    단순한 대화나 인사는 저장하지 마세요.
    """
    print(f'저장한 정보 : {info}')
    # 이 함수는 실제로는 실행되지 않고, 스키마(껍데기)만 LLM에게 전달
    # 실제 저장 로직은 아래 'save_node'에서 store 객체를 이용해 수행
    return "saved"

tools = [save_profile]
model_with_tools = model.bind_tools(tools)
docstring이 곧 판단 기준입니다

이 도구에서 가장 중요한 코드는 함수 본문이 아니라 docstring입니다. LLM은 저 설명문만 읽고 "지금 이걸 눌러야 하나?"를 결정하니까요.

"단순한 대화나 인사는 저장하지 마세요"라는 한 줄이 "안녕하세요"까지 죄다 저장되는 사태를 막는 안전장치입니다. 도구 설명을 쓰는 일은 프롬프트를 쓰는 일이라고 생각하세요.

이 함수의 본문은 실제로 실행되지 않습니다

주석에 적혀 있는 그대로예요. print도 return "saved"도 실행되지 않습니다. 진짜 저장은 잠시 후 만들 save_node가 합니다.

왜 이렇게 갈랐을까요? @tool 함수는 노드가 아니기 때문입니다. LangGraph가 store를 꽂아주는 건 그래프에 등록된 노드뿐이라, 도구 함수 안에서는 캐비닛에 손이 닿지 않아요.

그래서 역할을 나눕니다 — 도구는 "무엇을 저장할지" LLM에게서 받아내는 양식(스키마), 노드는 그 양식을 들고 실제로 캐비닛을 여는 손.

STEP 2. agent_node — 읽기 + 판단

from langgraph.store.base import BaseStore

# [Node 1] 에이전트: 대화 및 판단
def agent_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")

    # 1. 저장된 기억을 조회해서 컨텍스트로 주입
    memories = store.search(namespace)
    if memories:
        info = "\n".join([f"- {m.value['data']}" for m in memories])
        system_msg = f"당신은 사용자의 기억을 담당하는 비서입니다.\n[기억된 정보]\n{info}"
    else:
        system_msg = "당신은 사용자의 기억을 담당하는 비서입니다."

    # 2. LLM 호출
    return {"messages": [model_with_tools.invoke([SystemMessage(content=system_msg)] + state["messages"])]}

앞의 memory_agent_node와 비교하면 달라진 곳이 딱 둘입니다.

  • if "기억해" in ... 블록이 통째로 사라졌습니다. 쓰기는 더 이상 이 노드의 일이 아니에요. 이 노드는 읽고 판단만 합니다.
  • model 대신 model_with_tools를 호출합니다. 그래서 LLM은 답변을 만들 수도 있고, 도구를 부를 수도 있습니다.
🔑 키가 'content'에서 'data'로 바뀌었습니다

자세히 보세요. m.value['data']입니다. 앞 절에서는 m.value['content']였죠.

왜냐하면 이번엔 save_node가 {"data": info_to_save} 형태로 저장하기 때문입니다. 키 이름 자체에는 정답이 없습니다. put하는 쪽과 읽는 쪽이 짝만 맞으면 됩니다.

실수를 피하는 요령 — 프로젝트 안에서 키 이름을 하나로 통일하거나, 아예 상수로 뽑아 쓰세요. 두 방식을 한 노트북에서 섞으면 정확히 이런 혼동이 생깁니다.

STEP 3. save_node — 실제로 캐비닛을 여는 손

from langchain.messages import ToolMessage

# [Node 2] 저장 실행기: 실제 Store에 저장 (Action)
def save_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")

    # 에이전트가 보낸 '도구 호출' 메시지 가져오기
    last_message = state["messages"][-1]

    tool_outputs = []
    for tool_call in last_message.tool_calls:
        if tool_call["name"] == "save_profile":
            # AI가 저장하라고 한 정보
            info_to_save = tool_call["args"]["info"]

            print(f"\n💾 [System] AI의 요청으로 정보를 저장합니다: '{info_to_save}'")

            # [Store Write] 실제 저장 수행
            memory_id = str(uuid.uuid4())
            store.put(namespace, memory_id, {"data": info_to_save})

            # 도구 실행 결과 메시지 생성
            tool_outputs.append(
                ToolMessage(
                    content=f"정보 저장 완료: {info_to_save}",
                    tool_call_id=tool_call["id"]
                )
            )

    return {"messages": tool_outputs}

이 노드는 3강에서 쓰던 툴 노드를 직접 손으로 만든 버전입니다. 준비된 ToolNode를 쓰지 않고 직접 만든 이유가 바로 store를 파라미터로 받기 위해서예요.

tool_calls 읽기

직전 AIMessage의 tool_calls를 꺼냅니다. 여기에 LLM이 "이 정보를 저장해줘"라며 채워 넣은 인자가 들어 있습니다.

이름 확인

tool_call["name"] == "save_profile"인지 확인합니다. 도구가 여러 개로 늘어나도 안전하게 만드는 습관입니다.

store.put

여기가 진짜 저장입니다. uuid로 파일 이름을 뽑고 {"data": ...} 형태로 넣습니다.

ToolMessage 반환

반드시 tool_call_id를 짝지어 돌려줘야 합니다. "몇 번 요청에 대한 응답인지"를 알리는 접수번호예요. 이게 없으면 LLM이 대화 기록을 이해하지 못하고 에러가 납니다.

    │
    └── tool_calls 없음 ──→ __end__

save_node에서 agent로 돌아오는 화살표가 핵심입니다. 저장만 하고 끝내면 사용자는 아무 답변도 못 받으니까요. 저장을 마친 뒤 다시 에이전트에게 돌아가 "다 됐습니다"라고 보고하고, 에이전트가 그제야 사람에게 할 말을 만듭니다.

돌아온 agent는 방금 저장한 기억까지 읽습니다

두 번째로 실행되는 agent_node는 store.search를 다시 호출합니다. 그런데 그사이 save_node가 새 카드를 한 장 넣어놨죠.

그래서 돌아온 에이전트의 시스템 프롬프트에는 방금 저장한 정보가 이미 들어 있습니다. 같은 턴 안에서 쓰고 → 읽고 → 답하는 한 바퀴가 완성되는 겁니다.

checkpointer = InMemorySaver()
store = InMemoryStore()
app = workflow.compile(checkpointer=checkpointer, store=store)

컴파일은 아까와 완전히 동일합니다. 노드가 늘어도 설비는 그대로예요.

입력에는 "기억해"가 한 글자도 없습니다. 그냥 평범한 자기소개죠. 그런데 저장됐습니다. 게다가 문장을 통째로 넣은 게 아니라 "이름: Jay, 거주지: 샌프란시스코"로 정리해서 넣었어요. LLM이 "무엇이 프로필인지" 추려낸 결과입니다.

두 방식, 어느 쪽을 쓸까

키워드 트리거는 토큰을 안 쓰고 100% 예측 가능합니다. "저장" 버튼이 UI에 따로 있는 서비스라면 이쪽이 오히려 낫습니다.

도구화는 자연스럽지만 LLM의 판단에 의존합니다. 토큰을 더 쓰고, 가끔 엉뚱한 걸 저장하거나 저장해야 할 걸 놓칩니다. 그래서 docstring을 다듬는 일이 곧 품질 관리가 되죠.

실전에서는 섞어 씁니다 — 명시적 요청은 키워드로 확실하게 잡고, 나머지는 LLM에게 맡기는 식으로요.

5. LangGraph 설계 철학 — 왜 Store를 밖으로 꺼냈나

코드만 놓고 보면 LangChain 쪽이 편해 보입니다. request 하나만 받으면 Context든 Store든 다 꺼낼 수 있으니까요. 함수 시그니처도 짧고요. 그런데 LangGraph는 일부러 그 편의를 버렸습니다.

명시적인 것이 암시적인 것보다 낫다

이 빨간 상자의 위치 차이가 전부입니다.

LangChainLangGraph
함수 첫 줄 def inject_memory(request, handler) def save_node(state, config, store: BaseStore)
첫 줄만 보면 이 함수가 뭘 건드리는지 알 수 없다 Store를 건드린다는 게 바로 보인다
확인하려면 본문을 끝까지 읽어야 한다 안 읽어도 된다
노드 30개면 30개를 다 열어봐야 한다 시그니처만 훑으면 된다
🔍 비유 — 자재 반출 신청서

공사 현장에 작업자가 서른 명이라고 해봅시다. 어느 날 자재 창고에서 물건이 잘못 나갔습니다. 누굴 찾아가야 할까요?

모두에게 마스터키(request)를 나눠준 현장이라면 서른 명의 작업 일지를 전부 뒤져야 합니다. 누가 창고를 열었는지 알 방법이 없으니까요.

창고 열쇠를 신청서에 적고 받아 가는 현장이라면 신청서 목록만 보면 끝입니다. 세 명으로 좁혀지죠.

노드 시그니처가 바로 그 신청서입니다. store라고 적혀 있으면 창고를 건드리는 노드, 없으면 안 건드리는 노드 — 읽지 않고도 알 수 있는 정보가 되는 겁니다.

테스트하기도 훨씬 쉬워집니다

덤으로 따라오는 이점이 있습니다. save_node를 테스트하려면 가짜 state·config·store 세 개만 만들어 넣으면 됩니다.

반면 request를 받는 함수를 테스트하려면 request.runtime.store까지 갖춘 가짜 request 객체를 통째로 만들어야 하죠. 필요한 것만 받는 함수가 테스트하기 쉽다는 건 일반적인 원칙이기도 합니다.

로우 레벨 프레임워크의 대가

1강에서 LangGraph는 로우 레벨 오케스트레이션 프레임워크라고 했습니다. 그 말의 의미가 이제 구체적으로 와닿을 겁니다.

1결정권이 개발자에게

어떤 노드가 언제 실행될지, 어디로 갈지 전부 직접 정한다

2자동화 영역이 없다

알아서 되는 게 없으니 하나하나 다 적어야 한다

3코드가 길어진다

명시성이 올라가면 복잡성도 같이 올라간다

4그래서 더 명시한다

복잡해질수록 꼬이지 않게 못 박아두는 게 이득이다

③에서 ④로 넘어가는 게 핵심입니다. 보통 "코드가 길어진다"는 건 단점으로 여겨지죠. 그런데 LangGraph는 어차피 길어질 코드라면, 길어지는 방향을 "읽기 쉬운 쪽"으로 잡자고 결정한 겁니다.

🔍 비유 — 자동 변속기와 수동 변속기

LangChain은 자동 변속기입니다. create_agent 한 줄이면 루프도 분기도 알아서 돌아갑니다. 빠르고 편합니다.

LangGraph는 수동 변속기예요. 기어를 직접 넣어야 합니다. 번거롭지만 지금 몇 단인지 늘 알고 있죠.

그런데 수동 변속기 차에서는 계기판이 더 중요해집니다. 직접 조작할 게 많을수록 지금 상태가 한눈에 보여야 하니까요. 노드 시그니처에 state·config·store를 다 적는 것은 그 계기판을 다는 일입니다.

정리하면 이렇습니다. LangGraph가 Store를 Runtime에서 꺼낸 것은 취향이 아니라 필연이었습니다. 모든 것을 직접 조립하는 프레임워크에서는 "이 부품이 무엇과 연결되는지"가 겉으로 드러나야 부품이 백 개로 늘어나도 조립도가 무너지지 않기 때문입니다.

자주 걸리는 함정

1. put의 키와 읽을 때의 키가 다르다
store.put(ns, mid, {'content': text})       # 넣을 때는 content
info = m.value['data']                      # 꺼낼 때는 data  ← KeyError!

이번 노트북에서 실제로 두 방식이 다른 키를 씁니다 (키워드 버전은 'content', 도구 버전은 'data'). 섞어 쓰면 반드시 터집니다. 게다가 저장된 기억이 0건이면 에러가 안 나서, 두 번째 실행에서야 발견되는 게 더 고약하죠.

2. config에 user_id를 안 넣었다
KeyError: 'user_id'

{'configurable': {'thread_id': '1'}}만 넘기면 노드 첫 줄에서 바로 터집니다. thread_id는 LangGraph가 챙겨주지만 user_id는 우리 책임이에요. 노드 안의 철자와 config의 철자가 정확히 같은지 확인하세요.

3. namespace를 리스트로 넘겼다
namespace = [user_id, 'profile']    # ✗ 리스트
namespace = (user_id, 'profile')    # ✓ 튜플

괄호 하나 차이입니다. namespace는 튜플이어야 합니다.

4. compile에 store를 안 넘겼다

노드에 store: BaseStore라고 적어놨어도, compile(store=...)을 빠뜨리면 들어오는 건 None입니다. 그러면 store.search(...)에서 AttributeError가 납니다. compile 줄부터 확인하세요.

5. thread_id를 그대로 두고 테스트했다

가장 흔한 "잘못된 성공"입니다. 잘 대답하니까 넘어가지만, 사실은 장기 메모리를 전혀 안 쓰고 있어도 같은 결과가 나옵니다. 검증하려면 thread_id를 반드시 바꾸세요.

6. InMemoryStore는 휘발성이다

커널을 재시작하면 기억은 전부 사라집니다. "어제 저장했는데 왜 없지?"의 답은 대개 이것입니다. 영구 보관이 필요하면 DB 기반 스토어로 교체하세요 — 바꿀 곳은 store = ... 한 줄입니다.

7. 같은 내용이 계속 쌓인다

uuid로 매번 새 파일 이름을 만들기 때문에, "매운 거 싫어해"를 세 번 말하면 카드가 세 장 생깁니다. 중복 제거나 갱신 로직은 우리가 직접 만들어야 합니다 (예: 고정 key로 덮어쓰기, 또는 저장 전 search로 비슷한 기억 확인).

8. @tool 함수 안에서 store를 쓰려 했다

도구 함수는 노드가 아니라서 store가 주입되지 않습니다. 그래서 이번 실습은 도구는 "양식"만 담당하고, 실제 쓰기는 save_node가 맡도록 갈랐습니다. 도구 본문에 넣은 print가 안 찍힌다면 정상입니다 — 애초에 실행되지 않으니까요.

① 키워드 트리거 방식

# ══ 준비 ══════════════════════════════════════════════
import uuid
from langchain.chat_models import init_chat_model
from langchain.messages import AnyMessage, HumanMessage, SystemMessage
from typing_extensions import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.store.memory import InMemoryStore
from langgraph.store.base import BaseStore

model = init_chat_model("gpt-5-nano")

# ══ STEP 2. State ═════════════════════════════════════
class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

# ══ STEP 3. Node ══════════════════════════════════════
def memory_agent_node(state: ChatState, config, store: BaseStore):
    user_id = config['configurable']['user_id']       # ★ 누구의 기억인가
    namespace = (user_id, 'profile')                  # ★ 튜플! 폴더 경로

    # [WRITE] "기억해"가 있으면 저장
    last_message = state["messages"][-1]
    if "기억해" in last_message.content:
        memory_id = str(uuid.uuid4())                 # ★ 파일 이름은 고유하게
        store.put(namespace, memory_id, {'content': last_message.content})

    # [READ] 폴더 통째로 조회
    memories = store.search(namespace)
    if memories:
        memory_text = "\n".join([f"- {m.value['content']}" for m in memories])
        system_msg = f"""
        당신은 사용자의 정보를 기억하는 비서입니다.

        [장기 기억 저장소]
        {memory_text}

        위 기억을 참고하여 답변하세요.
        """
    else:
        system_msg = "당신은 도움이 되는 비서입니다. 아직 사용자에 대해 아는 것이 없습니다."

    # [주입] 시스템 메시지를 맨 앞에 끼워넣기
    prompt = [SystemMessage(content=system_msg)] + state["messages"]
    return {"messages": [model.invoke(prompt)]}

# ══ STEP 4. 그래프 + 두 메모리 ════════════════════════
workflow = StateGraph(ChatState)
workflow.add_node("agent", memory_agent_node)
workflow.add_edge(START, "agent")
workflow.add_edge("agent", END)

checkpointer = InMemorySaver()                        # 단기
store = InMemoryStore()                               # 장기
app = workflow.compile(checkpointer=checkpointer, store=store)

# ══ STEP 5. 실행 ══════════════════════════════════════
config_1 = {'configurable': {'thread_id': 'store_demo', 'user_id': 'jay'}}
input1 = {"messages": [HumanMessage(content="내 이름은 Jay이고, 나는 매운 음식을 싫어해. 이거 꼭 기억해.")]}
resp1 = app.invoke(input1, config_1)
print(resp1['messages'][-1].content)

# ★ 방을 바꿔도(thread_id) 사람이 같으면(user_id) 기억은 따라온다
config_2 = {"configurable": {"thread_id": "thread-2", "user_id": "jay"}}
input2 = {"messages": [HumanMessage(content="점심 메뉴 추천해줘.")]}
resp2 = app.invoke(input2, config=config_2)
print(resp2['messages'][-1].content)

② 도구화 방식

from langchain.tools import tool
from langchain.messages import ToolMessage

# ══ 1. 기억 버튼(Tool) ════════════════════════════════
@tool
def save_profile(info: str):
    """
    사용자에 대한 중요한 정보(이름, 취미, 특징 등)를 저장할 때 사용합니다.
    단순한 대화나 인사는 저장하지 마세요.
    """
    print(f'저장한 정보 : {info}')   # ★ 실제로는 실행되지 않는다 (스키마 역할)
    return "saved"

tools = [save_profile]
model_with_tools = model.bind_tools(tools)

# ══ 2. agent_node — 읽고 판단 ═════════════════════════
def agent_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")

    memories = store.search(namespace)
    if memories:
        info = "\n".join([f"- {m.value['data']}" for m in memories])   # ★ 키가 'data'
        system_msg = f"당신은 사용자의 기억을 담당하는 비서입니다.\n[기억된 정보]\n{info}"
    else:
        system_msg = "당신은 사용자의 기억을 담당하는 비서입니다."

    return {"messages": [model_with_tools.invoke([SystemMessage(content=system_msg)] + state["messages"])]}

# ══ 3. save_node — 실제 저장 ══════════════════════════
def save_node(state: ChatState, config, store: BaseStore):
    user_id = config["configurable"]["user_id"]
    namespace = (user_id, "profile")
    last_message = state["messages"][-1]

    tool_outputs = []
    for tool_call in last_message.tool_calls:
        if tool_call["name"] == "save_profile":
            info_to_save = tool_call["args"]["info"]
            print(f"\n💾 [System] AI의 요청으로 정보를 저장합니다: '{info_to_save}'")

            memory_id = str(uuid.uuid4())
            store.put(namespace, memory_id, {"data": info_to_save})    # ★ 키가 'data'

            tool_outputs.append(
                ToolMessage(content=f"정보 저장 완료: {info_to_save}",
                            tool_call_id=tool_call["id"])              # ★ 접수번호 필수
            )
    return {"messages": tool_outputs}

# ══ 4. 그래프 — 분기와 복귀 엣지 ══════════════════════
def should_continue(state: ChatState):
    last_message = state['messages'][-1]
    if last_message.tool_calls:
        return 'save_node'
    else:
        return END

workflow = StateGraph(ChatState)
workflow.add_node("agent", agent_node)
workflow.add_node("save_node", save_node)
workflow.add_edge(START, "agent")
workflow.add_conditional_edges('agent', should_continue, ['save_node', END])
workflow.add_edge("save_node", "agent")          # ★ 저장 후 다시 보고

checkpointer = InMemorySaver()
store = InMemoryStore()
app = workflow.compile(checkpointer=checkpointer, store=store)

# ══ 5. 실행 — "기억해"가 없어도 저장된다 ══════════════
config = {"configurable": {"thread_id": "1", "user_id": "jay"}}
input1 = {"messages": [HumanMessage(content="안녕, 나는 샌프란시스코에 사는 Jay라고 해.")]}
resp1 = app.invoke(input1, config=config)
print(resp1["messages"][-1].content)

input2 = {"messages": [HumanMessage(content="내 이름이 뭐고 어디 산다고 했지?")]}

print(resp2["messages"][-1].content)

📚 한 장 정리

오늘의 핵심 한 문장

장기 메모리는 compile할 때 붙이고(store), invoke할 때 사람을 지목하며(user_id), 노드가 파라미터로 직접 받아서 put·search로 다룬다.

  • State는 대화, Store는 사람 — thread_id가 바뀌면 State는 새것이 되지만, user_id가 같으면 Store는 그대로다. 그래서 장기 기억은 State가 아니라 Store에 둔다.
  • Store의 구조는 파일 탐색기다 — namespace(폴더, 반드시 튜플) + key(파일 이름) + value(내용 딕셔너리). ('jay', 'profile')은 jay/profile/ 폴더다.
  • 메서드는 셋뿐 — put(ns, key, value)는 저장, get(ns, key)는 파일 하나, search(ns)는 폴더 통째로. 실전에서는 uuid로 저장 + search로 조회 조합을 쓴다.
  • LangChain과 딱 두 군데 다르다 — ① request.runtime.store → 노드 파라미터 store, ② request.runtime.context.user_id → config['configurable']['user_id']. 메서드 이름도, 주입 로직도 완전히 같다.
  • 노드는 최대 세 개를 받는다 — state(공책) · config(작업 지시서) · store(캐비닛 열쇠). 이름만 맞춰 적으면 LangGraph가 알아서 채워 넣는다. BaseStore는 "저장소 표준 규격" 타입 힌트다.
  • 쓸 때의 키와 읽을 때의 키는 반드시 같아야 한다 — put에서 'content'로 넣었으면 m.value['content']로 꺼낸다. 기억이 0건일 땐 에러가 안 나서 늦게 발견된다.
  • 저장 방식은 두 가지
    • 키워드 트리거 — if "기억해" in .... 공짜·예측 가능하지만 말투가 조금만 달라도 놓친다.
    • 도구화 — @tool save_profile + bind_tools. LLM이 문맥으로 판단하고 정보를 정리해서 저장한다. docstring이 곧 판단 기준이다.
  • 도구화 그래프의 모양 — START → agent → (조건부) save_node 또는 END, 그리고 save_node → agent 복귀 엣지. 돌아온 agent가 새로 저장된 기억까지 읽어서 답을 만든다.
  • 도구 함수 안에서는 store를 못 쓴다 — 노드가 아니기 때문. 그래서 도구는 양식(스키마), 노드는 실행으로 역할을 나눈다.
  • 검증은 thread_id를 바꿔서 — 같은 방에서 물어보면 단기 메모리만으로도 맞힐 수 있어 아무것도 증명되지 않는다. 방은 바꾸고 사람은 유지하는 것이 올바른 실험이다.
  • 설계 철학 — 명시적인 것이 암시적인 것보다 낫다 — 빨간 상자가 "본문"에서 "첫 줄"로 옮겨간 것이 전부다. 노드가 무엇을 건드리는지 시그니처만 보고 알 수 있으면, 노드가 서른 개로 늘어도 유지보수가 무너지지 않는다.
  • 로우 레벨의 대가 — 개발자가 모든 노드와 경로를 직접 정하는 만큼 코드가 길어진다. LangGraph는 어차피 길어질 코드라면 읽기 쉬운 쪽으로 길어지게 설계했다.
🔍 마지막으로 — 이 장을 한 장면으로 기억한다면

카운터 뒤의 고객 카드 캐비닛을 떠올리세요. 캐비닛을 들여놓는 일은 개업 준비(compile)고, 서랍은 손님별로 나뉘어(namespace) 있습니다.

그리고 이 가게에는 규칙이 하나 있어요 — 캐비닛을 열 사람은 문 앞에서 열쇠를 받아 간다는 것. 주머니에 마스터키를 넣고 다니지 않습니다.

번거롭죠. 하지만 직원이 서른 명으로 늘어난 날, "누가 캐비닛을 열었나"를 열쇠 대장 한 장으로 알 수 있게 됩니다. 그게 def node(state, config, store)라는 한 줄이 사는 이유입니다.
