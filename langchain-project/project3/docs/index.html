Project 3 · LLM/Agent 평가·관측성 하네스

🔴 심화 · 인프라 관점  ·  ⏱ 2주  ·  스택: pydantic · pandas RAGAS LLM-as-judge Langfuse datasets · scores pytest

P1과 P2에서 평가는 마지막 한 단계였습니다. P3에서는 평가가 주인공입니다. P1(RAG)과 P2(Agent)를 시험 대상으로 놓고, 골든셋을 시험지로 고정하고(STEP 1), 명령 한 번으로 지표를 뽑고(STEP 3~5), 지난 실행과 비교해 나빠졌으면 알려 주는(STEP 6) 파이프라인을 만듭니다. 결과는 Langfuse에 쌓이고(STEP 7), 리포트와 자동 게이트로 마감합니다(STEP 8). 새 모델을 만드는 프로젝트가 아니라 "품질을 숫자로 관리하는 능력"을 증명하는 프로젝트입니다.

📖 이 문서 사용법 각 STEP은 🎯 목표 → 🧠 개념(왜) → 🛠 할 일(코드) → ✅ 검증 게이트 → 🎓 한 줄 정리 순서입니다. 검증 게이트를 통과하지 못하면 다음 STEP으로 넘어가지 마세요. P3는 앞 STEP의 파일을 뒤 STEP이 그대로 이어받아 키우는 구조라, 한 STEP이 비면 그 뒤가 전부 흔들립니다.
🧪 P1·P2와 무엇이 다른가 — "만드는 사람"에서 "시험 감독관"으로

일반 코드에는 테스트가 있습니다. 같은 입력에는 같은 출력이 나오니 통과 아니면 실패, 둘 중 하나죠. LLM 앱은 다릅니다. 같은 질문에도 답이 조금씩 달라지고, 정답도 한 문장으로 정해져 있지 않습니다. 그래서 점수는 0/1이 아니라 비율과 평균이고, 판정은 "틀렸다"가 아니라 "지난번보다 임계값 넘게 떨어졌다"입니다.

이 차이 때문에 P3에는 일반 테스트에 없는 부품 셋이 들어갑니다. 고정된 시험지(골든셋 + 버전), 채점자(코드 · RAGAS · LLM), 그리고 "그 채점자를 믿어도 되나"를 사람 점수로 확인하는 절차입니다. 한 번 만들어 두면 이후 LangGraph로 만드는 모든 것의 품질 게이트로 그대로 씁니다.

⚠️ 버전 기준 (한 번만 읽어두기) RAGAS는 0.4.x, Langfuse는 4.x(datasets · scores API) 기준입니다. RAGAS 0.4.x는 langchain-community 0.4.1과 맞물리므로 STEP 0에서 그 버전으로 고정합니다. 두 패키지 모두 마이너 버전에서 함수 이름이 바뀝니다 — ImportError가 나면 에러 메시지의 모듈명을 공식 문서에서 검색하세요.

✅ 완성 정의 (Definition of Done)

아래가 모두 충족되면 이 프로젝트는 "완성"입니다. STEP들이 이 목록을 하나씩 채워 나갑니다.

  • 골든셋 두 벌(RAG용 · Agent용, 각 15~20 케이스)이 스키마 검증을 통과하고 버전 태그가 있다 STEP 1
  • 명령 한 번으로 P1·P2를 돌려 케이스별 점수표(results.csv)와 요약(summary.json)이 폴더 하나에 남는다 STEP 2~3
  • RAG는 RAGAS 4종, Agent는 도구 선택 · 형식 · 차단 지표가 숫자로 나온다 STEP 3~4
  • LLM 채점 점수가 있고, 사람 라벨 10개와의 일치율이 숫자로 있다 STEP 5
  • 두 실행을 비교해 회귀 / 개선 / 유지를 판정하고, 일부러 나쁜 설정을 넣으면 회귀로 잡힌다 STEP 6
  • Langfuse에 케이스 = item, 실행 = run, 지표 = score로 쌓여 실행별 추이가 보인다 STEP 7
  • 실행마다 리포트 파일이 생기고, pytest 한 줄로 baseline 대비 회귀 여부가 판정된다 STEP 8
  • README에 문제정의 · 아키텍처 · 지표 · 배운 점이 정리돼 있다 STEP 9

🔗 P1·P2와의 관계 — 시험 감독관은 수험생의 코드를 읽지 않는다

P3는 P1의 rag.py도 P2의 agent.py도 import하지 않습니다. 아는 것은 주소 둘과 JSON 모양 둘뿐이고, 그래서 P3 환경에는 Chroma도 리랭커도 LangGraph도 깔리지 않습니다.

시험 대상P3가 보내는 것P3가 받는 것
P1 · 8000POST /query  { question, mode, include_contexts }{ answer, citations, contexts }
P2 · 8001POST /chat  { message, session_id }{ answer, sources, used_tools, blocked }

P3가 P1에 요구하는 변경은 딱 하나, include_contexts 옵션입니다(STEP 2). RAGAS가 검색된 원문을 읽어야 "답이 문맥에 근거했나"를 잴 수 있어서예요. 기본값은 false라 P2가 부를 때의 응답은 지금과 똑같습니다.

💡 이력서에 남는 문장 "평가 하네스를 시험 대상과 분리해, HTTP 창구만 있으면 어떤 서비스든 같은 시험지로 채점되게 설계했다." 이 문장 덕분에 다음 단계(LangGraph)에서 새로 만드는 G1을 P1과 같은 시험지로 비교할 수 있습니다 — "그래프로 바꿨더니 recall이 얼마나 올랐나"가 숫자로 나옵니다.
