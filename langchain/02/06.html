06. Middleware: Human-in-the-Loop (실행 승인)

실습 노트북: 06.ipynb  ·  원문: docs/02.agent-basic.md  ·  난이도: 🟡 중급  ·  선행: 05. TodoList

이 자료는 실습 노트북(06.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 지금까지 에이전트는 스스로 도구를 골라 알아서 실행했습니다. 그런데 이메일 전송, 결제, 파일 삭제처럼 되돌릴 수 없는 위험한 작업이라면요? 이 장에서는 Human-in-the-Loop — 민감한 도구를 실행하기 직전에 사람에게 "정말 할까요?" 하고 물어보는 안전장치를 배웁니다.

🔍 비유 — 이체 버튼 앞의 "정말 보내시겠습니까?" 은행 앱에서 100만 원을 이체할 때, 앱은 곧바로 돈을 보내지 않습니다. "수취인 · 금액을 확인하세요" 창을 띄우고 당신이 확인 버튼을 누를 때까지 모든 걸 멈춘 채 기다립니다. 잘못 보내면 되돌릴 수 없으니까요. Human-in-the-Loop이 바로 이 확인 창입니다. AI가 위험한 도구를 실행하려는 순간, 미들웨어가 손을 들어 "잠깐! 사람 승인부터"라고 흐름을 붙잡습니다.
이 장에서 배우는 것 HumanInTheLoopMiddleware를 에이전트에 끼우면, 지정한 도구를 실행하기 직전에 실행이 중단(interrupt)됩니다. 사람이 승인(approve) · 수정(edit) · 거절(reject) 중 하나를 고르면, 같은 대화(thread)를 이어서 실행이 재개되죠. "AI에게 운전대는 주되, 위험한 교차로에서는 사람이 브레이크를 밟는" 구조를 만드는 법을 배웁니다.
⚠️ 왜 꼭 필요한가 — 되돌릴 수 없는 작업들 LLM은 종종 엉뚱한 판단을 합니다. 그 판단이 이메일 발송 · 송금 · DB 삭제 · 외부 게시처럼 부작용(side effect)이 큰 작업과 연결되면, 한 번의 실수가 그대로 사고가 됩니다. "읽기"는 마음껏 자동화해도 되지만, "쓰기 · 보내기 · 지우기"는 사람이 최종 확인하는 게 안전합니다.

이 장의 전체 그림

1도구 호출 시도

AI가 send_email_tool을 실행하려 한다

2미들웨어가 가로챔

실행 직전 __interrupt__로 멈춘다

3사람이 결정

approve · edit · reject 중 선택

4같은 thread로 재개

invoke를 한 번 더 호출

5실제 실행 · 답변

승인됐다면 도구가 진짜 실행된다

0. 모델 · 도구 준비

먼저 말을 걸 모델과, 에이전트가 쓸 도구 2개를 준비합니다. 하나는 이메일 보내기(위험 — 부작용 큼), 하나는 이메일 읽기(안전 — 단순 조회)입니다. 일부러 "위험 vs 안전" 도구를 나란히 둬서, 뒤에서 둘을 다르게 취급하는 모습을 볼 겁니다.

📥 코드
from dotenv import load_dotenv
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent

# .env 파일에서 환경 변수 로드
load_dotenv()

# 모델 선언
model = init_chat_model("gpt-5-nano")
📥 코드
from typing import List, Dict
from langchain.tools import tool

@tool
def send_email_tool(to: str, subject: str, body: str) -> str:
    """지정한 주소로 이메일을 보내는 도구(프로토타입)."""
    return f"Email sent. to={to}, subject={subject}"

@tool
def read_email_tool(limit: int = 3) -> List[Dict[str, str]]:
    """최근 받은 이메일을 조회하는 도구(프로토타입)."""
    return [{"from": "hr@example.com", "subject": "정책 안내", "body": "..."}][:limit]
💡 지금은 "프로토타입" 도구 두 함수 모두 실제로 메일을 보내거나 받지는 않습니다. send_email_tool은 그냥 문자열을 돌려주고, read_email_tool은 가짜 메일 하나를 돌려줍니다. 이 장의 초점은 "도구가 뭘 하느냐"가 아니라 "위험한 도구를 실행하기 전에 어떻게 사람을 개입시키느냐"이기 때문입니다.

1. 미들웨어로 "검문소" 세우기

이제 에이전트를 조립하면서, 도구 목록 옆에 미들웨어(middleware)를 끼웁니다. 미들웨어는 에이전트의 실행 흐름 중간에 끼어들어 참견하는 중간 관리자예요. 여기서는 두 개를 넣습니다 — LLMToolEmulator(도구 흉내내기)와 오늘의 주인공 HumanInTheLoopMiddleware.

🔍 비유 — 공항 보안 검색대 HumanInTheLoopMiddleware는 도구들이 실행되러 가는 길목에 세운 보안 검색대입니다. 물병(안전한 read_email_tool)은 그냥 통과시키고, 수상한 가방(위험한 send_email_tool)은 "열어서 확인 좀 하겠습니다" 하고 붙잡죠. 무엇을 붙잡고 무엇을 통과시킬지는 interrupt_on이라는 검문 규칙표로 정합니다.
📥 코드
from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents.middleware import LLMToolEmulator, HumanInTheLoopMiddleware

checkpointer=InMemorySaver()

agent = create_agent(
    model=model,
    tools=[send_email_tool, read_email_tool],
    # tool emulator: 실제 도구 호출 대신 LLM으로 시뮬레이션, 즉, 도구가 만든 결과를 모킹하는것. gemini-2.5-flash 모델 사용
    middleware=[
        LLMToolEmulator(model="gpt-4o-mini"),
        HumanInTheLoopMiddleware(
            interrupt_on={
                # 이메일 전송은 부작용이 크므로 승인/수정/거절 옵션을 활성화
                "send_email_tool": {"allowed_decisions": ["approve", "edit", "reject"]},

                # 이메일 읽기는 단순 조회이므로 중단 없이 바로 실행 허용
                "read_email_tool": False,
            }
        ),
        ],
    )

# https://docs.langchain.com/oss/python/langchain/human-in-the-loop

코드의 핵심은 두 곳입니다. 첫째, checkpointer=InMemorySaver()로 대화 상태를 저장할 체크포인터를 준비했습니다. (중단됐다가 재개하려면 "어디서 멈췄는지"를 기억해야 하니까요.) 둘째, interrupt_on으로 도구별 검문 규칙을 정했습니다.

interrupt_on — 도구별 검문 규칙표

설정값의미이 노트북에서
{"allowed_decisions": [...]}실행 전 사람에게 검문. 허용할 결정 종류를 목록으로 지정send_email_tool (위험)
False검문 없이 바로 통과read_email_tool (안전)
True검문하되 기본 결정 세트 사용(사용 안 함)

사람이 고를 수 있는 세 가지 결정(decision)은 이렇습니다.

결정뜻결과
approve승인 — "그대로 보내"AI가 만든 원래 인자 그대로 도구 실행
edit수정 — "이렇게 고쳐서 보내"사람이 인자를 바꿔서 도구 실행
reject거절 — "보내지 마"도구 실행 취소, 모델에 거절 사실을 알림
📘 보충 — 함께 낀 LLMToolEmulator는 뭔가요?

LLMToolEmulator는 04번 노트북에서 배운 도구 시뮬레이터입니다. 실제 도구를 실행하는 대신, 다른 LLM이 "도구가 이런 결과를 냈을 거야"라고 그럴듯한 결과를 지어내 돌려줍니다. 아직 진짜 이메일 API를 붙이지 않은 프로토타입 단계에서, 흐름만 먼저 시험해 볼 때 유용하죠.

🔍 비유 — 대역 배우 위험한 액션 장면을 진짜 배우 대신 스턴트 대역이 대신 뛰듯, 진짜 도구 대신 LLM이 결과를 연기해 줍니다. 이 장에서 read_email_tool이 코드엔 없는 "5통의 메일 목록"을 술술 돌려주는 것도 이 대역 배우 덕분입니다.

2. 안전한 도구는 그냥 통과한다

먼저 안전한 쪽부터 확인합니다. "무슨 메일 왔는지 확인해줘"라고 요청하면 에이전트는 read_email_tool을 부릅니다. 이 도구는 interrupt_on에서 False로 설정했으므로 중단 없이 곧장 실행되고, 결과가 바로 돌아옵니다.

📥 코드
cfg = {"configurable": {"thread_id": "HIL-a"}}

# 안전한 도구(메일 조회) 호출 테스트
response = agent.invoke({"messages": [{"role": "user", "content": "무슨 메일 왔는지 확인해줘"}]}, cfg)

print(response["messages"][-1].content)
💡 thread_id에 주목하세요 cfg에 담긴 "thread_id": "HIL-a"는 이 대화의 이름표입니다. 뒤에서 중단됐다가 다시 이어갈 때, 바로 이 이름표를 그대로 써야 에이전트가 "아, 아까 그 대화구나" 하고 이어받습니다.
▶ 이렇게 나와요
다음은 최근 5통의 메일 요약입니다.

1) 제목: Project Update

   날짜: October 24, 2023
   미리보기: Hi team, I wanted to provide a quick update on the project timeline...

2) 제목: Meeting Reminder
   발신자: hr@company.com
   날짜: October 23, 2023
   미리보기: This is a reminder for the performance review meeting scheduled for tomorrow...

3) 제목: Newsletter - October Edition
   발신자: newsletter@updates.com
   ...

(중단 없이 read_email_tool 결과가 곧바로 텍스트로 정리되어 나온다)

요청이 멈춤 없이 끝까지 진행돼 최종 답변이 나왔습니다. 안전한 도구는 검문 대상이 아니니 당연한 결과죠. 이제 위험한 도구 쪽으로 넘어가 봅시다. 여기서부터가 진짜입니다.

3. 반전 — 정보가 부족하면 중단조차 없다

직관적으로는 "메일 보내줘"라고 하면 곧바로 send_email_tool이 붙잡힐 것 같습니다. 그런데 아래처럼 정보가 부족한 요청을 하면, 놀랍게도 중단(interrupt)이 아예 일어나지 않습니다.

📥 코드
# 민감한 도구(메일 발송) 호출 테스트
prompt = "교수님한테 내일 찾아뵙겠다는 메일 작성해서 보내줘."

response = agent.invoke(
    {"messages": [{"role": "user", "content": prompt}]},
    {"configurable": {"thread_id": "HIL-a"}}
)

# 이메일 읽기와 달리 tool_call이 호출되지 않은 것을 확인할 수 있다
# 사용자가 입력한 정보가 충분하지 않기 때문에 LLM이 tool을 호출하지 않는다
print(response)
print(response["messages"][-1].content)
▶ 이렇게 나와요 (핵심만)
AIMessage(content='좋습니다. 메일을 작성해 드릴 수 있는데, 보내려면 몇 가지 정보를
  알려주셔야 합니다. ...
  - 교수님의 이메일 주소
  - 교수님의 성함(정확한 표기)
  - 내일 가능한 시간대 ...',
  ...
  tool_calls=[],            ← 도구를 부르지 않았다!
  finish_reason='stop')     ← 그냥 텍스트로 마무리

# 결과에 __interrupt__ 키가 없다 → 미들웨어가 개입할 일이 없었다
🔍 비유 — 재료가 없으면 요리사는 요리를 시작하지 않는다 "이메일 보내"라는 주문을 받았지만, AI가 보니 받는 사람 주소(to)가 없습니다. 필수 재료가 없는데 무턱대고 조리를 시작할 수는 없죠. 그래서 AI는 도구를 부르는 대신 "이 정보들을 더 주세요"라고 되묻는 문장만 내놓습니다. 조리(도구 실행)를 시작하지 않았으니, 검색대(미들웨어)도 붙잡을 게 없습니다.
💡 핵심 — 중단은 "도구 호출"에 걸리는 것 interrupt_on은 AI가 실제로 도구를 호출하려 할 때(tool_calls가 생길 때)만 작동합니다. AI가 도구를 부르지 않고 말(텍스트)로만 답하면, 중단할 대상 자체가 없습니다. 즉 "정보 부족 → 도구 호출 생략 → 중단 없음"은 오류가 아니라 정상 동작입니다.

4. 정보가 충분하면 → 도구 호출 → 중단!

이번엔 받는 주소 · 제목 · 본문을 모두 담아 요청합니다. 필수 재료가 갖춰졌으니 AI는 드디어 send_email_tool을 호출하려고 시도합니다. 그리고 바로 그 순간, 검문소가 작동합니다.

📥 코드
# 민감한 도구(메일 발송) 호출 테스트
prompt = "내일 방문할 Jasper의 이메일 주소는 jasper@gmail.com 입니다. subject: 오늘 방문 예정, body: 오늘 방문 예정입니다. 이메일을 보내줘"

# 위 예시와 달리, 상세한 정보를 전달해주자 tool_call이 호출되는 것을 확인할 수 있다

response = agent.invoke(
    {"messages": [{"role": "user", "content": prompt}]},
    {"configurable": {"thread_id": "HIL-a"}}
)

print(response)
print(response["messages"][-1].content)
▶ 이렇게 나와요 (핵심만)
AIMessage(content='',                       ← 텍스트 답은 비어 있고
  tool_calls=[{'name': 'send_email_tool',
               'args': {'to': 'jasper@gmail.com',
                        'subject': '오늘 방문 예정',
                        'body': '오늘 방문 예정입니다.'}, ...}],
  finish_reason='tool_calls')

'__interrupt__': [Interrupt(value={
    'action_requests': [{'name': 'send_email_tool',
                         'args': {'to': 'jasper@gmail.com', ...},
                         'description': 'Tool execution requires approval ...'}],
    'review_configs': [{'action_name': 'send_email_tool',
                        'allowed_decisions': ['approve', 'edit', 'reject']}]
  }, id='cc2d312a5192d976e1e5b3d0da524106')]

결과를 보면 두 가지가 눈에 띕니다. 답변 텍스트(content)는 비어 있고, 대신 결과 딕셔너리에 __interrupt__라는 특별한 키가 생겼습니다. 이게 "멈췄다"는 증거입니다.

🔍 비유 — 결재 서류가 상사 책상에 올라간 순간 부하 직원(AI)이 "이 메일 보내겠습니다" 하고 결재 서류(action_requests)를 올렸습니다. 서류에는 무슨 도구를, 어떤 내용으로 실행할지가 적혀 있죠. 하지만 상사(사람)의 도장이 찍히기 전까지 메일은 발송함에 그대로 멈춰 있습니다. __interrupt__는 바로 이 "결재 대기중" 도장이에요.

__interrupt__ 속을 뜯어보면

필드담긴 것
action_requests실행 대기 중인 도구의 이름과 인자 (무엇을 보내려 하는지)
description"Tool execution requires approval" — 승인이 필요하다는 안내
review_configs사람이 고를 수 있는 결정 목록 (여기선 approve · edit · reject)
id이 중단 건의 고유 번호 — 나중에 edit할 때 이 번호로 지목
📘 보충 — content가 비어 있어도 오류가 아니다

print(response["messages"][-1].content)를 찍으면 아무것도 안 나올 수 있습니다. 특히 gpt-4o-mini 같은 모델은 텍스트 없이 도구 호출만 내놓기 때문에 content=''가 됩니다. (반면 gpt-5-nano는 상황에 따라 설명을 곁들이기도 합니다.) 어느 쪽이든 중단된 상태라는 사실은 같습니다.

그래서 상태를 확인할 땐 content 대신 아래처럼 봐야 합니다.

# AI가 호출하려는 도구 정보 확인
last_msg = response["messages"][-1]
if last_msg.tool_calls:
    print("AI가 호출하려는 도구:", last_msg.tool_calls[0]['name'])
    print("도구에 전달된 인자:", last_msg.tool_calls[0]['args'])

# 중단 여부 확인
if "__interrupt__" in response:
    print("사람의 승인이 필요한 상태로 중단되었습니다.")
⚠️ invoke는 "기다리지" 않는다 중단됐다고 해서 프로그램이 사용자 입력을 기다리며 멈춰(blocking) 있는 게 아닙니다. invoke는 __interrupt__를 담아 곧바로 반환하고 끝납니다. 실제 실행을 이어가려면, 당신이 결정을 내려 invoke를 한 번 더 호출해야 합니다. 다음 절이 그 이야기입니다.

5. 결정을 전달해 재개하기

멈춘 흐름을 다시 굴리는 방법은 같은 thread_id로 invoke를 한 번 더 부르되, 이번엔 메시지 대신 사람의 결정(decision)을 넣는 것입니다. InMemorySaver가 "HIL-a" 대화의 멈춘 지점을 기억하고 있어서, 그 자리에서 이어집니다.

🔍 비유 — 책갈피를 끼워둔 책 읽던 책을 덮어도 책갈피(체크포인터 + thread_id)가 끼워져 있으면, 다음에 폈을 때 그 페이지부터 이어 읽죠. 결정을 담은 두 번째 invoke는 "책갈피 끼운 그 페이지를 펴서, 이번엔 승인이라는 답을 들고 이어 읽는" 것과 같습니다. 책갈피 이름(thread_id)이 다르면 엉뚱한 책을 펴게 되니 반드시 같아야 합니다.

① 승인(approve) — "그대로 보내"

📥 코드
config = {"configurable": {"thread_id": "HIL-a"}}

response_after_approve = agent.invoke(
    {"decision": "approve"},
    config=config
)

print("최종 응답:", response_after_approve["messages"][-1].content)
▶ 이렇게 나와요 (예상 출력)
최종 응답: 메일을 성공적으로 보냈습니다.
(멈춰 있던 send_email_tool이 이제서야 실제로 실행되어
 "Email sent. to=jasper@gmail.com, subject=오늘 방문 예정" 결과가 반영된다)

② 수정(edit) — "이렇게 고쳐서 보내"

AI가 만든 인자가 마음에 안 들면, 사람이 인자를 갈아끼워 실행할 수 있습니다. 이때 어느 중단 건을 고치는지 action_request_id로 지목합니다(위 __interrupt__의 id).

📥 코드
response_after_edit = agent.invoke(
    {
        "decision": "edit",
        "action_request_id": response["__interrupt__"][0].id,
        "tool_call": {
            "name": "send_email_tool",
            "args": {
                "to": "professor@example.com",
                "subject": "[수정] 내일 방문 예정입니다",
                "body": "교수님, 내일 오후 2시쯤 찾아뵙고 싶습니다. 감사합니다."
            }
        }
    },
    config=config
)
💡 거절(reject)도 같은 자리 보내고 싶지 않다면 {"decision": "reject"}를 전달하면 됩니다. 도구는 실행되지 않고, "사용자가 거절했다"는 사실이 모델에 전해져 에이전트가 다른 방향으로 대화를 이어갑니다.

전체 흐름 다시 보기

Human
jasper@gmail.com 으로 "오늘 방문 예정" 메일 보내줘 ← 정보 충분
AI
send_email_tool(to=jasper@…) 호출 시도 ← tool_calls 발생
MW
잠깐! 승인이 필요한 도구야 → __interrupt__ ← 미들웨어가 중단
Human
approve (같은 thread_id로 재-invoke) ← 사람의 결정
AI
도구 실제 실행 → "메일을 보냈습니다" ← 재개 완료
💡 왜 이게 가능한가 — Stateful 에이전트 이 모든 게 되는 이유는 InMemorySaver(체크포인터)가 thread_id를 기준으로 현재까지의 작업 상태를 기억하기 때문입니다. 덕분에 중단된 지점부터 이어서 실행할 수 있습니다. 03번 노트북에서 배운 "메모리"가 여기서 승인 대기 상태를 붙잡아두는 역할로 다시 등장하는 셈이죠.

📚 한 장 정리

오늘의 핵심 Human-in-the-Loop은 "위험한 도구는 실행 직전에 멈추고, 사람의 승인을 받은 뒤에야 실제로 실행한다"는 안전장치다.
  • HumanInTheLoopMiddleware — 도구 실행 길목의 보안 검색대. interrupt_on으로 도구별 검문 규칙을 정한다.
  • interrupt_on — {"allowed_decisions": [...]}는 검문(위험), False는 바로 통과(안전).
  • 중단은 도구 호출에 걸린다 — AI가 tool_calls를 낼 때만 작동. 정보 부족으로 도구를 안 부르면 중단도 없다(정상).
  • __interrupt__ — "결재 대기" 도장. action_requests(무엇을) · review_configs(어떤 결정을) · id가 담긴다.
  • 재개 = 같은 thread_id + 결정 — {"decision": "approve" / "edit" / "reject"}를 담아 invoke를 한 번 더 호출한다.
  • 가능한 이유 — InMemorySaver가 멈춘 지점을 기억하는 stateful 구조 덕분(책갈피).
