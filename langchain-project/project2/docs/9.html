# P2 · 관측 가능한 Agent API 서비스

## 문제 정의
질문마다 필요한 정보의 출처가 다르다 — 약관은 사내 문서에, 금액은 계산에, 최신 정보는 웹에 있다.
사용자가 창구를 골라 찾아가게 하는 대신, 창구를 하나로 두고 Agent가 도구를 선택하게 했다.
동시에 "무엇을 왜 했는지"가 추적되고, 프롬프트 변경의 영향을 배포 전에 잴 수 있어야 한다.

## 아키텍처
사용자 → [입력 Guardrail] → Agent(LLM) → 도구 선택 → 답변(구조화 JSON)

- 도구 4종: get_today / calculate / web_search / **search_internal_docs (P1 RAG 서비스를 HTTP 호출)**
- 메모리: session_id → thread_id (checkpointer)
- 가드레일: 키워드 기반 입력 차단(LLM 호출 0회) + PII 마스킹
- 출력: ProviderStrategy(ChatReply) 로 { answer, sources, confident } 형식 강제
  (ToolStrategy는 tool_choice="any" 강제 → 후속 질문에서 검색 루프. 실측 후 교체)
- 안전망: ToolCallLimitMiddleware — 요청당 도구 호출 8회 상한
- 가로지르는 층: Langfuse(트레이싱·비용) / Multi-LLM(get_model) / 프롬프트 평가 하네스

### 설계 결정
- **P1을 import하지 않고 HTTP로 호출한다.** 검색 컴포넌트를 다른 서비스에서도 재사용할 수 있고,
  P1 장애 시에도 Agent는 나머지 도구로 계속 응답한다. P2는 Chroma·리랭커 의존성이 전혀 없다.
- **모델과 프롬프트를 Context + 미들웨어로 런타임 교체 가능하게 했다.** 그래서 A/B 실험이
  코드 수정 없이 가능하다.

## 실행 방법
서버가 두 개다. **P1을 먼저 띄운다.**

1. P1 (문서 검색, 포트 8000)
   cd ../project1 && uv run uvicorn main:app --reload
2. P2 (Agent API, 포트 8001)
   uv sync && uv run uvicorn main:app --reload --port 8001
3. 호출
   curl -X POST http://localhost:8001/chat -H "Content-Type: application/json" \
     -d '{"message":"신용카드 분실 시 회원 책임은?","session_id":"u1"}'
4. 평가 실행
   uv run python evaluate.py

필요한 환경변수(.env): OPENAI_API_KEY / GOOGLE_API_KEY / LANGFUSE_* / P1_API_URL

## 한계 / 다음
- 대화 저장이 InMemorySaver — 재시작 시 소실, 다중 워커에서 기억 분리. 운영 시 Postgres checkpointer 필요
- session_id를 클라이언트가 지정 — 인증 붙여 서버가 세션 소유권을 검증해야 함
- 같은 session_id 동시 요청 미보호 — 겹치면 쓰다 만 기록을 읽어 400. 세션당 잠금 필요
- LLM judge의 신뢰도를 사람 라벨과 대조하지 않음 → P3에서 일치율 측정
- 도구 추가는 tools.py에 함수 하나 + 목록 한 줄. 사내 API 등으로 그대로 확장 가능

"목적 — 질문마다 필요한 정보 출처가 다른 사내 문의를 단일 창구로 처리하면서, 품질 변화를 배포 전에 확인할 수 있어야 했다. 접근 — LangChain Agent에 도구 4종(사내 RAG는 P1 서비스를 HTTP로 호출)을 붙이고, 가드레일·구조화 출력·세션 메모리를 얹어 FastAPI로 서빙했다. 모델과 프롬프트는 미들웨어로 런타임 교체 가능하게 설계했다. 결과 — Langfuse로 도구 호출·토큰·비용을 전량 추적하고, 케이스 15개 자동 채점으로 프롬프트 개선의 형식 준수율을 0.67 → 1.00으로 검증했다."
