03. Custom Middleware: Wrap-style — 동적 모델 선택

실습 노트북: 03.ipynb  ·  원문: docs/03.advanced-agent.md 1.7 Wrap-style 심화  ·  난이도: 🟡 중급  ·  선행: 02. Node-style

이 자료는 실습 노트북(03.ipynb)을 열기 전에 먼저 읽는 강의 교재입니다. 이번 주제는 Wrap-style Hook(@wrap_model_call) — LLM을 부르는 순간을 중간에서 가로채(intercept), 요청을 살짝 고쳐 다른 모델로 갈아끼우는 기술입니다. 구체적으로는 사용자 질문의 길이에 따라 알맞은 크기의 모델을 자동으로 골라주는 "똑똑한 배차 시스템"을 비유와 함께 만들어 봅니다.

이 장에서 배우는 것 미들웨어(Middleware)는 사용자와 LLM 사이에 끼어드는 중간 관리자입니다. 그중 Wrap-style은 "LLM 호출"이라는 행위 자체를 통째로 감싸서, 호출 직전에 요청을 바꾸거나 호출 직후에 결과를 검사할 수 있습니다. 이번엔 "호출 직전에 어떤 모델을 쓸지를 상황에 맞게 바꿔치기"하는 데 집중합니다.
🔍 비유 — 손님과 주방 사이의 홀 매니저 식당에서 손님의 주문서(request)가 곧장 주방(handler, 실제 LLM 호출)으로 가지 않고, 중간에 홀 매니저를 한 번 거친다고 해봅시다. 매니저는 주문서를 주방에 넘기기 전에 "이 손님은 매운 걸 못 드시니 순한 맛으로" 하고 주문을 고쳐 쓸 수 있고, 요리가 나온 뒤에도 검수할 수 있습니다. Wrap-style 미들웨어가 바로 이 홀 매니저입니다. 오늘은 매니저가 주문서를 보고 "이 요리는 어느 셰프에게 맡길까(=어떤 모델을 쓸까)"를 정하는 일을 시켜봅니다.

Node-style vs Wrap-style — 무엇이 다를까

바로 앞 노트북(02. Node-style)에서는 @before_model 같은 데코레이터로 정해진 시점에 로직을 끼워 넣었습니다. Wrap-style은 접근 방식이 다릅니다. 실행 흐름을 감싸서(wrap) 그 안팎을 모두 제어합니다.

🔍 비유 — CCTV vs 톨게이트 Node-style은 도로 옆에 세워둔 CCTV와 같습니다 — 정해진 지점을 지켜보고 기록하지만, 지나가는 차 자체를 멈추거나 바꾸진 않죠(관찰·로깅에 적합). Wrap-style은 톨게이트(검문소)입니다 — 지나가려는 차를 실제로 세워서 짐을 바꿔 싣거나 다른 길로 보낼 수 있습니다(흐름 제어·변형에 적합). 오늘 우리는 "질문 길이"라는 조건을 보고 차를 다른 셰프에게 보내는 톨게이트를 만드는 겁니다.
구분Node-style HookWrap-style Hook
동작 방식특정 실행 지점(before/after)에서 순차적으로 동작실행 흐름(model·tool 호출)을 감싸서(intercept) 조작
입력 파라미터state, runtimerequest, handler
적합한 용도상태 확인, 로깅, 유효성 검사동적 프롬프트 삽입, 흐름 건너뛰기 등 흐름 제어·변형
데코레이터@before_model, @after_model 등@wrap_model_call, @wrap_tool_call

두 개의 손잡이 — request와 handler

Wrap-style 함수는 항상 두 개의 인자를 받습니다. 이 둘의 역할만 확실히 잡으면 나머지는 쉽습니다.

1request

이번에 LLM에 보낼 요청서. 모델·시스템 프롬프트·메시지·도구 목록이 담겨 있다.

2handler

요청서를 받아 실제로 LLM을 호출하는 함수. 우리가 handler(request)로 직접 눌러준다.

즉 우리는 handler를 부르기 직전에 request를 마음대로 손볼 수 있습니다. 오늘은 request 안의 model 항목을 상황에 맞는 모델로 바꿔치기한 뒤, 그 바뀐 요청으로 handler를 눌러줄 겁니다.

📘 보충 — request(ModelRequest) 안에는 무엇이 들었나

request는 이번 LLM 호출에 필요한 모든 재료를 담은 요청서 한 장입니다. 대표 항목만 추리면 다음과 같습니다.

필드의미
model어떤 모델을 쓸지 (예: ChatOpenAI) — 오늘 우리가 바꿀 대상
system_prompt시스템 프롬프트 (없을 수도 있음)
messages대화 메시지 목록 — messages[-1]이 가장 최근 발화
tools / tool_choice사용 가능한 도구 목록과 강제 선택 지정
runtime실행 환경 정보 (context, store, stream 등)

1. 동적 모델 선택 미들웨어 만들기

이제 핵심입니다. 사용자의 메시지 길이를 재서 — 짧으면 가벼운 모델, 길면 강력한 모델을 쓰도록 자동으로 갈아끼우는 미들웨어를 만듭니다. 왜 이렇게 할까요? 강력한 모델은 똑똑하지만 느리고 비쌉니다. "안녕하세요" 한마디에 최고급 모델을 쓰는 건 낭비니까요.

🔍 비유 — 물건 크기에 따른 배차(配車) 택배 회사는 짐마다 같은 트럭을 보내지 않습니다. 편지 한 통엔 날쌘 오토바이(gpt-5-nano), 중간 소포엔 승합차(gpt-5-mini), 대형 이삿짐엔 5톤 트럭(gpt-5)을 배차하죠. 큰 짐에 오토바이를 보내면 다 못 싣고, 편지 한 통에 5톤 트럭을 보내면 기름값만 아깝습니다. 우리 미들웨어는 질문의 "무게(길이)"를 저울에 달아 알맞은 차량(모델)을 배차하는 물류 담당자입니다.

노트북에 나온 배차 규칙을 표로 옮기면 이렇습니다.

메시지 길이선택 모델이유
< 10자gpt-5-nano간단한 질문 → 가벼운 모델로 비용 절약
10 ~ 30자gpt-5-mini중간 복잡도
> 30자gpt-5복잡하고 긴 질문 → 강력한 모델
📥 코드
from langchain_openai import ChatOpenAI
from typing import Callable

from langchain.agents.middleware import wrap_model_call
from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse

@wrap_model_call
def dynamic_model_selector(request: ModelRequest, handler: Callable[[ModelRequest], ModelResponse]) -> ModelResponse:
    # 최근 사용자의 입력 메시지 추출
    last_msg = request.messages[-1].content if request.messages else ""
    msg_len = len(last_msg)

    # 길이에 따라 모델 선택
    if msg_len < 10:
        model_name = "gpt-5-nano"
    elif msg_len < 30:
        model_name = "gpt-5-mini"
    else:
        model_name = "gpt-5"

    print(f"🔁 메시지 길이: {msg_len}, 선택된 모델: {model_name}")

    # request.model을 새로운 모델로 교체
    new_model = ChatOpenAI(model_name=model_name)
    new_request = request.override(model=new_model)

    # 수정된 요청으로 LLM 호출
    return handler(new_request)

한 줄씩 뜯어보면 톨게이트가 하는 일이 그대로 보입니다.

  • @wrap_model_call — 이 데코레이터가 아래 함수를 "LLM 호출을 감싸는 톨게이트"로 등록합니다.
  • request.messages[-1].content — 요청서에서 가장 최근 사용자 발화를 꺼냅니다. ([-1] = 리스트의 맨 끝)
  • len(last_msg) — 그 발화의 글자 수를 저울에 답니다. 이 숫자가 배차 기준입니다.
  • if / elif / else — 무게에 따라 오토바이·승합차·트럭 중 하나의 model_name을 고릅니다.
  • request.override(model=new_model) — 요청서의 모델 칸만 새 모델로 바꾼 사본을 만듭니다.
  • return handler(new_request) — 바뀐 요청서로 진짜 LLM을 호출하고 그 결과를 돌려줍니다.
⚠️ 함정 — handler를 부르지 않으면 아무 일도 안 일어난다 Wrap-style 함수는 반드시 handler(...)를 호출하고 그 반환값을 return해야 합니다. 톨게이트에서 차를 세워놓고 통과시키는 것을 깜빡하면, LLM이 영영 호출되지 않아 답이 나오지 않습니다.

request.override(...) — 원본은 두고 사본만 바꾸기

코드에서 눈여겨볼 부분은 request.override(model=new_model)입니다. 이건 원래 request 객체를 직접 수정하는 게 아니라, 모델 칸만 바꾼 새 요청 객체를 반환합니다. 원본 request는 손대지 않고 그대로 둔다는 뜻이죠(이런 성질을 불변, immutable이라고 합니다).

🔍 비유 — 이력서 "다른 이름으로 저장" 기본 이력서 파일이 하나 있다고 합시다. 지원할 회사마다 회사명 한 칸만 바꿔야 하는데, 원본 파일을 직접 고치면 실수로 이전 내용이 날아갈 수 있습니다. 그래서 우리는 "다른 이름으로 저장"해 사본을 만든 뒤 그 사본만 고치죠. override가 바로 이 "다른 이름으로 저장 후 한 칸만 수정"입니다. 원본(request)은 안전하게 남고, 바뀐 사본(new_request)만 주방으로 넘어갑니다.
💡 왜 굳이 불변으로? 미들웨어는 여러 개가 겹겹이 쌓일 수 있습니다. 각자 원본을 함부로 뜯어고치면 서로 충돌해 버그가 생깁니다. "원본은 그대로, 바꾼 사본만 다음으로 전달" 규칙을 지키면 여러 미들웨어가 안전하게 협력할 수 있어요.

2. Agent에 미들웨어 장착하고 호출하기

이제 만든 톨게이트를 실제 도로에 세울 차례입니다. create_agent의 middleware 목록에 dynamic_model_selector를 끼워 넣으면 됩니다. 그런 다음 길이가 서로 다른 세 문장을 던져봅니다.

📥 코드
routing_agent = create_agent(
    model="gpt-5-mini", # 기본 모델로 생성했지만, 미들웨어가 알아서 교체해 줍니다.
    tools=[],
    middleware=[dynamic_model_selector],
)

routing_agent.invoke({"messages": [{"role": "user", "content": "안녕하세요"}]})
routing_agent.invoke({"messages": [{"role": "user", "content": "안녕하세요. 저는 Jay입니다."}]})
routing_agent.invoke({"messages": [{"role": "user", "content": "안녕하세요. 저는 Jay입니다. 인공지능 에이전트 아키텍처에 관해 궁금한 게 있어요."}]})
💡 기본 모델은 "임시"일 뿐 create_agent(model="gpt-5-mini")로 기본 모델을 지정했지만, 매 호출마다 우리 미들웨어가 override로 모델을 갈아끼우므로 실제로 쓰이는 모델은 그때그때 달라집니다. 기본값은 미들웨어가 아무 결정도 못 할 때를 위한 "예비 차량"이라고 생각하세요.

세 입력이 각각 어떤 차량에 배차되는지 정리하면 이렇습니다. (len()은 공백·마침표까지 글자 수로 셈)

▶ 실행 결과 읽기

각 invoke가 실행될 때마다 미들웨어 안의 print가 먼저 찍힙니다. 길이에 따라 서로 다른 모델이 선택되는 것이 눈으로 확인됩니다.

▶ 이렇게 나와요
🔁 메시지 길이: 5, 선택된 모델: gpt-5-nano
🔁 메시지 길이: 17, 선택된 모델: gpt-5-mini
🔁 메시지 길이: 47, 선택된 모델: gpt-5

그리고 마지막 invoke(47자, gpt-5 배차)의 반환값은 대화 전체가 담긴 AIMessage입니다. 실제 답변은 매우 길어 일부만 옮기면 다음과 같습니다.

💡 model_name을 보면 배차가 증명된다 반환된 AIMessage의 response_metadata를 열어보면 'model_name': 'gpt-5-2025-08-07'이 찍혀 있습니다. 기본값(gpt-5-mini)이 아니라 미들웨어가 갈아끼운 gpt-5가 실제로 응답했음을 메타데이터가 증언해 주는 셈입니다.
⚠️ 길이 = 난이도는 아니다 이번 예제는 "글자 수"라는 가장 단순한 기준으로 배차했습니다. 하지만 짧아도 어려운 질문("P=NP?")도 있죠. 실전에서는 길이 대신 주제·사용자 등급·비용 예산 같은 더 똑똑한 기준으로 바꿔 끼우면 됩니다 — 바로 다음 노트북에서 다룰 멤버십(등급) 기반 모델 선택이 그 예입니다.

📚 한 장 정리

오늘의 핵심 Wrap-style 미들웨어는 LLM 호출을 톨게이트처럼 감싸서, 호출 직전에 요청을 바꿔치기한다. 오늘은 "질문 길이"를 저울에 달아 알맞은 크기의 모델을 자동 배차했다.
  • Node-style vs Wrap-style — Node는 CCTV(지켜보고 기록), Wrap은 톨게이트(세워서 변형). 오늘은 Wrap.
  • 두 손잡이 — request(요청서)와 handler(실제 호출 버튼). handler(request)를 꼭 return해야 답이 나온다.
  • 동적 모델 선택 — request.messages[-1] 길이로 gpt-5-nano / mini / gpt-5를 배차(짐 크기별 차량).
  • request.override(model=...) — 원본은 두고 사본만 수정(다른 이름으로 저장). 여러 미들웨어가 안전하게 협력하는 비결.
  • 기본 모델은 예비 차량 — create_agent(model=...)은 미들웨어가 매번 갈아끼우므로, 실제 응답 모델은 response_metadata로 확인한다.
