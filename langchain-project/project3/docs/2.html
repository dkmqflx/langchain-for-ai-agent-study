시험 대상 어댑터 — P1·P2를 같은 모양으로

🟢 뼈대 ⏱ 1~2시간
🎯 목표

P1의 /query와 P2의 /chat은 창구도 응답 모양도 다릅니다. 이 차이를 targets.py 한 파일이 흡수해서, 러너에게는 "질문을 넣으면 RunResult가 나온다"는 한 가지 모양만 보이게 합니다. 그 전에 P1에 옵션 하나를 더합니다 — 검색된 원문(contexts)을 평가 때만 함께 돌려주는 스위치예요.

🧠 개념 — 딱 하나만

수험생이 다른 언어로 답해도, 답안지 양식은 하나여야 채점기가 돈다

P1은 citations(문서·쪽)로 근거를 주고, P2는 sources(문자열 목록)로 줍니다. P2에는 used_tools·blocked가 있고 P1에는 없어요. 러너가 이 차이를 매번 if target == "rag"로 처리하면 STEP 3~7의 모든 코드에 그 분기가 퍼집니다. 대신 응답을 받자마자 하나의 양식(RunResult)으로 옮겨 적는 층을 둡니다. 러너는 그 양식만 압니다.

📚 P1 · /query{ answer, citations,
contexts }
→
🔄 targets.pyask_rag / ask_agent
차이는 여기서 끝난다
→
📦 RunResultanswer · sources · contexts
used_tools · blocked · latency · error
←
🤖 P2 · /chat{ answer, sources,
used_tools, blocked }
🌐 비유 — 통역사를 한 명 두면 회의실은 한 언어만 쓴다

참석자마다 통역사를 붙이지 않고, 입구에 한 명만 세웁니다. 안에서는 모두가 같은 양식으로 말하죠. 시험 대상이 셋, 넷으로 늘어도(다음 단계의 LangGraph 서비스) 통역사에게 문장 하나만 더 가르치면 회의실 안 코드는 그대로입니다.

🛠 할 일 — 다섯 조각
①

P1에 옵션 하나 — include_contexts

— P1 쪽 파일 둘에 세 줄. 기본값이 false라 평소 응답은 그대로다

RAGAS의 faithfulness·context precision·recall은 검색된 원문이 있어야 계산됩니다. P1의 answer()는 이미 contexts를 만들고 있고, /query 응답에서만 빼고 있었어요. 요청한 쪽만 받도록 스위치를 답니다.

project1/schemas.py — 두 줄 추가
class QueryIn(BaseModel):
    question: str
    mode: Literal["baseline", "hybrid", "rerank"] = "rerank"
    include_contexts: bool = False          # ← 추가(P3 STEP 2). 평가 때만 검색된 원문을 함께 받는다

class QueryOut(BaseModel):
    answer: str
    citations: list[Citation]
    contexts: list[str] = []                # ← 추가(P3 STEP 2). 기본은 빈 목록 — 평소 응답 크기는 그대로다
project1/main.py — query() 한 곳
@app.post("/query", response_model=QueryOut)
def query(body: QueryIn):
    result = answer(body.question, mode=body.mode)
    return {
        "answer": result["answer"],
        "citations": result["citations"],
        "contexts": result["contexts"] if body.include_contexts else [],   # ← 요청한 쪽만 받는다
    }

터미널 A의 P1은 --reload로 떠 있으니 저장하면 스스로 다시 뜹니다. P2는 이 옵션을 모르므로 P2가 받는 응답은 달라지지 않아요.

②

schemas.py — RunResult, 답안지 양식

— STEP 1의 파일에 클래스 하나 추가
class RunResult(BaseModel):
    answer: str
    sources: list[str] = []                   # 근거. RAG는 "문서 p.쪽", Agent는 sources 그대로
    contexts: list[str] = []                  # RAG만. 검색된 원문 — RAGAS가 읽는다
    used_tools: list[str] = []                # Agent만. 이번 턴에 부른 도구 이름
    blocked: bool = False                     # Agent만. 가드레일에 막혔나
    latency_ms: int                           # 요청 → 응답까지 걸린 시간
    error: str | None = None                  # 서비스가 죽어 있었으면 그 사유. 케이스는 계속 돈다

"RAG만", "Agent만" 칸이 섞여 있는 게 어색해 보일 수 있어요. 하지만 양식을 둘로 나누면 러너가 다시 분기해야 합니다. 안 쓰는 칸은 빈 값으로 두는 쪽이 코드 전체를 단순하게 유지합니다.

③

targets.py — 전화 한 통, 시간 재기, 실패를 값으로

— 예외를 밖으로 던지지 않는다
targets.py
import os
import time

import requests
from dotenv import load_dotenv

from schemas import RunResult

load_dotenv()
P1_API_URL = os.getenv("P1_API_URL", "http://localhost:8000")
P2_API_URL = os.getenv("P2_API_URL", "http://localhost:8001")


def _post(url: str, payload: dict, timeout: int = 120) -> tuple[dict | None, int, str | None]:
    """POST 한 번. (응답 JSON, 걸린 ms, 에러 사유)를 돌려준다. 서비스가 죽어 있어도 예외를 밖으로 던지지 않는다."""
    t0 = time.perf_counter()
    try:
        r = requests.post(url, json=payload, timeout=timeout)
        r.raise_for_status()                              # 4xx·5xx도 실패로 친다
        data, err = r.json(), None
    except requests.exceptions.RequestException as e:
        data, err = None, str(e)
    return data, int((time.perf_counter() - t0) * 1000), err

15개 중 하나가 타임아웃 났다고 실행 전체가 죽으면 나머지 14개의 답을 잃습니다. 그래서 실패는 예외가 아니라 값(error 칸)으로 돌려주고, STEP 3에서 ok라는 지표로 셉니다. "응답률 0.93"도 그 자체로 정보예요. latency_ms는 여기서 재는 게 정확합니다 — 러너가 재면 채점 시간까지 섞입니다.

④

targets.py — 통역 두 문장

— 응답을 RunResult로 옮겨 적는다
def ask_rag(question: str, *, mode: str = "rerank") -> RunResult:
    """P1 · POST /query. mode(baseline|hybrid|rerank)가 곧 '실험 손잡이'다."""
    data, ms, err = _post(f"{P1_API_URL}/query",
                          {"question": question, "mode": mode, "include_contexts": True})
    if err:
        return RunResult(answer="", latency_ms=ms, error=err)
    # 같은 페이지에서 청크가 여럿 걸리는 일이 흔하다 → 순서는 지키고 중복만 걷어낸다
    sources = list(dict.fromkeys(f"{c.get('source')} p.{c.get('page')}" for c in data["citations"]))
    return RunResult(answer=data["answer"], sources=sources,
                     contexts=data.get("contexts", []), latency_ms=ms)


def ask_agent(question: str, *, session_id: str) -> RunResult:
    """P2 · POST /chat. 케이스마다 session_id를 다르게 줘야 앞 케이스의 대화가 섞이지 않는다."""
    data, ms, err = _post(f"{P2_API_URL}/chat", {"message": question, "session_id": session_id})
    if err:
        return RunResult(answer="", latency_ms=ms, error=err)
    return RunResult(answer=data["answer"], sources=data["sources"],
                     used_tools=data["used_tools"], blocked=data["blocked"], latency_ms=ms)

ask_rag의 mode를 눈여겨보세요. P1이 API로 열어 둔 검색 구성(baseline · hybrid · rerank)이 P3에서는 실험 손잡이가 됩니다. STEP 6에서 "rerank를 baseline으로 바꾸면 회귀로 잡히는가"를 이 손잡이로 재현합니다.

⑤

targets.py — 러너가 부르는 입구 하나 + 헬스체크

— 분기는 여기 한 번뿐
def call_target(target: str, case, params: dict, run_id: str) -> RunResult:
    """러너가 부르는 단 하나의 입구. target 이름으로 어느 서비스에 보낼지 고른다."""
    if target == "rag":
        return ask_rag(case.question, **params)
    return ask_agent(case.question, session_id=f"eval-{run_id}-{case.id}", **params)


def health() -> dict[str, bool]:
    """두 서비스가 살아 있는지. 러너가 시작 전에 한 번 확인한다."""
    out = {}
    for name, base in (("rag", P1_API_URL), ("agent", P2_API_URL)):
        try:
            out[name] = requests.get(f"{base}/health", timeout=5).ok
        except requests.exceptions.RequestException:
            out[name] = False
    return out


if __name__ == "__main__":
    print("health:", health())
    print("\n[rag]  ", ask_rag("카드를 잃어버렸는데 누가 몰래 쓴 금액을 은행이 물어주나요?"))
    print("\n[agent]", ask_agent("오늘부터 30일 뒤는 며칠인가요?", session_id="smoke"))

params는 STEP 3에서 명령줄의 --param mode=baseline이 그대로 담겨 오는 상자입니다. 지금 P2에는 손잡이가 없지만, 나중에 P2가 /chat에 provider나 prompt 칸을 열면 이 코드는 그대로 두고 명령줄만 바꾸면 됩니다. 세션 id에 run_id가 들어가는 건 실행을 두 번 돌려도 P2의 메모리가 섞이지 않게 하려는 거예요.

🎓 한 줄 정리

시험 대상의 차이는 어댑터 한 파일에서 끝내고, 러너는 하나의 양식만 본다. 실패도 예외가 아니라 값으로 받아야 15개 중 14개의 답이 살아남는다.

더 알아보기 — timeout은 왜 120초인가 / 세 번째 시험 대상을 붙이려면

timeout 120초

P1의 rerank 구성은 리랭커 모델을 태워 질의당 10초 안팎이 걸리고, P2는 도구를 두세 번 부르면 그만큼 더 걸립니다. 넉넉히 두되 무한정 기다리지는 않습니다 — 타임아웃도 error로 기록되어 "응답률" 지표에 잡혀야 하니까요.

시험 대상을 하나 더 붙이는 데 필요한 것

다음 단계에서 LangGraph로 G1(Self-Corrective RAG)을 만들면 P3로 P1과 비교하게 됩니다. 그때 할 일은 셋뿐입니다: .env에 주소 한 줄, targets.py에 ask_g1() 한 함수, call_target에 분기 한 줄. 시험지(rag_v1.json)와 러너·지표·비교는 한 글자도 안 바뀝니다. 그게 이 STEP에서 양식을 하나로 맞춘 값입니다.
